# Origin 第二版功能盘点与第三版迁移矩阵

## 1. 文档目的

本文件用于核对 Origin v2 已有能力，明确每项能力在 v3 中的去向，避免完全重构时遗漏重要功能。

它不是要求 v3 首期一次性重做全部 v2。v3 先完成独立基础库，再按依赖逐个形成运行时和 RPC 闭环。

## 2. 里程碑定义

| 里程碑 | 目标 |
|---|---|
| M0 | 工程结构、基础错误和构建信息 |
| M1 | 独立日志库 |
| M2 | 独立 Buffer 内存复用库 |
| M3 | 独立配置加载库 |
| M4 | 独立程序命令与进程控制库 |
| M5 | 独立 TCP 网络基础库 |
| M6 | 独立 NATS 基础库 |
| M7 | Application、Node、Service 最小生命周期和注册装配 |
| M8 | Node 时间轮内核和内部 Deadline |
| M9 | Service 单执行槽、Await 和 Deadline 接入 |
| M10 | Service Timer、Ticker 和 Cron 接入 |
| M11 | RPC 契约、`origingen`、顶层 Protobuf、基础类型和同 Node Dispatcher |
| M12 | Origin 普通 Go 类型静态编解码、稳定字段 ID、容器和嵌套 Protobuf |
| M13 | TCP RPC 端到端闭环 |
| M14 | NATS RPC 端到端闭环 |
| M15 | 完整排空、OnStop Await、异常恢复和进程集成 |
| M15 后 | Module、事件、发现、路由、适配器等按独立系统逐个立项 |

## 3. 迁移策略

| 策略 | 含义 |
|---|---|
| 保留 | v3 继续提供相同核心能力，外观可规范化 |
| 重构 | 保留使用场景，但重新设计实现或接口 |
| 替换 | 使用 v3 的新能力覆盖 v2 旧机制 |
| 后置 | 首期不实现，在后续里程碑补齐 |
| 待评估 | 必须用真实项目需求和维护成本判断是否迁移 |

## 4. 核心对象与生命周期

| v2 能力 | v2 参考位置 | v3 处理 | 里程碑 | 验证重点 |
|---|---|---|---|---|
| Node 作为程序启动单位 | `node/` | 保留，并新增 Application 管理多个 Node | M7 | 单进程多 Node 与单进程单 Node 行为一致 |
| Service 注册与生命周期 | `service/service.go`、`service/manager.go` | M7 用 Application 私有 `app.Setup` 显式登记 Go 类型，各 Node 按配置创建独立实例和基础状态；M15 实现 Await 排空和 OnStop，就绪门、退休后置 | M7/M15 | 类型目录不保存实例、多 Application/Node 隔离、启停、排空、无停止后回调 |
| Module 生命周期 | `service/module.go` | 保留并改为静态树，生命周期与 Service 对齐 | M15 后 | 父子启动顺序和逆序释放 |
| Node 内 Service 启停顺序 | `node/`、配置示例 | M7 保留配置显式顺序；未配置的登记类型不创建实例，停止使用实际启动顺序的严格反序 | M7 | 空配置、重复项、未知类型和严格反序校验 |
| 模板 Service | v2 Service 配置与模板逻辑 | M7 保留以模板加新服务名创建实例的方式，并复用 `app.Setup` 类型目录 | M7 | 同一模板多实例隔离、生命周期顺序和实际名称 |
| Service 多协程数量配置 | `service/service.go` 的旧并发模型 | 替换为单执行权的协作式任务调度 | M9 | 任意时刻只有一个业务任务持有 Service 执行权 |

对应设计见 [设计文档索引](../design/设计文档索引.md)。

## 5. 调度、事件、定时器与诊断

| v2 能力 | v2 参考位置 | v3 处理 | 里程碑 | 验证重点 |
|---|---|---|---|---|
| Service 顺序事件处理 | `service/` | 保留，并允许任务在框架等待点挂起后交错执行 | M9 | 顺序编程外观、无 Service 状态并发 |
| `AsyncDo` 与队列异步执行 | `concurrent/` | 重构为受控异步执行与 Service 恢复投递 | M15 后 | 队列上限、取消、过载和泄漏 |
| 本地异步事件 | `event/` | 保留 | M15 后 | `NotifyAsync` 下一任务触发 |
| 本地同步事件 | `event/` | 新增明确的 `NotifySync` | M15 后 | 同一调用栈、禁止跨 Service 并发 |
| 内部 RPC/Await Deadline | `util/timer/`、`rpc/` | M8 提供 Node 时间轮和内部一次性 Deadline，M9 接入 Await，M13/M14 接入 RPC | M8/M9/M13/M14 | 超时、取消和资源释放 |
| 业务 Timer 与 Cron | `util/timer/`、Service 定时接口 | 重构为 Node 统一时间引擎和 Service 投递 | M10 | 取消、暂停、积压、停止清理 |
| 固定步长定时器 | v2 FrameTimer 相关能力 | 暂不进入 v3 首版 | 待评估 | MMO 场景确有需求后单独设计 |
| Profiler 与队列监控 | `profiler/`、`node/` | 后置并按 v3 调度指标重做 | M15 后 | 等待数、运行时长、队列水位、超时 |

## 6. RPC

| v2 能力 | v2 参考位置 | v3 处理 | 里程碑 | 验证重点 |
|---|---|---|---|---|
| 反射注册 RPC | `rpc/handler.go` 等 | 替换为 Go 接口契约和 Origin 自有代码生成 | M11 | 生成期发现非法签名、服务端绑定正确 |
| 同步 RPC | `rpc/` | 替换为生成的 `AwaitXxx` 顺序调用外观；M11 先完成同 Node 路径，M13/M14 接入远端 | M11/M13/M14 | 默认 15 秒、取消、挂起恢复 |
| 异步 RPC | `rpc/` | 保留为生成的 `AsyncXxx`；M11 先完成同 Node回调投递，M13/M14 复用 | M11/M13/M14 | 完成结果回到调用方 Service 调度器 |
| 可取消异步 RPC | v2 `withcancel` 风格 | 使用 Context 取消规范化；是否额外公开取消句柄在 M11 继续确认 | M11/M13/M14 | 取消竞态与迟到响应 |
| 无返回通知 | v2 `Go` 风格 | 重构为生成的 `NotifyXxx`；M11 先完成同 Node 投递 | M11/M13/M14 | 只保证接受结果，不伪装业务成功 |
| Broadcast / `CastGo` | `rpc/` | 保留广播语义，由内部连接管理按实例展开投递 | M15 后 | 部分失败结果和候选快照 |
| 指定 Node、Service 调用 | `rpc/` | 保留，生成强类型客户端并由内部 RPC 管理器选连接 | M11/M13 | 不生成重复的 Node 专用方法 |
| 任意实例调用 | `rpc/` | 保留并显式路由策略 | M15 后 | RoundRobin、Rand、ModKey、自定义路由 |
| 本地 RPC 优化 | v2 本地调用路径 | M13 不做透明短路，先保持网络行为一致 | M15 后 | 短路前后序列化、超时和错误一致 |
| TCP RPC | `rpc/server.go`、`rpc/client.go` 等 | M5 已完成独立 TCP 库，M13 接入静态目标、pending、错误语义和逻辑目标有效期间的有界退避重连；后续服务发现驱动同一目标存在状态 | M5 已完成；M13 | 真实网络、短写、断线、重连、背压、包大小限制 |
| NATS RPC | `rpc/nats*.go` | M6 已完成独立 NATS 发布订阅库；M14 沿用 v2 Node 级稳定请求/响应 Subject，ServiceName 与 RequestID 由统一 RPC Runtime 处理 | M6 已完成；M14 | 与 TCP 调用语义一致 |
| 外部 gRPC 接入 | v2 无 | 新增为外部协议适配插件，不作为内部核心协议 | M15 后 | 跨语言、鉴权、错误映射 |
| Protobuf/JSON/Raw 处理 | `rpc/processor*.go`、`network/processor*.go` | 顶层 Protobuf 与 `[]byte` 进入 M11；JSON 不作为隐式回退，显式 JSON 适配按用途后置 | M11/M15 后 | 分配、兼容、边界类型 |
| 普通 Go 类型和结构体 | v2 反射调用 | M12 重构为生成期布局和自有静态编码规则 | M12 | 嵌套、Map、指针、Protobuf 字段 |
| 最大包限制与压缩 | `rpc/compress.go`、配置 | 最大包限制进入 M5/M13，首版配置默认 `4M`；首版不实现压缩，只在线协议预留标志位和算法编号 | M5/M13；压缩在基准证明有收益后再立项 | 分配前校验包大小；收到压缩标志返回不支持；未来同时限制压缩前后大小 |
| 默认 RPC 超时 | v2 默认 15 秒 | 保留 15 秒，可按调用覆盖 | M8/M9/M13 | 未显式超时时仍可退出 |

## 7. 服务发现与配置

| v2 能力 | v2 参考位置 | v3 处理 | 里程碑 | 验证重点 |
|---|---|---|---|---|
| 内置服务发现 | `cluster/origin_discovery.go` | 保留，不依赖外部中间件；显式配置唯一内置 `DiscoveryService`，不再使用 Master 角色或 `IsMaster`；高可用场景使用 etcd | M15 后 | 注册、更新、TTL、发现服务恢复、失去发现、退休状态 |

| 静态配置发现 | 未配置动态 Discovery 时读取完整 Node 清单 | v3 首版不保留独立 `static` Provider，测试静态目标由网络/RPC 测试夹具承担 | 不进入 | 避免静态清单掩盖动态发现和失效问题 |
| TTL 与失效处理 | `cluster/ttl.go` | 保留并统一到发现状态机 | M15 后 | 时钟漂移和假死实例清理 |

| 正则发现筛选 | v2 `AllowDiscovery` | 替换为契约、Node 名、Service 名和多值标签规则 | M15 后 | 先筛选后建连、规则可组合 |

| 读取字段或解析结构体 | v2 Service 配置接口 | 保留 Service 局部读取和完整解析，并增加根配置 `GetConfig` | M15 后 | Module 可通过 Service 获取任意已定义配置 |

## 11. 新里程碑的兼容边界

M0～M6 只建立独立基础库，不承诺 v2 框架运行行为或源码级兼容：

1. M0 不包含 Application、Node、Service、RPC 或网络。
2. M1～M6 的日志、内存、配置、命令、TCP 和 NATS 可以独立测试，不依赖框架 Runtime。
3. M7～M15 逐步形成 Application、时间轮、调度器、业务 Timer、代码生成、静态编解码、TCP/NATS RPC
   和完整停止闭环。
4. 同进程多 Node 在 M13 后仍通过真实 RPC 传输边界交互，不引入只在开发环境成立的隐式行为。
5. Module、发现、退休、事件、复杂路由、etcd、外部 gRPC 和 v2 系统 Module 均在 M15 后
   独立立项。
6. 接口命名可以规范化，但尽量维持 v2 用户熟悉的调用结构。
7. 每补齐一个能力，都必须同时补兼容说明、测试和性能基线。

## 12. 盘点结论

v2 的能力面明显大于 v3 前期基础库。最稳妥的行动顺序是：

1. M0～M6 分别完成工程、日志、内存、配置、命令、TCP 和 NATS 独立库。
2. M7～M15 逐步完成运行时、时间轮、调度、业务 Timer、RPC 和优雅停止，不再用一个大
   里程碑同时实现。
3. M15 后按独立系统补齐 Module、发现、退休、事件、路由、etcd、外部 gRPC 和适配器。

这样既不会丢失 v2 功能视野，也不会让单个里程碑因跨系统依赖过多而失去可验收性。
