# Origin 第二版功能盘点与第三版迁移矩阵

## 1. 文档目的

本文件用于核对 Origin v2 已有能力，明确每项能力在 v3 中的去向，避免完全重构时遗漏重要功能。

它不是要求 v3 首期一次性重做全部 v2。v3 先完成独立基础库，再按依赖逐个形成运行时和 RPC 闭环。

## 3. 迁移策略

| 策略 | 含义 |
|---|---|
| 保留 | v3 继续提供相同核心能力，外观可规范化 |
| 重构 | 保留使用场景，但重新设计实现或接口 |
| 替换 | 使用 v3 的新能力覆盖 v2 旧机制 |
| 后置 | 首期不实现，在后续里程碑补齐 |
| 待评估 | 必须用真实项目需求和维护成本判断是否迁移 |

## 6. RPC

| v2 能力 | v2 参考位置 | v3 处理 | 里程碑 | 验证重点 |
|---|---|---|---|---|
| 反射注册 RPC | `rpc/handler.go` 等 | 替换为 Go 接口契约和 Origin 自有代码生成 | M11 | 生成期发现非法签名、服务端绑定正确 |
| 同步 RPC | `rpc/` | 替换为生成的 `AwaitXxx` 顺序调用外观；M11 先完成同 Node 路径，M13/M15 接入远端 | M11/M13/M15 | 与通用 Await 共用 `scheduler.default_await_timeout`，最终兜底 15 秒；显式 Context 可覆盖 |
| 异步 RPC | `rpc/` | 保留为生成的 `AsyncXxx`；立即提交失败直接返回 error，接受后最终结果通过回调；M11 先完成同 Node回调投递，M13/M15 复用 | M11/M13/M15 | 返回 nil 后完成结果严格一次回到调用方 Service 调度器 |
| 可取消异步 RPC | v2 `withcancel` 风格 | 使用 `context.WithCancel` 规范化，不额外公开取消句柄 | M11/M13/M15 | 取消竞态与迟到响应 |
| 无返回通知 | v2 `Go` 风格 | 重构为生成的 `NotifyXxx`；带返回值 RPC 也可显式 Notify 并放弃远端结果；M11 先完成同 Node 投递 | M11/M13/M15 | 所有 Notify 返回本地接受 error，不伪装业务成功 |
| Broadcast / `CastGo` | `rpc/` | M20 按客户端 Target 的 ServiceName/Node 基础范围展开；默认排除 Retired，`IncludeRetired()` 显式纳入；编码一次并放弃远端结果 | M20 | 不可变计划、按 Node 投递、断开即时失败、2010/2011 聚合和容量边界 |
| 指定 Node、Service 调用 | `rpc/` | 保留，生成强类型客户端并由内部 RPC 管理器选连接 | M11/M13 | 不生成重复的 Node 专用方法 |
| 任意实例调用 | `rpc/` | M19 保留并重构为可长期绑定的强类型客户端；`BindXxxRPC` 使用契约默认 ServiceName，模板改名用 `BindXxxRPCTo`，精确 Node 用 `OnNode`；自动候选默认合并本地/远端 Running 实例并排除已知断开 Transport；M20 的 `IncludeRetired()` 可显式纳入 Retired；Await 可在选择前等待 Connected，编码前只选择一次 | M19/M20 | RoundRobin、Random、稳定 Key、自定义 Selector、Retired 默认摘流与显式纳入、会话固定和零堆分配 |
| 本地 RPC 优化 | v2 本地调用路径 | M13 不做透明短路，先保持网络行为一致 | v3.0 后性能提案 | 短路前后序列化、超时和错误一致 |
| TCP RPC | `rpc/server.go`、`rpc/client.go` 等 | M5 独立 TCP 库和 M13 真实远程闭环均已完成；M13 已接入显式目标、pending、错误语义、心跳和逻辑目标有效期间的有界退避重连，后续服务发现驱动同一目标存在状态 | M5/M13 已完成 | 真实网络、短写、断线、重连、背压、包大小限制 |
| NATS RPC | `rpc/nats*.go` | M6 已完成独立 NATS 发布订阅库；M15 沿用 v2 Node 级稳定请求/响应 Subject，ServiceName 与 RequestID 由统一 RPC Runtime 处理 | M6 已完成；M15 | 与 TCP 调用语义一致 |
| 外部 gRPC 接入 | v2 无 | 新增为外部协议适配插件，不作为内部核心协议 | v3.0 后组件提案 | 跨语言、鉴权、错误映射 |
| Protobuf/JSON/Raw 处理 | `rpc/processor*.go`、`network/processor*.go` | 顶层 Protobuf 与 `[]byte` 进入 M11；JSON 不作为隐式回退，显式 JSON 适配按用途后置 | M11；JSON 为 v3.0 后组件 | 分配、兼容、边界类型 |
| 普通 Go 类型和结构体 | v2 反射调用 | M11 已重构为生成期布局和自有静态编码规则；M12 只增加显式自定义静态 Codec | M11/M12 | 嵌套、Map、指针、Protobuf 字段和特殊类型 |
| 最大包限制与压缩 | `rpc/compress.go`、配置 | 最大包限制进入 M5/M13，首版配置默认 `4M`；首版不实现压缩，也不预留压缩字段 | M5/M13；压缩在基准证明有收益后以新协议 Magic 立项 | 分配前校验包大小；未来同时限制压缩前后大小 |
| 默认 RPC 超时 | v2 默认 15 秒 | 与通用 Await 共用 `scheduler.default_await_timeout`，最终兜底 15 秒；调用方显式 Context 可覆盖 | M8/M9/M11/M13 | 未显式超时时仍可退出且不重复登记计时器 |

## 11. 新里程碑的兼容边界

M0～M6 只建立独立基础库，不承诺 v2 框架运行行为或源码级兼容：

1. M0 不包含 Application、Node、Service、RPC 或网络。
2. M1～M6 的日志、内存、配置、命令、TCP 和 NATS 可以独立测试，不依赖框架 Runtime。
3. M7～M16 逐步形成 Application、时间轮、调度器、业务 Timer、代码生成、静态编解码、服务发现、TCP/NATS RPC
   和完整停止闭环。
4. 同进程多 Node 在 M13 后仍通过真实 RPC 传输边界交互，不引入只在开发环境成立的隐式行为。
5. 发现 Provider 已在 M17/M18 实现，单目标路由在 M19 实现，多节点 Broadcast 在 M20
   收口；Module、退休 API、Service 配置和本地事件只进入 M21 工作包，M22 只做 v3.0
   稳定发布，外部 gRPC 与 v2 系统 Module 使用发布后组件工作包。
6. 接口命名可以规范化，但尽量维持 v2 用户熟悉的调用结构。
7. 每补齐一个能力，都必须同时补兼容说明、测试和性能基线。

## 12. 盘点结论

v2 的能力面明显大于 v3 前期基础库。最稳妥的行动顺序是：

1. M0～M6 分别完成工程、日志、内存、配置、命令、TCP 和 NATS 独立库。
2. M7～M16 逐步完成运行时、时间轮、调度、业务 Timer、服务发现、RPC 和优雅停止，不再用一个大
   里程碑同时实现。
3. M17/M18 已补齐公共、Origin 与 etcd 服务发现，M19 补齐单目标路由，M20 设计多节点
   Broadcast；M21 收口运行时扩展，M22 完成 v3.0 发布，之后不再增加 M23。

这样既不会丢失 v2 功能视野，也不会让单个里程碑因跨系统依赖过多而失去可验收性。
