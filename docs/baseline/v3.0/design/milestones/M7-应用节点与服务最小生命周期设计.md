# Origin 第三版 M7 应用、节点与服务最小生命周期设计

> 文档状态：已实现并通过 Windows/Linux 验收
> 创建日期：2026-07-26
> 最后更新：2026-08-01
> 适用里程碑：M7
> 前置里程碑：M0～M6

## 1. 目标

M7 建立第一个可以实际运行的 Origin 框架生命周期闭环：

1. 一个 Application 可以管理并顺序启动一个或多个 Node；
2. Application 内部执行程序命令、加载配置，并按启动命令选择一个或多个 Node；
3. 使用接近 v2 的 `app.Setup` 安装 Service 类型模板，每个 Node 创建并持有独立实例；
4. Node 配置中的 Service 声明顺序就是初始化和启动顺序，停止使用严格反序；
5. Application、Node 和 Service 都有明确、线程安全且可测试的状态；
6. 任一启动步骤失败时，已经进入生命周期的对象按严格反序回滚；
7. Application 内部接入 M4 `command.Runner`，直到收到停止 Context 并完成关闭；
8. 单进程多 Node 和单进程单 Node 使用完全相同的装配与生命周期路径；
9. Application 创建一个内部 BufferPool，供后续 Node 网络与 RPC 组件共享。

M7 只建立最小生命周期，不提前实现调度、RPC、服务发现和完整优雅停止。

## 2. v2 实现复核

v2 的主要外观是：

```go
node.Setup(
    &GatewayService{},
    &PlayerService{},
)
node.Start()
```

Node 配置中的 `ServiceList` 决定实际启用的 Service 及顺序。初始化流程大致为：

1. `node.Setup` 把 Service 实例放入包级 `preSetupService`；
2. Node 根据 `ServiceList` 查找对应实例；
3. 所有实例放入包级 Service Map 和有序 Slice；
4. 按顺序调用全部 `OnInit`；
5. 按顺序调用全部 `OnStart`；
6. 停止时按 Slice 严格反序调用 `Stop`。

该外观容易理解，Service 顺序也很直观，因此 v3 保留以下经验：

- Node 下直接列出实际启用的 Service；
- 配置顺序就是启动顺序；
- 停止顺序默认且固定为实际启动顺序的严格反序；
- 未配置到当前 Node 的登记类型不会创建实例；
- 允许一个可执行程序注册多个不同 Node 可能使用的 Service。

v2 的实现不能直接复用，原因如下：

1. Node ID、Service 注册表、Service 实例、停止信号和运行状态均为包级全局变量；
2. `Setup` 注册的是可变实例，同一个实例不能分别属于两个 Node；
3. Service 名称依赖运行时反射和可变 `SetName`；
4. 重复或未知 Service 的部分路径直接 `os.Exit` 或 `log.Fatal`，无法测试和回滚；
5. `OnStart` 不返回错误，启动失败不能形成完整回滚；
6. `OnStop` 与 `OnRelease` 语义不完整，部分初始化资源的所有权不清楚；
7. 生命周期、RPC、Timer、事件和 Module 初始化紧密耦合，无法先建立最小闭环。

M7 因此只保留使用习惯，不复用 v2 的全局可变实例和生命周期代码。

- Node 实例；
- Service 基础对象与生命周期接口；

- 普通 Service 实例装配；
- 模板 Service 实例装配；

## 4. 包与依赖边界

M7 将职责拆分为三个公共包：

```text
github.com/duanhf2012/origin/v3/application
github.com/duanhf2012/origin/v3/node
github.com/duanhf2012/origin/v3/service
```

主要类型归属：

```text
application.Application
application.Options
node.Node
node.Config
service.Service
service.IService
```

依赖方向固定为：

```text
application → node → service
application ─────────→ service
application、node、service → log
```

- `service` 不导入 `node` 或 `application`；
- `node` 只依赖 `service`；
- `application` 负责 Node 集合、Service 类型目录和顶层生命周期；
- 三个包不能反向导入，因此不会形成循环依赖；
- Service 查询所属 Node 的能力通过 `service` 包定义的最小运行时接口注入；
- Node 绑定 Service 时只调用 `service` 提供的一个窄装配入口，不把 Application 传入
  Service。

拆包会多两个 import，但职责和源码目录更清楚，不需要引入 Manager、Adapter 或深层
`internal` 转发包。后续如果某项能力导致循环依赖，必须先收窄接口，不能让三个包互相
引用。

跨包绑定只保留一个框架装配边界：

```go
// package service
type Runtime interface {
    NodeID() string
    ServiceName() string
    State() State
    Logger() log.Logger
    LookupLocalService(name string) (IService, bool)
}

func BindRuntime(target IService, runtime Runtime) error
```

`node` 实现 Runtime，并在实例装配时调用一次 `service.BindRuntime`。`service.Service`
只持有该最小接口，不导入 `node`；重复绑定会失败。该函数虽然因跨包调用必须导出，但属于
框架装配 API，业务代码不应直接调用。M7 不为拆包再增加第二套 Owner、Manager 或 Adapter。

独立基础库仍保持现状：

- `config` 负责目录加载，Application 只在内部持有合并后的只读配置；
- `command` 负责命令和进程控制，由 Application 的公开 `Start()` 统一驱动；
- `log` 负责日志；Application 创建并关闭 Runtime，Node 和 Service 只持有派生 Logger；
- `internal/bufferpool`、`internal/tcpnet`、`internal/natsnet` 保持内部基础设施边界。

M7 不增加第三方依赖，只使用 Go 标准库及已经完成的 `errs`、`log`、`config` 和 `command`。

## 5. 最小配置模型

### 5.1 框架配置

```go
// application 包内部配置模型，不导出给业务入口。
type runtimeConfig struct {
    BufferPool bufferPoolConfig
    Log        applicationLogConfig
    Nodes      []node.Config
}

type bufferPoolConfig struct {
    TrackUsage bool
}

```

```go
// node.Config
type Config struct {
    ID       string
    Private  bool
    Services []string
}
```

`runtimeConfig` 是框架内部配置模型，不作为 `application.New` 的参数或公共类型暴露给业务。
业务程序不再定义并传入组合后的 `ProjectConfig`。Application 在真正执行 `start` 命令时，
根据 M4 已经校验的 `--config` 目录调用 M3，自行加载完整配置根，再从中严格解析当前已经
实现的框架字段。

完整配置根只由当前 Application 实例持有，不进入包级全局状态，也不向业务返回可变
`map[string]any`。M7 只消费 `log`、`buffer_pool` 和 `nodes`；其他业务顶层字段作为
后续 `Service.GetConfig` 的数据保留，但 M7 尚不提供业务读取接口。RPC、Discovery、Timer
等框架保留字段只有在对应里程碑实现后才允许出现。

由于业务可以定义任意顶层名称，在不再传入 `ProjectConfig` 后，框架无法把所有未知顶层
名称都判定为拼写错误。规则调整为：

- `log`、`buffer_pool`、`nodes` 等框架已知区域内部继续严格拒绝未知字段；
- 已经约定为框架保留名称但尚未实现的区域继续报“能力尚未实现”；
- 其他顶层名称按业务配置保留，不由 M7 猜测其结构；
- Service 后续把某一路径解码到业务结构体时，目标结构体内部仍严格拒绝未知字段。

这样既不要求业务把完整配置类型传给 Application，也不会用宽松解码掩盖框架配置区域中的
拼写错误。

`buffer_pool.track_usage` 默认 `false`。Application 根据它创建一个内部
`bufferpool.Pool`，全部 Node 后续通过内部所有权引用共享该实例。M7 尚未接入网络和 RPC，
因此只完成创建、归属和统计配置，不让业务代码直接取得 BufferPool，也不为了“提前使用”
制造无意义的 Buffer 申请。

生命周期超时不增加配置区域，由可选的 `application.Options` 控制。两个字段省略或为零均
表示不设置 Deadline、一直等待；正数启用对应阶段上限，负数非法。M4 的外部
`stop --timeout` 只限制控制命令等待时间，不会中止 Application 内部仍在进行的无限或
长时间优雅关闭。

### 5.2 Node 选择和顺序

配置中不增加 `application`、`start_order` 或 `stop_order`：

- 命令行指定 `--node gateway-1,game-1` 时，严格按参数顺序启动；
- 未指定 `--node` 时，按顶层 `nodes` 声明顺序启动全部 Node；
- Stop 和启动失败回滚使用本次实际成功启动顺序的严格反序；
- 未选择的 Node 不创建、不初始化，也不进入停止列表。

### 5.3 Service 声明

普通 Service：

```yaml
nodes:
  - id: game-1
    services:
      - PlayerService
      - SceneManagerService
```

M7 支持普通、模板、私有和私有模板 Service：

```yaml
nodes:
  - id: game-1
    services:
      - PlayerService
      - scene-1001:SceneService
      - scene-1002:SceneService
      - _DebugService
      - _scene-debug:SceneService
```

解析结果：

| 配置值 | 实际 ServiceName | 类型模板名 | Private |
|---|---|---|---|
| `PlayerService` | `PlayerService` | `PlayerService` | false |
| `scene-1001:SceneService` | `scene-1001` | `SceneService` | false |
| `_DebugService` | `DebugService` | `DebugService` | true |
| `_scene-debug:SceneService` | `scene-debug` | `SceneService` | true |

解析只在装配阶段执行一次并保存为 `Name + Template + Private`。普通 Service 的模板名与
实际名称相同；模板实例通过 `Template` 查找 `app.Setup` 登记的类型，但运行身份始终使用
实际 `ServiceName`。M7 只保存 Private 元数据，不执行服务发现发布。

### 5.4 配置校验

加载任何 Node 前，必须完成全部静态校验：

- `nodes` 为空；
- Node ID 为空或重复；
- 启动选择包含空、重复或未知 Node ID；
- Node 的 `services` 为空；
- Service 配置为空、单独为 `_`、包含多个 `:` 或冒号任一侧为空；
- 去除一个私有前缀后实际 ServiceName 为空；
- 同一 Node 内规范化后的实际 ServiceName 重复；
- 选中 Node 在启动前仍缺少对应的 Application Service 类型模板。

未被本次选择的 Node 也应做基本结构校验，但只要求选中 Node 的 Service 类型已经登记。
这样同一配置目录可以包含当前可执行程序不会启动的其他项目 Node，而当前二进制无需注册其
业务实现。

### 5.5 配置所有权

Application 只在内部保存一次加载形成的不可变配置根，并另外保存当前里程碑实际使用的
强类型框架配置。所有 Node 都引用同一份只读配置所有者，不重复读取目录。

业务入口不会看到以下对象：

- Application 内部框架配置对象；
- M3 的解析节点；
- 合并后的原始 Map；
- Node 选择参数的可变 Slice。

后续 Service 配置访问只能通过 `GetConfig`、`GetServiceConfig` 和
`ParseServiceConfig` 解码到调用方目标，不得把内部配置树暴露出去。

## 6. Application 安装 Service 类型模板

### 6.1 API 外观

M7 保留接近 v2 的一次性预安装外观：

```go
func (app *Application) Setup(
    services ...service.IService,
)
```

程序创建 Application 后、运行前安装当前可执行程序支持的 Service 类型：

```go
app.Setup(
    &GatewayService{},
    &PlayerService{},
    &DBService{},
)
```

这里传入的对象是“类型样本”，只用于识别、校验和登记 Go 具体类型。Origin 不保存该可变
对象，也不会把它作为任何 Node 的运行实例。

`Setup` 不返回 error，目的是允许它与 v2 一样直接用于业务 `func init()`。登记过程中发现
的 nil、非法类型或名称冲突会累积到当前 Application 实例；只有真正执行 `start` 命令时才
统一返回，并保证在加载 Node 或调用任何业务生命周期前失败。`help`、`version` 和 `stop`
不需要业务 Service 类型，因此不会被安装错误阻断。

Application 按启动命令选择 Node 后，根据 Node 的 `services` 配置从自己的类型目录中查找
对应类型，并为每个实际 Service 调用一次 `reflect.New` 创建全新零值实例。

### 6.2 为什么选择 `app.Setup`

`app.Setup` 比 `node.Setup` 更适合当前模型：

- Application 已经拥有本次启动的多个 Node；
- 同一个可执行程序支持的 Service 类型集合通常对这些 Node 相同；
- 每种类型只登记一次，不需要遍历 Node 重复调用；
- Node 仍只持有根据自身配置创建的运行实例；
- 两个 Application 可以登记不同类型集合，测试和嵌入场景互不污染；
- 不需要包级全局模板目录，也不违反无可变全局状态原则。

如果由 `node.Setup` 安装，Application 必须先公开尚未启动的 Node，业务还要循环调用，既
增加外观代码，也把“可执行程序支持哪些类型”的职责重复下放给每个 Node。

### 6.3 为什么不保存传入实例

如果 Application 直接保存 `&PlayerService{}` 并把同一指针交给多个 Node，会导致：

- Service 状态、Module、Timer、RPC 和停止状态被多个 Node 共享；
- 一个 Node 停止时可能破坏另一个 Node；
- 单进程多 Node 测试与生产单 Node 行为不同；
- 同一 Node 无法从一个模板创建多个实际实例。

因此 v3 只复用 v2 的使用外观，不复用“共享可变运行实例”的实现。

### 6.4 类型和名称规则

```go
&PlayerService{} // 登记名称为 PlayerService
```

规则如下：

- 必须传入指向已命名结构体的非 nil 指针；
- 结构体必须嵌入 `service.Service` 并实现 `service.IService`；
- 类型样本必须是零值，禁止在样本字段中注入运行状态或依赖，因为样本本身不会被使用；
- 名称取具体结构体类型名，区分大小写；
- 普通 Service 使用实际名称查找类型，模板 Service 使用冒号右侧模板名查找类型；
- 不提供 `SetName` 修改普通 Service 名称；
- 同一个名称不能对应两个不同的 Go 类型；
- 重复登记同一个具体类型采用幂等成功，方便不同装配函数安全复用；
- 配置声明但未登记的 Service 在任何生命周期开始前统一报错；
- 已登记但未被选中 Node 使用的类型不会创建实例；
- Origin 框架包不提供隐式默认目录；只有最终可执行程序可以在 `init()` 中对自己明确持有的
  `app` 实例调用 `Setup`；
- `Setup` 只允许在 Application 的 `Created` 状态调用；开始执行命令后再调用会记录为启动
  错误，不能修改已经冻结的类型目录。

反射只用于低频启动路径：

1. `Setup` 时读取并校验具体类型；
2. Node 装配时为配置选中的 Service 创建零值指针。

反射不会进入 Service 事件、Timer 或 RPC 热路径。

### 6.5 Application 状态边界

类型目录由 Application 实例持有，只保存经过校验的 `reflect.Type`，不保存：

- Service 运行实例；
- Node 或配置反向引用；
- Context、Logger、Timer、RPC Client；
- 生命周期状态；
- 业务字段。

Application 开始启动时冻结目录，运行期只读，不在 Service 查询热路径加锁。创建新的
Application 即得到新的空目录，不需要公开 Reset，也不会让测试之间共享登记结果。

### 6.6 多 Node 与模板实例隔离

同一个类型模板可以供多个 Node 使用，但每个 Node 得到不同实例：

```text
Application / PlayerService 类型
├── gateway-1 / *PlayerService
└── game-1    / *PlayerService
```

两个实例只共享 Go 类型，不共享任何可变字段。单 Node 生产部署和多 Node 开发部署使用同一
条实例创建路径。

同一个 Node 中以下配置也会创建两个独立实例：

```yaml
services:
  - scene-1001:SceneService
  - scene-1002:SceneService
```

两个实例的实际名称分别为 `scene-1001` 和 `scene-1002`，类型模板名均为
`SceneService`。启动和停止顺序仍以配置顺序为准。

### 6.7 安装代码的工程组织

业务可以像 v2 一样，把安装代码拆到一个或多个 `init_*.go` 文件，并在 Go `func init()`
中对当前可执行程序明确持有的 Application 实例调用 `Setup`：

```go
// init_services.go
func init() {
    app.Setup(
        &GatewayService{},
        &PlayerService{},
        &DBService{},
        &SceneService{},
    )
}
```

Application 在包初始化阶段只创建空的实例，不读取配置、不创建 Node，也不启动 goroutine：

```go
// app.go
package main

var app = application.New()
```

main 最终只有一个入口：

```go
func main() {
    app.Start()
}
```

这是一项只允许出现在最终可执行程序 `main` 包中的受限例外：

- Origin 框架包仍禁止通过 `init()` 修改包级注册表；
- `app` 是业务程序明确持有的唯一实例，不是 Origin 隐藏的默认单例；
- `init()` 只能登记类型，不得读取配置、创建 Service 实例或启动 goroutine；
- 类型登记顺序不决定生命周期顺序，实际 Init/Start 顺序始终来自 Node 配置；
- 多个 `init_*.go` 可以分别登记独立系统，重复登记同一类型仍然幂等；
- 测试直接调用 `application.New()` 创建私有实例，不复用最终可执行程序的 `app`。

### 6.8 是否增加 `SetupTemplate`

M7 建议不增加 `app.SetupTemplate`。v2 需要区分两个接口，是因为普通 `Setup` 保存运行实例，
模板安装保存构造函数；v3 的 `app.Setup` 对两者都只保存 Go 类型，因此创建机制已经统一。

```go
app.Setup(
    &PlayerService{}, // 可用于普通 PlayerService
    &SceneService{},  // 可创建 scene-1001、scene-1002 等模板实例
)
```

配置是否包含冒号决定实际实例名称和是否属于模板实例，不改变类型的登记方式。单独增加
`SetupTemplate` 只会形成两个功能相同的入口，并带来“同一类型能否同时普通安装和模板安装”
等额外规则。

## 7. Service 基类与生命周期

### 7.1 基础外观

为尽量保持 v2 用户习惯，业务 Service 继续嵌入 `service.Service`：

```go
type PlayerService struct {
    service.Service
}
```

生命周期接口建议为：

```go
// package service
type IService interface {
    OnInit() error
    OnStart(ctx context.Context) error
    OnStop(ctx context.Context) error

    // 内部所有权方法由嵌入的 service.Service 提供，
    // 业务实现不直接调用。
    baseService() *Service
}
```

`service.Service` 为三个生命周期方法提供空实现，因此业务只需覆盖实际需要的钩子：

```go
func (s *PlayerService) OnInit() error {
    return nil
}

func (s *PlayerService) OnStart(ctx context.Context) error {
    return nil
}

func (s *PlayerService) OnStop(ctx context.Context) error {
    return nil
}
```

`OnStart` 和 `OnStop` 使用 `context.Context`，使 M7 已经具有取消边界，并保证 M9 接入
普通 Task Await、M14 接入 OnStart 生命周期 Await、M16 接入 OnStop 独占 Await 和完整
优雅停止时不修改业务接口。

### 7.2 基础查询

`service.Service` 提供只读查询：

```go
func (s *Service) Name() string
func (s *Service) NodeID() string
func (s *Service) State() State
func (s *Service) Logger() log.Logger
func (s *Service) LookupLocalService(name string) (IService, bool)
```

`LookupLocalService` 只查询所属 Node 的本地 Service。它不跨 Node，不调用 RPC，也不表示业务
方法可以绕过后续 Service 调度器并发执行。

M7 不提供：

- `SetName`；
- `SetNodeID`；
- 返回可变 Service Map；
- 包级 `GetService`；
- 通过模板名称查找多个实际实例；
- 运行时新增或删除 Service。

### 7.3 `OnInit`

所有 Service 实例都创建、绑定并加入当前 Node 的只读注册表后，才按配置顺序调用
`OnInit`。

`OnInit` 用于：

- 读取已经绑定的 ServiceName 和 NodeID；
- 检查本地 Service 是否存在；
- 校验静态业务字段；
- 建立后续 Module 树所需的纯内存结构。

M7 约束 `OnInit` 不应：

- 启动 goroutine；
- 打开网络监听；
- 建立数据库或远端连接；
- 启动 Timer；
- 执行需要在 `OnStop` 清理的外部资源操作。

外部资源应在 `OnStart` 获取。这样 `OnInit` 失败时可以直接放弃尚未启动的对象，不需要为了
纯配置阶段增加第四个清理钩子。

### 7.4 `OnStart`

全部 Service 的 `OnInit` 成功后，Node 按配置顺序调用 `OnStart(ctx)`。

- 调用前状态切换为 `Starting`；
- 返回 nil 后状态切换为 `Running`；
- 返回错误或 panic 时状态切换为 `Failed`；
- Node 不再启动后续 Service；
- 失败 Service 和此前已经进入 `OnStart` 的 Service 按反序执行 `OnStop`；
- `OnStart` 已经被调用的 Service 一定会获得一次对应的 `OnStop`，即使 `OnStart`
  返回错误。

最后一条保证业务可以把部分启动资源统一放在 `OnStop` 清理。业务的 `OnStop` 必须允许
处理“`OnStart` 只成功了一部分”的状态。

### 7.5 `OnStop`

M7 的 `OnStop(ctx)` 是最小直接生命周期回调：

- 当前没有业务 Runner、Ready、Waiting、RPC、Timer 或异步任务需要排空；
- Node 按 `OnStart` 实际进入顺序的严格反序逐个调用；
- 一个 Service 的错误或 panic 被记录并汇总，但不阻止后续 Service 停止；
- 每个进入过 `OnStart` 的 Service 最多调用一次；
- `OnStop` 返回后该实例不再重新启动或绑定给其他 Node。

M16 在相同接口上增加停止准入、任务排空、独占 finalizer 和 `OnStop` Await，不改变 M7
已经确定的业务方法签名。

## 8. 实例所有权

每次解析选中 Node 的 Service 声明时：

1. 普通 Service 使用规范化后的 ServiceName、模板 Service 使用 TemplateName 查找
   Application 私有类型目录；
2. 使用登记的结构体类型创建一个全新指针；
3. 检查新实例嵌入有效的 `service.Service`；
4. 一次性写入 Application、Node、实际 ServiceName、登记类型名和 Private 元数据；
5. 加入当前 Node 的有序 Slice 和按实际 ServiceName 查询的 Map。

不同 Node 即使使用同一个登记类型，也会分别创建实例。实例一旦绑定，即使启动失败或停止
完成，也不能再次绑定到另一个 Node。

Application 不向业务暴露修改 Node 所有权的方法。Node 不把内部 Service Map 暴露为可变
引用。

## 9. 状态模型

### 9.1 Application 状态

```go
// package application
type State uint8

const (
    StateCreated State = iota
    StateStarting
    StateRunning
    StateStopping
    StateStopped
    StateFailed
)
```

### 9.2 Node 状态

```go
// package node
type State uint8

const (
    StateCreated State = iota
    StateStarting
    StateReady
    StateStopping
    StateStopped
    StateFailed
)
```

### 9.3 Service 状态

```go
// package service
type State uint8

const (
    StateCreated State = iota
    StateInitializing
    StateInitialized
    StateStarting
    StateRunning
    StateStopping
    StateStopped
    StateFailed
)
```

M7 不加入 `Retired`。退休属于后续独立系统，但未来可以在 `Running` 与 `Stopping` 之间
增加稳定状态，不改变现有数值名称以外的 API。

### 9.4 状态规则

- 状态使用原子值提供无锁只读快照；
- 生命周期转换只由对象自己的单一控制路径执行；
- 不允许并发执行两套 Start 或 Stop；
- `Start` 和 `Stop` 的兼容状态在取得生命周期锁后检查；
- 状态不是分布式健康结果，只表示当前进程内对象生命周期；
- 回调期间不能持有 Application、Node 或 Service 注册表锁。

首版 Application 和 Node 都是一次性对象：

- `Created` 可以启动；
- 正常停止后进入 `Stopped`，不能再次启动；
- 启动失败并完成回滚后进入 `Failed`，不能原地重试；
- 重启通过创建新的 Application 实例完成。

这样可以避免需要重建 Channel、Context、Service 实例和外部资源的复杂复用语义。

## 10. Application 装配

公开构造外观：

```go
type Options struct {
    StartTimeout     time.Duration
    StopTimeout      time.Duration
    LogHandlerFactory func(log.Config) (log.Handler, error)
}

func New(options ...Options) *Application
```

绝大多数项目直接使用：

```go
var app = application.New()
```

只有需要由代码覆盖生命周期超时时才传入一份 Options：

```go
var app = application.New(application.Options{
    StartTimeout: 10 * time.Minute,
    StopTimeout:  3 * time.Minute,
})
```

`options` 只允许省略或传一份。采用可选的单个 Options，是为了同时保留最简
`application.New()` 外观和测试、嵌入场景的显式覆盖能力，不建立多组函数式 Option。

`LogHandlerFactory` 为 nil 时使用 Origin 内置 Zap Handler；自定义日志库通过该实例级
Factory 接入。Factory 只在真正执行 `start` 且日志配置已经加载后调用一次，返回的 Handler
随即由 Application 创建的日志 Runtime 接管并在最后关闭。`help`、`version`、`stop` 不会
创建 Handler。

默认值：

| 字段 | 默认值 | 说明 |
|---|---:|---|
| `StartTimeout` | `0` | 不设置启动 Deadline，一直等待 |
| `StopTimeout` | `0` | 不设置停止 Deadline，一直等待 |

超时规则：

- Options 中的零值表示一直等待；
- 允许设置任意大于零的 Duration，不设置人为最大值；
- 负数无效，并在执行 `start` 命令、创建任何运行资源前报错；
- 查询大数据库等启动场景可以设置 `5m`、`10m` 或更长；
- Start 和 Stop 分别配置，不能因为启动较慢就自动扩大停止时间；
- M4 `stop --timeout` 仍是独立的外部等待时间，部署脚本可以把它设置得比
  `StopTimeout` 更长。

构造函数只做以下工作：

- 创建 Created 状态的空 Application；
- 保存并初步校验可选 Options，错误延迟到 `start` 路径统一报告；
- 建立当前实例私有的空 Service 类型目录；
- 不读取配置；
- 不创建 BufferPool、Node 或 Service；
- 不启动 goroutine。

只有命令解析确认本次执行的是 `start` 后，Application 才加载配置、创建 BufferPool 和
Node。执行 `help`、`version`、`stop` 或自定义离线命令不会创建业务运行时资源。

## 11. 启动流程

### 11.1 Application

```go
func (app *Application) Start()
```

流程：

1. 创建 M4 `command.Runner`，并使用当前进程参数执行命令；
2. `help`、`version`、`stop` 和自定义离线命令由 Runner 直接处理；
3. 只有 `start` 才把 Runner 内部的运行 Context、配置目录和 NodeID 快照交给
   Application 私有 Start Handler；
4. 私有 Handler 从配置目录加载完整配置根，解析框架配置并冻结 Service 类型目录；
5. 根据内部收到的 NodeID 生成本次有效 Node 顺序；
6. 校验全部选中 Node 的配置 Service 均已登记类型模板；
7. 创建 Application BufferPool、全部选中 Node 和独立 Service 实例；
8. 状态切换为 `ApplicationStarting`；
9. 按有效顺序逐个启动 Node；
10. Node 进入 `NodeReady` 后加入成功启动列表；
11. 全部完成后切换为 `ApplicationRunning`；
12. 等待 Runner 的运行 Context 取消；
13. 使用独立停止 Context 完成严格反序停止；
14. 全部停止完成后私有 Handler 返回，Runner 才释放 PID 锁；
15. `Start()` 对错误只输出一次；非零退出码在所有资源已经释放后结束进程。

先完成全部选中 Node 的实例装配和缺失检查，再启动第一个 Node，可以让类型模板和配置错误
在任何 `OnInit` 前暴露。

`Start` 是无参数、阻塞式的完整程序入口，与 v2 使用习惯一致。业务不再接触
`context.Context`、配置目录、`command.StartRequest` 或 NodeID Slice。M7 不再额外公开
语义重复的 `Run` 方法。

为了同时满足正确退出码和最简 main，`Start()` 是规则中唯一允许调用 `os.Exit` 的框架
入口。它只在内部可测试执行函数已经返回、PID 锁已经释放、Node/Service/Logger 已经关闭后
按 M4 退出码结束进程；成功时正常返回。真实执行逻辑保持为不调用 `os.Exit` 的内部函数，
单元测试直接覆盖该函数，进程级集成测试覆盖公开 `Start()`。

Application 还提供 M4 自定义离线命令的实例级登记：

```go
func (app *Application) RegisterCommand(command command.Command) error
```

该方法只允许在 `Start()` 前调用，直接复用 M4 的名称、帮助和 Handler 规则；命令目录属于
当前 Application，不建立全局命令表。

### 11.2 Node

单个 Node 的启动顺序：

1. 状态从 `NodeCreated` 切换为 `NodeStarting`；
2. 按配置顺序把全部 Service 从 `Created` 推进到 `Initialized`；
3. 任一 `OnInit` 返回非 nil error 时，立即停止初始化后续 Service；当前 Node 未调用任何
   `OnStart`，Node 直接进入 `NodeFailed`，并向 Application 返回包含 NodeID、
   ServiceName 和 `OnInit` 阶段的错误链；
4. 全部初始化成功后，按相同顺序调用 `OnStart`；
5. 任一 `OnStart` 失败时，按实际进入 `OnStart` 的反序执行 `OnStop`；
6. 全部 Service 进入 `Running` 后，Node 切换为 `NodeReady`。

以上第 3 条是 M7 最小生命周期的历史实现边界。M16 已确认改为：同一 Node 的全部纯
`OnInit` 都按配置顺序执行后再聚合错误；任一失败时不进入任何 `OnStart`，也不调用业务
`OnStop`。M16 实施后以新规则为准。

M7 没有 Transport、RPC Runtime 和 Discovery 基础设施。M13/M14/M15 接入时，在
Service `OnStart` 前增加 Node 基础设施阶段，但不改变 Service 的相对顺序。

### 11.3 Application 启动失败

任一 Node 启动失败时：

1. 不再启动后续 Node；
2. 失败 Node 完成自身 Service 回滚；
3. Application 按成功启动列表严格反序停止此前 Node；
4. 汇总原始启动错误和全部回滚错误；
5. Application 最终进入 `ApplicationFailed`；
6. 私有 Start Handler 把聚合错误返回给 `app.Start()`；
7. `app.Start()` 使用 Error 级别打印一次完整错误日志，并以非零退出码结束程序。

Application 不越过 Node 边界直接清理其 Service。

因此，如果启动顺序为 `gateway-1 → game-1 → db-1`，而 `db-1` 的某个 Service
`OnInit` 返回 error，则 `db-1` 启动失败，Application 按 `game-1 → gateway-1` 停止已经
启动成功的 Node，最终整个程序启动失败，不允许只跳过 `db-1` 后继续运行。

## 12. 停止流程

```go
func (app *Application) Stop(ctx context.Context) error
```

正常停止：

1. Application 从 `Running` 切换为 `Stopping`；
2. 按实际成功启动 Node 列表严格反序逐个停止；
3. Node 按实际进入 `OnStart` 的 Service 列表严格反序逐个调用 `OnStop`；
4. 一个 Service 或 Node 停止失败不跳过其余对象；
5. 全部停止尝试结束后 Application 进入 `Stopped`；
6. 返回聚合停止错误。

M7 使用 Go 1.20 以来标准库 `errors.Join` 聚合错误，不增加自定义错误树。

重复 Stop 规则：

- `Stopped` 再次 Stop 返回 nil；
- `Failed` 且已经完成启动回滚时 Stop 返回 nil；
- `Stopping` 时后续调用等待同一停止结果；
- `Created` 时 Stop 直接进入 `Stopped`，不调用 Service；
- 与 `Starting` 并发的 Stop 取消启动 Context，并由同一生命周期控制路径完成回滚。

M7 不尝试强杀忽略 Context 的用户回调。超时后记录对应错误，但 Go 中仍不能安全回收永久
阻塞的业务 goroutine。完整诊断和进程退出策略在 M16 确认。

## 13. `Start` 与 M4 接入

`Start` 的时间边界：

1. `StartTimeout > 0` 时派生启动阶段 Context；为零时直接使用 Runner 的运行 Context；
2. 全部 Node Ready 后停止使用启动 Deadline，只等待运行 Context；
3. 运行 Context 取消后，从 `context.Background()` 创建独立停止 Context；
4. `StopTimeout > 0` 时再为停止 Context 增加 Deadline；为零时一直等待；
5. 调用内部统一停止路径并等待全部 M7 生命周期完成；
6. 私有 Start Handler 返回启动错误、运行 Context 原因或停止错误的适当组合。

停止 Context 不能直接复用已经取消的运行 Context，否则 `OnStop` 一进入就会看到取消。

最终业务入口：

```go
package main

import "github.com/duanhf2012/origin/v3/application"

var app = application.New()

func main() {
    app.Start()
}
```

Application 内部的等价关系是：

```text
app.Start()
  → command.Runner.Run(context.Background(), os.Args[1:])
  → 私有 Start Handler(ctx, request)
  → 内部 LoadDir(request.ConfigDir)
  → 内部选择 request.NodeIDs
  → 启动并等待 Application
  → Context 取消后优雅停止
  → Handler 返回后释放 PID 锁
```

M4 的外部 `stop` 默认等待 `30s`，与 Application 默认无限等待的 `StopTimeout=0` 是不同
边界。外部等待超时只让 stop 命令返回，不会强杀仍在优雅关闭的目标进程。部署环境需要
“先优雅、后强制”的上限时，应显式设置 Application `StopTimeout`，并让进程控制等待时间
略大于内部停止预算；如果坚持内部无限等待，则最终强杀策略只能由部署平台负责。

## 14. 本地查询和隔离

Application 提供只读查询：

```go
func (app *Application) State() State
func (app *Application) Node(id string) (*node.Node, bool)
func (app *Application) Nodes() []*node.Node
```

Node 提供：

```go
func (node *Node) ID() string
func (node *Node) State() State
func (node *Node) Service(name string) (service.IService, bool)
func (node *Node) Services() []service.IService
```

返回 Slice 时必须创建快照，不能暴露内部 Slice 容量。Service Map 不直接返回。

隔离规则：

- 每个 Application 拥有独立 Config 快照、Service 类型目录、Node Map 和生命周期状态；
- 每个 Node 拥有独立 Service Map、有序 Slice 和状态；
- 每个 Service 只能通过只读 owner 引用访问所属 Node；
- 两个 Application 即使使用相同 NodeID 和 ServiceName，也不能共享状态；
- 每个 Application 拥有一个独立 BufferPool；同一 Application 内的 Node 共享该实例；
- 不存在包级 Service 类型或运行实例目录、默认 Application 或当前 Node；
- 日志器可以是独立值；Logger 后端是否共享由调用方配置决定，不属于生命周期全局状态。

## 15. 并发模型

M7 不启动业务工作 goroutine。唯一可能长期阻塞的公开入口是调用方自己的 `Start`
goroutine。

生命周期并发规则：

- Application 使用一个短生命周期互斥锁保护状态转换、结果和完成 Channel；
- Node 和 Service 生命周期由 Application 的单一控制路径顺序调用；
- State 使用原子读；
- Service 类型目录和配置快照在 Start 前冻结，运行期只读；
- `Setup` 只在 Application 创建后、Start 前执行；
- 用户 `OnInit`、`OnStart`、`OnStop` 调用期间不持有框架锁；
- 并发 Stop 只提交一次停止意图，其他调用等待同一个完成结果；
- 不为每个 Service 创建空闲 goroutine；
- 不使用 Channel 模拟当前尚不存在的事件队列。

M8 先增加 Node 时间轮内核，M9 再为 Service 增加单执行槽和 Runner。M7 不提前放置空转
TimerEngine 或调度器。

## 16. panic 与错误

M7 使用已有统一错误码：

| 情况 | 错误码 |
|---|---|
| nil Context、非法 Setup 类型样本、非法状态调用 | `CodeInvalidArgument` |
| Node/Service 配置、名称冲突或缺少 Service 类型 | `CodeInvalidConfig` |
| 生命周期回调 panic | `CodeInternal` |
| 调用方 Context 取消 | `CodeCanceled` |
| 生命周期 Deadline | `CodeDeadlineExceeded` |
| 业务回调主动返回 Origin 错误 | 保留原错误码 |
| 业务回调返回普通 error | 保留 cause，由上层记录阶段上下文 |

M7 不新增 Service 专用错误码。`CodeServiceRetired`、`CodeServiceStopping`、
`CodeServiceStopped` 和 `CodeServiceQueueFull` 在后续准入与 RPC 里程碑启用。

三个生命周期钩子属于用户代码执行边界：

- 最外层执行 `recover`；
- 生成带调用阶段、NodeID、ServiceName 和堆栈的内部错误；
- 不让单个 panic 直接终止进程；
- 停止阶段 panic 不阻止剩余 Service 和 Node 清理；
- 同一钩子 panic 后不重复调用该钩子。

生命周期 error 采用“底层补上下文、顶层只打印一次”的规则：

- Service 返回的原始 error 必须通过 `%w` 或等价错误链完整保留；
- Node 增加 NodeID、ServiceName 和 `OnInit`/`OnStart`/`OnStop` 阶段，不靠修改原错误文本
  判断逻辑；
- Application 聚合原始启动错误及回滚错误，原始 `OnInit` error 必须仍可被
  `errors.Is`、`errors.As` 和 `errs.CodeOf` 识别；
- Service 和 Node 不重复打印同一个向上传递的 error；
- `app.Start()` 等全部启动回滚结束后，使用 Error 级别记录最终错误一次；
- 最终错误日志被日志 Runtime 接受并完成 Flush/Close 后，程序才使用非零退出码结束；
- 若正式 Logger 尚未成功初始化，则使用 M4 的 stderr 兜底打印，错误不能静默丢失。

## 17. 日志

M7 只记录低频生命周期日志：

- Application 开始、成功、停止和失败；
- Node 开始、Ready、停止和失败；
- Service 初始化、启动、停止状态；失败 error 由外层聚合后打印一次；
- 回滚开始、回滚错误和最终结果。

稳定字段通过 `With` 绑定：

```text
application_state
node_id
service_name
lifecycle_phase
error_code
```

正常状态读取和本地查询不写日志。生命周期 panic 使用 `ErrorStack`。日志错误不
改变生命周期主结果。

`OnInit` 返回 error 的最终日志至少包含：

```text
level=error
message="application start failed"
node_id=db-1
service_name=DBService
lifecycle_phase=on_init
error_code=<可识别时填写>
error=<原始 error 及包装上下文>
```

如果同时存在回滚错误，日志中的 `error` 保存聚合错误；主要失败字段仍指向最先导致启动
终止的 `OnInit` error，不能被后续停止错误覆盖。

## 18. 性能与内存

M7 不是消息热路径，但仍遵守项目性能规则：

1. Config 在 `start` 命令内部加载并形成一次 Application 私有快照，运行期不反复深拷贝；
2. Node 和 Service Slice 按已知配置数量一次分配容量；
3. Map 按已知数量预分配；
4. ServiceName 和 NodeID 绑定后不可变；
5. State 查询不分配并使用原子读；
6. 单个 Node 和 Service 查询不创建临时 Map；
7. `Nodes()`、`Services()` 只有显式请求快照时才分配；
8. 生命周期错误路径允许分配详细上下文，不为启动低频路径引入对象池；
9. 不池化 Application、Node 或 Service；
10. Application 类型目录只在 Setup 和启动冻结时短暂加锁；
11. 类型实例创建和生命周期回调期间不持有目录或生命周期锁。

Benchmark 至少记录：

- 100 个 Node、每个 20 个 Service 的静态校验和装配时间；
- 单 Application 顺序启停时间；
- State、Node 和 Service 查询的 `allocs/op`；
- 多个独立 Application 并行测试时的锁竞争。

M7 不设绝对纳秒门槛，先保存可复现基线。若优化会显著增加生命周期代码复杂度，按开发
原则先与开发者确认。

## 20. 测试设计

### 20.1 配置与类型目录

- 空和重复 NodeID；
- Node 选择为空、重复、未知；
- 普通、模板、私有和私有模板 Service 解析；
- 非法 `_`、多个冒号、冒号任一侧为空和规范化名称冲突；
- 空参数、nil 接口和接口内 nil 指针；
- 非零值类型样本；
- 未嵌入 `service.Service` 的类型；
- 未命名结构体和非结构体指针；
- 相同类型重复登记幂等；
- 相同名称对应不同类型；
- Application Start 后目录冻结；
- 未被选中 Node 使用的登记类型不创建实例；
- 配置声明但未登记的 Service 类型；
- 同一模板创建多个实际名称不同的独立实例。

### 20.2 生命周期顺序

- 全部 Service 先完成实例绑定，再开始第一个 `OnInit`；
- Service 按配置顺序执行 `OnInit`；
- 全部 `OnInit` 成功后才开始第一个 `OnStart`；
- Service 按配置顺序执行 `OnStart`；
- 正常 Stop 严格反序执行 `OnStop`；
- 任一 `OnInit` 失败时，失败 Node 内不执行任何 `OnStart` 或 `OnStop`；
- 任一 Node 的 `OnInit` 失败时，停止此前已经启动成功的全部 Node，程序以失败结束；
- `OnStart` 失败时包含失败 Service 在内严格反序 `OnStop`；
- `OnStop` 错误和 panic 不跳过剩余 Service；
- 每个钩子最多调用一次。

### 20.3 Application 与 Node

- 未指定 Node 时使用配置声明顺序；
- 指定多个 Node 时使用参数顺序；
- Application 只创建启动参数选中的 Node；
- Node 启动严格串行；
- Node 停止严格反序串行；
- 中间 Node 启动失败后不启动后续 Node；
- 失败 Node 自清理后，前序 Node 严格反序回滚；
- Node 停止失败不阻止其他 Node；
- `Created`、`Starting`、`Running/Ready`、`Stopping`、`Stopped/Failed` 状态正确；
- 重复和并发 Stop 只执行一次；
- Stopped/Failed 对象不能重新启动；
- Start/Stop 默认 `0` 且不创建 Deadline；
- Options 的正数超时、零值无限等待和负数错误；
- 自定义 `5m` 以上超时；
- 外部 `stop --timeout` 结束后，内部无限等待的关闭仍继续执行。

### 20.4 隔离

- 同一 Application 两个 Node 从同一类型模板创建不同实例；
- 同一 Node 的两个模板 Service 从同一类型创建不同实例；
- 两个 Application 使用相同 NodeID 和 ServiceName 仍完全隔离；
- 两个 Application 登记不同 Service 类型目录且互不影响；
- 一个 Application 启动失败不改变另一个 Application；
- BufferPool 统计开关映射、Application 间隔离和同一 Application 内共享；
- 快照 Slice 修改不影响内部顺序；
- 不存在包级 Service 类型或运行实例目录；
- 全仓 `go test -race` 无竞态。

### 20.5 M3/M4 集成

- `app.Start()` 内部把 M4 的配置目录交给 M3，业务入口不持有 `ProjectConfig`；
- `command.StartHandler` 内部传入一个或多个 Node，业务入口不接触 NodeID Slice；
- `help`、`version` 和 `stop` 不加载业务配置或创建运行资源；
- 多个 `init_*.go` 对同一 Application 登记类型，顺序不改变配置定义的 Service 启停顺序；
- 运行 Context 取消后使用独立停止 Context；
- Start 失败释放 M4 PID Lease；
- Stop 完成后 Start Handler 才返回。
- `OnInit` error 完成全局回滚后由 `app.Start()` 打印一次，并返回非零进程退出码。

## 23. 开工 Review

### 23.1 已确认

1. 拆分为 `application`、`node`、`service` 三个公共包，并保持
   `application → node → service` 单向依赖；
2. 使用 `app.Setup(&PlayerService{}, ...)` 登记当前 Application 可用的 Service 类型，
   不使用包级全局目录，也不要求逐个调用 `node.Setup`；
3. Application 只保存具体 Go 类型，每个 Node 根据配置创建全新的 Service 零值实例；
4. M7 实现普通、模板、私有和私有模板 Service；
5. 生命周期接口固定为 `OnInit() error`、`OnStart(ctx) error`、`OnStop(ctx) error`；
6. 任一 `OnInit` 失败时，失败 Node 内不调用任何 `OnStart` 或 `OnStop`；`OnStart` 一旦
   被调用，无论成功或失败都保证调用一次对应 `OnStop`；失败 Node 使 Application 停止全部
   此前已启动 Node，最终打印原始 error 并以非零退出码结束；
7. Node `services` 顺序就是 Init/Start 顺序，Stop 使用实际进入 Start 顺序的严格反序；
8. Application、Node、Service 都是一次性对象，Stopped 或 Failed 后不能原地重启；
9. 只保留无参数、阻塞式公开 `Start()`，配置目录、运行 Context 和 Node 选择全部由
   Application 内部承接 M4，不增加语义重复的 `Run`；
10. Start/Stop Timeout 默认均为 `0`，表示无限等待；允许通过 Options 设置任意大于零的
    自定义值，停止使用独立 Context；
11. Application 根据 `buffer_pool.track_usage` 创建一个内部共享 BufferPool，默认关闭
    统计，M7 不向业务公开该对象；
12. M7 暂不实现的调度、RPC、TCP/NATS 接入、完整排空、Module、Timer 和 Discovery 已按
    第 3.3 节登记到后续阶段。

13. `application.New()` 不接收项目配置；Application 仅在内部加载并持有配置，业务不再
    定义或传入 `ProjectConfig`；
14. 最终可执行程序允许在 `init_*.go` 的 `func init()` 中对明确的 Application 实例调用
    `app.Setup(...)`，但 Origin 框架自身仍禁止隐藏的全局目录和隐式注册；
15. `app.Setup(...)` 不返回 error，安装错误保存到当前 Application，并在真正执行
    `start` 且创建任何运行资源前统一报告；
16. 普通与模板 Service 统一使用 `app.Setup` 登记类型，不增加功能重复的
    `app.SetupTemplate`；
17. `app.Start()` 内部完成命令解析、配置加载、Node 选择、运行 Context 和优雅停止，业务
    main 不再传入任何参数。
18. `app.Start()` 是唯一进程级退出例外；内部执行函数仍通过 error/ExitCode 返回并可测试；
19. Application 保留 M4 自定义命令能力，通过实例级 `RegisterCommand` 转发；
20. Application 按配置创建日志 Runtime，默认使用 Zap，并允许 Options 提供实例级
    `LogHandlerFactory`。
