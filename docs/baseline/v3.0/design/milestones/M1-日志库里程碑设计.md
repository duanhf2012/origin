# Origin 第三版 M1 日志库里程碑设计

> 文档状态：已实现并通过验收
> 创建日期：2026-07-25
> 最后更新：2026-07-26

## 1. 目标

M1 在 M0 工程基础之上实现一套可以独立创建、使用、刷新和关闭的日志库，为后续 Application、Node、Service、网络、调度器和 RPC 提供统一日志能力。

M1 的交付结果必须同时满足：

1. 业务与框架只依赖稳定的 Origin 日志 API，不直接依赖 Zap 类型；
2. 普通日志不会在 Service 工作协程执行编码、文件写入或滚动；
3. 控制台与文件可以独立配置级别和格式；
4. 日志 Runtime 可以重复创建和关闭，不依赖全局可变 Logger；
5. 所有日志协程、归档协程、文件和事件都有明确所有者；
6. 保存延迟、吞吐和分配基线，为后续框架热路径提供依据。

完整语义以[日志系统设计](../details/2026-07-25-日志系统设计.md)为依据。本文只裁剪 M1 的实际范围、依赖、目录边界、验收标准和开工 Review 结论。

## 2. 前置依赖

M1 只依赖已经验收的 M0：

- Go module：`github.com/duanhf2012/origin/v3`；
- 最低 Go 版本：Go 1.26.5；
- `errs` 基础错误包；
- 构建、测试、竞态检测和 Benchmark 入口。

M1 不依赖：

- M2 内存复用库；
- M3 配置文件加载；
- Application、Node、Service；
- TCP、NATS、RPC、Timer 或调度器。

M1 只接收 Go `Config` 结构体。YAML、JSON 等外部配置文件到 M3/M7 再接入。

## 3. 实现范围

### 3.1 日志公共类型

M1 提供：

- `Level`：Debug、Info、Warn、Error；
- `Field`：String、Bool、常用有符号与无符号整数、Float32、Float64、Duration、Time、Bytes、Err，以及显式慢路径 Any；
- `Caller`：调用文件、行号和必要的 PC；
- `Record`：时间、级别、消息、Caller、可选 Stack；
- `Handler`：Enabled、Write、Sync、Close；
- 具体 `Logger`：级别判断、写日志、固定字段派生和 CallerSkip；
- 日志 `Runtime`：日志协程、队列、Flush 和 Close。

公共 API 不提供：

- Fatal、Panic、DPanic；
- printf 风格 Sugared Logger；
- 全局默认 Logger；
- 运行时任意替换 Handler；
- 业务可直接关闭共享 Logger 的接口。

### 3.2 Logger 外观

首版至少提供以下语义：

```go
logger.Enabled(level)
logger.Log(level, message, fields...)
logger.Debug(message, fields...)
logger.Info(message, fields...)
logger.Warn(message, fields...)
logger.Error(message, fields...)
logger.ErrorStack(message, fields...)
logger.With(fields...)
logger.WithCallerSkip(skip)
```

包级提供显式的 `NewNop()`，用于不需要实际输出的单元测试或明确禁用日志的组件。Nop Logger 不创建日志协程、不持有文件，也不输出内容；普通 Config 的所有输出均关闭仍然属于配置错误，不能静默退化成 Nop。

首版提供以下类型化字段构造函数：

```go
log.String(key, value)
log.Bool(key, value)
log.Int(key, value)
log.Int32(key, value)
log.Int64(key, value)
log.Uint(key, value)
log.Uint32(key, value)
log.Uint64(key, value)
log.Float32(key, value)
log.Float64(key, value)
log.Duration(key, value)
log.Time(key, value)
log.Bytes(key, value)
log.Err(err)
log.Any(key, value)
```

`Log` 用于日志级别在运行时确定的通用组件；Debug、Info、Warn、Error 仍是普通业务首选。`Err` 使用固定字段名 `error`。`Any` 需要在调用协程生成不可变快照，属于明确的反射慢路径。

约束：

- `Logger` 是具体类型，不为了未来实现提前定义大接口；
- `With` 和 `WithCallerSkip` 返回不可变派生 Logger，不修改父 Logger；
- 所有输出端均未启用对应级别时，不采集 Caller 或 Stack；
- `ErrorStack` 只在调用协程采集一次堆栈；
- 调用位置必须指向真正的业务或框架调用行；
- 普通日志字段不能覆盖 time、level、message、caller、stack 等保留字段。

### 3.3 Handler 与 Zap

M1 默认使用 Zap 的非 Sugared、类型化能力，但业务 API 不暴露 `zap.Field`。

Handler 语义：

```go
type Handler interface {
    Enabled(level Level) bool
    Write(record Record, fields []Field) error
    Sync() error
    Close() error
}
```

规则：

- `Enabled` 可以被多个调用协程并发执行；
- `Write` 只由日志协程串行执行；
- Handler 在 `Write` 返回后不得继续引用事件拥有的临时内存；
- 自定义 Handler 使用同步写入入口，不再建立第二套事件队列；
- Zap Handler 支持 JSON、Text 和自定义 Zap Encoder；
- Zap 具体类型只能出现在 Zap 适配边界，不能进入 Logger、Record、Field 或业务代码。

包边界确定为：

- `log` 是稳定公共核心包，定义 Config、Level、Field、Record、Handler、Logger、Runtime、Crash 输出控制和生命周期 API，不导入任何 Zap 包；
- `log/zaplog` 是默认 Zap 适配包，只由它导入 `go.uber.org/zap` 和 `go.uber.org/zap/zapcore`；
- `log/zaplog` 可以依赖 `log`，`log` 不得反向依赖 `log/zaplog`，因此不会形成循环依赖；
- 文件滚动的共享内部实现放在 `log/internal/rotate`，只供日志核心的 Crash 输出和 Zap 文件 Handler 使用，不公开为业务 API。

M1 固定使用 `go.uber.org/zap v1.28.0`。该版本是 2026-07-25 复核时的最新正式版本，许可证为 MIT。版本必须写入 `go.mod`，不得使用浮动版本。复核依据为 [Zap v1.28.0 Release](https://github.com/uber-go/zap/releases/tag/v1.28.0) 和该版本的 [LICENSE](https://github.com/uber-go/zap/blob/v1.28.0/LICENSE)。

公开构造和生命周期外观确定为：

```go
func DefaultConfig() Config
func NewRuntime(config Config, handler Handler) (*Runtime, error)
func NewNop() Logger

func (r *Runtime) Logger() Logger
func (r *Runtime) Stats() Stats
func (r *Runtime) Flush(ctx context.Context) error
func (r *Runtime) Close(ctx context.Context) error
```

`Stats` 是值快照，首版字段固定为：

```go
type Stats struct {
    DroppedDebug          uint64
    DroppedInfo           uint64
    DroppedWarn           uint64
    DroppedError          uint64
    WriteFailures         uint64
    ReliableWriteTimeouts uint64
}
```

默认 Zap 适配包提供：

```go
func zaplog.New(config log.Config, options ...zaplog.Option) (*log.Runtime, error)
func zaplog.NewHandler(config log.Config, options ...zaplog.Option) (log.Handler, error)
```

`Logger` 只负责记录日志和派生固定字段，不公开 Flush、Close，也不拥有 Handler。`Runtime` 是日志协程和 Handler 的唯一生命周期所有者。`Stats` 只返回计数快照，不暴露内部队列或可变状态。

### 3.4 日志 Runtime 与两种模式

每个 Runtime 拥有：

- 一个有界事件队列；
- 一个日志协程；
- 一个 Handler；
- 必要时一个文件归档维护协程；
- 丢弃和写入失败计数；
- 明确的运行、停止准入、排空和已关闭状态。

异步模式：

- Debug、Info、Warn 和普通 Error 成功入队后立即返回；
- 队列满时丢弃当前新日志，不阻塞、不创建 goroutine、不改为同步写；
- 按级别累计丢弃计数；
- ErrorStack 在内部 1 秒上限内等待写入，超时后走最小 stderr 兜底。

同步模式：

- 编码和 I/O 仍由日志协程执行；
- 调用协程等待该事件完成；
- 主要用于开发调试和确定性测试。

两种模式共享同一套 Runtime、Handler 和关闭流程，不实现两套日志系统。

### 3.5 Flush 与 Close

`Flush(ctx)`：

- 提交内部屏障；
- 等待屏障前已经接受的日志完成；
- 调用 Handler Sync；
- 不关闭 Runtime；
- Context 超时时返回错误，不永久等待。

`Close(ctx)`：

1. 停止接收新的日志事件；
2. 排空已经接受的事件；
3. 执行 Handler Sync；
4. 停止并等待归档维护协程；
5. 执行 Handler Close；
6. 等待日志协程退出。

`Close` 必须幂等。部分初始化失败时，也必须按已经成功创建资源的逆序清理。

### 3.6 控制台输出

控制台输出支持：

- 独立启用和最低级别；
- JSON 和 Text；
- Debug、Info、Warn 写 stdout；
- Error 写 stderr；
- stdout 与 stderr 的 LevelEnabler 互斥，同一事件不能重复输出；
- 每条日志包含短路径 caller；
- JSON 使用一行一个对象的 JSON Lines。

控制台输出失败时只能使用最小 stderr 兜底，不能递归调用 Logger。

### 3.7 文件输出

文件输出支持：

- 独立启用和最低级别；
- JSON 和 Text；
- 稳定活动文件名；
- 按大小滚动；
- 按 Local 或 UTC 自然日滚动；
- 保留天数；
- 保留文件数量；
- 可选 gzip 压缩；
- 启动时处理上次异常留下的临时压缩文件。

活动文件写入和滚动只在日志协程执行。归档扫描、压缩和清理由唯一的归档维护协程执行。

M1 不引入 Lumberjack 或已经归档的 file-rotatelogs，内置 Writer 只实现本文明确列出的能力。

### 3.8 Crash 输出

Go `runtime/debug.SetCrashOutput` 修改的是进程级状态，而 M0 开发规则要求同一进程可以存在多个相互独立的 Application。

M1 完整实现 Crash 文件、启动前滚动、归档复用以及 `runtime/debug.SetCrashOutput` 注册能力，但遵守以下所有权：

- Logger Runtime 和 Zap Handler 都不得自动调用 `SetCrashOutput`；
- 日志包公开 `InstallCrashOutput(fileConfig FileConfig) (*CrashOutput, error)`，调用名称明确表示它会修改进程级状态；
- 只有最终可执行程序入口可以持有一个 `CrashOutput`，正常退出时调用其幂等 `Close()` 取消注册；
- M1 只实现并测试该能力，M16 再由最终进程入口根据启用的内置文件配置进行一次安装；
- 同一进程只允许一个 Crash 输出所有者。重复安装属于调用方违反所有权约束，不通过包级可变全局状态建立隐式注册表；
- `SetCrashOutput` 成功后会由 Go Runtime 复制文件描述符，安装函数关闭自己打开的原始文件句柄；`CrashOutput.Close()` 使用 `SetCrashOutput(nil, ...)` 取消注册；
- 运行期间不滚动 Crash 文件；只在安装前检查并滚动旧文件，进程崩溃后由下一次启动继续处理。

文件输出默认关闭，因此 Crash 输出也不会被默认安装。将来最终进程入口显式启用内置文件输出时，默认同时安装派生路径的 Crash 输出；多 Application 场景仍只能由进程入口安装一次。

## 5. 配置边界

M1 使用强类型 Go Config，至少表达：

- async 或 sync；
- 控制台启用、级别、格式；
- 文件启用、级别、格式、路径；
- 大小和日期滚动；
- Local 或 UTC；
- 保留天数、保留数量和压缩。

已确认的默认值：

- mode：async；
- console：开启；
- console level：Info；
- console format：text；
- file：关闭；
- 控制台和文件日志记录时间：使用操作系统本地时区显示；
- 内部事件队列：10000 条。

日志记录的显示时间与文件滚动时区是两个概念。日志记录默认使用 `time.Now()` 的操作系统
本地时区，并由 Encoder 输出时区偏移；`rotation.timezone` 只决定按日期滚动和归档命名
使用 Local 还是 UTC，不改变每条日志记录的默认显示时区。

Kubernetes 部署模板可以把 console format 显式改为 JSON，并按部署需要显式开启文件输出，不改变日志库的上述默认值。

零值与默认值规则：

- `DefaultConfig()` 返回一份完整、可直接使用且后续可修改的配置；
- `Config{}` 不是默认配置，构造时返回 `errs.CodeInvalidConfig`；
- 不对零值字段逐项静默补默认值，避免无法区分“调用者显式关闭”与“忘记初始化”；
- 使用默认 Zap 时调用 `zaplog.New(log.DefaultConfig())`；
- 注入自定义 Handler 时调用 `log.NewRuntime(config, handler)`；该构造函数校验公共 Runtime 配置和非 nil Handler，由 Handler 构造函数校验其自身输出配置；
- `zaplog.New` 负责组合并校验完整的控制台和文件配置；控制台和文件均关闭时返回配置错误。

配置校验必须拒绝：

- 未知日志级别；
- 未知内置格式；
- 非法模式；
- 文件启用但路径为空；
- 负数大小、期限或数量；
- 非 Local、UTC 的时区；
- 控制台和文件均关闭且没有自定义 Handler 的无输出配置。

队列容量首版不进入公共 Config，内部固定默认值为十进制 `10000` 条事件。M1 必须记录单事件实际内存占用、队列满行为和突发流量 Benchmark；如果数据表明该默认值需要调整，必须按照开发原则先与开发者确认，不能在实现中自行改变。

## 6. 错误处理

- 构造和配置错误返回 `errs.CodeInvalidConfig`；
- Runtime 已关闭返回 `errs.CodeLogClosed`；
- 默认输出构造、Flush、Sync 或 Close 的底层输出失败返回 `errs.CodeLogOutputFailed` 并保留本地 cause；
- Flush 和 Close 的 Context 取消、超时分别复用 `errs.CodeCanceled`、`errs.CodeDeadlineExceeded`；
- Handler Write、Sync、Close 的 cause 只保留在本地错误链；
- 普通日志写入方法不返回 error，避免业务热路径增加错误分支；
- 写入失败通过指标和最小 stderr 兜底观测；
- 构造 Runtime、Flush 和 Close 返回 error；
- 日志库不得调用 os.Exit、log.Fatal 或吞掉业务 panic。

不为满队列、普通异步写失败或每种文件系统错误增加错误码：普通日志方法本来不返回 error，这些情况通过 `Stats`、指标和最小 stderr 兜底观测。

## 7. 性能与内存约束

必须保存以下 Benchmark：

- 关闭级别日志；
- 异步无字段日志；
- 异步常用字段日志；
- Caller 采集；
- With 固定字段；
- 同步等待；
- ErrorStack；
- 队列满；
- Zap Field 转换；
- JSON 和 Text 编码；
- 文件逐条写入；
- 文件滚动。

实现约束：

- 关闭级别不解析 Caller、不采集 Stack、不创建事件；
- 普通热路径不使用反射和 fmt 格式化；
- 不为每条日志创建 goroutine；
- 不在 M1 提前依赖 M2 对象池；
- 是否池化日志事件必须基于 M1 实际 Benchmark，不能预设；
- 队列容量必须结合单事件实际大小和突发流量测试，不只看吞吐；
- Any 明确属于反射和快照慢路径，框架热路径禁止使用。

## 10. 验收标准

1. 公共 Logger API 不暴露 Zap 类型。
2. 控制台和文件级别、格式互相独立。
3. Caller 指向真实调用位置，ErrorStack 只采集一次正确堆栈。
4. 异步普通日志不在调用协程执行编码或 I/O。
5. 队列有界，满队列行为可观测且不会创建额外 goroutine。
6. 同步模式在日志方法返回前完成 Handler Write。
7. Flush、Close、重复 Close 和 Context 超时均不会死锁。
8. 日志协程、归档协程和文件句柄全部可以回收。

## 11. 开工 Review

### 11.1 已确认

1. 公共包名使用 `log`，默认 Zap 适配放在 `log/zaplog`，核心包不导入 Zap；
2. 首版提供 `Log(level, message, fields...)`、`NewNop()` 和类型化 Field；
3. 默认模式为 async；默认 console 开启、Info、text；内部事件队列固定为十进制 `10000` 条且不进入公共 Config；
4. 固定使用 `go.uber.org/zap v1.28.0`，MIT 许可证；
5. `DefaultConfig()` 返回有效默认配置，`Config{}` 明确报错；
6. 文件输出默认关闭；
7. Crash、大小/日期滚动、保留和压缩全部进入 M1；
8. Crash 注册由最终进程入口显式且唯一持有，不由 Runtime 或 Handler 自动注册；
9. Logger、Runtime、Handler、Stats、Flush 和 Close 按本文第 3.3 节公开；
10. 日志新增最小错误码 `CodeLogClosed` 和 `CodeLogOutputFailed`；
11. 自定义 Zap Encoder 使用创建 Handler 时传入的实例级 Option，不使用 Zap 全局注册表或 Origin 包级可变注册表。

### 11.2 自定义 Encoder 最终规则

```go
type EncoderFactory func(zapcore.EncoderConfig) (zapcore.Encoder, error)

func WithEncoder(name string, factory EncoderFactory) Option
```

- Encoder 注册表只存在于本次 `New` 或 `NewHandler` 的构造过程和所得 Handler 实例中；
- `json`、`text` 为保留名称，自定义名称重复、为空、覆盖保留名称或 factory 为 nil 时返回 `errs.CodeInvalidConfig`；
- factory 在 Handler 构造阶段按实际启用的输出端调用，失败则构造失败并逆序清理已经创建的资源；
- 每个输出端拥有自己的 Encoder 实例，不在多个 Runtime 之间共享；
- Zap 类型只出现在 `log/zaplog` 的公开扩展接口中，使用普通 `log` 包的业务代码不依赖 Zap。
