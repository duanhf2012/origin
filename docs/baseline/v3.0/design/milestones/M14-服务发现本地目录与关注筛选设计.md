# Origin 第三版 M14 服务发现本地目录与关注筛选设计

> 文档类型：里程碑设计（已实现）
> 创建日期：2026-07-29
> 最后更新：2026-08-01
> 当前状态：已实现并通过 Windows、Ubuntu 与跨平台验收

> 后续语义：M14 保持 Running/Retired 都可见并维持精确路由连接需求；M19/M20 自动范围
> 默认只取 Running，`IncludeRetired()` 显式纳入 Retired；M19 单目标仍排除已知断开实例。

## 1. 文档目的

M13 已经完成 TCP RPC 端到端闭环，但当前所谓的 RPC 目标表只是由 Application 或测试
显式注入的临时连接目标，不是正式服务发现：

- 没有实现 `allow_discovery`；
- 没有按 `NodeID + ServiceName` 建立可见实例目录；
- 没有 Origin 或 etcd Discovery Provider；
- 没有发现、失去发现和退休状态事件；
- 同一 Application 当前会把选中的 TCP Node 地址直接互相登记。

用户已经确认：TCP 和 NATS 发起远端 RPC 前，都必须先检查当前 Node 的本地服务发现
结果。未发现目标时立即返回错误，不能先尝试 TCP 连接或向 NATS Subject 发布后再等待
超时。

因此原 M14“NATS RPC 端到端闭环”顺延为 M15；M14 先实现 Transport 无关的本地服务
发现目录、关注筛选、只读快照和监听基础。原 M15“完整停止、异常恢复与进程集成”顺延
为 M16。

## 3. M14 范围

M14 实现：

1. 每个 Node 独立拥有的本地服务发现目录；
2. Provider 原始完整快照的统一输入边界；
3. `allow_discovery` 的启动期解析、校验和预编译匹配规则；
4. 原始目录到当前 Node 可见服务快照的筛选；
5. `NodeID + ServiceName` 精确索引；
6. 按 `ServiceName` 查询候选实例的稳定索引；
7. 不可变快照的原子发布和无锁 RPC 查询；
8. TCP RPC 发送前的公共服务发现检查；
9. TCP 连接需求由可见快照变化驱动，不再把 M13 临时目标表当成事实来源；
10. 发现与失去发现的 Service 监听注册基础；
11. 同一 Application 多 Node 使用真实 Transport，但也经过本地发现目录；
12. 查询、筛选、Diff、监听补发、并发发布及性能基准；
13. `FindDiscoveredService`、`ListDiscoveredServices`、`AwaitService` 和
    `AwaitNodeService` 的公开能力；
14. OnStart 生命周期 Context 对 `Service.Await` 和生成 `AwaitXxx` 的合法支持；
15. 全 Node Service 越过统一就绪屏障后的一次性发布。

## 4. M14 明确不实现

以下能力继续保持独立里程碑，不混入本地目录内核：

- Origin 内置 `DiscoveryService` 和它的控制通道；
- etcd Client、Lease、Watch、TLS 和认证；
- Provider 的 TTL、重连及陈旧会话裁决；
- NATS RPC Transport；它属于顺延后的 M15；
- 完整 Service 退休、恢复和正式停止 API；
- RoundRobin、Random、按 Key、自定义 Selector；
- 多 Node Broadcast 展开；
- 热更新 `allow_discovery`；
- 服务发现审计日志或历史事件查询。

## 5. 所有权

### 5.1 Node 独占目录

已经确认：全部远端 Node 和 Service 的发现数据归当前 Node 所有。

概念所有权如下：

```text
Node
 ├─ 本地 Service 注册表
 ├─ Discovery Directory
 │   ├─ Provider 原始目录
 │   ├─ 当前 Node 的 allow_discovery 规则
 │   └─ 当前不可变可见快照
 └─ RPC Runtime
```

规则：

- 每个 Node 独立创建、启动和释放自己的目录；
- Application 不持有一份供全部 Node 共享的可见快照；
- 不同 Node 可以基于相同 Provider 原始数据得到不同可见结果；
- Service 不持有或复制完整发现列表；
- Service 只通过所属 Node 查询、等待目标或注册监听器；
- Node Stop 时先关闭目录准入和监听，再释放目录拥有的数据；
- 同 Node 本地 Service 调用使用本地 Service 注册表，不绕到远端服务发现。

### 5.2 Transport 不拥有发现事实

TCP 与 NATS 共用同一个 Node 本地目录：

- `allow_discovery`、状态、契约、候选筛选和错误判断只实现一次；
- TCP 连接管理器可以保留 `NodeID -> connection` 的内部连接状态，但它不是第二份服务
  发现目录；
- NATS 后续只在公共目录已经选出目标后使用 NodeID 构造稳定 Subject；
- Transport 连接状态和服务发现状态分别观察，不能互相冒充。

## 6. 原始数据输入

### 6.1 完整快照

已经确认：目录内核只接受一份完整原始快照，不同时公开全量和增量两套入口。

原始 DTO 和目录实现位于 `internal/discovery`，不向项目业务公开修改入口。概念类型：

```go
type RawSnapshot struct {
    Nodes []RawNode
}

type RawNode struct {
    NodeID     string
    SessionID  string
    Labels     map[string]string
    Transport  Transport
    Address    string
    Services   []RawService
}

type RawService struct {
    ServiceName         string
    State               ServiceState
    ContractID          uint64
    ContractFingerprint [32]byte
}
```

`Transport` 和 `ServiceState` 是发现目录内部使用的紧凑枚举，不直接复用完整的本地
Service 生命周期状态机。概念入口 `directory.ApplySnapshot(snapshot)` 只供 Application
过渡装配、测试夹具和后续 Discovery Provider 使用，不成为业务 Service 任意修改发现
状态的公共 API。

规则：

- 每次提交表示数据源当前确认的全部公开 Node 和 Service；
- `ApplySnapshot` 必须复制并规范化传入的 Slice、Map 和字符串，Provider 返回后可以安全
  复用或修改自己的 DTO；
- 目录只保留规范化后的自有不可变记录，索引可以共同引用同一记录；
- 目录一次性完成校验、筛选、稳定排序、Diff 和原子发布；
- Origin Provider 可以直接提交它收到的全量目录；
- etcd Provider 后续在自身内部维护 Watch 结果，只在内容有效变化时提交完整目录；
- 心跳、重复 Put 或内容完全相同的快照不会重新发布；
- Provider Revision 属于具体数据源内部状态，不进入 `RawSnapshot`；目录仅为实际发布的
  不同内容生成自己的单调版本；
- Add、Update、Remove 的乱序、Revision、租约和旧会话裁决属于 Provider，不进入公共
  目录内核；
- M14 尚无正式 Provider，同一 Application 的 Node 清单和测试夹具先通过同一入口验证
  目录、TCP 和监听闭环；Provider 接入后不修改 RPC Runtime。

### 6.2 实例身份与最小元数据

可见实例身份固定为：

```text
NodeID + ServiceName
```

该复合键表示稳定的逻辑位置；SessionID 区分同一逻辑位置上的不同进程会话：

- `NodeID + ServiceName + SessionID` 全部相同才表示同一个运行实例；
- 同一 `NodeID + ServiceName` 的 SessionID 改变表示旧实例已经退出、新实例已经启动；
- 该变化不能被净变化合并成“没有变化”；
- 监听方必须先收到旧会话的 `OnLost`，再收到新会话的 `OnDiscovered`；
- TCP 旧连接和 pending 仍按 M13 会话规则清理，新会话建立新的连接状态；
- SessionID 由 Application 过渡数据源或后续 Provider 生成，业务配置不能手写。

原始 Node 数据至少需要包含：

- NodeID；
- Provider 为本次 Node 进程生成的 SessionID；
- Node 标签；
- 业务 RPC Transport 类型；
- TCP 模式下的公开地址；
- 当前公开 Service 列表。

公开 Service 数据至少需要包含：

- 实际 ServiceName；
- 当前运行状态；
- ContractID；
- 完整 ContractFingerprint。

私有 Node 和以 `_` 标记的私有 Service 不进入原始发布目录。

发现目录不保存 RPC 方法列表。生成客户端已经固定 MethodID，目标 Node 的 Dispatcher
拥有方法表；发现阶段只需用 `ContractID + ContractFingerprint` 判断目标 Service 是否
实现完全一致的契约。

没有公开 RPC、但需要被其他 Service 发现和监听的 Service 合法存在于目录中，其
`ContractID` 和 `ContractFingerprint` 均为零。只要 ServiceName、会话和状态合法，它仍
可产生 `Discovered`、`Lost` 和后续状态变化；RPC 路由不会把它当作可调用目标。

### 6.3 M14 过渡数据源与未来 Provider

每个 Node 在启动时只选择一个发现数据源，整个生命周期不热切换，也不合并多个来源：

- M14 尚未配置正式 Provider 时，Application 根据本次实际启动的 Node 构造内部完整原始
  快照；
- Application 只保存构造原始快照所需的进程内记录，不拥有或共享任一 Node 的可见快照；
- 每个 Node 仍把完整原始快照复制到自己的所有权边界，再独立执行 `allow_discovery`
  筛选；
- 同一 Application 的 Node 继续使用真实 TCP 连接和握手，不允许通过 Runtime 或 Node
  指针短路；
- 只启动一个 Node 时，Application 过渡数据源不会伪造其他进程中的 Node；
- 后续配置 Origin 或 etcd Provider 时，每个 Node 只使用自己的 Provider 快照，
  Application 不再注入过渡快照；
- 同一 Application 中使用正式 Provider 的其他 Node 也必须正常注册和发现，保持与独立
  进程一致；
- Provider 快照包含当前 Node 时，本地目录过滤自身；本地调用继续使用本地 Service
  注册表；
- Application 过渡数据源不是可配置的 `static` Provider，不增加配置项。

每个 Node 在创建时生成独立 SessionID。整个 Node 的全部公开 Service 必须越过统一就绪
屏障后才一次性加入数据源：

- Node 基础设施和发现订阅先启动，使业务 `OnStart` 可以发现并调用已经 Ready 的远端
  Service；
- 当前 Node 的全部 Service 均成功完成 `OnStart` 前，不向 Application 过渡数据源或正式
  Provider 发布任何本 Node Service；
- 不能逐个发布已经先完成 `OnStart` 的 Service，避免其他 Node 观察到部分启动的 Node；
- 全部 `OnStart` 成功并开放本地入站准入后，才以一份 Node 记录原子发布全部公开
  Service；
- 任一 `OnStart` 失败或启动 Context 取消时，本 Node 从未对外可见，直接按现有反序规则
  回滚；
- 正式 Stop 开始关闭新任务准入前，先从过渡数据源移除该 Node 的公开 Service；正式
  Provider 的停止顺序由 M16 和对应 Provider 里程碑使用同一语义实现。

### 6.4 OnStart 生命周期 Await

已经确认：`OnStart` 复用正常业务代码中的 `Service.Await` 和生成的 `AwaitXxx` 外观，
但不复用普通业务 Task 的执行权切换。

Node 在调用每个 `OnStart` 前：

1. 已经启动 TimerEngine、RPC Client Runtime、Transport、发现订阅和本地目录；
2. 为当前 Service 准备 Scheduler、默认 Await 超时和 DeadlineQueue；
3. 不启动普通业务 Runner，不准入 RPC、Timer 回调、发现回调或其他业务任务；
4. 为本次生命周期调用派生只属于当前 Service 和本次启动代次的私有 Context 令牌。

`Service.Await(ctx, fn)` 根据令牌选择唯一合法路径：

- 普通 Origin Task Context：沿用 M9 协作式 Await，释放执行权并由替补 Runner 调度其他
  Ready 任务；
- 当前 Service 的 OnStart Context：在原生命周期 goroutine 中直接调用并等待 `fn`
  返回，不释放给其他业务任务，也不启动替补 Runner；
- `context.Background()`、其他 Service 的 Context或旧生命周期 Context：返回
  `CodeInvalidArgument`。

Go 不能可靠识别“当前 goroutine”。框架只能校验 Service、生命周期代次和 Context
有效期，不能证明业务没有把仍有效的 OnStart Context 传给另一个 goroutine。因此业务把
生命周期 Context 交给其他 goroutine 属于明确禁止的 API 误用，必须由代码审查、Race
测试和项目静态检查发现；框架不伪造无法实现的 goroutine 身份检查。

生命周期 Await 仍使用当前 Service 的 M8 DeadlineQueue。Scheduler 的既有 Deadline 控制
协程可以在 Prepared 阶段启动，但它只取消到期 Context，不执行用户回调；普通业务 Runner
仍要等整个 Node 越过就绪屏障才激活。等待函数在 OnStart 的原 goroutine 中执行，不为
`fn` 创建辅助 goroutine。

因此生成客户端不需要增加 `StartAwaitXxx` 等重复方法：

```go
func (s *GameService) OnStart(ctx context.Context) error {
    if err := s.AwaitService(ctx, "DBService"); err != nil {
        return err
    }

    loadCtx, cancel := context.WithTimeout(ctx, 5*time.Minute)
    defer cancel()
    return s.dbClient.AwaitLoadGameData(loadCtx)
}
```

统一超时规则保持不变：

- 单次调用显式 Deadline 优先；
- 没有显式 Deadline 时使用 Service、Node 或内置 `15s` 默认 Await 超时；
- Application/Node 整体启动默认没有框架 Deadline，由外部 Start Context 或 Stop 取消；
- 大数据加载使用显式长 Deadline，并优先按页或分批 RPC，不能依赖超过 RPC `4M`
  payload 上限的单个响应；
- 框架不自动重试 RPC；只有业务明确判定为幂等的查询才可以在 OnStart Context 范围内
  有界重试。

`AwaitService` 和 `AwaitNodeService` 直接等待目录版本变化形成的内部 Future，不依赖尚未
激活的业务发现监听回调，也不使用 Timer 轮询。发现 Provider 和 Transport 由独立基础设施
goroutine 持续工作，因此某个 OnStart 长时间等待不会阻塞其他已经运行 Node 的网络和发现。

两个接口只等待远端可见实例，并把 Running、Retired 及零 RPC 契约 Service 都视为已经
发现；真正发起 RPC 时再检查契约和 Transport。`AwaitNodeService` 传入当前 NodeID 时立即
返回 `CodeInvalidArgument`，不能等待当前 Node 在自身 OnStart 返回后才可能形成的发布。
同 Node 依赖使用 `LookupService` 和配置声明顺序。Application 多 Node 仍严格顺序启动，
依赖方必须位于被依赖方之后，不自动解析或解除启动循环依赖。

全部 OnStart 成功后，如果向正式 Provider 发布本 Node 记录暂时失败，Node 保持未公开，
在同一 Start Context 内使用有抖动的有界指数退避重试；不重复调用任何 OnStart。成功发布
后才完成 Node Ready；Context 取消则停止重试并反序回滚。

M16 扩展运行期 Transport 恢复规则：TCP Listener 或 NATS 入站能力暂时不可用时尽力撤销
当前 Node 公开记录；Transport 完全 Ready 后由框架自动重新发布一份完整 Node 快照。只有
Running/Retired 公共 Service 进入快照，Failed Service 保持撤销。恢复使用内部 generation
排除旧连接迟到回调，不把 generation 或 Revision 加入公共发现模型；真实 Lost 和恢复后的
Found/StateChanged 不做防抖。

启动中 Node 发起 RPC 时，调用方必须先发现目标；目标端不要求调用方已经出现在自己的
发现快照中，否则双方会形成“必须先互相发现才能首次调用”的循环依赖。TCP 握手仍携带并
固定调用方 NodeID 和 SessionID，鉴权属于后续独立安全层。

## 7. 不可变可见快照

### 7.1 原子发布

已经确认采用 `atomic.Pointer` 发布不可变快照，不使用 RPC 热路径上的 `RWMutex`。

更新流程：

1. 在发现更新冷路径构建完整新快照；
2. 完成校验、筛选、索引和稳定排序；
3. 计算旧快照与新快照的差异；
4. 使用一次原子 Store 发布新快照；
5. 发布成功后驱动 TCP 连接需求和业务监听通知；
6. 旧读者继续安全读取旧快照，之后由 Go GC 自然回收。

RPC 查询流程只有：

```go
snapshot := directory.current.Load()
instance := snapshot.byInstance[key]
```

每次查询不复制 NodeID、ServiceName、标签、契约或快照。

### 7.2 索引

快照概念上至少包含：

```go
type Snapshot struct {
    byInstance map[InstanceKey]*Instance
    byService  map[string][]*Instance
}
```

- `byInstance` 服务于 `ToServiceOnNode` 精确查询；
- `byService` 为后续自动路由、Broadcast 和等待 Service 提供稳定候选；
- `Instance` 只保存一份不可变记录，索引保存引用，不深复制业务元数据；
- 候选按 `NodeID + ServiceName` 稳定排序；
- 字符串字段在安全所有权边界内复用不可变字符串数据，不在每次索引间复制字符内容；
- 首版不增加字符串驻留池或复杂结构共享。

### 7.3 公开查询外观

已经确认采用“公开 `discovery` 数据类型，查询方法直接组合到 `Service`”的方案。业务
不需要取得目录对象，也不增加 `service.Discovery().Find(...)` 这一层门面。

公共只读类型位于 `discovery` 包，概念外观如下：

```go
package discovery

type State uint8

const (
    StateUnknown State = iota
    StateRunning
    StateRetired
)

type Instance struct {
    NodeID      string
    SessionID   string
    ServiceName string
    State       State
    Labels      map[string]string
}
```

`Address`、Transport、ContractID 和 ContractFingerprint 不向业务查询接口公开：

- 地址和 Transport 是 RPC Runtime 的连接实现细节；
- 契约信息由生成客户端和 RPC Runtime 校验；
- 业务路由通常只需要 NodeID、ServiceName、状态和标签；
- 减少公开字段可避免业务绕过统一 RPC Runtime，自行拼接连接或协议。

查询能力直接组合到 `service.Service`：

```go
func (s *Service) FindDiscoveredService(
    nodeID string,
    serviceName string,
) (discovery.Instance, bool)

func (s *Service) ListDiscoveredServices(
    serviceName string,
) []discovery.Instance
```

规则：

- `FindDiscoveredService` 只做 `NodeID + ServiceName` 精确查询；
- `ListDiscoveredServices` 只查询指定 ServiceName，不把空字符串解释为全量通配；
- 两个方法都只返回远端发现实例；同 Node 本地 Service 继续使用既有
  `LookupService`；
- `Running` 和 `Retired` 都返回，业务根据 `State` 自行决定如何处理；
- 精确查询不存在时返回零值和 `false`，批量查询不存在时返回 `nil`；
- 批量结果按 NodeID 稳定排序；
- 返回值由调用方独立持有，Labels 深复制，不能引用内部不可变快照；
- 公开查询属于业务控制与观察冷路径；RPC Runtime 不调用这些复制接口，仍直接读取内部
  不可变索引；
- 首版不增加“列出全部 Node”“列出全部 Service”或按任意条件扫描接口；路由、监听和
  诊断分别使用各自的窄接口。

公开 DTO 与内部目录实现分离：

- `discovery` 只包含业务可见的只读类型；
- `internal/discovery` 包含 RawSnapshot、不可变 Snapshot、索引、Diff 和发布逻辑；
- 业务无法取得 `ApplySnapshot` 或修改目录；
- 内部代码同时使用两个包时为实现包使用明确别名，禁止把公开 DTO 误当作内部零复制对象。

### 7.4 当前微基准

2026-07-29 在 Windows、AMD Ryzen 7 7840HS、100 个
`NodeID + ServiceName` 实例、无写入条件下完成临时微基准：

| 查询方式 | 单线程 | 14 线程并行吞吐 | 分配 |
|---|---:|---:|---:|
| `atomic.Pointer` 不可变快照 | 约 `14.6ns/op` | 约 `2.2ns/op` | `0` |
| `RWMutex + map` | 约 `15.7ns/op` | 约 `24.3ns/op` | `0` |

并行数据表示 Go Benchmark 的总体吞吐，不等同于单次端到端 RPC 延迟。M14 实现仍必须用
最终数据结构在 Windows/Linux 复测，不能把临时微基准当作永久性能承诺。

### 7.5 相等判断与 Diff

已经确认采用 Map 精确比较，不增加内容哈希、规范字节序列化或碰撞处理。

每次 `ApplySnapshot` 按以下顺序处理：

1. 完整校验并规范化所有新输入；
2. 按 `NodeID + ServiceName` 建立新的可见实例 Map；
3. 对每个新实例查询旧快照：
   - 字段完全相同：复用旧快照中的不可变 `Instance` 指针；
   - 旧快照不存在：记录 `Discovered`；
   - 逻辑位置相同但 SessionID 改变：记录旧会话 `Lost`，再记录新会话
     `Discovered`；
   - 会话相同但运行状态改变：记录状态变化，不伪装成 `Lost/Discovered`；
4. 遍历旧实例 Map，对新 Map 不存在的实例记录 `Lost`；
5. 实例数量相同且全部字段相同：立即保留旧快照，不增加目录版本，不产生连接和业务
   通知；
6. 存在真实变化时才建立并稳定排序 `byService` 候选索引；
7. 完成全部索引和 Diff 后，一次原子发布新快照。

比较函数必须显式包含影响发现、路由和连接的全部字段；新增字段时相等判断测试必须同步
覆盖。标签 Map 使用键和值精确比较，不依赖 Go Map 遍历顺序。

任意输入校验失败时整批拒绝：

- 旧快照和目录版本保持不变；
- 不修改 TCP 连接需求；
- 不提交业务监听任务；
- 不接受“部分合法实例先发布”的半成功状态。

算法的普通比较复杂度为 `O(n)`。只有真实变化时才执行候选排序。快照和 `Instance`
首版不池化，因为原子发布后旧快照可能仍被并发 RPC 读者持有；错误回池会产生数据竞态和
悬空复用风险。

## 8. 关注筛选

M14 直接实现已经确认的规则：

- 完全未配置 `allow_discovery`：发现 Provider 范围内全部公开 Service；
- 显式 `allow_discovery: []`：不发现任何远端业务 Service；
- 显式 `null`：配置错误；
- 多条规则之间为 OR；
- 同一规则中的 Service 名称为 OR；
- 同一标签多个值为 OR；
- 不同标签之间为 AND；
- 缺少 `services` 或 `node_labels` 表示不限制该维度；
- 空规则、空 Service 列表和空标签映射是配置错误；
- 标签区分大小写并精确匹配，不支持正则和通配符；
- 配置冷路径把单值和多值统一规范化并建立匹配集合；
- 热路径不解析配置、不执行正则。

配置仍位于各 Node 下，不引入 Application 配置概念。

## 9. RPC 发送前检查

已经确认 TCP 和 NATS 采用完全相同的规则：

1. 同 Node 本地目标先走本地 Service 注册表；
2. 远端目标先读取所属 Node 的当前可见快照；
3. 没有发现指定目标时立即返回 `CodeRPCNoRoute`；
4. 目标 Service 没有 RPC 契约或契约不匹配时返回对应契约错误；
5. 发现目标但当前 Node 与目标业务 Transport 不兼容时返回
   `CodeTransportUnavailable`；
6. M14 的精确目标在 `Running` 或 `Retired` 下均允许进入具体 TCP/NATS Transport；
   M19/M20 自动范围默认只接受 Running，显式 `IncludeRetired()` 后接受两者；
7. TCP 瞬时断线不把服务发现状态改成 Lost；M19 自动选择排除该断开实例；
8. 后续 NATS 向无订阅者 Subject 发布不能代替本地发现检查；
9. 不自动重选或重发非幂等 RPC。

M13 的 `AddRPCTarget/RemoveRPCTarget` 将降为 TCP 连接管理的内部目标生命周期输入，由
目录快照差异驱动，不再由业务或 Application 绕过发现规则直接维护。

### 9.1 TCP 连接需求与非阻塞对齐

已经确认采用“先发布发现状态，再非阻塞对齐连接目标”：

1. 一个远端 TCP Node 只要存在至少一个当前可见且 ContractID 非零的 Service，就产生
   一条 Node 级连接需求；
2. 同一 Node 上多个 Service 共享一条 TCP 连接，不按 Service 建连接；
3. `Retired` 仍允许精确 RPC，因此与 `Running` 使用相同连接需求；M19 自动路由只选择
   Running；
4. 只有 Node 不再存在任何可见 RPC Service、Node Lost 或 SessionID 被替换时，才删除
   旧连接需求；
5. 新快照完成校验和 Diff 后先原子发布，再把最新
   `NodeID + SessionID + Address` 目标集合交给 TCP Runtime，最后提交业务监听任务；
6. 新目标在后台建立连接和重连；删除目标只发出取消信号，不等待连接 goroutine 退出；
7. 快照已发布但新连接尚未完成的短暂窗口返回 `CodeTransportUnavailable`，不能回退到
   旧实例；
8. RPC 选择出的 SessionID 必须与连接目标 SessionID 一致，旧会话连接不能承载新请求；
9. TCP Hello/Ack 握手增加 SessionID 校验；该字段只存在于连接握手，不增加每个 RPC
   请求和响应包大小；
10. 同一 Node 的连续连接目标更新只保留最新集合，不增加轮询协程。

连接目标更新失败只影响 Transport 可用性，不回滚已经确认的服务发现事实；RPC 返回明确
Transport 错误，后续目标对齐或重连继续恢复。Node Lost 或会话替换后，旧连接上的出站
pending 按 M13 连接关闭规则失败；远端已经接收并进入 Service Runner 的请求仍继续执行，
不能因调用方连接关闭而撤回。

## 10. 发现监听

### 10.1 已确认外观

M14 采用显式、多监听器、ID 取消方案。概念 API：

```go
package discovery

type Event struct {
    NodeID   string
    Services []Service
}

type Service struct {
    ServiceName string
    State       State
}

type IListener interface {
    OnDiscovered(ctx context.Context, event Event)
    OnStateChanged(ctx context.Context, event Event)
    OnLost(ctx context.Context, event Event)
}

func (s *Service) AddDiscoveryListener(
    listener discovery.IListener,
) (discovery.ListenerID, error)

func (s *Service) RemoveDiscoveryListener(
    id *discovery.ListenerID,
) bool
```

规则：

- 一个 Service 可以注册多个监听器；
- `RemoveDiscoveryListener` 通过 ID 删除，完成后把外部 ID 置零；
- Service Stop 自动删除其全部监听器；
- 注册成功后补发当前已经可见的实例；
- 事件按 Node 批量携带变化 Service 的名称和状态；
- `OnDiscovered` 携带发现时的当前状态，`OnLost` 携带失去发现前的最后已知状态；
- `OnStateChanged` 携带状态变化后的最新状态；
- `Running <-> Retired` 产生 `OnStateChanged`，不伪装成 Lost/Discovered；
- `StateUnknown` 只作为公开结构的零值和非法输入防护，不会作为有效发现事件投递；
- 快照版本只在目录内部用于发布、合并和统计，不向业务事件公开；业务回调跨越 `Await`
  后仍应重新查询当前状态，不能依赖旧事件判断最新状态；
- 一个 Listener 对象只注册一次，同时实现三个明确回调，不需要分别注册；
- NodeID 和 ServiceName 使用稳定顺序；
- 回调进入所属 Service 的 FIFO 调度上下文；
- 回调收到当前 Service Task 的 Origin Context，可以在回调内使用 `Await`；
- Provider、TCP、NATS 或 Timer goroutine 不直接执行用户回调；
- 回调执行前已经发布对应的新快照；
- v3 使用 `OnDiscovered`、`OnLost`，不沿用不规范的
  `OnUnDiscoveryService`。

### 10.2 注册、补发与并发更新的原子顺序

已经确认采用冷路径短锁方案。`ApplySnapshot`、`AddDiscoveryListener` 和
`RemoveDiscoveryListener` 共用同一个目录写锁，用于保护监听器集合、快照版本推进和待
交付标记。RPC 查询只读取 `atomic.Pointer` 发布的不可变快照，不取得该锁。

注册监听器时在同一次加锁范围内完成：

1. 校验所属 Service 生命周期和监听器参数；
2. 分配带世代号的 `DiscoveryListenerID`，并把监听器加入所属 Service 的订阅集合；
3. 记录注册时的最新可见快照版本；
4. 把该监听器的“上次已交付状态”初始化为空状态；
5. 把所属 Service 标记为存在待交付发现变化；
6. 释放目录写锁，再按 Service Runner 规则尝试提交交付任务。

因此首次补发不是一类独立事件，而是“空状态 -> 注册完成时或任务执行前的最新状态”的
普通净变化。注册完成后即使立刻到达新快照，也只会把待交付目标版本推进到最新版本，不
会漏掉变化，也不会重复发送“首次补发 + 增量更新”。

具体并发规则：

- 快照更新、注册和移除在目录写入侧有唯一线性化顺序；
- 每个 Service 最多只有一个已入队发现同步任务，或者一个“发现状态待同步”布尔标记；
- Service 的 `Accepted` 已达到 `max_tasks` 任务准入上限时，不返回过载、不丢最终状态，
  也不建立无界备用事件队列；
- 达到准入上限时只把“发现状态待同步”设为 `true`；任一已接收任务完成并释放额度后，
  Scheduler 在同一个短锁事务中把它转换成一个普通 FIFO Ready 任务；
- 交付任务取得执行权时再读取目标最新版本并计算净变化；
- 任务执行期间到达的新版本只推进目标版本，当前任务完成后如仍有差异，再向 FIFO
  尾部提交一个任务；
- `RemoveDiscoveryListener` 使用 ID 中的世代号使已经排队的旧交付失效；旧任务开始
  时发现监听器已删除便跳过，不能回调已经取消的对象；
- Service Stop 通过相同取消路径清除全部监听器，陈旧任务同样只会跳过。

“发现状态待同步”不是另一条队列，也不保存 Event 对象或快照副本。它只是 Service
发现订阅状态中的一个布尔值。无论等待额度期间发生多少次快照变化，任务执行时都从上次
已交付状态直接对齐到当前最新状态。

监听器由业务显式注册，正常场景通常只注册一次。M14 不设置监听器数量上限，也不增加
`max_discovery_listeners` 或 `max_discovery_events` 配置：

- 每次注册都是一项独立订阅，业务必须保存 ID 并按需移除；
- Service Stop 自动移除该 Service 的全部订阅；
- 同一个监听器被业务重复注册时视为多项订阅，框架不增加反射去重逻辑；
- 发现交付只有一个任务或一个布尔待同步标记，不会因快照变化建立无界事件列表。

在 `OnInit` 或 `OnStart` 注册监听器是合法的。此时只建立订阅并记录待交付状态，不在
生命周期调用栈或 Provider goroutine 中直接回调；待 Service Runner 可以接收普通任务
后，再执行首次状态同步。

不采用“先查询再订阅”，因为两步之间存在必然竞态；也不采用全程无锁 CAS 状态机，因为
发现更新属于冷路径，额外复杂度和维护风险明显高于短锁收益。

### 10.3 连续版本合并

已经确认采用状态型监听，不把服务发现监听器设计为审计日志：

- 每个 Service 最多只有一个待执行的发现交付任务；
- 目录保存该 Service“上次已经交付的可见版本”和“当前最新可见版本”；
- 工作任务真正取得 Service 执行权时，计算两个版本之间的净变化；
- 工作任务尚未执行时到达的多个发现版本合并到最新版本；
- 快速出现又消失、且业务尚未处理的实例可以不产生无意义的先发现再失去回调；
- TCP 连接需求和 RPC 路由立即读取最新快照，不等待业务监听回调；
- Service 达到 `max_tasks` 任务准入上限时不创建无界事件列表，只记录发现状态需要同步；
- 一个发现任务完成后，如果执行期间又产生了新版本，则在 FIFO 尾部继续提交下一次
  净变化任务；
- Service 最终收到的状态不能丢失，但不承诺收到每一个短暂中间状态。

该规则替代详细设计中“监听器收到每一个 Provider 中间版本”的旧要求。

### 10.4 回调执行边界

监听回调属于可能访问业务状态的用户代码，必须遵守：

- 只在监听者所属 Service 的工作 Runner 中执行；
- 与 RPC、Timer、Async 恢复等任务共用唯一 Service 执行槽；
- 不建立 Discovery 专用业务 goroutine；
- 回调同步执行期间持有 Service 执行权；
- 回调调用 `Await` 时按 M9 规则释放执行权，完成后恢复原任务；
- 发现事件只表示需要重新对齐，Node 当前最新可见快照始终是事实来源；
- 回调跨越 `Await` 或其他长耗时阶段后，在提交业务状态前必须重新查询最新发现状态，
  不能用旧 Event 覆盖已经变化的新状态；
- 监听业务应按当前状态实现幂等对齐，不把回调次数当成资源引用计数；
- 回调返回后由当前 Runner 继续处理后续 FIFO 任务；
- 回调 panic 由 Service Task 边界恢复、记录并完成当前发现任务，不破坏目录或 Provider；
- Service 进入 Stopping 后不再准入新的发现回调，已经进入 Ready/Running/Waiting 的回调
  按 M16 最终停止规则排空。

### 10.5 不增加时间型防抖

已经确认：M14 本地目录和业务监听层不增加 `lost_grace`、Debounce Duration 或延迟 Lost。

原因：

- Provider 已经确认的状态是当前 Node 的事实来源；
- 延迟 Lost 会让目录、RPC 路由和业务缓存观察到不同时间点的状态；
- 业务监听器通常通过发现事件重新对齐自身状态，隐藏已确认变化反而可能扩大不一致；
- 固定防抖时间很难同时满足故障切换和昂贵业务回调；
- 已经开始执行的业务回调不能被 Go 安全强行撤销。

防止虚假抖动的职责放在 Provider：

- Origin Provider 在控制连接短暂断开时最多保留现有快照一个 TTL，不立即发布 Lost；
- etcd Provider 使用 Lease、初始 Range + Revision Watch，Watch 重连本身不制造 Lost；
- TCP/NATS 瞬时断线只改变 Transport 状态，不产生服务发现 Lost；
- 重复且内容相同的 Provider 快照由 M14 直接去重。

Provider 一旦提交内容确实不同的新快照，M14 必须立即：

1. 发布新的 RPC 可见快照；
2. 更新 TCP 连接需求；
3. 合并或提交 Service 工作任务；
4. 不等待人为防抖时长。

连续版本合并只发生在业务工作任务尚未开始时。监听方尚未观察这些中间版本，按当前最新
状态对齐不会产生状态倒退。工作回调一旦开始执行，后续变化将在它完成后继续生成新的净
变化任务；框架不隐藏已经被业务观察的状态。

## 11. 错误、性能与资源边界

### 11.1 错误码

M14 当前确认的场景优先复用已经存在且语义准确的统一错误码：

| 场景 | Code |
|---|---|
| `allow_discovery` 配置非法 | `CodeInvalidConfig` |
| 内部 `ApplySnapshot` 参数、重复实例或字段非法 | `CodeInvalidArgument` |
| RPC 目标未发现 | `CodeRPCNoRoute` |
| 目标已经发现但 Transport 不可用 | `CodeTransportUnavailable` |
| 等待发现超时或取消 | `CodeDeadlineExceeded` / `CodeCanceled` |
| 监听注册参数非法 | `CodeInvalidArgument` |
| 监听方正在停止或已经停止 | `CodeServiceStopping` / `CodeServiceStopped` |

复用 Code 的前提是语义完全一致，不能为了减少枚举而把错误强行归入相近类别。后续实现或
Provider 接入时，如果出现以下情况，应新增服务发现专用 Code，而不是滥用
`CodeInternal`、`CodeInvalidConfig` 或 Transport Code：

- 调用方需要稳定地区分并采取不同恢复动作；
- 错误会跨 RPC、进程或语言边界传递；
- 现有 Code 无法准确描述发现领域语义；
- 该错误不是一次只用于日志定位的内部实现细节。

新增前必须在统一错误码设计中记录明确触发条件、恢复语义和编号；不能只因错误文本不同
就增加 Code。M14 本地目录实现阶段没有必须新增的稳定场景，因此没有预占服务发现编号。
后续 M16 为“必需 Discovery Provider 运行期不可用”增加
`CodeDiscoveryUnavailable=5001`；该错误不改变 M14 的本地目录、无实例和等待语义。

来源适配层负责映射：

- Application 自己生成非法快照属于框架 Bug，外层映射为 `CodeInternal`；
- Origin Provider 收到非法线协议数据映射为 `CodeTransportProtocol`；
- etcd Provider 的值格式和一致性错误在对应里程碑根据可恢复语义决定，目录内核不提前
  代替其定义。

### 11.2 性能与资源边界

已确认：

- RPC 查询以零堆分配为目标；
- 发现更新允许在冷路径分配新 Map、Slice 和实例记录；
- 不因一次更新复制业务 payload；
- 内容相同的完整快照不发布新版本；
- 快照读取不加锁；
- 更新串行化只影响发现写入，不阻塞旧快照读取；
- 不为每个 Service 建立一份完整发现快照；
- TCP 连接需求按 Node 去重；
- 不为 NATS 的每个 Service 建立 Subscription；
- 监听器和发现事件不增加独立数量配置；
- 不设置 `max_nodes`、`max_services` 或其他目录规模上限，不按假定峰值预分配；
- 目录内部提供当前快照版本、Node 数量和 Service 实例数量等只读统计，供 Node 诊断和
  测试观察异常增长；M14 不因此增加业务公开 Stats API；
- NodeID、ServiceName、SessionID、重复逻辑实例和契约元数据必须严格校验；
- Origin、etcd Provider 后续分别负责其协议消息大小、分页和输入来源边界，本地目录不重复
  增加数量限制；
- 是否对快照或事件对象池化必须由最终 Benchmark 和逃逸分析决定，不能预先增加池化
  复杂度。

### 11.3 公共对象所有权

公共边界采用“业务独立持有”：

- 内部不可变 `Snapshot`、Map、Slice 和 `*Instance` 永不直接返回给业务；
- 每个监听器分别取得自己的 `discovery.Event.Services` Slice，一个监听器的修改不能影响
  其他监听器；
- Event 可以在回调返回后继续保存，不存在仅在回调期间有效的借用生命周期；
- 精确查询返回一个值副本；
- 批量查询返回按稳定顺序排列、由调用方拥有的 Slice；
- 查询结果若包含 Labels Map，必须深复制 Map；字符串和固定数组按值复制；
- 公共 Event 和查询结果不能池化，因为框架无法知道业务何时释放；
- RPC Runtime 热路径不调用公共复制接口，继续直接读取内部不可变指针并保持零分配。

服务发现和业务监听属于冷路径，正常 Service 通常只有一个监听器。这里接受少量复制成本，
换取明确所有权和跨 Await、长期保存时的安全性；不提供只在回调期间有效的零复制迭代器。

## 13. 已确认结论汇总

1. M14 从 NATS RPC 调整为本地服务发现目录与关注筛选；
2. NATS RPC 顺延到 M15，完整停止顺延到 M16；
3. 每个 Node 独立拥有发现目录和可见快照；
4. Service 只查询或监听，不拥有完整发现列表；
5. TCP/NATS 共用同一目录、筛选和错误语义；
6. 同 Node 本地调用不走远端服务发现；
7. 目录只接受完整原始快照；
8. 采用 `atomic.Pointer` 发布不可变快照；
9. 精确查询使用 `NodeID + ServiceName`；
10. 快照同时提供按 ServiceName 的稳定候选索引；
11. RPC 热路径不使用 `RWMutex`；
12. TCP/NATS 远端发送前必须先确认当前 Node 已发现目标；
13. 未发现目标返回 `CodeRPCNoRoute`；
14. 已发现但 Transport 不兼容返回 `CodeTransportUnavailable`；
15. M13 TCP 临时目标表降为目录驱动的连接内部状态；
16. 采用显式、多监听器、ID 取消的 Service 监听 API；
17. 监听回调在所属 Service FIFO 调度上下文执行；
18. 监听回调接收 Origin Task Context，可以安全使用 `Await`；
19. 尚未执行的多个发现版本合并为最新净变化；
20. 监听器是状态同步，不承诺逐个交付短暂中间版本；
21. 不增加时间型 Lost 防抖，Provider 确认的变化立即发布；
22. SessionID 变化必须投递旧会话 Lost 和新会话 Discovered，不能按同名实例抵消；
23. Origin/etcd Provider 保持后续独立里程碑。
24. 监听注册、移除和快照应用共用冷路径短锁；
25. 首次补发统一为“空状态到最新状态”的净变化；
26. Service 达到任务准入上限时只设置一个“发现状态待同步”布尔值，容量恢复后再进入
    FIFO；
27. 监听器取消使用 ID 世代号使陈旧交付任务安全失效；
28. `OnInit`、`OnStart` 可以注册，但必须等 Runner 可调度后才执行回调。
29. 不限制每个 Service 的监听器数量，不增加监听器或事件数量配置。
30. 不限制快照 Node 和 Service 数量，不增加 `max_nodes`、`max_services` 配置；
31. 快照按实际规模增长并在内部提供版本、Node 数和 Service 实例数统计，不增加业务
    Stats API。
32. 原始 DTO 和 `ApplySnapshot` 位于 `internal/discovery`，业务不能修改发现状态；
33. 目录取得传入 DTO 的独立内存所有权，不引用 Provider 后续可变数据；
34. 原始快照不携带 Provider Revision 和 RPC 方法列表；
35. 零 ContractID、零 Fingerprint 表示可发现但不公开 RPC 的 Service。
36. 重复快照使用 Map 精确比较，不使用内容哈希或规范字节序列化；
37. 未变化的不可变 `Instance` 指针在新快照中复用；
38. 输入校验失败时整批拒绝，旧快照、连接需求和监听状态均不改变；
39. 仅在真实变化时发布版本并排序候选索引，快照和实例首版不池化。
40. `Retired` 只是可观察状态，框架不限制精确 RPC/Notify/Broadcast 或入站处理；
    M19/M20 自动范围默认排除 Retired，显式 `IncludeRetired()` 后纳入；
41. 发现事件携带 ServiceName 和 ServiceState，Lost 携带最后已知状态；
42. TCP 连接按可见 RPC Service 形成 Node 级需求，Running/Retired 规则一致；
43. 快照先发布，再非阻塞对齐 TCP 目标，短暂未连接返回 Transport 错误；
44. TCP 连接目标和握手绑定 SessionID，旧会话连接不能承载新请求；
45. 一个监听器一次注册并实现 `OnDiscovered`、`OnStateChanged`、`OnLost`；
46. 三类事件都携带 ServiceName 和状态，状态变化不伪装成 Lost/Discovered。
47. 每个 Node 生命周期内只使用一个发现来源，不热切换或合并；
48. 无正式 Provider 时使用不可配置的 Application 过渡数据源，仍走真实 TCP；
49. Node 全部 Service 成功完成 `OnStart` 后才一次性发布，禁止部分 Service 提前可见；
50. OnStart 期间可以持续发现并调用已经 Ready 的远端 Service；
51. OnStart 使用带私有生命周期令牌的同一 `Service.Await` 和生成 `AwaitXxx` 外观；
52. 生命周期 Await 阻塞原启动 goroutine，不启动或切换普通业务 Runner；
53. 生命周期 Await 仍使用 M8 DeadlineQueue，非法、跨 Service 或陈旧 Context 被拒绝；
54. Provider 发布失败只重试发布，不重复 OnStart，取消后反序回滚；
55. 目标端接受启动中 Node 的 RPC 不要求调用方已经被目标发现；
56. 现有错误码只有语义准确时才复用；确有稳定、可区分的新语义时必须新增专用 Code；
57. M14 本地目录场景不需要新增服务发现错误码；后续 M16 的 Provider 健康状态使用独立
    `CodeDiscoveryUnavailable=5001`，不能用于普通无实例；
58. Event 不公开内部快照版本，每个监听器取得独立的 Services Slice；
59. 公共查询结果由业务独立持有，内部快照永不暴露；
60. 公共 Event 和查询结果不池化，RPC 热路径仍使用内部零复制快照；
61. 业务可见只读类型统一放在公开 `discovery` 包；
62. `FindDiscoveredService` 和 `ListDiscoveredServices` 直接组合到 `Service`；
63. 公开查询只返回远端实例，并同时返回 Running 与 Retired；
64. 地址、Transport 和契约元数据仅供内部 RPC Runtime 使用，不向业务查询接口公开；
65. 发现事件保留每个 Service 的 State，用于表达 Running、Retired 和 Lost 前最后状态；
66. 验收采用单元、真实 TCP 集成、Race、Fuzz、Benchmark、逃逸和 Windows/Linux 双平台
    全量验证，不在 M14 建设长期压测框架；
67. `AwaitService` 和 `AwaitNodeService` 只等待远端可见实例，不要求目标公开 RPC；
68. `AwaitNodeService` 指向当前 Node 时立即返回 `CodeInvalidArgument`，本地依赖使用
    `LookupService` 和声明顺序。

## 15. 实施与验收结果

### 15.1 实现结果

M14 已完成以下闭环：

1. 新增公开 `discovery` 只读 DTO、监听器和 ID 取消语义；
2. 新增 `internal/discovery` 完整快照、严格校验、关注筛选、稳定 Diff、不可变索引和
   `atomic.Pointer` 发布；
3. 每个 Node 独立拥有可见目录，Application 只持有进程内过渡 Source；
4. 全部 Service 完成 `OnStart` 后才一次性开放入站并发布本 Node，失败时不会形成部分
   可见状态；
5. `Service.Await` 支持带私有令牌的 OnStart 生命周期 Context，普通 Runner 在统一屏障
   前不会启动；
6. Service 查询、等待、监听、首次补发、状态变化、Lost、SessionID 替换和 FIFO 合并
   已接入唯一工作调度；
7. TCP RPC 在发送前统一读取发现目录，按可见性、契约、Transport 和 SessionID 选择
   连接；连接目标由目录完整集合对账；
8. 过渡 Source 会向全部消费者交付同一轮完整快照；单个消费者失败不会阻断其他健康
   Node，Source 会恢复发布前记录、广播回滚快照，并向发布方返回首个错误执行启动回滚；
9. 公共查询和 Event 由业务独立持有，内部快照、RPC 热路径对象和候选索引不向业务暴露。

实现未新增快照、事件或发现 Task 对象池。内部精确查询和候选读取实测为零分配；快照
更新是低频冷路径，公开 Event 又无法确定业务保存期限，池化只会增加所有权和 ABA 风险，
不符合当前收益与复杂度比例。
