# Origin 第三版服务退休设计

> 文档类型：已实现详细设计

## 1. 文档状态与范围

- 状态：本文范围内的方案已确认
- 首次确认：2026-07-24
- 最后更新：2026-08-09
- 适用版本：Origin v3

本文只规定 Service 退休状态，以及退休与正式停止之间的状态边界。

2026-07-29 最新确认覆盖早期“退休自动拒绝新入站 RPC”的方案：`Retired` 只是一项框架
维护并对外发布的可观察状态。Origin 不因退休自动拒绝 RPC、摘除路由、暂停 Timer 或进入
停止流程，具体业务行为由项目决定。

2026-07-30 的 M19 只增加自动摘流例外：`ToService` 自动实例选择排除 Retired；
`ToServiceOnNode` 精确调用、普通入站准入、发现可见性和连接需求保持不变。

2026-08-01 的 M20 统一自动范围规则：单目标和 Broadcast 默认都排除 Retired；业务需要
维护、排空或恢复类调用时，通过唯一的轻量值派生 `IncludeRetired()` 显式把 Running 与
Retired 一并纳入。精确 `OnNode` 仍直接允许 Retired。

M21 已实现公开 API、本地状态事件、发现发布顺序，以及 Node/Application 批量编排。M4
控制邮箱现已把 `retire/resume` 一级子命令接入运行中 Application；状态事件沿用本地事件的
错误隔离规则，批量状态切换按确定顺序尽力完成并返回聚合错误。

所有 Service 启动成功后固定先进入 `Running`。退休只属于运行期显式操作，不存在初始
Retired 启动分支。

## 2. 设计目标

1. 提供一个介于正常运行和正式停止之间的稳定、可观察状态；
2. 业务可以用该状态表达维护、迁移、人数控制或临时降级；
3. 框架不替业务猜测哪些 RPC、Timer 或事件应当停止；
4. 只有明确收到 Stop 信号，Service 才进入正式关闭流程；
5. 其他 Node 可以通过服务发现观察状态并自行调整业务；
6. 状态语义简单，不把退休、摘流、排空和停止绑定成隐式流程。

## 3. 状态模型

```text
Running  -> Retired
Retired  -> Running     仅由明确恢复操作触发
Running  -> Stopping    仅由明确 Stop 信号触发
Retired  -> Stopping    仅由明确 Stop 信号触发
Stopping -> Stopped
```

`Retired` 是稳定运行状态：

- 不会因任务排空自动进入 `Stopping`；
- 不会自动关闭 Service、Transport、Timer 或其他资源；
- 不会自动调用 `OnStop`；
- 没有 Stop 或 Resume 信号时可以一直保持 `Retired`。

`Resume` 的含义严格限定为 `Retired -> Running`：Service 本身一直处于运行中，只是重新加入
默认自动路由候选。它不是重启，不重新执行 `OnInit` 或 `OnStart`，也不能把 `Stopping`、
`Stopped` 或 `Failed` 恢复为 Running。需要重新创建资源或重跑生命周期的场景应执行完整
Stop 后重新启动 Node/Application，不能借用 `Resume`。

## 4. 状态切换

M21 已确认公开：

```go
func (s *Service) Retire(ctx context.Context) error
func (s *Service) Resume(ctx context.Context) error
```

`Running` 上 Retire、`Retired` 上 Resume 执行转换；同状态重复调用返回 nil。其他状态返回稳定的
生命周期错误。状态切换必须在 ServiceScheduler 的有序控制边界内完成：

1. 把状态从 `Running` 原子切换为 `Retired`，或从 `Retired` 切回 `Running`；
2. 更新状态进入时间和统计；
3. 向所属 Service 的本地事件队列提交 `ServiceStateChanged`；
4. Node 合并同一轮状态变化，并向 Discovery Provider 发布包含全部本地 Service 的最新完整快照；
5. `Retire/Resume` 在 Context 内等待对应或更新 generation 的 Provider Publish Ack。

状态锁内不能调用用户代码、执行网络操作或直接回调发现监听器。状态发布和业务回调使用
各自既有的异步边界。

### 4.1 为什么先产生本地状态事件，再发布发现快照

以 `PlayerService.Retire(ctx)` 为例：

1. 本地状态立即切为 Retired，本进程的自动 RPC 路由立刻不再选择该实例；
2. `ServiceStateChanged{Previous: Running, Current: Retired}` 进入该 Service 事件队列，业务可以暂停登录
   入口、调整 Timer，但精确管理 RPC 和存档仍可继续；
3. Node 向 Provider 发布包含 Retired 的最新完整快照；
4. 其他 Node 收到快照后，从默认自动路由候选移除该实例，但保留发现记录和连接；
5. Provider Ack 后 `Retire` 返回 nil。

这里的“先事件、后发布”指先确定本地事实并按顺序提交事件，再发起 Provider 发布；不要求业务
监听者必须在网络发布前全部执行完。若 Provider 暂时失败，`Retire` 返回发现错误，但本地状态
仍保持 Retired，Provider 发布器保留最新期望 generation 并在恢复后重试，不把本地状态静默
回滚为 Running。这样同一进程不会在返回错误后继续接收自动流量，远端也最终收敛到最新状态。

## 5. RPC、事件和后台任务

`Running` 与 `Retired` 使用相同的框架准入规则：

- 请求—响应 RPC 正常进入 Service Ready 队列；
- 已经精确投递到该实例的 Notify 和 Broadcast 正常进入 Service；
- `ToServiceOnNode` 精确单目标不会排除退休实例，自动单目标与 Broadcast 默认排除，
  `IncludeRetired()` 后显式纳入；
- Service 可以继续发起出站 RPC、Redis 和数据库访问；
- 本地同步、异步事件正常执行；
- Timer、Await 恢复和异步结果回调正常执行；
- TCP/NATS 连接不会仅因退休关闭。

业务需要摘流时，在自己的 RPC 实现、路由策略或状态钩子中明确处理。例如业务可以查询
当前 Service 状态后返回统一的 `errs.ErrServiceRetired`，也可以只拒绝登录类 RPC、继续
允许存档和管理 RPC。Origin 不在通用 Dispatcher 中增加退休判断。

这种边界避免框架统一拒绝后，业务无法在退休期间完成迁移、存档、管理或恢复操作。

## 6. Timer 行为

Service 退休时不自动暂停或取消任何 Timer。业务需要暂停某个 Timer 时，保存其 TimerID
并显式调用：

```go
PauseTimer(timerID TimerID) bool
ResumeTimer(timerID TimerID) bool
```

框架不猜测 Timer 属于流量入口、后台维护还是状态保存。

## 7. 与正式 Stop 的边界

只有明确 Stop 信号可以使 `Running` 或 `Retired` 进入 `Stopping`。进入 `Stopping` 后才
执行：

- 关闭新任务准入；
- 排空 Ready、Running、Awaiting 和 RPC pending；
- 取消或清理 Timer；
- 执行 `OnStop` 及其受控 Await；
- 关闭业务和 Transport 资源；
- 最终进入 `Stopped`。

退休不会提前执行上述步骤，也不会在任务排空后自动停服。完整停止顺序见
[Service 优雅停止设计](./2026-07-24-服务优雅停止设计.md)。

## 8. 服务发现与连接

退休不会使 Service 从发现目录消失：

- 不产生 `Lost`；
- Service 查询结果继续包含该实例及 `Retired` 状态；
- `ToServiceOnNode`/`OnNode` 精确 RPC、Notify 和 Broadcast 仍可选择该实例；
- 自动单目标和 Broadcast 默认不把该实例作为新流量目标；
- 显式 `IncludeRetired()` 后，自动单目标和 Broadcast 都把 Running 与 Retired 纳入；
- TCP 连接需求保持不变；
- `Running <-> Retired` 产生明确状态变化通知；
- 发现和失去发现事件均携带相应 Service 的状态，Lost 携带最后已知状态。

发现事件只是远端状态同步信号。它不同于所属 Service 通过
`ServiceStateChangedEventID` 收到的本地 `ServiceStateChanged`：本地事件只在真实转换时
异步投递，远端 discovery `OnStateChanged` 表示发现快照中的其他实例发生变化。业务跨越
Await 后提交状态前，需要重新查询当前最新快照。

## 9. 错误处理

`CodeServiceRetired` 和 `ErrServiceRetired` 继续作为推荐的统一错误语义保留，但改由业务
显式返回。Origin Runtime 和 RPC Dispatcher 不因看到 `Retired` 自动产生该错误；
M19/M20 自动范围默认摘除，在没有合法目标时返回 `CodeRPCNoRoute`。

Notify 和 Broadcast 没有远端错误响应时，业务自行决定忽略、处理或记录指标；框架不因
退休静默丢弃。

## 10. 并发与调度约束

- 状态切换由 ServiceScheduler 串行化；
- 状态切换不创建第二个业务执行协程；
- RPC、Timer、事件和 Await 恢复继续共用唯一 Service 执行槽；
- 状态监听回调进入监听方 Service Runner；
- Provider、TCP、NATS 或 Timer goroutine 不直接执行业务状态回调；
- 正式 Stop 与 Resume 竞争时，`Stopping` 一旦发布便不能恢复到 `Running`。

## 11. 可观测性

至少提供：

- 当前状态和状态进入时间；
- 退休、恢复次数及退休持续时间；
- 状态发布到 Discovery Provider 的延迟；
- 远端可见状态和本地实际状态不一致的持续时间；
- 业务主动返回 `CodeServiceRetired` 的数量可以按普通 RPC 错误码统计。

框架不再提供“因退休自动拒绝 RPC”的内部计数，因为不存在该自动行为。

## 12. 测试要求

实现至少验证：

1. `Running -> Retired -> Running` 状态转换；
2. Retired 不会自动进入 Stopping；
3. 只有明确 Stop 信号能进入 Stopping；
4. Retired 仍能接收请求—响应 RPC、Notify 和 Broadcast；
5. Retired 仍能执行本地事件、Timer、Await 恢复和异步回调；
6. Retired 仍能发起出站操作；
7. 业务可以主动返回 `ErrServiceRetired`；
8. 退休不产生 Lost，不关闭 TCP/NATS 连接；
9. 远端监听者能观察 Running 与 Retired 状态变化；
10. Stop 与 Resume 竞争时不会从 Stopping 恢复；
11. 全程满足 Service 单执行槽约束。
12. Application CLI 的 Retire/Resume 跨进程往返、总体 timeout、并发串行与崩溃恢复；
13. 真实状态转换产生 `ServiceStateChanged`，幂等重复调用不产生事件。

## 13. 已确认结论

- `Retired` 是稳定、可观察的运行状态；
- 框架不因退休自动拒绝或丢弃任何 RPC、Notify、Broadcast；
- `ToService` 自动路由排除退休实例，`ToServiceOnNode` 精确路由仍可调用；
- Broadcast 使用同一默认摘流规则，`IncludeRetired()` 为业务保留显式纳入能力；
- 退休不自动暂停 Timer、关闭连接、排空或停止；
- 业务自行决定退休期间允许和拒绝的具体操作；
- `CodeServiceRetired` 保留给业务主动返回；
- 退休状态通过服务发现发布，且不冒充 Lost；
- 只有明确 Stop 信号启动正式关闭；
- `Resume` 只执行 `Retired -> Running`，不重新调用 `OnInit/OnStart`；
- Service 状态先在本地线性化并提交状态事件，再由 Node 合并发布完整发现快照；
- Provider 发布失败不回滚本地状态，发布器保留最新 generation 并恢复重试；
- Node/Application Retire 按启动严格逆序，Resume 按启动正序；
- 批量状态切换尽力完成并聚合错误，不提供事务回滚，Stop 始终优先。

## 14. Node 与 Application 批量编排

M21 已确认提供薄的 Node/Application `Retire(ctx)`、`Resume(ctx)` 编排，不增加独立的
Node/Application Retired 状态：

```text
启动正序：  DatabaseService -> PlayerService -> GatewayService
Retire：    GatewayService  -> PlayerService -> DatabaseService
Resume：    DatabaseService -> PlayerService -> GatewayService
```

理由是启动顺序通常表达“依赖先启动、使用者后启动”：

- Retire 严格逆序，使入口和上层使用者先离开默认路由，避免它们继续把新工作交给已经退休的依赖；
- Resume 严格正序，使底层依赖先重新可选，再开放上层使用者和流量入口；
- 如果所有 Service 彼此独立，这一顺序不会带来额外语义；一旦存在依赖，它比统一正序或统一逆序更安全。

批量操作使用确定性的 best-effort：按上述顺序继续处理全部 Service，最后聚合错误；它不是事务，
不会因为中间一个 Service 发布失败而回滚已经完成的状态。Stop 与批量 Resume 竞争时 Stop 始终胜出。

### 14.1 Application 运行期命令

外部进程使用 AppName 和 PID 目录控制整个 Application：

```text
game-server retire --app-name game --pid-dir ./run --timeout 30s
game-server resume --app-name game --pid-dir ./run --timeout 30s
```

命令不接收 `--node` 或 `--service`。目标进程的唯一 Application 生命周期循环串行消费强类型
`ControlRequest`，分别调用 `Application.Retire/Resume`；同一时刻不会并发执行 Retire、Resume
和 Stop。`--timeout` 覆盖定位、控制锁、目标执行与响应等待，超时不 Kill、不回滚已提交状态。

Service 在 `OnInit` 注册本地事件：

```go
return s.SubscribeEvent(
    service.ServiceStateChangedEventID,
    func(_ context.Context, raw service.Event) error {
        changed := raw.(service.ServiceStateChanged)
        observe(changed.Previous, changed.Current, changed.ChangedAt)
        return nil
    },
)
```

监听器失败或 panic 按异步事件边界隔离，不能撤销状态；Provider 发布失败也只作为控制结果
返回并保留最新期望 generation，不回滚本地状态。
