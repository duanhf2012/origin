### 1.1 里程碑落地边界

本文描述的是 RPC 的完整目标语义，不表示所有能力都在 M11 一次实现：

- M11 生成 `AsyncXxx`、`AwaitXxx`、`NotifyXxx` 和 `BroadcastXxx`，并完成同 Node
  调用闭环；
- M11 的客户端统一使用一个生成类型、一个构造函数和 `rpc.Target`，不生成 Node 专用客户端；
- M11 请求—响应只使用最小本地完成状态，不引入 RequestID、远程 pending 表或连接状态；
- M11 一并完成普通 Go 结构体及其容器、嵌套 Protobuf 等内置静态编解码；
- M13 才引入 TCP 线协议、RequestID、远程 pending 状态和连接管理；
- M14 接入公共服务发现目录，M15 接入 NATS Transport；
- M11 的 `BroadcastXxx` 对当前 Runtime 已知的本地目标执行真实投递；服务发现和路由
  里程碑只扩展为多 Node 可见目标；
- M19 完成自动单目标路由，M20 完成多 Node Broadcast、显式 `IncludeRetired()` 和
  多目标部分失败聚合，不改变既有业务方法签名。

M11 的具体开工边界和已确认结论以
[M11 RPC 契约与代码生成设计](../milestones/M11-RPC契约与代码生成设计.md)为准。

## 2. 设计目标

1. 开发者只定义一份符合 Go 习惯的服务端 RPC 接口。
2. `origingen` 根据接口签名生成明确的 `Async`、`Await`、`Notify` 和 `Broadcast` 客户端方法。
3. 用户在普通场景中不需要直接操作 Future，也不需要手工组合 `Service.Await`。
4. 方法名称必须显式表达“立即返回”“挂起当前 Service 任务”或“不等待远端响应”。
5. 允许多个输入和多个输出，不强制所有内部 RPC 包装成单一 Request/Response。
6. 客户端始终获得统一的最终 `error`，不能丢失路由、传输、超时、取消和编解码错误。
7. 保留 v2 `Go` 和 `CastGo` 的通知、广播能力，但使用强类型生成接口和更明确的名称。
8. 所有生成外观共用同一个底层调用实现，不复制路由、序列化、pending 和超时逻辑。

## 3. RPC 接口声明

业务开发者使用 Go 接口声明服务端契约。例如：

```go
type PlayerRPC interface {
    GetPlayer(
        ctx context.Context,
        playerID int64,
    ) (*pb.Player, error)

    SavePlayer(
        ctx context.Context,
        player *pb.Player,
    ) error

    PlayerOnline(
        ctx context.Context,
        playerID int64,
    )
}
```

首版保持一个 Service 最多绑定一个公开 RPC 接口。该接口必须直接声明该 Service 的全部 RPC 方法，不支持嵌入其他接口，也不支持把不同 Service 的 RPC 聚合成一个客户端。一个 Service 可以完全不公开 RPC。

方法实现可以分散在多个 `.go` 文件中，但 RPC 接口保持一份明确的对外契约。详细的客户端生成与目标绑定规则见 [Origin v3 单目标 RPC 客户端与路由设计](./2026-07-24-单目标远程调用客户端与路由设计.md)。

服务端实现原始方法名：

```go
func (s *PlayerService) GetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error) {
    return s.repository.Load(ctx, playerID)
}
```

服务端不实现 `AsyncGetPlayer`、`AwaitGetPlayer`、`NotifyPlayerOnline` 或 `BroadcastPlayerOnline`。这些名称只属于生成的客户端。

## 4. 输入参数规则

### 4.1 Context

- `context.Context` 必须是第一个参数；
- 每个 RPC 只允许一个 Context；
- Context 不进入 RPC 数据载荷；
- 生成客户端使用该 Context 传播 Deadline 和取消信号。

### 4.2 多输入参数

Context 之后允许零个或多个输入参数，不设置人为数量上限。例如：

```go
TransferItem(
    ctx context.Context,
    fromPlayerID int64,
    toPlayerID int64,
    item *pb.Item,
    count int32,
) error
```

每个参数独立应用 RPC 数据与序列化设计中的类型规则。多个参数由生成的内部请求布局编码到同一个 RPC 帧，不要求开发者创建公开包装结构体。

### 4.3 禁止可变参数

RPC 接口不支持 `...T`：

```go
Bad(ctx context.Context, playerIDs ...int64)
```

应改为明确的 Slice：

```go
Good(ctx context.Context, playerIDs []int64)
```

这样可以保持线协议只有一种表达，也避免函数调用语法影响远端契约。

## 5. 输出参数与 error 规则

### 5.1 多业务输出

RPC 允许零个或多个业务输出。例如：

```go
GetPosition(
    ctx context.Context,
    entityID int64,
) (
    x float32,
    y float32,
    z float32,
)
```

### 5.2 error 可以声明，也可以省略

请求—响应 RPC 的服务端声明可以包含 `error`，也可以省略：

```go
GetPlayer(ctx context.Context, playerID int64) *pb.Player

GetPlayerWithError(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

服务端声明没有 `error` 时，服务端无法主动向调用方返回业务错误；生成客户端仍会追加一个最终 `error`，用于报告 RPC 框架错误。

服务端声明已经包含 `error` 时，生成客户端复用该位置，不再追加第二个错误。唯一的最终 `error` 同时承载服务端业务错误和 RPC 框架错误。

### 5.3 error 必须位于最后

只要返回列表中存在可赋值给 Go `error` 接口的类型，就必须满足：

- 最多出现一次；
- 必须是最后一个返回值。

合法：

```go
Xxx(ctx context.Context)
Xxx(ctx context.Context) error
Xxx(ctx context.Context) T1
Xxx(ctx context.Context) (T1, T2, T3)
Xxx(ctx context.Context) (T1, error)
Xxx(ctx context.Context) (T1, T2, T3, error)
```

非法：

```go
Xxx(ctx context.Context) (error, T1)
Xxx(ctx context.Context) (T1, error, T2)
Xxx(ctx context.Context) (T1, error, error)
Xxx(ctx context.Context) (error, error)
```

`origingen` 不得自动重排返回值。发现错误位置非法时，必须在生成阶段终止并给出修改建议。例如：

```text
cannot generate RPC method PlayerRPC.Xxxx

reason:
  error return must be the final result

got:
  (T1, error, T2, T3)

expected:
  (T1, T2, T3, error)
```

需要把错误详情作为普通业务数据传输时，应定义 `ErrorInfo` 等可序列化结构体，不应使用实现 `error` 的类型占据业务返回位置。

## 6. 方法分类与生成规则

`origingen` 根据服务端返回签名自动分类：

| 服务端返回签名 | 调用类型 | 生成方法 |
|---|---|---|
| 一个或多个业务返回值，无 `error` | 请求—响应，也允许主动放弃结果 | `AsyncXxx`、`AwaitXxx`、`NotifyXxx`、`BroadcastXxx`，请求—响应外观补最终 `error` |
| 一个或多个业务返回值，末尾为 `error` | 请求—响应，也允许主动放弃结果 | `AsyncXxx`、`AwaitXxx`、`NotifyXxx`、`BroadcastXxx`，请求—响应外观复用该 `error` |
| 只返回 `error` | 需要远端确认，也允许主动放弃确认 | `AsyncXxx`、`AwaitXxx`、`NotifyXxx`、`BroadcastXxx` |
| 完全没有返回值 | 只有通知语义 | `NotifyXxx`、`BroadcastXxx` |

带任意返回值的方法仍具有请求—响应语义，但调用方可以显式选择 `NotifyXxx` 或
`BroadcastXxx`，主动放弃业务结果和远端业务错误。接口名前缀明确表达这一选择，不额外增加
注解或重复契约方法。

## 7. Async 生成接口

### 7.1 外观

原始定义：

```go
GetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

生成：

```go
AsyncGetPlayer(
    ctx context.Context,
    playerID int64,
    callback func(
        context.Context,
        *pb.Player,
        error,
    ),
) error
```

多返回值按原业务顺序进入回调，并始终以最终 `error` 结尾：

```go
AsyncGetPosition(
    ctx context.Context,
    entityID int64,
    callback func(
        context.Context,
        float32,
        float32,
        float32,
        error,
    ),
) error
```

### 7.2 Service 执行语义

`AsyncXxx`：

1. 立即发起底层 RPC；
2. 注册完成回调；
3. 不释放当前 Service 执行槽；
4. 调用函数立即返回，当前 Service 任务继续运行；
5. RPC 完成、失败、取消或超时后，把回调作为新任务追加到调用方 Service 的 FIFO Ready 队列；
6. 回调重新取得 Service 执行槽后才能访问 Service 状态；
7. 回调不能在网络、NATS 或 TimerEngine goroutine 中直接执行；
8. 即使 RPC 在注册后立即完成，也不能抢占当前 Running 任务。

`AsyncXxx` 自身返回立即提交 `error`。参数、编码、目标、路由或队列准入失败时直接返回
非 nil，不创建 pending，也不投递回调；返回 nil 后，响应、业务错误、后续框架错误、取消
或超时必须且只能通过强类型回调完成一次。这样调用方可以立即处理尚未进入异步状态机的
框架错误，同时不会对同一失败既返回 error 又执行回调。

示例：

```go
if err := s.playerRPC.AsyncGetPlayer(
    ctx,
    playerID,
    func(
        callbackCtx context.Context,
        player *pb.Player,
        err error,
    ) {
        if err != nil {
            s.onLoadFailed(playerID, err)
            return
        }

        s.players[playerID] = player
    },
); err != nil {
    s.onLoadFailed(playerID, err)
    return
}

s.loadingPlayers[playerID] = true
```

普通业务用户不需要直接取得或保存 Future。生成的 `AsyncXxx` 内部仍可以使用 Future 统一管理 pending、完成、超时和取消。

### 7.3 Draining 中的 pending 与回调

每个 Async pending 记录必须包含所属 Service，供 RPC Runtime 在 Service 优雅停止时判断未完成调用。该归属本来就是把回调投递回调用方 Service 所需的信息，不为停止流程创建新的 TaskScope 或独立计数器。

Service 进入 Draining 后：

- Stop 前已经登记的 Async 继续等待响应、错误、超时或取消；
- 正在排空的任务和 Async 回调仍可以发起新的 `AsyncXxx`；
- 新调用在提交到 Transport 前先登记到所属 Service 的 pending 表；
- 所有新调用继承 Service 关闭 Context 的上限；
- 新的入站 RPC、Timer 和普通本地事件仍由 ServiceScheduler 拒绝。

Async 完成时必须：

1. 使用一次性终态转换防止响应、超时和取消重复完成；
2. 先把强类型回调发布到所属 Service 的 Ready 队列；
3. 确认发布成功后再删除 pending 记录。

该顺序保证排空检查不会在“pending 已删除、回调尚未进入 Ready”的窗口提前进入
`OnStop`。已经返回 nil 的调用即使立即完成也使用同一路径；尚未接受的立即提交失败直接由
`AsyncXxx` 返回，不登记 pending 或回调。

详细排空规则见 [Origin v3 Service 优雅停止设计](./2026-07-24-服务优雅停止设计.md)。

## 8. Await 生成接口

### 8.1 外观

原始定义：

```go
GetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

生成：

```go
AwaitGetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

调用：

```go
player, err := s.playerRPC.AwaitGetPlayer(ctx, playerID)
if err != nil {
    return err
}

s.players[playerID] = player
```

### 8.2 内部语义

`AwaitXxx` 内部：

1. 先完成不需要等待的静态参数、owner 和 Task Context 校验；
2. 调用 Service 执行系统的内部 Await 原语并原子释放当前 Service 执行槽；
3. 在原任务 goroutine 的 Await 等待函数中使用与 `AsyncXxx` 相同的底层调用核心；
4. 编码、路由、提交和等待都使用 Await 已计算的唯一有效 Context；
5. 提交失败或 Future 完成后，将原任务追加到 FIFO Ready 队列；
6. 原任务重新取得执行槽后，向业务代码返回结果。

在 `OnStop(ctx)` 的 finalizer 上下文中，生成接口外观不变，但内部不执行第 3、5、6 步的普通 Runner 交接。finalizer goroutine 直接等待 Future 或 Context，完成后由同一个 goroutine 继续执行 `OnStop`，期间不调度普通 Service 任务。

`OnStop` 的收尾外部调用只使用 `AwaitXxx`。`AsyncXxx`、Notify 和 Broadcast 不作为 finalizer 收尾方式，因为它们不能让 `OnStop` 的返回值准确表示远端工作已经完成。

该特殊路径只用于停止收尾，详见 [Origin v3 Service 优雅停止设计](./2026-07-24-服务优雅停止设计.md)。

概念上等价于：

```go
func (c *playerRPCClient) AwaitGetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error) {
    var player *pb.Player

    err := c.owner.Await(ctx, func(waitCtx context.Context) error {
        var callErr error
        player, callErr = c.callGetPlayer(waitCtx, playerID)
        return callErr
    })
    return player, err
}
```

该代码只描述语义。生成实现不公开 Future；闭包、调用状态和返回值保存是否产生分配必须
通过 M11 Benchmark 与逃逸分析验证。Deadline 从进入 Await 开始覆盖编码、路由、提交、
目标排队、业务执行、响应和恢复排队。

`Await` 前缀是显式挂起标记。普通用户不需要再手工写闭包：

```go
var player *pb.Player

err := s.Await(ctx, func(waitCtx context.Context) error {
    var callErr error
    player, callErr = client.GetPlayer(waitCtx, playerID)
    return callErr
})
```

### 8.3 PendingCall 与对象复用

v3 不复制 v2 中 Future、Call 和 Request 多套重叠对象。请求—响应调用使用一个内部 `pendingCall` 统一保存 RequestID、目标、Deadline、TimerID、一次性完成状态、结果和等待通知，并使用专用类型池复用。

`pendingCall` 的释放时机不是响应到达，而是：

1. 响应、超时、取消或断线完成一次性终态转换；
2. 从 pending 表删除；
3. Await 或 Async 消费者取得并复制结果；
4. 清空 response、error、Context、回调、Service、TimerID 和 channel 残留；
5. 放回专用池。

“复制结果”包含业务可见的普通 `[]byte`：Await 返回和 Async 回调取得独立 Slice，不能
引用 `pendingCall` 持有的响应 Buffer。nil 与非 nil 空 Slice 必须保持区别。业务可以在
Await 返回或 Async 回调结束后继续保存和修改该 Slice，不需要归还给框架。

响应、Timeout 和取消事件使用连接标识与 RequestID 查询 pending 表，不能长期持有可复用的 `*pendingCall` 指针。旧事件在记录删除后直接丢弃，防止操作已经复用的新调用。

Protobuf Request 和 Response 业务消息不自动池化。网络请求元数据优先使用值类型或预分配队列槽位；只有 Benchmark 证明仍存在显著分配热点时，才建立新的专用池。完整规则见 [Origin v3 内存复用与对象池设计](./2026-07-25-内存复用与对象池设计.md)。

### 8.4 统一 Deadline 与取消

RPC 不建立独立的默认超时配置。通用 `Service.Await`、生成的 `AwaitXxx`、生成的
`AsyncXxx` pending 以及 Redis、数据库等外部等待统一使用：

```text
调用方显式 Deadline
    > Service.SetDefaultAwaitTimeout
    > Node scheduler.default_await_timeout
    > Origin 内置 15s
```

一次调用只计算一个有效 Context、一个有效 Deadline，并且只能登记一个逻辑计时器。
`AwaitXxx` 直接使用 Service Await 原语，不再附加第二个 RPC `15s`。显式 Deadline
继续使用调用方 Context 已有的 Go Runtime Timer，不再登记 M8；没有 Deadline 的合法
Context 使用统一默认值和一条 M8 Deadline。M8 派生 Context 必须公开计算后的
`Deadline()`，但不能创建第二个 Go Runtime Timer。

`context.Background()` 和 `context.TODO()` 在超时选择层属于没有 Deadline；允许普通
Context 的框架入口会为其使用 M8 默认超时。生成的 `AwaitXxx` 仍需要当前 Origin Task
Context 维护调用方 Service 执行权，不能用裸 Background 绕过该校验。

`nil` 不属于“没有 Deadline 的 Context”，而是无效参数。生成的 `AwaitXxx` 必须在编码、
路由和投递前返回 `errs.ErrInvalidArgument`，不能将其替换成 `context.Background()` 或
自动套用 15 秒默认值。否则框架既无法识别当前任务，也无法证明调用该 API 的 goroutine
持有调用方 Service 的执行权。

### 8.5 跨进程 Deadline 传播

TCP 和 NATS Request 都在发送前读取上述唯一有效 Deadline，并在线协议中携带相对剩余
时间。两者统一使用向上取整的 `RemainingTimeoutMillis uint32`；TCP 从 M13 开发期实现的
`RemainingTimeoutNanos uint64` 迁移到该布局，并作为 M15 的同步实施范围。二者都不是
绝对 Unix 时间：

- 不依赖不同 Node 所在机器的时钟同步；
- 只做一次 Duration 计算和固定整数编解码；
- 不为封包额外创建 Timer、goroutine 或 Context；
- Notify 和 Response 不携带执行 Deadline。

目标 Node 在 Request 进入 Service FIFO 前检查剩余时间；值为零时按
`CodeDeadlineExceeded` 拒绝。合法 Request 使用目标 Node 共享的 M8 DeadlineQueue
建立一条本地 Deadline，覆盖目标 Service 排队和执行，并把可取消 Context 传给业务。
Redis、数据库和下游 RPC 应继续使用该 Context；下游发送前重新读取剩余时间，从而让
整条调用链消费同一时间预算。

调用方和目标端位于不同进程，不能共享 Timer。调用方的一条计时负责结束本地 pending，
目标端的一条 M8 计时负责终止目标资源占用，因此不违反“一次 Await 只登记一个调用方
Deadline”的规则。首版不发送 Cancel 包；手工取消只立即完成调用方，目标端最多运行到
原剩余 Deadline 或正常完成，迟到响应按 RequestID 终态安全丢弃。

NATS RPC Connection 禁用客户端 Reconnect Buffer；断线或重连期间的新调用直接失败，
不能把带有旧相对剩余时间的请求缓冲到重连后发送。普通网络传输造成的极小时间偏差首版
接受，不增加绝对时间戳、跨机时钟校准或第二个超时字段。

Async 不额外返回公开取消句柄。需要主动取消时，调用方使用 `context.WithCancel` 派生
Context；返回 nil 后的响应、超时、取消和断线通过同一个一次性终态完成回调，立即提交
失败直接返回且不进入该状态机。

## 9. Notify 通知

### 9.1 识别与生成

完全没有返回值的方法只有通知语义：

```go
PlayerOnline(
    ctx context.Context,
    playerID int64,
)
```

生成：

```go
NotifyPlayerOnline(
    ctx context.Context,
    playerID int64,
) error
```

带任意返回值的方法同时生成 Notify。例如：

```go
NotifyGetPlayer(
    ctx context.Context,
    playerID int64,
) error
```

`NotifyGetPlayer` 仍调用服务端 `GetPlayer`，但不编码、不传输也不保留其业务结果和业务
`error`。Notify 前缀明确表示调用方主动放弃远端结果。

### 9.2 语义

`NotifyXxx`：

- 根据路由规则选择一个目标 Service 实例；
- 不创建等待远端响应的 Future；
- 不进入 RPC pending 表；
- 不等待远端开始或完成业务处理；
- 返回的 `error` 只报告本地参数编码、服务路由、连接状态、发送排队或发送接受错误；
- 消息已经被底层接受后，Context 取消不能撤回消息；
- 服务端业务返回值不编码，业务失败或 panic 不能返回给调用方，只能通过服务端日志、
  指标和追踪暴露；
- 默认不自动重试，避免产生重复通知。

如果调用方必须确认远端是否执行成功，应调用该方法生成的 `AsyncXxx` 或 `AwaitXxx`；
`NotifyXxx` 无论原始方法是否返回 `error` 都不提供远端确认。

Notify 在接受前使用相同的有效 Context，内置 `15s` 最终兜底只约束本地编码、路由、
排队和发送接受阶段。底层接受后不创建 pending 或超时项，Context 取消不能撤回消息，
远端业务执行不受调用方 Deadline 约束。

## 10. Broadcast 广播

### 10.1 保留 v2 CastGo 能力

v2 `CastGo` 会把无响应 RPC 发送给当前网络中所有匹配服务所在的 Node。v3 保留该能力，
但把公共名称规范为 `BroadcastXxx`，并由 `origingen` 从 M11 起为全部 RPC 方法生成强类型
接口。

例如原始定义：

```go
PlayerOnline(
    ctx context.Context,
    playerID int64,
)
```

同时生成：

```go
BroadcastPlayerOnline(
    ctx context.Context,
    playerID int64,
) error
```

带返回值的 `GetPlayer` 同样生成：

```go
BroadcastGetPlayer(
    ctx context.Context,
    playerID int64,
) error
```

它只广播调用，不收集或编码任意远端 `Player` 与业务 `error`。

### 10.2 广播目标

`BroadcastXxx` 在语义上面向调用时客户端 Target 基础范围内所有可见且可路由的 Service。
M11 只有当前 Node `rpc.Runtime` 的本地注册快照，因此候选最多一个；没有目标或指定其他
Node 时返回无路由。后续服务发现接入后，继续使用相同方法并扩展为以下筛选：

标准 `ToService("AService")` 依次按以下条件筛选：

1. ServiceName 必须是 `AService`；
2. 必须支持生成阶段确定的稳定 RPC ContractID 和 MethodID；
3. 必须处于当前发现关注规则形成的可见快照；
4. 默认只接受 Running；Lost、未就绪、Retired、Failed、Stopping 或 Stopped 不进入
   自动目标集合；
5. 显式调用 `IncludeRetired()` 后，自动范围接受 Running 和 Retired；
6. 契约和生命周期合法但当前已知断开的实例仍属于 Broadcast 意图，并立即形成逐目标
   Transport 失败，不等待、不改选，也不静默删除。

M19 的 `ToService` 单目标自动选择默认只接受 Running，并排除已知断开实例；M20 让同一
`IncludeRetired()` 值派生同时作用于自动单目标选择和 Broadcast。精确 `OnNode` 本来就
允许 Running 或 Retired，因此不要求调用该派生。

因此，`node1/AService`、`node2/AService` 和 `node3/AService` 各收到一次；实现相同契约但
ServiceName 不同的实例不会误收。`ToServiceOnNode("node1", "AService")` 的基础范围最多
只有该实例。单目标轮询、随机、按 Key 或自定义 Selector 不缩小广播范围。

生成的 RPC 客户端和广播入口都是绑定 RPC 契约及当前 Node RPC Runtime 的强类型逻辑代理，不是一条 TCP 或 NATS 连接，也不拥有连接生命周期。连接建立、复用、重连和关闭统一由当前 Node 的连接管理器和 Transport 管理。

TCP 连接断开时，绑定在旧物理连接上的 pendingCall 立即以 Transport 不可用完成，不能等到
默认 `15s` 才发现断线。逻辑 Node 目标仍有效时，M13 Node 连接管理器使用有界指数退避和
抖动建立新的物理连接；目标被移除、Context 取消或 Node 停止时停止重连。重连只恢复后续
调用能力，框架不得自动重发已经失败的非幂等 Request 或 Notify。

TCP 发送队列过载时，新 Request 和 Notify 立即按过载失败；如果服务端连 Response 都无法
入队，则关闭该物理连接，使对端 pendingCall 立即结束。M5 只返回非阻塞 Transport 过载，
不理解这些 RPC 分类，也不会静默丢弃消息。

具体服务筛选与关注规则见 [Origin v3 服务发现与关注筛选设计](./2026-07-24-服务发现与关注筛选设计.md)。
Retired 只作为可观察状态，继续允许精确 RPC 和普通入站处理；M19/M20 自动范围默认摘除，
业务可以显式 `IncludeRetired()`。详见 [Origin v3 Service 退休设计](./2026-07-24-服务退休设计.md)。
单目标客户端与路由规则见 [Origin v3 单目标 RPC 客户端与路由设计](./2026-07-24-单目标远程调用客户端与路由设计.md)。

业务需要只广播某个区服、标签或任意业务子集时，可以从稳定发现快照筛选目标，再逐个构造
`ToServiceOnNode` 客户端调用 `NotifyXxx`。该能力作为自定义逃生通道保留；标准全范围广播
由 RPC Runtime 统一处理，业务不重复实现快照一致性、契约校验和传输优化。标准自动范围
默认排除 Retired；需要维护、排空或恢复类业务时显式调用 `IncludeRetired()`。

### 10.3 按 Node 合并投递

广播采用“语义按 Service 广播，传输按目标 Node 合并”的规则：

1. RPC Runtime 从一份不可变发现快照得到全部目标；
2. 发送端按 `NodeID + ServiceName` 去重；由于同一 Node 内 ServiceName 唯一，同名目标在
   每个 Node 最多一个；
3. 参数只编码一次，发送端对同一编码结果按目标 Node 投递；
4. 目标 Node 收到消息后，根据线协议中的 ServiceName、ContractID 和 MethodID 精确投递；
5. 调用方 Node 内存在目标时直接走相同本地分发，不经过网络；
6. 同一个 Service 重复注册同一 RPC 契约和方法属于配置错误，在注册阶段拒绝。

该规则避免业务层逐个查找、重复编码和重复处理发现状态，同时仍让 Transport 针对 TCP 与
NATS 选择最合适的投递方式。

TCP 和 NATS 必须保持相同的上层语义：

- TCP 对每个目标 Node 复用其连接并发送一次，目标 Node 再执行本地分发；
- NATS 普通 Request 和 Notify 发布到目标 Node 的稳定请求 Subject，目标 ServiceName
  保留在 RPC 线协议中，由目标 Node 本地分发；
- NATS Broadcast 根据发现结果逐 Node 发布到相同的稳定请求 Subject，不建立单独的广播
  Subject 或 Subscription；目标 Node 仍按 ServiceName、ContractID 和 MethodID 执行本地
  分发；
- 业务代码不因传输方式改变。

每个 NATS Node 始终只有一个普通请求入口和一个响应入口，本地 Service 数量与 Broadcast
都不会增加 Subscription。

### 10.4 错误与投递语义

广播不等待任意远端业务结果。返回的 `error` 只表示本地发现、编码和向各目标提交发送时的错误。

本地、TCP 或 NATS 出现多目标部分成功或全部失败时返回只读 `BroadcastError`，至少包含：

- 目标 Node 数量；
- 成功提交数量；
- 失败数量；
- 失败 Node 及原因。

部分成功使用 `CodeRPCBroadcastPartialFailed=2010`；多目标全部失败使用
`CodeRPCBroadcastFailed=2011`。只有一个目标时保留 Notify 的原始错误，零目标返回既有
无路由或契约错误，不构造聚合对象。已知断开目标立即记为失败，其他目标仍继续投递。

NATS 广播只报告本地编码、Publish 和 NATS 接受阶段的错误，不承诺获知每个目标 Node
是否已经收到或完成本地分发。TCP 也只以发送队列接受为成功边界。

Context 在扇出中途取消时停止尚未提交的目标，并把剩余目标记为相同取消原因；已经接受的
目标不可撤回。广播不自动重试、重新扫描或把失败实例替换为其他实例。

正常成功路径不为每个目标创建公开结果对象；逐目标详情只在失败路径构建。

返回值方法的 `BroadcastXxx` 仍是通知广播，不收集响应。需要收集多个服务响应的功能属于
独立设计，不复用通知广播语义。

## 11. 统一 error 语义

### 11.1 生成客户端始终暴露 error

所有生成的客户端调用都暴露一个最终 `error`：

- `AwaitXxx` 的最后一个返回值是 `error`；
- `AsyncXxx` 自身返回立即提交 `error`，回调的最后一个参数是提交成功后的最终 `error`；
- `NotifyXxx` 和 `BroadcastXxx` 直接返回本地发送阶段的 `error`。

如果服务端声明没有 `error`，生成器追加框架错误位置；如果已经有末尾 `error`，生成器复用该位置。

### 11.2 服务端未声明 error

例如：

```go
GetPlayer(
    ctx context.Context,
    playerID int64,
) *pb.Player
```

生成：

```go
AwaitGetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

该 `error` 可以报告路由、编解码、传输、超时、取消和远端 panic 等框架错误，但服务端无法主动报告业务错误。

如果服务端内部访问数据库失败后返回 `nil`，调用方可能得到 `player == nil && err == nil`。框架不能猜测 `nil` 的业务含义。需要传播失败时，服务端声明必须改成：

```go
GetPlayer(
    ctx context.Context,
    playerID int64,
) (*pb.Player, error)
```

### 11.3 panic

请求—响应处理发生 panic 时，框架必须恢复任务、记录服务端诊断信息，并通过最终 `error` 向调用方报告远端执行失败。

通知和广播没有响应通道，远端 panic 不能返回调用方，只在接收端记录日志、指标和追踪。

具体错误码、线协议和堆栈边界见 [Origin v3 统一错误码设计](./2026-07-24-统一错误码设计.md)。gRPC 状态映射仍由插件设计单独确定。

## 12. 多输入多输出的内部布局

多个输入和输出使用生成的内部逻辑位置编号；该编号用于生成静态布局和契约指纹，不作为
字段 Tag 写入每条固定顺序载荷：

```text
Request:
  field 1 = input 1
  field 2 = input 2
  field 3 = input 3

Response:
  field 1 = output 1
  field 2 = output 2
  field 3 = output 3
```

规则如下：

- 编号按原始参数位置稳定维护；
- 调换参数顺序属于不兼容修改；
- 在中间插入或末尾追加参数属于不兼容修改；
- 删除参数或修改位置类型属于不兼容修改；
- 删除参数后，不能在同名 RPC 中用新的业务语义复用原位置；
- 输入和业务输出分别维护自己的 `1`～`N` 位置；
- Context 不占输入位置，最终 `error` 不占业务输出位置；
- 参数名和返回值名称不进入位置布局；
- 经常演进或参数很多的方法建议主动使用 Request/Response 结构体；
- 参数总量不设置人为上限，但仍受 Node 的最大 RPC 消息大小和内存保护限制。

每个位置独立使用 RPC 数据与序列化设计规定的编码路径。顶层 Protobuf 参数使用标准 Protobuf 消息字节，其他 Go 类型使用 Origin 静态编码。

标准 gRPC 只直接支持单个 Protobuf Request 和单个 Protobuf Response。包含多个顶层输入或输出的 Origin RPC 不能直接自动暴露为标准 gRPC 方法，必须通过显式适配层映射到包装消息。

### 12.1 兼容演进

MethodID 保持简单稳定，只由契约名和方法名生成，不包含输入、输出或线签名。完整契约指纹
覆盖精确签名，并且必须在业务载荷解码前完成兼容性检查。

原 RPC 的兼容演进优先放在顶层 Protobuf Request/Response 内完成。保持消息全名和既有
字段编号，通过新增可选字段等 Protobuf 二进制兼容方式演进时，Go RPC 签名和 MethodID
保持不变。

任何顶层输入或输出的数量、顺序、类型以及最终 `error` 声明变化都属于不兼容修改。此时
优先建立独立的版本化 RPC 契约和 Service，先让新旧接收端同时存在，再迁移调用方，最后
删除旧契约。同一接口新增 `XxxV2` 会改变完整 ContractFingerprint，只适合整个契约的蓝绿
或协调切换。不能让旧调用方继续把旧载荷发送给已经改成新签名的同名方法。

## 13. 低延迟约束

- `AsyncXxx`、`AwaitXxx` 只生成薄包装，共用一个未导出的底层调用核心；
- 客户端不通过字符串方法名查找 RPC；
- 热路径不使用反射检查回调签名；
- Async 回调签名在生成阶段静态确定；
- Await 不为每个调用额外创建辅助 goroutine；
- Notify 和 Broadcast 不创建 pending response 条目；
- Broadcast 在编码前固定一次不可变计划，按稳定 NodeID 顺序在当前执行栈中提交，不创建
  逐目标 goroutine；
- Broadcast 参数只静态编码一次，每个成功目标使用独立 Buffer 所有权；
- 多参数直接编码到同一个输出缓冲区，不能为了接口方便在热路径反射组装通用 Map；
- 成功广播路径不构建逐目标公开结果集合；
- Future 可以作为内部状态机存在，但不是普通业务调用必须操作的公共对象。

实现阶段必须分别基准验证 Async、Await、Notify 和 Broadcast 的延迟、内存分配和吞吐。

## 14. 生成期校验

`origingen` 至少校验：

1. Context 存在且位于第一个参数；
2. 不存在第二个 Context；
3. 不使用可变参数；
4. 所有输入和业务输出类型均可静态编码；
5. error 最多一个且位于最后；
6. 无返回方法生成 Notify 和 Broadcast；
7. 有任意返回值的方法生成 Async、Await、Notify 和 Broadcast；
8. 生成后的方法名在客户端类型中不冲突；
9. 参数位置和类型变更符合兼容性规则；
10. 需要直接暴露为 gRPC 的方法满足单个 Protobuf Request/Response 限制。
11. RPC 接口没有嵌入其他接口；
12. 一个 Service 没有绑定多个公开 RPC 接口。

所有失败必须指出接口、方法、参数或返回值位置、失败原因和可执行的修改建议，不能延迟到运行时反射调用时失败。

## 15. 测试要求

至少覆盖：

1. `(T, error)` 生成 Async、Await、Notify 和 Broadcast；
2. `T` 生成 Async、Await、Notify 和 Broadcast，请求—响应外观自动追加框架 error；
3. `error` 生成无业务返回值的 Async、Await、Notify 和 Broadcast；
4. 完全无返回值生成 Notify 和 Broadcast；
5. 多输入、多输出和混合 Go/Protobuf 类型；
6. error 位于开头、中间或出现多次时生成失败；
7. 可赋值给 error 的自定义返回类型遵循末尾唯一规则；
8. 可变参数生成失败；
9. Async 回调只在调用方 Service 取得执行槽后运行；
10. Async 快速完成不能抢占当前任务；
11. Async pending 记录所属 Service，且先入 Ready、后删除 pending；
12. Async 立即提交失败直接返回且不回调；返回 nil 后响应、超时和取消只完成一次；
13. Draining 中的排空任务可以继续发起 Async，并受关闭 Context 限制；
14. Await 释放执行槽、FIFO 恢复并重新取得执行槽；
15. Await 与 RPC 共用有效 Deadline，不重复应用 `15s`；
16. Notify 不创建 pending、Future 或响应；
17. Notify 只报告本地发送阶段错误；
18. Broadcast 按 Target ServiceName、RPC 契约 ID 和方法 ID 匹配，不因同契约的其他
    ServiceName 或同名方法而误投；
19. Broadcast 在发送端按目标 Node 去重，每个目标 Node 只提交一次；
20. 同一 Node 内 ServiceName 唯一，同名匹配 Service 最多收到一次；
21. 同一 Service 重复注册相同 RPC 契约和方法时注册失败；
22. TCP Broadcast 覆盖零目标、单目标、多目标、全部成功和部分失败；
23. NATS 的单 Node 单逻辑订阅入口不会因本地 Service 数量产生重复消息；
24. TCP 与 NATS 的 Notify、Broadcast 业务语义一致；
25. 服务端未声明 error 时，框架错误仍能返回；
26. 请求处理 panic 返回远端执行错误，通知处理 panic 只产生接收端诊断；
27. 参数顺序、追加、插入、删除和类型修改的兼容性检查；
28. Async、Await、Notify 和 Broadcast 的低延迟基准；
29. RPC 接口嵌入其他接口时生成失败；
30. 一个 Service 绑定多个公开 RPC 接口时生成或注册失败；
31. 默认自动单目标和 Broadcast 排除 Retired，`IncludeRetired()` 显式纳入且所有值派生
    保留该标志；
32. 已知断开实例在 Broadcast 中产生失败而不被静默删除，其他目标继续投递；
33. 多目标部分成功使用 2010、多目标全部失败使用 2011，单目标保留原始错误；
34. `PrepareBroadcast -> Encode Once -> Submit Fan-out` 固定一次快照和连接视图，参数只
    编码一次且各目标 Buffer 所有权独立；
35. 8192/8193 目标边界、总放大容量、Context 中断、无重试和无逐目标 goroutine。

## 16. 已确认结论

Origin v3 RPC 接口与调用语义最终采用：

- 使用 Go 接口定义服务端 RPC；
- 一个 Service 可以没有公开 RPC，但最多绑定一个公开 RPC 接口；
- RPC 接口直接声明该 Service 的全部 RPC 方法，不支持接口嵌入或跨 Service 聚合；
- 允许多个输入和多个业务输出，不设置人为数量上限；
- Context 必须是第一个参数；
- 不支持可变参数，使用 Slice 代替；
- error 可以声明或省略，但最多一个且只能位于最后；
- 客户端生成接口始终暴露一个最终 error；
- 有任意返回值的方法生成 `AsyncXxx`、`AwaitXxx`、`NotifyXxx` 和 `BroadcastXxx`；
- 完全无返回值的方法生成 `NotifyXxx` 和 `BroadcastXxx`；
- `AsyncXxx` 使用强类型回调，并把回调投递回调用方 Service；
- `AsyncXxx` 自身返回立即提交错误；返回非 nil 时不回调，返回 nil 后回调严格一次；
- Async pending 记录所属 Service，完成时先发布 Ready 回调、再删除 pending；
- Draining 中的排空任务和回调可以继续发起 Async，并受 Service 关闭 Context 限制；
- `AwaitXxx` 内部自动使用 Service Await 规则，用户不手工操作 Future；
- Notify 面向一个路由目标，不等待远端响应；
- Broadcast 保留 v2 `CastGo` 的全目标广播能力，公共名称改为 `BroadcastXxx`；
- `rpcClient` 是逻辑代理，不拥有 TCP 或 NATS 连接；
- Broadcast 按客户端 Target 的 ServiceName、RPC 契约 ID 和方法 ID 匹配，语义上覆盖
  Target 基础范围内全部可见且可路由 Service；
- Broadcast 在传输层按目标 Node 投递，由目标 Node 根据 ServiceName、ContractID 和
  MethodID 精确分发；
- 自动单目标和 Broadcast 默认排除 Retired，统一通过 `IncludeRetired()` 显式纳入；
- 精确 `OnNode` 继续允许 Retired；
- Broadcast 编码前固定一次完整目标计划，参数只编码一次，已知断开目标立即形成失败；
- 多目标部分成功使用 2010，多目标全部失败使用 2011，单目标保留原始错误；
- 返回值 RPC 的 Broadcast 主动放弃结果，不支持广播收集多响应；
- Async、Await、Notify 和 Broadcast 共用同一个底层调用核心；
- Future 和 Call 的内部状态合并为池化的 `pendingCall`；
- 迟到响应、Timeout 和取消使用 RequestID 查询 pending 表，不长期持有可复用对象指针；
- Protobuf 业务 Request 和 Response 不自动池化；
- `pendingCall` 不是普通业务用户必须接触的 API。
