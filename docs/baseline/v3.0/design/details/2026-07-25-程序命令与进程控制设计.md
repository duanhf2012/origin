# Origin 第三版程序命令与进程控制设计

> 文档状态：M4 范围已实现并通过验收，M7 已完成最小 Application 接入，M16 完整停止接入已实现并通过验收
> 创建日期：2026-07-25  
> 最后更新：2026-07-29

## 1. 目标

v3 保留 v2 的 `start`、`stop`、`help` 和自定义命令能力，同时解决多 Node Application、跨平台优雅停止和命令扩展问题。

目标是：

- 命令外观明确，动作和参数不混用；
- 一个命令只执行一个主动作；
- `start` 可以选择一个或多个 Node；
- `stop` 始终进入 Application 统一优雅停止流程；
- Windows、Linux 和 macOS 使用相同的 `stop` 语义；
- 自定义命令不依赖全局变量，不引入 Cobra 等第三方 CLI 框架；
- `help`、参数错误和退出码适合人工使用与自动化脚本；
- 命令回调 panic 由统一异常边界处理。

## 2. v2 对照与保留内容

v2 的 `console` 包通过注册 bool、int、string flag 提供：

- `-start`；
- `-stop`；
- `-retire`；
- `-help`；
- 配置、日志、pprof 等参数；
- 使用者自定义回调。

v3 保留命令名称、帮助能力和可注册回调，但不直接沿用以下实现：

- 不再把所有选项都称为 Command；
- 不使用包级全局 `flag.CommandLine` 和全局命令列表；
- 不允许一次输入多个主命令并依赖注册顺序执行；
- 不把 `start` 特殊处理为“最后执行的 flag”；
- 不只凭 PID 和进程名判断目标，避免 PID 复用误停；
- Windows 不使用强制 `Kill` 代替优雅停止；
- 不在库代码中直接调用 `os.Exit`。

## 3. 命令外观

推荐的正式外观使用子命令：

```text
game-server start --app-name game-dev --config ./config --node gateway-1,game-1
game-server stop --app-name game-dev
game-server help
game-server help start
game-server version
```

规则：

- 第一个非程序名参数是唯一主命令；
- `start`、`stop`、`help`、`version` 是内置保留名；
- 无参数时显示简短帮助并返回参数错误码，不默认启动；
- `-h`、`--help` 和首参数 `-help` 都归一为 `help`；
- 为照顾 v2 使用习惯，首参数 `-start`、`-stop` 可以作为 `start`、`stop` 的兼容别名；
- 正式文档和新项目模板只使用无前缀子命令，不继续扩展 v2 的 `-start nodeid=...` 字符串语法。
- 内置长参数遵循 Kubernetes CLI 风格，统一使用双中划线和小写 kebab-case，例如 `--app-name`，不使用 `AppName`、`--appname` 或单中划线长参数；
- 带值参数同时接受 `--app-name game-dev` 和 `--app-name=game-dev`，正式文档优先使用前一种形式；
- 短参数只为高频通用能力保留；`app-name` 不增加 `-n` 别名，避免与 Node、namespace 等概念冲突。

这样保留 v2 熟悉的动作名称，同时避免 flag 执行顺序和多动作混用。

## 4. 内置命令

### 4.1 start

```text
game-server start --app-name name [--config dir] [--pid-dir dir] [--node id1,id2]
```

- `--app-name` 是必填参数，指定本次 Application 进程名，同时保留在启动命令行中，便于 `ps`、`grep` 和运维脚本定位；
- 缺少或非法的 `--app-name` 在加载配置前按参数错误返回；
- `--config` 只接受配置目录，默认 `./config`，不接受单个配置文件；
- `--pid-dir` 可以覆盖配置中的 PID 目录，默认 `./run`；
- `--node` 使用逗号分隔一个或多个 NodeID，并严格按参数从左到右作为本次启动顺序；
- 未指定 `--node` 时按配置中顶层 `nodes` 的声明顺序启动全部 Node；
- NodeID 两侧空白被去除，空项和重复项属于参数错误；
- 参数和完整配置在创建 Node、网络和业务资源前校验；
- 获得进程控制权后创建日志、Application 和选中的 Node；
- 重复启动同一 AppName 返回明确错误，不覆盖活动进程的 PID 记录。

生产环境通常只传一个 NodeID；开发环境可以使用逗号指定多个 Node。

### 4.2 stop

```text
game-server stop --app-name name [--pid-dir dir] [--timeout duration]
```

- `stop` 通过 AppName 定位一个 Application 进程，不是进程内的单个 Node；
- `--app-name` 是必填参数，必须与 start 使用同一名称；
- 缺少或非法的 `--app-name` 不猜测目标，直接按参数错误返回；
- `--pid-dir` 直接定位 PID 文件，stop 不加载业务配置目录；
- `--timeout` 默认 `30s`，只限制当前外部 stop 命令等待目标释放 PID 锁；它不传入目标
  进程，也不修改 Application 独立配置且默认无限的整体关闭 Deadline；
- 命令向目标进程发送 Stop 请求，目标进程使用 `sync.Once` 合并重复请求；
- 默认等待目标完成优雅停止或到达 timeout；
- 目标本来就未运行时按幂等成功处理，并输出 `not running`；
- 目标仍存活但控制通道不可用时返回错误，不默认发送强制 Kill；
- 强制终止由操作系统、systemd、Kubernetes 或运维工具明确执行，不伪装成 Origin 的优雅 stop。

### 4.3 help

```text
game-server help
game-server help start
game-server --help
```

- 不加载业务配置，不创建 Application，不初始化文件日志；
- 总帮助先显示内置命令，再按名称排序显示自定义命令；
- 子命令帮助显示 Usage、Summary 和参数；
- 未知命令同时输出简短错误和 `help` 提示；
- Help 输出写 stdout，参数错误写 stderr。
- 内置 `BuildTime` 非空时，在帮助头部显示构建时间；为空时整行省略，与 v2 行为一致；
- `BuildTime` 由编译脚本通过 `-ldflags -X` 注入，运行时不伪造构建时间。

例如 `BuildTime` 非空时：

```text
Origin v3 (build time: 2026-07-25 20:00:00 +0800)
```

`game-server help`、`game-server --help` 和兼容入口 `game-server -help` 使用同一份输出。

### 4.4 version

`version` 输出版本、提交号、构建时间、Go 版本和协议版本。该命令不初始化 Application。

### 4.5 retire

Service 退休能力进入对应里程碑后，可以增加：

```text
game-server retire --app-name game-1 --node game-1 --service PlayerService
```

退休命令进入对应里程碑时，再单独设计带动作类型和参数的本地控制协议；不能复用只表达 Stop 意图的空停止请求文件。M4 只保留命令名，不实现退休命令。

## 5. AppName 与配置目录

### 5.1 AppName

由于一个 Application 可以包含多个 Node，v2 只用 NodeID 命名 PID 文件已经不再适用。v3 使用 AppName 标识一个操作系统进程中的 Application。

规则：

- CLI 名称固定为 Kubernetes 风格的 `--app-name`，start 和 stop 都必须显式传入；
- AppName 值统一推荐小写 kebab-case，并限制为小写字母开头，后续只含小写字母、数字和中划线；
- 不从配置目录、可执行文件名、环境变量或第一个 NodeID 隐式推导 AppName；
- 同一 `pid_dir` 中 AppName 必须唯一；
- AppName 只用于本机进程控制和日志定位，不替代 NodeID，也不参与服务发现；
- `pid_dir` 由 `--pid-dir` 指定，未指定时使用 `./run`；相对路径以命令启动时的当前工作目录为基准并立即转为绝对路径；它不放入业务配置，避免 stop 为定位进程而加载整个配置目录；
- `pid_dir` 必须在启动业务资源前创建和校验；
- 生产模板应把 PID 目录放在进程可写且生命周期明确的位置。

显式必填虽然比自动取可执行文件名多写一个参数，但可以避免同一二进制启动多个实例时发生 PID 文件冲突，也能保证 `ps`、`grep`、start 和 stop 使用同一个稳定标识。`--app-name` 本身不执行额外业务回调，兼容 v2 `-name` 的空参数用途；v3 同时把它用于 PID 文件以及 Windows 普通控制台的停止请求文件命名，不再保留含义重复的“实例名”参数。

### 5.2 配置目录扫描

`--config` 的参数是目录：

```text
game-server start --app-name game-dev --config ./config --node gateway-1,game-1
```

加载规则参照 v2：

1. 递归扫描目录；
2. 只读取 `.json`、`.yml`、`.yaml` 文件；
3. 文件路径按字典序处理，保证重复运行结果一致；
4. 从配置内容中的 Node 列表查找指定 NodeID，不依赖文件名；
5. 同一个 NodeID 在多个文件重复定义时返回配置错误；
6. 指定 NodeID 不存在时，在创建 Application 资源前返回错误；
7. 不跟随指向目录的符号链接，避免配置扫描越出指定目录。

配置可以按集群、节点、公共 Service 和业务 Service 拆分成多个文件。`--config` 不同时兼容“目录或文件”两种语义，避免使用者无法判断实际扫描范围。

## 6. PID 文件与跨平台停止

v3 保留 v2“通过本地 PID 文件定位进程”的总体方式。PID 文件名改为：

```text
./run/game-dev.pid
```

PID 文件使用 AppName，而不是 NodeID 或完整 `os.Args[0]`。

v2 的具体实现不能原样复制，原因包括：

- 打开文件失败时仍会先执行 `defer f.Close()`，可能对 nil 文件调用 Close；
- 写 PID 使用 `O_TRUNC`，并发启动可能覆盖正在运行进程的 PID；
- 只比较 PID 和进程名，同一可执行文件发生 PID 复用时可能误判；
- 库代码直接调用 `os.Exit`，跳过统一清理；
- Windows stop 使用强制 Kill，不能执行 Application 优雅停止。

v3 的 `.pid` 文件只保存诊断所需的 PID 和本地启动时间：

```json
{
  "pid": 12345,
  "started_at": "2026-07-25T20:00:00+08:00"
}
```

`started_at` 使用进程所在机器的操作系统本地时区，与日志默认显示时区一致；序列化使用 RFC 3339 并保留数字时区偏移，例如 `+08:00`，不能写成没有时区的模糊时间。该字段只用于人工诊断，不承担进程身份认证。

运行进程在整个生命周期持有 PID 文件的操作系统独占锁。进程正常退出或异常崩溃后，操作系统会自动释放文件锁。因此文件即使仍保留在磁盘上也不代表进程仍在运行，不需要依靠 PID 数字或删除陈旧文件竞争启动权。

为使 PID 文件保持精简，v3 不再把控制地址、token、可执行路径和运行状态写入 PID 文件。

Linux 和 macOS 的 `game-server stop` 在确认 PID 文件锁被占用后，读取 PID 并发送标准
`SIGTERM`；Kubernetes 由 kubelet 直接发送 `SIGTERM`。目标进程通过信号监听取消
Start Handler 的 Run Context，不创建或轮询停止文件。

v2 Windows `stop` 实际调用 `os.Process.Kill()`，属于立即强杀，无法执行优雅关闭。
M4 只为 Windows 普通控制台保留同一 PID 目录中的瞬时停止请求文件：

```text
./run/game-dev.stop
```

规则：

- Windows 普通控制台按下 `Ctrl+C` 时，Go Runtime 产生 `os.Interrupt`，必须取消与
  `.stop` 文件相同的 Run Context，并进入完整 Application 优雅停止流程；
- `Ctrl+C` 不能直接调用 `os.Exit`、强杀进程或跳过 `OnStop`、日志 Flush 和 PID 锁释放；
- 停止请求文件名由 AppName 确定，不需要在 PID 文件中再保存寻址信息；
- Windows `stop` 只在确认 PID 文件锁正被运行进程占用后，原子创建停止请求文件；
- 运行进程使用一个轻量控制 goroutine 监听停止请求文件，不占用 Service Runner；
- 检测间隔默认 `100ms`，只用于启停控制，不进入游戏逻辑热路径；
- 检测到请求后立即删除请求文件，并在目标进程内取消 Start Handler 的 Run Context，Application 再建立独立 Stop Context 进入统一优雅关闭；
- 重复请求按幂等处理；
- 启动进程获得 PID 文件锁后、启动控制 goroutine 前，先删除同 AppName 的陈旧停止请求文件；
- PID 目录必须是本机磁盘目录，并限制为当前运行用户可读写；不支持 NFS 等共享目录；
- SIGINT、SIGTERM、Windows 控制台 `Ctrl+C`、进程内 Stop API 和停止请求文件必须进入同一个
  Run Context 取消路径。

Windows 兼容方式只使用文件、文件锁和一个低频控制 goroutine，不需要 loopback HTTP、
随机 token、固定端口或强制 Kill；正式 Linux/Kubernetes 运行时没有文件轮询。

Go `context.Context` 本身不跨进程传输。Unix 信号或 Windows `.stop` 文件负责把停止意图
送到目标进程；目标进程的信号监听或 Windows 控制 goroutine 调用本进程的 `cancel()`，
Start Handler 才通过 `ctx.Done()` 收到通知。已取消的 Run Context 不能用于 `OnStop`、
存档 RPC 或数据库写入；Application 必须为这些收尾操作建立带整体关闭 Deadline 的
独立 Stop Context。

## 7. 启动占用与陈旧 PID 文件

同一 AppName 只使用一个 PID 文件：

```text
./run/game-dev.pid
```

启动流程：

1. 打开或创建 `<app-name>.pid`；
2. 尝试获得非阻塞独占文件锁；
3. 锁失败表示同 AppName 已经被另一个进程占用，直接拒绝重复 start；
4. 锁成功表示不存在活动所有者，即使文件中保留旧 PID 也可安全覆盖；
5. Windows 普通控制台删除同 AppName 的陈旧停止请求文件；
6. 截断并写入 PID 和本地 `started_at`，执行文件 `Sync`；
7. 建立平台停止通知监听；只有 Windows 普通控制台启动文件监听 goroutine；
8. 启动 Application，并在整个进程生命周期持有文件描述符和独占锁；
9. 正常结束时释放锁；PID 文件可以保留供诊断，下次启动覆盖。

文件锁只解决 Origin 进程之间的协作，不防御同一用户恶意绕过锁修改文件。PID 目录权限仍是安全边界。

## 8. Stop 流程

`stop` 的完整流程：

1. 命令进程解析 pid_dir、AppName 和等待 Deadline；
2. PID 文件不存在时按幂等成功返回 `not running`；
3. PID 文件存在时尝试获得非阻塞独占锁；成功表示没有活动进程，释放锁并按 `not running` 返回；
4. 锁被占用表示同 AppName 的 Application 正在运行；
5. Linux/macOS 发送 `SIGTERM`；Windows 普通控制台原子创建 `<app-name>.stop`；
6. 目标进程的 Unix 信号监听、Windows `Ctrl+C` 监听或停止文件控制 goroutine把请求转换
   为同一个 Run Context 取消；
7. Application 按既定 Node、Service、Module 顺序排空和停止；
8. 日志系统最后排空并关闭；
9. 命令 Runner 停止控制 goroutine 并释放 PID 文件锁；
10. stop 命令轮询文件锁状态，直到锁释放或 timeout。

停止请求监听 goroutine 只负责发出停止意图，不直接执行完整 Stop，避免控制逻辑和关闭流程相互等待。

## 9. 自定义命令

命令注册表属于一个 Command Runner 实例，不是包级全局变量。精简外观：

```go
type Command struct {
    Name    string
    Summary string
    Usage   string
    Run     func(ctx CommandContext, args []string) error
}

type CommandContext struct {
    Context context.Context
    Stdin   io.Reader
    Stdout  io.Writer
    Stderr  io.Writer
}
```

注册示例：

```go
runner.Register(Command{
    Name:    "check-config",
    Summary: "检查配置但不启动服务",
    Usage:   "game-server check-config --config dir",
    Run: func(ctx command.CommandContext, args []string) error {
        return checkConfig(ctx, args)
    },
})
```

规则：

- 注册必须在 `Run` 前完成；
- 空名称、非法名称、重复名称和覆盖内置命令都返回错误；
- 名称只接受小写字母、数字和中划线，并以字母开头；
- 自定义命令默认是当前命令进程中的一次性离线任务；
- 回调自己解析所属参数，可以使用标准库 `flag.NewFlagSet(..., flag.ContinueOnError)`；
- Runner 提供可注入的 stdin/stdout/stderr，便于测试；
- 自定义命令 panic 转成命令失败，记录堆栈并返回非零退出码；
- Runner 不自动创建 Application。确实需要配置的命令显式加载配置；
- 首版不允许自定义命令扩展正在运行进程的停止请求机制，避免本地控制能力提前演变成管理后台。

## 10. 参数优先级

`start` 参数优先级：

```text
显式 CLI 参数 > 配置文件 > 框架默认值
```

只允许命令行覆盖适合进程启动选择的字段，例如配置目录、AppName、PID 目录和本次 Node 选择。Service 业务配置、网络安全配置和大批日志细节不逐项复制成 CLI 参数，避免形成两套配置系统。

`stop` 只读取定位目标和等待所需的最小配置，不初始化业务配置和外部依赖。

## 11. 返回与退出码

Origin 库代码只返回错误和退出码，不调用 `os.Exit`。最终可执行程序可以：

```go
func main() {
    os.Exit(run())
}
```

其中 `run()` 已经完成 panic 捕获、Application Stop、日志 Flush 和其他 defer 清理。

M4 固定退出码：

```text
0  成功、help、version、目标本来未运行
1  命令执行或 Application 运行失败
2  命令、参数或配置使用错误
3  目标进程控制失败
4  等待优雅停止超时
```

自定义命令普通 error 映射为 `1`。需要其他退出码时返回框架定义的 `ExitError`，不让任意整数散落在业务代码中。

M16 接入后，如果 Application 运行期间曾隔离无法恢复的 Failed Service，程序不会立即
退出；随后收到正式 Stop 并完成全部清理后，Application 返回 `CodeServiceFailed`，start
命令最终退出码为 `1`。清理成功不能把运行期严重故障改写为正常退出码 `0`。

## 12. 与日志及异常系统的顺序

- `help`、`version` 和参数错误只使用注入的 stdout/stderr；
- `start` 在静态配置校验后尽早初始化控制台日志，再初始化文件日志；
- 自定义离线命令可以选择只使用 stderr，也可以显式初始化 Logger；
- 命令 Runner 的 panic 恢复是最外层保底，具体用户回调仍只记录一次；
- `start` 正常退出时日志最后关闭；
- `stop` 命令进程不写目标进程日志；
- Windows 停止请求文件不承载业务数据。

异常边界见[异常隔离与恢复设计](./2026-07-25-异常隔离与恢复设计.md)。

## 13. M4、M7 与 M16 范围

M4 实现独立命令与进程控制库：

- 无第三方依赖的 Command Runner；
- `start`、`stop`、`help`、`version`；
- `-start`、`-stop`、`-help` 首参数兼容别名；
- `--app-name`、目录语义的 `--config`、`--pid-dir` 和逗号分隔的 `--node`；
- 可由 `-ldflags -X` 注入的 `BuildTime`，非空时显示在 help 中；
- 自定义离线命令注册；
- 只包含 PID 与本地启动时间的 AppName PID 文件、生命周期独占锁、Unix 信号和
  Windows 普通控制台瞬时停止请求文件；
- 可注入的 start、stop 生命周期 Handler，使用测试进程验证而不依赖 Application；
- 固定退出码；
- 重复启动、重复停止、遗留 PID 文件和 timeout 测试。

M16 再实现：

- start Handler 创建并运行真实 Application；
- Windows 请求文件、Windows 控制台 `Ctrl+C`、SIGINT、SIGTERM 和进程内 Stop 共用
  Application Stop；
- Application 排空、日志关闭和最终进程退出码集成。

M4 不实现：

- 远程管理控制台；
- 自定义在线控制命令；
- 强制 Kill；
- Service 退休命令；
- 命令自动补全、交互式 Shell 和彩色 UI；
- Cobra、urfave/cli 等第三方 CLI 依赖。

## 14. 验收要求

1. M4 的 start Handler 可以被注入和验证；M7 接入后可以按 `--node` 参数顺序启动一个或多个 Node，未传参数时使用配置声明顺序。
2. 同 AppName 重复 start 被文件锁拒绝，不覆盖活动 PID 记录。
3. M4 的 Unix SIGTERM 和 Windows 普通控制台 stop 请求都能送达测试进程；M7 接入最小
   Application Stop，M16 补齐完整排空。
4. M16 中 SIGINT、SIGTERM 和重复 stop 只触发一次 Application Stop。
5. 目标未运行时 stop 幂等成功。
6. 进程崩溃后文件锁自动释放，遗留 PID 文件不阻止重新启动，也不会误停复用同一 PID 的其他程序。
7. PID 文件半写、Unix 信号、Windows 停止请求文件重复创建和陈旧文件均有测试。
8. `help` 和 `version` 不初始化 Application。
9. 未知命令、非法参数和控制失败返回稳定退出码。
10. 自定义命令出现在总帮助中，重复和保留名称注册失败。
11. 自定义命令 panic 被捕获并返回非零退出码。
12. library 不调用 `os.Exit`。
13. Windows stop 不使用强制 Kill 代替优雅关闭。
14. Windows 普通控制台实际按下 `Ctrl+C` 时，完整执行 Service 排空、`OnStop`、日志关闭
    和 PID 锁释放，而不是直接结束进程。
14. `go test -race` 和重复启停泄漏检查通过。
