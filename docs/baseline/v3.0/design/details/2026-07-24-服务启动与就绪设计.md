## 2. 设计目标

1. Service 完成必要的数据加载和依赖检查之前，不接受外部业务 RPC。
2. `OnStart` 可以等待尚未出现的远端 Service，而不阻塞服务发现继续更新。
3. 服务发现等待由快照和增量事件驱动，不通过高频 RPC 重试碰运气。
4. Service 是否就绪由 `OnStart` 的返回结果唯一决定，不要求业务额外调用 `MarkReady`。
5. 支持等待任意同名 Service，也支持精确等待 `NodeID + ServiceName`。
6. 启动失败有明确回滚边界，不把初始化不完整的 Service 暴露出去。
7. 启动路径保持简单，不为等待发现创建业务 Runner、Timer 轮询或后台业务 goroutine。

## 3. Node 基础设施先于 OnStart、晚于纯 OnInit

Node 首先只建立构造和纯初始化所需的 Node 身份、静态配置以及 Service 绑定关系，然后按
配置顺序执行全部 `OnInit`。全部 `OnInit` 成功后，才依次建立：

1. TimerEngine 的系统计时能力；
2. TCP、NATS 等 Transport；
3. RPC Client Runtime 和 pending call 管理；
4. Discovery Provider 客户端；
5. 可见服务快照、路由表和发现等待管理器。

上述基础设施全部 Ready 后，Node 才按配置顺序执行本地业务 Service 的 `OnStart`。因此
“基础设施先启动”只针对 `OnStart` 阶段，不表示 `OnInit` 可以访问网络、Timer 或远端服务。

M17 接入正式 Discovery Provider 后，“基础设施 Ready”进一步固定为：

- NATS 本地 Server 连接、Request/Response Subscription 和 `max_payload` 校验已完成；
- TCP Listener、Accept 循环和拨号管理器已经运行，但不等待全部远端目标建立连接；
- 当前 Node 配置 `DiscoveryService` 时，先在基础设施阶段 Prepare 独立控制 Listener；
- Discovery Provider 已完成第一次权威同步并应用完整快照；
- TCP 已按快照安装候选并开始拨号。

不能等待所有已发现 TCP Node 全部连接成功，否则一个无关或故障目标会阻塞整个 Node
启动。`DiscoveryService` 控制 Listener 的 Prepare 不执行用户回调、不开放业务 RPC；
当前 Node 的 Provider 完成首次同步后，全部 Service 仍按原配置顺序执行 `OnStart`。
具体 Provider 契约见[服务发现提供者设计](./2026-07-26-服务发现提供者设计.md)。

服务发现由 Node 基础设施自己的 goroutine 持续接收全量和增量更新。业务 Service 的 `OnStart` 即使正在等待，服务发现仍能：

- 建立或恢复 Provider 连接；
- 接收远端 Node 和 Service 更新；
- 更新可见服务快照与可路由状态；
- 完成相应的发现等待。

因此，`OnStart` 不需要通过循环 RPC 或 `Sleep` 等待发现补齐。

## 4. `OnInit`、启动状态与就绪门

Node 先按配置顺序调用 Service：

```go
OnInit() error
```

`OnInit` 是纯初始化和静态校验阶段，只完成配置解析、Module 静态装配、不需要清理的内存
状态初始化，以及 RPC 实现、事件处理器和发现监听意向等静态登记。此时 Node 的
TimerEngine、RPC Transport、普通 Service Runner 和业务任务准入均未启动。

`OnInit` 明确禁止：

- `Await`、`Async`、`Notify` 和 `Broadcast`；
- 创建或触发业务 Timer；
- 投递普通任务、本地业务事件或启动业务 goroutine；
- 访问数据库、Redis、远端 RPC 或取得其他必须释放的外部资源。

这些调用统一返回 `CodeServiceNotReady`，不能静默排队等待第二阶段，也不能为了兼容旧代码
临时启动 Scheduler。该限制使“`OnInit` 失败不调用 `OnStop`”具有可证明的资源安全边界。

Node 仍按配置顺序调用本 Node 的全部 Service `OnInit`。单个 `OnInit` 返回错误或发生 panic
时，框架记录当前 NodeID、ServiceName 和 `on_init` 阶段并继续检查后续 Service；全部调用
结束后使用 `errors.Join` 按配置顺序聚合错误。只要聚合结果非空：

1. 当前 Node 不调用任何 Service 的 `OnStart`，也不进入 `Ready`；
2. 当前 Node 不调用任何业务 Service 的 `OnStop`；
3. Node 只关闭构造期已经创建的框架资源，并向 Application 返回聚合启动错误；
4. Application 停止后续 Node，并严格反序停止此前已经启动成功的全部 Node；
5. 全部清理结束后，`app.Start()` 打印一次 Error 日志并以非零退出码结束程序。

如果错误来自 Module `OnInit`，框架立即停止当前 Service 的 Module 树构建，拒绝继续添加
其余兄弟或子 Module，并解除无效子树的静态引用；它不会调用 Module `OnStop`。当前 Service
记为初始化失败，但不影响 Node 继续执行后续 Service 的 `OnInit`，从而一次返回完整的
Service 级初始化错误集合。

Service 和 Node 只补充错误上下文，不在每一层重复打印同一个 error。配置、类型绑定等无法
安全创建完整 Service 列表的框架错误发生在进入 `OnInit` 循环之前，仍然立即返回，不属于
可聚合的业务 `OnInit` 错误。

Service 启动期间处于 `Starting`。框架调用：

```go
OnStart(ctx context.Context) error
```

如果 Service 组合 Module，框架先调用 `Service.OnStart(ctx)`，成功后再按父先子后、同级
添加顺序调用全部 `Module.OnStart(ctx)`。Module 依赖所属 Service 提供的 Scheduler、Timer、
Await、RPC、配置和共享业务资源，因此 Service 是生命周期父级，必须先启动并最后停止。
单个 Service 与全部 Module 都返回成功只表示该对象树已经越过启动回调；当前 Node 的全部
Service 均成功前，任何 Service 都不能向远端发布。任一 Module 启动失败都会把失败 Module
自身和此前所有真正进入过 `OnStart` 的 Module 按实际启动顺序严格逆序调用一次 `OnStop`，
随后调用一次 `Service.OnStop`，并使 Node 启动失败。

`OnStart` 返回前：

- Service 不接受入站请求—响应 RPC；
- Notify 和 Broadcast 不向该 Service 投递；
- Service 不进入普通 RPC 候选路由；
- 不启动普通业务 Runner；
- 不处理普通本地事件和业务 Timer；
- 可以使用启动上下文执行 `AwaitService`、`AwaitNodeService` 和 Await 风格的 RPC、Redis、数据库操作。
- 可以预先登记业务 Timer，但 Timer 只在整个 Node 越过就绪屏障后开始触发；
- Async、Notify、Broadcast、普通任务和本地业务事件仍返回 `CodeServiceNotReady`。

当前 Node 的全部 `OnStart` 均返回 `nil` 后，框架越过统一 Node 就绪屏障：

1. 将全部 Service 切换为 `Running`；
2. 激活全部 Service Runner、Timer 回调和本地入站准入；
3. 以一份 Node 记录向发现数据源原子发布全部公开 Service；
4. 发布成功后把 Node 切换为 `Ready`。

禁止在前面的 Service 完成、后面的 Service 仍处于 `OnStart` 时逐个发布。这样远端只能
观察到“整个 Node 尚未就绪”或“整个 Node 已经就绪”，不会调用到部分初始化完成的进程。

`OnStart` 返回成功就是唯一的就绪确认。首版不提供 `MarkReady`、`SetReady` 或 `auto_ready: false`，避免遗漏调用、重复开放以及 Node 部分就绪带来的额外状态。

## 5. 服务发现等待接口

Service 提供两个语义明确的接口，不解析 `NodeID.ServiceName` 组合字符串：

```go
AwaitService(
    ctx context.Context,
    serviceName string,
) error

AwaitNodeService(
    ctx context.Context,
    nodeID string,
    serviceName string,
) error
```

### 5.1 `AwaitService`

`AwaitService` 等待可见服务快照中至少存在一个满足以下条件的实例：

- 实际 `ServiceName` 与参数完全相同；
- 通过当前 Node 的 `allow_discovery` 筛选；
- 当前存在于远端可见快照。

该接口不固定目标 Node，适合普通高可用服务。Running、Retired 以及没有公开 RPC 契约但
允许被发现的 Service 都可以完成等待；后续真正发起 RPC 时再由 RPC Runtime 检查契约和
Transport。

### 5.2 `AwaitNodeService`

`AwaitNodeService` 等待由以下复合身份确定的具体实例：

```text
NodeID + ServiceName
```

目标必须存在于远端可见快照。该接口适用于分片归属、指定玩家所在 Node 或其他必须定向
到具体实例的场景。

`NodeID` 是发现目录中的唯一 Node 身份。v3 不为该接口增加语义重复的 `NodeName`。

默认优先使用 `AwaitService`。不需要精确实例时使用 `AwaitNodeService` 会削弱故障转移能力。

两个等待接口都只观察远端发现目录，不等待当前 Node 的本地 Service。当前 Node 本身会从
可见快照中过滤；`AwaitNodeService` 显式传入当前 NodeID 时立即返回
`CodeInvalidArgument`，避免形成永远只能由当前 OnStart 返回后才能解除的自等待。本地
Service 依赖使用既有 `LookupService` 和配置声明顺序，不使用服务发现等待。

### 5.3 名称规则

- `serviceName` 匹配公开的实际 `ServiceName`；
- 模板 Service 必须使用创建后的实际名称，不能使用模板名称代替；
- 方法参数不接受 RPC 契约名、Go 接口名或 RPC 方法名；
- Node 与 Service 参数分开传递，不保留 `.` 作为隐式分隔符。

## 6. 等待实现语义

调用等待接口时：

1. 先查询当前不可变可见服务快照；
2. 已存在匹配的可路由实例时立即返回，不创建等待项；
3. 不存在时，在发现等待管理器中注册一次等待；
4. 后续快照更新或实例状态变化时重新匹配相关等待；
5. 匹配成功、Context 取消或 Deadline 到期时完成一次并移除等待项。

快照检查与等待注册必须使用同一个有序边界，或使用快照版本进行二次校验，避免实例恰好在两步之间出现而造成丢失唤醒。

发现等待是一次性 Future，不是 Timer 轮询。服务发现更新只检查可能受本次变化影响的等待键，不在每次更新中扫描无关业务对象。

如果本地 `allow_discovery` 配置从 Service 名称维度已经确定不可能匹配目标，调用立即返回对应的服务发现配置错误。需要依赖尚未出现的远端标签或实例信息才能判断时，等待由启动 Context 的 Deadline 结束。

两个等待接口遵守已经确认的统一 Await Deadline 规则：

```text
调用方显式 Deadline
    > Service.SetDefaultAwaitTimeout
    > Node scheduler.default_await_timeout
    > Origin 内置 15s
```

`OnStart` 传入的启动 Context 已有 Deadline 时直接继承该 Deadline，不再叠加另一层 `15s`。

## 7. `OnStart` 示例

```go
func (s *PlayerService) OnStart(ctx context.Context) error {
    if err := s.AwaitService(ctx, "DBService"); err != nil {
        return err
    }

    data, err := s.dbRPC.AwaitLoadGlobalData(ctx)
    if err != nil {
        return err
    }

    s.globalData = data
    return nil
}
```

等待指定实例：

```go
func (s *SceneService) OnStart(ctx context.Context) error {
    return s.AwaitNodeService(
        ctx,
        "world-1",
        "WorldService",
    )
}
```

`AwaitNodeService` 只负责确认指定实例当前可路由，不把后续普通 RPC 隐式绑定到该 Node。
需要调用同一实例时，调用方把精确 Target 交给生成客户端：

```go
client := contract.NewWorldRPCClient(
    s,
    rpc.ToServiceOnNode(
        "world-1",
        "WorldService",
    ),
)
```

完整外观见 [单目标 RPC 客户端与路由设计](./2026-07-24-单目标远程调用客户端与路由设计.md)。

实例可能在等待成功后、定向 RPC 发起前丢失，因此 RPC 仍必须正常处理无可用路由、断线、取消和超时。

## 8. 重试与失败处理

服务发现等待和 RPC 重试是两个不同问题：

- 尚无可路由实例时，使用 `AwaitService` 或 `AwaitNodeService` 等待发现事件；
- 已经发现 TCP 实例、但候选连接仍在拨号时，Await RPC 使用本次调用 Context 无轮询等待
  任一候选变为可发送；`AwaitService` 本身仍只表达发现可见，不混入 Transport 状态；
- NATS 在本地连接 Ready 且目标已发布后即可发送，不存在每个目标一条客户端连接；
- Await RPC 只等待首次可发送条件，请求一旦发出就不因断线自动重放非幂等调用；
- Notify、Async 等非 Await 调用没有可发送目标时保持快速失败，不建立隐藏等待队列；
- 框架不把无可用实例隐藏成无限 RPC 重试；
- 只有明确可安全重试的幂等 RPC 才能使用有界重试；
- 重试必须继承 `OnStart` 的 Context，不得突破其 Deadline；
- 非幂等 RPC 默认不自动重试。

`OnStart` 出现以下任一结果时启动失败：

- 返回非 `nil` 错误；
- 启动 Context 被取消；
- 启动 Context 的 Deadline 到期；
- 发生 panic。

启动失败后：

1. 失败 Service 不进入 `Running`，也不发布为可路由；
2. Node 停止启动后续 Service；
3. 返回错误的 Service 和此前所有真正进入过 `OnStart` 的 Service 均进入启动记录；
4. Node 在 RPC、Timer 和发现输入仍可用时，按该启动记录的严格反序逐个执行
   `OnStop(stopCtx)`；
5. 单个 `OnStop` 返回错误或 panic 不阻止后续 Service 和框架资源清理；
6. Node 向 Application 返回原始启动错误与全部回滚错误的聚合结果。

Context 取消和超时使用统一错误码设计中的 `CodeCanceled` 与 `CodeDeadlineExceeded`。业务返回错误保留其原始 Origin Code，Node/Application 负责聚合，不通过错误文本判断原因。

无论失败来自 `OnInit` 还是 `OnStart`，Application 都不能在部分 Node 成功的状态下继续
运行。最先导致启动终止的错误是主要错误，回滚错误追加到错误链但不能覆盖主要错误及其
NodeID、ServiceName 和阶段字段。

业务在 `OnStart` 返回前创建、但尚未把所有权登记到 Service 的临时资源，仍必须通过
`defer` 或本地错误路径释放；只有已经明确转交给 Service 持有的资源才能由启动失败时的
`OnStop` 回收。

Module 使用相同规则：只要 `Module.OnStart` 已被调用，即使它返回错误，也必须执行一次
`Module.OnStop`；尚未进入 `OnStart` 的 Module 不执行 `OnStop`。Service 已先进入
`OnStart`，所以 Module 启动失败的回滚会在全部已进入的 Module 严格逆序停止后调用一次
`Service.OnStop`。如果 `Service.OnStart` 自身失败，则不调用任何 `Module.OnStart`，只调用
一次 `Service.OnStop` 清理已经交给 Service 持有的资源。

### 8.1 启动过程中收到 Stop

Stop 意图优先于继续启动：

- `OnInit` 没有 Context，框架不能强制中断当前正在执行的回调；等待当前回调返回后，不再
  调用后续 Service 的 `OnInit`；
- Transport/Provider 正在建立或重试时立即取消 startCtx 并停止重试；
- `OnStart` 正在执行时取消其 startCtx，等待当前回调按 Context 返回，不再启动后续
  Service；
- 已经进入过 `OnStart` 的 Service 仍按严格反序执行 `OnStop(stopCtx)`；
- 只有 Stop/信号取消且清理成功时视为正常停止，退出码为 `0`；Stop 到达前已经存在真实
  `OnInit`、`OnStart` 或框架启动错误时仍返回原错误并使用退出码 `1`。

正常启动中的“全部调用 OnInit 后聚合错误”不覆盖 Stop 语义。收到停止意图后不应为了收集
更多初始化错误继续启动尚未进入生命周期的 Service。

### 8.2 OnStart 中的同 Node 调用

统一就绪屏障越过前，同一 Node 的所有 Service 都没有普通 Runner 和入站准入。因此
`OnStart` 通过 RPC 调用当前 Node 的任意 Service，包括此前已经成功返回 `OnStart` 的
Service，均立即返回 `CodeServiceNotReady`，不建立“启动期本地 RPC 内联执行”的特殊路径。

同 Node 初始化依赖应使用普通同步初始化组件、Module 或私有初始化函数表达；运行期
Service 间调用仍统一使用 RPC。这样不会出现调用方等待目标 Runner、而目标 Runner 又必须
等全部 `OnStart` 完成后才能激活的启动死锁。

## 9. 启动顺序与交叉依赖

Application 已确认按 `--node` 参数顺序启动 Node；未传入时使用顶层 `nodes` 声明顺序。前一个 Node 进入 `Ready` 后才启动下一个 Node。因此：

- 依赖方 Node 必须排在被依赖方 Node 之后；
- 如果 Node A 的 `OnStart` 等待尚未启动的 Node B，而配置又要求 A Ready 后才启动 B，A 最终会超时并导致启动失败；
- 两个 Service 在 `OnStart` 中互相等待对方可路由会形成启动环；
- 服务发现补齐和 RPC 重试不能解决启动环。

v3 不为启动阶段引入依赖图和自动解环。项目通过明确的 Node 启动顺序以及单向初始化依赖避免启动环。确实存在双向运行依赖时，至少一方必须先完成不依赖对方的启动，在进入 `Running` 后再建立非启动关键路径的联系。

## 10. 调度规则

`OnStart` 由唯一的生命周期 goroutine 执行。它的 Await 行为与 `OnStop` 的 finalizer 等待路径相似：

- 等待期间占用该生命周期 goroutine；
- 不占用一个正在执行用户业务事件的 Runner；
- 不创建替代业务 Runner；
- `OnStart` Context 携带只属于当前 Service 和本次启动代次的私有令牌；
- `Service.Await` 和生成的 `AwaitXxx` 自动识别该令牌，不增加生命周期专用 RPC 方法；
- 等待函数直接在原生命周期 goroutine 执行，不创建辅助 goroutine；
- 默认 Deadline 使用已经准备好的 M8 DeadlineQueue，Deadline 控制协程不执行用户代码；
- Future 由 RPC Runtime、Discovery Provider 或外部适配器的 goroutine 完成；
- Future 完成后唤醒同一个生命周期 goroutine，从 Await 后继续顺序执行。

这样可以在启动逻辑中使用顺序代码，同时保证 Service 状态尚未开放给并发业务任务。

业务不得在 `OnStart` 中：

- 使用 Async 回调作为启动完成条件；
- 注册业务 Timer 轮询依赖；
- 把 OnStart Context 交给另一个 goroutine 冒充生命周期调用；
- 提前开放入站 RPC；
- 通过 Notify 或 Broadcast 代替需要确认完成的初始化调用。

业务可以在 `OnStart` 中创建自己明确拥有的 goroutine 或工作池，例如 Module 内部用于 AOI
计算的固定 Worker：

- Origin 不拦截 Go 的 `go` 语句，也不尝试检测业务是否创建 goroutine；
- Worker 可以并发处理与 Service 可变状态隔离的输入快照、不可变数据或自己独占的数据；
- Worker 不得直接并发读写 Service 的普通 Map、Slice、玩家对象或 Module 共享状态；
- 需要修改 Service 状态时，通过线程安全的 `DispatchAsync` 把结果交回唯一执行槽；
- `DispatchAsync` 失败时 Worker 自行释放尚未移交的结果；
- Service/Module 必须持有 Worker 的取消函数和等待句柄，在 `OnStop` 中停止并等待退出；
- 不可取消、不可等待、所有权不明确的 fire-and-forget goroutine 仍不允许。

框架只能在 Await、Timer、Dispatch 和 RPC 等公开边界校验生命周期，无法阻止业务直接访问
字段；并发正确性还必须由代码审查、Race 测试和项目测试保证。

业务不想重复编写顶层 recover 时使用 `s.GoSafe(fn)`。该方法在新 goroutine 最外层捕获
panic 并打印完整 ErrorStack，防止整个进程退出；它不自动重跑已经发生部分副作用的函数，
也不替业务管理 Context、WaitGroup 和停止等待。直接使用原生 `go` 创建的 goroutine 无法
被另一个 goroutine 中的框架调用边界 recover，这是 Go 语言本身的限制。

长驻 Worker 需要在某个 Job panic 后继续处理下一 Job 时，在 Worker 循环内使用
`s.RunSafe(fn)`。`RunSafe` 同步执行当前 Job，panic 时打印 ErrorStack 并返回
`CodeInternal`；外层循环继续。它只隔离 panic，不让 Worker 获得 Service 执行槽，计算结果
仍通过 `DispatchAsync` 返回 Service。

普通业务 Task Context 继续使用协作式执行权交接；生命周期 Context 按 API 契约只允许在
原 OnStart 调用栈使用。`context.Background()`、其他 Service Context 和已经完成的旧
生命周期 Context 会被拒绝。Go 无法可靠识别当前 goroutine，因此仍在有效期内却被业务
错误转交给其他 goroutine 的 Context 不能由框架完全识别；该行为明确禁止，并由代码审查、
Race 测试和项目静态检查约束。

Application/Node 整体启动默认无限等待，但所有等待仍可被 Start Context 或 Stop 取消。
单次 Await 没有显式 Deadline 时使用统一默认 `15s`。耗时较长的数据加载应显式设置更长
Deadline，并按页或分批 RPC，避免超过单条 RPC `4M` payload 上限。

全部 OnStart 完成后，Provider 发布暂时失败只重试发布本身，不重复执行 OnStart。Node
保持未公开状态，直到发布成功进入 Ready，或启动 Context 取消后反序回滚。

`private: true` 或没有公开业务 Service 的 Node 仍在 `OnStart` 前启动 Provider 并完成远端
权威同步，但发布屏障为 `NotRequired`，不发送空 Node 记录；其 Ready 不等待不存在的
PublishAck。需要发布的 Node 只有收到 PublishAck 后才越过屏障。正常 Stop 先在 Stop Context
内等待 WithdrawAck，再停止业务入站并执行 Service finalizer，最后关闭 Provider；Ack
等待超时不阻止后续本地清理。

## 11. 可观测性

至少记录：

- 每个 Service 的 `Starting` 开始、成功和失败时间；
- `OnStart` 总耗时；
- 当前等待的 ServiceName、可选 NodeID 和等待耗时；
- 服务发现快照版本以及完成等待的实例身份；
- 初始化 RPC 的目标、耗时和 Origin Code；
- 启动 Context 取消、超时和 panic；
- Node 启动回滚顺序与回滚错误。

日志和 Trace 可以携带 NodeID、ServiceName 等诊断字段，但 RPC 线协议错误仍遵守统一错误码的轻量规则。

## 12. 测试要求

后续实现至少验证：

1. Discovery Provider 和 RPC Client Runtime 在 `OnStart` 前可用；
2. Node 全部 `OnStart` 返回前，任一 Service 都不接受远端入站 RPC 且不进入远端候选；
3. Node 全部 `OnStart` 成功后，全部 Service 越过统一就绪屏障并一次性发布；
4. 当前快照已有实例时，`AwaitService` 立即完成；
5. 实例稍后被发现时，等待可以被增量更新唤醒；
6. 快照查询与等待注册竞争时不会丢失唤醒；
7. `AwaitService` 可以由任意同名可路由实例完成；
8. `AwaitNodeService` 只能由指定 `NodeID + ServiceName` 完成；
9. `Starting` 或不可路由实例不能完成等待；`Retired` 与 `Running` 一样可以完成等待；
10. Context 取消或超时会移除等待项并返回统一错误；
11. 显式 Deadline 和默认 `15s` 兜底遵守统一 Await 优先级；
12. 模板 Service 只能通过实际 ServiceName 匹配；
13. 任一 `OnStart` 失败时本 Node 的全部 Service 均从未发布，并触发 Node 回滚；
14. `OnStart` 等待期间服务发现仍能更新快照；
15. `OnStart` 不创建普通业务 Runner、Timer 轮询或 Async 回调；
16. 启动顺序错误和交叉等待最终由启动 Context 有界失败；
17. `AwaitNodeService` 不会把后续普通 RPC 隐式绑定到目标 Node；
18. 目标在等待成功后、RPC 发起前丢失时，RPC 正常返回路由错误；
19. TCP 与 NATS 使用相同的等待匹配和就绪语义。
20. OnStart 可以直接复用生成的 `AwaitXxx`，且不会激活普通业务 Runner；
21. 生命周期 Await 使用 M8 DeadlineQueue，不创建 Go 默认 Timer 或额外等待 goroutine；
22. Provider 发布重试不会重复调用 OnStart；
23. 启动中 Node 可以调用已发现目标，目标不要求调用方已经被发现。
24. 所有 Service 的 `OnInit` 均会被调用，多个错误按配置顺序聚合；
25. `OnInit` 中 Await、Async、Notify、Broadcast、Timer 和普通任务均返回
    `CodeServiceNotReady`；
26. `OnInit` 聚合失败不调用当前 Node 的任何业务 `OnStop`；
27. `OnStart` 返回错误的 Service 也进入回滚列表并执行一次 `OnStop`；
28. `OnStop` 回滚错误不会覆盖最先发生的 `OnStart` 错误。
29. 启动中收到 Stop 时取消 startCtx，不再进入新的生命周期回调，并反序清理已经进入
    `OnStart` 的 Service；
30. `OnStart` 调用当前 Node 的任意 Service RPC 均返回 `CodeServiceNotReady`；
31. OnStart 允许创建有明确取消、等待和所有权的业务 Worker，跨 goroutine 结果通过
    `DispatchAsync` 返回 Service 执行槽。
32. `Service.GoSafe` 为业务 goroutine 提供顶层 panic 保底，但不自动重启、不自动
    cancel/wait，也不把 Worker 纳入 Scheduler 排空。
33. `Service.RunSafe` 在当前 goroutine 的单 Job 边界 recover 并返回 `CodeInternal`，使
    Worker 能继续下一 Job，但不允许借此并发访问 Service 可变状态。
34. M17 正式 Provider 接入后，首次权威快照必须在业务 `OnStart` 前完成；
35. TCP 只等待本地监听与拨号管理器 Ready，不全局等待全部远端连接；
36. `AwaitService` 只等待发现可见，Await RPC 可以继续等待已发现 TCP 候选可发送；
37. Notify、Async 不继承 Await RPC 的连接等待语义。
38. 私有或零公开 Service Node 完成同步但不发布空 Node，发布状态为 `NotRequired`；
39. 需要发布的 Node 只有收到 PublishAck 后 Ready，停止时先等待 WithdrawAck；
40. Provider 控制连接晚于业务 finalizer 关闭，Stop 超时仍继续本地资源清理。

## 13. 已确认结论

- Node 先启动 Transport、RPC Runtime 和服务发现等基础设施，再执行业务 Service 的 `OnStart`；
- Node 在启动上述运行期基础设施前，先完成全部 Service 的纯 `OnInit`；
- Node 全部 Service 完成 `OnStart` 前均不对外发布，禁止部分 Service 提前可见；
- `OnStart` 返回成功就是唯一就绪确认，首版不提供手动 `MarkReady`；
- 服务发现等待由快照和增量事件驱动，不使用 RPC 或 Timer 轮询；
- 提供 `AwaitService(ctx, serviceName)` 等待任意同名可路由实例；
- 提供 `AwaitNodeService(ctx, nodeID, serviceName)` 等待指定实例；
- Node 与 Service 参数分开，不解析 `NodeID.ServiceName` 组合字符串；
- 精确身份继续使用已确认的 `NodeID + ServiceName`，不增加 `NodeName`；
- 发现等待遵守统一 Await Deadline 规则，复用
  `scheduler.default_await_timeout`，最终兜底为内置 `15s`；
- `AwaitNodeService` 不自动绑定后续 RPC 的路由目标；
- 无实例等待、首次 TCP 可发送等待与已发送请求重试保持分离，非幂等 RPC 不自动重试；
- `OnStart` 失败时 Service 不开放，Node 按启动失败规则回滚；
- 所有 `OnInit` 都执行后再统一判断聚合错误；失败时当前 Node 不调用任何业务 `OnStop`；
- `OnInit` 禁止 Await、Async、Notify、Broadcast、Timer、外部访问和业务 goroutine；
- `OnStart(ctx) error` 保留明确失败通道；返回错误的 Service 与此前进入过 `OnStart` 的
  Service 均按严格反序执行 `OnStop`；
- Module `OnInit` 失败时终止当前 Service 的 Module 树构建，但继续后续 Service 的
  `OnInit` 并聚合错误；已进入 `Module.OnStart` 的失败 Module 自身也执行一次 `OnStop`；
- 启动中收到 Stop 时不继续进入新的 `OnInit/OnStart`，取消当前 startCtx 并反序清理；
- OnStart 不支持同 Node 启动期 RPC 特例，目标尚未 Ready 时统一返回
  `CodeServiceNotReady`；
- 允许 Service/Module 创建自己持有且可取消、可等待的业务 Worker；Worker 不直接访问
  Service 可变状态，结果使用 `DispatchAsync` 切回唯一执行槽；
- 显式启动顺序必须保证被依赖 Node 先 Ready，启动交叉依赖不自动解环。
- OnStart 使用私有生命周期 Context 复用 Service.Await，等待期间只阻塞启动 goroutine；
- 全部 OnStart 后的 Provider 发布失败只重试发布，不重做业务初始化。

运行期 Transport 暂时失效和恢复不重新执行 `OnStart`。M16 在入站能力恢复并完成就绪检查
后自动重新发布完整 Node 快照；Failed、Stopping、Stopped 和私有 Service 不重新发布，
Running/Retired 保留原状态。

运行期全部公开 Service 都进入 Failed，或者 TCP Listener/NATS 整体 RPC 能力进入
Recovering 时，Node 生命周期仍保持 Ready，Application 保持 Running；存活检查成功，外部
就绪检查失败。恢复并重新发布发现后自动恢复外部就绪，不重新执行任何 Service 生命周期。
TCP 单个远端目标连接断开只影响该目标路由，不改变当前 Node 的整体就绪。

部分公开 Service Failed 时只撤销失败实例，Node 仍就绪但健康快照标记 Degraded；Retired
继续按健康服务处理。没有公开 Service 的内部 Node 完成启动且必需基础设施正常时仍然
就绪。必需 Discovery Provider 不可用时使用 `CodeDiscoveryUnavailable` 取消就绪并持续
恢复。单次 RPC 超时、业务错误、队列过载和已恢复的任务 panic 不改变就绪状态。

Node 首次启动时，全部纯 `OnInit` 成功后才启动 Transport、RPC Runtime、TimerEngine 和
服务发现输入。Transport 暂时不可达、connection refused、timeout、临时 DNS 等网络错误
使用有上限退避持续重试到 Start Context 结束；默认 StartTimeout 无限。非法配置、证书
解析或身份校验、鉴权/权限拒绝、监听地址被占用和 `max_payload` 不足等确定性错误立即启动
失败。Transport Ready 后只进入 `OnStart`；网络重试不会重复调用任何 `OnInit` 或
`OnStart`。
