# Origin 第三版服务发现提供者设计

> 文档类型：详细设计
> 状态：M17/M18 已实现并通过验收
> 创建日期：2026-07-26
> 最后更新：2026-07-30
> 适用版本：Origin v3
>
> 后续覆盖：Origin Provider 不再维护独立 TCP Listener；它复用顶层 `rpc` 所选 Transport，
> `server.node` 是唯一配置引导。本文中旧的 `server.listen/address` 描述由当前配置模型覆盖。

## 1. 范围

本文定义服务发现数据从哪里产生、Provider 如何接入 Node，以及 Origin 内置发现和 etcd
Provider 如何配置、注册、续约和失效。公共契约同时以未来可以增加 Consul 或项目自定义
Provider 为验收条件，但 M17/M18 不实现 Consul。

关注筛选、可见快照、发现/失去发现/退休事件见[服务发现与关注筛选设计](./2026-07-24-服务发现与关注筛选设计.md)，不在本文重复。

## 2. 已确认边界与里程碑拆分

已确认：

1. Application 只管理 Node 启停；
2. Origin、etcd 和第三方 Provider 输出相同的 Node、Service、会话与状态变化语义；
3. Provider 只更新原始发现目录，不直接调用业务监听器；
4. 发现数据更新不进入 RPC 调用热路径，RPC 路由读取已经发布的只读快照；
5. 框架内置 `origin` 和 `etcd`，不实现独立 `static` Provider，但允许 Application 注册
   `consul` 等自定义 Provider；
6. Origin 内置发现首版只支持一个 `DiscoveryService`，不实现多实例高可用；
7. etcd 配置支持多 Endpoint、网络、认证和 TLS 场景，但不直接暴露全部底层 Client
   调优项。

Discovery Provider 配置放在顶层，整个项目只选择一套 Provider。Application 不持有共享 Provider 实例或连接；每个启动的 Node 根据同一份顶层配置独立创建和释放自己的 Provider，保持 Node 生命周期与资源所有权隔离。

公共契约、Origin 和 etcd 一起设计，避免到 M18 才反向修改 Node、Directory、RPC 或业务
API；实现仍拆成两个里程碑：

- M17 实现最小公共 Provider 基座、公开扩展 SPI、Origin Provider 和公共一致性测试；
- M18 只增加 etcd Provider、Lease/Watch/认证/TLS 和 etcd 故障矩阵；
- M18 接入后不得修改 Node、Directory、RPC 或业务发现 API；如果 etcd 暴露出公共契约
  缺陷，必须先重新 Review，不能在 etcd 适配器中建立旁路。

## 3. 公共 Provider 契约

### 3.1 一个小而完整的公开扩展面

公开扩展位于独立的 `discovery/provider` 包。第三方实现者只需要：

1. 提供一个 Factory；
2. 实现一个 Provider；
3. 在 Application 加载配置或启动前注册一次。

概念接口保持为：

```go
type Factory func(Context) (Provider, error)

type Provider interface {
    Start(context.Context) error
    Publish(context.Context, Node) error
    Withdraw(context.Context) error
    Close(context.Context) error
}
```

上述名称和方法集合就是 M17 冻结的公开契约，不在实施阶段再拆成注册器、租约器、
Watcher、重试器等多组要求第三方分别实现的接口。`Context` 及其受限能力固定为：

```go
type Context struct {
    NodeID    string
    SessionID uint64
    Config    Config
    Host      Host
    Logger    log.Logger
}

type Config struct { /* 框架私有字段 */ }

func (Config) Decode(dst any) error

type Host struct { /* 框架私有字段 */ }

func (Host) ReplaceSnapshot(Snapshot) error
func (Host) Report(Report)
func (Host) SetTTL(time.Duration) error
```

`Config` 和 `Host` 都是框架构造的具体值，不是要求第三方实现或注册的新接口。`Decode`
只能严格解码当前选中的 Provider 配置块；`Host.ReplaceSnapshot` 是唯一目录写入能力，
`Host.Report` 是唯一运行状态上报能力。`Host.SetTTL` 必须在第一次快照或状态上报前恰好
设置一次 Provider TTL，使框架能够统一执行旧快照过期；重复设置相同值幂等，不同值返回
配置错误。Provider 不获得 `Application`、`Node`、内部
Directory、RPC Runtime 或业务监听器指针，不能绕过框架校验直接修改目录或触发业务事件。

`Report` 只携带 `State`、`Reconnects`、`ConsecutiveFailures` 和 `ErrorCode`。Provider
状态只有 `Starting/Ready/Recovering/Stopped`；首次同步和本地发布是否完成由框架根据
成功调用 `ReplaceSnapshot`、`Publish`、`Withdraw` 的屏障维护，不能由 Provider 自报。
其中 `Reconnects` 为 `uint64`，`ConsecutiveFailures` 为 `uint32`，`ErrorCode` 为
`errs.Code`；`Report` 不携带 endpoint、动态 error 文本、后端 revision 或远端节点。

SPI 跟随 Origin v3 模块的兼容性规则，并由公开契约测试固定行为；M17 不实现 Go `.so`
动态装载或独立 Provider 进程协议。将来需要 sidecar 时，可以用一个普通的已注册 Provider
作为进程间适配器，不改变本契约。

### 3.2 Application 私有注册

自定义 Provider 使用唯一入口注册：

```go
err := app.RegisterDiscoveryProvider("consul", consul.NewFactory())
```

规则：

- 注册表属于单个 Application，不使用包级可变全局变量；
- 必须在加载项目配置或启动 Application 前注册；
- 名称使用稳定的小写标识，重名、非法名称立即返回错误；
- 内置 `origin`、`etcd` 名称保留，第三方不能覆盖；
- 配置引用未注册 Provider 时，在创建任何 Node 前失败；
- “替换”表示项目配置选择另一个 Provider，不表示运行期热切换或覆盖内置实现。

### 3.3 严格配置联合

顶层配置固定使用 `type + 同名配置块`：

```yaml
discovery:
  type: consul
  consul:
    addresses:
      - 127.0.0.1:8500
    ttl: 15s
```

框架只允许 `type` 和与其同名的一个配置块，拒绝同时提供多套 Provider 配置。框架先按
已注册名称找到 Factory，再只把选中块包装为 `Context.Config`；Factory 调用
`Config.Decode(&typedConfig)` 严格解码，未知字段、类型不匹配和非指针目标必须报错。
公开 API 不暴露 YAML AST、原始字节或 `map[string]any`，Provider 也不能绕过严格解码。

Origin、etcd 和自定义 Provider 的 TTL 均放在各自配置块内，不放入
`services.DiscoveryService`。密码、Token、私钥和证书内容不得进入日志、错误详情、状态
快照或配置转储。

### 3.4 完整权威快照

Provider 对框架只提交完整权威快照，不公开 Add/Update/Delete 增量写接口：

- Origin 或 Consul 的全量查询可以直接生成完整快照；
- etcd Watch 先更新 Provider 私有镜像，再提交完整快照；
- Provider 自己的 revision、Consul index、etcd revision 等只用于本实现排序，不能进入
  Directory 或业务 API；
- 框架统一校验 NodeID、SessionID、Labels、Transport、Address、ServiceName、状态和
  RPC 契约；
- 框架限制节点数、服务数和总大小，深拷贝可变容器，规范化后原子替换 Directory；
- 无变化快照必须被识别并跳过，不能产生伪事件。

第三方 Provider 不需要理解业务监听器、RPC 路由或 Directory 差异算法，只需持续给出
自己当前确认的完整远端事实。

公开 DTO 与业务只读 `discovery.Instance`、内部 `RawNode` 分离，固定包含：

```go
type Snapshot struct {
    Nodes []Node
}

type Node struct {
    NodeID    string
    SessionID uint64
    Labels    map[string]string
    Transport Transport
    Address   string
    Services  []Service
}

type Service struct {
    ServiceName         string
    State               ServiceState
    ContractID          uint64
    ContractFingerprint [32]byte
}
```

`Transport` 只有 `None/TCP/NATS`，`ServiceState` 只有 `Running/Retired`；零值只用于非法
输入防护。TCP 使用 `Address`，None/NATS 必须为空。`ContractID` 与 fingerprint 必须同时
为零或同时非零。框架在 `ReplaceSnapshot` 返回前校验并深复制 Slice、Map，Provider 可以
在返回后复用自己的容器；框架也不把内部快照容器反向暴露给 Provider。

### 3.5 生命周期、期望发布与恢复

每个 Node 独占一个 Provider 实例。框架串行化生命周期操作并持有公共状态机，具体
Provider 持有后端连接、租约、Watch、心跳和重连资源：

1. `Start` 在 Node 的纯 `OnInit` 全部完成后执行，只有后端控制连接可用、订阅或 Watch
   就绪并提交首个权威快照后才成功；
2. `Start` 受启动 Context 限制；初次同步失败时不能进入任何业务 `OnStart`；
3. 全部业务 `OnStart` 成功后，Node 向 Provider 提交完整本地 Node 发布期望；
4. `Publish` 和 `Withdraw` 必须幂等；Provider 暂时不可用只改变 Readiness 并持续收敛，
   不重复执行任何业务 `OnInit` 或 `OnStart`；
5. 后端恢复后 Provider 必须重新建立 Watch/订阅，并按当前期望自动重新发布本 Node；
6. 正常 Stop 先 Withdraw，再停止 RPC 入站和业务，最后 Close Provider；
7. `Close` 返回后禁止再提交快照或状态，全部 Provider goroutine、连接、租约和订阅均已
   退出。

框架拥有 Readiness、旧快照保留 TTL、快照差异和事件语义；Provider 拥有后端协议、
连接恢复、租约续期和私有 revision。框架可以提供统一的退避参数或工具，但不要求所有
后端伪装成相同连接模型。

框架保证同一 Provider 实例的 `Start/Publish/Withdraw/Close` 串行调用。Provider 内部可以
并发收包，但必须把 `Host.ReplaceSnapshot` 和 `Host.Report` 串行提交，保证状态和快照的
因果顺序。任何 Host 调用都不能持有会阻塞 Provider 停止或网络恢复的锁；框架也不能在
Host 调用中执行用户回调。`Close` 必须等待自己创建的 goroutine 退出，且保持幂等。

### 3.6 断线、权威变化与 Lost

不对已确认的发现变化做防抖：

- 主动注销、Origin TTL 过期、etcd Lease 删除或过期、权威全量快照缺少旧实例，以及
  同 NodeID 的 SessionID 替换，均立即应用并产生对应事件；
- 本地 Provider 控制连接或 Watch 中断时，立即进入 `Recovering`、令 Node Readiness 为
  false，但这只表示暂时失去权威来源，不能立即推断全部远端实例已经消失；
- 断线期间最多保留最后权威快照一个 Provider TTL；超过 TTL 仍未恢复时，框架提交空
  远端快照并产生 `Lost`；
- TTL 内恢复后立即用新的权威全量快照对账；其中缺少的实例立即 `Lost`，新增实例立即
  `Discovered`，SessionID 替换产生旧会话 `Lost` 加新会话 `Discovered`，未变化实例不产生
  伪事件。

因此“断线立即报告”作用于 Provider 健康和 Readiness；“确认实例消失后立即 Lost”作用于
业务发现事件。短暂控制连接断开又恢复、且权威实例集合没有变化时不产生 Lost/Discovered，
不会造成服务间状态不一致。

### 3.7 状态快照

Node 提供无锁、无分配的 `DiscoveryStatus()`，冻结为：

```go
type DiscoveryStatus struct {
    Kind                string
    State               DiscoveryState
    Synchronized        bool
    Publication         PublicationState
    Reconnects          uint64
    ConsecutiveFailures uint32
    ErrorCode           errs.Code
}
```

`DiscoveryState` 只有 `Starting/Ready/Recovering/Stopped`；`PublicationState` 只有
`NotRequired/Pending/Published`。私有 Node 或没有公开业务 Service 的 Node 使用
`NotRequired`，不能为了复用 `Published=false` 把“不需要发布”和“发布尚未成功”混为一谈。
状态由不可变小对象原子替换，查询只做一次原子读取和结构复制。

该快照用于区分“控制连接已建立但尚未完成首次同步”“远端目录已同步但本 Node 发布失败”
以及 RPC Transport 自身故障。它不包含 Endpoint、账号、Token、证书、Provider revision
或远端 Node 列表。

### 3.8 `OnStart` 前的 RPC 可用性

进入业务 `OnStart` 前必须满足：

- NATS 本地连接、Request/Response Subscription 和 `max_payload` 校验全部完成；
- TCP 监听、Accept 循环和拨号管理器已经运行；
- Provider 首个权威快照已经应用，TCP 已为候选目标安装路由并开始拨号。

TCP 不等待全部已发现目标建立连接，否则一个无关或故障目标会阻塞整个 Node 启动。
`AwaitService` 继续只表示目录中存在可路由实例，不混入 Transport 状态。生成的 Await RPC
在发送前没有可用 TCP 连接时，使用调用 Context 无轮询等待任一候选变为可发送；NATS 在
本地连接 Ready 且目标已经发布后即可发送。非 Await 的 Notify/Async 保持快速失败，不建立
隐藏的无界等待队列。

### 3.9 Provider 一致性测试

M17 公开 `discovery/providertest` 契约测试和必要的假 Sink/状态观察工具。内置 Origin、
M18 etcd 及未来 Consul 都必须通过同一组基础行为：

- 首次快照、空快照、无变化快照；
- 发布、重复发布、撤销、重复撤销；
- 权威删除立即 Lost，控制断线先 Recovering、一个 TTL 后才批量 Lost；
- SessionID 替换、恢复全量对账和无伪事件；
- 严格配置、秘密信息脱敏、容量上限；
- 生命周期串行、期望发布幂等、Close 后无回调和无 goroutine 泄漏；
- `private` 或零公开 Service Node 同步远端目录但不发布本地空记录；
- 同一测试在 Race 下通过。

后端特有协议仍由各 Provider 自己补充集成、故障和性能测试。公开测试包只固定公共契约，
不要求第三方实现 Origin、etcd 或 Consul 专属测试接口。

### 3.10 Consul 可替换性门禁

M17 不实现 Consul，但冻结公共 SPI 前必须保存一张设计级映射并通过 Review：

| Consul 能力 | M17 公共契约映射 | 只能留在适配器内的状态 |
|---|---|---|
| 配置与 Client 创建 | `Factory(Context)`、`Config.Decode` | 地址、数据中心、认证和 TLS |
| 服务注册/更新 | `Publish(Node)` | Consul 注册请求与健康检查参数 |
| 注销 | `Withdraw()` | deregister 请求和当前注册 ID |
| 初始完整查询 | `Start` 后 `Host.ReplaceSnapshot` | blocking query 参数与 Consul index |
| 后续变化 | 私有镜像重建后 `ReplaceSnapshot` | index、等待和去重 |
| 断流与恢复 | `Host.Report(Recovering/Ready)` | 退避、Client 重建和重新注册 |
| 停止 | `Close()` | 请求取消和 Client 资源 |

通过标准是未来增加 Consul 时只新增 Provider 包、注册调用和 `discovery.consul` 配置块，
不修改 Node、Directory、RPC、业务发现 API 或公共 Provider 接口。Consul 实现必须能够
直接运行 `discovery/providertest`；若映射失败，先 Review 公共契约，禁止建立后端旁路。

### 3.11 稳定错误映射

公共服务发现错误只新增：

| Code | 名称 | 含义 |
|---:|---|---|
| 5001 | `CodeDiscoveryUnavailable` | 必需 Provider 不可用或尚未重新同步/发布 |
| 5002 | `CodeDiscoveryDuplicateNode` | 活跃 Session 冲突或陈旧 Session 覆盖当前会话 |
| 5003 | `CodeDiscoveryCapacity` | 固定节点、连接、服务、记录、快照或 Actor 队列达到上限 |
| 5004 | `CodeDiscoverySnapshotInvalid` | 完整快照或 Publish Node 的业务字段、排序或契约非法 |

未注册 Provider、配置或地址非法使用 `CodeInvalidConfig`；Wire 结构/方向非法、Body
过大和连接发送队列满分别复用 `CodeTransportProtocol`、
`CodeTransportMessageTooLarge`、`CodeTransportOverloaded`。Warming 是状态，不是错误。
Origin Error 帧只发送 Code，不发送动态文本。完整登记见
[统一错误码设计](./2026-07-24-统一错误码设计.md)。

## 4. v2 对照

v2 的 Origin Discovery 使用：

- `MasterNodeList` 判断哪些 Node 自动注入 `DiscoveryMaster`；
- `LocalMasterNodeId` 指定当前 Node 只向哪个 Master 注册；
- Master 在内存中维护 Node 目录并通过 RPC 推送快照；
- NATS 模式通过 Ping 和 TTL 判断失联；
- TCP 模式主要依赖连接断开判断失联。

该实现可以完成按 Master 分区的发现，但多个 Master 之间没有选主、共识或完整目录复制，因此不能把 `MasterNodeList` 直接等同于高可用集群。v3 保留内置发现能力，不保留隐式 Master 角色和自动注入 Service 的方式。

## 5. Origin 内置发现

### 5.1 显式 `DiscoveryService`

框架提供保留名称 `DiscoveryService` 的内置 Service。它可以配置在任意 Node，并允许与
任意普通业务 Service 共存，不要求建立只能承载发现服务的专用 Node：

```yaml
rpc:
  transport: tcp
  tcp:
    send_queue_messages: 16384

nodes:
  - id: discovery-1
    rpc:
      tcp:
        listen: 0.0.0.0:7000
        advertise: 10.0.1.10:7000
    services:
      - DiscoveryService
      - AdminService
```

规则：

- 不提供 `IsMaster`；
- 不根据服务器列表隐式创建 Service；
- `DiscoveryService` 使用普通 Service 的构造、生命周期、调度、退休和优雅停止机制；
- `DiscoveryService` 是框架保留名称，业务不能注册同名 Service；
- 同一 Node 可以同时配置一个 `DiscoveryService` 和多个普通业务 Service；
- 其 RPC 契约是框架内部契约，不进入普通业务 RPC 广播和路由选择。

`DiscoveryService` 不再从普通 Service 业务配置读取 TTL。TTL 属于 Provider 后端协议，
统一位于顶层 `discovery.origin.ttl`。

### 5.2 客户端引导

使用 Origin Provider 时，项目必须在顶层显式配置发现服务器：

```yaml
discovery:
  type: origin
  origin:
    ttl: 15s
    server:
      node: discovery-1
```

TCP 不能依赖尚未建立的服务发现查找 `DiscoveryService`，但服务器地址从 `server.node`
指向的 `nodes[].rpc.tcp.advertise` 推导；NATS 则直接复用所有 Node 的顶层 `rpc.nats`
连接并按服务器 NodeID 发送保留 Subject。`server.node` 是唯一的发现引导配置。

M17 的 Origin 控制通道固定使用独立 TCP：

- 不再提供 `origin.transport` 配置；
- 复用 M5 的通用 TCP 基础组件，不复用业务 RPC Runtime、业务 TCP 连接或 RPC 线协议；
- 业务 RPC 使用 NATS 的 Node 也建立一条轻量 TCP 发现控制连接；
- 控制通道只承载发现数据，不桥接不同 Transport 的业务 RPC；
- 同一 Application 仍允许混合 TCP/NATS Node，但业务 RPC 只路由到 Transport 兼容目标；
- 控制监听地址不得与当前 Node 的业务 TCP Listener 冲突。

每个普通 Node 都根据顶层配置创建自己的 Provider 客户端；Provider 客户端、私有镜像、
心跳和取消函数均归对应 Node 所有。

同一进程同时启动发现 Node 和业务 Node 时，应把发现 Node 放在启动参数最前面：

```text
game-server start --app-name game-dev --node discovery-1,game-1
```

这样 `discovery-1` 先进入 `Ready`，Stop 时 Application 按实际启动顺序的严格倒序先停止 `game-1`，最后停止 `discovery-1`。

### 5.3 共置 Node 的自举边界

已确认 `DiscoveryService` 可以与普通业务 Service 共置，因此不能通过“发现 Node 不创建
Provider”规避自举。固定顺序为：

1. Node 仍先完成全部 Service 的纯 `OnInit`；
2. 框架在基础设施阶段识别 `DiscoveryService`，先 Prepare 独立控制 Listener；
3. Listener Ready 后启动当前 Node 自己的 Origin Provider，并通过该 Listener 完成首次
   权威同步；
4. 然后按原配置顺序执行全部 Service 的 `OnStart`，不强制把 `DiscoveryService` 调整到
   Service 列表第一位；
5. 任一后续启动失败时关闭 Provider 和已 Prepare 的控制 Listener，并执行既有严格反序
   回滚。

控制 Listener 属于保留系统 Service 的框架资源，Prepare 不执行用户回调、不开放业务
RPC，也不表示该 Node 已经发布。当前 Node 的所有普通 Service 仍只在全部 `OnStart`
成功后一次性发布。

如果同一 Application 选择了多个 Node，`server.node` 必须位于显式启动顺序第一位；
框架不静默重排用户顺序，顺序错误在启动前失败。这里限制的是启动顺序，不限制
`DiscoveryService` 与其他业务 Service 共置。

### 5.4 首版单实例规则

一个 Origin 发现域只配置一个 `DiscoveryService`。首版不支持多个 Master、Leader 选举、发现端复制或客户端合并多个发现源。

原因：

- 多实例会增加每个 Node 的控制连接；
- 需要处理重复快照、事件去重、会话冲突和不同发现源的版本比较；
- 需要定义网络分区、部分实例恢复和旧数据重新出现时的裁决；
- 测试矩阵会从单一注册/续约流程扩展到大量故障组合；
- 这些复杂度与首版“内置、轻量、不依赖中间件”的定位不匹配。

需要服务发现高可用的项目使用 etcd Provider，由 etcd 集群负责租约存储和一致性。

### 5.5 会话、TTL 与失效

- Node 每次启动生成随机会话 ID；
- 实例身份为 `NodeID + SessionID`；
- 相同 `NodeID + SessionID` 允许控制连接断开后重新绑定；
- 相同 NodeID 的旧控制连接仍活跃时，不同 SessionID 可以先 Hello 并同步，但 Publish
  返回重复 Node 错误；
- 旧控制连接已经断开时，允许不同 SessionID 立即接管，不再等待旧 TTL；接管立即产生
  旧 Session `Lost` 和新 Session `Discovered`；
- 被接管的旧 Session 后续重连必须拒绝，不能反向覆盖当前活跃 Session；
- TTL 默认 `15s`，最小 `3s`；
- 心跳周期为 `TTL / 3`，最小 `1s`；
- TTL 判断使用单调时钟；
- 主动退休和正常停止通知唯一 `DiscoveryService`；
- 异常退出由 TTL 清理；
- `DiscoveryService` 连接中断时，Node 最多保留当前只读发现快照一个 TTL，不立即批量发布 `Lost`；
- 快照保留期间，TCP 连接断开等独立 Transport 事实仍可移除不可达路由；
- 超过一个 TTL 仍未恢复时，缓存实例过期并按正常差异规则发布 `Lost`；
- `DiscoveryService` 恢复后，Node 重新注册并以新的权威全量快照立即对账；快照中缺少的旧实例立即发布 `Lost`，不再增加第二段防抖 TTL；
- 发现服务不可用期间不能发现新 Node、接收退休变化或可靠判断 NATS 目标是否仍存活，相关状态必须暴露给监控。

单实例是发现控制面的单点，但不要求发现端短暂故障时立即中断所有既有 TCP RPC。生产环境应由 systemd、Kubernetes 等进程管理器自动拉起它；需要发现层自身高可用时使用 etcd。

### 5.6 初始全量、有序增量与背压

Origin 私有控制协议使用“首次全量、后续有序增量、缺口重新全量”：

- `DiscoveryService` 每次进程启动生成新的 `ServerEpoch`，当前 Epoch 内维护单调递增的
  `Revision`；
- 客户端完成注册后先取得 `ServerEpoch + Revision + FullSnapshot`；
- 后续注册、更新、主动撤销、Session 接管和 TTL 到期产生连续 Revision 的 Delta；
- Provider 先把 Delta 应用到自己的私有镜像，再向公共 Snapshot Sink 提交一份完整权威
  快照；
- Epoch 改变、Revision 不连续、帧校验失败或客户端本地镜像失效时，丢弃镜像并请求当前
  完整快照；
- 服务端不维护无限 Delta 历史，不能连续衔接时直接重新发送当前完整快照。

Delta 只保留两种 Node 级变化：

- `UpsertNode` 携带一份完整 RawNode；
- `DeleteNode` 携带 NodeID 与 SessionID；
- Service 增加、删除、退休或契约变化都形成所属 Node 的完整 Upsert；
- 心跳、重复 Publish 和内容无变化的 Publish 不增加 Revision、不广播 Delta；
- FullSnapshot 中 Node 按 NodeID 排序，每个 Node 内 Service 按 ServiceName 排序。

每条客户端连接只有一个固定有界发送队列。队列满时服务端关闭该慢连接，由客户端按恢复
流程重连并获取最新全量快照；不阻塞注册/TTL 处理，不静默丢 Delta，也不无限积累补发
历史。节点数、服务数、连接数、队列长度、单帧长度和完整快照大小使用 5.10 冻结的固定
上限。

### 5.7 新 ServerEpoch 的权威收敛

`DiscoveryService` 为纯内存单实例。服务端重启后，各 Node 会陆续重新注册；如果第一条
注册到达就把当前部分目录宣布为权威，会把尚未来得及重连的健康 Node 错误发布为 `Lost`，
随后又发布 `Discovered`。

因此只有新 `ServerEpoch` 冷启动使用一次收敛窗口：

- 服务端立即接受注册，但先报告 `Warming`，不发布部分目录为权威 FullSnapshot；
- 已经完成过本地发布的存活客户端收到 `Warming` 后，必须先把期望的完整 Node 记录重新注册，
  不能等待 FullSnapshot 后才注册；服务端据此在窗口结束前重建权威目录；
- 窗口固定为 `min(TTL / 3, 5s)`，最低 `1s`，不增加业务配置项；
- 已持有旧快照的客户端保持 `Recovering` 并继续遵守原来的一个 TTL 本地过期时间；
- 新启动且没有旧快照的 Provider 等待窗口结束和首个权威全量后，才完成 `Start`；
- 窗口结束时服务端发布一份权威 FullSnapshot，此后注册、撤销、Session 接管和 TTL
  到期全部立即产生 Delta，不再使用收敛窗口；
- 如果客户端旧快照先达到一个 TTL，仍立即清空，冷启动窗口不能无限延长旧事实。

该窗口只解决“服务端刚重启时还没有重新收齐注册”的权威建立问题，不是对已确认实例变化
做防抖。

### 5.8 可信内网安全边界

M17 Origin Provider 定位为可信内网发现，首版不实现 TLS、mTLS、Token 或自定义 HMAC：

- `listen` 必须显式配置，不提供隐式公网监听默认值；
- 部署必须使用防火墙、安全组、容器 NetworkPolicy 等限制控制端口；
- 不能把控制端口直接暴露到公网或其他不可信网络；
- Session 冲突规则只解决实例所有权，不构成身份认证；
- 不实现“明文 Token”这种看似认证、实际可被窃取的半套安全方案；
- 需要现成认证、TLS 和高可用时使用 M18 etcd Provider。

未来增加 Origin 安全层时在独立 TCP `net.Conn` 外包装标准 TLS，不修改 Provider SPI、
Full/Delta 语义、Directory、RPC 或业务 API；安全能力应作为独立里程碑完整设计，不能在
M17 预留未使用字段。

### 5.9 控制身份、同步与发布屏障

建立控制连接不等于发布当前 Node：

1. 客户端先发送 `Hello(NodeID, SessionID)` 建立控制身份；
2. 服务端返回携带当前 Epoch/Revision 和 `Warming/Ready` 的 HelloAck；Ready 时紧接
   FullSnapshot，Warming 时等待收敛窗口结束后再发送 FullSnapshot；
3. Provider 取得首个权威全量后才完成 `Start`；
4. Node 再按既有顺序执行全部业务 `OnStart`；
5. 全部成功后，Provider 发送携带完整本地 RawNode 的 `Publish`；
6. 服务端原子应用发布或 Session 接管，返回包含 Revision 的 `PublishAck`；
7. 收到 Ack 后当前 Node 才完成对外发布并进入 Ready。

这样新 Session 在 `OnStart` 失败时不会提前替换旧 Session。不同 Session 的待接管连接可以
先同步远端目录；只有其完整 RawNode 真正 Publish 成功时，才原子产生旧 Session `Lost` 和
新 Session `Discovered`。

`Publish` 不提供 Service 级部分更新。暂时失败只重试 Publish，不重新执行 `OnStart`。
正常停止发送 `Withdraw` 并等待 `WithdrawAck`；Stop Context 到期时停止等待，但仍继续本地
反序清理。

### 5.10 数值、字符串与容量边界

公共字段固定使用：

- SessionID：非零 `uint64`；
- ServerEpoch：每次服务端启动随机生成的非零 `uint64`；
- Revision：从 `1` 开始的 `uint64`，溢出时切换新 Epoch，禁止回绕；
- NodeID：1～63 字节小写 kebab-case；
- ServiceName：沿用框架名称规则并限制为 1～255 UTF-8 字节；
- TCP Address：1～255 字节的合法 `host:port`；
- Label Key：1～63 UTF-8 字节；
- Label Value：1～255 UTF-8 字节；
- 所有字符串拒绝非法 UTF-8、NUL 和控制字符，并在分配或转换为 `int` 前校验长度。

M17 使用固定框架上限，不增加 limits 配置：

| 资源 | 上限 |
|---|---:|
| 已发布 Node | 8192 |
| 控制连接，含同步中连接 | 16384 |
| 单 Node 公开 Service | 256 |
| 全域公开 Service 总数 | 65536 |
| 单 Node Label | 32 |
| 单个编码后 Node 记录 | 256 KiB |
| 单个 FullSnapshot/控制帧 Body | 16 MiB |
| 每客户端待发送发现消息 | 64 |

这些额度不预分配。达到注册、发布或快照上限时返回稳定容量错误；慢客户端积累 64 条
Delta 后关闭连接并通过全量重建恢复。FullSnapshot 不拆成无限分片；超过固定上限说明该
发现域不再适合单实例 Origin Provider，应改用 etcd 或重新评估架构。

### 5.11 TTL、超时与恢复默认值

Origin 只配置 TTL，其余控制参数派生：

- TTL 默认 `15s`，范围 `3s～5m`；
- 心跳周期为 `TTL / 3`，加入 ±10% 抖动；
- Dial、Hello 和单帧写超时使用 `clamp(TTL / 3, 1s, 5s)`；
- 每次心跳必须收到 Ack；超过下一个心跳时间仍未收到时立即进入 `Recovering`；
- 旧快照过期点按最后一次有效 Ack 的单调时间加 TTL 计算，不能因晚发现断线再延长；
- 重连退避从 `100ms` 指数增长到 `5s`，加入 ±20% 抖动；
- 启动期受 Start Context 限制，运行期持续恢复到 Application Stop；
- 连续稳定一个 TTL 后重置退避和连续失败计数；
- 协议、配置和容量等确定性错误立即失败，不进入持续网络重试。

最终配置面只保留：

```yaml
discovery:
  type: origin
  origin:
    ttl: 15s
    server:
      node: discovery-1
```

只有 `node` 必填，且必须存在并包含唯一的 `DiscoveryService`。TCP 的监听与拨号地址由该
Node 的 `nodes[].rpc.tcp.listen` 和 `advertise` 声明；NATS 的连接、命名空间和认证只在顶层
`rpc.nats` 声明一次。`server.listen` 和 `server.address` 为严格拒绝的旧字段。M17 不公开
heartbeat、grace、queue、frame、dial、retry、TLS 或 auth 字段。

### 5.12 精简 TCP 分帧

TCP 是没有消息边界的字节流，一次 Read 可能只读到半条消息，也可能同时读到多条消息，
因此长度分帧不能删除。M17 不重新实现分帧，直接复用 M5 已有的四字节长度前缀、完整帧
读取、超长校验和 Buffer 所有权。

Discovery Payload 只保留 `FrameType uint8 + Body`，不增加独立 WireVersion、ASCII
Magic、Checksum、Compression 或 Reserved。首帧必须是 `Hello`；将来只有真正不兼容的
布局才增加新的 Hello FrameType，例如 `HelloV2`。旧实现收到未知 Hello 类型立即关闭连接，
不猜测布局、不做复杂版本协商。

### 5.13 FrameType 与逐字段二进制布局

FrameType 固定分配为：

| 方向 | 值 | FrameType |
|---|---:|---|
| Client → Server | `0x01` | `Hello` |
| Client → Server | `0x02` | `Publish` |
| Client → Server | `0x03` | `Withdraw` |
| Client → Server | `0x04` | `Heartbeat` |
| Client → Server | `0x05` | `Resync` |
| Server → Client | `0x81` | `HelloAck` |
| Server → Client | `0x82` | `FullSnapshot` |
| Server → Client | `0x83` | `UpsertNode` |
| Server → Client | `0x84` | `DeleteNode` |
| Server → Client | `0x85` | `PublishAck` |
| Server → Client | `0x86` | `WithdrawAck` |
| Server → Client | `0x87` | `HeartbeatAck` |
| Server → Client | `0xFF` | `Error` |

首帧不是 `Hello`、方向错误、未知 FrameType、字段非法或存在尾随字节时，尽力返回
`Error(CodeTransportProtocol)` 后立即关闭连接。`HelloAck.SyncState` 只有
`Warming/Ready`；Warming 不是错误，也不增加独立帧。Ready 的 HelloAck 后立即发送
FullSnapshot；Warming 的连接在收敛窗口结束后再收到 FullSnapshot。

所有整数使用网络大端，不使用 JSON、Protobuf、反射、结构体内存布局或平台相关 padding。
字符串使用 `u8 length + UTF-8 bytes`；Node、Service、Label 的字段顺序固定为：

```text
Node =
  NodeID:str8 |
  SessionID:u64 |
  Transport:u8 |
  Address:str8 |
  LabelCount:u8 | repeated(LabelKey:str8 | LabelValue:str8) |
  ServiceCount:u16 | repeated(Service)

Service =
  ServiceName:str8 |
  State:u8 |
  ContractID:u64 |
  ContractFingerprint:[32]byte
```

Label 按 Key 严格升序，Service 按 ServiceName 严格升序；解码器拒绝重复或非规范顺序。
FullSnapshot 中 Node 按 NodeID 严格升序。所有数量、长度、剩余字节和乘加运算必须先校验
再分配；解码过程同时执行 5.10 的单 Node、全域和 Body 容量限制。

各 Body 固定为：

```text
Hello         = NodeID:str8 | SessionID:u64
HelloAck      = ServerEpoch:u64 | Revision:u64 | SyncState:u8
Publish       = Node
Withdraw      = empty
Heartbeat     = empty
Resync        = empty
FullSnapshot  = ServerEpoch:u64 | Revision:u64 |
                NodeCount:u16 | repeated(Node)
UpsertNode    = Revision:u64 | Node
DeleteNode    = Revision:u64 | NodeID:str8 | SessionID:u64
PublishAck    = Revision:u64
WithdrawAck   = Revision:u64
HeartbeatAck  = empty
Error         = Code:u32
```

空注册表从 Revision `0` 建立首个 FullSnapshot，第一次权威变化递增为 `1`；Warming
期间的 HelloAck 和幂等 Ack 使用当前 Revision。Epoch 只出现在 HelloAck 和
FullSnapshot：一条连接必须先越过 Full 屏障才接收 Delta，因此在每条 Delta 中重复 Epoch
没有增加判定能力。`u16` 已完整覆盖固定的 8192 Node 上限，比 `u32` 更紧凑。Error 不携带
远端动态文本、地址、配置或底层 error。

### 5.14 有序请求、Ack 丢失与幂等

一条控制连接内请求和响应有序，不增加 RequestID、操作序号或服务端去重缓存：

- 同一时刻只允许一个 Publish/Withdraw 状态变更等待 Ack；Heartbeat 使用独立帧类型识别
  且最多存在一个未 Ack 心跳；
- 相同 Node 内容的 Publish 返回当前 Revision，不递增、不广播；
- PublishAck 丢失或连接断开后，Provider 按当前完整发布期望重新发送 RawNode；
- Withdraw 只作用于 Hello 已绑定的精确 NodeID/SessionID，重复 Withdraw 返回当前 Revision；
- 旧 Session 不能撤销已经接管的当前 Session；
- Resync 无参数，服务端总是返回当前完整 FullSnapshot，不维护 Delta 补发区间。

因此重试表达的是“重新提交当前期望状态”，不是重复执行一次命令；正常重试不会制造新
Revision 或伪事件。

### 5.15 服务端 Actor、广播与 Buffer 所有权

`DiscoveryService` 使用一个系统 Actor 独占注册表、Session、ServerEpoch、Revision、客户端
逻辑状态和 TTL 到期提交。该 Actor 可以在基础设施 Prepare 阶段启动，不属于业务 Service
Runner，也不执行用户回调：

- M5 Handler 只校验最小帧外观并向 Actor 提交命令；
- Actor 命令队列固定为 32768，满时返回 `CodeDiscoveryCapacity` 并关闭来源连接；
- Actor 不执行阻塞式 socket 写入、业务回调或其他可能阻塞的操作；
- 一次注册表变化先原子提交事实和 Revision，再生成一份不可变编码消息；
- 每客户端直接复用 M5 已有的固定 64 帧 FIFO 发送队列和独占 Writer goroutine，溢出时
  `Conn.Send` 立即失败并关闭连接；
- Actor 生成不可变 Body；调用非阻塞 `Conn.Send` 前复制到该连接独占的
  `bufferpool.Buffer`；
- `Send` 成功后 Buffer 所有权完全转移给 M5，失败时由 Actor 立即释放；M5 队列满即关闭
  客户端，不改变 M5 的唯一 Buffer 所有权规则；
- 同一次 Delta 广播只编码一份 Body；FullSnapshot 在冷路径按当前注册表生成，不保留第二
  份长期可变缓存。

该设计不在 M5 Writer 之外再建立逻辑发送层、工作池或每客户端 goroutine，不引入共享
可变 Buffer、引用计数 Buffer 或 M5 API 旁路。相比重复建设第二层队列，这一收口保留了
同样的 FIFO、背压和所有权语义，状态更少。

### 5.16 TTL 到期调度

Actor 使用一只私有 `time.Timer` 驱动 generation 最小堆，不为每个 Node 创建 Timer 或
goroutine。该 Timer 属于发现基础设施并早于业务 Scheduler 启动，不依赖业务 Service 的
M8 时间轮；每次有效 Heartbeat/Ack 更新 Session generation 和单调时钟截止点，堆中旧
generation 到期项直接忽略，无需在热路径任意删除。

一次唤醒最多处理 1024 个有效到期 Session，仍有到期项时立即安排下一轮，避免大量同时
失效长期阻塞注册、心跳和 Withdraw。分批只限制单次 Actor 占用，不增加时间防抖；每个
Session 一旦轮到处理就立即删除并发布 Lost。

### 5.17 无需发布的 Node 与停止顺序

`private: true` 或当前没有公开业务 Service 的 Node 仍创建 Provider、完成首个远端权威
快照并维持同步，但不 Publish 空 Node，`DiscoveryStatus.Publication` 为 `NotRequired`。
它在 Provider、Transport 和本地生命周期满足条件后可以 Ready。`DiscoveryService` 的控制
面身份不作为普通业务 Service 写入 RawNode；若共置 Node 另有公开业务 Service，只发布
这些业务 Service。

正常停止顺序固定为：

1. 需要发布的 Node 提交 Withdraw 期望并在 Stop Context 内等待 WithdrawAck；
2. 停止新业务入站并按 M16 顺序排空、执行 Service/Module finalizer；
3. finalizer 结束后关闭该 Node 的 Provider 控制连接；
4. 同一 Application 中承载 DiscoveryService 的 Node 因为最先启动而最后停止；它的控制
   Listener 和 Actor 保持到其他 Node 已停止；
5. 最后拒绝新 Hello、关闭全部控制连接、停止 Actor，再释放快照与 Buffer 引用。

Stop Context 到期只停止等待远端 Ack，不跳过可安全执行的本地反序清理。DiscoveryService
与业务 Service 共置时，业务 finalizer 仍遵守普通 Service 逆序；控制 Listener/Actor 是
Node 基础设施资源，晚于这些 finalizer 释放。

### 5.18 Origin 实现验收矩阵

除 3.9 的公共 Provider 契约测试外，M17 Origin 实现必须完成：

1. FrameType、全部逐字段编解码、非法顺序、尾随数据和大小边界单测；
2. Decoder、帧状态机和 Node/FullSnapshot 输入 Fuzz；
3. 真实 TCP 多 Node 的 Hello、首次 Full、Publish、Delta、Withdraw 闭环；
4. ServerEpoch 重启、Warming、旧快照 TTL 和首个权威 Full 对账；
5. 相同 Session 重连、活跃旧 Session 冲突、断线后新 Session 接管及陈旧重连拒绝；
6. Revision 缺口、未知 FrameType、Resync 和无 Delta 历史时的 Full 重建；
7. 心跳 Ack 丢失、TTL 到期、退避恢复和稳定一个 TTL 后计数复位；
8. 命令队列、客户端逻辑队列和 M5 队列溢出时关闭慢连接且不阻塞 Actor；
9. 256 KiB Node、16 MiB Body 的等于上限成功与超过上限失败；
10. 8192 已发布 Node、16384 控制连接和 65536 Service 的模拟容量测试，并保留真实 socket
    子集验证；
11. Close、启动回滚、停止超时、重复关闭、goroutine 和 Buffer 所有权泄漏测试；
12. Windows/Linux、`go test -race` 以及可重复执行的编码、广播、FullSnapshot Benchmark。

Benchmark 保存 `allocs/op`、`B/op`、吞吐及 p50/p95/p99 基线；M17 在取得真实基线前不设置
缺乏依据的硬延迟 SLA。任何容量测试都不得通过预分配完整上限或降低生产校验规避真实边界。

## 6. etcd Provider

### 6.1 配置外观

```yaml
discovery:
  type: etcd
  etcd:
    endpoints:
      - https://etcd-1.example.com:2379
      - https://etcd-2.example.com:2379
      - https://etcd-3.example.com:2379
    # 可省略，默认 /origin；共享 etcd 集群时建议显式隔离项目或环境。
    namespace: /origin/game-prod
    local_network: cn-east
    watch_networks:
      - cn-north
    ttl: 15s
    dial_timeout: 5s
    request_timeout: 5s

    auth:
      username: origin
      password: change-me
      token: ""

    tls:
      ca_file: certs/etcd-ca.pem
      cert_file: certs/origin-client.pem
      key_file: certs/origin-client-key.pem
      server_name: etcd.example.com
      insecure_skip_verify: false
```

### 6.2 支持场景

- 单 endpoint 和 etcd 集群多 endpoint；
- 明文 HTTP；
- 使用系统根证书的 HTTPS；
- 自定义 CA 的 HTTPS；
- 双向 TLS；
- 无认证、用户名/密码认证和 Token 认证；
- 单网络和关注多个网络；
- Kubernetes ConfigMap/Secret 以文件片段挂载到配置目录。

### 6.3 校验和默认值

- `endpoints` 至少一个，必须显式使用 `http://` 或 `https://`，同一 Provider 不得混用；
- endpoint 禁止包含 Path、Query、Fragment 或 UserInfo，规范化、去重后保持配置顺序；
- 一个 Provider 的全部 Endpoint 必须属于同一个逻辑 etcd 集群；
- `namespace` 可省略，默认 `/origin`；显式值必须是非根绝对前缀，规范化后不能以 `/` 结尾；
- `local_network` 必填；有效读取范围为它与 `watch_networks` 的并集，自动去重并稳定排序；
- `watch_networks` 可以为空，不需要重复填写 `local_network`；有效网络最多 64 个；
- Node 只发布到 `local_network`，不能通过 `watch_networks` 向其他网络发布；
- `ttl` 默认 `15s`，范围 `3s～5m`，必须能精确表示为整数秒；
- `dial_timeout` 默认 `5s`；
- `request_timeout` 默认 `5s`，只限制一次 etcd 操作；
- `cert_file` 与 `key_file` 必须同时配置；
- `username` 与 `password` 必须同时配置，`token` 与它们互斥；
- HTTP 禁止出现任何 TLS 字段；
- HTTPS 最低使用 TLS 1.2；没有 `ca_file` 时使用系统根证书，配置后只信任指定 CA；
- `insecure_skip_verify` 默认关闭，启用时输出一次明确警告；
- TLS 相对路径统一相对于配置根目录解析；
- 密码、私钥内容和认证 Token 不得写入日志、错误详情或配置转储。

首版不暴露 etcd Client 的 gRPC KeepAlive、Endpoint 自动同步、自定义 DialOption、内部日志器和消息大小等高级字段。框架固定安全默认值，避免配置与具体 etcd 依赖版本耦合；真实部署出现明确需求后再增加独立高级配置。

### 6.4 依赖、兼容版本与集群边界

M18 固定直接依赖 `go.etcd.io/etcd/client/v3 v3.7.1`，由 Go Module 锁定其传递依赖；
生产代码不直接依赖或嵌入 etcd Server。集成测试至少覆盖 etcd Server `3.6.14+` 和
`3.7.x`，实现只使用这两个系列共同支持的 v3 API 能力。

每个 Node 拥有一个独立 Provider 和一个官方 etcd Client。该 Client 可以使用多个 Endpoint
连接同一个逻辑 etcd 集群，但 M18 不合并多个独立集群，也不启用 Endpoint AutoSync。首次
取得非零 ClusterID 后将其冻结；后续任一响应出现不同 ClusterID 时立即进入
`Recovering`，丢弃当前镜像并重建，避免把误配置的两套集群混成一个权威目录。单个
Endpoint 不可达不等于集群不可用，只要 Client 仍能通过同集群的其他 Endpoint完成操作。

### 6.5 Namespace、Network 与 Key

`namespace` 和 `network` 表达两个不同层次：

- `namespace` 是部署、环境或租户的完整发现域，例如 `/origin/game-prod`；
- `network` 是该发现域内部的网络可见性分区，例如 `cn-east`、`cn-north`；
- `local_network` 决定本 Node 写入哪个分区；
- `local_network + watch_networks` 决定本 Node 读取哪些分区；
- Provider 网络范围先于 M14 `allow_discovery`，后者继续按 Service 和 Label 过滤已进入
  当前 Node 原始发现目录的记录。

最终 Key 固定为：

```text
${namespace}/v1/networks/<network>/nodes/<nodeID>
```

其中 `v1` 是 etcd 持久化记录布局版本，不是 Origin TCP Wire 版本。Network 前缀使
每个 Provider 只需 Range/Watch 最多 64 个选中前缀，并且 RBAC 可以只授予本地前缀写权限
和关注前缀读权限。备选方案是 `${namespace}/v1/nodes/<nodeID>` 并把 Network 只放在
Value；它会要求所有 Node 读取整个 namespace 后本地过滤，增加无关 Watch 流量并扩大读
权限。`namespace` 的默认值为 `/origin`，共享 etcd 集群的项目可以显式覆盖，例如
`/origin/game-prod`。

无论最终选择哪种 Key，NodeID 在一个 Provider 的全部有效网络中必须全局唯一，因为 M14
Directory 仍以 NodeID 作为身份。不同网络出现相同 NodeID 时，Provider 不按网络顺序选择
胜者，而是把完整快照报告为 `CodeDiscoverySnapshotInvalid`。

### 6.6 etcd 记录

Value 使用专用、确定性 Protobuf `EtcdNodeRecordV1`，表达 M17 公共 Node DTO：

- NodeID、SessionID、Network、Transport 和 Address；
- 按 Key 排序的 Labels；
- 按 ServiceName 排序的完整公开 Services；
- ServiceState、ContractID 和 ContractFingerprint。

记录不复用 Origin 私有 TCP Wire，也不提供 JSON 或用户自定义 Codec。重复字段、非规范
排序、Key 与 Value 中的 NodeID/Network 不一致、未知枚举和非法 DTO 均拒绝。Protobuf
允许增加可忽略的兼容字段；需要不兼容语义时必须使用新的 Key 布局版本。单条编码记录最大
256 KiB，且仍受 M17 的单 Node Service、Label 和字符串限制。

### 6.7 原子发布与 Session 所有权

发布不能使用无条件 Put。固定流程为：

1. 对本 Node Key 做线性化读取，取得当前 Value、Version 和 ModRevision；
2. Key 不存在时，以 `Version == 0` 的 Txn 创建并绑定当前 Lease；
3. Key 已属于当前 Session 时，以读取到的 `ModRevision` 做 CAS 更新；
4. Key 属于其他 Session 时返回 `CodeDiscoveryDuplicateNode`，不覆盖旧记录；
5. CAS 竞争失败时重新读取并按相同规则判断，不能退化为最后写入者获胜；
6. 相同内容且仍绑定当前 Lease 时作为幂等成功，不制造无意义 Put 和 Watch 事件。

退休状态仍通过同一完整记录 Publish。新进程不能像 Origin Provider 那样依靠控制连接断开
立即接管；它必须等旧记录被主动删除或旧 Lease 过期，之后再用 `Version == 0` 创建。

### 6.8 Lease 生命周期

- 私有 Node 或规范化后没有公开 Service 的 Node 不发布记录，也不创建 Lease；
- 有发布需求时惰性 Grant 一个 Node 独占 Lease；
- Provider 先启动 KeepAlive，收到首个有效 KeepAlive 响应后才用 Txn 发布记录；
- KeepAlive channel 关闭、返回 nil、TTL 非正数或 Lease 已失效时立即进入
  `Recovering`；
- 恢复所有者授予新 Lease，并以当前完整发布期望重新执行 CAS Publish；
- Provider 不使用 `concurrency.Session`，避免引入并不需要的选举与锁语义；
- LeaseID 只存在于 Provider 内部，不进入 M17 Snapshot、Directory、状态或业务事件。

Lease 失效造成的权威 Key 删除立即反映到其他健康 Watch 并产生 Lost。当前 Node 自己的
Lease/连接失败只先报告 `Recovering`；框架继续按 M17 规则从最后有效 Ack 起保留旧远端
快照一个 TTL。

### 6.9 初始 Range、分页与 Watch 衔接

全部有效网络使用同一个快照 revision：

1. 第一个有效网络的第一页使用默认线性化 Range，按 Key 升序读取最多 32 条并取得全局
   revision `R`；
2. 其余网络及所有后续页固定使用 `R`，从上一页末尾 Key 的严格后继继续读取；
3. 每个网络在 `R` 完成完整 Range 后，从 `R + 1` 创建 Prefix Watch；
4. Watch 使用 `WithRequireLeader`、`WithFragment` 和创建通知；
5. 全部 Watch 建立后使用显式 progress 屏障，确认历史事件已经交付，再提交一次合并的
   完整权威快照并完成 `Start`。

固定 revision 的历史 Watch 负责覆盖 Range 与 Watch 建立之间的变化，因此不能沿用 v2
“先创建普通 Watch、再执行不带 revision 的 Get”。分页期间 revision 已被压缩时，丢弃该
前缀的临时结果并重新开始；分页数量和 Watch 参数不暴露为配置。

Provider 在累积过程中持续检查 M17 固定上限：最多 8192 个 Node、65536 个公开 Service、
16 MiB 完整快照和 256 KiB 单记录。达到上限立即返回
`CodeDiscoveryCapacity`，不能先无限读取再校验。

### 6.10 Watch 所有权、活性与提交

每个有效网络使用一条 Prefix Watch，最多 64 条。Watch 接收 goroutine 只把有界事件交给
一个 Provider owner；owner 串行维护各网络私有镜像、最新 revision、状态报告和
`Host.ReplaceSnapshot`，保证快照与状态的因果顺序。不得为每个 Key 创建 Watch 或
goroutine，也不得从整个 namespace 接收后再建立无界本地队列。

Watch revision 只要求单调，不能要求逐一连续，因为中间 revision 可能属于未关注 Key。
同一事务或同一 WatchResponse 被分片时，必须收齐 Fragment 后再原子应用，不能向 Host
暴露事务的部分结果。一次事务同时修改多个 Network 前缀时，owner 按 ModRevision 暂存
各 Watch 的变化，只有全部前缀都通过该 revision 后才向 Host 提交一份合并快照。内部
gRPC KeepAlive 和请求进度检测使用框架固定值；Provider 每
30 秒请求 Watch progress，并要求活动前缀在进度超时窗口内收到事件或进度响应。
`WithRequireLeader` 用于避免连接到失去 Leader 的分区成员后无限等待。

### 6.11 Compaction、断流与恢复

以下情况立即进入 `Recovering` 并停止提交新的 Host 快照：

- Watch 被 Compaction、Canceled 或返回不可继续的错误；
- Watch channel、gRPC 连接或进度检测失去活性；
- Range/Watch 返回不同 ClusterID；
- 私有镜像或记录校验失败；
- 运行期认证或权限被撤销。

普通前缀失败时重建该前缀，但在全部有效前缀重新健康前冻结合并快照提交；ClusterID 改变
时重建全部前缀。恢复完成后只提交一份新的完整快照，交给 M17 统一产生精确 Diff。恢复
使用单一所有者、有上限且带抖动的退避持续进行，直到 Application Stop；不能累积 Watch、
Client、goroutine 或待重放事件。

确定性配置、启动期认证和权限错误立即使 Start 失败。运行期认证或权限错误立即报告，不
伪装成普通短暂网络抖动；考虑到管理员可能在线修复权限，Provider 使用固定低频重试恢复，
但不刷日志或隐藏错误码。

### 6.12 非法远端数据

以下任一情况都使合并后的完整快照失败关闭：

- Key 结构非法，或 Key 与 Value 的 NodeID/Network 不一致；
- Protobuf 不可解析、Schema 不支持、枚举或字段非法；
- 单记录、Node、Service 或完整快照超过固定容量；
- 同一有效网络内 Key/Node 重复，或跨网络 NodeID 冲突；
- 同一记录内 Label、Service 重复或排序不规范。

Provider 不静默跳过坏记录，也不提交部分健康网络。它报告
`CodeDiscoverySnapshotInvalid` 并保留上一份有效镜像；M17 再按一个 TTL 的统一规则决定
何时清空旧远端快照。

### 6.13 认证、RBAC 与 TLS

认证只支持互斥的无认证、用户名/密码和 Token。M18 不创建用户或角色，只记录最小权限
部署模板：

- 对全部有效网络前缀具有 Range/Watch 权限；
- 对 `local_network` 的 Node 前缀具有 Range、Txn、Put 和 Delete 权限；
- 具有当前发布所需的 Lease Grant、KeepAlive 和 Revoke 能力。

共享凭据只能提供前缀级隔离；需要更强隔离时由部署为不同网络或 Node 配置独立用户、
角色或 mTLS 客户端证书。TLS 文件在 Client 创建时加载；不运行文件监听器，下一次 Client
重建时重新读取，因而 Secret 轮换会在后续重建生效。日志、状态和错误不得包含凭据、
证书内容、完整认证响应或带 UserInfo 的 Endpoint。

### 6.14 Withdraw、Close 与资源退出

Withdraw 对本 Node Key 做线性化读取，只在 SessionID 匹配时使用 ModRevision CAS Delete；
Key 已不存在或已属于其他 Session 时视为幂等成功，旧进程绝不能删除新进程记录。删除后
尽力 Revoke 自己的 Lease；Revoke 失败不改变已完成的精确 Delete 结果。

正常 Stop 不额外发布一个短暂 Retired Node，而是直接 Withdraw；业务 Service 主动进入
Retired 仍通过普通 Publish 更新完整记录。Close 取消 Range、Watch、KeepAlive、请求、
恢复和进度检查，等待全部自有 goroutine 退出，最后关闭官方 Client。Close 保持幂等，
返回后不得再调用 Host。

### 6.15 错误与状态映射

- Endpoint、namespace、网络、认证组合、TLS 文件和字段值非法：
  `CodeInvalidConfig`；
- 集群不可用、Watch 未同步、Lease/发布尚未恢复：
  `CodeDiscoveryUnavailable`；
- 不同 Session 占用同一 NodeID：`CodeDiscoveryDuplicateNode`；
- 记录、Node、Service 或快照超过固定上限：`CodeDiscoveryCapacity`；
- 远端记录、Key 或合并快照非法：`CodeDiscoverySnapshotInvalid`。

Provider 不新增 etcd 专属公开错误码。etcd cause 只用于本地诊断和结构化日志，不能进入
业务 API、稳定状态快照或跨网络协议。

## 7. 确认状态

### 7.1 M17 已确认结论

已确认：

1. 框架内置 `origin` 和 `etcd`，不实现 `static`，同时允许 Application 注册自定义 Provider；
2. Origin 内置发现端显式配置为保留名称 `DiscoveryService` 的普通 Service；
3. 一个 Origin 发现域首版只允许一个 `DiscoveryService`，但它可以与任意业务 Service
   配置在同一 Node；
4. 默认 TTL 为 `15s`，心跳周期为 `TTL / 3`；
5. 需要服务发现高可用时使用 etcd；
6. etcd 只公开部署场景所需字段，不直接暴露底层 Client 调优项；
7. Discovery Provider 配置位于顶层，整个项目只选择一套方案；
8. Application 不共享 Provider 实例或连接，每个 Node 根据顶层配置独立实例化并拥有自己的资源；
9. 公开 SPI 只有一个包、一个注册入口和最小 Factory/Provider 契约，复杂状态机由框架承担；
10. Provider 只提交完整权威快照，框架统一校验、差异和事件；
11. 控制连接断开立即报告 Recovering，但只在一个 TTL 后仍未恢复时清空旧快照；
12. 权威删除和恢复后的全量对账立即产生变化，不做事件防抖；
13. `AwaitService` 不混入 Transport 状态，Await RPC 自己等待可发送 TCP 候选；
14. M17 提供公开一致性测试，未来 Consul 必须通过同一公共契约；
15. Origin 控制通道固定使用独立 TCP，不复用业务 RPC Transport、连接或协议；
16. Origin 内部同步使用首次全量、连续 Revision Delta 和缺口全量重建；
17. 相同 NodeID 的活跃旧连接阻止新 Session；旧连接断开后新 Session 可以立即接管；
18. 慢客户端队列满时断开并通过全量重连恢复，不阻塞服务端或静默丢 Delta；
19. `DiscoveryService` 可以与业务 Service 共置，框架先 Prepare 控制 Listener，再完成
    当前 Node Provider 首次同步，最后按原顺序执行全部 `OnStart`；
20. 新 ServerEpoch 使用一次 1～5 秒固定收敛窗口，不能把部分重注册目录冒充权威快照；
21. M17 Origin Provider 只支持可信内网明文控制通道，不实现 TLS、认证或预留安全字段；
22. Hello 只建立控制身份和同步目录，完整 RawNode 在全部 `OnStart` 后单独 Publish；
23. Delta 只有完整 Node Upsert 和 Node Delete，无变化 Publish 不递增 Revision；
24. 已发布 Node 和控制连接上限分别为 8192 与 16384，其余固定容量见本章；
25. Origin 只配置 TTL 与 server.node；TCP/NATS 连接参数由顶层 rpc 和 Node RPC 端点提供，
    超时与退避由 TTL 派生；
26. TCP 长度分帧完全复用 M5，Discovery Payload 只有 FrameType 与 Body，不设独立
    WireVersion。
27. 第三方只实现一个 Provider 和一个 Factory；Context 只提供严格 Config、Host、身份和日志；
28. 公共 DTO 与内部 Directory/业务 DTO 隔离，Host 只允许完整快照和状态报告；
29. Provider 生命周期由框架串行，Host 提交由 Provider 串行，Close 返回后不得再回调；
30. DiscoveryStatus 使用固定状态、同步状态和 `NotRequired/Pending/Published` 发布枚举；
31. FrameType、手写大端二进制布局、严格排序和无尾随字节规则已经冻结；
32. 控制请求依靠单连接顺序和期望状态幂等，不增加 RequestID 或去重缓存；
33. DiscoveryService 使用单 Actor、有界命令队列，并直接复用 M5 有界发送队列与 Writer；
34. 同一次广播只编码一份消息，发送时复制到连接独占 M5 Buffer，不改变 M5 所有权；
35. TTL 使用单最小堆与 generation，不创建每 Node Timer/goroutine；
36. 私有或零公开 Service Node 仍同步但不发布空 Node；
37. M17 必须完成公共 providertest、Origin Wire/Fuzz/Race/容量/跨平台和资源泄漏验收；
38. Consul 映射已证明可仅增加 Provider 包和配置，不需要修改 Node、Directory、RPC 或业务
    API。

### 7.2 M18 第一轮确认

2026-07-30 已确认第一轮第 1、2、4～18 项推荐方案，包括依赖与兼容版本、单逻辑集群、
