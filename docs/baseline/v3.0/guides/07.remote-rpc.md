# 07：跨节点 RPC

## 我想先用 TCP 调用另一个 Node

从 TCP 开始，因为它不需要 NATS。运行：[examples/07-remote-rpc/01-tcp-two-nodes](../../../../examples/07-remote-rpc/01-tcp-two-nodes)。

### TCP 配置

下面是这个示例的完整配置。`discovery.origin.server.node` 只指出哪个 Node 承载
`DiscoveryService`；它的控制消息复用该 Node 的 RPC 传输，不再单独配置 `listen/address`。
顶层 `rpc` 声明整个 Application 共用的传输与连接参数，TCP 的地址仍由每个 Node 声明：

```yaml
log:
  console:
    enabled: true                 # 是否把日志输出到控制台。
    level: info                   # 最低日志级别；info 会输出常规运行信息。
    format: text                  # 控制台日志格式；示例使用便于阅读的文本格式。

rpc:
  transport: tcp                  # 整个 Application 使用 Origin TCP；不能在 Node 间混用传输。
  tcp:
    send_queue_messages: 16384    # 每条 TCP 连接的发送队列上限。
    read_idle_timeout: 15s        # 读空闲上限；0s 表示关闭应用层心跳。
    write_timeout: 15s            # 写出一个完整 TCP 帧的最长时间。

discovery:
  type: origin                    # 使用 Origin 内置服务发现，不依赖外部中间件。
  origin:
    ttl: 5s                       # 发现租约的保留时间；超过后未续租的实例会被视为过期。
    server:
      node: discovery-1           # 承载 DiscoveryService 的 Node ID。

nodes:
  - id: discovery-1               # 每个 Node 的唯一小写 kebab-case ID。
    rpc:
      tcp:
        listen: 127.0.0.1:18080   # RPC 和 Discovery 控制连接共同绑定的本机地址。
        advertise: 127.0.0.1:18080 # 其他 Node 连接 discovery-1 的可达地址。
    services:
      - DiscoveryService          # 在该 Node 上创建服务发现服务。
  - id: player-1
    rpc:
      tcp:
        listen: 127.0.0.1:18101   # player-1 本机绑定的 TCP 监听地址。
        advertise: 127.0.0.1:18101 # 发布给其他 Node 拨号的可达地址。
    services:
      - PlayerService             # 该 Node 对外提供的业务 Service 模板。
  - id: gateway-1
    rpc:
      tcp:
        listen: 127.0.0.1:18102   # gateway-1 本机绑定的 TCP 监听地址。
        advertise: 127.0.0.1:18102 # 发布给其他 Node 拨号的可达地址。
    services:
      - GatewayService             # 网关业务 Service，负责发起调用。
```

`listen` 是本机绑定地址，可以使用 `0.0.0.0:端口` 监听多个网卡；`advertise` 必须填写其他
Node 能够访问到的真实地址，不能写成 `0.0.0.0`。本地示例使用 `127.0.0.1`，只适合单机
多 Node 演示；部署到多台机器时应改成对应的内网地址，并确保端口可达。

该示例在同一个 Application 中启动发现服务、`gateway-1` 与 `player-1`，并由网关执行：

```go
// 派生一个只指向 player-1 的客户端值，不修改 s.players。
player, err := s.players.
    OnNode("player-1").
    // Await 仍在调用方 Service 的当前 Context 中完成。
    AwaitGetPlayer(ctx, playerID)
```

`OnNode` 适合已知目标 Node；未指定时，客户端从发现目录的 Running 实例中选择一个候选。

契约、客户端和静态 Dispatcher 与传输无关。每个示例把普通 `PlayerService` 实现放在
自己的业务目录，只复用 `_support/tutorialrpc` 中的契约和 `player_service.rpc.gen.go`；
业务 Service 不需要生成文件。

## 如果项目使用 NATS

NATS 是需要独立部署和运维的第三方 Transport，不属于框架基础教程。项目确定使用 NATS 时，阅读
[使用 NATS 承载跨节点 RPC](../../../extensions/nats-rpc.md)；RPC 契约、业务客户端和下面的路由规则
不会因 Transport 改变。

## 我想按业务键选择实例或广播

运行：[examples/07-remote-rpc/03-route-and-broadcast](../../../../examples/07-remote-rpc/03-route-and-broadcast)。

这里的“实例”是一个已经启动的 `PlayerService` 服务运行时，以 `NodeID + 实际 ServiceName`
唯一标识。每次单目标调用都会从当前 Runtime 可见的最新发现快照中生成候选列表：先匹配目标
ServiceName 与 RPC 契约，再按生命周期、传输兼容性和连接就绪状态过滤；默认只保留 `Running`
实例。候选按 `NodeID`、`ServiceName` 升序稳定排列，不能依赖 Discovery Provider 原始返回顺序。

```go
// Route 在本次调用读取的候选列表中选一个 PlayerService 实例：整数 playerID 直接转换为
// uint64，随后按 playerID % 候选数取下标；候选列表不变时，同一 playerID 会落到同一 Node。
// string 和 []byte Key 则先按 FNV-1a 64 位哈希，再按同样规则取模；这不是一致性哈希，实例
// 上下线或候选顺序改变时，已有 playerID 可能映射到不同 Node，不能把它当作玩家状态所有权目录。
client.Route(playerID).AwaitGetPlayer(ctx, playerID)

// RouteRoundRobin 使用当前 Node 的 Runtime 级原子计数器，在同一服务、契约和目标范围的候选
// 列表中按递增计数 % 候选数轮换。它用于尽量分摊请求，但不保证跨调用方 Node 的全局严格轮询，
// 也不保证同一 playerID 固定命中同一实例；需要稳定映射时使用上面的 Route(playerID)。
roundRobinClient := client.RouteRoundRobin()
roundRobinClient.AwaitGetPlayer(ctx, playerID)

// RouteRandom 为每次调用生成快速伪随机值，并按该值 % 候选数选择一个已过滤、已就绪的实例。
// 它适合不要求会话粘性且可接受短期不均衡的负载分散；随机序列不可复现，也不用于安全用途。
randomClient := client.RouteRandom()
randomClient.NotifyRefresh(ctx, version)

// RouteBy 把同一份已过滤候选列表以只读 RouteCandidates 交给业务，例如按 region 标签优先选择。
// Selector 只能返回列表下标，不能加入或绕过已被过滤的实例；它必须同步、快速、可安全并发调用，
// 返回 false 表示当前没有合适候选，越界下标或 panic 会使这次调用以路由错误失败。
customClient := client.RouteBy(selector)
customClient.AwaitGetPlayer(ctx, playerID)

// BroadcastRefresh 不执行上面的单目标策略；它在本次广播快照中向全部合格 PlayerService 实例
// 提交无响应的 Refresh 通知。提交成功只表示本地传输接受了通知，不表示每个远端实例已经处理；
// 单个目标失败会被汇总到 BroadcastError，不能被静默忽略。
client.BroadcastRefresh(ctx, version)
```

以上方法都返回派生客户端值，不会修改基础 `client`；候选也不会在派生时固定，而是在实际调用
时从最新快照重新计算。单目标路由只影响 `Await`、`Call`、`Async` 和 `Notify`；`Broadcast`
忽略 `RouteRoundRobin`、`RouteRandom`、`Route(key)` 和 `RouteBy`，但会保留 `OnNode` 对精确
目标范围的限制。需要按标签或其他业务条件广播子集时，先从发现结果中筛出 NodeID，再对各个
`OnNode(nodeID)` 分别发送通知。检查返回的 `*rpc.BroadcastError`，读取成功数量和每个失败目标。

## 深入一点

默认自动选择会排除 `Retired` 实例：当客户端没有用 `OnNode` 指定唯一 Node，而是通过
默认选择、`RouteRoundRobin`、`RouteRandom`、`Route(key)` 或 `RouteBy` 为 `Await`、`Call`、
`Async`、`Notify` 选择候选时，只会从 `Running` 实例中选择；`Broadcast` 默认也只发送给
`Running` 实例。这样可以避免新请求继续进入已经准备下线的实例。

如果业务确实需要在排空、迁移或兼容旧实例期间继续访问 `Retired`，显式派生一个包含它们的
客户端值：

```go
client := tutorialrpc.BindPlayerService(s)

// 自动路由现在同时允许 Running 和 Retired；基础 client 仍保持默认规则。
retiredAware := client.IncludeRetired()
value, err := retiredAware.RouteRoundRobin().AwaitGetPlayer(ctx, playerID)
if err != nil {
    // 仍需处理无候选、连接不可用和调用超时等错误。
}

// IncludeRetired 同样可以与 Broadcast 组合，让通知覆盖 Retired 实例。
err = retiredAware.BroadcastRefresh(ctx, version)
```

`IncludeRetired()` 只改变候选生命周期过滤，不改变路由策略，也不修改原始客户端。若使用
`OnNode("player-1")` 精确指定目标，精确目标本身允许为 `Retired`，因此不需要额外调用
`IncludeRetired()`。远端发现事实、TCP/NATS 连接就绪和单次调用超时是不同状态：发现到实例
不表示其连接已可用，调用仍需处理超时与传输不可用错误。
