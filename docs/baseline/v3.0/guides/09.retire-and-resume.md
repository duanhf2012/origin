# 09：Retire、Resume 与优雅停止

## 我想让运行中的整个 Application 退休

运行：[examples/09-retire-and-resume/01-service-retire-resume](../../../../examples/09-retire-and-resume/01-service-retire-resume)。这个示例使用两个终端，控制的是同一 Application 中的全部 Node，而不是只控制 `start` 时的某个 Node。

终端 A 正常启动目标；所有 Service 完成 `OnInit`、`OnStart` 后进入 `Running`：

```text
game-server start --app-name game --config ./config --pid-dir ./run
```

终端 B 使用相同的 AppName 和 PID 目录执行：

```text
game-server retire --app-name game --pid-dir ./run --timeout 30s
```

目标进程收到请求后，Application 按 Node 启动顺序的倒序调用 `Node.Retire`，每个 Node 再按 Service 启动顺序的倒序退休。命令返回成功时，全部可转换 Service 已处理完成，且相应发现发布已确认。

`retire` 是一级子命令，不与 `start` 同时使用；start 不提供初始退休选项。AppName 定位的是整个 Application 进程，因此命令不接收 `--node`。

## 我想监听退休和恢复事件

在 Service 的 `OnInit` 中注册本地状态事件：

```go
func (s *MaintenanceService) OnInit() error {
    return s.SubscribeEvent(
        service.ServiceStateChangedEventID,
        func(_ context.Context, raw service.Event) error {
            changed := raw.(service.ServiceStateChanged)
            s.Logger().Info(
                "service state changed: " +
                    changed.Previous.String() + " -> " + changed.Current.String(),
            )
            return nil
        },
    )
}
```

`ServiceStateChanged` 提供 `Previous`、`Current` 和 `ChangedAt`。只有真实的 `Running -> Retired` 或 `Retired -> Running` 转换才投递事件；在 Retired 上重复 Retire、在 Running 上重复 Resume 都幂等成功，不重复投递。

这是当前 Service 的本地事件，监听器在所属 Service Runner 中异步执行。它不同于 discovery 的远端状态变化监听：后者表示其他 Node 看到的发现快照变化。事件监听器返回错误或 panic 会按本地事件隔离规则记录，但不会回滚已经提交的状态。

## 我想恢复整个 Application

维护完成后在终端 B 执行：

```text
game-server resume --app-name game --pid-dir ./run --timeout 30s
```

Resume 使用正序：Application 按 Node 启动顺序恢复，每个 Node 按 Service 启动顺序恢复，让依赖先重新进入默认候选。Resume 不重新执行 `OnInit` 或 `OnStart`。

## `--timeout 30s` 到底限制什么

它是当前外部控制命令的总等待上限，覆盖：定位目标、等待同 AppName 控制锁、投递请求、目标 Application 执行以及等待响应。它不是 Service 内部 Timer，也不是强制关闭期限。

timeout 到达时：

- 命令以 `ExitControlTimeout`（进程退出码 `4`）和 `CodeDeadlineExceeded` 返回；
- 目标进程继续运行，不会被 Kill；
- 已经完成的 Service 状态不会回滚；
- 批量操作是 best-effort，可能已有部分 Service 提交状态；
- 应读取日志、Diagnostics 和发现状态确认实际结果，再决定重试 Retire、Resume 或告警。

一个 Node/Service 失败不会跳过后续对象，最终错误会聚合。发现发布失败也不回滚本地状态；发布协调器保留最新期望并在 Provider 恢复后重试。

## Retire 与 Stop 有什么区别

Retire 是可恢复的运行状态：不调用 `OnStop`，不关闭 TCP/NATS，不暂停 Timer，也不自动排空任务。Retired Service 仍可处理精确管理、存档和恢复类工作。

Stop 才进入一次性关闭流程。完成维护后如果需要结束进程，执行：

```text
game-server stop --app-name game --pid-dir ./run --timeout 30s
```

Stop 使 Running 或 Retired 进入 Stopping，排空调度、执行 `OnStop` 并释放资源；Stopped/Failed 不能通过 Resume 复活。

## 我只想控制单个 Service 或 Node

进程内管理代码继续使用 Go API：

```go
if err := targetService.Retire(ctx); err != nil {
    return err
}
if err := targetService.Resume(ctx); err != nil {
    return err
}

if err := targetNode.Retire(ctx); err != nil {
    return err
}
return targetNode.Resume(ctx)
```

`Application.Retire/Resume` 使用与 CLI 相同的批量顺序。CLI 面向整个 Application，不提供 Node/Service 过滤；精确编排应留在受控的进程内代码中。批量 API 示例见 [02-node-and-application](../../../../examples/09-retire-and-resume/02-node-and-application)。

## 我仍需要调用 Retired Service

默认自动单目标和 Broadcast 排除 Retired。精确 `OnNode` 仍可命中；自动选择确有维护需求时，显式派生 `IncludeRetired()`：

```go
value, err := players.IncludeRetired().AwaitGetPlayer(ctx, playerID)
```

见 [03-include-retired](../../../../examples/09-retire-and-resume/03-include-retired)。不要把 `IncludeRetired()` 当作普通失败后的兜底重试；业务应明确哪些操作允许在退休期间继续执行。
