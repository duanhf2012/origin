# 08：服务发现

## 我想使用 Origin 内置发现

运行：[examples/08-discovery/01-origin-provider](../../../../examples/08-discovery/01-origin-provider)。

Origin Provider 需要在任意一个 Node 配置唯一 `DiscoveryService`，并在顶层选择
`discovery.type: origin`。它复用 Application 的 RPC 传输；下面使用不依赖第三方基础设施的 TCP。
项目选择 NATS 时，先完成独立的 [NATS RPC 教程](../../../extensions/nats-rpc.md)：

```yaml
rpc:
  # 整个 Application 统一使用的远程传输。
  transport: tcp
  tcp:
    # 每条 TCP 连接可排队等待发送的完整消息数。
    send_queue_messages: 16384
    # 读空闲上限；0s 表示关闭应用层心跳。
    read_idle_timeout: 15s
    # 写出一个完整 TCP 帧的最长时间。
    write_timeout: 15s

discovery:
  # 选择内置 Origin 发现 Provider。
  type: origin
  origin:
    # 服务目录失联后的存活租约。
    ttl: 5s
    server:
      # DiscoveryService 所在 Node。
      node: discovery-1

nodes:
  - id: discovery-1
    rpc:
      tcp:
        # RPC 与 Discovery 控制连接复用的本机监听地址；允许通配监听地址。
        listen: 0.0.0.0:18080
        # 其他 Node 实际拨号的可达地址，不能使用通配地址。
        advertise: 10.0.0.10:18080
    services: [DiscoveryService]
```

`DiscoveryService` 可以与该 Node 的其他 Service 共存，不要求专用 Node。`server.node` 是唯一
引导信息：TCP 会从该 Node 的 `rpc.tcp.advertise` 获取地址并建立独立控制连接，NATS 则在
已有 NATS Connection 上使用框架保留 Subject。因此不能再配置 `server.listen` 或
`server.address`；它们会在启动前作为未知字段拒绝。

## 如果项目使用 etcd

etcd 是需要独立部署和运维的第三方 Provider。项目确定使用 etcd 时，阅读

## 我想按游戏类型筛选服务

下面的 `labels` 和 `allow_discovery` 是 Node 的公共配置，Origin、etcd 和自定义 Provider
都支持。

假设游戏分区一同时运行战斗房间和棋牌房间，它们都提供 `RoomService`。先给提供服务的 Node 添加游戏类型标签：

```yaml
nodes:
  - id: battle-room-1
    labels:
      # 给当前 Node 发布的服务记录添加游戏类型标签。
      game_type: battle
    services: [RoomService]

  - id: card-room-1
    labels:
      game_type: card
    services: [RoomService]
```

分区一的网关只允许发现战斗类 `RoomService`：

```yaml
nodes:
  - id: gateway-1
    services: [GatewayService]
    # 指定当前 Node 允许发现哪些远端服务。
    allow_discovery:
      - services: [RoomService]
        node_labels:
          # 根据远端 Node 的 nodes.labels 标签筛选服务。
          game_type: battle
```

`gateway-1` 最终能发现 `battle-room-1.RoomService`，不会发现 `card-room-1.RoomService`。

这里的配置分别表示：

- `nodes[].labels`：给当前 Node 发布的服务记录添加标签；
- `nodes[].allow_discovery`：指定当前 Node 允许发现哪些服务；
- `nodes[].allow_discovery[].node_labels`：根据远端 Node 的 `nodes[].labels` 筛选服务。

一条规则可以允许多个服务名，多个服务名是“或”关系：

```yaml
allow_discovery:
  - services: [RoomService, MatchService]
    node_labels:
      game_type: battle
```

这表示允许发现 `game_type=battle` 的 `RoomService` 或 `MatchService`。

如果省略规则中的 `services`，则不限制远端 Service 名称，只按其他条件筛选：

```yaml
allow_discovery:
  - node_labels:
      # 发现 game_type=battle 的全部公开 Service。
      game_type: battle
```

`services: []` 不是“发现零个 Service”的写法，而是无效配置，会在启动前拒绝。需要关闭当前 Node 的全部远端业务服务发现时，应直接写：

```yaml
allow_discovery: []
```

`labels` 也可以使用紧凑 YAML 写法：

```yaml
labels: {game_type: battle}
```

### 深入一点：自定义标签键

标签名和值由业务定义，只要都是非空字符串即可。一个 Node 也可以添加多个标签：

```yaml
nodes:
  - id: battle-room-1
    labels:
      game_type: battle
      game_mode: ranked
      version: v1
    services: [RoomService]
```

每个标签键只能填写一个值；筛选条件引用同名标签时才会参与筛选。

### 深入一点：筛选多个候选值

使用方可以让同一个标签键接受多个值。例如，网关同时发现战斗类和棋牌类房间：

```yaml
nodes:
  - id: gateway-1
    services: [GatewayService]
    allow_discovery:
      - services: [RoomService]
        node_labels:
          # game_type=battle 或 game_type=card 均可匹配。
          game_type: [battle, card]
```

同一个标签键的多个候选值是“或”关系。

### 深入一点：按多个维度同时筛选

同一条规则中的不同标签键必须同时满足。例如，只发现战斗类排位房间：

```yaml
nodes:
  - id: gateway-1
    services: [GatewayService]
    allow_discovery:
      - services: [RoomService]
        node_labels:
          game_type: battle
          game_mode: ranked
```

目标 Node 必须同时具有 `game_type=battle` 和 `game_mode=ranked`。`services` 与 `node_labels` 之间也是“且”关系。

同一条规则中的多个服务名是“或”关系；如果同时配置 `services` 和 `node_labels`，服务名条件与所有标签条件之间是“且”关系。例如：

```yaml
allow_discovery:
  - services: [RoomService, MatchService]
    node_labels:
      game_type: battle
      game_mode: ranked
```

它表示发现战斗类排位玩法的 `RoomService` 或 `MatchService`。

### 深入一点：使用多条筛选规则

需要表达两组独立条件时，增加多条规则。规则之间是“或”关系：

```yaml
allow_discovery:
  # 规则一：战斗类且排位房间。
  - services: [RoomService]
    node_labels:
      game_type: battle
      game_mode: ranked
  # 规则二：棋牌类房间，不限制玩法模式。
  - services: [RoomService]
    node_labels:
      game_type: card
```

满足规则一或规则二的服务都会被发现。标签匹配使用区分大小写的精确比较，不支持通配符或正则表达式。

### 深入一点：默认范围与发现网络

完全省略 `allow_discovery` 时，Node 会发现 Provider 范围内的全部公开 Service；明确配置 `allow_discovery: []` 时，不发现任何远端业务 Service。空规则（例如 `- {}`）没有明确筛选意图，会作为配置错误拒绝启动。

标签筛选既适用于 etcd Provider，也适用于 Origin Provider 和第三方 Provider；它们只负责提供目录，筛选规则由框架统一执行。

## 我想监听上线、下线和 Lost

服务发现不只是用来“找到一个 RPC 地址”，业务通常还需要知道远端实例什么时候出现、状态什么时候变化、什么时候已经不能再使用。监听器就是接收这些可见目录变化的入口。

运行：[examples/08-discovery/03-watch-and-lost](../../../../examples/08-discovery/03-watch-and-lost)。这个示例不依赖 etcd 或真实网络，而是注册一个可控的内存 Provider，故意按以下时间线提交快照：

```text
启动
  │
  ├─ Provider 发布 player-1:PlayerService (Running)
  │       └─ 监听器收到 OnDiscovered
  │
  └─ 500ms 后 Provider 发布空快照
          └─ 监听器收到 OnLost
```

示例中 `watcher-1` 是本地 Node，`DiscoveryWatcherService` 在 `OnInit` 中注册监听器。完整可运行代码见：[03-watch-and-lost/main.go](../../../../examples/08-discovery/03-watch-and-lost/main.go)。

```go
func (target *DiscoveryWatcherService) OnInit() error {
    // 监听器归属于当前 Service；进入 OnStop 前由框架自动移除。
    _, err := target.AddDiscoveryListener(target)
    return err
}
```

正常随 Service 生命周期结束的监听不需要保存 `ListenerID`。停止流程会先停止发现事件准入并删除该 Service 的全部监听器，再排空已经接收的任务，最后调用 `OnStop`。只有需要在 Service 仍运行时提前取消某一项监听，才需要保存返回 ID 并调用 `RemoveDiscoveryListener`。

监听器需要实现三个回调：

| 回调 | 什么时候触发 | 业务通常做什么 |
| --- | --- | --- |
| `OnDiscovered` | 远端 Service 从不可见变为可见，或新会话重新出现 | 建立候选、刷新路由、解除降级 |
| `OnStateChanged` | 同一个远端 Service 的 `Running/Retired` 状态变化 | 更新状态、暂停或恢复业务流量 |
| `OnLost` | 已经可见的远端 Service 不再出现在权威快照中 | 移除候选、断开关联、重试、降级或告警 |

每个回调收到一个 `discovery.Event`：

```go
func (target *DiscoveryWatcherService) OnDiscovered(_ context.Context, event discovery.Event) {
    // event.NodeID 是发生变化的远端 Node；Services 可能一次包含多个 Service。
    target.Logger().Info(fmt.Sprintf(
        "discovered node=%s services=%v", event.NodeID, event.Services,
    ))
}

func (target *DiscoveryWatcherService) OnStateChanged(_ context.Context, event discovery.Event) {
    // Running/Retired 等状态变化在这里处理。
    target.Logger().Info(fmt.Sprintf(
        "state changed node=%s services=%v", event.NodeID, event.Services,
    ))
}

func (target *DiscoveryWatcherService) OnLost(_ context.Context, event discovery.Event) {
    target.Logger().Info(fmt.Sprintf(
        "lost node=%s services=%v", event.NodeID, event.Services,
    ))
}
```

`Lost` 与 `Retired` 不是一回事：`Retired` 仍在发现快照中，只触发 `OnStateChanged`；
`Lost` 表示实例已经从当前可见快照中消失。

权威记录被删除时不做防抖，立即产生 `Lost`。如果是当前 Node 自己与 Origin 或 etcd
失去连接，Provider 先进入 `Recovering` 并保留最后快照；超过一个 TTL 仍未恢复时，才清空
快照并产生 `Lost`。监听器回调跨异步等待后，应重新查询当前快照。

执行 `run.bat` 或 `./run.sh` 后，预期先看到类似 `discovered node=player-1`，约 500ms 后看到 `lost node=player-1`。该示例的 Provider 实现见：[03-watch-and-lost/main.go](../../../../examples/08-discovery/03-watch-and-lost/main.go)。

## 我想等待远端服务出现

运行：[examples/08-discovery/05-await-service](../../../../examples/08-discovery/05-await-service)。在启动依赖另一个 Node 时，先等待发现目录出现目标，再读取其快照：

```go
if err := s.AwaitService(ctx, "PlayerService"); err != nil {
    // 任意 Node 上都没有目标、超时或取消时结束当前流程。
    return err
}
if err := s.AwaitNodeService(ctx, "player-1", "PlayerService"); err != nil {
    // 指定 Node 尚未发布目标 Service 时继续等待或返回错误。
    return err
}
// 读取指定 Node 的当前发现快照。
instance, ok := s.FindDiscoveredService("player-1", "PlayerService")
// 读取全部同名 Service 候选快照。
instances := s.ListDiscoveredServices("PlayerService")
```

`AwaitService` 等待任意 Node 上的指定 Service；`AwaitNodeService` 等待明确 Node；`FindDiscoveredService` 和 `ListDiscoveredServices` 读取当前快照。两种等待都复用 `Service.Await`，应传入生命周期或当前业务任务的 `Context`，并处理超时和取消。监听器通过 `AddDiscoveryListener` 注册，随 Service 停止时由框架自动移除；只有需要提前取消时才调用 `RemoveDiscoveryListener`。

## 深入一点：安全和边界

Origin 内置发现应部署在受限网络中。第三方 Provider 的认证和 TLS 见各自扩展教程。Provider 只能
报告规范化快照，框架负责目录更新、路由唤醒和发布顺序。
