# 11：性能测试与容量理解

## 我想自己运行 RPC 基准测试

运行：[本地 Await](../../../../examples/11-performance/01-local-rpc-benchmark)、
[TCP Await](../../../../examples/11-performance/02-tcp-rpc-benchmark) 或
[NATS Await](../../../../examples/11-performance/03-nats-rpc-benchmark)。三个 `run` 脚本都使用真实生成客户端；
TCP/NATS 还覆盖真实回环 Transport。它们用于快速回归，不代表并发容量上限。

```bash
# 只运行指定 Benchmark，跳过普通测试；benchmem 输出分配指标。
go test ./tests/integration/rpcfixture -run '^$' \
  -bench '^BenchmarkGeneratedRemoteLoopback$' -benchmem -benchtime=3s
```

普通 Benchmark 输出平均 `ns/op`、`B/op`、`allocs/op`；TCP/NATS 的 `MB/s` 按请求业务 Payload
计算，不包含响应、协议头或链路总字节。不要把它写成网络带宽。Ubuntu 还可单独观察分位数：

```bash
go test ./tests/integration/rpcfixture -run '^$' \
  -bench '^BenchmarkGenerated(Local|Remote|NATS)AwaitLatency$' \
  -benchtime=1s -count=3
```

分位数 Benchmark 每次调用额外读取时钟，只用于比较 P50/P95/P99；平均热路径仍看前三个普通
Benchmark。该入口不在 Windows 构建，因为微秒级 `time.Now` 精度不足以稳定输出分位数。

若修改了 RPC、调度、Codec 或 Transport，可先用内嵌依赖的短矩阵验证 24 个分支：

```bash
ORIGIN_M22_RPC_PERF_SHORT=1 \
  go test ./tests/integration/rpcfixture \
  -run '^TestM22RPCPerformanceMatrix$' -count=1 -v
```

短矩阵只验证场景、统计与清理链路，不能作为性能数据。正式矩阵需要真实 etcd/NATS、固定环境、
5 秒预热、15 秒测量和 3 轮结果，留到发布性能验收执行。

## 我该看什么指标

- QPS：每秒完成的请求数；只有业务响应和回调完成才算一次完成。
- TPS：每秒完成的业务事务数；一个事务可以包含多个 RPC。
- 延迟：单次完成时间，应同时观察平均值和分位数。
- 吞吐：单位时间传输的字节量；大 Payload 时比单纯 QPS 更有意义。

先固定 Commit、Go 版本、机器、`GOMAXPROCS`、并发、Payload、Transport、依赖版本和采样参数，
预热后至少运行三轮并比较中位数。测试期间避免编译、杀毒扫描、节能模式和其他高负载任务。
不要把某台机器上的回环 TCP/NATS 结果外推为生产 SLA；代码没有变化但环境不同的结果也不能
直接判定为回归。
