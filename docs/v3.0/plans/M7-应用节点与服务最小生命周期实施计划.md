# M7 应用节点与服务最小生命周期实施计划

状态：已完成实施并通过完整验证。

## 一、实施边界

M7 只建立 `Application → Node → Service` 最小生命周期，不提前接入 RPC、TCP/NATS、
Discovery、Timer、Module 或 Service Runner。M5、M6 已完成的传输库保持独立，后续由
RPC 适配层组合。

## 二、实施顺序

1. 建立 `service` 包的最小生命周期接口、默认基类和只读 Runtime。
2. 建立 `node` 包的有序 Service 容器、状态机、panic 边界和反序清理。
3. 建立 `application` 私有 Service 类型目录，实现 `app.Setup` 和模板实例化。
4. 从配置目录解析 M7 已实现的 `log`、`buffer_pool`、`nodes`。
5. 接入 M4 Runner、PID 运行权、自定义命令和运行 Context。
6. 实现多 Node 顺序启动、失败回滚、正常反序停止和日志最终错误。
7. 增加单元测试、命令集成测试、示例工程和跨平台构建验证。

## 三、验收重点

- `OnInit` 失败的 Node 不调用任何 `OnStart/OnStop`；
- `OnStart` 失败的 Service 及此前进入过 `OnStart` 的 Service 均执行反序 `OnStop`；
- 一个 Node 失败时，已经成功的 Node 严格反序停止；
- 原始业务 error、Origin 错误码、NodeID、ServiceName、阶段和 panic 堆栈不丢失；
- 同一模板在不同 Node 或同一 Node 的多个实际名称下生成独立实例；
- 并发 Stop 不丢失，停止 Context 不复用已经取消的运行 Context；
- 日志 Runtime 最后关闭，PID 锁在 Start Handler 返回后由 M4 释放；
- Windows、Linux、竞态检测和仓库全量测试通过。

## 四、实际验证结果

- Windows 全仓单元与集成测试通过；
- Windows 全仓竞态检测和 `go vet` 通过；
- Application、Node、Service 覆盖率约为 81%、88%、78%；
- Node 本地 ServiceName 查询约 `10 ns/op`、`0 B/op`、`0 allocs/op`；
- Windows 示例进程 start/stop、PID 锁和反序 OnStop 通过；
- Ubuntu 使用 Go 1.26.5 容器完成全仓普通测试、竞态测试、示例构建和实际
  start/stop；
- Linux 测试发现的 M3 目录符号链接误判已修复，并在 Windows/Linux 回归通过。
