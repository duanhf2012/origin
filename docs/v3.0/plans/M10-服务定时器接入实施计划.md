# Origin 第三版 M10 服务定时器接入实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`
> 逐项执行本计划。所有执行步骤使用复选框跟踪。

**Goal:** 在 M8 Node 时间轮和 M9 Service 单执行权调度器之上，实现可直接由业务 Service
使用的一次性、周期和 Cron 定时器完整闭环。

**Architecture:** 每个 Node 继续只拥有一个 M8 `TimerEngine`，每个 Service Scheduler
保存自己的业务 Timer 容器、Deadline Binding 和到期待准入队列。时间轮只交付内部 ID，
Timer 回调统一转换成 M9 根任务并在所属 Service 的唯一执行槽中运行；Node 负责全局唯一
TimerID 和三百万共享额度。

**Tech Stack:** Go 1.26.5、现有 `internal/timerwheel`、现有
`internal/container/ringqueue`、`sync.Pool`、`github.com/robfig/cron/v3 v3.0.1`。

## Global Constraints

- 严格遵守 [开发指导原则](../../../AGENTS.md)，尤其是精简实现、中文注释、资源所有权、有界
  队列、TDD、性能验证和里程碑提交规则。
- 只实现 [M10 服务定时器接入设计](../design/milestones/M10-服务定时器接入设计.md)
  已确认范围；不实现 Module、退休、RPC 系统 Timer、固定步长、持久化 Timer 或指标后端。
- 默认每 Node 最多 `3000000` 个业务 Timer，全部 Service 共享额度；该值只是硬上限，不能
  按上限预分配 Timer、Map 或队列内存。
- NewTicker/Cron 第 `99` 次连续 panic 后停止安排第 100 次及后续回调；任意一次正常返回
  都立即把连续计数清零。
- 默认 Cron 时区为创建 Application 时冻结的 `time.Local`；特殊场景只通过
  `application.TimerOptions.Location` 设置，不新增 YAML/JSON Timer 配置。
- `AfterFunc`、`NewTicker`、`CronFunc`、`PauseTimer`、`ResumeTimer`、
  `CancelTimer` 和 `TimerStats` 的外观必须与设计完全一致。
- 所有 Timer 回调只能进入现有 Service Ready FIFO；不能创建第二个业务执行器、每 Timer
  goroutine 或每 Timer `time.Timer`。
- Await 和业务 Timer 复用同一 Service `DeadlineQueue` 与 watcher；RPC 等未来组件仍使用
  独立 Queue。
- 当前错误码已经足够：参数错误使用 `CodeInvalidArgument`，未就绪、停止中、已停止分别
  使用现有 Service 错误，Node Timer 额度耗尽使用 `CodeServiceQueueFull`；M10 不新增错误码。
- 业务 Timer 容器使用 Scheduler 私有池，但必须通过 Benchmark、逃逸分析和堆 Profile
  验证；如果数据不支持池化，停止实施并带数据回到设计 Review。
- 所有新增和修改代码都补充完整中文 GoDoc、关键字段注释和函数内分步骤注释。
- 每个任务完成后运行其局部测试和 `git diff --check`，但不形成中间实现提交；M10 全部
  验收并完成文档回写后，按仓库规则形成一个包含 M10 编号的中文里程碑提交。

```go
type nodeTimerResources struct {
    maxTimers    int64
    activeTimers atomic.Int64
    nextTimerID  atomic.Uint64
    timerLocation *time.Location
}

func (node *Node) acquireTimerSlot() (service.TimerID, bool) {
    for {
        active := node.timerResources.activeTimers.Load()
        if active >= node.timerResources.maxTimers ||
            !node.timerResources.activeTimers.CompareAndSwap(active, active+1) {
            if active >= node.timerResources.maxTimers {
                return service.InvalidTimerID, false
            }
            continue
        }
        break
    }
    for {
        previous := node.timerResources.nextTimerID.Load()
        if previous == math.MaxUint64 {
            node.releaseTimerSlot()
            return service.InvalidTimerID, false
        }
        if node.timerResources.nextTimerID.CompareAndSwap(previous, previous+1) {
            return service.TimerID(previous + 1), true
        }
    }
}
```

`Node` 增加一个 `timerResources nodeTimerResources` 字段。Application 构建每个 Node 时明确
传入同一组冻结选项：

```go
        TimerLocation:    app.options.Timer.Location,
    },
)
```

`serviceRuntime` 只委托到所属 Node，不保存第二份计数。

```go
func ActivateScheduler(target IService) error {
    scheduler := target.baseService().scheduler.Load()
    if scheduler == nil {
        return errs.ErrServiceNotReady
    }
    scheduler.mu.Lock()
    if scheduler.state != schedulerPrepared {
        scheduler.mu.Unlock()
        return invalidArgument("ServiceScheduler 只能激活一次")
    }
    scheduler.state = schedulerRunning
    scheduler.mu.Unlock()
    go scheduler.run()
    go scheduler.watchDeadlines()
    return nil
}
```

## 2. 实施顺序不变量

执行中必须始终保持：

1. Node TimerEngine 先于任何 Service Scheduler Prepare 启动；
2. OnStart 可以注册 Timer，但 Activate 前绝不执行回调；
3. Scheduler 锁只保护状态和小对象移动，用户 callback、Context cancel 和日志写出均在锁外；
4. 每个 Timer 同时只处于一个主状态，周期 Timer 额外只允许
   `pauseAfterRun`/`cancelAfterRun`；
5. TimerID 不复用，DeadlineID 每次重排更新 generation；
6. Node Slot 只在业务 Timer 脱离全部容器后归还一次；
7. DuePending 不增加 Accepted，进入 Ready 后才成为 M9 根任务；
8. Await 恢复项永远不被容量二次拒绝；
9. 第 99 次连续 panic 后不再安排第 100 次；
10. Service Stop 完成后不存在 Timer Map、Binding、Queue 项、callback、Cron Schedule、
    Task 引用或工作 goroutine。
