# 日志易用性、输出格式与运行时控制实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:test-driven-development`
> and execute every task in order. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不增加第二套日志 Runtime 的前提下，实现易用的全局日志、Service/Module
作用域日志、独立 Console/File 运行时控制、清晰的 text/json 输出和 Application 文件名前缀，
并提供完整教程与可运行示例。

**Architecture:** `log.Runtime` 继续唯一拥有有界队列和 Handler；包级快捷函数只通过原子
默认 Logger 转发。默认 `zaplog.handler` 为 Console 与 File 各维护独立的原子控制器和
Encoder，记录到达输出端时再应用字段掩码。Application 负责默认 Logger 的安装/所有者清理
和活动文件路径派生，Diagnostics 只读取不可变状态快照。

**Tech Stack:** Go 1.26.5、Origin `log` Runtime、Zap、现有 rotate Writer、YAML/JSON 配置。

## Global Constraints

- v3.0 baseline 保持冻结，全部新设计与记录写入 `docs/maintenance/v3.1`。
- 不创建第二套日志队列，不增加无认证 HTTP/RPC 写控制端点。
- 多 Application 仍可构造；包级默认 Logger 只代表最近安装且尚未清理的进程默认实例。
- `Application.Logger()` 与 `Node.Logger()` 在 v3.1 仅废弃，不做破坏性删除。
- 所有新增公开 API 必须有中文 GoDoc，复杂并发和生命周期路径必须说明不变量。
- 每个生产行为先写失败测试，确认失败原因后再写最小实现。
