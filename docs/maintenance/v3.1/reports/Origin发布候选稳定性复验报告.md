> 目标：v3.1.0 发布候选
> 兼容性：不改变当前使用者外观；本轮未发现需要修复的缺陷
> 复验日期：2026-08-10
> 提交基线：`cfb2d6f feat(v3): complete pre-release review and hardening`

## 1. 结论

在当前提交和本报告列出的场景内，未发现可复现的功能缺陷、数据竞争、死锁、请求遗留、
生成漂移或脚本语法错误。发布候选可以继续保持冻结。

这份结论表示已验证范围内没有已知缺陷，不是数学意义上的“绝无 Bug”证明。后续若修改
RPC、生命周期、调度、Transport、依赖版本或部署脚本，必须重跑受影响场景和完整发布门禁。

## 2. 复验原则与范围

既有验收已经覆盖自调用 RPC、TCP/NATS 重连、优雅停止、取消和资源回收。本轮不重复扩大
生产代码或增加推测性抽象，而是对最可能出现偶发时序问题的已有真实协议测试执行高次数、
乱序 Race 验证：

1. 服务调用自身 RPC：`Call`、`Await`、`Async`、`Notify` 和 Service Task 内同步 `Call` 的
   Deadline 边界；
2. TCP 目标重启后的重连与新请求恢复；
3. NATS Broker 断开后的旧 pending 快速失败、不重放和恢复后的新请求；
4. TCP/NATS 已接受请求与 `Node.Stop` 并发时的优雅排空；
5. 调用取消后迟到响应的 pending 回收。

每轮使用 `-race` 和 `-shuffle=on`；测试夹具会在结束时停止 Node、关闭内嵌 Broker，并断言
Buffer 使用量归零。没有发现缺陷时不为了提高覆盖数字新增没有明确风险依据的测试或生产代码。

## 4. 风险结论与后续门禁

本轮没有发现需要退回设计或生产实现阶段的 Bug，因此不产生代码修复提交。保留以下发布后
质量措施：

1. 将本报告的 6 个测试保留为改动 RPC、Transport、Service Runner 或停止语义时的定向
   `-race -count=20 -shuffle=on` 门禁；
2. 每个真实缺陷必须先增加稳定复现测试，再以最小修复关闭，随后重跑本组测试和全仓门禁；
3. 发布前若运行环境、依赖版本或部署方式改变，应在对应 Ubuntu 环境重新执行完整门禁；
4. 正式上线后应基于真实业务负载继续观察错误率、超时率、重连次数、goroutine、连接数和
   内存趋势；观察到异常再以 Profile 或 Trace 定位，避免无证据性能改造。
