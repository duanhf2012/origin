# 10 Admin 管理 HTTP、Diagnostics 与 pprof

> 状态：已实施
> 基线：v3.0
> 目标版本：v3.1.0
> 兼容性：`--diagnostics`、独立 Diagnostics HTTP API 和旧 `/debug/origin/diagnostics` 已删除；本地 `Application.Diagnostics()` 与独立 pprof Listener 保留

本章把进程内运维能力拆成三个边界：**Admin** 是 Application 持有的通用 HTTP 控制面；
**Diagnostics** 是它的内置只读能力；**pprof** 仍是独立、短时开启的高敏感 Listener。完整可运行
程序位于 [`examples/10-admin-diagnostics-and-pprof`](../../../../examples/10-admin-diagnostics-and-pprof/README.md)。

## 先会用：启动唯一的管理 HTTP 入口

Admin 默认关闭。启动时传入唯一的管理 HTTP 参数：

```text
game-server start --app-name game --config ./config --admin 127.0.0.1:6061
```

它在 Service `OnInit`/`OnStart` 之前绑定，并固定提供 Diagnostics、Application/Node/Service
Retire/Resume，以及启动阶段已经登记好的自定义端点。`--admin` 与 `--pprof` 可以同时使用，
但不是同一个 Listener。

没有 Guard 时，Admin **只允许环回地址**；`0.0.0.0`、`[::]` 和其他非环回地址会拒绝启动。
生产环境需要跨主机访问时，先在执行命令前设置唯一 Guard，再配合 TLS、网络策略或受认证代理。

### Guard：认证谁、允许做什么

`app.SetAdminGuard(...)` 的作用是给当前 Application 安装唯一的 Admin 认证和授权策略。每个请求的
处理顺序是：先由 Guard 认证请求，再按固定操作授权，成功后才读取业务 Body 或调用 Endpoint。
因此 Guard 既能阻止未登录请求读取 Diagnostics，也能限制已登录操作者只能 GET、不能 POST。

下面是一个最小实现示例。下面两段代码放在同一个 `package main` 文件中：它用部署环境传入的完整
`Authorization` 值做演示，并让已经认证的
`operator` 只允许所有 GET 与名为 `reload-routing` 的 POST。真实生产环境通常让 mTLS/OIDC/反向
代理完成认证，Guard 再验证代理传来的可信身份；不要把这个固定凭证示例当成完整身份系统。

```go
import (
    "context"
    "crypto/subtle"
    "net/http"
    "os"

    "github.com/duanhf2012/origin/v3/admin"
)

// operatorGuard 保存部署期注入的认证材料；不要把真实值写进源码、日志或 Principal。
type operatorGuard struct {
    expectedAuthorization string // 例如环境变量中的 "Bearer <opaque-secret>"
}

// Authorize 在框架读取 POST Body 和调用业务 Handler 之前执行。
func (guard operatorGuard) Authorize(
    _ context.Context,
    request *http.Request,
    operation admin.Operation,
) (admin.Principal, error) {
    // 认证：Header 缺失、为空或与部署配置不匹配时，返回 401；Handler 不会执行。
    received := request.Header.Get("Authorization")
    if guard.expectedAuthorization == "" ||
        subtle.ConstantTimeCompare([]byte(received), []byte(guard.expectedAuthorization)) != 1 {
        return admin.Principal{}, admin.ErrUnauthenticated
    }

    // Principal 只放安全、低敏的身份摘要。框架会把它复制给 Handler，并用于脱敏审计。
    principal := admin.Principal{
        Subject: "operator",
        Roles:   []string{"ops"},
        Attributes: map[string]string{
            "issuer": "trusted-admin-gateway",
        },
    }

    // 授权：Operation 是框架从已冻结路由产生的固定目标，不包含 Body、Query 或凭证。
    // 本例允许所有只读 GET，也只允许这一条明确的 POST 写操作。
    if operation.Method == http.MethodGet ||
        (operation.Method == http.MethodPost && operation.Endpoint == "reload-routing") {
        return principal, nil // 认证与授权都成功，框架继续处理请求。
    }
    return principal, admin.ErrForbidden // 已认证但没有权限，返回 403，Handler 不会执行。
}
```

在 `app.Start()` 之前、通常是在 `init` 中完成注册。`SetAdminGuard` 只能成功设置一次；重复设置、
或在命令已经开始执行后设置会返回错误，说明安全策略不应在运行期悄悄改变：

```go
func init() {
    app.Setup(&ControlService{})

    // 部署系统负责安全地注入该值；仓库、配置文件和日志中都不保存真实凭证。
    expected := os.Getenv("ORIGIN_ADMIN_AUTHORIZATION")
    if expected == "" {
        panic("ORIGIN_ADMIN_AUTHORIZATION is required for non-loopback Admin")
    }
    if err := app.SetAdminGuard(operatorGuard{expectedAuthorization: expected}); err != nil {
        // 这里代表启动装配错误，例如重复注册 Guard；不是把认证失败暴露给 HTTP 客户端。
        panic(err)
    }
}
```

请求示例把同一个值放进标准 `Authorization` Header，而不是 Query；框架不会把它写入审计或错误响应：

```bash
curl -i \
  -H "Authorization: $ORIGIN_ADMIN_AUTHORIZATION" \
  http://admin.example:6061/admin/v1/diagnostics
```

Guard 接收固定的 `admin.Operation`（HTTP Method、端点名、Node/Service 目标），直接按 GET/POST
授权；没有 Read/Write/Action 三套分类。`admin.ErrUnauthenticated` 映射为 `401`，
`admin.ErrForbidden` 映射为 `403`；其他 Guard 错误会被安全地收敛为 `500`。框架不启用 CORS，
不从 Query 读取 Token，也不记录 Authorization、Cookie、请求/响应 Body 或业务错误链。审计记录
只含 RequestID、脱敏 Principal、固定操作目标、HTTP 状态、耗时、响应字节数与低基数结果。

> 若认证由反向代理完成，必须确保 Admin Listener 不可被绕过，并由代理删除客户端伪造的身份 Header
> 后再写入可信 Header；否则客户端可以自行伪造“已认证”身份。Guard 不替代 TLS、网络隔离或密钥轮换。

Admin 使用私有 `http.Server` 与私有 Mux，不使用 `http.DefaultServeMux`。默认单端点执行预算
15 秒、POST Body 1 MiB、业务响应 4 MiB、全局活动请求 64；因此没有无界 HTTP 等待队列。
端点 Deadline 是协作式 Context 取消：任意 Handler 若忽略 Context，框架不能安全地强杀它，
该请求仍会占用一个活动额度直到返回。

运行中的 Application 也可调用 `StartAdminServer(address)`、`AdminAddress()`、
`StopAdminServer(ctx)`；同一地址重复 Start 是幂等的，换地址前必须 Stop。Listener 重开不会重新
发现 Provider 或修改路由，路由始终是启动前冻结的那一份。`StopAdminServer` 可能等待活动请求排空，
所以从 Service Task 调用时应放入 `Await`。

### 空闲和查询成本

Admin Listener 空闲时**不会**周期采样 Diagnostics；它只保留 Listener、HTTP Server 和必要的
等待运行资源，并非绝对零成本。每次成功查询才会读取 Go Runtime、BufferPool，并聚合每个
Node 的健康、发现、RPC、Service Scheduler、Timer 和 Event，再编码 JSON；这不是“只读内存”。

默认 Summary 面向秒级拉取；`detail=full` 面向人工排障。本机 Windows/amd64、Go 1.26.5 以
`go test ./application -run '^$' -bench 'BenchmarkDiagnostics(Summary|SummaryJSON)/Nodes64_Services64$' -benchmem -count=3`
复验：64 Node × 64 Service 的 Summary 约 `0.2 ms/op`、约 `77.2 KB response-bytes`、
约 `33.5 KB/op`、`3 allocs/op`；加 JSON 编码后约 `0.8 ms/op`、约 `77.2 KB response-bytes`、
约 `204–208 KB/op`、`207 allocs/op`。时间会随 CPU、负载和 Go 版本变动；这些仅是当前机器
参考，不是跨机器容量承诺。采集频率应按真实规模、响应字节和监控需求调整。

## Service：声明 GET 查询和 POST 操作

Service 只需可选实现 `admin.Provider`。Application 在真实 Service 实例完成 Runtime 绑定后、
`OnInit` 前调用一次 `AdminEndpoints()`，收集并冻结路由；该方法只声明静态 Endpoint，不能读写
尚未初始化的业务字段、做 I/O、启动 goroutine 或在运行中增删路由。

```go
func (target *LogicService) AdminEndpoints() []admin.Endpoint {
    return []admin.Endpoint{
        admin.Get("summary", target.getSummary),
        admin.Post("reload-logic", target.reloadLogic),
        admin.Post(
            "refresh-player",
            target.refreshPlayer,
            admin.WithSuccessStatus(http.StatusAccepted),
        ),
    }
}
```

Endpoint 名称是小写 kebab-case。GET 无副作用且不接受 Body，默认成功为 `200`；POST 可修改、
重载或触发操作，默认成功为 `204`，也可显式返回 `200` 或 `202`。首版只公开
`WithTimeout`、`WithMaxBodyBytes`、`WithMaxResponseBytes`、`WithSuccessStatus` 四类边界选项。
不提供 PUT/PATCH/DELETE、流式响应、WebSocket 或运行期路由注册。

### 查询：直接读取本 Service 字段

Service Endpoint 会进入目标 Service 现有的有界 FIFO，并取得与 Timer、Event、RPC Handler
相同的唯一执行权。因此这里可以直接读取普通字段，不需要为 Admin 再建一把锁：

```go
func (target *LogicService) getSummary(
    _ context.Context,
    _ admin.Request,
) (admin.Response, error) {
    return admin.JSON(http.StatusOK, struct {
        Version string `json:"version"`
        Reloads int    `json:"reloads"`
    }{
        Version: target.version,
        Reloads: target.reloads,
    })
}
```

框架在 Handler 尚持有执行权时完成 `admin.JSON` 编码；不要返回稍后会被业务任务修改的 Map、
Slice 或指针后再由 HTTP goroutine 编码。Endpoint 收到的是已复制的 `admin.Request`，不会暴露
`*http.Request`、`ResponseWriter` 或可延后读取的网络 Body。`Request.DecodeJSON` 只接受一个
JSON 值，并拒绝空 Body、未知字段和尾随值。

### 修改或重载：Await 期间只操作局部值

可能等待文件、数据库或远端配置时，用 `Await` 释放 Service 执行权；等待回调只能操作局部变量，
恢复后重新取得执行权再提交状态：

```go
func (target *LogicService) reloadLogic(
    ctx context.Context,
    request admin.Request,
) (admin.Response, error) {
    var input struct {
        Version string `json:"version"`
    }
    if err := request.DecodeJSON(&input); err != nil {
        return admin.Response{}, err
    }

    var next string
    if err := target.Await(ctx, func(waitCtx context.Context) error {
        loaded, err := loadLogic(waitCtx, input.Version) // 不触碰 target 字段。
        if err == nil {
            next = loaded
        }
        return err
    }); err != nil {
        return admin.Response{}, err
    }

    target.version = next // Await 返回后，已恢复目标 Service 的唯一执行权。
    target.reloads++
    return admin.Empty(http.StatusNoContent), nil
}
```

POST 必须带 `Content-Type: application/json` 和恰好一个 JSON 值。完整的 GET、严格 JSON、
Await 重载与并发串行断言见
[`01-admin-service-endpoints`](../../../../examples/10-admin-diagnostics-and-pprof/01-admin-service-endpoints/README.md)。

### 异步通知：202 是已受理，不是已完成

Handler 可以把后续工作再次投递到同一 Service 的有界队列：

```go
func (target *LogicService) refreshPlayer(
    _ context.Context,
    request admin.Request,
) (admin.Response, error) {
    var input struct {
        PlayerID string `json:"player_id"`
    }
    if err := request.DecodeJSON(&input); err != nil {
        return admin.Response{}, err
    }
    if err := target.DispatchAsync(func(context.Context) {
        target.refreshes++
        target.refresh(input.PlayerID)
    }); err != nil {
        return admin.Response{}, err
    }
    return admin.Empty(http.StatusAccepted), nil
}
```

`202 Accepted` 只表示这项后续工作已被接受，并不表示刷新完成。队列满快速返回 `429`；请求在
入队前取消时不会执行，已入队的任务会先检查取消；Handler 已提交修改后才取消不会自动回滚。
Retired Service 仍允许精确 Admin 路由，以便恢复或修复；Starting、Stopping、Stopped、Failed
或 Scheduler 未就绪时返回 `503`。

## Application 端点与内置控制

不属于某个 Service 的进程级只读或控制操作，可在首次执行命令前调用
`Application.RegisterAdminEndpoint`：

```go
state := newControlState() // 自己保证并发安全，例如 atomic 或 mutex。
if err := app.RegisterAdminEndpoint(admin.Get("routing-status", func(
    _ context.Context,
    _ admin.Request,
) (admin.Response, error) {
    return admin.JSON(http.StatusOK, map[string]uint64{
        "routing_revision": state.revision.Load(),
    })
})); err != nil {
    panic(err)
}
```

Application Handler 在 HTTP goroutine 并发执行，只能访问不可变/并发安全数据，或调用已有的
公开并发安全控制方法；**不能直接读写 Service 的普通字段**。需要 Service 状态或修改 Service
数据时，声明该 Service 的 Provider Endpoint。

业务只提供端点名，不能注册任意绝对路径。下面的框架路径固定保留：

```text
GET  /admin/v1/diagnostics
GET  /admin/v1/diagnostics?detail=full

POST /admin/v1/application/retire
POST /admin/v1/application/resume
POST /admin/v1/nodes/{node}/retire
POST /admin/v1/nodes/{node}/resume
POST /admin/v1/nodes/{node}/services/{service}/retire
POST /admin/v1/nodes/{node}/services/{service}/resume

GET  /admin/v1/application/endpoints/{endpoint}
POST /admin/v1/application/endpoints/{endpoint}
GET  /admin/v1/nodes/{node}/services/{service}/endpoints/{endpoint}
POST /admin/v1/nodes/{node}/services/{service}/endpoints/{endpoint}
```

Retire/Resume 是幂等的流量状态切换，不等同于 Stop/Start。POST 也必须发送 JSON，例如：

```bash
curl -i -X POST -H "Content-Type: application/json" -d '{}' \
  http://127.0.0.1:6061/admin/v1/nodes/game-1/services/LogicService/retire
```

完整 Application GET/POST 与 Application、Node、Service 内置控制见
[`02-admin-application-control`](../../../../examples/10-admin-diagnostics-and-pprof/02-admin-application-control/README.md)。
跨 Service 编排、长期任务、幂等记录或补偿不应塞进框架；把它实现为普通的业务
ManagementService，并通过其 Endpoint、RPC、Event 与 Await 编排。

## 取消、错误与审计

请求会依次经过全局并发额度、Guard、方法/Query/Body 校验、固定路由和目标 Service 调度。
GET/POST 以外的方法、非法路径或未知 Endpoint 不会回退到“相近”路由。错误响应只给稳定的
HTTP 状态文本，不返回错误链、文件路径、配置或业务数据。

| 情况 | HTTP |
| --- | --- |
| 参数/Query/JSON 无效；GET 带 Body | 400 |
| 方法不匹配；POST 缺少或错误 Content-Type | 405 / 415 |
| POST Body 超出端点上限 | 413 |
| Guard 认证失败 / 未授权 | 401 / 403 |
| Node、Service 或 Endpoint 不存在 | 404 |
| Retire 等状态冲突 | 409 |
| 全局额度或 Service FIFO 已满 | 429 |
| Service 未就绪、正在停止、已停止或失败 | 503 |
| 调用取消 / Endpoint Deadline | 408 / 504 |
| Handler panic、响应超限或未知内部失败 | 500 |

所有 POST、认证/授权拒绝和异常结果都会审计；GET 也记录低基数的调用元数据。不要把 Token、
Cookie、密码或原始业务输入放进 `Principal.Attributes`、日志字段或错误消息。

## Diagnostics：Summary v2 与 Full Snapshot v2

Admin 内置 Diagnostics 路由默认返回低成本、低基数的 **Summary schema v2**：

```bash
curl -s http://127.0.0.1:6061/admin/v1/diagnostics
```

人工排障才显式请求完整 **Full Snapshot schema v2**：

```bash
curl -s "http://127.0.0.1:6061/admin/v1/diagnostics?detail=full"
```

`detail` 只能省略或严格等于 `full`；重复值、未知 Query 和其他值返回 `400`。Summary v2 是有意
变更过 JSON 外形的监控契约，消费者必须按 `schema_version: 2` 解析；Full 保持原有 v2 的详细
兼容面。

### 快照所有权：Application 与 Node 不重复

`Application.Diagnostics()` 返回的是一次聚合文档，不是 ApplicationSnapshot 的别名：

```text
Snapshot（Full v2）
├── 采集元数据：collected_at、started_at、collect_cost
├── Application：名称、生命周期、Admin/pprof Listener
├── Runtime：整个 Go 进程的 Runtime
├── BufferPool：当前 Application 拥有的共享池
└── Nodes[]：当前 Application 拥有的 Node
    └── Services[]：该 Node 拥有的本地 Service
```

Application 不重复 Node 健康、Transport、Discovery、RPC 或 Service 数据；Node 不重复整个
进程的 Runtime。一个进程如果承载多个 Application，它们读取到的 Runtime 可能相同，这不是
重复采集错误。每次调用都生成新的按值快照；它不持有可变 Node/Service，也不是跨组件事务视图。

本地代码不需要 HTTP，直接调用：

```go
snapshot := app.Diagnostics() // Full Snapshot v2
```

完整所有权关系与 `diagnostics_server` 的迁移说明见
[`03-diagnostics-snapshot`](../../../../examples/10-admin-diagnostics-and-pprof/03-diagnostics-snapshot/README.md)。

### Summary v2 保留什么、刻意省略什么

| 范围 | Summary v2：面向告警、趋势与容量 | Full v2：按需排障细节 |
| --- | --- | --- |
| Application | 名称、状态；Admin/pprof 的 `state`、`error_code` | Listener 地址；`diagnostics_server` 仍以已废弃、恒为 `stopped` 的字段保留 |
| Go Runtime | goroutine、runnable、GOMAXPROCS、Go 管理内存、Heap allocation/goal、是否配置内存上限及其值、累计分配/GC/GC CPU/GC pause/mutex wait | `heap_objects`、NextGC、最后 GC 时间/暂停等既有 v2 字段 |
| BufferPool | 当前启用状态、在用 buffer/容量、零大小与超大 buffer 汇总 | 相同的既有 v2 BufferPool 字段 |
| Node | ID/状态、健康、Transport、Discovery/发布/目录数量 | 相同节点信息与逐项 Service 明细 |
| RPC | Local/TCP/NATS 合并后的 pending、最大 high-water、入/出完成/失败/超时/拒绝和收发字节 | 每一种 Transport 的独立树、accepted 与恢复详情 |
| Service 工作 | 状态计数；Scheduler 当前占用与结果计数；Timer 当前占用、结果计数和最大 ready delay；Event 同步/异步通知与失败计数 | 每个 Service 名称、状态时间、错误码，以及 Scheduler/Timer 的完整细节 |

Summary 的**输出形状**只随 Node 数增长，不建立逐 Service 的输出 DTO；采集仍会顺序读取每个
Service 的并发安全叶子并汇总。它省略 Listener 地址、`heap_objects`、逐 Transport RPC、
逐 Service 名称/细节和常规过渡状态；这些字段易增加拓扑暴露、响应大小或监控基数，但仍能在
Full 中取得。新增的 `memory_limit_configured` 防止把 Go 的无限
GOMEMLIMIT 哨兵误报成可用容量：未配置时是 `false` 与 `0`。`heap_goal_bytes` 可帮助判断
堆增长目标与内存压力。

对于每个 Node，Scheduler 保留 `accepted`、`ready`、`running`、`awaiting` 当前值，以及
`dispatched_total`、`completed_total`、`rejected_total`、`await_timeout_total`、`panic_total`。
Timer 保留 `active`、`due_pending`、`ready`、`running` 与
`triggered_total`、`completed_total`、`rejected_total`、`panic_total`、`max_ready_delay`；
Event 把同步/异步通知总数与 handler 失败总数一起给出，以免孤立错误计数失去流量上下文。

Admin HTTP 方式和 Summary/Full 请求成本说明见
[`04-admin-diagnostics`](../../../../examples/10-admin-diagnostics-and-pprof/04-admin-diagnostics/README.md)。

### 监控边界

`go_memory_used_bytes`、Heap、GC 与 mutex wait 都是 **Go Runtime** 口径，不能替代系统资源
指标。OS RSS、文件描述符、容器 working set/memory limit/throttling、进程 CPU、宿主机负载和
网络吞吐，应由进程/容器/主机的外部监控采集，再与 Application/Node/Service Summary 关联。

一个监控周期先采样一次，再交给多个输出端，避免 Prometheus、OpenTelemetry 与日志分别重复
聚合：

```go
summary := app.DiagnosticsSummary() // 本轮只采样一次。
publishPrometheus(summary)
publishOpenTelemetry(summary)
```

不要把旧 Summary 永久当实时状态，也不要将 pprof 当作 Metrics 拉取接口。最小适配器见
[`06-metrics-adapter`](../../../../examples/10-admin-diagnostics-and-pprof/06-metrics-adapter/README.md)。

## pprof：独立 Listener，按需关闭、重开、再关闭

`--pprof` 只决定启动初态：

```text
game-server start --app-name game --config ./config --pprof 127.0.0.1:6060
```

pprof 不注册到 Admin。它可以使用不同地址、不同暴露时长和更严格的网络保护；关闭它不会关闭
Admin。CPU Profile、Trace 具有进程级互斥和采样开销，heap/goroutine/mutex 也可能制造大快照，
因此仅在受控排障窗口开启。

下面是与完整示例使用同一签名的 Service 片段：2 秒关闭、4 秒重开并读取实际地址、6 秒再次关闭。`StopPprof`
可能等待活动 profile 请求结束，因此放入 `Await`；`StartPprof` 和 `PprofAddress` 是短冷路径。

```go
import (
    "context"
    "fmt"
    "time"

    "github.com/duanhf2012/origin/v3/service"
)

type DebugService struct{ service.Service }

func (target *DebugService) OnStart(context.Context) error {
    runtime := target.Application()
    if runtime == nil {
        return fmt.Errorf("application runtime is unavailable")
    }

    target.AfterFunc(2*time.Second, func(ctx context.Context, _ service.TimerID) {
        if err := target.Await(ctx, func(waitCtx context.Context) error {
            return runtime.StopPprof(waitCtx)
        }); err != nil {
            target.Logger().Error("first StopPprof failed")
        }
    })
    target.AfterFunc(4*time.Second, func(context.Context, service.TimerID) {
        if err := runtime.StartPprof("127.0.0.1:6060"); err != nil {
            target.Logger().Error("StartPprof failed")
            return
        }
        if address, running := runtime.PprofAddress(); running {
            target.Logger().Info(fmt.Sprintf("pprof restarted: http://%s/debug/pprof/", address))
        }
    })
    target.AfterFunc(6*time.Second, func(ctx context.Context, _ service.TimerID) {
        if err := target.Await(ctx, func(waitCtx context.Context) error {
            return runtime.StopPprof(waitCtx)
        }); err != nil {
            target.Logger().Error("second StopPprof failed")
        }
    })
    return nil
}
```

诊断 CPU 突增、持续内存增长、goroutine 泄漏、锁竞争或启动变慢时，可在短窗口中选择：

```bash
go tool pprof "http://127.0.0.1:6060/debug/pprof/profile?seconds=10"
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
curl -s "http://127.0.0.1:6060/debug/pprof/goroutine?debug=1"
go tool pprof http://127.0.0.1:6060/debug/pprof/mutex
```

完整的关闭—重开—地址查询—再次关闭程序及测试见
[`05-pprof-toggle`](../../../../examples/10-admin-diagnostics-and-pprof/05-pprof-toggle/README.md)。
绝不把 pprof 直接暴露到公网；同时运行 CPU profile 或 Trace 前，应确认没有其他进程级采样正在进行。

## 从 v3.0 迁移

- 删除 `--diagnostics`；启动通用入口改用 `--admin 127.0.0.1:6061`。
- 删除 `StartDiagnosticsServer`、`StopDiagnosticsServer`、`DiagnosticsAddress` 和
  `/debug/origin/diagnostics`；本地 Full 快照仍使用 `Application.Diagnostics()`。
- HTTP Diagnostics 默认地址改为 `/admin/v1/diagnostics`；完整详情使用唯一 Query
  `?detail=full`。
- 监控消费者按 Summary schema v2 更新：它不再带 Listener 地址、`heap_objects`、逐 Transport
  RPC 或逐 Service DTO；需要这些细节时改读 Full v2。
- 旧的 `examples/10-diagnostics-and-pprof` 已迁移为六组
  [`10-admin-diagnostics-and-pprof`](../../../../examples/10-admin-diagnostics-and-pprof/README.md) 示例。

v3.0 冻结章节只保留历史说明和迁移入口；新项目应以本章为准。
