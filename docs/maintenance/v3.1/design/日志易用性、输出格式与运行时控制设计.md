# 日志易用性、输出格式与运行时控制设计

> 状态：已实施并验收
> 基线：v3.0
> 目标：v3.1.0
> 兼容性：新增全局快捷日志、Module Logger、输出字段配置和运行时控制；v3.1 将
> `Application.Logger()`、`Node.Logger()` 标记为废弃并从教程移除，下一主版本再删除
> 提案日期：2026-08-08

## 1. 目标与边界

本设计在继续复用每个 Application 已有日志 Runtime、唯一日志队列和 Handler 的前提下，
完成以下调整：

1. 普通业务、子模型和工具代码可以直接调用 `log.Debug/Info/Warn/Error`；
2. 业务只区分“普通日志”和“所属 Service 日志”，不再公开 Application、Node 两套作用域
   Logger；
3. 文本输出改为适合人工阅读的作用域前缀与 `key=value`，不再附加整段 JSON；
4. JSON 输出继续保持单行结构化格式；
5. `app_name` 不再进入日志内容，只用于日志文件名前缀；
6. Console 和 File 分别控制 `node_id`、`service_name` 是否输出；
7. Console 和 File 分别支持运行时修改级别、恢复配置级别以及暂停、恢复输出；
8. 保留现有按大小/日期滚动、期限清理、最大归档数和 gzip 压缩能力。

本次不增加按 goroutine 自动推断 Service、远程日志、运行时更换 Handler、配置文件回写、
内置无认证 HTTP/RPC 管理端点或第二套日志队列。

本设计已经开发者最终确认。v3.0 冻结基线保持不变，v3.1 按配套实施计划同步修改代码、
测试、示例和教程。

## 2. 公开调用外观

### 2.1 普通日志

日志包增加进程默认 Logger 和包级快捷函数：

```go
func Default() Logger
func SetDefault(logger Logger)

func Enabled(level Level) bool
func Debug(message string, fields ...Field)
func Info(message string, fields ...Field)
func Warn(message string, fields ...Field)
func Error(message string, fields ...Field)
func ErrorStack(message string, fields ...Field)
```

普通业务默认写法：

```go
log.Info(
    "player loaded",
    log.Int64("player_id", playerID),
)
```

包级函数只原子读取当前默认 Logger，之后复用既有 `Logger`、Runtime、队列和 Handler。
包装层必须补偿 caller skip，最终位置仍指向业务调用点，不得指向 `log/global.go`。

Application 的日志 Runtime 创建完成后、进入业务生命周期前安装默认 Logger；完成全部停止
回调和最终停止日志后，先以所有者校验清除默认值，再 Flush、Close。初始化前和停止后普通
日志使用 Nop Logger，不 panic、不创建临时 Runtime。

同进程并行运行多个 Application 时，包级默认 Logger 无法判断调用归属；该场景不得依赖
包级日志及运行时控制。当前架构仍允许测试构造多个独立 Application，不为日志便利性引入
Application 包级单例。

### 2.2 Service 和 Module 日志

保留：

```go
func (service *Service) Logger() log.Logger
```

新增：

```go
func (module *Module) Logger() log.Logger
```

`Module.Logger()` 直接委托所属 Service Logger；未绑定 Module 返回 Nop Logger，不创建
Module 独立 Logger，也不自动加入 `module_name`：

```go
func (module *Module) Logger() log.Logger {
    owner := module.ownerService()
    if owner == nil {
        return log.NewNop()
    }
    return owner.Logger()
}
```

需要区分 Module 时使用普通业务字段：

```go
module.Logger().Info(
    "rank module started",
    log.String("component", "RankModule"),
)
```

从 v3.1 推荐业务外观和教程中移除：

```go
Application.Logger()
Node.Logger()
```

Application、Node 内部继续保存私有 Logger，用于框架日志和向 Service 派生运行时 Logger；
v3.1 的方法仍保留并标记 Deprecated，删除的是推荐使用外观，不是内部归属字段能力。

最终公开使用语义只有两类：

```text
log.Xxx()                  普通进程日志，不自动带 Node/Service
service/module.Logger()    所属 Service 日志，可带 Node/Service
```

v3.0 已作为冻结基线保存，直接删除两个公开方法属于源代码不兼容变更。因此 v3.1 只从
教程和推荐外观移除并标记 Deprecated，真正删除延后到下一主版本。

## 3. 框架归属字段

Application 根 Logger 不再预绑定 `app_name`。Node 私有 Logger 绑定 `node_id`，Service
Logger 在此基础上绑定实际配置名称 `service_name`。

跨 `application`、`node`、`service` 包组装作用域时统一使用
`Logger.WithScope(nodeID, serviceName)`。这是框架构造期专用入口，会替换已有归属并过滤
业务伪造的保留 Key；教程不把它作为普通业务绑定方法。

归属能力如下：

| 调用来源 | `node_id` | `service_name` |
| --- | --- | --- |
| `log.Xxx()` | 无 | 无 |
| Node 框架内部 Logger | 有 | 无 |
| `service.Logger()` | 有 | 有 |
| `module.Logger()` | 有 | 有 |

`app_name`、`node_id`、`service_name` 是框架保留 Key，业务不得伪造或覆盖。记录目标、远端
或其他实例时改用：

```go
log.String("target_app_name", targetAppName)
log.String("target_node_id", targetNodeID)
log.String("remote_service_name", serviceName)
```

## 4. 输出端配置

`node_id`、`service_name` 是否显示属于输出格式策略，分别放入 Console 和 File，而不是
日志顶层：

```yaml
log:
  console:
    enabled: true
    level: info
    format: text
    context_fields:
      # 省略时默认 true。
      node_id: true
      # 省略时默认 true。
      service_name: true

  file:
    enabled: true
    level: debug
    format: json
    path: logs/origin.log
    context_fields:
      # 省略时默认 true。
      node_id: true
      # 省略时默认 true。
      service_name: true
```

两个字段独立控制，缺失、`context_fields: {}` 和显式两个 `true` 等价。显式 `false` 必须
覆盖默认值，YAML、JSON 和拆分配置具有相同语义。

典型配置可以让控制台简洁、文件保留完整归属：

```yaml
log:
  console:
    enabled: true
    level: info
    format: text
    context_fields:
      node_id: true
      service_name: false

  file:
    enabled: true
    level: debug
    format: json
    context_fields:
      node_id: true
      service_name: true
```

由于两个输出端可能采用不同掩码，完整归属字段进入日志队列，由 Console/File 在编码时
分别过滤。实现使用构造期预计算掩码和栈上小数组，不为普通字段过滤增加堆分配。

## 5. 文本输出格式

`format: text` 不再使用 Zap ConsoleEncoder 的尾部 JSON，固定为：

```text
TIME LEVEL [NODE/SERVICE] CALLER MESSAGE FIELDS
```

普通日志：

```text
2026-08-08T18:20:31.123 INFO application/application.go:407 application started node_count=2
```

Node 框架日志：

```text
2026-08-08T18:20:31.123 INFO [game-1] node/node.go:280 node started
```

Service/Module 日志：

```text
2026-08-08T18:20:31.123 INFO [game-1/PlayerService] player/player.go:42 player loaded player_id=10001 online=true
```

只显示 Service 时使用 `[PlayerService]`；两个归属字段均关闭时省略整个 `[...]`。

普通结构化字段使用稳定 `key=value` 编码：

```text
player_id=10001 online=true latency=15ms player_name="Boyce Duan"
error="mongodb connection refused" position={"x":10,"y":20}
```

简单值不加引号；包含空白、控制字符或分隔歧义的字符串加引号并转义；`Any` 保持单个字段
的紧凑 JSON，不再把整组字段包成 JSON 后缀。

文本时间使用操作系统本地时间并去掉数字时区偏移：

```text
2026-08-08T18:20:31.123
```

`rotation.timezone` 继续只控制自然日滚动边界和归档命名，不改变文本记录使用本地时间的
规则。

## 6. JSON 输出格式

`format: json` 继续输出一条日志一行的紧凑 JSON。时间统一转换为 UTC，并使用 RFC3339
毫秒精度 `Z`：

```json
{"time":"2026-08-08T10:20:31.123Z","level":"info","node_id":"game-1","service_name":"PlayerService","caller":"player/player.go:42","msg":"player loaded","player_id":10001,"online":true}
```

普通日志没有 Node/Service：

```json
{"time":"2026-08-08T10:20:31.123Z","level":"info","caller":"application/application.go:407","msg":"application started","node_count":2}
```

JSON 内容同样不包含 `app_name`。字段写出顺序保持稳定，消费者不得依赖 JSON 对象的字段
顺序语义。

## 7. 文件名、滚动与磁盘上限

Application 名称只用于活动、归档和 Crash 文件名前缀。Application 名为 `game`，配置：

```yaml
file:
  path: logs/origin.log
```

实际文件：

```text
logs/game-origin.log
logs/game-origin-2026-08-08T18-30-00.123.log
logs/game-origin-2026-08-08T18-30-00.123.log.gz
logs/game-origin.crash.log
```

归档名冲突时追加 `-1`、`-2`。显式 `logs/server.log` 同样解析为
`logs/game-server.log`，防止多个 Application 复用同一份配置时写入相同文件。

现有滚动与保留配置继续有效：

```yaml
rotation:
  max_size: 512M
  by_date: true
  timezone: Local
retention:
  max_age: 14d
  max_files: 30
  compress: true
```

规则：

- `max_files` 只统计归档，不包含当前活动文件；默认最多保留 30 个；
- `max_files: 0` 表示不按数量限制；
- `max_age: 0s` 表示不按时间清理；
- 时间和数量同时配置时，满足任意清理条件即可删除；
- `compress` 只压缩归档；
- 生产环境不建议同时配置 `max_age: 0s` 与 `max_files: 0`；
- 默认 `512M × 30` 在不考虑 gzip 的极端情况下约占 15 GiB，再加活动文件；磁盘较小的
  部署应显式降低 `max_size` 或 `max_files`。

本次不改变现有保留算法，只补充完整教程和边界测试。

## 8. 运行时级别控制

Console 和 File 的运行时接口保持成对、无 Output 枚举：

```go
func SetConsoleLevel(level Level) error
func ResetConsoleLevel() error

func SetFileLevel(level Level) error
func ResetFileLevel() error
```

使用示例：

```go
// 收到管理指令后临时开启控制台 Debug。
if err := log.SetConsoleLevel(log.DebugLevel); err != nil {
    return err
}

// 恢复 YAML/JSON 中 console.level 的启动配置。
if err := log.ResetConsoleLevel(); err != nil {
    return err
}
```

文件独立调整：

```go
if err := log.SetFileLevel(log.WarnLevel); err != nil {
    return err
}

if err := log.ResetFileLevel(); err != nil {
    return err
}
```

级别表示最低接收级别：Debug 接收 Debug 及以上，Info 接收 Info 及以上，依次类推。
Set 只改变内存中的当前级别，不写回配置；Reset 精确恢复对应输出启动时的配置，而不是写死
恢复为 Info。设置同一值幂等，并发调用安全。

本设计不再增加：

```go
log.SetLevel(...)
log.ResetLevel()
Application.SetLogLevel(...)
Application.CurrentLogLevels()
log.Output
```

常规程序只有一个进程默认 Application，运行时日志控制统一通过 `log` 包完成。允许多个
Application 对象存在的测试不能依赖包级控制，不为少见测试场景扩大业务 API。

## 9. 运行时暂停与恢复输出

增加：

```go
func SetConsoleEnabled(enabled bool) error
func SetFileEnabled(enabled bool) error
```

调用 `false` 后不再向对应输出写新日志，另一个输出不受影响；调用 `true` 恢复。运行时
暂停不修改配置文件，Application 重启后重新使用 `enabled` 启动值。

本提案采用低复杂度的“可用性与当前状态分离”规则：

- 配置 `enabled: true` 表示启动时创建该输出并默认开启；
- 运行时 `false` 只暂停写出，File Writer、滚动维护和必要资源保留到 Application 停止；
- 再次 `true` 立即恢复，不重新建立队列、Encoder、Core 或文件 Writer；
- 配置 `enabled: false` 表示该输出没有在启动时创建；运行时尝试改为 `true` 返回输出不可用；
- 彻底关闭资源仍由 Application.Stop 负责。

该语义避免文件关闭与异步写入竞态、运行期重新打开失败、滚动协程反复创建以及 Crash 输出
所有权切换。若未来需要“配置关闭但运行中首次创建文件”，应单独设计惰性文件输出，不与
本次轻量启停混合。

设置输出级别时，即使该输出当前被运行时暂停，也保存新的当前级别并在恢复后生效；如果输出
从未配置、不可用，则 Set/Reset/Enabled(true) 都返回明确错误。

## 10. 状态查询与 Diagnostics

增加进程级状态快照：

```go
type OutputStatus struct {
    Available  bool
    Enabled    bool
    Level      Level
    ConfigLevel Level
}

type Status struct {
    Console OutputStatus
    File    OutputStatus
}

func CurrentStatus() (Status, error)
```

`Level` 是当前有效级别，`ConfigLevel` 是 Reset 将恢复的启动配置。日志尚未初始化或已经
关闭时返回明确错误。

`Application.Diagnostics()` 使用同一状态模型增加只读日志状态：

```json
{
  "log": {
    "console": {
      "available": true,
      "enabled": true,
      "level": "debug",
      "config_level": "info"
    },
    "file": {
      "available": true,
      "enabled": false,
      "level": "warn",
      "config_level": "debug"
    }
  }
}
```

框架不自动暴露可修改状态的 Diagnostics HTTP 接口。业务管理 Service 可以在完成自己的
鉴权和审计后直接调用 `log.SetConsoleLevel` 等包级函数。

## 11. Handler 扩展边界

现有第三方替换接口保持不变：

```go
type Handler interface {
    Enabled(level Level) bool
    Write(record Record, fields []Field) error
    Sync() error
    Close() error
}
```

运行时控制使用可选接口，避免强迫只需要固定级别的第三方 Handler 扩大实现：

```go
type Controller interface {
    SetConsoleLevel(level Level) error
    ResetConsoleLevel() error
    SetFileLevel(level Level) error
    ResetFileLevel() error
    SetConsoleEnabled(enabled bool) error
    SetFileEnabled(enabled bool) error
    Status() Status
}
```

默认 Zap Handler 实现 Controller。第三方 Handler 未实现时仍可正常写日志，但包级运行时
控制返回“不支持”错误。Console stdout/stderr 共享同一原子级别和启用状态；File 使用独立
原子状态。更新不重建 Runtime 或日志队列。

## 12. 并发、性能与边界

- 默认 Logger、Console/File 当前级别和启用状态使用原子读取；
- `Logger.Enabled` 热路径不增加互斥锁；
- 运行时控制是低频冷路径；
- 关闭的输出不执行编码或 Writer.Write；
- 已经进入异步队列的日志允许按照处理时的最新输出状态决定是否写出；
- 降低到 Debug 不补发此前被过滤的 Debug；
- Runtime 未就绪、正在关闭或已关闭时，控制接口返回明确状态错误；
- 非法 Level 返回参数错误；
- 第三方 Handler 不支持 Controller 时返回稳定错误 7003（`ErrLogControlUnsupported`）；
- 启动时未创建目标输出资源时返回稳定错误 7004（`ErrLogOutputUnavailable`）；
- 运行时暂停不影响队列、Stats 和另一个输出端；
- 全局包装、文本编码和双输出字段过滤必须通过 Benchmark 验证 `ns/op`、`B/op`、
  `allocs/op`。
