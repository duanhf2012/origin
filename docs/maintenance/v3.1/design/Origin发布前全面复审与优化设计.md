# Origin 发布前全面复审与优化设计

> 状态：已确认，允许编写实施计划
> 基线：v3.0
> 目标：v3.1.0 发布候选收口
> 兼容性：Origin v3 尚未对外发布，不保留未发布版本之间的源码、配置或线协议兼容；已经人工检查的当前使用者外观以代码为准，未经单独确认不得改变
> 形成日期：2026-08-09
> 确认日期：2026-08-09

## 1. 目标

Origin 当前功能、测试和教程已经基本完成。本轮工作不继续扩展功能，而是在正式发布前完成
一次有边界、可验证、不会因局部修改反复返工的整体复审与优化。

本轮需要完成：

1. 复核最终功能范围，区分必须发布、明确删除、明确延期和仅供内部使用的能力；
2. 复核整体设计、模块边界、生命周期、并发模型、资源所有权和公开契约；
3. 只实施能够解决真实问题且净收益明确的设计、代码和性能优化；
4. 按影响半径从大到小完成必要的生产代码修改，再收口测试、示例和教程；
5. 建立功能、设计、代码、测试、性能和教程之间的可追踪关系；
6. 通过系统级正确性、容量、性能、跨平台和文档验收后冻结发布候选。

本轮不以减少代码行数、统一个人风格、追求抽象完整或预留未来扩展为目标，也不因为尚未
发布就重新设计已经人工确认的使用者外观。

## 2. 基本原则

### 2.1 使用者外观以当前代码为准

当前面向使用者的外观已经过人工检查。设计文档、教程、示例或测试与当前外观代码不一致
时，先判断冲突是否属于使用者外观：

1. 属于使用者外观且没有明确缺陷时，以当前代码为准，修正文档、示例和测试；
2. 不得为了匹配历史设计、形式统一、减少方法数量或追求架构美观而修改当前外观；
3. 只有存在明确的功能错误、安全问题、无法正确实现的语义冲突，或开发者单独确认时，
   才能改变当前外观；
4. 内部实现可以在保持调用方式、默认行为和错误语义的前提下优化；
5. “无需历史兼容”只允许清理未发布版本的遗留路径，不等于允许随意改变当前确认外观。

使用者外观至少包括经过复核后认定的以下内容：

- 公开类型、函数、方法和推荐调用入口；
- Application、Node、Service、Module 的业务使用方式；
- RPC 生成客户端的方法、参数、返回值和完成位置；
- Timer、Event、Await、Retire、Resume 的调用语义；
- 配置字段、默认值、单位和校验错误；
- 命令行命令、Admin Endpoint、Diagnostics Schema 和日志控制入口；
- Discovery Provider、Codec、Handler 等明确提供给使用者的扩展 SPI；
- 错误码及使用者能够稳定判断的错误语义；
- 教程明确推荐的标准使用路径。

复审开始后必须从当前代码建立外观基线，并区分“正式外观”“扩展 SPI”“底层高级入口”和
“内部实现”。不能仅按 Go 标识符是否导出判断其是否属于正式外观。

### 2.2 当前代码不是所有内部设计的默认真相

外观代码优先原则不扩展到全部内部实现。内部代码与设计不一致时，应按以下依据判断：

1. 开发者确认的最终功能和本设计原则；
2. 正确性、并发安全、资源所有权和运行时不变量；
3. 已经确认且仍然适用的系统设计；
4. 当前代码已经形成的事实；
5. 测试、Benchmark、验收报告和 Git 历史证据。

测试通过只能证明当前行为受到验证，不能自动证明当前行为就是正确设计。发现冲突时必须
记录冲突来源、影响和推荐处理方式；需要改变既有确认结论时，先更新设计并取得确认。

### 2.3 先判断优化是否必要

“发现另一种做法”不等于“需要优化”。每项设计、代码或性能优化必须回答：

1. 当前存在什么具体问题；
2. 不修改会产生什么实际影响；
3. 是否存在影响更小的解决方案；
4. 修改后如何证明收益大于改动、回归和验证成本。

“保持现状”必须作为正式备选方案。无法说明问题、收益或验收方式的项目不进入实施计划。

优化按必要性分为：

| 分类 | 处理方式 | 典型情况 |
| --- | --- | --- |
| 必须修改 | 纳入发布阻断项 | 功能错误、竞态、死锁、泄漏、无界资源、安全问题、协议错误、无法回滚 |
| 有证据时修改 | 比较保持现状、最小方案和较大方案后决定 | 重复职责、公开面过大、兼容分支持续扩大、真实热点、难以验证的高风险代码 |
| 原则上不修改 | 记录后关闭或延期 | 个人风格、单纯减少行数、未来抽象、冷路径微优化、处于测量噪声内的收益 |

简化必须减少真实的概念、状态、分支、依赖、公开面或所有权歧义。仅把复杂度转移到另一层、
把顺序代码压缩成技巧性写法或增加只服务一个调用点的抽象，不算优化。

### 2.4 已确认改动按影响半径从大到小

“大改优先”只适用于已经通过必要性判断的项目。影响等级按改动半径而不是代码行数划分：

| 等级 | 范围 | 示例 |
| --- | --- | --- |
| L0 | 功能和外部契约 | 功能范围、公开 API、配置、错误码、生成契约、Wire、Schema |
| L1 | 核心架构和运行模型 | 包边界、生命周期、状态机、调度、并发、资源所有权 |
| L2 | 跨模块公共实现 | 重复机制、兼容层、公共算法、错误或 Context 处理 |
| L3 | 单模块和单功能 | 局部缺陷、代码简化、局部性能、可观测性 |
| L4 | 叶子内容 | 测试整理、Example、教程、注释、链接和排版 |

实施顺序原则上为 L0、L1、L2、L3、L4。同等级项目再按实际包依赖自底向上实施；一个小型
签名变化如果影响大量调用方，仍属于高影响修改。每个提交必须保持可构建、可验证，不能为
了利用编译错误长时间保留破损工作树。

### 2.5 性能贯穿设计和功能闭环

性能不单独延迟到所有功能完成之后，也不在结构尚未稳定时盲目优化：

1. 设计复核时区分冷路径和热路径，确认容量、延迟、分配和过载边界；
2. L0～L2 结构调整时避免引入可预见的热路径开销；
3. L3 功能复核时为对应功能执行 Benchmark、Profile 和必要的局部性能优化；
4. 全部功能稳定后执行系统级吞吐、P50/P95/P99、峰值积压和长期资源验收；
5. 系统验收发现问题时退回所属功能处理，不在末尾追加跨模块性能补丁。

性能修改必须由目标、基线、Benchmark、Profile、Trace 或可重复的端到端结果支持。不得为
未经证明的收益引入 `unsafe`、无界缓存、复杂无锁算法、难以验证的对象池或额外抽象。

### 2.6 测试保护与生产代码修改同步

生产代码改动总体前置，但保护改动的测试不能全部推迟到最后：

- 重构前补充能够锁定必须保留行为的最小特征测试；
- 缺陷修复先增加能够稳定复现问题的失败测试；
- 修改后立即执行相关包测试、Race 和必要的 Benchmark；
- 每个阶段定期执行全仓回归；
- 每个功能批次及时补齐对应覆盖率盲区，最终阶段只处理残余测试、整理和全量门禁。

不得通过跳过测试、放宽断言、降低重复次数或隐藏不稳定结果使门禁表面通过。

### 2.7 复审必须覆盖的完整维度

本轮不能只检查已经暴露的问题。每个系统和功能都必须从以下维度得到明确结论：

| 维度 | 必须回答的问题 |
| --- | --- |
| 功能范围 | 目标功能是否全部实现；迁移矩阵、外观、设计、代码、测试和教程之间是否存在遗漏或范围漂移 |
| 设计 | 在当前必须支持的功能前提下，职责、边界、状态、数据流和失败语义是否合理；是否存在有必要的简化或优化 |
| 代码 | 多次迭代是否留下重复路径、过度抽象、兼容分支、死代码或难以阅读的实现；功能代码是否完整 |
| 正确性 | 正常、边界、错误、并发、取消、回滚、关闭和恢复路径是否存在潜在问题 |
| 测试 | 单元、集成、端到端、Race、Fuzz、覆盖率和故障验证是否与真实风险匹配，是否需要补充 |
| 性能 | 热路径是否存在不必要分配、复制、调度、锁竞争或尾延迟；容量和过载边界是否可验证 |
| 教程与示例 | 是否站在使用者角度、语言简洁、路径连续；Example 是否可运行且必要注释完整 |
| 发布质量 | 安全、敏感信息、可观测性、运维、跨平台、依赖许可证、可重复构建和生成一致性是否满足发布要求 |

“功能已实现”不能只由某个测试通过或某个文件存在来判断。必须至少核对目标功能、当前外观、
实际代码路径、风险测试和使用者教程；明确延期的内容不算遗漏，但必须在功能矩阵中留下结论。

设计复审必须对每个主题给出“保持现状”“需要简化”“需要修正”或“需要拆分后再确认”之一，
不能只有问题描述。代码复审必须区分功能缺陷、必要简化、可选整理和不应修改，避免把普通
风格差异扩大成本轮优化。

### 2.8 使用模块横向复核与教程纵向复核的双层策略

本轮不在“完全按教程”与“完全按模块”之间二选一，而是按改动阶段组合两种视角：

1. **前半程横向复核**：按影响等级和真实包依赖检查功能范围、整体设计、公共契约、核心
   状态机和跨模块实现，优先完成会影响多个功能的必要大改；
2. **后半程纵向复核**：整体结构稳定后，按教程学习路径逐项贯通设计、外观、实现、测试、
   性能、Example 和文档，验证使用者能够完成真实任务；
3. **最终横向补漏**：按生命周期、并发、资源、安全、配置、错误、性能、平台和运维等横切
   风险再次扫描，发现教程单条路径无法暴露的问题。

教程是功能范围、可用性和最终验收的重要输入，但不用于决定前半程大范围代码修改顺序。
模块复核用于保证架构和公共机制一致，但不能替代使用者端到端闭环。动态问题只进入一份总
实施计划和追踪矩阵；每批只处理一个边界清楚的高影响主题或一个完整功能闭环，避免同时
展开过多未收口内容。

### 2.9 设计和性能优化必须控制范围

本轮是发布前复审和必要优化，不是重新设计 Origin。无论问题影响等级多高，都只能在解决
当前已确认功能的真实问题所需范围内修改；“大改优先”表示先处理已经确认且影响广的改动，
不表示允许扩大目标、顺手重构相邻系统或追求理论上的最优架构。

设计优化必须遵守：

1. 以当前发布功能和已经确认的使用者外观为边界，不为未来需求增加抽象、扩展点或配置；
2. 现有设计职责清楚、行为正确、风险可控且测试充分时，即使存在其他可行方案也保持现状；
3. 优先选择能够解决问题的最小闭环方案，不为了全局对称或形式统一改造需求不同的模块；
4. 一次只复核和调整一个边界清楚的系统或决策主题，跨系统影响只处理必要接口和不变量；
5. 发现相邻问题但不阻塞当前目标时进入台账，不自动并入当前批次；
6. 方案开始增加新的概念、状态、层级或验证成本，却没有相应减少更大复杂度时停止实施；
7. 任何超出原定“涉及模块、外观、行为和验证”范围的扩展都必须重新判断必要性和影响等级。

性能优化必须遵守：

1. 只针对当前发布负载、已确认热路径、明确容量目标或稳定性能退化，不全面追逐微小开销；
2. 优化前固定场景、数据规模、基线、目标和允许复杂度，避免测量过程中不断扩大问题范围；
3. 当前指标已经满足目标且没有显著热点时保持现状，不为了更好看的 Benchmark 继续修改；
4. 优先选择局部、可回退、能由现有测试和 Benchmark 证明的方案；
5. 局部收益处于噪声范围、不能改善实际端到端结果或会明显增加复杂度时不实施；
6. 优化一个热路径时只检查必要的上下游影响，不借机重写整条调用链；
7. 达到预定目标、边际收益不再显著或风险开始大于收益时立即停止，保留验证结果。

每项设计或性能优化在进入实施计划前必须写明范围内、范围外、停止条件和验收标准。实施中
发现必须扩大范围才能正确完成时，应暂停当前项目并重新确认，不能用连续的小改动绕过范围
门禁。

### 2.10 全量覆盖审计与无已知缺陷目标

本轮必须对全部当前生产代码执行测试覆盖审计，不允许只查看全仓总覆盖率。覆盖审计至少下钻
到包、文件、函数和可稳定触发的关键分支，逐项判断未覆盖代码是测试遗漏、不可达代码、平台
限制、生成代码，还是确实无法稳定构造的系统故障。

重点功能以达到 `100%` 可达语句覆盖并覆盖全部可稳定触发的关键分支为目标。重点功能包括
公开外观背后的核心路径，以及生命周期、调度、Timer、Event、Await、RPC、Codec/Wire、
Transport、Discovery、配置、日志、Admin/Diagnostics、错误映射、资源所有权和失败回滚等
一旦出错会影响正确性、稳定性、数据或可用性的代码。不能只用语句覆盖率代替分支、状态转换
和并发场景验证。

全部生产代码必须满足：

1. 每个可达函数都经过覆盖审计，不存在无人检查的低覆盖文件或函数；
2. 正常、空值、零值、边界、非法输入、溢出和稳定错误分支具有有效断言；
3. 生命周期和资源代码覆盖部分初始化失败、逆序回滚、重复关闭、取消、超时和泄漏；
4. 并发代码除覆盖率外必须经过 Race、重复执行和必要的压力验证；
5. Codec、配置、协议和其他输入空间较大的代码使用 Fuzz 补充示例测试；
6. TCP、NATS、etcd、进程控制和管理 HTTP 使用真实协议或独立进程集成测试；
7. 生成代码通过生成器测试、黄金结果、契约测试和生成一致性验证，不机械追求逐行覆盖；
8. 平台专属或无法稳定触发的故障分支必须记录具体位置、原因、替代验证和剩余风险；
9. 不为了百分比编写没有有效断言、复制生产实现或只能验证测试自身的用例；
10. 修复任何缺陷前先增加稳定复现测试，修复后保留为长期回归用例。

覆盖率不能替代代码 Review。全部核心生产代码必须按包和功能阅读完整实现，而不是只检查本轮
Diff；重点检查控制流、状态转换、并发时序、资源所有权、错误路径、边界、性能、可读性和注释
是否与真实行为一致。高风险功能在实现复核后还要使用新的任务上下文进行独立二次 Review；
每个有效发现必须关联修复、回归测试或明确的不修改依据，不能只留下一条无结论意见。

发布质量目标是 Origin 在已确认功能、平台、配置和负载范围内无已知缺陷，且不存在未解释的
测试失败、偶发失败、竞态、死锁、泄漏、数据错误或性能退化。软件测试不能证明数学意义上的
绝对零 Bug，因此“稳定可靠”必须由代码 Review、覆盖审计、单元/集成/端到端测试、Race、
Fuzz、故障注入、压力与长期运行、跨平台验证和剩余风险记录共同支撑，不能只凭一次全仓测试
通过下结论。

### 2.11 Ubuntu 实机验证是强制门禁

Linux 不能只由 Windows 上的交叉编译替代。本轮所有生产代码修改都必须在指定 Ubuntu 实机
上验证，且使用与发布候选一致的当前工作树；测试凭据、主机密码和临时密钥不得写入仓库、
计划或报告。

验证分三层执行：

1. 每个代码修改子批次在本地定向验证后，在 Ubuntu 执行受影响包的普通测试，并按风险执行
   Race、Fuzz、重复测试或真实协议测试；
2. 每个 Task 收口前，在 Ubuntu 执行全仓普通测试、Vet、生成一致性和适用的全仓或分组 Race，
   不能只依赖目标包通过；
3. 系统验收和最终发布门禁在 Ubuntu 执行真实 TCP、NATS、etcd、进程、文件系统、信号、
   长期运行、压力与性能场景，并保留环境、命令、结果和限制证据。

Windows 继续负责 Windows 专属进程、文件锁、路径和平台分支；macOS 在没有实机条件时允许以
交叉构建和平台私有单元证据补充。Windows、Ubuntu 和 macOS 证据相互补充，任何一个平台的
成功都不能掩盖另一个目标平台的失败。Ubuntu 环境缺失、代码未同步或测试未执行时，相应批次
只能标记为未完成，不能降低门禁或用“本地已通过”关闭。

## 3. 文档与事实的处理规则

### 3.1 依据优先级

本轮工作的依据顺序为：

```text
开发者确认的最终功能和行动原则
→ 当前已经人工确认的使用者外观代码
→ 本轮复审总设计
→ 正确性及运行时不变量
→ 对应系统仍然有效的设计文档
→ 当前内部代码事实
→ 测试、报告和历史材料
```

该顺序用于解决冲突，不表示较低层材料可以不检查。当前 `docs/baseline/v3.0` 仍作为历史
设计和实现依据；其“已发布、冻结”表述与当前实际尚未对外发布的关系，应作为文档一致性
问题在本轮确认，但不在本设计尚未复核时直接重写历史材料。

### 3.2 冲突分类

| 冲突 | 处理 |
| --- | --- |
| 外观文档与当前外观代码不同 | 当前代码优先，后续修正文档、示例和测试 |
| 内部代码偏离仍有效的设计 | 判断代码是否需要修正，实施前记录依据 |
| 设计已过时、代码行为正确 | 更新单一主设计及其引用 |
| 设计和代码都存在问题 | 形成新的设计决策，确认后实施 |
| 只是表达差异 | 澄清文档，不修改代码 |
| 没有实际影响 | 记录并关闭，不为了形式一致制造改动 |

### 3.3 文档数量控制

本轮开始时只建立本总设计；确认后再建立一份总实施计划。只有独立且重大的 L0/L1 变化
才新增或更新对应系统设计。局部代码整理、死代码删除、测试和注释补充只进入实施计划，
不分别创建设计文档。全部完成后形成一份总验收报告。

## 4. 执行阶段

### 4.1 阶段 0：范围与现状基线

1. 确认发布功能范围和明确延期项；
2. 建立功能、设计、代码、测试、性能、教程追踪矩阵；
3. 建立当前使用者外观清单和契约保护；
4. 保存全仓测试、Race、逐包/逐函数覆盖率、跨平台构建和 Benchmark 基线；
5. 对问题标记必要性、L0～L4、依赖、风险和验证方式。

本阶段除必要的基线工具和契约测试外，不修改生产行为。

### 4.2 阶段 1：全局设计复核

按“功能范围、整体架构、核心运行模型、外部契约、子系统设计”的顺序复核。先处理会影响
多个系统的结论，再处理单系统细节。阶段结束前集中提交需要开发者确认的问题；未确认的
L0/L1 项目不得进入实现。

每个设计主题必须同时阅读当前有效设计文档和对应代码，以当前必须支持的功能为边界，检查
设计是否合理、是否完整、是否可以用更少职责、状态、接口或数据转换实现。必要时按功能和
独立决策边界拆分设计，再按依赖与影响排序逐一确认；不得只根据历史设计推导当前外观，也
不得只根据当前内部代码反向认定设计正确。

### 4.3 阶段 2：L0/L1 生产代码调整

先实施已经确认的公开契约、生成器、配置、协议和 Schema 变化，再按实际依赖图自底向上
调整核心状态、生命周期、调度、并发和资源所有权。当前使用者外观默认冻结，只有经过单独
确认的外观缺陷才能进入本阶段。

### 4.4 阶段 3：L2 跨模块结构优化

删除确认无用的兼容路径和 Deprecated 入口，合并真实重复实现，收缩公共边界，统一错误、
Context 和资源处理。每项修改必须证明减少了真实维护面，不能为了目录、命名或形式统一
重写需求不同且已经稳定的实现。

本阶段还要专门复核多次迭代产生的复杂度：同一语义的多套路径、只服务历史实现的回退、
单一实现却增加理解成本的接口、过深调用层级、分散的状态提交、重复校验和失效注释。优化
应优先使控制流、所有权和失败处理易于阅读；不能用压缩行数、技巧性表达或新的通用框架
替代原本清晰的代码。兼容代码只有确认不属于当前外观、扩展 SPI 或必要测试边界后才删除。

### 4.5 阶段 4：L3 功能闭环

整体结构稳定后，按使用者学习路径逐项复核：Application 与配置、日志与 Service/Module、
Timer/Event/Await、RPC、Transport、Discovery、Retire/Resume、Admin/Diagnostics/pprof、
性能和故障排查。

每项功能依次完成：功能完整性、正确性测试、缺陷修复、局部简化、Benchmark/Profile、必要
性能优化、完整单元/集成/Race/Fuzz 和功能验收。原则上不再修改整体架构和当前外观。

纵向批次按教程和依赖组织为：

| 批次 | 功能 |
| --- | --- |
| A | 00～02：快速入口、Application、Node、配置和命令 |
| B | 03～04：日志、Service、Module 和业务配置 |
| C | 05：Timer、Event、Await、安全执行和 Node 游戏逻辑时间 |
| D | 06：RPC 契约、生成器、Codec 和本地调用（含 Service 自调用 RPC） |
| E | 07～09：TCP/NATS 远程 RPC、路由、Discovery、Retire/Resume 和优雅停止 |
| F | 10：Admin、Diagnostics、pprof 和指标适配 |
| G | 11～12：性能理解、故障排查，以及不占教程编号的部署运维材料 |

批次 D 必须显式验证 Service 使用自身生成客户端调用自身的边界：普通 goroutine 的 `Call`，
Service Task 内协作式 `Await`、`Async`、`Notify`，以及 Task 内同步 `Call` 不释放当前执行槽、
只能由 Deadline 结束的误用边界。不能只用“两个不同 Service 的同 Node RPC”替代这组重入测试。

每个批次都必须检查功能是否遗漏、代码是否完整以及潜在问题，覆盖正常路径、边界输入、错误
分支、部分初始化失败、逆序回滚、取消、Deadline、队列满、资源上限、并发竞争、重复调用、
幂等关闭、panic、恢复和平台差异。发现跨批次 L0/L1 问题时停止当前批次并退回对应阶段，
不能在功能代码中局部绕过整体设计。

每个批次结束前生成对应包的覆盖率明细，检查未覆盖函数和语句，并用人工分支清单补足 Go
语句覆盖率不能表达的状态转换和错误分支。重点功能未达到 `100%` 可达语句与关键分支目标时，
必须补测或记录无法达到的具体技术原因、替代验证和剩余风险；不能用其他高覆盖包抬高全仓
平均值掩盖关键路径缺口。

### 4.6 阶段 5：系统级正确性、容量和性能验收

覆盖多 Node、多 Service、真实 TCP/NATS/etcd、断线恢复、Discovery 更新、退休恢复、过载
拒绝、日志与诊断并行、长期 goroutine/连接/Timer/内存稳定性以及受支持平台差异。阶段通过
后冻结生产代码；发现问题必须退回所属阶段处理并重新验收。

除运行时性能外，本阶段还要横向检查 Admin/pprof 暴露、认证授权、敏感配置和日志脱敏、
错误可诊断性、容量指标、依赖维护状态与许可证、生成和构建可重复性，以及部署、停止、故障
恢复和数据采集的可操作性。没有明确发布要求的扩展能力不顺手实现，只记录剩余风险或延期
结论。

系统验收必须包含故障注入、并发压力、重复启停、长时间运行和资源基线比较，专门寻找单元
覆盖率无法发现的时序、积压、恢复和泄漏问题。任何失败、超时、波动或资源增长都必须定位；
未解释结果不能按偶发问题忽略，也不能仅靠增加超时或重试次数使验收通过。

### 4.7 阶段 6：L4 测试、Example 和教程收口

在生产代码冻结后复核并补齐不要求改变生产行为的残余覆盖率盲区，整理脆弱或重复测试，
更新 Example、中文注释、教程、运行脚本、预期输出、常见错误和链接。残余测试发现生产代码
问题时必须退回所属阶段修复并重新通过冻结门禁。现有教程在前面阶段作为需求输入，但最终
改写和润色放在本阶段，避免外观和行为变化造成重复返工。

教程必须站在第一次使用 Origin 的开发者角度编写，语言简洁，先说明要解决的问题和最短
成功路径，再解释必要原理和边界。每章至少核对前置条件、完整命令、预期输出、停止与清理、
常见错误和下一步；删除实现历史、重复说明和使用者完成任务不需要的内部细节。

每个可运行 Example 必须与教程调用方式一致，能够参与构建并按公开命令运行。示例中的公开
类型、生命周期步骤、并发归属、资源释放、容易误用的调用和关键断言必须有完整准确的中文
注释；注释解释目的、顺序和原因，不机械翻译每一行。文档代码片段不能代替完整 Example，
Example 也不能依赖 README 未说明的隐含环境或后台状态。

### 4.8 阶段 7：只读终审和发布门禁

终审不安排主动重构或探索性优化。若发现 L0/L1 问题，必须正式退回相应阶段，不能在终审
中局部打补丁。发布候选至少满足：

- 功能矩阵没有未知项，延期和删除项均有明确结论；
- 没有未关闭的发布阻断问题；
- 外观、设计、实现、测试、示例和教程一致；
- 兼容路径、Deprecated 入口和高级公开入口均有删除或保留依据；
- 全部生产代码已完成逐包、逐文件和逐函数覆盖审计，没有无人检查的可达路径；
- 重点功能达到 `100%` 可达语句和关键分支目标，或对例外提供具体原因、替代验证和剩余风险；
- 全仓测试、Race、静态检查、生成一致性和跨平台构建通过；
- 真实协议集成、容量、尾延迟和长期资源验收通过；
- 不存在已知功能缺陷，以及未解释的性能退化、偶发失败、竞态、死锁或泄漏；
- 从干净环境能够按教程完成主要用户路径。

## 8. 模型使用策略

Sol 高完成普通实施，Sol 极高负责高影响设计和终审”。模型建议依据
[OpenAI 模型目录](https://developers.openai.com/api/docs/models)和
[GPT-5.6 使用指南](https://developers.openai.com/api/docs/guides/latest-model)；模型输出不能

## 11. 全局设计复核冻结结论

2026-08-09 已按“公共约束 → 生命周期与资源所有权 → 调度 → RPC → Transport/Discovery →
Admin/Diagnostics”的依赖顺序完成代码与设计对照。详细证据、范围控制和验证命令统一记录在
[总实施计划 Task 2](../plans/Origin发布前全面复审与优化实施计划.md#8-task-2全局设计与-l0l1-复核)。

候选结论如下：

1. 没有发现需要改变 `Application → Node → Service → Module` 所有权、单执行槽调度、生成 RPC、
   Transport/Provider owner 或 Admin 独立控制面的 L0 架构问题；
2. 当前使用者外观、错误码数值、配置、Wire、控制文件格式和 Diagnostics Schema 均保持不变；
3. 不因文件长度、状态数量、形式统一、未来扩展或微小冷路径收益重写现有状态机；
4. 唯一 L1 是控制邮箱协议可靠性：Windows 响应读取需要只对 sharing/lock violation 做有界
   重试，控制响应白名单需要包含当前已存在的 Admin `8003/8004`；
