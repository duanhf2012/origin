**Goal:** 在不扩张业务运行时和使用者交付范围的前提下，补齐不可变 Diagnostics 快照、
可控 Diagnostics/pprof Server、受限 Service Application 外观、RPC 有界统计和发布前质量
门禁，使当前代码达到 v3.0 发布候选质量。

**Architecture:** 新的 `diagnostics` 叶子包只保存稳定 DTO 和 `Source`；RPC 仅维护固定
Local/TCP/NATS 原子累计器，Node 把现有叶子状态映射成诊断 DTO，Application 顺序聚合并
拥有两个相互独立的 HTTP 控制器。Service 通过 Node 私有 Runtime 桥取得最小
`ApplicationRuntime`，不持有具体 Application。命令行参数只决定初始监听状态，最终清理
仍由 Application 统一倒序执行。

**Tech Stack:** Go 1.26.5、标准库 `net/http`/`net/http/pprof`/`runtime`、Origin M0～M21。
不增加第三方直接依赖。

## 全局约束

- 严格按本计划顺序执行；每项先写失败测试或 Benchmark，再实现最小生产代码。
- `diagnostics` 不导入 application、node、service 或 rpc；快照不携带 error、配置原文、
  业务 Payload、远端地址和动态 Label。
- RPC 热路径只增加固定原子计数，不增加逐请求对象、Map、字符串格式化、接口回调、
  goroutine 或 Histogram。
- Diagnostics 和 pprof 各自使用 Application 私有 Listener、ServeMux、Server、状态锁和
  等待机制；禁止使用 `http.DefaultServeMux`。
- Start 只允许资源初始化后的 Starting/Running；Stop 始终幂等。非预期 Serve 退出只标记
  对应诊断资源失败，不终止业务 Application。
- 不加入 Prometheus、OpenTelemetry、历史快照、CI、使用者文档、示例、发布制品、正式
  标签或 M23。
- 新增公开符号必须写中文 GoDoc；所有资源所有权、状态转换和错误映射必须在实现附近说明。

**Internal model:**

```go
type TransportStats struct {
    Pending, PendingHighWater uint64
    OutboundAccepted, OutboundCompleted, OutboundFailed uint64
    OutboundTimeout, OutboundRejected uint64
    InboundAccepted, InboundCompleted, InboundFailed uint64
    InboundTimeout, InboundRejected uint64
    PayloadSentBytes, PayloadReceivedBytes uint64
    Reconnects, ConsecutiveFailures uint64
}

type Stats struct {
    Local TransportStats
    TCP   TransportStats
    NATS  TransportStats
}

func (runtime *Runtime) Stats() Stats
```

Runtime 内保存三个固定 `atomic.Uint64` 计数块。prepared transport 直接选择计数块，不能
构建动态 key。提交成功时 accepted/pending++；提交前失败计 rejected；最终业务口径在
Client 层收口：Await 解码返回后、Async `decodeAndCallback` 返回后才 completed/pending--。
错误按稳定码区分 timeout 与 failed。Notify 不进入 request pending，但仍统计投递和 Payload。
入站在解析/路由准入、Dispatcher 最终返回、超时和拒绝位置计数；TCP/NATS 共享相同口径。

私有控制器状态为 stopped/serving/failed/closing，持有 mutex、Listener、Server、实际地址、
done channel 和稳定错误码；它只复用资源生命周期，不统一路由。Start 先验证生命周期和地址，
再 `net.Listen`，提交状态后由 Application 所有 goroutine 执行 Serve。Stop 先从状态中摘出
Server，再 Shutdown；Context 耗尽时 Close Listener 并等待 Serve 退出。并发 Start/Stop、
同地址幂等和不同地址冲突在线性化测试中固定。

Diagnostics 使用私有 ServeMux，只注册 `GET /debug/origin/diagnostics`。handler 每次调用
`app.Diagnostics()` 并用 `json.Encoder` 流式写出；非 GET 返回 405。设置 ReadHeader、Write、
Idle 超时和 MaxHeaderBytes；不注册控制端点。

### 双平台质量门禁

- Windows/amd64 使用 Go 1.26.5 完成全仓测试、Race、70.0% 覆盖率、Vet、构建、模块校验、
  RPC 生成器只读检查和适用 Benchmark；Windows/amd64、macOS/amd64、macOS/arm64 与
  Linux/arm64 目标构建通过；
- Ubuntu/amd64 使用 Go 1.26.5 完成全仓测试、Race、70.4% 覆盖率、Vet、构建、模块校验、
  RPC 生成器只读检查和真实集群测试；
- `govulncheck v1.6.0` 报告 0 个可达漏洞、0 个导入包漏洞。依赖模块中另有两个未调用
  报告：GO-2026-5932 位于未使用的 `x/crypto/openpgp`，GO-2026-5841 位于未导入的
  `klauspost/compress/s2`，均不构成当前调用路径；
- 真实 NATS 三节点连接和跨 Node RPC 通过；硬终止首节点后客户端按
  `Disconnected -> Reconnected` 转移到剩余节点。真实 etcd 3.7.1 三成员全部终止后
  Provider 进入 Recovering，恢复集群后待提交 Publish 完成重放并成功 Withdraw；
- 验收中修正了 NATS 1 MiB 默认 Payload 与 64 KiB 并发矩阵不匹配、集群发现地址未广播、
  etcd 空闲多端点过度 Ping、Windows CPU Tick 单样本校准、停止文件幂等竞态和压测子进程

## 计划自查结论

- 依赖顺序与 M22 设计第 14 节一致：DTO → RPC → 聚合/外观 → HTTP → CLI/清理 → 验收。
- 每个公开能力都有失败、并发、幂等、清理或性能测试，不用 mock 调用次数代替行为验证。
- RPC 完成口径放在真正完成业务语义的 Client/Dispatcher 边界，避免把网络响应误记为业务
  callback/解码完成；固定累计器满足低分配约束。
- Service Runtime 使用可选私有桥，不破坏现有最小 Runtime 和第三方测试替身。
- HTTP 资源由 Application 单一所有，能覆盖启动回滚、运行时异常、Context 耗尽和最终释放。
- Ubuntu 长压测和人工环境门禁已经完成；M22 只标记发布候选质量收口完成，未创建
  `v3.0.0` 标签、发布制品、使用者文档、使用示例、CI 或 M23。
