# Origin 第三版 M9 Service 调度与协作式等待实施计划

> 文档状态：已完成
> 创建日期：2026-07-27
> 对应设计：[M9 Service 调度与协作式等待设计](../design/milestones/M9-服务调度与协作式等待设计.md)

## 1. 实施目标

M9 在 M7 生命周期和 M8 Node 时间轮之上建立每个 Service 独立的串行调度器。本里程碑只
实现普通异步任务、协作式 Await、Deadline 控制和停止排空，不提前接入 RPC、业务 Timer、
Module、事件或服务发现。

实现必须满足：

- 每个 Service 任意时刻最多一个业务任务持有执行权；
- 普通任务由长期 Runner 连续执行，不为每个普通任务创建 goroutine；
- Await 在当前任务 goroutine 中执行等待函数，释放执行权后由替补 Runner 处理其他任务；
- Await 恢复时把执行权交还原 goroutine，保留原调用栈；
- Ready 任务使用公共有界环形队列，恢复项不被容量二次拒绝；
- 每个 Scheduler 使用独立 DeadlineQueue 和一个可等待退出的 Deadline 控制 goroutine；
- Node 按已确认顺序启动和停止 Scheduler；
- 过载、取消、超时、panic 和停止路径均具有稳定错误及完整资源回收；
- 通过 Benchmark、逃逸分析和堆数据决定 Task 最终是否池化。

## 2. 代码范围

新增公共算法包：

```text
internal/container/ringqueue
```

该包只提供无锁、有界、可增长的泛型环形队列。它不依赖 Service、日志、统计或框架错误码，
并由调用方负责并发同步。

主要修改：

- `service`：调度配置、执行统计、Task Context、Runner、Await、Deadline 控制和装配接口；
- `node`：为每个 Service 启停 Scheduler，并保持 TimerEngine 的所有权；
- `application`：解析 Node 下的 `scheduler` 配置并填充默认值；
- `errs`：补齐已确认的 Service 生命周期和过载错误码；
- `docs`：记录实测结果、Task 池化结论和里程碑状态。

## 3. 实施步骤

### 3.1 公共环形队列

1. 建立 `ringqueue.Queue[T]`，构造时校验初始容量和硬上限；
2. 实现入队、出队、长度、容量和完整清空；
3. 初始容量按 `min(64, max_tasks)` 创建，满时按两倍增长且不超过硬上限；
4. 出队与清空必须把槽位置零，避免闭包和大对象被底层数组长期引用；
5. 单元测试覆盖空队列、回绕、扩容、硬上限和引用释放；
6. Benchmark 对比环形队列和固定容量 Channel 在同等锁路径下的成本。

### 3.2 ServiceScheduler 与普通任务

1. 为每个运行 Service 创建一次性 Scheduler；
2. 使用一个短锁统一裁决状态、Ready、Accepted、Running、Awaiting 和累计统计；
3. `DispatchAsync` 只接收新的根任务，成功后使用容量 1 Channel 合并唤醒；
4. Runner 从 Ready FIFO 连续取任务，在用户代码执行期间不持有调度锁；
5. Task 最外层恢复业务 panic、记录原始堆栈并准确归还执行槽；
6. 完成后清空函数、Context 和临时引用；
7. Running、Draining、Stopped 分别返回已确认的稳定错误。

### 3.3 Await 与执行权交接

1. Task Context 携带私有执行令牌，Await 校验 receiver、Scheduler、Task 和当前执行权；
2. 按“调用方 Deadline、Service 覆盖、Node 默认、内置 15s”确定有效超时；
3. 使用 `context.WithCancelCause` 创建等待 Context，并把 Deadline 登记到 M8；
4. 当前 Task 转为 Waiting 后启动一个替补 Runner，原 goroutine 直接执行 `fn`；
5. `fn` 返回或 panic 后把同一个 Task 作为恢复项加入 Ready，不增加 Accepted；
6. 活动 Runner 遇到恢复项时退出并把执行权交还原 goroutine；
7. 原 goroutine 清理 Deadline 和等待引用后继续原调用栈；
8. Context 取消、Deadline 到期、停止取消和 `fn` panic 只完成一次。

### 3.4 Deadline 与生命周期

1. Scheduler 从 Node TimerEngine 创建并独占一个 DeadlineQueue；
2. Deadline 控制 goroutine 分批消费到期 ID，只取消等待 Context，不执行业务代码；
3. Scheduler 启动失败按创建逆序关闭 Queue、控制 goroutine 和 Runner；
4. Node 在 `OnStart` 成功后启动 Scheduler，再发布 Service Running；
5. 停止时先发布 Service Stopping，再让 Scheduler 拒绝根任务并排空已接受任务；
6. 停止 Context 到期只取消 Scheduler 生命周期 Context，仍等待实际任务返回；
7. Runner 全部退出后关闭 DeadlineQueue、等待控制 goroutine，再调用 `OnStop`；
8. TimerEngine 最后仍由 Node 关闭。

### 3.5 配置、错误和统计

1. Node 默认配置为 `max_tasks=20000`、`max_await_tasks=10000`、
   `default_await_timeout=15s`；
2. 校验总任务硬上限不超过 `65536`，Await 上限不超过总任务上限；
3. 增加 Service NotReady、Stopping、Stopped、QueueFull 等稳定错误；
4. `ExecutionStats` 在一次短锁内返回一致快照，不公开内部对象；
5. 高水位和拒绝数只做低成本累计，不在热路径同步刷日志。

## 4. 测试与性能验证

单元测试和竞态测试至少覆盖：

- FIFO、单执行槽、多提交方、同一 Runner 连续处理和停止排空；
- Await 释放、恢复、原 goroutine、连续 Await、乱序完成和恢复排队；
- 显式/Service/Node/内置 Deadline 优先级，以及忙 Runner 下的及时取消；
- nil、错误 Context、跨 Service Context、过载、取消、超时和 panic；
- 1、100、1000、10000 个 Waiting 的恢复、取消和超时风暴；
- Scheduler 启动失败、重复停止、Queue 关闭竞争和 goroutine 退出；
- 配置默认值、非法边界、未知字段以及 Node 启动失败回滚；
- 大闭包引用清理和旧 Context 不会获得后续任务执行权。

Benchmark 至少覆盖普通串行/并行投递、Ready 排空、Await 交接、已完成等待、并发 Waiting、
超时、统计、RingQueue、Channel 对照和 Task Pool 对照。最终根据 `ns/op`、`B/op`、
`allocs/op`、逃逸分析和堆占比决定是否池化 Task。
