# Origin 第三版 M2 内存复用库实施计划

> 计划状态：已完成并通过验收
> 创建日期：2026-07-25
> 对应里程碑：[M2 内存复用库里程碑设计](../design/milestones/M2-内存复用库里程碑设计.md)

## 1. 实施目标

在不接入 Application、TCP 或 RPC 的前提下，完成可独立创建、并发使用和诊断的内部 Buffer 池。

M2 只交付 `internal/bufferpool`、配套测试、Benchmark、逃逸分析和内存滞留基线。统计默认关闭，只有使用者显式设置 `Options.TrackUsage=true` 时才记录当前未归还 Buffer。

## 2. 实施步骤

1. 建立 `internal/bufferpool` 基础类型：
   - 定义 `Options`、`Pool`、`Buffer`、`Stats` 和 `BucketStats`；
   - `Options.TrackUsage` 零值为 false；
   - 所有公开标识和关键内部字段补充中文注释；
   - 不建立接口、全局 Pool、`init()` 或第三方依赖。
2. 实现固定容量档位：
   - 档位为 `16 B`、`32 B`、`64 B`、`128 B`、`256 B`、`512 B`、`1 KiB`、`2 KiB`、`4 KiB`、`8 KiB`、`16 KiB`、`32 KiB`、`64 KiB`；
   - 使用固定数组和位运算定位；
   - 每个档位独立使用 `sync.Pool`；
   - 不预分配、不增加 `8 B` 和 `128 KiB` 档位。
3. 实现 Buffer 生命周期：
   - `Acquire(size)` 返回长度等于请求值、容量等于档位值的可写切片；
   - `Acquire(0)` 返回可释放的非池化空 Buffer；
   - 负长度触发内部不变量 panic；
   - 大于 `64 KiB` 直接分配并在释放时清除底层切片引用；
   - `Release` 定义在 Buffer 上，支持 nil 和可检测窗口内的重复释放；
   - 释放后访问在可检测窗口内触发 panic；
   - 默认不清零底层字节。
4. 实现可选未归还统计：
   - `TrackUsage=false` 不执行统计原子加减；
   - `TrackUsage=true` 分档记录当前未归还数量；
   - 记录空 Buffer、超大 Buffer 数量和超大容量；
   - `Stats()` 返回总量、总容量和分档快照；
   - 关闭统计时返回 `Enabled=false` 的零值快照；
   - 不记录指针、调用栈、累计次数、命中率、峰值或 `sync.Pool` 缓存数量。
5. 补充单元和并发测试：
   - 覆盖零值、负值、全部档位和超大边界；
   - 覆盖长度、容量、Pool 隔离、重复释放和释放后访问；
   - 覆盖默认不清零；
   - 覆盖统计开启、关闭、分档、空 Buffer、超大 Buffer 和静止点归零；
   - 覆盖多 goroutine、多 Pool 和随机尺寸压力；
   - 全部并发测试通过竞态检测。
6. 建立性能与内存基线：
   - 比较强制逃逸直接分配与池化；
   - 覆盖 `16 B`、`32 B`、`64 B`、`256 B`、`1 KiB`、`4 KiB`、`32 KiB`、`64 KiB` 和 `128 KiB`；
   - 分别测试统计关闭与开启、串行与 `RunParallel`；
   - 记录 `ns/op`、`B/op` 和 `allocs/op`；
   - 执行逃逸分析并记录 Buffer 相关结论；
   - 固定 `GOMAXPROCS` 执行多轮突发与 GC，记录内存滞留基线；
   - 验证超大 Buffer 不重新进入池。
7. 完成质量门禁并把实现结果、命令和基线回写到本计划及 M2 设计。

## 3. 关键实现边界

- M2 包路径固定为 `internal/bufferpool`，包名为 `bufferpool`，业务项目不能直接导入。
- Pool 可以被多个 goroutine 并发使用，单个 Buffer 仍只有一个所有者。
- 不实现运行中动态切换统计；`TrackUsage` 只在 `NewPool` 时读取。
- 不根据开发或生产环境自动设置统计。
- M2 不读取 YAML、JSON、环境变量或命令行；M7 再映射 Application 级对外配置。
- M2 不依赖 M1 日志；M16 再处理停止后的非零统计告警。
- 不实现 Config、Close、Append、Resize、引用计数、零拷贝或安全清零开关。
- 不实现 `timerEntry`、`pendingCall`、Protobuf 消息池或通用对象池。
- 不实现最大包长、发送队列、背压、TCP、NATS 或 RPC。
- 不使用 `unsafe`，不预先实现小包栈上快速路径。

### 7.2 性能基线

基线环境：Go 1.26.5、Windows/amd64、AMD Ryzen 7 7840HS。

下表单位为 `ns/op`；括号内为 `B/op, allocs/op`。直接分配基线通过测试专用逃逸接收点强制堆分配，避免编译器把局部切片优化到栈上。

| 请求大小 | 直接分配 | 默认池化 | 默认并发池化 | 开启统计 | 开启统计并发 |
|---|---:|---:|---:|---:|---:|
| 16 B | 23.34（16, 1） | 15.06（0, 0） | 2.10（0, 0） | 15.18（0, 0） | 28.95（0, 0） |
| 32 B | 28.16（32, 1） | 15.94（0, 0） | 2.07（0, 0） | 15.45（0, 0） | 22.44（0, 0） |
| 64 B | 45.03（64, 1） | 15.10（0, 0） | 2.15（0, 0） | 16.57（0, 0） | 17.56（0, 0） |
| 256 B | 117.7（256, 1） | 16.43（0, 0） | 2.25（0, 0） | 15.67（0, 0） | 26.50（0, 0） |
| 1 KiB | 283.8（1024, 1） | 15.32（0, 0） | 2.24（0, 0） | 15.35（0, 0） | 17.35（0, 0） |
| 4 KiB | 932.7（4096, 1） | 14.85（0, 0） | 2.18（0, 0） | 14.81（0, 0） | 25.18（0, 0） |
| 32 KiB | 5245（32768, 1） | 15.25（0, 0） | 2.10（0, 0） | 15.25（0, 0） | 19.11（0, 0） |
| 64 KiB | 10616（65536, 1） | 14.95（0, 0） | 2.29（0, 0） | 16.79（0, 0） | 32.83（0, 0） |
| 128 KiB | 17025（131072, 1） | 34972（131121, 2） | 39044（131123, 2） | 32916（131120, 2） | 41792（131124, 2） |

结论：

- `16 B`～`64 KiB` 稳态池化路径达到 `0 B/op、0 allocs/op`；
- `128 KiB` 超出池化上限，按设计直接分配并在释放时丢弃，因此不应使用池化路径追求收益；
- 默认关闭统计时无原子计数；开启统计的串行成本较低，并发下会产生可见的原子竞争，符合“显式诊断开关”的定位。

### 7.3 逃逸与内存滞留

针对 `bufferpool` 包执行定向逃逸分析，结论如下：

- Pool miss 时创建的 `Buffer` 和底层字节切片进入 `sync.Pool`，按设计逃逸；
- Pool hit 的稳定路径不产生新分配，Benchmark 为 `0 B/op、0 allocs/op`；
- `Stats()` 的分档快照切片会逃逸，但该接口仅用于低频诊断，不进入收发热路径；
- 实现未使用 `unsafe`，也没有额外后台 goroutine。

突发测试取得并释放 `512 × 64 KiB` 池化 Buffer 和 `128 × 128 KiB` 超大 Buffer，经两轮 GC 与 `debug.FreeOSMemory` 后：

```text
baseline=331432 B
after=332440 B
delta=1008 B
```

未发现持续无界增长，超大 Buffer 没有重新进入池。
