# Origin 第三版 M4 程序命令与进程控制库实施计划

> 计划状态：已完成并通过验收
> 创建日期：2026-07-26
> 对应里程碑：[M4 程序命令与进程控制库设计](../design/milestones/M4-程序命令与进程控制库设计.md)

## 1. 实施目标

实现公开 `command` 包，为最终可执行程序提供实例级命令运行器、`start`、`stop`、
`help`、`version` 和自定义离线命令，并以 AppName PID 文件锁实现可靠的本机进程占用。

M4 只把平台停止通知转换为 Start Handler 的 Run Context 取消。它不创建 Application，
也不实现 Node、Service、RPC、配置加载、退休或业务优雅停止逻辑。

## 2. 实施步骤

1. 固定 `golang.org/x/sys v0.47.0`，在 `errs` 中登记两个进程控制错误码；
2. 建立公开 `command` API、实例级 Runner、稳定退出码和无全局状态的自定义命令注册；
3. 实现内置命令归一化、参数校验、帮助、构建信息和稳定错误映射；
4. 实现 AppName、NodeID 列表、配置目录和 PID 目录校验；
5. 实现 PID 文件诊断记录以及 Windows、Linux、macOS 的非阻塞独占文件锁；
6. 实现 Unix SIGINT/SIGTERM Run Context 和 Windows `.stop` 文件控制 goroutine；
7. 实现 stop 请求送达、PID 锁释放等待、幂等未运行和外部超时；
8. 补齐单元测试、跨进程辅助程序、集成测试和基础 Benchmark；
9. 执行 Windows 与 Linux 原生测试、竞态检测、静态检查及三平台构建；
10. 回写设计、计划、索引和复核清单的验收结果，完成 M4 提交。

## 3. 实现边界

- `command` 只依赖 M0 的 `buildinfo`、`errs`、标准库和固定版本 `x/sys`；
- 不依赖 M1 日志、M2 BufferPool 或 M3 配置加载；
- 不使用 Cobra、urfave/cli、fsnotify、本地 TCP、Named Pipe 或其他控制协议；
- PID 文件锁是运行状态的唯一事实来源，PID 数值只用于 Unix 发送 `SIGTERM` 和人工诊断；
- Windows `.stop` 文件只表达停止意图，不携带参数或业务数据；
- 不调用 `os.Exit`、`log.Fatal` 或强制 Kill；
- 不创建包级 Runner、注册表或可变全局状态；
- 不实现 M7、M15 或后续里程碑能力。

## 4. 错误码实施说明

两个进程控制错误属于本机命令与通用进程生命周期错误，使用通用错误区间中尚未占用的
连续编号：

```text
CodeProcessAlreadyRunning = 6
CodeProcessControlFailed  = 7
```

错误名称和数量均保持 M4 已确认设计；数值进入稳定错误码测试，发布后不得改变或复用。

信息不写入仓库。

## 8. 验收记录

完成日期：2026-07-26。

### 8.1 实际实现

- 新增公开 `command` 包及实例级 `Runner`，实现 `start`、`stop`、`help`、`version`
  和自定义离线命令；
- 支持正式子命令、v2 首参数兼容别名、严格 AppName、顺序 NodeID、绝对配置目录和
  PID 目录快照；
- 新增 `CodeProcessAlreadyRunning=6` 与 `CodeProcessControlFailed=7`，错误数量与
  已确认 M4 范围一致；
- PID 文件只保留 PID 和带本地数字时区偏移的 RFC 3339 启动时间，正常退出后保留；
- Linux/macOS 使用 `flock`、SIGINT 和 SIGTERM，Windows 使用 `LockFileEx`、
  `os.Interrupt` 和 `100ms` `.stop` 文件监听；
- Windows 锁区从 PID JSON 首字节调整到 `4 GiB` 固定偏移，避免活动锁阻止 stop
  读取 PID；该锁区位于 EOF 之外，不扩容 PID 文件；
- Windows 停止请求已严格限定为普通文件；同名目录、设备或其他文件类型返回进程控制
  错误，不再被误判成另一个 stop 已经创建的幂等请求；
- Start Handler、自定义命令和 Runner 最外层 panic 均转换为带本地堆栈的
  `CodeInternal` error，库代码不终止进程；
- 新增跨进程测试辅助程序，验证真实锁竞争、停止送达、超时不强杀和异常退出释放；
- 没有引入 Application、Node、Service、配置加载、RPC、在线控制协议或后续里程碑能力。

### 8.2 Windows 验收

以下命令均通过：

```text
gofmt
go vet ./...
go test ./...
go test -count=10 ./command/...
go test -count=5 ./tests/integration/command/...
go test -race ./...
go test -cover ./command/...
go test -run '^$' -bench '.' -benchmem ./command/...
scripts\buildwin.bat
scripts\buildlinux.bat
GOOS=darwin GOARCH=amd64 go build ./...
GOOS=darwin GOARCH=arm64 go build ./...
```

覆盖率：

```text
command                         89.7%
command/internal/processlock   100.0%
```

逐函数覆盖率审计已经覆盖全部命令分发、帮助、版本、自定义命令、命名校验、主要目录
错误、活动 PID 损坏、停止超时、Context 取消、panic、Windows 控制文件和锁竞争路径。
剩余未覆盖代码主要是需要人为制造文件 `Sync`、`Close`、`Unlock` 内核故障的极端分支；
本里程碑不为这些低频故障向生产代码加入复杂注入接口。

### 8.4 Linux 原生验收

测试主机为 `x86_64` Linux，内核为 `7.0.0-28-generic`。远端账号没有安装 Go
工具链，因此本机以当前源码交叉编译 Linux 测试二进制和辅助程序，上传后直接执行：

```text
command.test -test.count=10
processlock.test -test.count=10
integration.test -test.count=10
```

三组测试全部通过。集成测试实际使用 Linux `flock` 和 SIGTERM，覆盖正常停止、重复
启动、停止超时、异常退出释放及未运行幂等语义。远端临时测试目录在完成后已经删除。

Linux `-race` 因远端缺少 Go/CGO 工具链未单独执行；同一份 Go 并发代码已经通过 Windows
全仓 `go test -race ./...`，Linux 平台专属代码没有自行创建共享可变状态。
