## 1. 用途

本文列出 M0～M15 在实施前必须重新阅读和 Review 的设计文档。

每个里程碑开工前必须：

1. 阅读本里程碑设计；
2. 阅读本节列出的主设计文档；
3. 复核依赖里程碑的公开接口和验收结果；
4. 补齐“待补设计”；
5. 重新确认仍为草案或参数待定的内容；
6. 将 Review 日期、结论和调整记录写回本文；
7. 全部通过后，才为该里程碑编写实施计划和代码。

详细设计已经确认，不代表进入某个里程碑时不需要再次 Review。实现范围、依赖接口或性能数据发生变化时，应及时调整设计后再执行。

## 9. M5：TCP 网络基础库

### 主设计

- [M5 TCP 网络基础库设计](./M5-TCP网络基础库设计.md)。

### 关联参考

- [内存复用与对象池设计](../details/2026-07-25-内存复用与对象池设计.md)中的 Buffer 所有权；
- [Application 与 Node 生命周期设计](../details/2026-07-22-应用与节点生命周期设计.md)中的网络隔离原则；
- [原最小闭环设计储备](./原最小闭环设计储备.md)中的最小 TCP Runtime，仅作拆分参考。

### 开工前必须确认

- Listener、Connection、ReadLoop、WriteLoop 的职责；
- 长度帧、大小端、最大包和非法帧处理；
- 有界发送队列和待发送字节上限；
- Buffer 所有权和短写；
- Close 幂等、半关闭和 goroutine 回收；
- 基础库不包含 RequestID、ServiceName 和 RPC 错误；
- M5 与 M6 不共享虚假的大基础接口，M13/M14 由 RPC 使用方定义最小发送适配接口；
- `internal/tcpnet` 可见性、默认参数、Transport 错误码和 Benchmark 对照方案。

2026-07-26 已确认：

- M5 同时作为 TCP RPC 与后续 TcpModule 的共同内部 TCP 基础库；
- M5 支持一、二、四字节长度字段以及大端、小端，RPC Adapter 固定四字节大端；
- payload 允许为空但 nil Buffer 非法，默认最大消息为 `4M`；
- M5 通用发送队列默认 `4096` 帧和 `8M`，M13 RPC 覆盖为 `16384` 帧和 `8M`，上层可以
  显式调整两个限制；
- 队列满由 M5 非阻塞返回过载；RPC Request/Notify、RPC Response 和 TcpModule 慢客户端
  分别由所属上层决定后续动作；
- 接收直接读入最终池化 Buffer，发送不为帧头复制完整 payload；跨平台 Benchmark 后已
  采用连接级复用描述符的 scatter/gather 实现；
- M5 支持默认关闭的 ReadTimeout 和默认 `15s` 的 WriteTimeout；心跳接入后由 M13 设置
  非零读空闲超时；
- M5 使用立即关闭，不增加只能保证本地字节写出的 Transport Drain；
- M5 只提供单次 Dial 和关闭通知；RPC 目标仍有效时的有界退避重连属于 M13 Node 连接
  管理器，断线不自动重发非幂等 RPC；
- 接收 Buffer 可以由 RPC Adapter 同步释放，也可以继续转移给 TcpModule Service 事件；
- TcpModule 的 ClientID、Codec/Processor、事件和业务 API 不进入 M5，后续独立设计。

M5 设计 Review 已于 2026-07-26 通过。开发者随后明确指示“实现”，
[M5 TCP 网络基础库实施计划](../../plans/M5-TCP网络基础库实施计划.md)已执行完成；
Windows、Linux 真实网络测试、全仓竞态、Fuzz、Benchmark 和跨平台构建均通过。

- 完整清零、防 ABA，以及百万活跃条目下 `sync.Pool` 不能减少活跃集合内存的边界；

- M8 不依赖 Service Scheduler，不公开 `ITimer`、Ticker 或 Cron；
- M8 不开放顶层 `timer` 配置。

- [异常隔离与恢复设计](../details/2026-07-25-异常隔离与恢复设计.md)用于预留正确恢复边界。

### 开工 Review 结论

- `Service.DispatchAsync(func(context.Context))` 和
  `Service.Await(ctx, func(waitCtx context.Context) error)` 的最终外观；
  `DispatchAsync` 明确表示从任意 goroutine 异步切回 Service 串行执行上下文，不再使用
  含义过宽的 `Post`；
- Await 通过闭包局部变量接收任意业务结果，不公开泛型 `service.Await[T]`、`AwaitFunc`
  或不接收 Task Context 的重载；
- RPC、Timer、`DispatchAsync`、异步事件和 Module 业务入口统一由框架提供 Origin
  Task Context；`waitCtx` 必须传给真正等待的外部操作；Task Context 不得交给其他
  goroutine调用需要当前执行权的 Service API；
- `StartScheduler/StopScheduler` 两个跨包框架装配函数，Node 内部 TimerEngine 显式传入
  `StartScheduler`；
- Node 默认 `max_tasks=20000`、`max_await_tasks=10000` 和 `15s`；
- `max_await_tasks` 专门限制已经进入 Await、释放执行权但尚未恢复返回的任务数量，不表示
  Ready 队列中等待执行的任务数；配置结构体、YAML 示例和公开统计必须使用完整注释；
- Ready 使用 `internal/container/ringqueue` 的通用可增长环形队列，初始容量为
  `min(64, max_tasks)`，按需增长，硬上限不得超过 `65536`；不使用按最大容量预分配且不能
  删除 Scheduler 状态锁的固定容量 Channel；
- M9 不实现软过载状态机或专用限频器，只保留硬上限、最高水位和拒绝计数；
- 满载只拒绝新根任务，Await 恢复和 Stop 控制路径不得被容量二次拒绝；
- 只限制 Accepted 与 Waiting，恢复项永不二次拒绝；
- Service 只保留一个业务 Ready FIFO；M9 当前只实现 `DispatchAsync` 根任务和 Await
  恢复项，RPC、Timer、事件和 Module 的具体转换语义留到对应里程碑；
- 首版 Ready FIFO 不增加任务优先级；恢复项保证入队但仍排到队尾，Stop 使用独立控制
  状态和唤醒路径；
- Await Deadline 直接登记到 M8 TimerEngine，不创建第二个 Runtime Timer；每个 Scheduler
  使用一个只取消 Context、不执行业务代码的 Deadline 控制协程及时消费到期 ID；
- Scheduler 在 `OnStart` 后启动、`OnStop` 前完成本地排空；
- 生命周期 Await、完整 finalizer 和 RPC/Async pending 排空留到 M15；
- Runner 交接原型、Benchmark、逃逸和 goroutine 泄漏验证；
- Task 先建立不池化基线，但 M9 验收前必须通过 Benchmark、逃逸分析、堆 Profile 和受控
  池化对比形成最终决定；必要且风险可控时在 M9 内完成池化；
- M9 只实现维持调度不变量所需的最小 Task panic 恢复；
- M9 不接入远程 RPC、Future、业务 Timer、Module、事件或 Discovery。
