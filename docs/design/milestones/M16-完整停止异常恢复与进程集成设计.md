# Origin 第三版 M16 完整停止、异常恢复与进程集成设计

> 文档类型：里程碑设计
> 创建日期：2026-07-29
> 最后更新：2026-07-29
> 当前状态：开工 Review 已通过，允许编写实施计划

## 1. 里程碑目标

M16 完成 Origin v3 第一阶段运行时的最终生命周期闭环：

1. Stop 后立即停止新的业务准入；
2. 自然排空 Stop 前已经接受的任务、Waiting、Async 回调和已到期 Timer；
3. 在普通业务执行已经结束后，独占执行一次 `OnStop(ctx)`；
4. `OnStop` 可以使用顺序代码 `Await` RPC、Redis 或数据库存档；
5. 在 `OnStop` 返回后，严格逆序释放 RPC、Timer、日志和其他框架资源；
6. RPC、Timer、普通 Task、Async 回调等单个任务调用边界的 panic 打印完整堆栈，只结束
   当前问题任务并归还 Service 执行权，Service 继续运行；
7. Unix SIGINT/SIGTERM、Windows 控制台 `Ctrl+C`、Windows `.stop` 文件、Transport
   持续恢复和进程内 `Application.Stop` 各自遵守清晰的所有权边界；只有收到明确 Stop
   意图时才进入 Service 停止流程；
8. 日志最后排空，Crash 输出和进程运行权最后释放；
9. 停止完成后不残留 Runner、Deadline watcher、连接、pending 或框架 Buffer。

M16 不扩展业务功能，只把 M7～M15 已经实现的运行时部件组合成可生产使用的完整启停闭环。

## 2. 为什么 Origin 和 etcd 服务发现放在 M16 之后

建议顺序固定为：

```text
M16  完整停止、异常恢复与进程集成
M17  Origin 内置服务发现 Provider
M18  etcd 服务发现 Provider
```

原因如下：

1. Origin Provider 需要在停止时撤销注册、停止心跳、关闭控制连接并处理 TTL 快照；
2. etcd Provider 需要停止 Watch、更新或删除注册 Key、撤销 Lease 并关闭 Client；
3. 两种 Provider 都必须知道 Node 何时停止入站、何时仍允许 `OnStop` 出站 RPC、何时可以
   关闭 TimerEngine；
4. `DiscoveryService` 本身是普通 Service，也依赖 M16 的排空和独占 `OnStop`；
5. Provider 任务边界的 panic 和持续恢复异常需要进入 M16 建立的统一诊断入口，但不能擅自
   触发 Service 停止；
6. 如果先实现 Provider，M16 冻结停止阶段后还要重新调整租约、Watch 和控制连接释放顺序。

M16 只冻结 Provider 将来接入所需的停止阶段和所有权边界，不提前定义或实现 Origin/etcd
控制协议。两个 Provider 属于相对独立系统，继续使用独立设计文件和里程碑。

## 3. 已有基础与本轮缺口

### 3.1 已经完成的能力

M16 直接复用：

- M4 的 PID 文件锁、Unix 信号和 Windows 停止请求文件；
- M7 的 Application 多 Node 顺序启动、严格反序停止和独立 Stop Context；
- M8 的 Node 时间轮和 DeadlineQueue；
- M9 的 Service 单执行槽、Ready/Running/Waiting、协作式 Await 和任务池；
- M10 的业务 Timer 停止准入、已到期任务排空和未到期 Timer 取消；
- M13/M15 的 TCP/NATS 入站停止与最终关闭两阶段；
- M14 的发现撤销、监听器移除和发现等待取消；
- M15 的 Transport Closed 上报、发现撤销和诊断基础；
- M1 的日志排空和 Crash 输出；
- M2 的 Buffer 未归还统计。

### 3.2 当前仍缺少的接缝

当前代码在普通任务排空后立即完全关闭 Scheduler，再调用 `OnStop`。因此：

- `OnStop` 中的 `Service.Await` 无法取得有效执行上下文；
- Scheduler 的 DeadlineQueue 已关闭，无法承载 finalizer 默认超时；
- `OnStop` 无法使用生成的 `AwaitXxx` 完成存档；
- Draining 期间从已接受任务发起的新 Async 回调会被普通新任务准入拒绝；
- Application 停止 Deadline 在 Node 和日志阶段可能被重复创建，而不是共享一个总体时限；
- Crash 输出尚未由最终 Application 生命周期安装；
- BufferPool 最终未归还统计尚未在完整停止后检查；
- 单个任务调用边界的 panic 堆栈和完成规则尚未完全统一；
- M15 当前在 TCP Listener 异常退出或 NATS Closed 时会取消 Application，必须按最新结论改为
  “详细记录错误并撤销不可达路由，但不停止 Service”；实现时需要拆分当前
  `application.handleRuntimeFailure` 的“记录诊断”和“取消 Application”两项职责，Transport
  恢复回调只能调用前者；
- M10 当前会按一秒窗口聚合周期 Timer 的重复 panic 堆栈；M16 按最新结论改为每次 panic
  都独立输出一次完整堆栈，不遗漏具体发生次数；
- M6 当前拒绝 `Reconnect.MaxAttempts=-1`，RPC Adapter 使用通用默认 60 次；M16 必须只
  放行 `-1` 这一无限哨兵并由 RPC NATS 固定设置，其他负数仍报配置错误；
- 当前 TCP Listener 临时 Accept 错误可以原地恢复，但 Listener 永久退出后不会重新
  Listen；M16 增加单所有者、同地址、由 Application 生命周期约束的持续恢复循环；
- 当前没有运行期 Transport generation 和恢复后重新发布闭环；M16 增加内部代次、撤销和
  自动重发完整快照，但不改变 M14 公共发现结构；
- 当前没有 `CodeServiceFailed`、`Service.Failure()` 和 `Node.ServiceStatus()`；M16 同批
  增加并覆盖并发只读与线协议错误测试；
- 当前 Application 不会保留运行期 Failed Service 根因供最终退出结果使用；M16 增加一个
  只写冷路径的首次根因记录，运行期间不触发 Stop，正式 Stop 完成后再参与最终错误聚合。

M16 只修复这些接缝，不重写已经通过验收的调度、Timer、TCP 或 NATS 实现。

## 4. 公开状态与内部阶段

公开状态继续保持简单：

```text
Application: Running -> Stopping -> Stopped / Failed
Node:        Ready   -> Stopping -> Stopped / Failed
Service:     Running -> Stopping -> Stopped / Failed
```

Service 的 `Stopping` 内部增加不可公开枚举的两个阶段：

```text
Draining -> Finalizing
```

- `Draining`：拒绝新根任务，排空已经接受的普通任务和延续；
- `Finalizing`：普通任务已经排空，只允许最后一个 Service Runner 执行 `OnStop` 及其 Await；
- `Stopped`：`OnStop`、Scheduler 最终回收和 Service 引用清理均已完成。

内部阶段只用于断言、诊断和测试，不增加业务可依赖的公开状态分支。

Transport 的 Recovering/Failed 不修改 Node 和 Application 的生命周期状态：

- Node 已完成启动后继续保持 `Ready`；
- Application 继续保持 `Running`；
- Transport 入站健康和重连状态由 `Node.TransportStatus()` 独立表达；
- Node 对外综合健康状态由 `Node.HealthStatus()` 表达，服务发现发布状态不塞进 Transport；
- 远端无法通过发现选择当前 Node，但本地 Service、Timer、事件和其他健康 Transport
  继续运行；
- 收到正式 Stop 后才进入既有 `Stopping -> Stopped/Failed` 生命周期。

生命周期状态、存活状态和外部就绪状态相互独立：

- 生命周期 `Ready` 只表示 Node 已经完成启动且尚未进入正式 Stop；
- 存活表示进程、Node 控制循环和故障恢复循环仍能运行；
- 外部就绪表示当前 Node 仍具备被外部流量选择的完整条件；
- 全部公开 Service 都进入 Failed 时，Node/Application 不自动 Stop，存活保持成功，但
  外部就绪失败；
- TCP Listener 或 NATS 整体 RPC 能力进入 Recovering 时，存活保持成功、外部就绪失败；
- TCP 只有某个远端目标连接断开时只影响该目标路由，不改变当前 Node 的整体就绪；
- M16 只提供一份无锁只读的统一健康快照，不内置 HTTP Server；Kubernetes、systemd 或
  项目自定义 Probe 适配器在后续独立模块中读取该快照。

公共健康外观固定为：

```go
type HealthStatus struct {
    Liveness  bool
    Readiness bool
    Degraded  bool
    ErrorCode errs.Code
}

func (n *Node) HealthStatus() HealthStatus
```

该结构只表达探针所需的最小稳定结果：

- 不包含动态字符串、原始 error、时间、Service 列表或 Transport 列表；
- 内部在生命周期、Service、Transport 或 Discovery 状态变化时重新计算并原子发布不可变
  快照；
- 查询只复制小结构，不获取 Scheduler、Transport 或 Discovery 锁，也不产生堆分配；
- `ErrorCode` 只表示当前最主要原因，健康恢复后清零；详细现场继续通过
  `ServiceStatus()`、`TransportStatus()`、指标和日志查询；
- M16 不增加内置 HTTP 监听端口、路由、认证和 TLS 配置。

健康计算规则固定为：

| 场景 | Liveness | Readiness | Degraded | ErrorCode |
|---|---:|---:|---:|---|
| Node 正常 Ready | true | true | false | `CodeOK` |
| 部分公开 Service Failed，仍有 Running/Retired 公开 Service | true | true | true | `CodeServiceFailed` |
| 原本存在公开 Service，现已全部 Failed | true | false | true | `CodeServiceFailed` |
| TCP Listener 或 NATS 整体能力 Recovering/Failed | true | false | true | `CodeTransportUnavailable` |
| 必需 Discovery Provider 不可用或尚未完成重新发布 | true | false | true | `CodeDiscoveryUnavailable` |
| Node Starting | true | false | false | `CodeServiceNotReady` |
| Node Stopping | true | false | false | `CodeServiceStopping` |
| Node Stopped | false | false | false | `CodeServiceStopped` |
| Node 启动失败且控制循环已经结束 | false | false | true | 原始启动错误的稳定 Code，无法识别时为 `CodeInternal` |

补充规则：

- 没有公开 Service 的纯内部 Node 不属于“全部公开 Service Failed”；完成启动且必需基础设施
  正常时照常 Ready；
- Running 和 Retired 都属于健康公开 Service；Retired 是业务可观察状态，不自动拒绝 RPC，
  也不设置 Degraded；
- 部分公开 Service Failed 时只撤销失败实例，健康实例继续工作，避免一个局部故障让整个
  Node 的健康服务被摘除；
- 同时存在多个问题时，`ErrorCode` 按“Stopping/Stopped、全部公开 Service Failed、
  Transport、Discovery、部分 Service Failed”的固定顺序选择，保证结果稳定；
- 单次 RPC 超时、取消、单目标 TCP 断线、单次 Redis/数据库失败、队列过载和已经 recover
  的单任务 panic 不改变健康快照，只返回错误并累计指标；
- 项目需要根据持续过载扩缩容时读取指标，不把瞬时流量峰值转换成就绪抖动。

`StateFailed` 继续作为已有公开终态使用，同时扩展为“启动失败或运行期 Scheduler 无法安全
恢复”。运行期进入 Failed 不执行正式 Stop：

- 只撤销该 Service 的发现，不撤销同 Node 的健康 Service；
- 新任务和入站 RPC 返回 `CodeServiceFailed`；
- Application、Node 和其他 Service 继续运行；
- `Service.Failure()` 返回本进程内保存的最后一个根因，正常状态返回 nil；
- Failure 只供本地诊断，不通过 RPC 发送原始 error、堆栈或内部路径；
- 收到正式 Stop 后才进入最大努力清理。

## 5. 唯一停止所有者

### 5.1 Application 运行协程是唯一所有者

Application 的 `run` 调用链是唯一完整停止所有者：

- 外部信号只取消运行 Context；
- `Application.Stop(ctx)` 只发出停止意图并等待最终结果；
- Transport 或 Provider 回调只报告恢复状态、记录详细错误并撤销不可达发现记录，不取消
  Application 运行 Context；
- 任何回调 goroutine 都不能直接调用 `Node.Stop` 或 `Application.Stop`；
- 真正的 Node 反序停止只在 Application 运行调用链执行一次。

这样可以避免网络回调等待自己退出，也不需要额外的 Stop 管理 goroutine。

### 5.2 重复停止

- 第一个停止意图取得触发权；
- 后续 Unix SIGINT/SIGTERM、Windows `Ctrl+C`、Windows `.stop` 或进程内 Stop 只合并；
- 多个 `Application.Stop(ctx)` 调用者等待同一个 `done`；
- 等待方自己的 Context 只限制该调用者等待，不修改 Application 内部停止 Deadline；
- `Stopped` 和完成回滚后的 `Failed` 重复 Stop 返回首次最终结果或幂等成功；
- `OnStop`、Transport Close、日志 Close 和 Crash Close 都必须严格一次。

### 5.3 Windows Ctrl+C

Windows 普通控制台的 `Ctrl+C` 必须与 `game-server stop` 使用同一条优雅停止路径：

1. `signal.NotifyContext(..., os.Interrupt)` 把 `Ctrl+C` 转换为 Run Context 取消；
2. 信号回调不直接停止 Node，不调用 `os.Exit`；
3. Application 运行调用链被唤醒后创建独立总体 `stopCtx`；
4. 多 Node、Service、Waiting、Timer 和 RPC 按本设计正常排空；
5. 全部 `OnStop`、资源关闭和日志 Flush 完成后才释放 PID 锁并退出；
6. `Ctrl+C` 与同时到达的 `.stop` 文件或进程内 Stop 合并，不能执行两套清理。

M16 必须在 Windows 子进程或等价平台集成环境中验证真实控制台中断能够到达该路径，不能
只用直接取消测试 Context 代替全部平台验证。

## 6. Application 总体停止 Context

### 6.1 默认值

保持已经确认的规则：

- `application.Options.StopTimeout == 0`：框架内部不设置停止 Deadline；
- 大于零：限制一次完整 Application 停止；
- 负数：构造阶段直接报错；
- `game-server stop --timeout` 默认 `30s`，只限制外部命令等待 PID 锁释放；
- 外部 30 秒等待不传入目标进程，也不改变 Application 的内部停止策略。

因此默认情况下 Origin 会一直等待业务安全退出，不主动丢弃玩家存档或强杀进程。

### 6.2 只创建一次总体 Deadline

收到停止意图后只创建一个独立于已取消运行 Context 的 `stopCtx`：

```text
stopCtx
  -> Node N Stop
  -> ...
  -> Node 1 Stop
  -> BufferPool 最终检查
  -> Crash 输出注销
  -> 日志 Flush/Close
```

不得为每个 Node、每个 Service 或日志关闭重新获得一份完整 `StopTimeout`。所有阶段共享
同一个绝对 Deadline，后执行阶段只取得真实剩余时间。

### 6.3 Deadline 到期

总体 Deadline 到期后：

1. 取消仍处于 Waiting 的普通任务和 finalizer Await；
2. 取消 TCP/NATS pending；
3. `Await` 以稳定超时错误恢复一次；
4. `OnStop` 应观察 Context 并尽快返回；
5. 继续执行可以安全完成的关闭和引用清理；
6. 最终返回 `CodeGracefulShutdownTimeout` 并使用非零进程退出码。

Go 不能安全强杀忽略 Context 的用户函数或系统调用。若业务代码永久阻塞且不遵守 Context，
Origin 不伪装成已经优雅退出，也不在库内直接强杀进程；systemd、Kubernetes 或运维系统可在
它们自己的更外层期限到达后执行强制终止。

## 7. Node 完整停止顺序

Application 按真实成功启动顺序的严格反序逐个停止 Node。单个 Node 的顺序固定为：

```text
1. Node -> Stopping
2. 从服务发现撤销当前 Node 的公开记录
3. 停止新的远端入站 RPC
4. 按 Service 实际启动顺序的严格反序逐个停止
5. 最终关闭 RPC Runtime、连接、Subscription、pending 和入站 Deadline
6. 关闭 Node TimerEngine
7. 关闭发现订阅和将来 Provider 的本地资源
8. Node -> Stopped
```

关键规则：

- 第 2 步在未来由 Origin/etcd Provider 实现相同语义；
- 第 3 步只停止新入站，不提前关闭出站能力和既有连接；
- 第 4 步期间后停止的依赖 Service/Node 仍可被 `OnStop` 调用；
- RPC Runtime 和 TimerEngine 必须晚于全部 Service `OnStop`；
- 任一 Service 停止失败不能跳过后续 Service；
- 任一 Node 停止失败不能跳过后续 Node；
- 全部错误使用 `errors.Join` 聚合，首个根因仍可通过稳定错误码识别。

### 7.1 Node 内 Service 配置顺序

每个 Node 只使用 `nodes[].services` 的声明顺序：

- `OnInit` 按配置顺序执行；
- 单个 `OnInit` 错误不跳过后续纯初始化，全部执行后按配置顺序聚合；
- 全部初始化成功后，先启动 Node 运行期基础设施，再按配置顺序执行 `OnStart`；
- 实际进入过 `OnStart` 的 Service，包括返回错误的 Service，依次记录；
- 正常停止与启动失败回滚都按实际记录的严格倒序执行 `OnStop`；
- 不增加第二份启停顺序配置；
- 一个 Service 停止失败只加入聚合错误，不能阻止倒序列表中的后续 Service 停止。

因此配置为 `A, B, C` 时，启动固定为 `A -> B -> C`，停止固定为
`C -> B -> A`。

### 7.2 两阶段启动与统一就绪屏障

Node 启动固定分为以下阶段：

```text
1. 构造并绑定全部 Service
2. 按配置顺序执行全部 OnInit，聚合错误
3. 全部 OnInit 成功后启动 TimerEngine、RPC Transport 和发现输入
4. 按配置顺序逐个执行 OnStart(ctx) error
5. 全部 OnStart 成功后激活全部 Scheduler、Timer 和入站准入
6. 原子发布当前 Node 的全部公开 Service，Node -> Ready
```

`OnInit` 只允许配置校验、静态装配和无需清理的内存初始化。Await、Async、Notify、
Broadcast、业务 Timer、普通任务、外部访问和业务 goroutine 均返回
`CodeServiceNotReady`。多个 `OnInit` error 或 panic 在全部 Service 检查结束后使用
`errors.Join` 聚合；当前 Node 不执行任何 `OnStart` 或业务 `OnStop`，只清理构造期框架
资源。

`OnStart` 保留 `error` 返回值并允许使用私有生命周期 Context 执行 Await RPC、Redis 和
数据库初始化。Await 直接在当前生命周期 goroutine 等待，复用 M8 DeadlineQueue，不启动
普通 Runner，也不切换 Service 执行权。Async、Notify、Broadcast、普通任务和本地业务事件
继续拒绝；业务 Timer 可以登记，但只能在整个 Node 越过就绪屏障后触发。

任一 `OnStart` 返回 error、Context 取消或超时、或者发生 panic 时，Node 停止启动后续
Service。失败 Service 与此前真正进入过 `OnStart` 的 Service 均按严格反序执行一次
`OnStop(stopCtx)`；随后清理框架资源，并由 Application 反序停止此前已经 Ready 的 Node。
框架库不得在失败点直接调用 `os.Exit`。

启动过程中收到 Stop 时：

- 当前 `OnInit` 返回后不再调用后续 `OnInit`；OnInit 没有 Context，框架不尝试强制中断；
- 立即取消 Transport/Provider 重试或当前 `OnStart` 的 startCtx；
- 当前 `OnStart` 返回后不再启动后续 Service；
- 已进入过 `OnStart` 的 Service 仍严格反序执行 `OnStop`；
- 单纯由 Stop/信号取消且清理成功时退出码为 `0`，此前已经发生真实启动错误时仍为 `1`。

`OnStart` 不支持同 Node RPC 特例。当前 Node 尚未越过统一屏障时，调用其中任意 Service
均返回 `CodeServiceNotReady`，不能内联执行并绕过 Runner。

业务可以在 `OnStart` 中创建 Service/Module 自己持有的 goroutine 或固定工作池，例如 AOI
计算 Worker。Origin 不检测或拦截 `go` 语句；Worker 必须只处理与 Service 可变状态隔离的
数据，结果通过线程安全的 `DispatchAsync` 返回唯一执行槽，并由 `OnStop` 负责取消和等待。
不可取消、不可等待或直接并发访问 Service 状态的 fire-and-forget goroutine 不符合资源
所有权和单执行槽规则。

M16 不增加 WorkerManager、业务 Worker 注册表或另一套工作队列。业务使用自己的 Context、
CancelFunc 和 WaitGroup 管理数量、取消与等待。为了降低业务忘记 recover 导致整个 Go
进程退出的风险，`service.Service` 增加一个只负责 goroutine 顶层 panic 保底的便捷方法：

```go
func (s *Service) GoSafe(fn func()) error
func (s *Service) RunSafe(fn func()) error
```

两项能力同时组合进 `IService`，因此 Module 通过 `m.Service()` 也可以使用，不要求 Module
保存具体 Service 实现指针。

`GoSafe` 规则固定为：

- 在 `OnStart` 和 Running 阶段可以调用；OnInit 返回 `CodeServiceNotReady`，停止阶段返回
  `CodeServiceStopping`；
- 内部启动一个 goroutine，并在该 goroutine 最外层 recover；
- panic 时打印一次包含 NodeID、ServiceName 和完整堆栈的 ErrorStack，避免整个进程退出；
- panic 会结束当前业务 goroutine；Go 无法恢复已经展开的调用栈，因此不自动重跑整个
  `fn`，避免重复执行有副作用的业务；
- Service Scheduler、RPC、Timer、事件和 Dispatch 回调仍在每个任务调用边界自动 recover，
  所以一个任务 panic 后可以继续执行 FIFO 中的下一任务；
- `GoSafe` 不跟踪业务 Worker、不自动 cancel/wait，也不把 Worker 算入 Scheduler 排空；
  业务仍须在 `OnStop` 中取消并等待；
- 直接使用原生 `go` 仍是 Go 语言能力，但该 goroutine 的 panic 无法由其他 goroutine 中的
  Origin 边界 recover，不具备引擎保底。

`RunSafe` 在调用方当前 goroutine 同步执行一次 `fn`：

- `fn == nil` 返回 `CodeInvalidArgument`；
- 正常返回时返回 nil；
- panic 时先执行 `fn` 调用栈内的 defer，再由 `RunSafe` 打印一次 ErrorStack，并返回保留
  `CodeInternal` 的轻量 error；
- panic 不会越过 `RunSafe`，因此外层 Worker 循环可以继续取得下一 Job；
- `RunSafe` 只隔离 panic，不授予 Service 执行槽；从业务 Worker 调用时仍不能并发访问
  Service 可变状态；
- `runtime.Goexit`、进程 OOM、栈溢出和操作系统强制终止不保证可恢复。

典型 AOI Worker：

```go
func (m *AOIModule) runWorker() {
    defer m.workerWG.Done()

    for job := range m.jobs {
        if err := m.Service().RunSafe(func() {
            result := m.calculate(job)
            m.publishResult(result)
        }); err != nil {
            m.releaseJob(job)
        }
    }
}
```

`GoSafe` 可以复用 `RunSafe` 的内部 panic 边界，但顶层 panic 后不自动重启整个 Worker
函数；需要连续处理 Job 的 Worker 应把 `RunSafe` 放在 Job 边界。这样既能继续处理下一项，
又不会盲目重复已经发生部分副作用的 Job 或重新执行整个 Worker 初始化。

`GoSafe` 或 `RunSafe` 捕获的业务 Worker panic 不改变 Service 的 `Running`、`Retired`
等公开生命周期状态，也不能触发 `Failed`。框架不知道某个 AOI、寻路或排行榜 Worker
是否属于业务关键组件；是否重建 Worker、退休 Service 或报警由业务根据错误返回和日志
自行决定。

## 8. Service 完整停止顺序

单个 Service 的停止固定为：

```text
1. 移除该 Service 的发现监听器并取消发现等待
2. 原子关闭新根任务和新业务 Timer 准入
3. Service -> Stopping / Draining
4. 排空已经接受的任务及其框架延续
5. 最后一个 Service Runner 保持执行权，Service -> Stopping / Finalizing
6. 由该 Runner 独占执行 OnStop(finalizerCtx)
7. OnStop 返回后结束最后一个 Runner
8. 最终关闭 Scheduler DeadlineQueue，取消残留 Timer 并释放池和队列存储
9. Service -> Stopped
```

M16 将当前“一次完成所有操作”的 Scheduler Stop 拆成内部两步：

- `DrainScheduler`：完成第 2～4 步，选定并保留最后一个 finalizer Runner，同时保留
  finalizer 所需 Deadline 基础；
- `FinishStopScheduler`：在 `OnStop` 返回后完成第 8 步。

这两个函数属于 Node 与 Service 的内部生命周期接缝，不扩展到业务公开接口。

## 9. Draining 的排空集合

### 9.1 已接受任务

以下工作属于排空集合：

- 正在运行的普通 Service Task；
- 已经进入 Ready FIFO 的任务；
- 已经处于 Waiting 的任务；
- 已经进入 Ready 的 Timer 回调；
- `AsyncXxx` 在提交远端请求前预留的完成任务；
- 上述任务的 Await 恢复、Async 完成、超时和取消。

尚未到期的 Timer、Stop 后到达的入站 RPC、普通事件和业务 Post 不属于排空集合。

### 9.2 不增加 TaskScope 或第二份 pending 计数

现有 `AsyncXxx` 已经先在调用方 Service 中预留一个完成 Task，再提交 RPC。该 Task 在响应
返回前通过正常 Await 进入 Waiting，因此 Scheduler 的 `accepted/ready/running/awaiting`
已经完整表示 Async 生命周期。

M16 不再新增：

- `TaskScope`；
- 父子任务树；
- Service 级裸 `pendingAsync` 计数器；
- RPC pending 的第二份镜像表。

排空只以 Scheduler 已有状态为事实来源，TCP/NATS pending 继续负责响应关联和取消。

### 9.3 Draining 中的框架延续

Service 始终只有一个业务执行槽。Stop 原子关闭准入后：

- 只有 Stop 前已经接受的任务及其框架延续可以依次取得该执行槽；
- 不存在另一个普通业务协程与 Draining/Finalizing 逻辑并发进入 Service；
- 业务自行创建的裸 goroutine 不拥有有效 Task Context，不能调用 Service RPC、创建 Timer
  或投递普通任务；这些调用统一返回 `CodeServiceStopping`；
- Draining 中创建新 Timer 一律拒绝，因为新 Timer 会形成无法自然排空的未来根任务；
- 当前已接受任务可以完成已开始的顺序业务流程，包括发起 RPC、Await、Async、Notify 或
  Broadcast；这些操作仍受 Stop Context 和原有完成语义约束。

Stop 前已经接受的任务可以在 Draining 中继续：

- `Await` RPC、Redis 或数据库；
- 发起带完成回调的 `AsyncXxx`；
- 在 Async 回调中继续 Await 或 Async。

为此增加一个仅供框架内部使用的“延续投递”入口：

1. 必须携带当前 Service 的有效 Task Context；
2. 必须证明来源 Task 已经属于排空集合；
3. 只允许 RPC Async 等框架完成任务使用；
4. 普通 `DispatchAsync`、事件、业务 Post 和 Timer 创建继续拒绝；
5. 延续 Task 成功入队后立即计入现有 `accepted`；
6. Stop Deadline 取消来源 Context 后，不得继续派生新延续。

这不是公开的绕过停止接口，也不允许任意外部 goroutine 向 Draining Service 添加任务。

## 10. 独占 finalizer

### 10.1 执行协程

`OnStop` 固定由该 Service 的最后一个 Runner 执行：

- Stop 关闭准入后，Scheduler 继续按单执行槽规则排空 Ready、Running 和 Waiting；
- 最后一个任务完成且排空条件成立时，当前 Runner 不退出，而是原子切换到 Finalizing；
- 如果 Stop 到达时 Service 已经空闲，由一个原本等待工作的 Service Runner取得 finalizer
  执行权；没有可复用 Runner 的极端构造期回滚才允许创建一个专用 Service finalizer Runner；
- finalizer Runner 直接执行 `OnStop`，返回后通知 Node 生命周期调用链；
- Node 生命周期调用链只负责按反序逐个发起并等待 Service Stop，不直接执行业务
  `OnStop`；
- 一个 Service 的 finalizer 完成后，Node 才开始停止反序列表中的下一个 Service；
- 不会出现普通任务与 `OnStop` 并发访问 Service 状态。

这保留了 Service 代码始终由 Service 自己的协程执行的直观模型。实现只增加一个
finalizer 所有权状态，不建立 TaskScope、父子任务树或第二套调度器。

### 10.2 finalizer Context

框架传给 `OnStop` 的 Context 包含私有 finalizer 令牌：

- 令牌绑定唯一 Service 和本次停止代次；
- 业务不能构造、复制到其他 Service 或在 `OnStop` 返回后继续使用；
- `Service.Await` 识别令牌后进入 finalizer Await；
- 普通 Task Context 仍进入 M9 Runner 交接 Await；
- 没有合法 Task/finalizer 令牌的 Context 不能访问 Service Await。

业务必须把收到的 `ctx` 传给 `AwaitXxx`。在 `OnStop` 中改用
`context.Background()` 会失去 finalizer 身份，框架返回明确参数错误，而不是猜测调用来源。

### 10.3 finalizer Await

finalizer Await 固定执行：

1. 在当前 finalizer goroutine 调用等待函数；
2. 当前 goroutine 直接等待 Future、外部结果或 Context；
3. 等待期间不启动或切换普通 Service Runner；
4. RPC Runtime、Transport 和 TimerEngine 在其他框架 goroutine 中完成结果；
5. 同一个 finalizer goroutine 被唤醒并继续执行 `OnStop`；
6. 一次 Await 完整结束后才能开始下一次 Await。

finalizer Await 会占用最后一个 Service Runner；等待期间该 Runner 被 Go runtime 挂起，
不会创建替代业务 Runner，也不会再执行普通业务任务，因此不会造成 Service 状态并发访问。

### 10.4 finalizer 调用限制

`OnStop` 可以：

- 读取和整理 Service 最终状态；
- 使用 `AwaitXxx` 或通用 `Await`；
- 调用仍处于 Running/Retired 的其他 Service；
- 返回业务收尾错误。

`OnStop` 不能：

- 使用 `AsyncXxx`；
- 使用 `NotifyXxx` 或 `BroadcastXxx` 代替需要确认的收尾；
- 注册 Timer；
- 提交普通事件或业务 Post；
- 启动 fire-and-forget goroutine；
- 调用本 Service 自身的 RPC。

生成客户端和 Service API 在识别 finalizer Context 后，对 Async、Notify、Broadcast 和新的
根任务统一返回 `CodeServiceStopping`。调用本 Service RPC 因目标正在 Finalizing，也立即
返回 `CodeServiceStopping`，不能形成自调用死锁；本地清理应直接调用私有业务方法。

## 11. finalizer Deadline

一次 finalizer Await 的有效期限仍使用统一优先级：

```text
调用方显式 Deadline
  > Service.SetDefaultAwaitTimeout
  > Node scheduler.default_await_timeout
  > Origin 内置 15s
```

同时不能突破 Application 总体 `stopCtx`：

- `stopCtx` 更早时，以总体停止 Deadline 为准；
- 单次显式 Deadline 更早时，以单次 Deadline 为准；
- `stopCtx` 没有 Deadline 且调用方没有显式 Deadline 时，使用 Service 默认链；
- 框架默认超时继续使用 M8 DeadlineQueue，不为每次 Await 创建 Go Timer；
- 业务显式使用 `context.WithTimeout` 时，Go Timer 属于调用方明确选择，不重复登记 M8
  默认 Deadline；
- 每次 Await 最终只存在一个有效 Deadline 来源。

`OnStop` 本身不额外获得一份固定 15 秒总时限；15 秒是每次未显式配置的 Await 默认值。
Application 是否设置整体 StopTimeout 由项目决定。

## 12. 启动失败回滚

启动失败仍遵守：

- 所有业务 `OnInit` 均执行后再聚合错误；任一失败时当前 Node 的全部 Service 都不调用
  `OnStart` 或业务 `OnStop`；
- 已经真正进入 `OnStart` 的 Service 无论成功或失败都调用一次 `OnStop`；
- 当前失败 Node 先清理，已经 Ready 的 Node 再按实际启动顺序严格反序停止；
- 尚未启动的 Node 只关闭构造期资源，不调用业务生命周期；
- 回滚使用独立 stopCtx，不复用已经取消或超时的 startCtx；
- 回滚中的 `OnStop` 同样可以使用 finalizer Await；
- 回滚错误与原始启动错误聚合，但原始启动错误保持主要诊断位置。

`OnStop(ctx) error` 的错误只表示业务收尾没有完整成功，不能阻止后续 Service、Node 和框架
资源继续关闭，也不能把 Service 恢复为 Running。框架不自动重试 `OnStop`；业务需要的存档
重试必须在本次回调内完成。Node/Application 按实际停止顺序使用 `errors.Join` 聚合错误，
全部清理和日志 Flush 完成后由最外层返回非零退出码。

## 13. 任务 panic 与框架不变量

### 13.1 单个任务调用边界 panic

以下规则同时适用于业务代码和在该任务调用栈内执行的框架代码：

- RPC、Timer、普通 Task、Async 回调 panic 只结束当前任务；
- Service 执行槽、请求响应和 Buffer 必须在 defer 中归还；
- 入站请求返回稳定 `CodeRPCExecutionPanic` 或既有内部错误；
- Service 默认继续处理后续任务；
- `OnInit`、`OnStart` panic 等价于生命周期返回错误并触发回滚；
- `OnStop` panic 转为停止错误，随后继续停止其他 Service、Node 和框架资源；
- 每次 panic 必须通过 `ErrorStack` 恰好记录一次完整本地堆栈以及 NodeID、ServiceName、
  TaskKind、ContractID/MethodID 或 TimerID 等可用的低基数定位字段；
- 结束问题任务并归还执行权后，Service 继续处理下一项任务；
- 线协议不发送堆栈和原始 panic 值。

恢复逻辑放在现有 Scheduler、RPC、Timer 和生命周期的任务调用边界中，不新建一个所有路径
都经过的通用包装层，也不让正常热路径承担额外对象分配。

### 13.2 调度器不变量或控制主循环 panic

`ServiceScheduler` 是每个 Service 私有的任务调度器，负责 Ready FIFO、Waiting 恢复、
Runner 唤醒和停止排空。“执行槽”不是操作系统线程，也不是预先创建的协程池，只是
Scheduler 内部的一份独占所有权：

```text
running = 0：当前没有任务可以访问 Service 状态
running = 1：只有 runningTask 指向的任务可以访问 Service 状态
```

任务调用 `Await` 时归还执行槽；其他 Runner 可以顺序执行后续任务。原任务等待完成后排回
Ready FIFO，重新取得同一执行槽才能继续。因此任何时刻都不会有两个任务并发访问 Service
状态。

所谓“不变量错误”是代码观察到理论上不可能的组合，例如：

- `running == 1`，但 `runningTask == nil`；
- Ready 队列取出的 Task 已经是 Completed；
- 一个 Await Task 同时被记为 Running 和 Waiting；
- Accepted、Running、Waiting 计数与真实任务状态不一致。

队列满、RPC 超时、TCP 断线、NATS 重连、Context 取消和业务 error 都是正常可预期错误，
绝不能进入上述分支。正常运行不应因为这些情况退出进程。

这些分支在正确实现中不应发生，通常只可能来自 Origin Scheduler 内部缺陷、错误的所有权
转移、极端竞态未被正确处理，或者使用 unsafe/数据竞争破坏了框架内部内存。它不是业务
可主动设置的状态，也不能把资源过载和普通业务错误升级成 Failed。

M16 固定采用分级恢复，不把 Scheduler 异常直接升级为进程退出：

1. 能在修改共享状态前检查出的异常改为返回内部 error，不使用 panic；
2. 若问题只属于当前 Task，调用边界打印完整堆栈、完成当前 Task、配平计数并继续 Runner；
3. 若 Runner 意外结束，但锁、队列、计数和当前 Task 快照验证一致，则重新唤醒一个 Runner；
4. 只有无法证明调度状态仍一致时，才隔离受影响的单个 Service Scheduler：撤销该 Service
   的发现、拒绝新任务、完成可以安全完成的 pending，并记录完整现场；
5. Scheduler 隔离不取消 Application，不停止其他 Service，也不退出进程；
6. 进程收到正式 Stop 后再对隔离 Service 做最大努力清理；只有能够重新建立独占 finalizer
   权限时才调用其 `OnStop`，不能用可能并发的收尾扩大数据风险。

首版不自动重建一个已经无法证明状态一致的 Scheduler。要安全重建必须额外维护所有
Waiting Task、Context、Timer 和 pending 的第二份权威索引，明显增加热路径复杂度和出错
面，不符合当前精简原则。任务级故障和状态一致的 Runner 故障都应自动恢复；只有确实无法
安全恢复的单个 Service 被隔离。

### 13.3 Failed 状态查询

公共外观保持最小，不扩大 `IService` 的生命周期契约：

```go
type ServiceStatus struct {
    State   service.State
    Failure error
}

func (s *Service) Failure() error
func (n *Node) ServiceStatus(name string) (ServiceStatus, bool)
```

业务通过嵌入 `service.Service` 自动获得 `Failure()`，不需要自行实现；管理代码可直接通过
Node 查询任意本地 Service。两个入口都是冷路径只读快照，不进入 RPC、Timer 或 Scheduler
热路径；内部使用原子发布的不可变失败快照。首次无法恢复的根因作为主错误保存，后续清理
错误通过日志记录，不能覆盖最有价值的现场。Service 完成正式 Stop 后继续保留 Failure，
直到该一次性 Service 对象随 Node 被释放；正常停止且从未 Failed 的 Service 始终返回 nil。

### 13.4 Failed Service 的正式 Stop

Failed 只是运行期隔离，不等于已经执行正式 Stop。随后收到正式 Stop 时按以下规则最大努力
清理：

1. 内部不变量一旦失败，当前 Service 一律不再执行业务 `OnStop`。这样无需再实现一套
   “尝试证明 finalizer 独占”的恢复状态机，也避免业务回调读取已经无法证明一致的状态；
2. 首个故障边界已经输出完整 ErrorStack，并把 `CodeServiceFailed` 加入最终停止聚合错误；
3. 取消该 Service 的 Timer、Await、RPC pending 和发现监听器，释放框架明确拥有且能够
   证明所有权的队列、Deadline 和 Buffer；
4. 无法证明所有权的对象只记录泄漏诊断，不能为了“清零”执行可能重复释放的操作；
5. 当前 Service 清理完成或总体 Stop Context 到期后，继续倒序停止其他 Service 和 Node。

M16 把故障根因发布在不依赖 Scheduler 锁的原子快照中。故障边界只有限尝试取得短锁；
如果无法证明锁所有权，则正式 Stop 直接走保守清理，不等待、不强制解锁，也不执行依赖
该锁的池化回收，保证一个损坏 Service 不会卡死整个 Application。

### 13.5 Application 最终结果

运行期出现无法恢复的 Failed Service 时：

- Application 不立即停止，State 继续为 Running；
- Application 保存首次运行期根因作为主错误，同时按 Node 和 Service 的稳定顺序保存每个
  Failed Service 的安全摘要；
- 正式 Stop 仍完整执行全部 Node、Service、Transport、日志和 PID 清理；
- 清理结束后把首次运行期根因与 Stop 错误通过 `errors.Join` 聚合；
- 最终 Application State 为 Failed，命令退出码为 `1`；
- 即使 Failed Service 的框架资源最终全部清理成功，也不能把曾经发生的严重运行期故障
  改写成正常退出码 `0`；
- 原始 panic 堆栈仍只在本地日志中，最终 error 保留稳定 `CodeServiceFailed` 和安全文本。

多个 Failed Service 的最终错误使用 `errors.Join` 汇总，但每个 Service 只加入一条安全
摘要，包含 NodeID、ServiceName 和 `CodeServiceFailed`，不包含堆栈、玩家数据或任意高基数
请求字段。首次根因保持主诊断顺序，清理错误追加在运行期失败摘要之后。

如果一个 Node 原本至少包含一个公开 Service，而这些公开 Service 在运行期全部进入
Failed，则：

- Node 和 Application 仍保持运行，不自行调用 Stop，也不自动重启进程；
- 每个 Failed Service 都从发现目录撤销并拒绝新任务；
- 本地健康 Service、私有 Service、Timer、事件、Transport 恢复和诊断能力继续运行；
- Node 存活状态保持成功，但外部就绪状态失败；
- 正式 Stop 到来后才执行既定清理，并按上述规则返回运行期失败结果。

## 14. 基础设施持续恢复与异常终止

本文中的 Transport 指 Node 内部供 RPC Runtime 使用的“网络传输层”，负责连接或订阅、
收发字节、连接代次和断线恢复；当前实现可以是 TCP，也可以是 NATS。业务 Service 和生成的
RPC Client 不直接操作 Transport：RPC Runtime 负责契约、编解码、RequestID、pending 和
超时，Transport 只负责把已经编码的 RPC 帧送到目标 Node 并接收返回帧。服务发现负责说明
“目标在哪里”，也不属于 Transport。

Transport 状态表示当前 Node 的整体 RPC 入站能力，而不是任意一条远端连接：TCP 对应本地
Listener，某个目标 Node 的单独 TCP 连接断开只影响该目标路由；NATS 对应当前 Node 唯一
Connection 及 Request/Response Subscription 的整体能力。

运行期 TCP/NATS 网络故障没有“重试次数耗尽后的永久终态”。只要 Application 尚未收到
Stop，Transport owner 就持续恢复：

- 使用 Error 或聚合 Warning 记录详细错误，至少包含 NodeID、Transport、连接状态、恢复
  次数和安全的原始 error 链；
- 撤销受影响 Node 的可见发现记录，使其他 Node 不再把新 RPC 路由到当前不可达传输；
- 完成无法跨连接代次继续等待的 pending，使调用方收到稳定
  `CodeTransportUnavailable`；
- 不取消 Application 运行 Context，不调用 Service Stop，不改变 Service 的
  Running/Retired 状态；
- 本地事件、Timer、业务任务和仍可用的其他组件继续正常运行；
- 恢复成功后重新建立 Connection、订阅和内部 Transport generation，再原子发布完整发现
  记录；Node 进程级 `SessionID` 在本次进程生命周期内保持不变。

只有以下情况不进入网络恢复循环：

- Application 已经收到 Stop，主动关闭连接或 Listener；
- 启动阶段发现地址、证书、鉴权或配置等确定性错误，Node 尚未 Running，直接启动失败；
- Transport owner 自身出现无法证明状态一致的内部不变量错误，此时
  `TransportFailed` 表示框架缺陷隔离，不表示普通网络断开。

恢复矩阵固定为：

| 异常 | 恢复动作 | 是否撤销发现 |
|---|---|---|
| TCP 单连接断开、reset、EOF | 只关闭该连接；发现仍存在时按退避和抖动重连 | 否 |
| TCP 临时 Accept 错误 | Listener 原地退避后继续 Accept | 否 |
| TCP Listener 意外失效 | 保证旧 Listener 已退出后，按原地址持续重试 Listen，直到成功或 Stop | 恢复期间临时撤销 |
| 非法帧、校验失败、超大消息 | 只关闭并记录来源连接，不影响 Listener 和其他连接 | 否 |
| 发送或接收队列满 | 当前调用返回过载，不关闭连接 | 否 |
| NATS Disconnected/Reconnecting | 使用 nats.go 无限重连、退避和抖动；不缓冲、不重放新调用 | 恢复期间尽力撤销 |
| NATS 异步错误或慢消费者 | 记录详细错误并让受影响调用失败，连接可用时继续 | 视连接能力决定 |
| NATS 非 Stop 导致的 Closed | 完成旧代次 pending，由 Transport owner 周期性重建 Connection、Subscription 和内部 Transport generation | 是 |

RPC 场景固定在 Application 运行期持续重连，不新增公开重连次数配置：

- TCP 出站连接沿用 `200ms` 起步、`5s` 封顶和抖动，只要目标仍在发现目录就持续重试；
- TCP Listener 重建使用相同 `200ms`～`5s` 封顶退避和抖动；
- NATS 使用 `2s` 等待、普通 `500ms` Jitter、TLS `1s` Jitter，并把
  `MaxReconnects` 固定为 `-1`，其含义是由 Application 生命周期和 Stop Context 约束，而
  不是允许资源无界增长；
- NATS 同时启用 `IgnoreAuthErrorAbort`，避免运行期连续相同鉴权错误提前结束无限重连；
- Stop Context 可以立即终止全部重试；
- 重连期间新 RPC 快速返回 `CodeTransportUnavailable`，不进入重连缓冲、不自动重放；
- 断线时当前 pending 立即以 `CodeTransportUnavailable` 完成；迟到响应丢弃，且不因
  重连产生第二份请求。

TCP 重新 Listen 只恢复 Listener，不重建整个 Node Transport。NATS 的内部重连只在
Connection 尚未 Closed 时工作；非 Stop 导致 Closed 后改由 Node 唯一 Transport owner
执行外层恢复：

1. Closed 回调只携带当前 generation 发出恢复信号，不直接创建新 Connection；
2. owner 原子切换到 Recovering、撤销发现并完成旧 generation 的 pending；
3. owner 关闭旧 Connection 和 Subscription，递增内部 generation；
4. 使用与 NATS 内部重连一致的 `2s` 等待和 Jitter 周期性创建 Connection；
5. Request/Response Subscription 和新 Transport generation 全部建立成功后才原子发布；
6. 旧 generation 的迟到回调、Response 和关闭事件全部忽略；
7. 任一步部分成功都由 owner 关闭本轮临时资源后继续下一次重试。

外层恢复同时只能存在一个循环，不增加公开配置，不允许双 Connection、双 Subscription 或
双 Transport generation 并存。这里的 generation 只隔离同一个 Node 进程内的旧连接回调，
不是发现协议中的进程代次；Node 的随机 `SessionID` 只在 Node 重新构造时变化。运维系统仍
可根据持续 Recovering 告警决定是否重启进程，但框架自身会一直尝试恢复，直到成功或收到
Stop。

### 14.1 Transport 恢复后的发现重新发布

Transport 恢复后由框架自动重新发布发现，不要求业务参与。重新发布必须同时满足：

1. 当前恢复回调属于最新 Transport generation，旧 Listener/Connection 的迟到回调被忽略；
2. TCP Listener 已成功 Listen 并进入 Accept 循环，或 NATS Connection 已 Connected 且
   Request/Response Subscription 已全部建立；
3. Node 未进入 Stopping/Stopped；
4. Service 仍处于 Running 或 Retired；Failed、Stopping、Stopped 和私有 Service 不发布；
5. 发布内容保留恢复前的 Service 状态，Retired 不能被恢复事件误改成 Running；
6. Provider 接受完整 Node 快照后才把本地发布状态标记为成功。

恢复期间会产生真实的 Lost，恢复成功后产生真实的 Found/StateChanged，不增加防抖，也不
隐藏状态变化。内部 generation 只用于排除陈旧回调，不进入发现协议，不重新引入已经删除的
Revision 字段。若当前 M14 进程内发现源发布失败，Transport 保持可用但 Node 继续处于
未发布状态并把 Discovery 标为不可用；M17/M18 的 Provider owner 负责按各自退避规则持续
重试发布。M16 不为尚未实现的 Provider 提前建立第二条重试 goroutine。

整体 Transport 进入 Recovering 时，Node 的存活状态保持成功，外部就绪状态立即失败；
恢复连接、Listener 或 Subscription 并成功重新发布发现后，外部就绪自动恢复。TCP 单个
远端目标连接断开不属于整体 Transport Recovering，只让该目标调用快速失败并在后台重连，
不能撤销本 Node 服务发现或改变本 Node 外部就绪。

### 14.2 启动阶段的 Transport 恢复

Node 先完成全部 Service 的纯 `OnInit`。全部 `OnInit` 成功后，再让 RPC Transport 达到
基础设施 Ready，然后调用业务 Service `OnStart`；此时 Transport 已经能够建立连接和完成
出站请求，但 Service 入站准入仍关闭，直到整个 Node 越过统一就绪屏障。错误分为两类：

首版可重试错误：

- NATS Server 暂时不可达、connection refused、timeout、临时 DNS 或 no route；
- 后续 M17/M18 Provider 暂时不可用时，由对应 Provider owner 重试。

这些错误使用与运行期相同的有上限退避持续重试，直到：

- Transport 成功 Ready；
- Start Context 被取消；
- 项目显式配置的 Application StartTimeout 到期。

Application StartTimeout 默认仍为无限，因此默认会等待基础设施恢复，但每次等待都能响应
进程 Stop 或启动取消。

不可重试错误：

- 地址、namespace 或配置格式非法；
- TLS 证书、私钥或 CA 无法解析、证书身份校验确定失败；
- NATS 用户名、Token、Credentials、NKey 或权限确定被拒绝；
- TCP 初次 Listen 的任意绑定失败，包括地址权限不足、地址不存在或端口已经被占用；
- Server 公布的 `max_payload` 小于 Origin 配置要求；
- 其他重复尝试不会改变结果的确定性错误。

不可重试错误立即导致当前 Node 启动失败，并按既有 Application 规则回滚已经启动的 Node。
重试期间只按状态变化和低频聚合写日志，不为每次失败打印完整错误；连接错误不是 panic。
Transport Ready 后只继续 `OnStart`；网络重试不会重复调用任何 `OnInit` 或 `OnStart`。

### 14.3 Transport 状态查询

Node 提供一个 RPC 入站 Transport 的无锁只读快照：

```go
type TransportKind uint8

const (
    TransportNone TransportKind = iota
    TransportTCP
    TransportNATS
)

type TransportState uint8

const (
    TransportDisabled TransportState = iota
    TransportStarting
    TransportReady
    TransportRecovering
    TransportFailed
    TransportStopping
    TransportStopped
)

type TransportStatus struct {
    Kind                TransportKind
    State               TransportState
    Reconnects          uint64
    ConsecutiveFailures uint64
    ErrorCode           errs.Code
}

func (n *Node) TransportStatus() TransportStatus
```

规则：

- 内部以原子指针发布不可变快照，查询只复制一个小结构，不获取 Transport 锁；
- `Reconnects` 统计成功恢复次数，不统计每一次失败尝试；
- Ready 后 `ConsecutiveFailures` 清零，累计次数继续由内部 Stats 保存；
- `ErrorCode` 表示当前 Transport 故障；恢复 Ready 后清零，历史错误由日志、Reconnects 和
  内部累计 Stats 保留；
- TCP 的 State 表示当前 Node 入站 Listener，不因某一个远端目标连接断开把整个 Node 标为
  Recovering；
- NATS 的 State 表示 Node 唯一 Connection 及 Request/Response Subscription 整体能力；
- TransportStatus 不包含发现发布状态；Discovery 属于独立基础设施，统一健康结果通过
  `HealthStatus()` 表达；
- 状态中不包含 Server URL、用户名、证书路径、Token 或其他敏感配置。

### 14.4 Transport 重试日志

可恢复连接错误不属于 panic。M16 首版沿用 TCP/NATS 基础库已有日志和恢复 owner 日志：

1. 首次断开或整体 Closed 立即记录详细 Warning/Error；
2. 后续失败受 `200ms`～`5s` 或 NATS 固定重连等待限制，不会形成忙循环；
3. 恢复成功立即记录 Info 和累计恢复次数；
4. 确定性启动错误立即记录 Error；
5. panic 继续遵守“每次完整 ErrorStack”；
6. Stop 主动造成的 Context canceled、Listener close 或 NATS close 不写故障日志。

M16 不额外实现一套 `lastLogAt/suppressed/firstFailureAt` 状态。基础库和 Adapter 同时再做
精确十秒聚合，需要增加日志过滤开关并形成第二层日志状态，收益不足以抵消复杂度；若生产
观测确认有刷屏，再在独立可观测性设计中基于实际频率补充。

## 15. 日志、Crash 与 stderr

最终资源顺序固定为：

```text
业务和框架资源停止
  -> BufferPool 最终检查
  -> 写出最终停止结果
  -> 关闭 CrashOutput 注册
  -> Flush/Close 日志 Runtime
  -> 释放 PID 运行权
```

规则：

- 配置启用文件日志时，由正在持有进程运行权的 Application 安装一次 CrashOutput；
- Crash 路径继续由日志包从活动日志路径派生，例如 `origin.crash.log`；
- CrashOutput 不进入普通日志队列，不在运行期间滚动；
- 正常退出时幂等注销 CrashOutput；
- 日志 Runtime 是最后一个异步框架组件；
- Error、ErrorStack 和最终停止日志先可靠提交，再执行 Close；
- 日志 Close 失败加入最终错误并映射非零退出码；
- 日志尚未创建或日志本身失败时，最后使用 stderr 输出一次未报告错误；
- 不重复打印已经由结构化 Logger 报告过的同一错误。

## 16. BufferPool 最终诊断

当 `buffer_pool.track_usage: true` 时：

1. 全部 Node、Transport、pending、Timer 和 Service 已停止后读取最终 Stats；
2. `InUseBuffers == 0` 时不写额外日志；
3. 非零时写一条 Warning，包含未归还数量、容量、超大 Buffer 数量和非零档位；
4. 默认不因诊断计数非零改变正常停止结果，避免统计功能本身改变生产行为；
5. 测试环境必须把框架自身未归还 Buffer 视为失败；
6. `track_usage: false` 时不做原子统计和最终扫描。

M16 同时补齐 Application 级只读诊断快照，返回公开只读 DTO，不把
`internal/bufferpool` 类型暴露到公共 API。该接口只用于监控、测试和排障，不进入 RPC
热路径。

## 17. 退出码

继续使用 M4 已冻结的退出码：

```text
0  正常停止、help、version、目标原本未运行
1  Application 启动、停止或运行期出现过 Failed Service
2  命令、参数或配置错误
3  进程控制失败
4  外部 stop 命令等待超时
```

说明：

- 目标进程内部 `CodeGracefulShutdownTimeout` 属于 Application 停止失败，目标进程退出码
  为 `1`；
- 独立的 `stop` 命令在自身 30 秒等待到期时退出码为 `4`；
- 外部 stop 超时不会向目标进程发送 Kill；
- 正常 Stop 中某个 `OnStop` 返回错误时，资源仍全部清理，最终退出码为 `1`。

## 18. 错误码

M16 首选复用现有错误码：

- `CodeCanceled`；
- `CodeInternal`；
- `CodeServiceStopping`；
- `CodeServiceStopped`；
- `CodeServiceFailed`；
- `CodeGracefulShutdownTimeout`；
- `CodeTransportUnavailable`；
- `CodeDiscoveryUnavailable`；
- `CodeLogOutputFailed`。

新增 `CodeServiceFailed = 1007`，专门表示 Service 在运行期发生无法安全恢复的内部故障并
已被隔离。Draining、Finalizing、重复 Stop 或普通任务 panic 不新增公开错误码。

新增 `CodeDiscoveryUnavailable = 5001`，表示已经配置为 Node 必需基础设施的 Discovery
Provider 当前断线、租约或 Watch 失效，或者恢复连接后尚未成功重新发布完整 Node 快照。
该状态持续重试，恢复后从 `HealthStatus.ErrorCode` 清除；配置格式错误仍使用
`CodeInvalidConfig`，普通无路由仍使用 `CodeRPCNoRoute`。

## 19. 可观测性

至少记录以下低基数字段：

- Application、Node、Service 的停止开始、结束和耗时；
- Service 的 Draining、Finalizing 耗时；
- Stop 开始时的 Accepted、Ready、Running、Awaiting 和 Timer 数量；
- 因 Stop 被拒绝的新任务、RPC、Notify 和 Timer 数量；
- finalizer Await 次数、超时和取消数量；
- `OnStop` 错误或 panic；
- 基础设施持续恢复状态及所属 Node、组件、连接状态和原始错误链；
- Failed Service 的首次根因、隔离时间和被拒绝任务数量；
- Transport 恢复次数、连续失败次数、当前退避和发现重新发布结果；
- Transport 启动重试分类、不可重试错误和状态快照变化；
- Transport 聚合日志抑制数量、故障持续时间和恢复耗时；
- 总体 Stop Deadline 是否到期；
- 日志关闭错误；
- BufferPool 最终未归还数量。

玩家 ID、RequestID、完整 Service 配置和凭据不能作为高基数长期指标或错误详情。

## 20. 性能和复杂度约束

M16 主要发生在启停慢路径，但仍必须遵守项目低延迟原则：

- 正常 RPC、Timer 和 Scheduler 热路径不增加全局锁；
- 不为每次任务增加 Stop 专用对象、TaskScope 或引用计数；
- finalizer Context 只在每个 Service 停止一次时创建；
- framework continuation 复用现有 Task 池和 FIFO；
- 总体 Stop 只创建一个 Deadline Context；
- 默认 Await Deadline 复用 M8，不增加每次调用 Go Timer；
- panic 堆栈只在真实异常时分配；
- BufferPool Stats 默认关闭；
- 不池化 finalizer、panic 错误或一次性停止对象。

## 21. 测试范围

### 21.1 Service 排空

- Stop 前 Ready、Running、Waiting 全部完成；
- 未到期 Timer 被取消，已入 Ready 的 Timer 完成；
- Draining 拒绝新的普通根任务；
- Draining 时普通业务代码始终只有一个执行槽，其他业务任务不能并发进入；
- 业务裸 goroutine 调用 Service API 和创建 Timer 被拒绝；
- 已接受 Task 可以继续 Await；
- 已接受 Task 可以创建受控 Async 延续；
- 外部 goroutine 不能借延续入口绕过停止；
- Async 快速响应、超时、取消和 Stop 竞争只回调一次；
- 排空结束后没有 Runner、Task、Deadline binding 或 Timer 残留。

### 21.2 OnStop

- `OnStop` 只调用一次；
- `OnStop` 由最后一个 Service Runner 在与普通任务无并发的情况下执行；
- `Await` 在同一 finalizer goroutine 返回；
- finalizer Await 期间不调度普通 Runner；
- TCP、NATS 和同 Node RPC 存档都能完成；
- 调用本 Service RPC立即返回停止错误，不死锁；
- Async、Notify、Broadcast、Timer 和业务 Post 在 finalizer 中被拒绝；
- 使用错误 Context 不能伪造 finalizer；
- `OnStop` error、panic 和 Deadline 均继续执行框架清理。

### 21.3 Application 与进程

- 多 Node 按实际启动严格反序停止；
- 单个 Node 的多个 Service 按配置顺序启动、按实际启动顺序严格倒序停止；
- 依赖 Node 在调用方 `OnStop` 完成前保持可用；
- Unix SIGINT/SIGTERM、Windows 真实 `Ctrl+C`、Windows `.stop` 和进程内 Stop 合并；
- 并发重复 Stop 只执行一套清理；
- 外部 30 秒等待不改变目标内部 Stop Context；
- 共享总体 Deadline 不在各阶段重置；
- 正常停止和启动回滚映射正确退出码；
- TCP/NATS 持续恢复记录详细错误并撤销不可达发现，但不触发 Application/Node/Service
  停止；
- PID 锁在日志和 Crash 清理后才释放。

### 21.4 异常与资源

- 用户 Task panic 后 Service 继续运行且执行槽归还；
- RPC、Timer、Async 和普通 Task panic 均打印完整堆栈，随后下一项任务仍可执行；
- 可归属于当前 Task 的框架 panic 完成当前任务后继续 Runner；
- Runner 异常退出但状态快照一致时可以重新唤醒，且仍只有一个执行槽；
- 故障注入制造无法证明一致的 Scheduler 状态时，只隔离目标 Service，不取消 Application、
  不停止其他 Service，也不退出测试进程；
- Failed Service 返回 `CodeServiceFailed`，`Failure()` 保留首次根因且不暴露到线协议；
- Failed Service 一律跳过业务 `OnStop`，继续释放可证明所有权的框架资源和后续
  Service，避免为极少数内部故障再建立第二套 finalizer 恢复状态机；
- Failed Service 出现后 Application 保持 Running，正式 Stop 完整清理后返回
  `CodeServiceFailed` 并使用退出码 `1`；
- `OnStop` panic 不阻止其他 Service 和 Node；
- 每次 panic 恰好记录一次完整堆栈，不能被多层边界重复记录，也不能因限频而省略；
- TCP/NATS pending 和 Buffer 均只完成或释放一次；
- TCP reset、临时 Accept 错误、Listener 重建、NATS Reconnecting、慢消费者和意外 Closed
  分别覆盖内部重连与外层重建路径；
- TCP/NATS 连续故障期间按 Application 生命周期持续重试、退避有上限，且 Stop 能立即中断；
- Transport 恢复后只发布 Running/Retired 公共 Service，陈旧 generation 不会重复发布；
- 启动时 NATS 临时网络错误持续重试；TCP 初次绑定和配置、证书、鉴权等确定性错误立即
  失败；
- `TransportStatus()` 并发查询不阻塞 RPC 热路径，TCP 单目标断线不改变 Node 入站状态；
- Transport Recovering/Failed 时 Node State 保持 Ready，恢复成功不重复生命周期；
- `HealthStatus()` 并发查询无锁、无分配，并按固定优先级返回稳定结果；
- 部分和全部公开 Service Failed、全部 Retired、零公开 Service 分别符合健康矩阵；
- Discovery Provider 断线时就绪失败、存活成功，恢复发布后自动就绪；
- 队列满、单次 RPC 超时、业务错误和单任务 panic 不改变健康快照；
- 首次网络错误和恢复成功均有明确日志，持续失败受固定退避限制；
- 日志正常排空，日志关闭失败仍有 stderr 兜底；
- BufferPool 统计开启时正常路径最终为零；
- Windows/Linux 执行完整测试和 Race；
- 子进程验证实际信号、PID 锁、Crash 文件和退出码；
- 重复运行泄漏测试确认 goroutine 数量收敛。

  恢复后重新发布接缝；

3. 整次停止只创建一个总体 stopCtx，不为 Node、Service 和日志重置时限；
4. Windows 控制台 `Ctrl+C` 必须进入正常完整停止流程；
5. Node 内 Service 按配置顺序启动、按实际启动顺序严格倒序停止；
6. M16 不夹带 Provider、Module、事件、路由或外部适配器；
7. 单个 Service 必须逐个停止，`OnStop` 由该 Service 的最后一个 Runner 独占执行；
8. Draining 关闭新根任务和 Timer 准入，已接受任务仍按单执行槽顺序排空；业务裸
   goroutine 无有效 Task Context，不能绕过停止准入；
9. Draining 排空任务可完成 RPC/Await/Async/Notify/Broadcast，Finalizing 只允许
   `OnStop` 和 Await；
10. 单个任务调用边界每次 panic 必须打印完整堆栈、只结束问题任务、归还执行权，Service
    继续运行；
11. TCP/NATS 进入持续恢复时必须记录详细错误、撤销不可达路由并完成不能跨代次保留的
    pending，但不取消 Application，也不退出或停止 Service；
12. Scheduler Stop 拆为 Drain 和最终 Finish，中间执行独占 `OnStop`；
13. `OnStop` Await 在同一个 finalizer Runner 直接等待，不创建替代 Runner；
14. 不增加 TaskScope、父子任务树或第二份 pending 计数；
15. 默认 Await Deadline 使用 M8，总体 stopCtx 作为不可突破的上限；
16. 文件日志启用时由 Application 生命周期安装并释放 CrashOutput；
17. BufferPool 最终诊断按告警和测试规则执行；
18. 复用现有错误码和退出码；
19. Scheduler 和执行槽不变量异常采用分级恢复，不能直接导致 Application 或进程退出；
20. TCP/NATS 运行期恢复没有次数上限；TCP 无限重建 Listener，NATS 内部无限重连，意外
    Closed 后再由唯一 Transport owner 周期性重建 Connection、Subscription 和内部
    Transport generation；Node 进程级 SessionID 不随 Transport 重连变化；
21. 每一次 panic 都恰好输出一次完整堆栈，首版不对相同 panic 做日志限频；
22. 无法恢复的单个 Service 使用已有 `StateFailed`，新增 `CodeServiceFailed=1007` 和本地
    `Failure()` 查询，撤销该 Service 发现但不影响同 Node 其他 Service；
23. RPC TCP/NATS 固定无限重连且退避有上限，不开放重连次数配置；重连期间快速失败、
    不缓冲、不重放；
24. Transport 完全 Ready 后自动重新发布 Running/Retired Service，使用内部 generation
    排除陈旧回调，不增加公开 Revision；
25. Failed Service 正式 Stop 时一律跳过业务 `OnStop`；首个故障边界记录完整现场，
    Stop 只释放可证明所有权的框架资源，保持实现简单且不会并发访问损坏状态；
26. 启动期 NATS 可恢复网络错误持续重试到 Start Context 结束；TCP 初次 Listen 失败与
    确定性配置、证书、鉴权和权限错误立即启动失败；
27. Node 公开无锁只读 `TransportStatus()`，只表示 RPC 入站整体健康，不枚举 TCP 远端
    连接或暴露敏感配置；
28. Failed Service 不立即停止 Application，但正式 Stop 后最终 State 为 Failed、退出码
    为 `1`，不能因清理成功掩盖运行期严重故障；
29. Transport Recovering/Failed 时 Node 公开生命周期仍保持 Ready；Transport 细节由
    `TransportStatus()` 表达，综合存活、就绪、降级与发现状态由 `HealthStatus()` 表达；
30. 可恢复网络错误首次立即记录、后续尝试受固定退避限制、恢复立即记录；确定性错误立即
    Error，panic 每次 ErrorStack；M16 不增加第二套精确日志聚合状态；
31. 多个 Failed Service 全部以安全摘要加入最终 `errors.Join`，首次根因保持主顺序；
32. `TransportStatus.ErrorCode` 只表示当前故障，恢复 Ready 后清零；
33. `Failure()` 在 Service Stopped 后继续保留到一次性对象释放，正常 Service 保持 nil。
34. Node 使用两阶段启动：全部纯 `OnInit` 成功后才启动运行期基础设施并进入 `OnStart`；
35. `OnInit` 中 Await、Async、Notify、Broadcast、业务 Timer、普通任务、外部访问和业务
    goroutine 均返回 `CodeServiceNotReady`；
36. 所有业务 `OnInit` 均执行，错误按配置顺序聚合；聚合失败时当前 Node 不调用任何业务
    `OnStop`；
37. 保留 `OnStart(ctx) error`；OnStart Await 使用同一生命周期 goroutine 和 M8
    DeadlineQueue，不激活普通 Runner；
38. `OnStart` 失败 Service 与此前进入过 `OnStart` 的 Service 都按严格反序执行一次
    `OnStop`，随后回滚已经 Ready 的 Node；
39. 全部 `OnStart` 成功后才统一激活 Runner、Timer、入站准入并发布当前 Node 的完整服务
    记录；
40. `OnStop` error 不中断后续清理、不恢复 Running、不自动重试；最终按停止顺序聚合并由
    最外层返回非零退出码。
41. 启动中收到 Stop 时不再进入新的生命周期回调；取消当前 startCtx，反序清理已经进入
    `OnStart` 的 Service；纯 Stop 且清理成功使用退出码 `0`；
42. OnStart 调用当前 Node 的任意 Service RPC 均返回 `CodeServiceNotReady`，不增加启动期
    本地内联调用；
43. Origin 不禁止或检测业务 `go` 语句；Service/Module 可以持有可取消、可等待的工作池，
    但 Worker 不直接并发访问 Service 可变状态，结果通过 `DispatchAsync` 返回唯一执行槽；
44. 运行期 Service 进入 Failed 只表示 Scheduler 内部不变量已经无法证明，正常业务错误、
    任务 panic、过载和网络错误均不能触发。
45. TCP/NATS 普通网络故障不存在永久终态；非 Stop 的 NATS Closed 使用单一 owner、
    generation 隔离和固定退避持续重建，直到成功或收到 Stop。
46. M16 不增加 WorkerManager；业务 Worker 的 Context、CancelFunc、WaitGroup 和队列由
    Service/Module 自己持有；
47. 增加 `Service.GoSafe(func()) error` 作为业务 goroutine 顶层 panic 保底；它打印
    ErrorStack 但不自动重跑整个函数，也不替业务执行 cancel/wait；
48. Draining 后 Worker 新提交的 `DispatchAsync` 返回 `CodeServiceStopping`；必须参与
    存档的 Worker 状态由 `OnStop` 取消并等待 Worker 后直接汇总；
49. Transport 故障恢复 Ready 后清除当前错误状态，不污染以后正常 Stop 的最终退出码；
50. Transport 长期 Recovering 只持续重试、撤销发现并暴露状态，不由 Origin 自动重启
    进程，是否重启由 Kubernetes、systemd 或运维策略决定。
51. 增加同步 `Service.RunSafe(func()) error`；它在单 Job 边界 recover、打印 ErrorStack 并
    返回 `CodeInternal`，使业务 Worker 可以继续处理下一 Job，但不授予 Service 执行槽。
52. 已冻结后续 Module 里程碑的生命周期规则：Module `OnInit` 失败立即终止当前
    Service 的 Module 树构建，不调用 Module `OnStop`；Node 继续执行后续 Service
    `OnInit` 并按配置顺序聚合错误。M16 不实现 Module 静态树。
53. 已冻结后续 Module 里程碑的回滚规则：只要 `Module.OnStart` 已经被调用，即使返回
    错误也进入实际启动记录，并与此前 Module 严格反序执行一次 `OnStop`。M16 不据此
    增加任何 Module 代码。
54. `GoSafe`、`RunSafe` 捕获的业务 Worker panic 只记录和返回当前错误，不改变 Service
    生命周期，也不触发 `Failed`。
55. 全部公开 Service 都进入 Failed 时，Node/Application 不自动 Stop；撤销失败服务并
    保持诊断和内部运行能力，存活成功、外部就绪失败，等待正式 Stop 或运维处置。
56. TCP Listener 或 NATS 整体能力 Recovering 时存活成功、外部就绪失败，恢复并重新发布
    后自动就绪；TCP 单目标连接断开不改变本 Node 整体健康。
57. M16 只提供统一无锁健康快照，不内置 HTTP Probe Server；具体 Kubernetes、systemd
    或项目 Probe 适配器后置为独立模块。
58. `Node.HealthStatus()` 固定返回 Liveness、Readiness、Degraded 和 ErrorCode 四个字段，
    内部使用原子不可变快照，查询不加锁、不分配。
59. 部分公开 Service Failed 时保持就绪并标记 Degraded；Retired 不是故障，仍按健康服务
    处理；原本存在的公开 Service 全部 Failed 时才取消就绪。
60. 没有公开 Service 的纯内部 Node 完成启动且必需基础设施正常时保持就绪，不能使用空
    集合误判为全部失败。
61. 必需 Discovery Provider 不可用时存活成功、就绪失败、后台持续恢复；新增
    `CodeDiscoveryUnavailable=5001`，重新发布成功后自动恢复。
62. 队列过载、单次 RPC 超时、业务错误和已恢复的单任务 panic 不改变健康状态，只返回
    对应错误并记录指标。

当前 M16 公共行为与公共 API 已无待确认项；实施前剩余的错误优先级、原子发布和测试组合
均已在本文固定，不再另行增加对话确认。

### 23.1 最后一次开工终审收敛

编码前对 M7～M15 现有实现、关联明细设计和本文件再次逐项对照，结论如下：

1. M16 的五个实现主题虽然较多，但都落在同一条生命周期控制链上：两阶段启动决定何时开放
   Transport，Service finalizer 决定何时关闭 Transport，Transport 状态决定发现发布和健康
   快照，Application 最后统一关闭 Crash、日志和进程资源。因此不再人为拆出一份会产生
   临时双状态机的中间里程碑；
2. `StopScheduler` 不能继续在 `OnStop` 之前关闭 DeadlineQueue。实现统一收敛为
   `Draining -> Finalizing -> Stopped`，沿用现有 `accepted`、Ready FIFO 和 Await
   Deadline，不增加 TaskScope、父子任务树、第二份 pending 计数或第二套 Scheduler；
3. `OnInit` 实现必须从“首错立即返回”改为“所有纯初始化均执行、按配置顺序聚合”，但
   Stop/Context 已经明确到达时不再开始新的生命周期回调；这两条规则分别处理业务错误和
   外部停止，不互相冲突；
4. Service Retire/Resume 公开 API 仍属于 M16 之后的独立里程碑。M16 的健康和发现发布代码
   只保证未来 `Retired` 与 `Running` 同属健康可发布状态，不提前增加退休控制接口；
5. Origin/etcd Provider 仍不进入 M16。M16 只建立 Provider 将来需要提交的健康输入与
   `CodeDiscoveryUnavailable`，不增加临时 Provider、租约、Watch 或配置字段；
6. NATS 恢复只更换内部 Transport generation，不更换 Node `SessionID`。否则同一进程恢复
   后会让既有发现记录和 RPC 包头产生不必要的进程代次漂移，也会与 TCP 语义不一致；
7. `HealthStatus`、`TransportStatus` 和 Service Failure 都走冷路径原子快照；正常 RPC、
   Timer、队列投递和编解码热路径不增加锁、反射、字符串拼接或每调用分配；
8. 运行期普通网络错误只进入 Recovering，不能再复用现有“Transport 终态取消
   Application”的路径；Application 最终非零结果只保留启动/停止错误及真正隔离的
   `CodeServiceFailed`；
9. CrashOutput、BufferPool 最终诊断和日志关闭复用同一个总体 `stopCtx`。不得在日志阶段
   重新获得一份完整 StopTimeout；
10. Windows `Ctrl+C`、Unix SIGINT/SIGTERM 和 Windows `.stop` 已由 M4 统一成 Run Context
    取消；M16 只补充 Application 端到端验收，不再增加平台专用停止状态机。

终审没有发现需要改变已确认公共 API 或重新向开发者确认的阻塞问题，允许生成实施计划并
进入编码。

### 23.2 实施验收记录

M16 已于 2026-07-29 完成实现和最终 Review，实际结果如下：

1. Service 停止状态机已经收敛为 `Draining -> Finalizing -> Stopped`；停止边界之后只
   接受能够由既有 Task Context 证明来源的异步延续，最后一个 Runner 独占执行
   `OnStop(ctx)`，并允许复用 M8 DeadlineQueue 完成顺序 Await；
2. 正常业务 panic 只结束当前 Task，`GoSafe`、`RunSafe` 为业务 Worker 提供显式保底；
   真正 Scheduler 不变量故障只隔离目标 Service。无法证明内部锁所有权时使用原子故障
   快照和保守清理，不阻塞 Node 继续停止其他 Service；
3. TCP Listener 由唯一 owner 负责运行期重建；NATS 使用官方客户端无限重连和外层
   generation 重建。断线立即失败当前 pending，不重放 Request/Notify，Node SessionID
   在同一进程生命周期内保持不变；
4. Application 整次关闭只创建一个总体 Stop Context，依次覆盖 Node、Service、RPC、
   Timer、BufferPool 最终诊断、CrashOutput 和日志关闭，不再给每个阶段重新分配完整
   StopTimeout；
5. Windows 已通过全仓单元测试、Race、构建和关键 Benchmark；Ubuntu Go 1.26.5 已通过
   全仓单元测试、Race 和构建；真实三节点 NATS 集群已通过跨 Broker RPC，并通过强制
   断开当前连接节点验证自动切换与恢复；
