# Origin 第三版 M4 程序命令与进程控制库设计

> 文档状态：待开发者 Review
> 创建日期：2026-07-26
> 最后更新：2026-07-26

## 1. 目标

M4 实现一个独立、可测试的程序命令与本地进程控制库，负责：

- 提供 `start`、`stop`、`help`、`version` 内置命令；
- 保留 v2 常用命令名称和首参数兼容入口；
- 允许注册一次性自定义离线命令；
- 通过必填 `--app-name` 标识当前 Application 进程；
- 使用 PID 文件独占锁防止同名进程重复启动；
- 使用本地停止请求文件向运行中的进程传递优雅停止意图；
- 通过可注入的 Start Handler 验证完整启停闭环；
- 返回稳定退出码和错误，不在库代码中终止进程。

M4 只解决“怎样启动一个进程、怎样请求它停止、怎样把启动参数交给上层”。
它不认识 Application、Node、Service、Module、RPC 和服务发现的内部实现。

完成 M4 后，M7 可以把最小 Application 生命周期接入 Start Handler；M12 再把
SIGINT、SIGTERM、Service 排空、`OnStop`、日志关闭等完整优雅停止流程接入同一停止意图。

## 2. 前置依赖与边界

### 2.1 直接依赖

M4 直接依赖：

- M0 的 Go module、Go 1.26.5、`buildinfo`、`errs` 和质量门禁；
- Go 标准库；
- 一个固定版本的 `golang.org/x/sys`，只用于 Windows、Linux 和 macOS 文件锁适配。

建议在实施 Review 时固定：

```text
golang.org/x/sys v0.47.0
```

选择 `x/sys` 而不是自己维护原始系统调用的原因：

1. Go 标准库 `syscall` 已冻结，官方建议新代码优先使用 `golang.org/x/sys`；
2. Windows 需要 `LockFileEx`/`UnlockFileEx`，Unix 需要 `flock`，自行维护常量、
   结构体布局和系统调用会明显增加跨平台代码量及错误风险；
3. `x/sys` 由 Go 项目维护，M4 只使用很小的文件锁 API，不引入 CLI 框架或运行时服务。

参考：

- [Go syscall 包说明](https://pkg.go.dev/syscall)；
- [golang.org/x/sys](https://pkg.go.dev/golang.org/x/sys)；
- [Windows LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)；
- [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)。

### 2.2 不直接依赖

M4 不直接依赖：

- M1 日志库；
- M2 BufferPool；
- M3 配置目录加载；
- Application、Node、Service、Module 或调度器；
- TCP、NATS、Protobuf、RPC 或服务发现；
- Cobra、urfave/cli 或其他第三方 CLI 框架。

`start --config` 只把清理后的配置目录传给 Start Handler。配置内容的读取、强类型解码
和业务校验由以后接入的 Handler 调用 M3 完成。命令层不定义或复制 Application 配置模型。

`help`、`version`、参数错误和进程控制错误直接使用注入的标准输入输出。M4 不为几个
低频命令初始化异步日志系统，也不会让日志失败阻止 `stop` 请求。

## 3. v2 对照与重构重点

v2 的 `console` 和 `node` 包提供了 `-start`、`-stop`、`-retire`、`-help`、
配置路径、日志参数、pprof 参数和自定义回调。v3 保留使用者熟悉的主要动作名称，
但不复制其代码。

v2 当前存在以下问题：

1. 使用包级 `flag.CommandLine` 和全局命令列表，多个实例及测试之间容易互相污染；
2. 一次命令行可以出现多个主动作，实际执行顺序依赖注册顺序；
3. `start` 被特殊推迟到其他 flag 之后执行，Command 与 Option 概念混合；
4. PID 文件名包含 `os.Args[0]` 和 NodeID，不适合一个 Application 管理多个 Node；
5. PID 文件使用 `O_TRUNC` 直接覆盖，并发启动存在竞争窗口；
6. 只比较 PID 和进程名，PID 复用时可能误判；
7. Windows 的停止退化为强制 Kill，无法执行统一优雅停止；
8. 多处库代码直接调用 `os.Exit`；
9. 打开 PID 文件失败后仍可能对 nil 文件执行 `Close`；
10. 命令回调没有实例级输入输出和清晰的 panic 边界。

M4 的重构方向：

- Command Runner 实例持有注册表，不使用可变包级状态；
- 一个进程命令只执行一个主动作；
- AppName 标识 Application 进程，NodeID 只表示本次选择启动哪些 Node；
- 操作系统文件锁是“是否正在运行”的唯一判定依据，PID 数字只供诊断；
- Windows、Linux、macOS 统一发送停止意图，不默认强杀；
- 库返回 `error` 和退出码，最终 `main` 决定是否 `os.Exit`。

## 4. 命令外观

正式外观使用子命令：

```text
game-server start --app-name game-dev --config ./config --node gateway-1,game-1
game-server stop --app-name game-dev
game-server help
game-server help start
game-server version
```

规则：

1. 第一个参数是唯一主命令；
2. `start`、`stop`、`help`、`version` 是内置保留名；
3. 无参数时显示简短帮助，并返回参数错误；
4. `-h`、`--help` 和首参数 `-help` 归一为 `help`；
5. 首参数 `-start`、`-stop` 分别作为 `start`、`stop` 的 v2 兼容别名；
6. 不兼容 v2 的 `-start nodeid=...` 字符串参数，v3 使用独立的 `--node`；
7. 内置长参数统一使用小写 kebab-case；
8. 带值参数接受 `--name value` 和 `--name=value`；
9. 不为 `--app-name`、`--config`、`--pid-dir`、`--node` 增加含义容易冲突的短别名；
10. 内置参数使用各自独立的 `flag.FlagSet` 和 `flag.ContinueOnError`，不接触
    `flag.CommandLine`。

正式文档、构建脚本和示例工程只使用无前缀子命令。兼容别名只降低 v2 迁移成本，
不继续扩展新功能。

## 5. 内置命令

### 5.1 start

```text
game-server start \
  --app-name game-dev \
  [--config ./config] \
  [--pid-dir ./run] \
  [--node gateway-1,game-1]
```

参数规则：

- `--app-name` 必填；
- `--config` 默认 `./config`，只表示目录；
- `--pid-dir` 默认 `./run`；
- `--node` 使用逗号分隔一个或多个 NodeID；
- NodeID 去除两侧空白后不能为空；
- 同一次命令中的重复 NodeID 是参数错误；
- NodeID 顺序保持与命令行一致，后续作为 Application 的启动顺序；
- 未传 `--node` 时传递空切片，由以后接入的 Application 按配置中顶层 `nodes`
  声明顺序启动全部 Node；
- 停止顺序不由 M4 计算，M7/M12 按最终启动顺序倒序停止。

M4 在调用 Handler 前完成：

1. 解析并校验命令参数；
2. 清理并绝对化配置目录与 PID 目录；
3. 确认配置路径存在且是目录，但不读取其中的配置文件；
4. 创建并校验 PID 目录；
5. 获得 AppName 对应的进程独占锁；
6. 清除同 AppName 的陈旧停止请求文件；
7. 在锁保护下写入 PID 诊断记录并 `Sync`；
8. 启动一个 M4 所有的停止请求监听 goroutine；
9. 同步执行 Start Handler。

Start Handler 返回后，M4 按逆序：

1. 停止并等待控制 goroutine 退出；
2. 释放 PID 文件锁并关闭文件；
3. 返回 Handler 的执行结果。

Start Handler 必须同步运行到上层 Application 已经完全结束。Handler 返回即表示 M4
可以释放同 AppName 的进程占用权。

### 5.2 stop

```text
game-server stop \
  --app-name game-dev \
  [--pid-dir ./run] \
  [--timeout 30s]
```

规则：

- `--app-name` 必填；
- `--pid-dir` 默认 `./run`；
- `stop` 不读取 `--config`，也不初始化业务配置；
- `--timeout` 是 stop 命令等待目标进程释放占用权的最长时间；
- 建议首版默认 `30s`；
- `--timeout` 使用 Go `time.ParseDuration` 风格，必须大于零；
- 目标未运行时返回幂等成功，并向 stdout 输出 `not running`；
- 目标运行时原子创建停止请求文件；文件已存在表示已有停止请求，不重复报错；
- 发出请求后轮询 PID 文件锁，直到锁释放或等待超时；
- 等待超时只结束 stop 命令，不强制终止目标进程，也不删除目标仍可能处理的请求文件；
- 目标进程控制文件不可访问、锁状态无法判断或请求文件无法创建时返回进程控制错误。

`--timeout` 与 Application 内部优雅停止 Deadline 是两个不同概念：

- M4 的 timeout 只限制“调用 stop 的终端或脚本等待多久”；
- M12 的 Application Deadline 决定目标进程内部最多花多久排空和关闭；
- stop 命令不加载业务配置，因此不能可靠复用 Application 的配置值；
- 使用者可以按部署环境通过 `--timeout` 把外部等待设置得比内部 Deadline 更长。

固定 `30s` 是当前推荐值，避免默认无限等待导致脚本永久挂住。该默认值需要在 M4
开工 Review 中最终确认。

### 5.3 help

```text
game-server help
game-server help start
game-server --help
```

规则：

- 不读取配置；
- 不获得 PID 锁；
- 不创建控制 goroutine；
- 不初始化日志或 Application；
- 总帮助先显示内置命令，再按命令名排序显示自定义命令；
- 子命令帮助显示 Usage、Summary 和参数；
- 帮助写 stdout；
- 参数错误写入调用方返回的 error，由最终程序只打印一次；
- `buildinfo.BuildTime()` 非空时在帮助头部显示，为空时整行省略。

### 5.4 version

`version` 不初始化任何运行时资源，固定输出：

```text
version: v3.0.0
commit: abcdef123456
build_time: 2026-07-26T10:00:00+08:00
go_version: go1.26.5
```

规则：

- `version`、`commit`、`build_time` 使用 M0 `buildinfo`；
- `go_version` 使用 `runtime.Version()`；
- 未注入的字段输出 `unknown`，保持输出字段稳定；
- M4 不输出“协议版本”，因为 RPC 线协议要到 M9/M10 才定义；
- M10 确认协议版本后如确有运维需求，再独立增加字段。

### 5.5 retire

M4 不实现 `retire`。

Service 退休是在线运行时能力，需要携带 Node、Service 和动作语义，不能复用只表达
“停止整个 Application”的空请求文件。退休控制接口进入 M12 之后的独立里程碑再设计。

## 6. AppName 规则

一个 Application 可以管理多个 Node，因此进程控制不能再使用单个 NodeID 命名。

AppName 规则：

- start 和 stop 都必须显式传入 `--app-name`；
- 不从可执行文件名、配置目录、环境变量或第一个 NodeID 推导；
- 使用小写 kebab-case；
- 建议正则为 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`；
- 最大长度建议为 63 个 ASCII 字符；
- 不允许路径分隔符、点、空白、连续中划线或末尾中划线；
- 同一 PID 目录中的 AppName 必须唯一；
- AppName 只用于本地进程控制和人工定位，不替代 NodeID，也不进入服务发现。

显式 AppName 会保留在进程命令行中，便于：

```text
ps ... | grep -- "--app-name game-dev"
```

PID 文件与停止请求文件分别为：

```text
<pid-dir>/<app-name>.pid
<pid-dir>/<app-name>.stop
```

## 7. PID 文件与独占锁

### 7.1 PID 文件内容

PID 文件只保存诊断信息：

```json
{
  "pid": 12345,
  "started_at": "2026-07-26T10:00:00+08:00"
}
```

规则：

- `pid` 使用当前进程 PID；
- `started_at` 使用当前机器本地时间；
- 时间格式为 RFC 3339，并保留数字时区偏移；
- 不保存 executable、address、token、state、Node 列表或业务配置；
- PID 内容不承担进程身份认证，也不是“是否正在运行”的判定依据；
- PID 文件正常退出后保留，便于诊断；下次获得锁后覆盖。

### 7.2 锁的语义

运行进程在整个 Start Handler 生命周期内持有 PID 文件的非阻塞独占锁：

- Linux/macOS 使用 `unix.Flock(fd, LOCK_EX|LOCK_NB)`；
- Windows 使用带 `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`
  的 `windows.LockFileEx`；
- Windows 锁定从偏移零开始的一个字节；操作系统允许锁定超过当前文件末尾的范围；
- Unix 使用文件描述符关联的整文件 advisory lock；
- 锁释放同时执行显式 unlock 和 `Close`，任一步骤失败均保留错误；
- 进程异常退出时，操作系统关闭文件句柄并释放锁；
- 首版只支持本机磁盘，不承诺 NFS、SMB 或其他共享文件系统的锁语义。

文件权限建议：

- PID 目录在 Unix 创建为 `0750`；
- PID 文件和停止请求文件创建为 `0600`；
- Windows 使用当前用户 ACL，Go FileMode 只作为兼容参数。

### 7.3 为什么不能用临时文件替换 PID 文件

进程锁绑定已打开的文件对象。获得锁后再用“临时文件 + rename”替换 PID 路径，
可能使锁仍属于旧文件，而其他进程从新路径打开了未锁定文件。

因此写 PID 记录时必须：

1. 先打开固定 PID 文件并获得锁；
2. 在同一个已锁定文件描述符上 `Truncate(0)`；
3. 从偏移零写入完整 JSON；
4. 执行文件 `Sync`；
5. 全生命周期不替换该路径对应的文件对象。

stop 命令不依赖 PID JSON 内容，因此崩溃造成的半写记录只影响人工诊断，不影响
运行状态判断或停止寻址。

## 8. 停止请求文件

停止请求文件为：

```text
<pid-dir>/<app-name>.stop
```

规则：

1. stop 命令先检查 PID 文件锁确实被占用；
2. 使用 `O_CREATE|O_EXCL` 原子创建请求文件；
3. 文件内容为空，不传递业务参数；
4. 请求文件已存在按“已经请求停止”处理；
5. 目标进程每 `100ms` 检查一次请求文件；
6. 检测到后先删除请求文件，再取消 Start Handler 的运行 Context；
7. 多次请求通过同一个取消函数自然合并；
8. start 获得 PID 锁后、启动监听前，先删除同 AppName 的陈旧请求文件；
9. 控制 goroutine 不执行 Application Stop，只负责产生停止意图；
10. Start Handler 返回时，M4 取消并等待控制 goroutine，不能遗留 goroutine。

不采用 `fsnotify`，因为一个 `100ms` 的低频本地控制轮询不在游戏逻辑热路径，
标准库实现更简单，也避免增加文件系统监听依赖和各平台差异。

### 8.1 关键竞争规则

需要明确处理以下竞争：

- stop 确认锁占用后，目标恰好退出：请求文件可能成为陈旧文件；下一次 start
  获得锁后会先删除它；
- 两个 stop 同时执行：只有一个创建成功，另一个把文件已存在视为幂等；
- 目标删除请求文件后仍在排空，第二个 stop 又创建文件：目标已收到取消信号，
  新文件允许残留并由下次 start 清除；
- stop 轮询时成功获得锁：立即释放该锁并返回停止完成，绝不能覆盖 PID 内容；
- stop 等待超时：不删除请求文件，不强杀目标，不取得目标资源所有权。

## 9. 公开包与 API 外观

### 9.1 包位置

建议建立公开包：

```text
command
```

不继续使用 v2 的 `console` 名称，因为该包同时负责命令解析和本地进程控制，
并不表示日志控制台。

平台文件锁实现放在：

```text
command/internal/processlock
```

只允许 `command` 包使用，不向业务暴露锁句柄或控制文件操作。

### 9.2 核心类型

建议公开外观：

```go
package command

type ExitCode int

const (
    ExitSuccess        ExitCode = 0
    ExitFailure        ExitCode = 1
    ExitUsage          ExitCode = 2
    ExitProcessControl ExitCode = 3
    ExitStopTimeout    ExitCode = 4
)

type StartRequest struct {
    AppName  string
    ConfigDir string
    PIDDir    string
    NodeIDs   []string
}

type StartHandler func(ctx context.Context, request StartRequest) error

type Options struct {
    ProgramName string
    Stdin       io.Reader
    Stdout      io.Writer
    Stderr      io.Writer
    Start       StartHandler
}

type Runner struct {
    // 仅包含未公开的实例状态。
}

func New(options Options) (*Runner, error)
func (runner *Runner) Register(command Command) error
func (runner *Runner) Run(
    ctx context.Context,
    args []string,
) (ExitCode, error)
```

字段对齐在实际代码中由 `gofmt` 决定，以上只表示 API 语义。

规则：

- `args` 传入 `os.Args[1:]`，不包含可执行文件路径；
- `ProgramName` 为空时使用当前可执行文件的 base name；
- nil stdin/stdout/stderr 分别使用 `os.Stdin`、`os.Stdout`、`os.Stderr`；
- `Start` 必须非 nil，构造时校验；
- `Runner` 不支持并发 `Register` 或并发 `Run`；
- `Run` 不调用 `os.Exit`；
- help、version 和正常状态由 Runner 写到注入输出；
- 普通失败作为 `error` 返回，由最外层程序向 stderr 只打印一次；
- `NodeIDs` 在交给 Handler 前复制，Handler 不得修改 Runner 内部参数状态。

### 9.3 Start Handler 的取消语义

Runner 为每次 start 建立一个派生 Context：

- 调用方传入的 Context 取消时，派生 Context 取消；
- 检测到停止请求文件时，派生 Context 取消；
- M12 接入 SIGINT/SIGTERM 后，也取消同一个 Context；
- Handler 收到 `ctx.Done()` 后负责启动上层优雅停止；
- Runner 不假设 Context 取消后 Handler 会立即返回；
- Runner 必须一直持有 PID 锁，直到 Handler 实际返回。

示例：

```go
runner, err := command.New(command.Options{
    ProgramName: "game-server",
    Start: func(ctx context.Context, request command.StartRequest) error {
        app, err := newApplication(request)
        if err != nil {
            return err
        }
        return app.Run(ctx)
    },
})
if err != nil {
    return 1
}

code, err := runner.Run(context.Background(), os.Args[1:])
if err != nil {
    fmt.Fprintln(os.Stderr, err)
}
return int(code)
```

M4 测试使用一个阻塞到 `ctx.Done()` 的假 Handler。M4 不创建假的 Application 类型。

## 10. 自定义离线命令

建议外观：

```go
type Context struct {
    context.Context
    Stdin  io.Reader
    Stdout io.Writer
    Stderr io.Writer
}

type Command struct {
    Name    string
    Summary string
    Usage   string
    Run     func(ctx Context, args []string) error
}
```

注册示例：

```go
err := runner.Register(command.Command{
    Name:    "check-config",
    Summary: "检查配置但不启动服务",
    Usage:   "game-server check-config --config ./config",
    Run: func(ctx command.Context, args []string) error {
        flags := flag.NewFlagSet("check-config", flag.ContinueOnError)
        flags.SetOutput(ctx.Stderr)

        configDir := flags.String("config", "./config", "配置目录")
        if err := flags.Parse(args); err != nil {
            return err
        }

        var cfg ProjectConfig
        return config.LoadDir(*configDir, &cfg)
    },
})
```

规则：

- 注册表属于 Runner 实例；
- 注册在首次 `Run` 前完成；
- 名称使用与 AppName 相同的小写 kebab-case 语法；
- 空名称、重复名称和覆盖内置命令返回参数错误；
- Summary 和 Usage 不能为空；
- Run 必须非 nil；
- 总帮助按名称稳定排序；
- 回调收到命令名之后的原始参数；
- 回调按需使用独立 `flag.FlagSet`；
- 自定义命令默认是一次性离线任务，Runner 不自动获得 PID 锁或创建 Application；
- 普通 error 映射为 `ExitFailure`；
- 首版不允许业务自定义任意退出码，避免退出码契约失控；
- 首版不允许自定义命令向已运行进程发送在线控制消息。

## 11. panic 边界

M4 在以下边界执行 `recover`：

- Start Handler；
- 自定义命令回调；
- Runner 最外层调度。

规则：

1. panic 转为带原始 panic 值和 `runtime/debug.Stack()` 的本地错误；
2. 返回 `ExitFailure`；
3. M4 不初始化 M1 Logger，最外层可执行程序把该错误写到 stderr；
4. 已经获得 PID 锁的 start 仍必须停止控制 goroutine并释放文件；
5. recover 只保证命令进程完成资源回收，不保证发生 panic 的 Application 可以继续运行；
6. M12 接入后，Application 自己的异常隔离与受控停止仍按独立设计执行。

M4 不捕获 Go runtime 无法恢复的 fatal error，也不把普通 error 当成 panic 记录堆栈。

## 12. 错误语义

M4 复用：

```text
errs.CodeInvalidArgument
errs.CodeInvalidConfig
errs.CodeCanceled
errs.CodeDeadlineExceeded
errs.CodeInternal
```

建议新增两个最小错误码：

```text
CodeProcessAlreadyRunning
CodeProcessControlFailed
```

使用规则：

- 命令、AppName、Node 列表和 timeout 非法：`CodeInvalidArgument`；
- 配置目录不存在或不是目录：`CodeInvalidConfig`；
- 同 AppName 锁已被占用：`CodeProcessAlreadyRunning`；
- PID 目录、文件锁或停止请求文件操作失败：`CodeProcessControlFailed`；
- stop 等待超时：`CodeDeadlineExceeded`，同时返回 `ExitStopTimeout`；
- Handler 返回的错误保持原错误链；
- panic 转为 `CodeInternal`；
- “目标未运行”是幂等成功，不建立错误码。

错误消息必须包含 AppName 和清理后的控制路径，但不得包含环境变量值、Token、
业务配置内容或其他敏感数据。

## 13. 退出码

退出码固定为：

```text
0  成功、help、version、目标本来未运行
1  Start Handler 或自定义命令执行失败、panic
2  未知命令、参数错误、配置目录错误
3  重复启动或本地进程控制失败
4  stop 等待目标优雅退出超时
```

映射由当前内置命令的执行阶段决定，不把任意 `errs.CodeDeadlineExceeded` 都映射为 4。
例如 Start Handler 内部一次 Redis 超时仍是运行失败 1；只有 stop 等待锁释放超时才是 4。

最终可执行程序可以：

```go
func main() {
    os.Exit(run())
}
```

`run()` 必须先打印 Runner 返回的 error，并确保所有清理已经完成。除最终 `main` 外，
任何 Origin 库代码都不得调用 `os.Exit` 或 `log.Fatal`。

## 14. 资源与 goroutine 所有权

M4 start 最多创建一个控制 goroutine。

所有权规则：

- Runner 创建、取消并等待控制 goroutine；
- Runner 打开、锁定、同步、解锁并关闭 PID 文件；
- stop 命令创建停止请求文件，但不持有目标进程资源；
- Start Handler 拥有其创建的 Application 和全部业务资源；
- Handler 必须在返回前完成自己资源的关闭；
- Runner 不关闭 Handler 未显式交给它的资源；
- 参数校验或启动任一步失败时，按成功创建资源的逆序回滚；
- 所有 `Close`、取消和 unlock 路径必须允许安全的重复清理；
- Runner 返回后不得遗留控制 goroutine或打开文件。

控制轮询不是游戏工作协程，不进入 Service Runner，也不执行定时器、RPC 或业务回调。

## 15. 跨平台实现

建议目录：

```text
command/
├── command.go
├── runner.go
├── start.go
├── stop.go
├── help.go
├── process.go
├── error.go
├── command_test.go
├── process_test.go
└── internal/
    └── processlock/
        ├── lock.go
        ├── lock_unix.go
        ├── lock_windows.go
        └── lock_test.go
```

实际实现可以按职责合并文件，不为了目录外观创建空文件。

平台边界：

- `lock_unix.go` 使用 build tag 覆盖 M4 声明支持的 Linux 和 macOS；
- `lock_windows.go` 只包含 Windows 适配；
- 公共 `lock.go` 定义最小内部接口和平台无关错误分类；
- 不在业务逻辑中散落 `runtime.GOOS` 分支；
- 不依靠信号实现 `stop`，三个平台都使用相同停止请求文件语义；
- 不支持的平台在编译期明确失败，不提供“没有真实锁的空实现”。

## 16. 测试方案

### 16.1 单元测试

至少覆盖：

1. start、stop、help、version 的参数解析；
2. `-start`、`-stop`、`-help` 兼容别名；
3. 未知命令、无参数和多余位置参数；
4. AppName 合法、非法和长度边界；
5. NodeID 去空白、顺序保持、空项和重复项；
6. 默认及显式 config、pid-dir、timeout；
7. help 稳定排序和 BuildTime 条件显示；
8. version 空构建信息显示 `unknown`；
9. 自定义命令注册、帮助、执行和错误；
10. 内置名称冲突和非法注册；
11. Start Handler、自定义命令及最外层 panic 恢复；
12. 错误码与退出码不混淆。

### 16.2 文件与锁测试

至少覆盖：

1. 首次 start 获得锁并写入 PID；
2. 同 AppName 重复 start 被拒绝；
3. 不同 AppName 可以同时持有各自锁；
4. 正常释放和重复清理；
5. 遗留 PID 文件不阻止新 start；
6. 半写和非法 PID JSON 不影响锁判断；
7. PID 文件包含 PID、本地 RFC 3339 时间及数字时区；
8. start 清理陈旧 `.stop`；
9. 两个 stop 并发创建请求时保持幂等；
10. stop 获取到空闲锁后不改写 PID；
11. stop timeout 不删除请求文件或强杀目标；
12. 不可写 PID 目录、文件打开失败、lock/unlock/Sync 失败；
13. 控制 goroutine 正常取消并被等待；
14. 反复启停不泄漏文件句柄或 goroutine。

### 16.3 跨进程集成测试

文件锁必须使用真实独立进程验证，不能只用同进程 mutex 模拟。

按照工程测试目录规则，建立唯一必要的辅助程序：

```text
tests/helpers/commandprocess
```

辅助程序只用于：

- 启动并持有指定 AppName 锁；
- 把“已开始持锁”通过测试管道通知父测试；
- 等待 stop Context；
- 可配置立即退出、延迟退出或忽略取消；
- 验证异常退出后操作系统自动释放锁。

集成测试放在：

```text
tests/integration/command
```

至少覆盖：

1. 父进程 start，子进程重复 start 被拒绝；
2. stop 请求送达目标，目标 Handler 收到 Context 取消并退出；
3. stop 在目标释放锁后成功；
4. 目标未运行时 stop 成功；
5. 目标忽略取消时 stop 超时且目标继续运行；
6. 目标被测试进程异常终止后，锁可再次获得；
7. 请求创建与目标退出竞争不会误停下一次启动；
8. Windows、Linux 使用原生测试运行；
9. macOS 至少通过交叉编译；配置 macOS CI 后运行同一集成测试。

辅助程序是跨进程语义所必需，不放入 `testdata`，也不作为 example 发布。

### 16.4 竞态与性能

- 全部并发和控制 goroutine 测试执行 `go test -race`；
- 反复运行跨进程启停测试检查稳定性；
- 命令和进程控制不属于 RPC 热路径，不要求纳秒级 Benchmark；
- 保存 AppName 校验、Node 列表解析和 help 生成的基础 Benchmark，用于防止明显退化；
- 不为低频 CLI 路径引入对象池、BufferPool、`unsafe` 或复杂缓存。

## 17. 明确不实现

M4 不实现：

- Application、Node、Service 或 Module；
- 配置文件内容解析和业务配置模型；
- Node 启停和倒序回收；
- Service 退休；
- SIGINT、SIGTERM 与 Application Stop 的最终汇合；
- Service 排空、`OnStop`、Await、Timer 和日志关闭；
- 在线管理控制台、HTTP 控制端口或本地 Socket 控制协议；
- 强制 Kill；
- 自定义在线命令；
- 命令自动补全、交互式 Shell、彩色 UI 和多语言帮助；
- PID 身份认证、Token 和远程控制；
- NFS、SMB 等共享文件系统进程协调；
- daemonize、后台启动和自动重启；
- pprof、日志级别及业务配置的命令行覆盖；
- 任意自定义退出码；
- 包级全局 Runner、注册表或 `init()` 注册。

## 19. 验收标准

1. M4 只新增独立命令与本地进程控制库，不引入 Application 实现；
2. Runner 不使用 `flag.CommandLine`、可变包级注册表或 `init()`；
3. 一个命令行只执行一个主命令；
4. `start` 通过 Start Handler 获得完整参数，并同步运行到 Handler 返回；
5. 同 AppName 重复 start 被文件锁可靠拒绝；
6. PID 文件只保存 PID 和带本地时区偏移的启动时间；
7. PID 内容损坏或 PID 复用不会影响运行状态判断；
8. stop 在 Windows、Linux、macOS 使用相同请求语义，不默认强杀；
9. stop 未运行幂等成功，运行中可送达，超时不取得目标资源所有权；
10. 控制 goroutine、锁和文件句柄具有唯一所有者并完整回收；
11. help、version 和参数错误不初始化日志、配置或 Application；
12. 自定义离线命令实例隔离、稳定排序且 panic 可恢复；
13. 错误码和退出码稳定，库不调用 `os.Exit` 或 `log.Fatal`；
14. 跨进程测试验证真实文件锁、停止送达、异常退出释放和超时；
15. 单元测试、集成测试、竞态检查和三平台构建通过；
16. 只新增已确认的 `x/sys` 固定版本依赖；
17. M4 不顺带实现 M7 或 M12 能力。

## 20. 与早期详细设计的调整

本里程碑设计从
[程序命令与进程控制设计](../details/2026-07-25-程序命令与进程控制设计.md)
裁剪 M4 范围，并作以下优化：

1. M4 不直接依赖 M1 日志，CLI 低频路径使用注入的 stdout/stderr；
2. M4 不直接调用 M3 加载配置，只把配置目录交给 Start Handler；
3. 只需要一个 Start Handler；stop 的本地请求和等待由 M4 自己完成，不再增加重复的
   Stop Handler 抽象；
4. stop 外部等待默认建议独立使用 `30s`，不再假设它能读取 Application 内部 Deadline；
5. version 首版不输出尚未定义的 RPC 协议版本；
6. 明确 PID 文件不能通过 rename 原子替换，以免锁对象与路径分离；
7. 明确跨进程测试辅助程序与普通单元测试、example 的目录边界；
8. 明确 `x/sys` 是跨平台文件锁的唯一新增依赖候选。

早期详细设计仍保存完整讨论背景；M4 实施时以开发者最终确认后的本文件为范围门禁。
