# Origin 第三版 M4 程序命令与进程控制库设计

> 文档状态：已实现并通过验收
> 创建日期：2026-07-26
> 最后更新：2026-07-26

## 1. 目标

M4 实现一个独立、可测试的程序命令与本地进程控制库，负责：

- 提供 `start`、`stop`、`help`、`version` 内置命令；
- 保留 v2 常用命令名称和首参数兼容入口；
- 允许注册一次性自定义离线命令；
- 通过必填 `--app-name` 标识当前 Application 进程；
- 使用 PID 文件独占锁防止同名进程重复启动；
- Linux、macOS 和 Kubernetes 使用标准进程信号传递优雅停止意图；
- Windows 普通控制台使用本地停止请求文件补足 Go 无法跨进程发送 Interrupt 的限制；
- 通过可注入的 Start Handler 验证完整启停闭环；
- 返回稳定退出码和错误，不在库代码中终止进程。

M4 只解决“怎样启动一个进程、怎样请求它停止、怎样把启动参数交给上层”。
它不认识 Application、Node、Service、Module、RPC 和服务发现的内部实现。

完成 M4 后，M7 可以把最小 Application 生命周期接入 Start Handler；M14 再把
Service 排空、`OnStop`、日志关闭等完整优雅停止流程接入同一停止意图。

## 2. 前置依赖与边界

### 2.1 直接依赖

M4 直接依赖：

- M0 的 Go module、Go 1.26.5、`buildinfo`、`errs` 和质量门禁；
- Go 标准库；
- 一个固定版本的 `golang.org/x/sys`，只用于 Windows、Linux 和 macOS 文件锁适配。

固定依赖版本：

```text
golang.org/x/sys v0.47.0
```

选择 `x/sys` 而不是自己维护原始系统调用的原因：

1. Go 标准库 `syscall` 已冻结，官方建议新代码优先使用 `golang.org/x/sys`；
2. Windows 需要 `LockFileEx`/`UnlockFileEx`，Unix 需要 `flock`，自行维护常量、
   结构体布局和系统调用会明显增加跨平台代码量及错误风险；
3. `x/sys` 由 Go 项目维护，M4 只使用很小的文件锁 API，不引入 CLI 框架或运行时服务。

参考：

- [Go syscall 包说明](https://pkg.go.dev/syscall)；
- [golang.org/x/sys](https://pkg.go.dev/golang.org/x/sys)；
- [Windows LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)；
- [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html)。

### 2.2 不直接依赖

M4 不直接依赖：

- M1 日志库；
- M2 BufferPool；
- M3 配置目录加载；
- Application、Node、Service、Module 或调度器；
- TCP、NATS、Protobuf、RPC 或服务发现；
- Cobra、urfave/cli 或其他第三方 CLI 框架。

`start --config` 只把清理后的配置目录传给 Start Handler。配置内容的读取、强类型解码
和业务校验由以后接入的 Handler 调用 M3 完成。命令层不定义或复制 Application 配置模型。

`help`、`version`、参数错误和进程控制错误直接使用注入的标准输入输出。M4 不为几个
低频命令初始化异步日志系统，也不会让日志失败阻止 `stop` 请求。

## 3. v2 对照与重构重点

v2 的 `console` 和 `node` 包提供了 `-start`、`-stop`、`-retire`、`-help`、
配置路径、日志参数、pprof 参数和自定义回调。v3 保留使用者熟悉的主要动作名称，
但不复制其代码。

v2 当前存在以下问题：

1. 使用包级 `flag.CommandLine` 和全局命令列表，多个实例及测试之间容易互相污染；
2. 一次命令行可以出现多个主动作，实际执行顺序依赖注册顺序；
3. `start` 被特殊推迟到其他 flag 之后执行，Command 与 Option 概念混合；
4. PID 文件名包含 `os.Args[0]` 和 NodeID，不适合一个 Application 管理多个 Node；
5. PID 文件使用 `O_TRUNC` 直接覆盖，并发启动存在竞争窗口；
6. 只比较 PID 和进程名，PID 复用时可能误判；
7. Windows 的停止退化为强制 Kill，无法执行统一优雅停止；
8. 多处库代码直接调用 `os.Exit`；
9. 打开 PID 文件失败后仍可能对 nil 文件执行 `Close`；
10. 命令回调没有实例级输入输出和清晰的 panic 边界。

M4 的重构方向：

- Command Runner 实例持有注册表，不使用可变包级状态；
- 一个进程命令只执行一个主动作；
- AppName 标识 Application 进程，NodeID 只表示本次选择启动哪些 Node；
- 操作系统文件锁是“是否正在运行”的唯一判定依据，PID 数字只供诊断；
- 各平台使用自己的标准控制入口，但统一取消同一个 Run Context，不默认强杀；
- 库返回 `error` 和退出码，最终 `main` 决定是否 `os.Exit`。

## 4. 命令外观

正式外观使用子命令：

```text
game-server start --app-name game-dev --config ./config --node gateway-1,game-1
game-server stop --app-name game-dev
game-server help
game-server help start
game-server version
```

规则：

1. 第一个参数是唯一主命令；
2. `start`、`stop`、`help`、`version` 是内置保留名；
3. 无参数时显示简短帮助，并返回参数错误；
4. `-h`、`--help` 和首参数 `-help` 归一为 `help`；
5. 首参数 `-start`、`-stop` 分别作为 `start`、`stop` 的 v2 兼容别名；
6. 不兼容 v2 的 `-start nodeid=...` 字符串参数，v3 使用独立的 `--node`；
7. 内置长参数统一使用小写 kebab-case；
8. 带值参数接受 `--name value` 和 `--name=value`；
9. 不为 `--app-name`、`--config`、`--pid-dir`、`--node` 增加含义容易冲突的短别名；
10. 内置参数使用各自独立的 `flag.FlagSet` 和 `flag.ContinueOnError`，不接触
    `flag.CommandLine`。

正式文档、构建脚本和示例工程只使用无前缀子命令。兼容别名只降低 v2 迁移成本，
不继续扩展新功能。

## 5. 内置命令

### 5.1 start

```text
game-server start \
  --app-name game-dev \
  [--config ./config] \
  [--pid-dir ./run] \
  [--node gateway-1,game-1]
```

参数规则：

- `--app-name` 必填；
- `--config` 默认 `./config`，只表示目录；
- `--pid-dir` 默认 `./run`，相对于命令启动时的操作系统当前工作目录解析；
- `--node` 使用逗号分隔一个或多个 NodeID；
- NodeID 去除两侧空白后不能为空；
- 同一次命令中的重复 NodeID 是参数错误；
- NodeID 顺序保持与命令行一致，后续作为 Application 的启动顺序；
- 未传 `--node` 时传递空切片，由以后接入的 Application 按配置中顶层 `nodes`
  声明顺序启动全部 Node；
- 停止顺序不由 M4 计算，M7/M14 按最终启动顺序倒序停止。

M4 在调用 Handler 前完成：

1. 解析并校验命令参数；
2. 清理并绝对化配置目录与 PID 目录；
3. 确认配置路径存在且是目录，但不读取其中的配置文件；
4. 创建并校验 PID 目录；
5. 获得 AppName 对应的进程独占锁；
6. Windows 普通控制台清除同 AppName 的陈旧停止请求文件；
7. 在锁保护下写入 PID 诊断记录并 `Sync`；
8. 建立当前平台的停止通知监听；只有 Windows 普通控制台需要启动文件监听 goroutine；
9. 同步执行 Start Handler。

Start Handler 返回后，M4 按逆序：

1. 停止并等待控制 goroutine 退出；
2. 释放 PID 文件锁并关闭文件；
3. 返回 Handler 的执行结果。

Start Handler 必须同步运行到上层 Application 已经完全结束。Handler 返回即表示 M4
可以释放同 AppName 的进程占用权。

### 5.2 stop

```text
game-server stop \
  --app-name game-dev \
  [--pid-dir ./run] \
  [--timeout 30s]
```

规则：

- `--app-name` 必填；
- `--pid-dir` 默认 `./run`，相对于 stop 命令启动时的操作系统当前工作目录解析；
- `stop` 不读取 `--config`，也不初始化业务配置；
- `--timeout` 是 stop 命令等待目标进程释放占用权的最长时间；
- 首版默认 `30s`；
- `--timeout` 使用 Go `time.ParseDuration` 风格，必须大于零；
- 目标未运行时返回幂等成功，并向 stdout 输出 `not running`；
- Linux/macOS 目标运行时读取受锁保护的 PID 记录并发送 `SIGTERM`；
- Windows 普通控制台目标运行时原子创建停止请求文件；文件已存在表示已有停止请求；
- 发出请求后轮询 PID 文件锁，直到锁释放或等待超时；
- 等待超时只结束 stop 命令，不强制终止目标进程；Windows 也不删除目标仍可能处理的请求文件；
- PID 文件、锁、信号或 Windows 请求文件操作失败时返回进程控制错误。

`--timeout` 与 Application 内部优雅停止 Deadline 是两个不同概念：

- M4 的 timeout 只限制“调用 stop 的终端或脚本等待多久”；
- M14 的 Application Deadline 决定目标进程内部最多花多久排空和关闭；
- stop 命令不加载业务配置，因此不能可靠复用 Application 的配置值；
- 使用者可以按部署环境通过 `--timeout` 把外部等待设置得比内部 Deadline 更长。

固定 `30s` 可以避免默认无限等待导致脚本永久挂住。该默认值已经通过 M4 开工 Review。

### 5.3 help

```text
game-server help
game-server help start
game-server --help
```

规则：

- 不读取配置；
- 不获得 PID 锁；
- 不创建控制 goroutine；
- 不初始化日志或 Application；
- 总帮助先显示内置命令，再按命令名排序显示自定义命令；
- 子命令帮助显示 Usage、Summary 和参数；
- 帮助写 stdout；
- 参数错误写入调用方返回的 error，由最终程序只打印一次；
- `buildinfo.BuildTime()` 非空时在帮助头部显示，为空时整行省略。

### 5.4 version

`version` 不初始化任何运行时资源，固定输出：

```text
version: v3.0.0
commit: abcdef123456
build_time: 2026-07-26T10:00:00+08:00
go_version: go1.26.5
```

规则：

- `version`、`commit`、`build_time` 使用 M0 `buildinfo`；
- `go_version` 使用 `runtime.Version()`；
- 未注入的字段输出 `unknown`，保持输出字段稳定；
- M4 不输出“协议版本”，因为 RPC 线协议要到 M11/M12 才定义；
- M12 确认协议版本后如确有运维需求，再独立增加字段。

### 5.5 retire

M4 不实现 `retire`。

Service 退休是在线运行时能力，需要携带 Node、Service 和动作语义，不能复用只表达
“停止整个 Application”的空请求文件。退休控制接口进入 M14 之后的独立里程碑再设计。

## 6. AppName 规则

一个 Application 可以管理多个 Node，因此进程控制不能再使用单个 NodeID 命名。

AppName 规则：

- start 和 stop 都必须显式传入 `--app-name`；
- 不从可执行文件名、配置目录、环境变量或第一个 NodeID 推导；
- 使用小写 kebab-case；
- 正则固定为 `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`；
- 最大长度固定为 63 个 ASCII 字符；
- 不允许路径分隔符、点、空白、连续中划线或末尾中划线；
- 同一 PID 目录中的 AppName 必须唯一；
- AppName 只用于本地进程控制和人工定位，不替代 NodeID，也不进入服务发现。

参数名继续使用 `--app-name`，不改成 `--appname`。项目的多单词长参数统一使用
kebab-case，`app-name` 能直接表达“Application 名称”是两个单词，也与
`--pid-dir` 等参数保持一致。首版不同时接受两种拼写，避免帮助、脚本和测试形成两套外观。

显式 AppName 会保留在进程命令行中，便于：

```text
ps ... | grep -- "--app-name game-dev"
```

所有平台都有 PID 文件；Windows 普通控制台另外使用停止请求文件：

```text
<pid-dir>/<app-name>.pid
<pid-dir>/<app-name>.stop  # 仅 Windows 普通控制台
```

`./run` 中的 `.` 是 start 或 stop 命令各自启动时的当前工作目录。Runner 在解析命令时
立即调用 `filepath.Abs` 固定为绝对路径；后续业务即使改变工作目录，也不会改变已经
打开的控制文件位置。start 与 stop 必须解析到同一个 PID 目录，因此生产环境应固定
进程工作目录，或者为两个命令显式传入相同的绝对 `--pid-dir`。默认值不改为可执行文件
所在目录，因为二进制目录在容器镜像和只读部署中经常不可写。

## 7. PID 文件与独占锁

### 7.1 PID 文件内容

PID 文件只保存诊断信息：

```json
{
  "pid": 12345,
  "started_at": "2026-07-26T10:00:00+08:00"
}
```

规则：

- `pid` 使用当前进程 PID；
- `started_at` 使用操作系统本地时区，与日志默认显示时区一致；
- 序列化格式使用 RFC 3339，并保留数字时区偏移，例如东八区写为 `+08:00`；
- 不保存 executable、address、token、state、Node 列表或业务配置；
- PID 内容不承担进程身份认证，也不是“是否正在运行”的判定依据；
- PID 文件正常退出后保留，便于诊断；下次获得锁后覆盖。

### 7.2 锁的语义

运行进程在整个 Start Handler 生命周期内持有 PID 文件的非阻塞独占锁：

- Linux/macOS 使用 `unix.Flock(fd, LOCK_EX|LOCK_NB)`；
- Windows 使用带 `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`
  的 `windows.LockFileEx`；
- Windows 锁定从 `4 GiB` 固定偏移开始的一个字节；操作系统允许锁定超过当前文件
  末尾的范围，因此不会扩容 PID 文件；
- Windows 不能锁定 PID JSON 实际占用的首字节，否则其他进程会因锁区冲突而无法读取
  PID 并发送停止通知；
- Unix 使用文件描述符关联的整文件 advisory lock；
- 锁释放同时执行显式 unlock 和 `Close`，任一步骤失败均保留错误；
- 进程异常退出时，操作系统关闭文件句柄并释放锁；
- 首版只支持本机磁盘，不承诺 NFS、SMB 或其他共享文件系统的锁语义。

文件权限建议：

- PID 目录在 Unix 创建为 `0750`；
- PID 文件在 Unix 创建为 `0600`；
- Windows 使用当前用户 ACL，Go FileMode 只作为兼容参数。

### 7.3 为什么不能用临时文件替换 PID 文件

进程锁绑定已打开的文件对象。获得锁后再用“临时文件 + rename”替换 PID 路径，
可能使锁仍属于旧文件，而其他进程从新路径打开了未锁定文件。

因此写 PID 记录时必须：

1. 先打开固定 PID 文件并获得锁；
2. 在同一个已锁定文件描述符上 `Truncate(0)`；
3. 从偏移零写入完整 JSON；
4. 执行文件 `Sync`；
5. 全生命周期不替换该路径对应的文件对象。

stop 命令不依赖 PID JSON 内容，因此崩溃造成的半写记录只影响人工诊断，不影响
运行状态判断或停止寻址。

## 8. 平台停止通知

公开命令外观保持一致：

```text
game-server stop --app-name game-dev
```

内部通知按平台实现，但全部只负责取消同一个 Start Handler Run Context：

```text
Linux/macOS       -> SIGTERM
Kubernetes        -> kubelet 直接发送 SIGTERM
Windows Service   -> SERVICE_CONTROL_STOP，进入后续部署集成
Windows Console   -> 当前控制台 os.Interrupt + 跨进程本地 .stop 请求文件
```

Linux、macOS 和 Kubernetes 不创建、不监听 `.stop` 文件，因此正式 Linux/Kubernetes
游戏服务器没有文件轮询开销。

### 8.1 Linux、macOS 和 Kubernetes

Unix stop 流程：

1. stop 命令检查 PID 文件锁确实被目标进程占用；
2. 在锁仍被占用的前提下读取并严格校验 PID 记录；
3. 使用 `SIGTERM` 通知该 PID；
4. 目标进程通过 `signal.NotifyContext` 取消 Start Handler Run Context；
5. stop 命令轮询 PID 文件锁，等待目标完成优雅关闭并释放运行权；
6. 等待超时只结束 stop 命令，不发送 `SIGKILL`。

Kubernetes 不需要执行 `game-server stop`。kubelet 直接向容器主进程发送 `SIGTERM`，
目标进程进入相同的 Run Context 取消路径；部署层的 Grace Period 决定何时由平台强制终止。

v3 统一使用标准 `SIGTERM`，不沿用 v2 自定义数字信号，便于 systemd、Kubernetes
和普通运维工具直接控制。

### 8.2 Windows 普通控制台方案

v2 Windows `stop` 调用 `os.Process.Kill()`，属于立即强杀，不会执行 Service 排空、
`OnStop`、玩家存档或日志关闭。v3 不复制这一行为。

仅 Windows 普通控制台使用停止请求文件：

```text
<pid-dir>/<app-name>.stop
```

规则：

1. stop 命令先检查 PID 文件锁确实被占用；
2. 使用 `O_CREATE|O_EXCL` 原子创建空请求文件；
3. 请求文件已存在按“已经请求停止”处理；
4. 目标进程的独立控制 goroutine 每 `100ms` 检查一次；
5. 检测到后先删除文件，再取消 Start Handler Run Context；
6. start 获得 PID 锁后、启动监听前先删除陈旧请求文件；
7. Handler 返回时取消并等待控制 goroutine，不能遗留 goroutine；
8. stop 仍通过等待 PID 锁释放确认目标真正关闭完成。

该方案比 v2 多一个平台文件、一个绝大多数时间挂起的 goroutine，以及对应竞争测试，
但实现边界局限在 `stop_windows.go`，不进入 Application、Service 或游戏工作协程。
它换取 Windows 开发环境也能验证真实优雅关闭和存档流程，收益高于复制 v2 强杀。

不采用 `fsnotify`、Named Pipe 或本地 TCP。对单个低频停止动作，`100ms` 文件检查更容易
验证和回收，也不需要增加第二个 IPC 协议或新的第三方依赖。

Windows Service 的 SCM 接入属于部署能力；进入相应里程碑后，把
`SERVICE_CONTROL_STOP` 映射到同一个 Run Context 取消函数，并可关闭控制台文件兼容入口。

### 8.3 关键竞争规则

所有平台共同处理：

- stop 确认锁占用后目标恰好退出：发送通知得到“进程不存在”时，再检查一次锁；
  锁已释放按停止成功处理；
- 两个 stop 同时执行：允许重复发送 `SIGTERM` 或重复表达 Windows 停止意图；
- stop 轮询时成功获得锁：立即释放该锁并返回停止完成，绝不能覆盖 PID 内容；
- stop 等待超时：不强杀目标，也不取得目标资源所有权。

Windows 另外处理：

- 请求文件可能在目标退出竞争中成为陈旧文件；下一次 start 获得锁后先删除；
- 两个 stop 同时创建请求时，只有一个创建成功，另一个把文件已存在视为幂等；
- 目标删除请求后仍在排空，第二个 stop 又创建文件：允许残留并由下次 start 清除；
- stop 等待超时不删除目标仍可能处理的请求文件。

### 8.4 start 防止重复启动的完整流程

以 `game-server start --app-name game-dev` 为例：

1. 根据 AppName 得到固定文件 `run/game-dev.pid`；
2. 打开或创建该 PID 文件；
3. 尝试获得非阻塞独占文件锁；
4. 第一个进程获得锁后，在整个 Start Handler 生命周期中一直持有该锁；
5. 第二个同名 start 可以打开文件，但不能获得独占锁，因此立即返回
   `CodeProcessAlreadyRunning` 和退出码 3；
6. 第二个进程不能截断或覆盖活动进程的 PID 记录，也不能创建 Application；
7. 第一个进程正常退出或异常终止后，操作系统释放锁；
8. 下次 start 即使看到遗留 PID 文件，只要能够获得锁，就可以安全覆盖旧诊断记录并启动。

重复启动的判定只依赖“同一个 PID 文件当前能否获得独占锁”，不依赖 PID 数字、
进程名或 PID 文件是否存在，从而避免 PID 复用和陈旧文件误判。

### 8.5 stop 控制运行进程的完整流程

以 `game-server stop --app-name game-dev` 为例：

1. stop 根据相同 AppName 和 PID 目录定位 `run/game-dev.pid`；
2. PID 文件不存在，或 stop 能够获得其独占锁，表示当前没有活动进程，按幂等成功返回；
3. stop 不能获得锁，表示 start 进程仍持有运行权；
4. Linux/macOS 发送 `SIGTERM`；Windows 普通控制台原子创建 `run/game-dev.stop`；
5. 目标进程通过信号监听或 Windows 控制 goroutine取消 Start Handler Run Context；
6. M7 接入真实 Application 后，公开 `app.Start()` 内部的 Start Handler 收到
   `ctx.Done()`，执行当前里程碑的 `OnStop` 和 Node 倒序停止；M14 再扩展为完整 Service
   排空和日志关闭；
7. Application 全部关闭后 Start Handler 返回，Runner 才释放 PID 文件锁；
8. stop 命令持续尝试获得该锁；成功获得后立即释放，并确认目标已完成退出；
9. 等待超过 `--timeout` 时 stop 返回退出码 4，但不强制 Kill 目标进程。

平台通知只负责传递一次“请优雅停止”的意图。真正的关闭工作始终在目标进程内执行，
因此底层传递方式不同，但 Application 看到的业务语义完全一致。

## 9. 公开包与 API 外观

### 9.1 包位置

公开包固定为：

```text
command
```

不继续使用 v2 的 `console` 名称，因为该包同时负责命令解析和本地进程控制，
并不表示日志控制台。

平台文件锁实现放在：

```text
command/internal/processlock
```

只允许 `command` 包使用，不向业务暴露锁句柄或控制文件操作。

### 9.2 核心类型

公开外观固定为：

```go
package command

type ExitCode int

const (
    ExitSuccess        ExitCode = 0
    ExitFailure        ExitCode = 1
    ExitUsage          ExitCode = 2
    ExitProcessControl ExitCode = 3
    ExitStopTimeout    ExitCode = 4
)

type StartRequest struct {
    AppName  string
    ConfigDir string
    PIDDir    string
    NodeIDs   []string
}

type StartHandler func(ctx context.Context, request StartRequest) error

type Options struct {
    ProgramName string
    Stdin       io.Reader
    Stdout      io.Writer
    Stderr      io.Writer
    Start       StartHandler
}

type Runner struct {
    // 仅包含未公开的实例状态。
}

func New(options Options) (*Runner, error)
func (runner *Runner) Register(command Command) error
func (runner *Runner) Run(
    ctx context.Context,
    args []string,
) (ExitCode, error)
```

字段对齐在实际代码中由 `gofmt` 决定，以上只表示 API 语义。

规则：

- `args` 传入 `os.Args[1:]`，不包含可执行文件路径；
- `ProgramName` 为空时使用当前可执行文件的 base name；
- nil stdin/stdout/stderr 分别使用 `os.Stdin`、`os.Stdout`、`os.Stderr`；
- `Start` 必须非 nil，构造时校验；
- `Runner` 不支持并发 `Register` 或并发 `Run`；
- `Run` 不调用 `os.Exit`；
- help、version 和正常状态由 Runner 写到注入输出；
- 普通失败作为 `error` 返回，由最外层程序向 stderr 只打印一次；
- `NodeIDs` 在交给 Handler 前复制，Handler 不得修改 Runner 内部参数状态。

### 9.3 Start Handler 运行期 Context 的原理

Runner 为每次 start 建立一个派生 Context：

- 调用方传入的 Context 取消时，派生 Context 取消；
- Linux/macOS 收到 SIGINT 或 SIGTERM 时，派生 Context 取消；
- Windows 普通控制台收到 `os.Interrupt` 或检测到停止请求文件时，派生 Context 取消；
- Windows Service 后续收到 SCM Stop 时，也取消同一个 Context；
- Handler 收到 `ctx.Done()` 后负责启动上层优雅停止；
- Runner 不假设 Context 取消后 Handler 会立即返回；
- Runner 必须一直持有 PID 锁，直到 Handler 实际返回。

`context.Context` 是 Go 进程内的取消通知对象，不会被序列化，也不会发送到另一个进程。
真正的跨进程桥梁是当前平台的停止通知：

```text
stop 命令进程
  -> Unix 发送 SIGTERM / Windows 创建 <app-name>.stop
  -> 目标进程的信号监听或 Windows 控制 goroutine收到通知
  -> 目标进程内调用 cancel()
  -> Start Handler 持有的 ctx.Done() 被关闭
  -> Application 开始优雅停止
```

核心原理等价于：

```go
runCtx, cancelRun := context.WithCancel(parent)

go waitPlatformStop(runCtx, cancelRun)

err := startHandler(runCtx, request)
cancelRun()
return err
```

以上代码只说明取消关系。实际实现还必须等待控制 goroutine 退出，并按逆序释放文件锁。

Start Handler 收到的 `runCtx` 表示 Application 的“运行期”，它被取消只表示应该开始停止。
已经取消的 `runCtx` 不能继续作为 `OnStop`、存档 RPC 或数据库写入的超时 Context，否则
这些收尾操作会立即得到 `context.Canceled`。真实 Application 在收到运行期取消后，
必须另外建立具有关闭 Deadline 的 Stop Context：

```go
<-runCtx.Done()

stopCtx, cancelStop := context.WithTimeout(
    context.Background(),
    applicationStopTimeout,
)
defer cancelStop()

return app.Stop(stopCtx)
```

因此这里存在两个职责不同的 Context：

- Run Context：表示“服务是否应该继续运行”，由 `.stop`、信号或进程内 Stop 请求取消；
- Stop Context：表示“优雅关闭最多还能执行多久”，供排空、`OnStop`、存档 RPC 和资源回收使用。

如果 stop 命令在另一台机器执行，必须先通过 SSH、Kubernetes exec 或其他运维通道在
目标主机/容器内运行 `game-server stop`。M4 不建立远程控制协议；Windows 在其他机器
本地创建同名 `.stop` 文件也不能通知目标进程。

M4 作为独立库的底层组合示例：

```go
runner, err := command.New(command.Options{
    ProgramName: "game-server",
    Start: func(ctx context.Context, request command.StartRequest) error {
        // M4 只把已经校验的请求交给上层；此处不规定 Application 公开 API。
        return runApplication(ctx, request)
    },
})
if err != nil {
    return 1
}

code, err := runner.Run(context.Background(), os.Args[1:])
if err != nil {
    fmt.Fprintln(os.Stderr, err)
}
return int(code)
```

M7 接入后，上述 Runner 和 Start Handler 由 Application 内部组合，最终业务程序不再重复
编写这段适配代码，只调用：

```go
app.Start()
```

M4 测试使用一个阻塞到 `ctx.Done()` 的假 Handler。M4 不创建假的 Application 类型。

## 10. 自定义离线命令

公开外观固定为：

```go
type Context struct {
    context.Context
    Stdin  io.Reader
    Stdout io.Writer
    Stderr io.Writer
}

type Command struct {
    Name    string
    Summary string
    Usage   string
    Run     func(ctx Context, args []string) error
}
```

注册示例：

```go
err := runner.Register(command.Command{
    Name:    "check-config",
    Summary: "检查配置但不启动服务",
    Usage:   "game-server check-config --config ./config",
    Run: func(ctx command.Context, args []string) error {
        flags := flag.NewFlagSet("check-config", flag.ContinueOnError)
        flags.SetOutput(ctx.Stderr)

        configDir := flags.String("config", "./config", "配置目录")
        if err := flags.Parse(args); err != nil {
            return err
        }

        var cfg ProjectConfig
        return config.LoadDir(*configDir, &cfg)
    },
})
```

规则：

- 注册表属于 Runner 实例；
- 注册在首次 `Run` 前完成；
- 名称使用与 AppName 相同的小写 kebab-case 语法；
- 空名称、重复名称和覆盖内置命令返回参数错误；
- Summary 和 Usage 不能为空；
- Run 必须非 nil；
- 总帮助按名称稳定排序；
- 回调收到命令名之后的原始参数；
- 回调按需使用独立 `flag.FlagSet`；
- 自定义命令默认是一次性离线任务，Runner 不自动获得 PID 锁或创建 Application；
- 普通 error 映射为 `ExitFailure`；
- 首版不允许业务自定义任意退出码，避免退出码契约失控；
- 首版不允许自定义命令向已运行进程发送在线控制消息。

## 11. panic 边界

M4 在以下边界执行 `recover`：

- Start Handler；
- 自定义命令回调；
- Runner 最外层调度。

规则：

1. panic 转为带原始 panic 值和 `runtime/debug.Stack()` 的本地错误；
2. 返回 `ExitFailure`；
3. M4 不初始化 M1 Logger，最外层可执行程序把该错误写到 stderr；
4. 已经获得 PID 锁的 start 仍必须停止控制 goroutine并释放文件；
5. recover 只保证命令进程完成资源回收，不保证发生 panic 的 Application 可以继续运行；
6. M14 接入后，Application 自己的异常隔离与受控停止仍按独立设计执行。

M4 不捕获 Go runtime 无法恢复的 fatal error，也不把普通 error 当成 panic 记录堆栈。

## 12. 错误语义

M4 复用：

```text
errs.CodeInvalidArgument
errs.CodeInvalidConfig
errs.CodeCanceled
errs.CodeDeadlineExceeded
errs.CodeInternal
```

新增两个最小错误码：

```text
CodeProcessAlreadyRunning = 6
CodeProcessControlFailed  = 7
```

使用规则：

- 命令、AppName、Node 列表和 timeout 非法：`CodeInvalidArgument`；
- 配置目录不存在或不是目录：`CodeInvalidConfig`；
- 同 AppName 锁已被占用：`CodeProcessAlreadyRunning`；
- PID 目录、文件锁、进程信号或 Windows 停止请求文件操作失败：`CodeProcessControlFailed`；
- stop 等待超时：`CodeDeadlineExceeded`，同时返回 `ExitStopTimeout`；
- Handler 返回的错误保持原错误链；
- panic 转为 `CodeInternal`；
- “目标未运行”是幂等成功，不建立错误码。

错误消息必须包含 AppName 和清理后的控制路径，但不得包含环境变量值、Token、
业务配置内容或其他敏感数据。

## 13. 退出码

退出码固定为：

```text
0  成功、help、version、目标本来未运行
1  Start Handler 或自定义命令执行失败、panic
2  未知命令、参数错误、配置目录错误
3  重复启动或本地进程控制失败
4  stop 等待目标优雅退出超时
```

映射由当前内置命令的执行阶段决定，不把任意 `errs.CodeDeadlineExceeded` 都映射为 4。
例如 Start Handler 内部一次 Redis 超时仍是运行失败 1；只有 stop 等待锁释放超时才是 4。

最终可执行程序可以：

```go
func main() {
    os.Exit(run())
}
```

`run()` 必须先打印 Runner 返回的 error，并确保所有清理已经完成。除最终 `main` 外，
任何 Origin 库代码都不得调用 `os.Exit` 或 `log.Fatal`。

## 14. 资源与 goroutine 所有权

M4 start 在 Windows 普通控制台最多创建一个文件控制 goroutine；Unix 使用信号通知，
不创建文件轮询 goroutine。

所有权规则：

- Runner 停止信号监听；Windows 另外创建、取消并等待文件控制 goroutine；
- Runner 打开、锁定、同步、解锁并关闭 PID 文件；
- Unix stop 命令发送 `SIGTERM`；Windows stop 命令创建停止请求文件；两者都不持有
  目标进程资源；
- Start Handler 拥有其创建的 Application 和全部业务资源；
- Handler 必须在返回前完成自己资源的关闭；
- Runner 不关闭 Handler 未显式交给它的资源；
- 参数校验或启动任一步失败时，按成功创建资源的逆序回滚；
- 所有 `Close`、取消和 unlock 路径必须允许安全的重复清理；
- Runner 返回后不得遗留控制 goroutine或打开文件。

Windows 控制轮询不是游戏工作协程，不进入 Service Runner，也不执行定时器、RPC
或业务回调。

## 15. 跨平台实现

建议目录：

```text
command/
├── command.go
├── runner.go
├── start.go
├── stop.go
├── help.go
├── process.go
├── stop_unix.go
├── stop_windows.go
├── error.go
├── command_test.go
├── process_test.go
└── internal/
    └── processlock/
        ├── lock.go
        ├── lock_unix.go
        ├── lock_windows.go
        └── lock_test.go
```

实际实现可以按职责合并文件，不为了目录外观创建空文件。

平台边界：

- `lock_unix.go` 使用 build tag 覆盖 M4 声明支持的 Linux 和 macOS；
- `lock_windows.go` 只包含 Windows 适配；
- 公共 `lock.go` 定义最小内部接口和平台无关错误分类；
- 不在业务逻辑中散落 `runtime.GOOS` 分支；
- Unix 使用 SIGINT/SIGTERM；Windows 普通控制台监听当前进程 `os.Interrupt`，并使用
  停止请求文件接收另一个命令进程的 stop；
- 各平台通知最终只调用同一个 Run Context 取消函数；
- 不支持的平台在编译期明确失败，不提供“没有真实锁的空实现”。

## 16. 测试方案

### 16.1 单元测试

至少覆盖：

1. start、stop、help、version 的参数解析；
2. `-start`、`-stop`、`-help` 兼容别名；
3. 未知命令、无参数和多余位置参数；
4. AppName 合法、非法和长度边界；
5. NodeID 去空白、顺序保持、空项和重复项；
6. 默认及显式 config、pid-dir、timeout；
7. help 稳定排序和 BuildTime 条件显示；
8. version 空构建信息显示 `unknown`；
9. 自定义命令注册、帮助、执行和错误；
10. 内置名称冲突和非法注册；
11. Start Handler、自定义命令及最外层 panic 恢复；
12. 错误码与退出码不混淆。

### 16.2 文件与锁测试

至少覆盖：

1. 首次 start 获得锁并写入 PID；
2. 同 AppName 重复 start 被拒绝；
3. 不同 AppName 可以同时持有各自锁；
4. 正常释放和重复清理；
5. 遗留 PID 文件不阻止新 start；
6. 半写和非法 PID JSON 不影响锁判断；
7. PID 文件包含 PID、本地 RFC 3339 时间及数字时区；
8. Windows start 清理陈旧 `.stop`；
9. Windows 两个 stop 并发创建请求时保持幂等；
10. stop 获取到空闲锁后不改写 PID；
11. stop timeout 不删除请求文件或强杀目标；
12. 不可写 PID 目录、文件打开失败、lock/unlock/Sync 失败；
13. 控制 goroutine 正常取消并被等待；
14. 反复启停不泄漏文件句柄或 goroutine。

### 16.3 跨进程集成测试

文件锁必须使用真实独立进程验证，不能只用同进程 mutex 模拟。

按照工程测试目录规则，建立唯一必要的辅助程序：

```text
tests/helpers/commandprocess
```

辅助程序只用于：

- 启动并持有指定 AppName 锁；
- 把“已开始持锁”通过测试管道通知父测试；
- 等待 stop Context；
- 可配置立即退出、延迟退出或忽略取消；
- 验证异常退出后操作系统自动释放锁。

集成测试放在：

```text
tests/integration/command
```

至少覆盖：

1. 父进程 start，子进程重复 start 被拒绝；
2. Unix SIGTERM 和 Windows `.stop` 请求都能送达目标，Handler 收到 Context 取消并退出；
3. stop 在目标释放锁后成功；
4. 目标未运行时 stop 成功；
5. 目标忽略取消时 stop 超时且目标继续运行；
6. 目标被测试进程异常终止后，锁可再次获得；
7. 请求创建与目标退出竞争不会误停下一次启动；
8. Windows、Linux 使用原生测试运行；
9. macOS 至少通过交叉编译；配置 macOS CI 后运行同一集成测试。

如果开发者提供可访问的 Linux 测试机，实施阶段可以通过 SSH 在该机器上执行原生
`go test`、竞态检查和跨进程集成测试。连接凭据不得写入仓库、脚本、日志或测试输出；
优先使用临时、最小权限的 SSH 公钥账号，不在对话或命令参数中传递长期密码。测试完成后
删除临时工作目录，并由开发者撤销临时账号或公钥。

辅助程序是跨进程语义所必需，不放入 `testdata`，也不作为 example 发布。

### 16.4 竞态与性能

- 全部并发和控制 goroutine 测试执行 `go test -race`；
- 反复运行跨进程启停测试检查稳定性；
- 命令和进程控制不属于 RPC 热路径，不要求纳秒级 Benchmark；
- 保存 AppName 校验、Node 列表解析和 help 生成的基础 Benchmark，用于防止明显退化；
- 不为低频 CLI 路径引入对象池、BufferPool、`unsafe` 或复杂缓存。

## 17. 明确不实现

M4 不实现：

- Application、Node、Service 或 Module；
- 配置文件内容解析和业务配置模型；
- Node 启停和倒序回收；
- Service 退休；
- SIGINT、SIGTERM 和 Windows 停止请求已经在 M4 汇合为 Run Context 取消，但真实
  Application Stop、Service 排空及退出结果集成不属于 M4；
- Service 排空、`OnStop`、Await、Timer 和日志关闭；
- 在线管理控制台、HTTP 控制端口或本地 Socket 控制协议；

## 19. 验收标准

1. M4 只新增独立命令与本地进程控制库，不引入 Application 实现；
2. Runner 不使用 `flag.CommandLine`、可变包级注册表或 `init()`；
3. 一个命令行只执行一个主命令；
4. `start` 通过 Start Handler 获得完整参数，并同步运行到 Handler 返回；
5. 同 AppName 重复 start 被文件锁可靠拒绝；
6. PID 文件只保存 PID 和带本地时区偏移的启动时间；
7. PID 内容损坏或 PID 复用不会影响运行状态判断；
8. Linux/macOS 使用 SIGTERM，Windows 普通控制台使用停止请求文件；外观一致且都不默认强杀；
9. stop 未运行幂等成功，运行中可送达，超时不取得目标资源所有权；
10. 信号监听、Windows 控制 goroutine、锁和文件句柄具有唯一所有者并完整回收；
11. help、version 和参数错误不初始化日志、配置或 Application；
12. 自定义离线命令实例隔离、稳定排序且 panic 可恢复；
13. 错误码和退出码稳定，库不调用 `os.Exit` 或 `log.Fatal`；
14. 跨进程测试验证真实文件锁、停止送达、异常退出释放和超时；
15. 单元测试、集成测试、竞态检查和三平台构建通过；
16. 只新增已确认的 `x/sys` 固定版本依赖；
17. M4 不顺带实现 M7 或 M14 能力。

## 20. 与早期详细设计的调整

本里程碑设计从
[程序命令与进程控制设计](../details/2026-07-25-程序命令与进程控制设计.md)
裁剪 M4 范围，并作以下优化：

1. M4 不直接依赖 M1 日志，CLI 低频路径使用注入的 stdout/stderr；
2. M4 不直接调用 M3 加载配置，只把配置目录交给 Start Handler；
3. 只需要一个 Start Handler；stop 的本地请求和等待由 M4 自己完成，不再增加重复的
   Stop Handler 抽象；
4. stop 外部等待默认独立使用 `30s`，不再假设它能读取 Application 内部 Deadline；
5. version 首版不输出尚未定义的 RPC 协议版本；
6. 明确 PID 文件不能通过 rename 原子替换，以免锁对象与路径分离；
7. 明确跨进程测试辅助程序与普通单元测试、example 的目录边界；
8. 明确 `x/sys v0.47.0` 是跨平台文件锁的唯一新增依赖。

早期详细设计仍保存完整讨论背景；M4 实施时以开发者最终确认后的本文件为范围门禁。

## 21. 开工 Review（已通过）

### 21.1 已由前序讨论确认

1. 使用正式子命令外观，并保留 v2 首参数兼容别名；
2. `--app-name` 必填，采用 Kubernetes 风格参数名，不改为 `--appname`；
3. `--config` 只指定目录；
4. `--node` 可以选择多个 Node，并按参数顺序启动；
5. 未指定 Node 时使用配置声明顺序，停止时倒序；
6. PID 文件名以 AppName 为准；
7. PID 内容只保存 PID 和操作系统本地时区的启动时间；
8. help 中 BuildTime 非空才显示；
9. 支持自定义离线命令；
10. library 不直接终止进程；
11. 真实 Application 接入不属于 M4；
12. `./run` 相对于命令启动时的当前工作目录，并在解析后固定为绝对路径；
13. Context 不跨进程传输；平台通知负责跨进程传递停止意图，目标进程在本地取消
    Start Handler 的 Run Context；
14. Linux、macOS 和 Kubernetes 使用标准 SIGTERM，不使用停止文件轮询；
15. Windows 普通控制台使用空 `.stop` 文件和 `100ms` 控制 goroutine 轮询，
    不复制 v2 的 `os.Process.Kill()` 强杀。

### 21.2 本轮 Review 已确认

1. 公开包名使用 `command`，不沿用 `console`；
2. Start Handler、Runner 和自定义 Command 采用第 9、10 节的 API 外观；
3. stop 外部等待默认值为 `30s`，且与 Application 内部关闭 Deadline 分离；
4. 文件锁固定引入 `golang.org/x/sys v0.47.0`，不自行维护原始系统调用；
5. AppName 使用 63 字符以内的严格小写 kebab-case；
6. PID 文件正常退出后保留，下次获得锁后覆盖；

8. 退出码固定为 0～4，自定义命令首版不能自定义其他退出码；
9. version 未注入字段显示 `unknown`，首版不显示 RPC 协议版本；
10. M4 直接依赖仅为 M0 和 `x/sys`；M1、M3 由以后接入的 Handler 按需使用；
11. M4 的跨进程测试辅助程序放入 `tests/helpers/commandprocess`，集成测试放入
