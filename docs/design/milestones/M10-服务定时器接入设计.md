> 文档状态：已实现并完成验收
>
> 适用里程碑：M10
>
> 前置里程碑：M0～M9
>
> 创建日期：2026-07-27
>
> 确认日期：2026-07-27

> 最后更新：2026-07-27

## 1. 里程碑目标

M10 在不建立第二套时间结构的前提下，把 M8 的 Node 时间轮内核和 M9 的 Service 单执行权
调度器连接起来，形成业务可以直接使用的定时器最小闭环：

1. 业务 Service 可以创建一次性、周期和 Cron Timer；
2. 到期只由 M8 交付内部 ID，任何业务回调都由 M9 Scheduler 串行执行；
3. Timer 回调可以使用 M9 `Await`，并保持同一 Service 同时只执行一个业务任务；
4. 业务只持有 `TimerID`，不持有内部对象；
5. 暂停、恢复、取消、过载和 Service 停止都有确定且可测试的语义；
6. 活跃 Timer、到期积压和内部对象数量全部有界；
7. 三百万活跃业务 Timer 场景具有明确的内存与延迟验收基线。

M10 只完成 Service Timer。它不借机实现 Module、RPC、服务发现、退休状态或完整优雅停止。

- [Origin v2 功能盘点与 v3 迁移矩阵](../../migration/第二版功能盘点与第三版迁移矩阵.md)。

M8 已经提供：

- 每个 Node 一个 10ms、五层×256 槽的 `TimerEngine`；
- 一次性内部 `DeadlineID`；
- 独立 `DeadlineQueue`、批量到期 ID 和容量为 1 的合并通知；
- 取消、批量关闭、内部 `timerEntry` 池和可注入时钟。

M9 已经提供：

- 每个 Service 一个 FIFO Ready 队列和唯一执行槽；
- 可增长但有硬上限的 `internal/container/ringqueue`；
- 普通 Runner 复用、Await 交接和恢复；
- 每个 Service 一个 Deadline 消费协程；
- Task Context、任务池和停止排空。

M10 只增加两者之间缺失的业务 Timer 容器、公开 API 和状态转换。

## 3. 范围

### 3.1 本里程碑实现

- `service.TimerID`、`service.TimerFunc` 和 `service.ITimer`；
- `IService` 直接组合 `ITimer`；
- `AfterFunc`、`NewTicker`、`CronFunc`；
- `PauseTimer`、`ResumeTimer` 和指针形式的 `CancelTimer`；
- Service 级 `TimerStats` 快照；
- Application Timer Options、Node 生命周期内唯一 TimerID 和活跃 Timer 总上限；
- OnStart 注册、启动完成后激活回调；
- 公开 TimerID 与 M8 DeadlineID 的映射；
- 到期回调进入 M9 Ready FIFO；
- Service 已满时的一次性回调保留和周期回调合并；
- Timer 容器专用对象池及防 ABA；
- Cron 5/6 段数字表达式和 Application 统一时区；
- Service 停止期间的 Timer 清理；
- Windows、Linux、macOS 构建与行为验证。

### 3.2 明确延后

- Module 树和 Module 独立 Timer 资源作用域；
- Service 退休/恢复接口；M10 只保证未来退休不会隐式操作 Timer；
- RPC、连接管理和服务发现的内部周期任务；
- 固定步长、补帧和游戏世界 Tick；
- 持久化 Timer、跨进程恢复和分布式 Timer；
- 动态修改 Node 时区；
- 单个 Cron 表达式自带时区；
- Cron 英文月份、英文星期、描述符和 `@every`；
- Timer 指标对 Prometheus 等外部系统的适配；
- M16 的 Stop Deadline、独占 finalizer 和 `OnStop` Await。

延后能力不在 M10 提前建立公开扩展接口。

## 4. 核心取舍

| 主题 | M10 建议 |
|---|---|
| 公开类型归属 | 全部放在现有 `service` 包，不新增只有少量类型的公开 `timer` 包 |
| 时间结构 | 只复用 M8 `TimerEngine`，不使用 `time.AfterFunc`、每 Timer goroutine 或第二个最小堆 |
| DeadlineQueue | 同一 Service 的 Await 和业务 Timer 共用 M9 已有 Queue 与消费协程 |
| 公开 ID | Node 生命周期内单调递增且不复用；`0` 永远无效 |
| 业务容器 | 每个 Service 自己保存 Map 和对象池，Node 只提供 ID 与总额度 |
| 调度 | 到期回调最终成为 M9 普通根任务，不建立第二个业务执行器 |
| 过载 | Ready 满时先留在有界“到期待准入 FIFO”，不丢一次性回调、不突破 `max_tasks` |
| 周期 | 固定节拍、错过合并、同一 Timer 永不重叠 |
| Cron | 引入固定版本的 `robfig/cron/v3`，只使用 Parser 和 `Schedule.Next` |
| 启动 | OnInit 不可创建 Timer；OnStart 可以创建，但回调要等 Service Running 后执行 |
| 停止 | 停止准入后取消未进入 Ready 的 Timer；已进入 Ready/Running/Waiting 的回调参与排空 |
| panic | 一次性 Timer 正常结束；NewTicker/Cron 连续 panic 未达到 99 次时继续触发 |
| Module | M10 不实现，也不预建 Module Scope 抽象 |

### 4.1 为什么复用同一 Service DeadlineQueue

详细设计储备曾按“Await、业务 Timer、RPC 分别使用 DeadlineQueue”描述隔离方式。结合 M9
已经实现的接口，M10 建议作一个范围内调整：

- Await 和业务 Timer 都归同一个 Service Scheduler；
- 两者到期后最终都只修改当前 Scheduler 的状态；
- 两者使用相同停止顺序、锁和 Deadline 消费批次；
- 再增加一条 Queue 和一个 goroutine 不能提供额外故障隔离，反而会增加每 Service 常驻资源。

因此，同一 Service 内复用现有 Queue 和 watcher，并为 Deadline Binding 增加内部种类：

- Await Binding：到期后取消 Await Context；
- Timer Binding：到期后把业务 Timer 转入待调度状态。

RPC Runtime、连接管理和服务发现仍必须使用各自独立的 DeadlineQueue，不能复用 Service
Queue。这样既保留组件隔离，也避免 Service 内部重复资源。

## 5. 公开 API

### 5.1 类型与接口

公开类型放在 `service` 包：

```go
package service

type TimerID uint64

const InvalidTimerID TimerID = 0

type TimerFunc func(
    ctx context.Context,
    timerID TimerID,
)

type ITimer interface {
    AfterFunc(
        delay time.Duration,
        fn TimerFunc,
    ) TimerID

    NewTicker(
        interval time.Duration,
        fn TimerFunc,
    ) TimerID

    CronFunc(
        expression string,
        fn TimerFunc,
    ) (TimerID, error)

    PauseTimer(timerID TimerID) bool
    ResumeTimer(timerID TimerID) bool
    CancelTimer(timerID *TimerID) bool

    TimerStats() TimerStats
}
```

`IService` 直接组合：

```go
type IService interface {
    ITimer

    OnInit() error
    OnStart(ctx context.Context) error
    OnStop(ctx context.Context) error

    DispatchAsync(fn func(context.Context)) error
    Await(
        ctx context.Context,
        fn func(context.Context) error,
    ) error
    SetDefaultAwaitTimeout(timeout time.Duration) error
    ExecutionStats() ExecutionStats

    baseService() *Service
}
```

不增加 `Timers()`、`TimerManager()` 或公开 Timer 对象，业务仍直接使用 `s.AfterFunc(...)`。

### 5.2 使用外观

```go
type PlayerService struct {
    service.Service

    saveTimer service.TimerID
}

func (s *PlayerService) OnStart(
    _ context.Context,
) error {
    s.saveTimer = s.NewTicker(
        30*time.Second,
        func(
            ctx context.Context,
            timerID service.TimerID,
        ) {
            var snapshot PlayerSnapshot
            err := s.Await(
                ctx,
                func(waitCtx context.Context) error {
                    var err error
                    snapshot, err = s.repository.Load(
                        waitCtx,
                    )
                    return err
                },
            )
            if err != nil {
                s.Logger().Error(
                    "load player snapshot failed",
                    originlog.Error(err),
                )
                return
            }
            s.apply(snapshot)
        },
    )
    if s.saveTimer == service.InvalidTimerID {
        return errors.New("create save timer failed")
    }
    return nil
}

func (s *PlayerService) stopSaveTimer() {
    s.CancelTimer(&s.saveTimer)
}
```

Timer 回调收到的是新的 Origin Task Context。该 Context：

- 可以传给当前调用栈内的 `s.Await`；
- 可以派生给本次等待的 Redis、数据库、HTTP 或后续 RPC；
- 不能保存到回调返回之后；
- 不能交给其他 goroutine调用 Service 执行权 API。

## 6. 参数与失败语义

### 6.1 AfterFunc

- `delay < 0`：返回 `InvalidTimerID`；
- `delay == 0`：至少等到 M8 后续 Tick 和 M9 后续调度轮次，不能同步回调；
- `fn == nil`：返回 `InvalidTimerID`；
- Service 未进入可注册阶段、已经停止准入或 Node Timer 额度已满：返回
  `InvalidTimerID`；
- 创建成功：返回非零且不会复用的 TimerID。

### 6.2 NewTicker

- `interval <= 0`：返回 `InvalidTimerID`；
- 小于 10ms 的正周期允许创建，但受 M8 10ms 基础精度量化，不承诺亚 10ms 触发；
- 其他失败语义与 `AfterFunc` 一致。

M10 不静默把非法周期改成 10ms，避免掩盖配置错误。

### 6.3 CronFunc

- 表达式或回调无效：返回 `InvalidTimerID` 和 `CodeInvalidArgument` 错误；
- Cron 使用 Application 创建时已经冻结的 Location，不在注册热路径加载时区文件；
- Service 状态或 Timer 额度导致的创建失败返回对应 Origin error；
- 成功时返回非零 ID 和 `nil`。

`AfterFunc`、`NewTicker` 保留已经确认的简洁单返回值外观；调用方通过 `id == 0` 判断失败。
框架同时记录拒绝统计并使用限频聚合日志，不能为每次拒绝同步写日志。

### 6.4 与 v2 的命名对齐

M10 保留 v2 已经清晰且常用的名称，但不复制重复或含义模糊的接口：

| v2 外观 | v3 外观 | 结论 |
|---|---|---|
| `AfterFunc` / `SafeAfterFunc` | `AfterFunc` | 保留规范名称，删除重复的 `Safe` 前缀 |
| `NewTicker` / `SafeNewTicker` | `NewTicker` | 与 v2 和 Go `time.NewTicker` 命名一致 |
| `CronFunc` / `SafeCronFunc` | `CronFunc` | 保留规范名称 |
| `CancelTimerId` | `CancelTimer` | 参数类型已经说明是 TimerID，不重复增加 `Id` 后缀 |
| 无 | `PauseTimer` / `ResumeTimer` | v3 新增能力 |

v2 的 `Safe` 同时表达过“返回内部 Timer 对象”和“使用 ID 管理”两套不同外观，且部分方法
已经标记 Deprecated。v3 全部只返回 TimerID，内部状态统一由 Scheduler 裁决，不再需要
`Safe` 区分。

v3 只对齐清晰的使用习惯，不机械复制 v2 参数：

- 创建函数直接返回 TimerID，不再通过第一个指针参数回写；
- 只有 `CancelTimer(*TimerID)` 使用指针，以便取消后统一清零；
- 不返回 `*Timer`、`*Ticker` 或 `*Cron` 内部对象；
- 不保留 `AdditionData interface{}`，业务直接使用类型安全的闭包捕获所需数据；
- 回调统一增加 Origin Task Context，使其中可以安全使用 Await。

## 7. Application Timer Options

### 7.1 默认无需设置

普通项目不在 YAML/JSON 的 Node 配置中增加 `timer` 段：

```yaml
nodes:
  - id: game-1

    services:
      - PlayerService
```

Application 使用稳定默认值：

```text
每个 Node 的最大业务 Timer 数 = 3000000
Cron 时区                    = time.Local
```

默认值不会按三百万预分配内存，只是运行时额度上限。绝大多数项目不需要了解或设置这两个值。
默认 Cron 时间完全跟随进程看到的 `time.Local`；如果 Kubernetes 容器实际使用 UTC，那么
Cron 也按 UTC 计算。只有业务明确要求固定地区时间且部署环境不能保证本地时区时，才需要
设置 Location。

### 7.2 特殊场景使用 Application Options

公开 Options 建议为：

```go
package application

type TimerOptions struct {
    // MaxTimersPerNode 为每个 Node 的业务 Timer 总额度。
    // 零值使用 3000000。
    MaxTimersPerNode int

    // Location 为 Cron 使用的时区。
    // nil 使用创建 Application 时的 time.Local。
    Location *time.Location
}

type Options struct {
    StartTimeout      time.Duration
    StopTimeout       time.Duration
    LogHandlerFactory LogHandlerFactory
    Timer             TimerOptions
}
```

特殊项目才显式设置：

```go
location, err := time.LoadLocation("Asia/Shanghai")
if err != nil {
    return err
}

app := application.New(
    application.Options{
        Timer: application.TimerOptions{
            MaxTimersPerNode: 2000000,
            Location:         location,
        },
    },
)
```

`MaxTimersPerNode` 是每个 Node 全部 Service 合计的活跃业务 Timer 上限：

- 负值无效；
- 零值表示使用默认值，不表示禁止 Timer 或无限；
- 显式非零值必须大于零；
- 只作为额度，不按该数值预分配对象或 Map；
- Scheduled、Paused、DuePending、Ready、Running 和 Awaiting Timer 都占用额度；
- Timer 完成或完全取消且已脱离所有队列后才归还额度；
- Await、RPC Deadline 和 M8 内部系统 Deadline 不占用该业务额度；
- Options 的有效值就是当前 Node 的资源硬边界，不再增加一个难以解释的框架绝对最大值。

默认三百万用于满足 MMO 单 Node 大量玩家定时任务的目标；真实项目可以按 Node 类型调低。
同一 Application 的所有 Node 使用相同上限，但每个 Node 独立计数，保证单进程多 Node 和
生产环境单 Node 进程具有一致行为。

`Location` 规则：

- `nil` 使用创建 Application 时的 `time.Local`；
- `time.UTC`、`time.FixedZone` 和 `time.LoadLocation` 返回值都可以直接传入；
- 时区在 Node 创建后保持只读；
- Origin 使用标准库 `time/tzdata` 提供内嵌 IANA 数据，避免精简容器缺少系统时区文件；
- Node 启动日志记录最终时区名称，不为每次 Cron 注册重复输出。

M10 不允许表达式内使用 `TZ=` 或 `CRON_TZ=` 覆盖 Application Location，保持一套统一规则。
若未来出现同一 Application 内不同 Node 必须使用不同时区的真实需求，再单独增加 Node
覆盖；M10 不提前增加双重配置优先级。

## 8. 生命周期接入

### 8.1 为什么 OnStart 必须能够注册 Timer

初始化心跳、存档、排行榜刷新等周期任务通常发生在 `OnStart`。如果只能在 Service Running
后创建，业务还要额外投递一个启动任务，使用比 v2 更复杂。

M10 因此把 M9 Scheduler 的框架装配拆成两个内部阶段：

1. `PrepareScheduler`：创建 Ready、DeadlineQueue 和 Timer 状态，但不运行用户任务；
2. `ActivateScheduler`：Service `OnStart` 成功且状态发布为 Running 后启动 Runner 和
   Deadline watcher。

这两个函数是 `node` 包使用的框架装配边界，不加入业务接口。

### 8.2 Node 启动顺序

每个 Node 使用以下顺序：

1. 所有 Service 按配置顺序完成 `OnInit`；
2. 启动 Node `TimerEngine`；
3. 为当前 Service Prepare Scheduler 和 Timer 资源；
4. 把当前 Service 记入实际进入 OnStart 的停止序列；
5. 调用 `OnStart(ctx)`；
6. OnStart 成功后把 Service 状态发布为 Running；
7. Activate Scheduler；
8. 继续启动下一个 Service；
9. 全部成功后发布 Node Ready。

OnStart 中允许：

- 创建、暂停、恢复和取消 Timer；
- 查询 `TimerStats`。

OnStart 中仍不允许：

- 使用 `DispatchAsync` 提前执行普通业务根任务；
- 使用通用 `Await`；OnStart 生命周期 Await 留在 M14；
- 让 Timer 回调与 OnStart 并发执行。

在 OnStart 期间已经到期的 Timer 只积累内部到期 ID。Activate 后按到期顺序转入 Service
调度，绝不与 OnStart 并发。

### 8.3 启动失败

- Prepare 失败：当前 Service 尚未进入 OnStart，不调用它的 OnStop；
- OnStart 失败：停止当前 Prepared Scheduler、取消其全部 Timer，然后按现有规则调用
  OnStop；
- Activate 失败：视为当前 Service 启动失败，执行同样的反序回滚；
- 任一 Service 启动失败：Application 停止之前已经启动的其他 Node。

Timer 清理失败必须加入原始启动错误，不能覆盖真正的根因。

## 9. 公开 Timer 与内部 Deadline 的映射

每个 Service Scheduler 保存：

```text
TimerID -> businessTimer
DeadlineID -> deadlineBinding
```

一个 `businessTimer` 至少保存：

- Node 唯一 TimerID；
- 当前内部 DeadlineID；
- Deadline generation；
- Timer 类型；
- 当前状态；
- 回调；
- 周期或 Cron Schedule；
- 下一名义触发时间；
- 暂停剩余时间；
- 当前是否已经存在 Ready/Running Task；
- 池化与队列所有权字段。

暂停、恢复、周期重排和 Cron 重排可以产生新的 DeadlineID，但不改变 TimerID。

Deadline Binding 必须同时校验：

- Binding 种类；
- Timer 指针；
- TimerID；
- generation；
- 当前 DeadlineID；
- Timer 当前状态。

因此，迟到的旧 DeadlineID 不能触发已经恢复、重排或池化复用后的 Timer。

## 10. Timer 状态

M10 只使用一个明确枚举表达 Timer 的唯一主状态：

| 状态 | 含义 |
|---|---|
| Scheduled | 已登记内部 Deadline，尚未到期 |
| DuePending | 已到期，但因 `max_tasks` 暂不能进入 Ready |
| Ready | 回调已经进入 M9 Ready FIFO |
| Running | 回调持有 Service 执行权，或因 Await 挂起但尚未完整返回 |
| Paused | 保留业务 Timer，但没有未来 Deadline 或可执行回调 |
| Completed | 一次性 Timer 自然完成，等待统一回收 |
| Canceled | 已取消，等待脱离可能存在的内部任务引用后回收 |

周期 Timer 在 Running 状态下还允许设置：

- `pauseAfterRun`：当前回调结束后进入 Paused；
- `cancelAfterRun`：当前回调结束后清理，不再安排下一次。

不使用多个互相矛盾的布尔字段重复表示同一个主状态。

## 11. 到期、Ready 与过载

### 11.1 正常投递

Timer Deadline 到期后：

1. M8 把 DeadlineID 放入当前 Service 的 DeadlineQueue；
2. M9/M10 共用 watcher 分批 Drain；
3. watcher 通过 Binding 找到 `businessTimer`；
4. Timer 从 Scheduled 转为 DuePending；
5. Scheduler 有任务额度时，把 Timer 转为一个内部 Timer Task；
6. Timer Task 进入现有 Ready FIFO；
7. Runner 取得唯一执行权后才调用用户回调。

Timer Task 和普通根任务使用相同 Task Context、Await、panic 边界和完成计数。

### 11.2 max_tasks 已满

M10 不能同时承诺“Ready 硬上限”和“所有到期 Timer 立即进入 Ready”。采用以下确定规则：

- 已到期但暂时没有任务额度的 Timer 进入每 Service 的 `DuePending` FIFO；
- FIFO 复用 `internal/container/ringqueue`，不重新实现队列；
- DuePending 最大数量不可能超过 Node 的 `MaxTimersPerNode` 额度，因此仍然有界；
- 每当一个根任务完成并释放额度，先把最早 DuePending Timer 转入 Ready；
- 接收新的 `DispatchAsync` 前也先提升已有 DuePending；
- 已经在 Ready 的普通任务不被 Timer 插队；
- 如果提升 Timer 后达到 `max_tasks`，新的 `DispatchAsync` 返回
  `ErrServiceQueueFull`；
- 取消或暂停的 DuePending 条目在出队时跳过，不创建无意义 Task；
- Stop 会批量清理尚未进入 Ready 的 DuePending。

这个额外 FIFO 保存轻量 `dueTimerEntry{timer, generation}`，不复制回调和业务数据。
`generation` 用于识别暂停、恢复和取消留下的旧条目，避免池化 Timer 的 ABA。它是任务准入
边界，不是第二个业务执行队列；真正用户代码仍只从 M9 Ready FIFO 执行。

### 11.3 一次性 Timer

- 到期后不能因 Ready 已满而丢弃；
- 到期顺序在 DuePending 和 Ready 两段中保持稳定；
- 允许因 Service 忙而延后执行；
- 回调完整返回或 panic 后自然完成并释放。

### 11.4 周期 Timer 合并

- 同一个 Ticker/Cron 最多存在一个 Scheduled、DuePending、Ready、Running 或 Waiting
  触发；
- 回调完整返回前不安排同一个 Timer 的下一 Deadline；
- 完成后按名义时间轴计算下一个未来点；
- Ticker 错过的多个固定节拍累计到 `CoalescedTotal`，不补执行历史次数；
- Cron 从当前墙上时间直接计算下一个未来匹配点，不遍历可能跨越数年的历史表达式，也不
  增加 `CoalescedTotal`；
- 因此周期 Timer 不会在 DuePending 中重复占位，也不会与自己重叠。

## 12. Timer Task 外观与分配

M10 在 M9 `serviceTask` 中增加内部任务种类：

- 普通 `DispatchAsync` Task；
- Timer Task；
- Await Recovery 仍是同一根 Task 的恢复项，不是新 Task。

Timer Task 保存 `*businessTimer`，不为每次触发再创建捕获 TimerID 和 callback 的闭包。
执行时：

1. 在 Scheduler 锁内裁决 Timer 是否仍允许开始；
2. 锁外调用 `TimerFunc(ctx, timerID)`；
3. 无论正常返回或 panic，都在统一完成路径更新 Timer；
4. 一次性 Timer 清理，周期 Timer 计算下一次 Deadline；
5. 清空 Task 对 Timer 的引用，再归还 M9 Task 池。

Timer callback 本身是业务提供的函数值，Origin 不尝试池化或复制它。

## 13. AfterFunc 语义

- 使用单调时间计算相对延迟；
- 小于 10ms 的正延迟向上量化，不提前触发；
- `delay == 0` 仍异步进入后续 Tick；
- Scheduled 时暂停保存剩余时间；
- DuePending/Ready 但尚未开始时暂停，剩余时间记为零；
- Running 后不能暂停或成功取消；
- 回调返回或 panic 后 TimerID 失效并释放额度。

业务变量中的旧非零 ID 不会由自然完成自动改写。再次控制该 ID 返回 `false`。只有
`CancelTimer(&id)` 可以直接把调用方变量清零。

## 14. NewTicker 语义

Ticker 使用固定节拍：

```text
名义触发点 = 首次创建时间 + N × interval
```

回调结束后，依据当前单调时间选择严格晚于当前时刻的下一个名义触发点。假设本次名义触发为
`T`，回调在 `Now` 完成：

```text
next = 第一个满足 T + N×interval > Now 的时间
```

中间跳过的触发累计到 `CoalescedTotal`，不创建补偿任务。

暂停规则：

- Scheduled：保存距离下一名义触发点的剩余时间；
- DuePending/Ready：暂停后阻止尚未开始的回调，剩余时间为零；
- Running/Waiting：当前回调继续，结束后保持暂停；
- Resume 后第一次触发使用保存的剩余时间；
- 之后重新按原 interval 建立固定节拍。

## 15. CronFunc 语义

### 15.1 表达式

支持：

- 5 段：`分 时 日 月 周`，秒默认为 `0`；
- 6 段：`秒 分 时 日 月 周`；
- 数字、`*`、`,`、`-`、`/`；
- 星期 `0`～`6`，`0` 表示星期日；
- 日和星期同时受限时沿用 v2/POSIX 的 OR 语义。

不支持：

- 英文月份和星期；
- `?`、`L`、`W`、`#`；
- `@daily`、`@every` 等描述符；
- 表达式内时区和 Year 字段。

M10 先严格检查字段数量和字符集合，再使用固定版本
[`github.com/robfig/cron/v3`](https://github.com/robfig/cron) 的 Parser 与
`Schedule.Next`。只复用表达式解析和下一时间计算，
不启动该库的 Cron Runner、goroutine、Timer 或日志器。

采用成熟 Parser 的原因：

- Cron 的日期边界、日/星期组合和夏令时比表面语法复杂；
- 自行复制 v2 Parser 会增加长期维护和时区缺陷风险；
- 该库是 MIT 许可、无运行时调度强绑定，允许只使用小范围 API；
- 依赖版本必须固定，并在实施计划中记录许可证、版本和生成结果。

建议固定当前稳定版本 `v3.0.1`。开工前再次核对模块版本，不跟随未发布提交。

### 15.2 墙上时钟变化

- 每次内部 Deadline 到期时重新读取当前墙上时钟；
- 系统时间向后调整且尚未到名义时间：重新计算剩余时长，不提前执行；
- 系统时间向前调整：最多执行当前应触发的一次，不补历史次数；
- 回调结束后只计算下一个未来匹配点；
- 暂停期间全部跳过，Resume 时从当前时间计算未来匹配点；
- 夏令时行为由 IANA Location 和 Cron Schedule 共同决定，并使用可控时钟测试边界。

## 16. Pause、Resume 与 Cancel

### 16.1 线性化

所有 Timer 主状态由所属 Scheduler 的同一互斥锁裁决。到期、开始回调、暂停、恢复、取消和
停止都在这个锁上形成可说明的先后顺序，用户回调始终在锁外执行。

### 16.2 PauseTimer

```go
PauseTimer(timerID TimerID) bool
```

- 零 ID、不属于当前 Service、已完成或已取消：返回 `false`；
- 已经暂停：返回 `false`；
- Scheduled、DuePending、Ready：成功阻止尚未开始的回调并返回 `true`；
- AfterFunc 已经 Running/Waiting：返回 `false`；
- Ticker/Cron 已经 Running/Waiting：标记 `pauseAfterRun` 并返回 `true`；
- Pause 不终止已经开始的回调，也不取消其 Await Context。

Pause 与回调开始竞争时，以 Scheduler 锁顺序为准。Pause 返回 `true` 就保证回调尚未开始，
或周期回调只完成当前这一轮。

### 16.3 ResumeTimer

```go
ResumeTimer(timerID TimerID) bool
```

- 只有 Paused 或 `pauseAfterRun` 尚未完成当前回调时具有恢复语义；
- 重复恢复和无效 ID 返回 `false`；
- After/Ticker 按保存的剩余时间恢复；
- 剩余时间为零时仍通过 M8 后续 Tick 异步触发；
- Cron 从当前墙上时间计算下一个未来匹配点；
- 对正在运行的周期回调取消 `pauseAfterRun` 后，当前回调完成时正常安排下一次。

### 16.4 CancelTimer

```go
CancelTimer(timerID *TimerID) bool
```

固定规则：

1. 参数为 `nil`：返回 `false`；
2. `*timerID == 0`：返回 `false`；
3. 读取原值后立即把调用方变量设为 `0`；
4. ID 不属于当前 Service、已完成或已经取消：返回 `false`；
5. Scheduled、DuePending、Ready、Paused：取消成功，回调不得再开始；
6. AfterFunc 已经 Running/Waiting：返回 `false`，不能强杀当前回调；
7. Ticker/Cron 已经 Running/Waiting：停止后续周期并返回 `true`，当前回调继续；
8. 所有非零 ID 调用结束后，调用方变量都保持为零。

第 7 条对详细设计储备作实用性修正：周期 Timer 必须允许在自己的回调中停止后续触发。
否则业务只能增加额外状态并在回调返回后从其他任务取消，既不直观也不兼容常见游戏逻辑。

调用方的 `TimerID` 变量不由 Origin 加锁。同一变量只能由 Service 执行上下文拥有，或由业务
自行同步；框架只保证内部 Timer 状态并发安全。

## 17. panic 处理

Timer 回调复用 M9 根任务 panic 边界：

- 捕获原始 panic 值和堆栈；
- 使用 `ErrorStack` 可靠记录 NodeID、ServiceName、TimerID 和 Timer 类型；
- Scheduler 继续处理后续任务；
- AfterFunc 自然完成并释放；
- NewTicker/Cron 增加当前 Timer 私有的连续 panic 计数；
- 连续 panic 少于 `99` 次时，仍按原周期规则安排下一次触发；
- 任意一次回调正常返回后，连续 panic 计数立即清零；
- 第 `99` 次连续 panic 后自动取消该 Timer 的后续触发并完整清理；
- Pause/Resume 不清零连续 panic 计数；
- 普通触发、panic 和达到上限取消分别计入 TimerStats。

`99` 是 M10 固定安全上限，不增加配置项。它让偶发 panic 不会永久关闭周期任务，同时保留
一个防止永远重复 panic 的最终边界。这里不是业务重试器：不增加独立退避、补执行或错误
回调；需要更复杂恢复策略的业务仍应在自己的 TimerFunc 内实现。

第 99 次回调本身已经开始执行；只有它再次 panic、连续计数达到 99 后，框架才停止安排
第 100 次及后续回调。

## 18. Service 停止与退休边界

### 18.1 Stop

Service 进入 Stopping 后：

1. `AfterFunc`、`NewTicker` 和 `CronFunc` 拒绝新增；
2. 取消 Scheduled 和 Paused Timer；
3. 清理尚未转入 Ready 的 DuePending；
4. 已经进入 Ready 的 Timer Task 属于 Stop 前已接受任务，继续按 FIFO 排空；
5. Running/Waiting Timer 回调继续执行；
6. NewTicker/Cron 当前回调结束后不再安排下一 Deadline；
7. Stop Context 到期时沿用 M9 规则取消 Task Context，但仍等待不响应 Context 的函数真实返回；
8. Scheduler 排空后关闭共用 DeadlineQueue 和 watcher；
9. 清空 Timer Map、DuePending FIFO、callback 和全部内部映射；
10. 最后进入 OnStop；OnStop 不能创建新 Timer。

已经到达 M8 DeadlineQueue、但还没有被 watcher 转入 Ready 的 ID，不属于业务排空集合。停止
会移除其 Binding 并清理 Timer；watcher 随后看到旧 ID 时直接忽略。

M16 只补充进程级停止 Deadline 和 finalizer，不改变上述 Timer 准入边界。

### 18.2 退休

Service 退休功能尚未实现。M10 不读取或修改退休状态。后续退休里程碑接入时固定保持：

- 退休只是可观察状态，框架不自动拒绝 RPC；
- Timer、Await、本地事件和所有普通任务继续；
- 业务需要时自行调用 PauseTimer/ResumeTimer。

## 19. 资源所有权与对象池

### 19.1 所有者

- Node 拥有 TimerEngine、TimerID 生成器和活跃 Timer 总额度；
- Service Scheduler 拥有业务 Timer Map、DuePending FIFO 和 Timer 容器池；
- DeadlineQueue 仍由 Scheduler 独占关闭；
- Timer Task 进入 Ready 后由 Scheduler 拥有；
- 业务只拥有 TimerID 值和自己的变量。

### 19.2 业务 Timer 容器池

业务 Timer 容器使用每 Scheduler 私有 `sync.Pool`：

- 不与 M8 `timerEntry` 池混用；
- 不作为容量控制；
- 每次取得后分配新的 Node TimerID；
- 只有脱离 Timer Map、Deadline Binding、DuePending、Ready、Running 和 Waiting 后才能回池；
- 释放前清空 callback、Cron Schedule、Scheduler、Task、ID、Deadline、时间、链路和状态；
- 旧 TimerID 永远不能控制池化后的新 Timer；
- 池统计默认关闭；Benchmark 仍要比较池化和不池化。

已经确认使用对象池，但若逃逸分析和 Benchmark 显示没有实际收益，必须把数据带回 Review，
不能为了形式保留复杂池化。

### 19.3 Node TimerID 与额度

Node 使用实例内原子计数：

- ID 从 1 单调增加；
- 使用 CAS 防止 `uint64` 回绕后重复；
- 达到最大值后永久拒绝当前 Node 的新 Timer；
- 活跃额度通过独立原子计数申请和归还；
- ID 生成与额度均不使用包级全局状态。

NodeID 唯一而 TimerID 只要求 Node 生命周期内唯一，不进入网络协议。

## 20. 可观测性

公开 `TimerStats` 建议包含：

```go
type TimerStats struct {
    Active     int
    Scheduled  int
    DuePending int
    Ready      int
    Running    int
    Paused     int

    ActiveHighWatermark int

    CreatedTotal            uint64
    RejectedTotal           uint64
    TriggeredTotal          uint64
    CompletedTotal          uint64
    CanceledTotal           uint64
    PausedTotal             uint64
    ResumedTotal            uint64
    CoalescedTotal          uint64
    PanicTotal              uint64
    PanicLimitCanceledTotal uint64

    LastReadyDelay time.Duration
    MaxReadyDelay  time.Duration
}
```

规则：

- 快照在 Scheduler 短锁内复制；
- 不在热路径维护直方图或字符串标签；
- P50/P95/P99 由后续指标适配层根据事件采样计算，M10 不内置重型指标库；
- `ExecutionStats.Accepted/Ready/Running/Awaiting` 继续统计实际根任务，其中包含已经进入
  M9 调度的 Timer Task；
- DuePending 尚未成为根任务，只进入 TimerStats；
- `CoalescedTotal` 只统计 NewTicker 跳过的固定名义节拍；Cron 跳过历史不做昂贵枚举；
- 无效 ID 控制只计数，不逐条打日志；
- panic 和额度耗尽使用限频聚合日志；连续 panic 的准确次数由统计保留。

## 21. Cron 依赖边界

M10 建议只新增：

```text
github.com/robfig/cron/v3
```

要求：

1. 固定已发布版本，不引用 branch、commit 或 fork；
2. 只调用 Parser 和 `Schedule.Next`；
3. 不创建该库的 `Cron` Runner；
4. Origin 自己负责 TimerID、M8 Deadline、Service Ready、暂停、停止和 panic；

- 是否开启 Race 或对象池统计。

Benchmark。M10 还要补充三百万内部 Deadline 的容量验证，确认默认业务额度不会超过底层
时间轮的可用范围。

## 24. 代码边界建议

预计职责如下，最终文件拆分在实施计划中确定：

```text
service/
  timer.go            公开类型、ITimer 和 Service 方法
  timer_options.go    运行时默认值和 Application Options 转换
  timer_runtime.go    业务 Timer 状态、Map、DuePending 和对象池
  timer_cron.go       严格表达式入口和 Schedule 适配
  timer_stats.go      统计快照
  scheduler.go        最小改造：Prepared/Active、Timer Task 和 Deadline Binding

node/
  node.go             TimerID、额度、Location 和生命周期装配

application/
  options.go          可选 TimerOptions，不增加 YAML/JSON 字段
```

不新增公开 `timer` 包，不把业务 Timer 逻辑塞入 `internal/timerwheel`。M8 仍只认识内部一次性
Deadline。

## 25. 对已有详细设计的建议调整

本轮已经把开发者明确确认的以下结论同步回
[定时器系统设计](../details/2026-07-23-定时器系统设计.md)：

1. 对外使用与 v2 规范外观一致的 `AfterFunc`、`NewTicker`、`CronFunc`；
2. 默认不增加 YAML/JSON Timer 配置，特殊场景使用 Application TimerOptions；
3. NewTicker/Cron 连续 panic 少于 99 次时继续，正常返回清零，第 99 次才取消。

其余已经随本次 M10 Review 一并确认：

1. 同一 Service 的 Await 与业务 Timer 共用一条 DeadlineQueue 和 watcher；
2. Node 全部 Service 共享 Application `MaxTimersPerNode` 总额度；
3. Ready 满时增加有界 DuePending FIFO；
4. OnStart 可注册 Timer，但回调在 Scheduler Activate 后才执行；
5. 周期 Timer Running 时 Cancel 成功停止后续触发；
6. M10 使用 `robfig/cron/v3` Parser，不复制 v2 Cron 代码；
7. M10 公开轻量 TimerStats，P50/P95/P99 聚合留给后续指标适配；
8. Module Timer 资源作用域完整延后，不在 M10 预建抽象。

## 26. 开工 Review 已确认

开发者已确认以下全部结论：

1. `TimerID`、`TimerFunc`、`ITimer` 和 `TimerStats` 放在 `service` 包；
2. 对齐 v2 的规范名称：`AfterFunc`、`NewTicker`、`CronFunc` 和 `CancelTimer`，不保留
   `Safe*` 与 `CancelTimerId`；
3. 默认每 Node 最多 3000000 个业务 Timer，全部 Service 共享额度且不预分配；
4. YAML/JSON 不增加 Timer 配置；特殊场景只通过 Application `TimerOptions` 设置每 Node
   上限和 `*time.Location`；
5. Scheduler 增加 Prepare/Activate 两阶段，使 OnStart 可以注册、但不能执行 Timer 回调；
6. Await 与业务 Timer 共用现有 Service DeadlineQueue 和 watcher；
7. Ready 满时使用有界 DuePending FIFO，一次性不丢、周期不重复；
8. DuePending 优先于后续新 `DispatchAsync`，但不越过已经在 Ready 的任务；
9. Running NewTicker/Cron 的 Cancel 成功停止后续触发，当前回调继续；
10. NewTicker/Cron 连续 panic 未达到 99 次时继续触发，正常返回清零，达到上限才取消；
11. Cron 固定使用 `robfig/cron/v3 v3.0.1` 的 Parser/Next 子集；
12. 业务 Timer 容器池化，但必须用 Benchmark、逃逸分析和堆 Profile 验证；
13. M10 不实现 Module、退休、RPC 系统 Timer、固定步长或持久化 Timer；
14. 相关详细设计、复核清单和路线图同步后，允许创建 M10 实施计划。

## 27. 实施与验收结果

### 27.1 实际实现

M10 已完成以下闭环：

1. `IService` 直接组合 `ITimer`，公开 `AfterFunc`、`NewTicker`、`CronFunc`、
   `PauseTimer`、`ResumeTimer`、指针形式 `CancelTimer` 和 `TimerStats`；
2. Application 默认冻结本地时区和每 Node 3000000 个 Timer 额度，Node 负责单调且不
   复用的 `TimerID`；
3. Scheduler 使用 Prepare/Activate 两阶段，OnStart 可登记 Timer，但 Activate 前没有
   Runner 执行业务回调；
4. Await 与业务 Timer 共用一条 DeadlineQueue 和 watcher，到期后统一进入 Service Ready
   FIFO；
5. Ready 额度不足时使用已有 RingQueue 建立有界 DuePending，代次和引用计数防止旧条目
   与对象池复用形成 ABA；
6. Timer 回调可以 Await；恢复项保持 Timer Running 状态并交还原 goroutine，不会被当成
   Ready 墓碑；
7. Node 停止先在 Scheduler 锁内进入 Draining，再发布 Service Stopping，Timer 创建与
   停止准入具有同一线性化边界；
8. Stop 排空后主动置空高水位 Map、Ready/DuePending 队列、Deadline 引用和私有对象池，
   Node Engine Close 同样释放高水位索引和条目池；累计统计及幂等停止结果继续保留；
9. Ticker/Cron 连续 panic 第 99 次自动取消；周期 panic 与额度耗尽使用一秒窗口聚合日志，
   第 99 次可靠越过限流输出；
10. Cron 固定使用 `robfig/cron/v3 v3.0.1` 的 Parser/Next 子集，并通过数字语法、日/星期
    OR、月末、闰年、DST、时区和墙钟后退测试。

实现文件按实际职责保持精简：Deadline Binding、watcher、Ready Task 和停止排空继续位于
`service/scheduler.go`，没有为了计划中的候选文件图拆出只含少量转发代码的文件。

### 27.4 对象池、逃逸和内存结论

`businessTimer` 会因为进入 Scheduler Map、Deadline Binding、DuePending、Ready Task 和
`sync.Pool` 而逃逸到堆；这是跨回调生命周期保存状态的必要结果。池化对照在 Windows 连续
五次结果为：

- 不池化：85.99～108.9 ns/op、160 B/op、1 alloc/op；
- Service 私有池：14.19～21.76 ns/op、0 B/op、0 alloc/op。

因此保留 Service 私有 `businessTimer` 池。公开 `TimerID` 永不复用，内部代次及
`dueReferences`/`taskReferences` 保证池化不会把旧 Deadline、DuePending 或 Ready 墓碑
作用到新 Timer。Stop 最终把 `sync.Pool` 替换为零值并置空高水位容器，停止后的 Service
不会长期持有峰值存储。

当前 Go 1.26.5 发行环境不包含 `go tool pprof`，因此没有提交或引用不可复验的 pprof
Top 输出；容量 Benchmark 的主动 GC 指标、活跃保留 Byte/条、停止后的内部引用断言和
逃逸分析共同作为本里程碑内存门禁。

### 27.5 已知边界

- Cron 跳过历史触发时直接从当前墙上时间求下一个未来点；为避免在 Scheduler 锁内遍历
  很长的日历区间，`CoalescedTotal` 只统计 NewTicker 跳过的固定节拍；
- M10 的 Stop 只完成本地 Scheduler/Timer 排空，RPC pending、OnStop Await、退休和最终
  进程级优雅关闭仍按路线图留到 M16；
- P50/P95/P99 指标聚合、Prometheus 适配、固定步长与持久化 Timer 不在 M10 范围内。
