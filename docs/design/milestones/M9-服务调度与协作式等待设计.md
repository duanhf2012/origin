# Origin 第三版 M9 Service 调度与协作式等待设计

> 文档状态：已实现并完成验收
> 创建日期：2026-07-27
> Review 日期：2026-07-27
> 适用里程碑：M9
> 前置里程碑：M0～M8

## 1. 目标

M9 在 M7 生命周期骨架和 M8 Node 时间轮内核上建立可独立运行和验证的 Service 执行系统：

1. 每个 Service 同时最多只有一个任务访问业务状态；
2. 普通任务使用一个长期 Runner 和 FIFO Ready 队列，不为每个任务创建 goroutine；
3. 业务通过显式 `Await` 顺序等待 Redis、数据库和其他支持 Context 的 I/O；
4. `Await` 期间原任务释放 Service 执行权，其他 Ready 任务可以继续执行；
5. 等待完成后恢复原 goroutine 和原 Go 调用栈；
6. 所有 Await 都有有效 Deadline，未指定时最终使用内置 `15s`；
7. 使用明确、简单的过载上限，防止任务和挂起 goroutine 无限增长；
8. 每个 Scheduler 使用一个内部 Deadline 控制协程及时消费 M8 到期 ID，不让业务 Runner
   的执行时间延迟 Await 取消；
9. 与 M7 的 Node、Service 启停路径结合，停止时不遗留 Runner、Deadline 控制协程或
   `DeadlineQueue`；
10. 为 M10 Service Timer、M11 本地 RPC Dispatcher 和 M13/M15 远程 RPC 保留唯一任务
   投递与恢复入口；
11. 通过竞态、故障、容量和 Benchmark 验证正确性与低延迟基础。

M9 不以“功能多”为目标。它只完成 Service 调度最小内核，不把 RPC、业务 Timer、Module 或
Discovery 提前混入同一实现。

## 3. v2 与 M7 复核

### 3.1 v2 Service 执行模型

v2 每个 Service 默认启动一个 goroutine，在一个 `select` 中处理：

- RPC 请求和响应；
- 本地事件；
- Timer；
- 并发回调；
- Stop 信号。

该模型的优点是：

- Service 状态默认串行访问；
- 普通事件处理路径直观；
- 回调结束后同一 goroutine 继续处理后续事件；
- 不会为每个事件创建 goroutine。

需要在 v3 修正的问题包括：

1. `chanEvent` 默认容量达到 `2000000`，容量与内存成本过大；
2. 事件、Timer 和并发回调使用多个 Channel，无法形成统一 FIFO；
3. 队列满前先读取 `len(channel)` 再发送，存在并发竞争窗口；
4. 阻塞调用会占住唯一 Service goroutine；
5. 多 goroutine 模式会直接并发访问 Service 状态；
6. Stop 立即关闭循环，没有 Waiting、恢复和排空语义；
7. goroutine、Service、队列和状态大量依赖包级全局数据。

M9 保留“普通任务由同一 Runner 连续处理”的优点，并用显式 Await 解决 I/O 等待问题。

### 3.2 M7 当前边界

M7 已经具备：

- `application → node → service` 单向包依赖；
- 每个 Node 独立的 Service 实例；
- `service.Service` 基础对象和一次性 Runtime 绑定；
- `OnInit`、`OnStart(ctx)`、`OnStop(ctx)`；
- 配置顺序启动和严格反序停止；
- 启动失败回滚；
- Service 原子生命周期状态。

M7 尚未创建 Service Runner 或任务队列。M9 在 `service.Service` 内持有调度器，Node 只通过
窄的框架装配函数启动和停止它，不把调度细节放入 `node` 包。

## 4. 里程碑范围

### 4.1 M9 包含

- 每个 Service 一个 `ServiceScheduler`；
- 一个逻辑执行槽；
- 一个 FIFO Ready 队列；
- 普通任务的长期 Runner；
- 一个只消费 M8 到期 ID、从不执行业务代码的 Deadline 控制协程；
- 线程安全的异步 `DispatchAsync`；
- Service 方法形式的通用 `Await`；
- Waiting 任务、恢复项和 Runner 交接；
- 任务 Context 和内部执行令牌；
- 显式 Deadline、Service 默认值、Node 默认值和内置 `15s`；
- 总已接受任务上限和 Awaiting 任务上限；
- M9 范围内的停止准入与本地任务排空；
- 最小任务 panic 恢复，保证执行槽和 Runner 不被永久卡住；
- 执行统计快照；
- 单元测试、跨包集成测试、竞态测试、故障测试和 Benchmark。

### 4.2 M9 不包含

- RPC 契约、生成代码、Future、Dispatcher 和 pendingCall；
- TCP/NATS RPC 接入；
- RPC 的 `AsyncXxx`、`AwaitXxx`、Notify 和 Broadcast；
- 公开 `ITimer`、Ticker 和 Cron；
- 调度式 Sleep；
- Module 树；
- 同步和异步本地事件系统；
- 服务发现、路由、退休和就绪门；
- CPU 密集、cgo 或不支持 Context 阻塞函数的工作池；
- 完整的 RPC/Async pending 排空；
- `OnStop` 中 Await 的 finalizer 专用路径；
- 进程级强制停止策略。

M9 使用 M8 TimerEngine 完成 Await Deadline，但不使用 M5 TCP 或 M6 NATS。远程 RPC
明确留到 M13/M15。

### 4.3 后续能力接入点

| 后续能力 | 只允许使用的 M9 接入点 |
|---|---|
| M10 业务 Timer | 到期后向所属 Service 投递普通根任务 |
| M11 本地 RPC Dispatcher | 通过内部调度入口向目标 Service 投递一个普通根任务 |
| M13/M15 RPC Await | 通过 M9 Await 恢复原任务，不自行切换 Runner |
| RPC Async 回调 | 作为普通 Ready 任务进入同一 FIFO |
| 本地异步事件 | 通过普通任务投递 |
| Module | 与所属 Service 共用同一个调度器和执行槽 |
| M16 优雅停止 | 扩展 M9 的 Running、Ready、Waiting 和本地排空状态 |

其他系统不得再建立第二套 Service Channel、Runner 或协程切换机制。

## 5. 公共 API 外观

### 5.1 DispatchAsync：切回 Service 执行上下文

固定增加：

```go
package service

func (service *Service) DispatchAsync(
    fn func(ctx context.Context),
) error
```

`DispatchAsync` 用于把任意 goroutine 已经取得的结果，安全地交回当前 Service 的串行执行
上下文处理。典型场景包括：

- 不支持 Context/Await 的第三方 SDK 在自己的 goroutine 中回调；
- 由业务明确拥有、可以取消并可以等待退出的后台组件完成工作后，需要修改 Service 状态；
- 适配旧代码时，需要把外部并发回调收敛回单 Service 执行槽。

示例：

```go
func (s *PlayerService) onLegacyLoadFinished(
    playerID string,
    profile *PlayerProfile,
    loadErr error,
) {
    dispatchErr := s.DispatchAsync(func(ctx context.Context) {
        // 该函数执行时已经重新进入 PlayerService 的唯一串行执行上下文，
        // 可以在这里读取和修改 Service 状态。
        s.finishLoadPlayer(ctx, playerID, profile, loadErr)
    })
    if dispatchErr != nil {
        // Service 可能已经停止或达到容量上限。
        // 外部 goroutine 只能清理自己的结果，不能直接修改 Service 状态。
        releaseProfile(profile)
    }
}
```

示例只展示第三方回调如何切回 Service，不授权创建无法取消、无法等待退出的
fire-and-forget goroutine。后台组件仍必须遵守开发指导原则中的资源所有权规则。

`DispatchAsync` 语义固定为：

- 只表示把一个新的根任务加入当前 Service 的 FIFO；
- 成功返回只表示调度器已经接收，不表示任务已经执行；
- 即使从当前 Service 的执行函数中调用，也不在当前调用栈内同步执行；
- 不创建“每任务一个 goroutine”；
- 可以由框架 I/O goroutine 或其他 goroutine 并发调用；
- 队列过载、未运行、停止中或已停止时立即返回错误；
- `fn == nil` 返回 `CodeInvalidArgument`；
- 投递成功后，函数按照统一 FIFO 顺序获得 Service 执行权；
- 不保证由某一个固定 goroutine 执行，只保证执行 `fn` 时持有当前 Service 唯一执行槽；
- 不恢复发起投递位置的原 Go 调用栈；需要保留原调用栈并按顺序继续执行时应使用 Await；
- 调用方负责处理投递失败时尚未移交的 Buffer、对象和其他资源；
- 业务若需要等待调用完成结果，应使用 Await、RPC 或 Future，不能轮询该函数。

`DispatchAsync` 是有意公开的低层逃生口，但不是普通业务流程的首选接口：

- Context 感知的 Redis、数据库、HTTP 和 RPC 顺序等待优先使用 `Await`；
- 一对多或具备明确事件语义的业务通知优先使用 `NotifySync/NotifyAsync`；
- Service 之间的调用优先使用 RPC；
- 只有需要把任意 goroutine 的结果切回 Service 执行上下文时，才直接使用
  `DispatchAsync`；
- 后台 goroutine 不得在投递前读取或修改 Service 的普通 Map、Slice、玩家对象和 Module
  状态；
- 自行创建的 goroutine 不计入 Service 已接受任务，停止期间可能投递失败；要求停止时必须
  排空的工作应使用 Await 或框架管理的 Async/RPC 机制。

后续 `NotifyAsync`、RPC 入站、Timer 和 Await 恢复会复用相同的内部调度器，但不会通过
公共 `DispatchAsync` 绕一层。内部必须区分“新根任务”和“已接受任务恢复”，保证恢复项
不会因容量已满被二次拒绝。

`IService` 增加：

```go
DispatchAsync(func(context.Context)) error
```

所有嵌入 `service.Service` 的类型自然获得默认实现。名称使用 `DispatchAsync` 而不是
`Post`、`RunAsync` 或 `Go`，用于明确表达“异步派发到 Service 执行上下文”，避免被误解为
立即执行或启动一个新的并行业务 goroutine。

### 5.2 通用 Await

Go 不支持带独立类型参数的方法。为获得自然的 `s.Await(...)` 外观，并避免公开泛型辅助
函数、额外 `owner` 参数和 `AwaitFunc`，最终统一为普通 Service 方法：

```go
func (service *Service) Await(
    ctx context.Context,
    fn func(waitCtx context.Context) error,
) error
```

需要返回业务结果时，通过只属于当前调用栈的局部变量接收：

```go
// 在释放 Service 执行权前复制稳定的并发安全 Client 和普通参数。
repository := s.repository
playerID := player.ID

var profile *PlayerProfile

err := s.Await(ctx, func(waitCtx context.Context) error {
    loaded, loadErr := repository.LoadPlayer(waitCtx, playerID)
    if loadErr != nil {
        return loadErr
    }

    // 这里只写当前调用栈的局部结果，不修改 Service 状态。
    profile = loaded
    return nil
})
if err != nil {
    return err
}

// Await 返回后已经重新取得 Service 执行权。
s.players[playerID] = profile
```

多个结果使用多个局部变量接收，不增加 Tuple、`any`、反射或泛型包装：

```go
repository := s.repository
playerID := player.ID

var (
    profile *PlayerProfile
    version int64
)

err := s.Await(ctx, func(waitCtx context.Context) error {
    var loadErr error
    profile, version, loadErr =
        repository.LoadPlayerVersion(waitCtx, playerID)
    return loadErr
})
```

receiver 就是 owner。Await 必须校验 `ctx` 中的内部执行令牌确实属于 receiver 对应的
Service 和当前 Running Task。

`IService` 增加：

```go
Await(
    context.Context,
    func(context.Context) error,
) error
```

业务 Service 嵌入 `service.Service` 后直接获得 `s.Await(...)`；Module 的同名方法委托给
所属 Service，不创建独立 Await 调度器。

首版不提供以下重叠接口：

- 泛型自由函数 `service.Await[T](owner, ctx, fn)`；
- `AwaitFunc`；
- `AwaitBlocking`、`AwaitIO`、`AwaitAsync`；
- 不接收 Task Context 的 `s.Await(fn)`。

不提供 `s.Await(fn)` 是因为 Go 没有可靠的当前 goroutine标识。若缺少 Task Context，任意
持有 Service 指针的外部 goroutine都可能错误释放当前任务的执行权，框架也会失去上层取消、
Deadline 和 Stop 传播链。

### 5.3 外层 ctx 与 waitCtx

两个 Context 的职责不同：

- 外层 `ctx` 是当前 Origin Service Task Context，用于校验 Service、Task 和执行权，并作为
  上层取消与 Deadline 的父节点；
- `waitCtx` 是 Await 依据有效超时派生的实际等待 Context，必须传给 Redis、数据库、HTTP、
  RPC 等真正等待的外部操作。

```go
redisClient := s.redis

err := s.Await(ctx, func(waitCtx context.Context) error {
    // 正确：把 Await 最终生成的 Deadline 和取消信号传给 Redis。
    return redisClient.Delete(waitCtx, key)
})
```

禁止在 `fn` 中绕过 `waitCtx`：

```go
err := s.Await(ctx, func(waitCtx context.Context) error {
    // 错误：外层 ctx 可能没有 Await 附加的默认 15s Deadline。
    return redisClient.Delete(ctx, key)
})
```

`fn` 中不得再捕获 `s`、Player、Module 或其他可能在 Await 期间被 Service 后续任务修改或
释放的对象。即使某个 Client 在生命周期内保持不变，也应在 Await 前复制其稳定引用，让
代码审查能够直接确认 `fn` 没有越过执行权读取 Service 状态。

如果函数完全不需要 Context：

- 非阻塞函数直接同步调用，不使用 Await；
- CPU 密集函数不进入普通 Await，后续使用有界工作池；
- 不支持 Context 的阻塞函数无法安全取消，不进入普通 Await，必须增加专用适配或有界
  工作池。

### 5.4 RPC 外观不受影响

M11 生成、M13/M15 接入远端 Transport 的 RPC 客户端仍提供：

```go
player, err := client.AwaitGetPlayer(ctx, playerID)
```

生成方法已经绑定调用方 Service 和 RPC Future，因此用户不需要在 RPC 调用点再手写
闭包式 `s.Await(...)`。M9 的通用 API 主要用于 Redis、数据库和其他非 RPC I/O。

### 5.5 Service 默认 Await 超时

固定增加：

```go
func (service *Service) SetDefaultAwaitTimeout(timeout time.Duration) error
```

规则：

- 只允许在当前运行实例的 `OnInit` 中调用；
- `timeout` 必须大于零；
- 未调用表示不设置 Service 级覆盖；
- 调度开始后修改返回 `CodeInvalidArgument`；
- 类型样本调用不会影响运行实例，并返回参数错误；
- 正常 Await 热路径只读取启动前冻结的值，不加锁。

示例：

```go
func (s *PlayerService) OnInit() error {
    return s.SetDefaultAwaitTimeout(3 * time.Second)
}
```

高延迟 Service 可以设置更长默认值；单次业务仍可通过传入带 Deadline 的 Context 覆盖。

### 5.6 统计快照

固定提供只读快照：

```go
type ExecutionStats struct {
    Accepted              int
    Ready                 int
    Running               int
    Awaiting              int
    AcceptedHighWatermark int
    DispatchedTotal       uint64
    CompletedTotal        uint64
    RejectedTotal         uint64
    AwaitTotal            uint64
    AwaitCanceledTotal    uint64
    AwaitTimeoutTotal     uint64
    PanicTotal            uint64
}

func (service *Service) ExecutionStats() ExecutionStats
```

快照用于测试、诊断和后续指标接入，不返回内部队列、Task 或 Runner 引用。瞬时值和累计值
都在调度器同一把短锁内一次复制，保证快照一致；统计查询不是业务热路径。

### 5.7 框架装配 API

Scheduler 实现在 `service` 包内，由 Node 负责按生命周期启动和停止。由于 `node` 与
`service` 是不同包，需要保留两个导出的框架装配函数：

```go
type SchedulerConfig struct {
    // MaxTasks 限制当前 Service 已接受、但尚未完整返回的根任务总数。
    // 它同时包含 Ready、Running 和 Awaiting，不只是 Ready 队列长度。
    MaxTasks int

    // MaxAwaitTasks 限制已经调用 Await、释放 Service 执行权且尚未恢复返回的任务数。
    // 每个 Awaiting 任务仍保留原 goroutine、调用栈和闭包引用，因此必须单独限制。
    MaxAwaitTasks int

    // DefaultAwaitTimeout 是当前 Node 下 Service 的默认 Await 超时。
    // 单次调用方显式 Deadline 和 Service 级覆盖的优先级高于该值。
    DefaultAwaitTimeout time.Duration
}

func DefaultSchedulerConfig() SchedulerConfig

func (config SchedulerConfig) Validate() error

func StartScheduler(
    target IService,
    config SchedulerConfig,
    timerEngine *timerwheel.Engine,
) error

func StopScheduler(
    ctx context.Context,
    target IService,
) error
```

这些函数与 M7 的 `BindRuntime` 一样，因跨包装配而必须导出，不是业务生命周期入口：

- 业务只实现 `OnInit/OnStart/OnStop`；
- `node` 在 `OnStart` 成功后把自己持有的内部 TimerEngine 传给 `StartScheduler`；
- `node` 在调用 `OnStop` 前调用一次 `StopScheduler`；
- TimerEngine 始终由 Node 拥有和最终关闭，Scheduler 只拥有自己从中创建的
  `DeadlineQueue`；
- `StartScheduler` 返回错误时必须已经清理本次创建的 Queue、Runner 和控制协程，保证
  失败结果不留下部分启动资源；
- 重复启动、跨 Service 停止或无效状态返回错误；
- 不返回内部 Scheduler、Runner、队列或执行槽；
- 不增加 `SchedulerManager`、`RunnerFactory` 或 Adapter 层。

`timerwheel.Engine` 位于 Origin 内部包中，该参数只服务于 `node → service` 的框架装配，
不会成为业务项目需要构造或替换的 API。

## 6. 配置外观

### 6.1 Node 级配置

调度器属于每个 Service，但默认策略属于 Node。固定在每个 Node 下配置：

```yaml
nodes:
  - id: game-1
    scheduler:
      # 单个 Service 已接受但尚未完整结束的根任务总上限，
      # 包含 Ready、Running 和 Awaiting，不等同于 Ready 队列长度。
      max_tasks: 20000

      # 单个 Service 中已经进入 Await、释放执行权但尚未恢复返回的任务上限。
      # 每个 Awaiting 任务仍保留一个 goroutine、原调用栈和闭包引用。
      max_await_tasks: 10000

      # Await 未获得调用方或 Service 显式超时时使用的 Node 默认值。
      default_await_timeout: 15s
    services:
      - PlayerService
      - SceneService
```

省略 `scheduler` 时使用相同默认值：

```text
max_tasks = 20000
max_await_tasks = 10000
default_await_timeout = 15s
```

同一 Node 的每个 Service 都获得独立上限，不共享同一个任务队列。Service 可以在 `OnInit`
中只覆盖默认 Await 超时，首版不增加 Service 专属容量配置表。

`20000` 是普通游戏逻辑 Service 的默认安全容量，用于为可预期的短时峰值留出空间，不表示
正常运行时允许长期积压两万个任务。`max_await_tasks=10000` 也不会预先创建一万个
goroutine；只有真实进入 Await 的任务才占用 goroutine、调用栈和闭包内存。M9 必须使用
10000 个并发 Await 的容量测试记录最坏情况下的内存与恢复延迟，不能把配置上限误当成正常
运行目标。

### 6.2 校验规则

- `max_tasks` 必须大于零；
- `max_tasks` 不能超过 `65536`；若单 Service 需要更大队列，应先评审服务拆分、批处理、
  路由扩容或入口限流，不能恢复为 v2 的超大队列；
- `max_await_tasks` 必须大于零；
- `max_await_tasks` 不能大于 `max_tasks`；
- `default_await_timeout` 必须大于零；
- 时间继续使用 M3 的 `config.Duration`，只接受带单位形式；
- `0` 不表示无限容量或无限超时；
- 未知字段继续由 M3/M7 严格拒绝；
- 配置在 Node 创建前完成校验，不能启动后静默修正。

### 6.3 为什么只保留两个容量参数

首版不同时公开 Ready 容量、Awaiting 容量和 Accepted 容量三个相互重叠的参数。

只保留：

1. `max_tasks`：当前 Service 已接受但尚未完整返回的根任务总数；
2. `max_await_tasks`：这些任务中已经调用 Await、释放 Service 执行权且尚未恢复返回的
   数量；它不是“在 Ready 队列中等待执行”的任务数量。

因此：

```text
Accepted = Ready 根任务 + Running 根任务 + Waiting/待恢复根任务
Waiting <= Accepted
```

恢复项属于原任务，不是新任务，永远不因 `max_tasks` 再次被拒绝。这样可以避免“外部操作
已经完成，但恢复项因为队列满而永远不能回来”的死锁。

Ready 队列的实际元素数量自然受 `max_tasks` 限制，不需要第三个公开容量。

内部任务状态仍使用 `Waiting` 表示“任务已释放执行权并等待外部操作完成”；公开配置和统计
统一使用 `Await`/`Awaiting`，避免被误解为 Ready 队列中尚未执行的普通等待任务。

## 7. 调度状态

### 7.1 任务状态

每个根任务依次处于：

```text
Ready -> Running -> Completed
             |
             v
          Waiting -> Ready(恢复项) -> Running
```

同一个任务可以多次进入 `Waiting`，但同时只能有一个未完成 Await。

### 7.2 调度器内部状态

M9 使用内部状态：

```text
Created -> Running -> Draining -> Stopped
```

- `Created`：已经装配但 Runner 尚未启动；
- `Running`：接受新的 `DispatchAsync` 和框架根任务；
- `Draining`：拒绝新根任务，完成已经接受的任务；
- `Stopped`：Runner、Deadline 控制协程和 Queue 已退出，所有任务和引用已清理。

这些不是新的公开 Service 生命周期状态。公开状态仍使用 M7 的
`Created/Initializing/Initialized/Starting/Running/Stopping/Stopped/Failed`。

M9 不增加一个只能停留却不能完成 Application 受控退出的 Scheduler `Failed` 半成品状态。
业务 Task panic 在任务边界恢复并继续 Service；真正违反调度器内部不变量且无法安全继续时
使用 panic，其最终处置由 M16 Review 单独确认，不能与普通任务 panic 混为一类。

### 7.3 单执行槽不变量

任何时刻必须满足：

1. 每个 Service 最多一个活动 Runner；
2. 最多一个任务处于 `Running`；
3. 只有 `Running` 任务可以访问非并发安全 Service 状态；
4. `Waiting` 和恢复排队中的原 goroutine不能执行 Service 业务代码；
5. 调度器锁内不执行任何用户函数；
6. Runner 交接时不能出现“两个 goroutine都认为自己拥有执行权”的窗口；
7. 任一任务只完成一次，Accepted 只减一次；
8. 任一 Await 只恢复一次。

## 8. Ready 队列与唤醒

### 8.1 一个 FIFO

M9 只定义三类内部入口：

```text
新根任务 -> 受 max_tasks 准入后进入 Ready FIFO
恢复项   -> 属于已经接收的任务，直接进入同一 Ready FIFO
控制信号 -> 修改停止等控制状态，不作为业务任务入队
```

M9 当前只有公共 `DispatchAsync` 根任务和 Await 恢复项。后续 RPC、业务 Timer、事件和
Module 只复用这三个入口，各自的 pending、过载和资源释放语义留在对应里程碑设计，不在
M9 提前展开。

首版不增加业务优先级队列：

- 所有可执行业务项使用严格 FIFO；
- Await 恢复保证能够入队，但仍追加到队尾；
- Stop 的独立控制路径不属于“高优先级业务队列”；
- 只有 Benchmark 和生产指标证明 FIFO 存在实际延迟问题时，才重新讨论执行配额或多级
  队列，不能提前增加调度复杂度。

### 8.2 队列实现

M9 固定使用 `internal/container/ringqueue` 中的简单泛型可增长环形队列：

- 初始容量为 `min(64, max_tasks)`，不按 `max_tasks` 为每个 Service 一次性预分配；
- 容量不足时按两倍增长，最后一次增长不得超过 `max_tasks`；
- 增长不能超过 `max_tasks`；
- 出队后立即清空槽位中的闭包、Task 和 Context 引用；
- RingQueue 只实现入队、出队、长度、清理和有界扩容，不内置锁、日志、指标或调度语义；
- ServiceScheduler 已经使用短锁统一裁决 Accepted、Awaiting、Runner、Stop 和队列状态，
  RingQueue 直接复用这把锁，不增加第二次并发同步；
- 不使用无锁队列；
- 不使用 `container/list` 的逐节点分配；
- 不把 Task 放入承载任务本身的 Channel。

#### 为什么不直接使用 Channel 保存 Ready Task

Channel 的代码表面更短，但在当前模型中不能真正删除 Scheduler 状态锁，并具有明确成本：

1. `make(chan *task, 20000)` 会为每个 Service 按最大容量一次性建立缓冲区；可增长 RingQueue
   从 64 个槽位开始，只有真实峰值到来时才扩容；
2. Accepted 同时包含 Ready、Running 和 Awaiting，Await 恢复又必须在满载时进入，单靠
   Channel 的 `len/cap` 不能完成这些原子状态裁决；
3. Stop、Runner 交接、Await 完成和并发投递仍需要同一把短锁，使用 Channel 会在锁之外再
   增加一次 Channel 同步；
4. Channel 关闭与并发发送需要额外协调，而 RingQueue 由 Scheduler 唯一拥有，不需要关闭
   数据通道；
5. Ready 槽位中的引用何时清零、队列如何增长和停止时如何检查为空，RingQueue 的行为更
   直接且容易测试。

因此当前场景中 RingQueue 的内存优势和状态一致性优势明显，并不会让业务调度状态机更复杂。
新增的数据结构作为独立内部公共算法包实现和测试，Scheduler 只调用其最小 API。

### 8.3 合并唤醒

每个调度器使用容量为 `1` 的内部唤醒 Channel：

- 唤醒只表示“可能存在 Ready 项”，不承载 Task；
- 提交方在锁内成功入队后，非阻塞尝试发送唤醒；
- 已有唤醒时不重复发送；
- Runner 醒来后仍以锁内 Ready 队列为唯一事实来源；
- Ready 未空时 Runner 直接继续出队，不往返 Channel。

这样保留 v2 单循环的连续处理路径，同时消除多 Channel 之间无法定义统一顺序的问题。

## 9. Runner

### 9.1 普通快速路径

Service 进入 Running 后启动一个 Runner。普通任务过程：

1. Runner 从 FIFO 取得队首任务；
2. 在锁外执行用户 Task；
3. Task 返回；
4. 完成 Task、减少 Accepted 并清理引用；
5. Runner 直接取得下一项；
6. 队列为空时阻塞等待合并唤醒。

普通 Task 不创建 goroutine、交接 Channel或额外 Future。

### 9.2 Await 交接

任务 A 调用 Await 时：

1. 校验 Task Context、receiver 所属 Service、状态、容量和 Deadline；
2. A 原子释放执行槽并进入 Waiting；
3. 创建一个替代 Runner B；
4. A 所在的原 goroutine在锁外执行 `fn(waitCtx)`；
5. B 继续处理其他 Ready 任务；
6. `fn` 返回后，A 的恢复项追加到 FIFO 队尾；
7. 当前活动 Runner 取得 A 的恢复项；
8. 活动 Runner 原子把执行槽授予 A；
9. A 的原 goroutine收到交接信号并从 Await 返回；
10. 交出执行槽的 Runner 退出；
11. A 完整返回后成为普通 Runner，继续处理后续 Ready 项。

一个 Service 稳定状态下由 Scheduler 拥有的 goroutine 数量为：

```text
1 个活动 Runner
+ 1 个 Deadline 控制协程
+ 尚未从 Await 返回的任务数量
```

Deadline 控制协程从不执行业务代码，也不拥有 Service 执行槽；它只消费 M8 到期 ID 并取消
对应 Context。`max_await_tasks` 限制的是最后一项，默认 10000 不会预先创建 goroutine。

### 9.3 交接 Channel

每个真正使用 Await 的 Task 延迟创建一个容量为 `1` 的私有交接 Channel：

- 从不 Await 的普通 Task 不创建；
- Channel 只传递执行权，不传递业务结果；
- 同一 Task 的每次 Await 创建独立 Channel，恢复完成后立即清空引用；
- Channel 不进入对象池，避免残留信号和代次混淆；
- 交接前先在锁内修改唯一活动 Runner，再在锁外发送信号；
- 必须通过高并发测试证明没有残留信号、重复交接或 ABA。

M9 不使用 goroutine ID，也不解析 runtime 栈文本识别当前 goroutine。

### 9.4 为什么不使用固定 Runner 池

Await 必须保留原业务 goroutine的调用栈。固定 Worker 池不能把一个已经挂起的 Go 调用栈
迁移到另一个 goroutine，因此仍然需要原 goroutine恢复。

首版每次进入 Waiting 时只创建一个替代 Runner。恢复交接后替代 Runner 退出，原 goroutine
成为新的活动 Runner。只有 Benchmark 证明创建替代 Runner 是实际瓶颈时，才重新讨论更复杂
的 Runner 复用，不提前引入池和任务状态机代码生成。

## 10. Task Context 与使用约束

### 10.1 内部执行令牌

调度器为每个 Task 创建标准 `context.Context`，并通过私有 Context Key 保存不可伪造的执行
令牌。令牌至少关联：

- 所属 Service 调度器；
- 当前 Task。

Await 代次、DeadlineID 和一次性完成状态保存在 Task 内部状态中，不塞入业务 Context。
Task 主对象可以池化，但私有 Context 令牌永不池化；Task 完成时先原子清空令牌中的 Task
指针，因此旧 Context 不会因为主对象复用而错误指向另一个任务。

`s.Await` 必须校验：

1. Context 来自 Origin 当前 Task；
2. Context 对应的 Service 与 receiver `s` 相同；
3. 该 Task 当前确实持有执行槽；
4. 当前没有另一个未完成 Await。

校验失败时不执行 `fn`，返回 `CodeInvalidArgument`。

业务可以通过 `context.WithCancel`、`WithTimeout` 或 `WithValue` 派生 Context，因为派生
Context 会继续保留内部令牌。业务不能在 Task 中改用 `context.Background()` 调用 Await。

Go 没有受支持的当前 goroutine ID。私有令牌只能证明 Context 属于哪个 Service 和 Task，
不能证明调用 `Await` 的正是原业务 goroutine。如果业务在原 Task 仍处于 Running 时把
Context 交给另一个 goroutine调用 Service API，外部 goroutine 可能先通过状态校验并错误
释放执行槽，而原 goroutine仍继续访问 Service 状态。

因此固定使用规则为：

- Task Context 可以在当前调用栈中向普通辅助函数传递；
- Task Context 可以沿当前调用栈传递，也可以派生取消、Deadline 和不可变元数据；其他
  goroutine 可以观察派生 Context 的取消状态，但不得用它调用 `Await`、
  `DispatchAsync` 的同步替代接口或其他需要当前 Service 执行权的 API；
- 跨 goroutine 的结果必须使用 `DispatchAsync` 切回 Service；
- 框架不使用 goroutine ID、runtime 栈解析或 goroutine-local 第三方库伪装成可强制校验；
- 违反该规则属于业务并发错误，应由竞态测试、代码审查和后续静态检查尽早发现。

Origin 必须为所有能够执行 Service 业务代码的入口提供 Task Context：

- RPC 服务端方法的第一个参数；
- Timer 回调；
- `DispatchAsync` 回调；
- 异步本地事件监听者；
- Await 和 RPC Async 恢复后的继续执行；
- 后续 Module 通过所属 Service 接收的业务回调。

业务辅助方法继续显式向下传递该 Context。`context.Background()` 只适合创建 Application
等最顶层 Context，不能用来伪造 Service Task Context。

### 10.2 Await 期间的状态访问

调用 Await 前，业务应复制外部调用所需参数：

```go
playerID := player.ID
version := player.Version
```

`fn` 执行期间：

- 可以使用局部变量；
- 可以使用并发安全的 Redis、数据库、HTTP 或其他 Client；
- 不能读取或修改 Service 的普通 Map、Slice、玩家对象和 Module 状态；
- 不能再次调用当前 Service 的 Await；
- 不能通过捕获的指针绕过执行权规则。

Await 返回后已经重新取得执行槽，但等待期间其他任务可能改变状态，业务仍需重新校验玩家
是否在线、对象版本是否变化等逻辑条件。

## 11. Await 结果、取消与 panic

### 11.1 正常结果

`fn` 在原任务 goroutine执行。返回值保存在原调用栈中，不经过 `any`、反射或序列化。

`fn` 返回不表示 Await 立即返回。原任务必须先进入 FIFO，并重新获得执行槽。

### 11.2 Context 结果优先级

如果外部函数已经返回，但原任务在恢复队列中等待过久，Context 可能在重新取得执行槽前
过期。交接完成后按以下规则返回：

1. `fn` panic：重新抛出 panic，由 Task 边界处理；
2. 有效 Context 已取消或超时：使用 `context.Cause(waitCtx)` 区分
   `context.Canceled` 与 `context.DeadlineExceeded`，再映射为对应 Origin 错误；
3. 否则返回 `fn` 的结果和 error。

因此 Deadline 覆盖：

```text
外部 I/O 时间 + 外部结果完成后的 FIFO 恢复排队时间
```

### 11.3 fn 忽略 Context

M9 不为 `fn` 再创建辅助 goroutine。若 `fn` 永久阻塞且完全忽略 Context，Go 无法安全强制
终止该函数，Await 也无法在 Deadline 到达时伪装成已经恢复。

允许放入普通 Await 的函数必须：

- 接受并传播 Context；
- 在取消后能够返回；
- 主要等待 Go 网络 I/O 或其他可协作取消操作。

CPU 密集、cgo、`time.Sleep`、无 Context 的旧式阻塞调用不进入普通 Await。后续若确有需要，
单独设计有界工作池。

### 11.4 fn panic 的恢复执行权

`fn` 与 Task 位于同一个 goroutine。若 `fn` 在 Service 执行权已经释放后直接向外展开 panic，
业务 defer 可能在没有执行权时访问 Service 状态，并与替代 Runner 并发。

因此 Await 内部必须：

1. 在同一个 goroutine捕获 `fn` 的 panic 值和原始堆栈；
2. 像正常返回一样把原任务加入恢复 FIFO；
3. 等待重新取得 Service 执行权；
4. 取得执行权后重新抛出原 panic；
5. Task 在重新抛出前临时保存捕获的原始堆栈；最外层 Task 边界恢复到该 panic 时优先记录
   原始堆栈并完成任务；
6. Task 完成时清空 panic 值和堆栈引用。

Await 不吞掉 panic，也不在两层重复记录。

## 12. Deadline 实现

### 12.1 有效 Deadline

优先级固定为：

```text
调用方 Context 显式 Deadline
    > Service 默认 Await 超时
    > Node scheduler.default_await_timeout
    > Origin 内置 15s
```

规则：

- 显式 Deadline 原样继承，可以短于或长于默认值；
- Context 只有取消、没有 Deadline 时仍附加默认 Deadline；
- Context 进入 Await 前已经取消时，直接返回取消错误，不释放执行槽、不调用 `fn`；
- 创建出的 CancelFunc 在 Await 完整恢复后立即调用，释放关联资源；
- 每个 Scheduler 创建独立生命周期 Context，所有 Task Context 都由它派生；
- `StopScheduler(ctx)` 进入 Draining 时不立即取消生命周期 Context；只有停止 `ctx` 到期或
  被取消时才取消它，从而取消全部尚未返回的 Await；
- 单次显式 Deadline不能突破已经存在的调用方或 Scheduler 生命周期取消。

### 12.2 按 Context 类型选择唯一计时器

M9 的每个 ServiceScheduler 从所属 Node TimerEngine 创建一条内部 `DeadlineQueue`，但只为
没有显式 Deadline 的 Context 登记 M8 Deadline：

1. 根据第 12.1 节计算唯一有效 Deadline；
2. 调用方 Context 已有 Deadline 时直接继承，由调用方已经建立的 Go Timer 驱动取消，
   不再登记 M8；
3. 调用方 Context 没有 Deadline 时，把统一默认超时登记到 M8 `DeadlineQueue`，取得内部
   `DeadlineID` 并与当前 Waiting Task 关联；
4. 默认超时使用框架私有轻量 Context 向下游公开计算出的 `Deadline()`，但不调用
   `context.WithTimeout`/`context.WithDeadline` 创建第二个 Runtime Timer；
5. 外部函数先完成时立即取消对应 M8 Deadline；显式 Deadline 路径不取消调用方拥有的
   Timer；
6. M8 Deadline 或显式 Context 先到期时取消派生 Context，外部函数观察 Context 返回后仍
   通过正常恢复路径把原 goroutine交回执行槽；
7. 到期、外部完成、调用方取消和 Stop 由同一 Task 状态机裁决，只完成一次。

M8 只提供到期 ID，不认识 Context 或 Task。默认超时派生 Context 的 `Deadline()` 必须返回
计算后的绝对时间；M8 到期后，`context.Cause` 和 Await 最终错误必须表现为
`context.DeadlineExceeded`。内部实现可以复用 `context.WithCancelCause` 的取消传播，再用
私有轻量包装补充 Deadline 和错误语义，但不能增加 Go Runtime Timer。

`context.Background()`、`context.TODO()` 以及只有取消能力而没有 Deadline 的合法输入，
在超时选择层都使用默认链和一条 M8 Deadline。“合法输入”仍受第 9.1 节 Origin Task
Context 校验约束；裸 Background 不能作为 `Service.Await` 的执行权令牌。

本节是 2026-07-28 已确认的最终目标。M9 当前实现仍会把显式 Deadline 同时登记到 M8，
并且默认超时派生 Context 尚未公开 `Deadline()`。进入 M11 编码前必须修正该实现差异，
补充显式 Go Timer、默认 M8 Timer、取消竞争和零残留回归测试，并通过 Benchmark 确认热
路径没有引入不可接受的分配。

### 12.3 Deadline 控制协程

每个 ServiceScheduler 固定创建一个 Deadline 控制协程：

1. 等待 `DeadlineQueue.ExpiredSignal()`；
2. 按有界批次调用 `DrainExpired`；
3. 通过内部 `DeadlineID → Waiting Task` 索引取得取消函数；
4. 在 Scheduler 锁外调用取消函数；
5. Queue 中仍有到期 ID 时继续处理，不执行任何 Service 业务函数。

该协程是必要的控制路径。如果只由业务 Runner 消费到期 ID，Runner 正在执行一个较长业务
函数时会延迟其他 Await 的 Context 取消，破坏 M8 已经建立的统一 Deadline 语义。控制协程
只取消 Context；原 `fn` 返回、恢复入队和执行槽交接仍由原任务与 Scheduler 状态机完成。

### 12.4 不建立第二套 Deadline 调度器

M9 禁止：

- 为每个 Await 创建 `time.Timer`；
- 使用 `time.After`；
- 建立调度器私有最小堆；
- 建立另一套时间轮；
- 用轮询扫描 Waiting Task 是否超时。

这保证 Await、后续 RPC 和业务 Timer 从首次实现起就使用同一 Node 时间基础设施，不存在
以后迁移 Deadline 实现的返工。

### 12.5 DeadlineQueue 生命周期

- Scheduler 启动时创建 `DeadlineQueue`；
- Queue 创建成功后启动唯一 Deadline 控制协程；
- Scheduler 停止准入后拒绝新的根任务，但已接受 Task 仍可登记 Await Deadline；
- 停止 Context 到期时取消 Scheduler 生命周期 Context，使 Waiting 函数尽快返回；
- 全部 Task 完成后关闭 `DeadlineQueue`，唤醒并等待 Deadline 控制协程退出；
- Deadline 控制协程退出后才允许销毁 Scheduler；
- Node TimerEngine 最后停止，因此 Service 排空期间仍可正常计时。

如果业务 `fn` 忽略 Context，Go 无法安全强杀它。为避免 `OnStop` 与仍在运行的旧任务并发
访问 Service 状态，M9 的 `StopScheduler` 在发出取消后仍等待任务真正返回，因此可能超过
调用方 Deadline。完整的进程级超时与强制退出策略留到 M16。

M9 不实现 `ITimer`、Ticker、Cron、暂停或恢复。M10 业务 Timer 接入会创建独立
`DeadlineQueue`，
避免业务 Timer Ready 和 Await Deadline 状态混在同一索引中。

## 13. 过载规则

### 13.1 过载策略依据

M9 综合采用以下成熟系统的做法：

- Skynet 的 Service 队列从 `64` 开始按两倍增长，并从 `1024` 开始报告过载，适合吸收
  短时峰值；M9 保留小容量起步和渐进扩容，但增加硬上限，避免持续增长；
- Akka 的有界非阻塞邮箱在溢出时不会阻塞提交方；M9 同样禁止阻塞，但会按任务语义返回
  明确错误，而不是统一投入 Dead Letters；
- NATS 同时按消息数量和字节数保护慢消费者，并明确指出扩大缓冲区只适合短时峰值，不能
  解决持续处理能力不足。

参考：

- [Skynet 消息队列源码](https://github.com/cloudwu/skynet/blob/master/skynet-src/skynet_mq.c)；
- [Akka Mailbox](https://doc.akka.io/libraries/akka-core/current/mailboxes.html)；
- [NATS Slow Consumers](https://docs.nats.io/running-a-nats-service/nats_admin/slow_consumers)。

队列容量按以下关系评估：

```text
需要容量 ≈（峰值进入速率 - Service 消费速率）× 峰值持续时间
```

队列只能吸收短峰值。若进入速率长期大于消费速率，增大队列只会增加延迟和内存占用；
此时应采用路由扩容、Service 拆分、批处理、入口限流或业务安全的事件合并。

### 13.2 首版只实现硬上限

M9 不实现 `max_tasks/4` 软过载状态机、专用日志限频器或额外配置。Scheduler 只维护
Accepted 历史最高水位和拒绝总数，后续指标系统可以按项目阈值告警，不把观测策略固化进
调度热路径。

### 13.3 DispatchAsync 过载

当 `Accepted >= max_tasks` 时：

- 新 `DispatchAsync` 立即返回 `CodeServiceQueueFull`；
- 不阻塞提交 goroutine；
- 不丢弃已接受任务；
- 不关闭 Service；
- 不为每次拒绝同步写日志；
- 增加低开销拒绝计数，由后续指标或上层入口决定是否记录限频日志。

### 13.4 Await 过载

当 `Awaiting == max_await_tasks` 时：

- 当前 Await 不释放执行槽；
- 不调用 `fn`；
- 返回 `CodeServiceQueueFull`；
- 当前 Task 可以按业务规则降级、稍后重试或返回；
- 不取消其他已经 Waiting 的任务。

复用 `CodeServiceQueueFull`，不为同一种 Service 过载再增加 `CodeServiceAwaitLimit`。
Ready/Awaiting 的实际数量通过结构化日志、统计和指标区分。

### 13.5 恢复永远可进入

已经接受任务的以下内部事件不能被容量拒绝：

- 外部操作完成；
- Context 取消；
- Deadline 到达后外部函数返回；
- panic 后恢复执行权；
- 停止阶段的取消恢复。

它们只把原任务从 Waiting 转为恢复 Ready，不增加 Accepted。

### 13.6 默认容量只是安全起点

`20000/10000` 是普通游戏逻辑 Service 的推荐初始默认值，不宣称适合所有项目。配置不会
按上限预分配 Task 或 goroutine。实现阶段
必须记录：

- 每个普通任务内部对象大小；
- 每个 Waiting goroutine 的实际栈和堆占用；
- 1、10、100 个 Service 下的总内存；
- 不同容量下的吞吐、排队时间和 GC；
- 10000 个并发 Await 的总内存、取消风暴和恢复风暴延迟；
- 热点 Service 的过载行为。

延迟高度敏感的场景可以主动降低容量；已知短峰值场景可以在 `65536` 以内调整。若 Benchmark
证明默认值不合理，在 M9 开工 Review 或验收前重新确认，不能静默修改。

RPC 接入里程碑还必须在传输和 Dispatcher 入口按“消息数量 + 暂存字节数”双重限制，
避免大量接近最大消息尺寸的 RPC 仅满足任务数量限制却耗尽内存。M9 不持有网络 payload，
因此不在 Service Scheduler 中重复维护字节预算。

## 14. 生命周期接入

### 14.1 启动顺序

M9 保持 M7 的生命周期顺序：

```text
全部 Service OnInit
    -> 启动 Node TimerEngine
    -> OnStart
    -> StartScheduler（创建 Queue、Runner 和 Deadline 控制协程）
    -> Service Running
```

具体约束：

- `OnInit` 和 `OnStart` 仍由 Node 生命周期控制协程直接调用；
- Scheduler 在 `OnStart` 成功后才启动；Node 最后把公开 Service 状态切换为 Running，
  `DispatchAsync` 同时检查公开状态和 Scheduler 状态，不能在发布 Running 前接收任务；
- Scheduler 启动前 `DispatchAsync` 返回 `CodeServiceNotReady`；
- `OnInit` 可以设置 Service 默认 Await 超时；
- M9 的通用 Await 只能在 Scheduler Task 中调用；
- `OnStart` 中直接使用支持 Context 的同步初始化调用，不使用 M9 调度式 Await；
- 后续 RPC 启动与就绪阶段需要的 Await 由对应里程碑单独接入，不在 M9 改造生命周期。

这样避免为了尚未存在的 RPC 在 M9 引入“生命周期伪 Task”和第二套完成 Channel。

M14 在该边界上增加已经确认的生命周期 Await，但不修改 M9 普通 Task 交接算法：

- PrepareScheduler 在 OnStart 前准备默认超时、DeadlineQueue 和私有生命周期令牌；
- OnStart 继续由 Node 生命周期 goroutine直接调用；
- Service.Await 识别合法 OnStart 令牌后在原 goroutine 同步等待，不创建替补 Runner；
- 普通 Task Context 仍走本章的 Running -> Waiting -> RecoveryReady -> Running；
- Background、跨 Service 和陈旧生命周期 Context 仍属于非法调用；Go 无法可靠验证
  goroutine 身份，业务不得把有效生命周期 Context 交给其他 goroutine；
- Node 全部 OnStart 完成后才统一激活普通 Runner。

因此生命周期路径不是伪造一个普通 Task，也不与业务 Ready 队列竞争容量。

### 14.2 M9 停止顺序

M9 只排空自己已经接受的本地 Task：

```text
Service StateStopping
    -> Scheduler 进入 Draining，拒绝新的 DispatchAsync 和框架根任务
    -> 完成 Ready/Running/Waiting
    -> 停止最后一个 Runner
    -> 关闭 DeadlineQueue 并等待 Deadline 控制协程退出
    -> OnStop
    -> Service StateStopped
```

规则：

- 已接受 Task 可以继续调用 Await；
- 没有 RPC Future、Async pending、Timer 或事件登记需要统计；
- 停止 Context 到期时取消仍在 Waiting 的有效 Context；
- Running 中无法抢占的普通 Go 代码只能等待其返回；
- 忽略 Context 的 `fn` 仍可能阻止停止，框架不能安全强杀 goroutine；
- 调度器未完全停止前不能并发调用 `OnStop`；
- M9 的 `OnStop` 仍由 Node 生命周期控制路径调用，不宣称由已经退出的最后 Runner 执行；
- M9 不在 `OnStop` 中提供 Await；
- M16 再加入 RPC/Async pending 排空、finalizer Await 和进程级保底策略。

> M16 最新决策：完整实现时不再先停止最后一个 Runner；排空完成后由最后一个或空闲
> Service Runner 原子进入 Finalizing 并执行 `OnStop`，返回后才结束该 Runner。上面的
> 顺序只描述 M9 当时已经实现的阶段性能力。

这与 M7 当前 `OnStop` 忽略 Context 时仍可能阻塞的 Go 语义一致。默认 Stop Timeout 为无限；
项目显式设置 Deadline 时，业务代码必须传播 Context。

### 14.3 启动失败与回滚

- `OnInit` 失败：Scheduler 尚未启动，不需要停止；
- `OnStart` 失败：Scheduler 尚未启动，继续按 M7 规则调用一次 `OnStop`；
- Scheduler 启动出现框架内部错误：当前 Service 启动失败并触发 Node/Application 逆序回滚；
- 已经启动 Scheduler 的前序 Service 先完成 M9 本地排空，再调用 `OnStop`；
- Scheduler 和 Service 都是一次性对象，停止后不能原地重启。

## 15. 错误码

M9 实现已在详细设计中预留的错误码：

```go
const (
    CodeServiceStopping  Code = 1002
    CodeServiceStopped   Code = 1003
    CodeServiceQueueFull Code = 1004
)
```

并增加：

```go
const CodeServiceNotReady Code = 1006
```

> M16 最新规则另外增加 `CodeServiceFailed=1007`，表示运行期 Scheduler 无法安全恢复后
> 隔离单个 Service；这不是 M9 当时的实现范围。

语义：

- `CodeServiceNotReady`：Service 尚未完成 `OnStart` 或 Scheduler 尚未开放；
- `CodeServiceStopping`：Scheduler 已经进入 Draining；
- `CodeServiceStopped`：Scheduler 已经终止或 Service 已失败；
- `CodeServiceQueueFull`：总任务或 Awaiting 达到上限；
- `CodeCanceled`：有效 Context 被取消；
- `CodeDeadlineExceeded`：有效 Context 超时；
- `CodeInvalidArgument`：nil Task、nil Context、Context 与 receiver 不匹配或无效
  Task Context；
- `CodeInternal`：Task panic 或调度器内部失败。

固定高频错误使用只读哨兵，不在热路径动态拼接 ServiceName、TaskID 和数量。诊断字段进入
结构化日志和统计。

## 16. panic 最小边界

完整异常系统仍属于 M16，但 M9 必须先实现调度器生存所需的最小边界：

- 每个普通 Task 的最外层用户代码调用处恢复一次 panic；
- panic 后当前 Task 标记完成并归还执行槽；
- Accepted/Running/Waiting 计数只清理一次；
- 记录 Service、Node、Task 类型和原始堆栈；
- 后续 Ready 任务继续执行；
- 不增加多档 panic 策略；
- 调度器内部不变量 panic 不在业务 Task 边界吞掉。

M9 没有 RPC 响应和 Future，因此只保证本地 Task 完成与调度器继续运行。M16 再统一：

- RPC `CodeRPCExecutionPanic` 响应；
- Async/Future 完成；
- 生命周期与 Module panic；
- 框架不变量能够证明状态一致时恢复，无法证明单个 Scheduler 一致时只隔离目标 Service；
- 每次 panic 恰好记录一次完整 ErrorStack，不使用堆栈指纹限频。

## 17. 内存、对象池与逃逸

### 17.1 BufferPool 边界

M2 的 `internal/bufferpool` 只池化字节 Buffer。M9 没有网络 payload，不应为了“使用已有
内存池”把 Task、Channel 或 Context 强行塞入字节池。

### 17.2 Task 对象池最终结论

M9 先以不池化 Task 的清晰版本建立了正确性和性能基线，并在完成 Benchmark、逃逸分析、
堆 Profile 和安全池化对照后，最终采用“Task 主对象池化、Task Context 令牌不池化”：

- 每个 Scheduler 使用自己的 `sync.Pool` 复用内部 `serviceTask`；
- 每个根任务仍创建一个唯一 `taskContext`，该令牌永不回池；
- 令牌通过原子 Task 指针绑定当前主对象，Task 完成时先把该指针置空；
- Task 回池前完整清空闭包、Context、交接 Channel、结果、panic 和 Deadline 引用；
- Deadline 索引同时校验 DeadlineID、Await 代次、Task 和唯一令牌；
- 即使业务错误保留旧 Context，旧令牌也只能观察到 nil，不能因主 Task 复用获得新任务
  执行权；
- 普通 Task 不创建交接 Channel，只有真正进入 Await 时才按次创建。

Windows Go 1.26.5 的稳定基准显示：

| 场景 | 不池化基线 | 安全池化结果 |
|---|---:|---:|
| 普通 Dispatch | `531.2 ns/op`、`240 B/op`、`2 allocs/op` | `470.9 ns/op`、`48 B/op`、`2 allocs/op` |
| Await 交接 | `1637 ns/op`、`472 B/op`、`6 allocs/op` | `1583 ns/op`、`280 B/op`、`6 allocs/op` |
| 受控安全 Task 获取/释放 | `160.7 ns/op`、`240 B/op`、`2 allocs/op` | `50.43 ns/op`、`32 B/op`、`1 allocs/op` |

Linux Go 1.26.5 的安全 Task 对照为：不池化 `70.37 ns/op`、`240 B/op`、`2 allocs/op`，
池化 `47.87 ns/op`、`32 B/op`、`1 allocs/op`。收益主要来自消除约 200 Byte 的
`serviceTask` 主对象分配；仍保留的唯一令牌分配是旧 Context 防 ABA 的必要成本，不为追求
零分配而复用它。

堆 Profile 进一步表明，池化后普通 Dispatch 的剩余主要分配已经变成唯一 Context 令牌和
Benchmark 业务闭包，不再是 `serviceTask` 主对象。该结果同时通过旧 Context、完整清零、
10,000 Waiting、竞态和停止回收测试，因此池化收益明确且安全边界可控。

### 17.3 必须实施的低复杂度优化

- 普通 Task 不创建 goroutine；
- 从不 Await 的 Task 不创建交接 Channel；
- Ready 使用环形队列，不逐节点分配；
- Ready 环形队列复用 `internal/container/ringqueue`，不在 Scheduler 内复制一份算法；
- 队列出队和 Task 完成时清空闭包、Context、结果和 panic 引用；
- Task 主对象进入 Scheduler 私有池，唯一 Context 令牌永不池化；
- 调度器状态使用一个短锁，不在用户代码期间持锁；
- 统计使用原子计数或一次锁内快照；
- 固定错误使用哨兵；
- Await 结果通过闭包局部变量保留，不装箱成 `any`；实现阶段用逃逸分析确认局部结果和
  闭包是否发生不必要的堆分配；
- 反射不进入调度热路径。

## 18. 并发正确性

实现必须明确处理以下竞争：

1. 多 goroutine同时 `DispatchAsync`；
2. 最后一个 Ready 出队与新 DispatchAsync 同时发生；
3. Task 调用 Await 与 Stop 同时发生；
4. `fn` 返回与 Stop 取消同时发生；
5. 恢复项入队与 Runner 空闲同时发生；
6. 恢复项交接与新的 DispatchAsync 同时发生；
7. 多个 Waiting 按任意顺序完成；
8. `fn` panic 与 Stop 同时发生；
9. Context 超时发生在外部 I/O 阶段或恢复排队阶段；
10. Task 完成与 Draining 空集合判断同时发生。

所有状态转换集中在调度器短锁中裁决。Channel 只用于唤醒和执行权交接，不作为任务状态
的唯一事实来源。

## 19. 可观测性

M9 至少保留：

- 当前 Accepted、Ready、Running、Awaiting；
- DispatchAsync 接收和拒绝总数；
- Task 完成和 panic 总数；
- Await 发起、完成、取消和超时总数；
- Runner 和 Deadline 控制协程是否已经退出。

M9 尚无统一指标导出器，因此：

- 当前值通过 `ExecutionStats` 查询；
- 热路径只累计低成本计数；
- panic 使用结构化日志记录一次原始堆栈；
- Ready 排队、Await 外部操作、恢复排队、排空耗时和不同 Waiting 数量下的分位数只在
  Benchmark 与测试中记录，不在 M9 热路径维护直方图；
- 不把玩家 ID、RequestID 等高基数字段加入累计统计。

## 20. 测试要求

### 20.1 单元测试

至少覆盖：

1. 普通 Task 严格 FIFO；
2. 普通 Task 连续执行使用同一 Runner；
3. 多提交方不会产生两个活动 Runner；
4. 任意时刻最多一个 Task 访问 Service 状态；

8. Await 释放执行槽后其他 Task 可以运行；
9. 恢复项排在已有 Ready 后面；
10. 交接后原 goroutine继续执行；
11. 同一 Task 连续多次 Await；
12. 多 Waiting 乱序完成；
13. Context 与 receiver 不匹配、错误 Context、Background Context 和嵌套 Await；
14. 显式、Service、Node、内置 `15s` Deadline 优先级；
15. 外部函数返回后恢复排队超时；

17. `fn` 观察 Context 后正常取消恢复；
18. `fn` panic 先恢复执行权，再由 Task 边界处理；
19. panic 后后续 Task 继续执行；
20. 总任务和 Awaiting 上限；
21. 恢复项在满容量下仍可进入；
22. Draining 拒绝新的 DispatchAsync；
23. Stop 排空 Ready、Running 和 Waiting；
24. 停止后没有 Runner 和残留 Task 引用；
25. 重复启动和重复停止不会重启一次性调度器；

27. Queue 关闭、到期批量 Drain 和 Scheduler Stop 竞争时只清理一次；
28. `StartScheduler` 部分启动失败会关闭 Queue 并回收全部已创建 goroutine；
29. 停止 Context 到期会取消 Await，但忽略 Context 的函数不会导致 `OnStop` 并发执行；
30. `internal/container/ringqueue` 的空队列、扩容、回绕、硬上限和引用清理；
31. 配置默认值、非法值和未知字段。

## 21. M9 完成标准

M9 只有同时满足以下条件才算完成：

1. 一个 Service 永远最多一个业务 Task 持有执行权；
2. 普通 Task 复用 Runner，不创建每任务 goroutine；
3. Await 明确释放、FIFO 恢复并保留原 Go 调用栈；
4. fn 在原任务 goroutine执行，不创建辅助 goroutine；
5. 对遵守 Context 的等待函数，panic、取消、超时和停止都不会遗留永久 Waiting；
6. 配置容量能够稳定拒绝过载；
7. 停止后 Runner、Deadline 控制协程和 DeadlineQueue 全部退出；
8. M7 生命周期、命令和跨平台行为不回归；
9. Windows/Linux 全仓测试和竞态测试通过；
10. Benchmark、分配、逃逸和内存结果写入 M9 实施验收记录，并明确记录 Task 最终是否池化；
11. 没有接入 RPC、业务 Timer、Module 或 Discovery；
12. 实现完成后形成独立 Git 提交。

## 22. 开工 Review 已确认

开发者于 2026-07-27 确认按开发指导原则执行以下结论：

1. 公共切回 Service 执行上下文使用
   `Service.DispatchAsync(func(context.Context)) error`，不再使用含义过宽的 `Task/Post`
   外观；
2. 通用 Await 使用
   `Service.Await(ctx, func(waitCtx context.Context) error) error`，通过局部闭包变量接收
   任意业务结果；
3. 不公开泛型 `service.Await[T]`、`AwaitFunc` 或不接收 Task Context 的 Await 重载；
4. RPC、Timer、`DispatchAsync`、异步事件和 Module 业务入口统一由框架提供 Origin
   Task Context；Context 可沿当前调用栈传递，其他 goroutine 可观察派生 Context 的取消，
   但不得用它调用需要当前执行权的 Service API；跨 goroutine 结果使用 `DispatchAsync`；
5. 跨包装配只增加 `StartScheduler/StopScheduler` 两个框架函数；`StartScheduler` 额外
   接收 Node 内部 TimerEngine，Engine 仍归 Node 所有；
6. `SetDefaultAwaitTimeout` 只允许在 `OnInit` 调用；
7. 每个 Node 的默认配置使用 `max_tasks=20000`、
   `max_await_tasks=10000`、`default_await_timeout=15s`；
8. Ready 使用 `internal/container/ringqueue` 中的可增长环形队列，从
   `min(64, max_tasks)` 开始增长，硬上限可配置但不得超过 `65536`；固定容量 Channel
   会按每个 Service 的最大容量预分配，而且不能消除 Scheduler 状态锁，因此不作为 Ready
   容器；
9. 容量只保留总任务和 Awaiting 两个限制，恢复项永不二次拒绝；
10. M9 不实现软过载状态机或专用限频器，只保留硬上限、最高水位和拒绝计数；
11. 每个 Service 只使用一个业务 Ready FIFO 和独立控制状态，首版不增加业务优先级队列；
12. Await Deadline 直接登记到 M8 TimerEngine，不创建第二个 Runtime Timer、临时堆或
    时间轮；
13. 每个 Scheduler 使用一个内部 Deadline 控制协程及时消费 M8 到期 ID；该协程只取消
    Context，不执行业务代码；
14. Scheduler 在 `OnStart` 成功后启动，在 `OnStop` 前完成本地任务排空；M9 的
    `OnStop` 仍由 Node 生命周期控制路径调用；
15. M9 本里程碑的 Await 只允许普通 Scheduler Task；M14 按第 14.1 节补充不伪造 Task 的
    OnStart 生命周期 Await；
16. M9 实现 Task panic 后归还执行槽所必需的最小恢复，完整异常系统仍在 M16；
17. M9 先建立不池化 Task 的正确性基线，但里程碑完成前必须通过 Benchmark、逃逸分析和
    堆 Profile形成最终池化决定；确有明显收益且风险可控时在 M9 内直接实现；
18. 增加 `CodeServiceNotReady=1006`，Awaiting 过载复用
    `CodeServiceQueueFull`；
19. 满载只拒绝新根任务；恢复和控制路径必须可进入，框架不阻塞、不覆盖旧任务；
20. M9 只接入 M8 TimerEngine 的内部 `DeadlineQueue`，不接入远程 RPC、Future、公开
    `ITimer`、Module、事件或 Discovery；
21. RPC、Timer、事件和 Module 的具体准入、pending 与过载行为留到各自里程碑，不在 M9
    提前设计；
22. 上述结论已经允许编写
    `docs/plans/M9-服务调度与协作式等待实施计划.md`。

## 23. 实施与验收结果

M9 已于 2026-07-27 完成实现和验收：

1. 新增 `internal/container/ringqueue`，从 64 槽按需增长到配置硬上限，出队和清空均释放
   引用；
2. 每个 Service 建立一个串行 Scheduler、一个 Ready FIFO、一个活动 Runner 和一个
   Deadline 控制协程；
3. `DispatchAsync`、`Await`、默认超时设置和统计快照已经加入 `IService`；
