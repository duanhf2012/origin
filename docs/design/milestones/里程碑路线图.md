# Origin 第三版里程碑路线图

> 文档状态：已确认  
> 确认日期：2026-07-25  
> 最后更新：2026-07-29

## 1. 目标

Origin v3 不再用一个大里程碑同时实现基础库、运行时、调度器、代码生成、RPC 和优雅停止。

新的里程碑遵循：

1. 每个里程碑只交付一个边界清晰、可以独立测试的结果；
2. 前置基础库不依赖 Application、Node、Service 或 RPC；
3. TCP 与 NATS 基础库只处理连接、字节和资源生命周期，不提前包含 RPC 方法、ServiceName、ContractID 等语义；
4. 后续里程碑只能依赖已经验收的前置里程碑；
5. 已经讨论完成的详细设计继续作为设计储备，进入对应里程碑时再裁剪实现范围；
6. 每个里程碑完成后保存测试、Benchmark、分配和竞态检测基线。

每个里程碑对应的必读设计、缺失设计和 Review 门禁见[里程碑设计文档复核清单](./里程碑设计文档复核清单.md)。

## 2. 前置独立库阶段

### M0：工程基础

- Go module、目录和包边界；
- 最低 Go 版本和基础依赖规则；
- 轻量错误类型与基础错误码；
- BuildTime、版本和提交信息注入；
- 单元测试、Benchmark、竞态检测和生成代码校验入口。

M0 不依赖 Zap、Protobuf、NATS 或 Application。

### M1：日志库

- Zap 类型化日志门面；
- 控制台和文件独立级别；
- 异步日志协程与开发同步等待模式；
- 文件行号、`ErrorStack`、滚动、保留、压缩和 crash 文件；
- 可替换 Handler 和自定义 Encoder。

### M2：内存复用库

- 内部 Buffer、容量档位和单一所有权；
- Reset、重复释放检查和大 Buffer 回收边界；
- 逃逸分析、分配 Benchmark 和突发流量后的内存滞留测试。

M2 不实现 `pendingCall`、TimerEntry 或 Protobuf 消息池，这些对象进入其所属运行时里程碑。

### M3：基础配置库

- 配置目录递归扫描；
- YAML、JSON 文件读取；
- 确定性文件顺序；
- 重复定义、非法格式和来源位置错误；
- 配置片段解析到强类型结构体。

M3 不提前定义完整 Application、Node、Service 业务配置模型。

### M4：程序命令与进程控制

> 状态：已完成并通过 Windows、Linux 原生验收及 macOS 交叉构建。

- Command Runner；
- `start`、`stop`、`help`、`version` 和自定义离线命令；
- 必填 `--app-name`、PID 文件锁、Unix 信号和 Windows 普通控制台停止请求文件；
- BuildTime 在 help 中的条件显示；
- 通过可注入的生命周期 Handler 和测试进程验证，不依赖真实 Application。

详细范围、开工 Review 和验收结论见
[M4 程序命令与进程控制库设计](./M4-程序命令与进程控制库设计.md)。

实际 Application 的启动和优雅停止接入放在 M16。

### M5：TCP 网络基础库

> 状态：已完成并通过 Windows、Linux 原生网络验收及 macOS 交叉构建。

- Listener、Connection 和连接关闭；
- RPC 与后续 TcpModule 共用的长度帧、最大包限制、完整写入和短写处理；
- 一、二、四字节长度字段以及大端、小端，RPC 固定四字节大端；
- 允许空 payload，有界帧数与字节数发送队列、非阻塞过载返回；
- TCP 库允许上层设置队列容量、读空闲超时和写超时，M13 RPC 使用自己的默认覆盖；
- 与 M2 Buffer 的收发、队列和 TcpModule 异步事件所有权转移；
- 直接读入最终池化 Buffer，并通过 scatter/gather Benchmark 验证低拷贝发送；
- 网络 goroutine 的创建、退出和泄漏检查。

M5 不包含 RPC RequestID、ContractID、MethodID、ServiceName、错误映射和路由，也不包含
TcpModule 的 ClientID、Processor 和 Service 事件 API。

### M6：NATS 基础库

> 状态：已完成并通过 Windows、Linux 真实 NATS 验收及 macOS 交叉构建。

- NATS 连接、普通发布订阅和 Queue Group 基础封装；
- Context、超时、重连通知和关闭；
- 连接及订阅资源回收；
- 原始 `[]byte` 所有权、固有 GC 分配基线和慢消费者保护；
- 面向真实 NATS 的集成测试。

M6 不生成 RPC 方法，也不强迫 NATS 与 TCP 暴露完全相同的基础接口。二者在后续 RPC
Transport 适配层接入同一 RPC Runtime。

## 3. 框架核心阶段

### M7：Application、Node 与 Service 最小生命周期

状态：已完成并通过 Windows/Linux 验收。

- Application 管理并选择启动一个或多个 Node；
- `application`、`node`、`service` 三个单向依赖公共包；
- `app.Setup` 登记 Service 类型，普通与模板 Service 创建和 Node 归属；
- `application.New()` 不接收业务配置，最终业务入口只调用无参数 `app.Start()`；
- Application 内部完成 M3 配置加载、M4 命令适配和 Node 选择；
- 最终可执行程序可以在 `init_*.go` 中向自己明确持有的 Application 实例登记 Service；
- Node 与 Service 基本状态机；
- 最小配置模型、Options 默认无限等待的生命周期超时和显式启停顺序；
- 不使用包级全局 Service 实例或 Node 单例。

### M8：Node 时间轮内核

状态：已完成并通过 Windows/Linux 原生验收及 macOS 交叉构建。

- [M8 Node 时间轮内核设计](./M8-节点时间轮内核设计.md)；
- 每个 Node 一个独立 TimerEngine；
- 五层、每层 256 槽、基础精度 10ms 的分层时间轮；
- 单一可复用唤醒源，空闲时不按 10ms 固定轮询；
- 一次性内部 Deadline、取消、独立 `DeadlineQueue` 到期交付和批量关闭；
- 到期只交付 ID，不执行 Service 或业务回调；
- `timerEntry` 对象池、百万活跃 Deadline 容量和延迟基线；
- 不接入 Service、Await、RPC、`ITimer`、Ticker 或 Cron。

### M9：Service 调度、Await 与内部 Deadline

状态：已完成实现和 Windows/Linux 验收。

- [M9 Service 调度与协作式等待设计](./M9-服务调度与协作式等待设计.md)；
- FIFO Ready 队列和单执行槽；
- `internal/container/ringqueue` 可增长 Ready 容器；
- 普通任务 Runner 复用；
- Await 挂起、替代 Runner 和恢复交接；
- 每个 Service 一个只消费到期 ID、取消 Context 的 Deadline 控制协程；
- Await Deadline 直接使用 M8 TimerEngine，默认 15 秒；
- Task Context 不跨 goroutine调用 Service 执行权 API；
- 默认 `max_tasks=20000`、`max_await_tasks=10000` 和硬过载上限；
- Task 主对象按实测结果使用 Scheduler 私有池，唯一 Context 令牌不池化并防止旧 Context
  ABA；
- 暂不接入远程 RPC。

### M10：Service Timer 接入

- 状态：已完成实现和 Windows/Linux 验收。
- [M10 Service 定时器接入设计](./M10-服务定时器接入设计.md)；
- 公开 `TimerID` 和组合到 `IService` 的 `ITimer`；
- 与 v2 规范名称对齐的 `AfterFunc`、`NewTicker` 和 `CronFunc`；
- `PauseTimer`、`ResumeTimer` 和指针形式的 `CancelTimer`；
- Timer 到期回调统一进入 M9 Service Ready FIFO；
- 默认不增加配置，特殊场景使用 Application TimerOptions；
- 每个 Node 默认最多三百万个业务 Timer，全部 Service 共享且不预分配；
- NewTicker/Cron 连续 panic 达到 99 次后取消后续触发；
- 周期触发合并、Timer 资源作用域、Cron 时区和 Service 生命周期清理；
- 复用 M8 TimerEngine，不建立第二套时间结构；
- 已完成三百万业务 Timer/Deadline 容量、对象池、Race、覆盖率和跨平台构建门禁。

### M11：RPC 契约、代码生成与本地 Dispatcher

- [M11 RPC 契约与代码生成设计](./M11-RPC契约与代码生成设计.md)；
- `//origin:rpc` Go 接口契约扫描、模块级 `origingen rpc ./...` 生成命令和
  `origingen rpc --check ./...` 只读校验命令；
- ContractID、MethodID、完整契约指纹、稳定性和碰撞失败规则；
- 顶层 Protobuf 消息、基础标量、字符串、`[]byte`、普通指针、数组、Slice、Map、普通
  结构体和嵌套 Protobuf 的静态编解码；
- 单一生成客户端与 `rpc.Target`，通过 `ToService`、`ToServiceOnNode` 表达目标；
- 强类型 `AsyncXxx`、`AwaitXxx`、`NotifyXxx`、`BroadcastXxx` 客户端；
- 服务实现自动识别、静态 Dispatcher 和 Node 注册绑定；
- 同一 Node 内经过真实编码、调度、业务方法和解码的 RPC 闭环；
- 普通结构体按导出字段声明顺序编码且不使用 Tag/字段 ID，Map 不排序，递归类型在生成期
  拒绝；
- 生成前校验完整可达类型图，任何不支持类型都报告完整路径并阻止全部生成物写入；
- 编码先计算大小再一次取得最终 Buffer，热路径不使用反射、JSON、字符串查找或运行时
  Codec 分派；
- 不经过 TCP/NATS，不引入 RequestID、pendingCall、服务发现、多 Node Broadcast 或复杂
  路由。

M11 的目标是一次锁定契约、生成物、常用 Go 数据类型和运行时边界。普通结构体、容器及
嵌套 Protobuf 必须与本地 Dispatcher 一起验收，避免网络传输开工后再修改数据协议。

### M12：Origin 自定义静态编解码扩展

- 实施状态：已完成，Windows/Linux 验收通过；
- 自定义静态编解码扩展边界；
- 自定义 Codec 的声明、优先级、错误语义、Buffer 所有权和 Codec ID/版本指纹；
- `time.Time` 等不能由“只处理导出字段”规则完整表达的特殊类型；
- 由代码生成选择 Codec 并产生静态直接调用，不引入运行时注册表、Map、接口查找、反射、
  JSON 或运行时类型分支作为回退；
- 不接入 TCP/NATS，以自定义编解码往返、分配和延迟 Benchmark 独立验收。

### M13：TCP RPC 端到端闭环

- 状态：已实现并完成 Windows/Linux、真实双进程、Race、Fuzz、Benchmark 和交叉构建验收；
- RPC 线协议；
- 静态 `NodeID + ServiceName` 目标；
- RequestID、pendingCall、超时和断线完成；
- 单向关注建立一条有向连接，双方互相关注时最多两条物理连接；
- 握手固定 Node 身份并返回公开 Service 契约目录；
- 相同 NodeID 的先建立连接保留，后来重复连接拒绝；地址只允许显式 Remove 后迁移；
- 逻辑目标有效期间的有界退避重连，旧连接断开不自动重发非幂等 RPC；
- 调用方断线后，目标 Service 已准入任务继续执行到完成或原 Deadline；
- 调用方复用 M8/M9 唯一 Deadline，目标端复用 Node 共享 M8 DeadlineQueue；
- BufferPool 使用 headroom 原地前置协议头，避免复制完整业务 payload；
- pendingCall 以值存入会话 Map，跨平台热路径基准为零分配，不增加对象池；
- M11 RPC Runtime 和静态编解码器、M12 自定义扩展与 M5 TCP 的 Transport 适配；
- 单进程双 Node 和双进程单 Node 使用相同真实 TCP 路径。

### M14：服务发现本地目录与关注筛选

- 每个 Node 独立拥有本地发现目录和不可变可见快照；
- 完整原始快照输入、`allow_discovery` 筛选、稳定 Diff 和原子发布；
- `NodeID + ServiceName` 精确索引和按 ServiceName 的候选索引；
- TCP/NATS 共用同一发现事实，远端发送前必须先确认目标可见；
- M13 TCP 临时目标表改由目录差异驱动；
- 多监听器、注册补发及 Service FIFO 调度；
- 公开发现查询、`AwaitService`、`AwaitNodeService` 和 OnStart 生命周期 Await；
- 全部 Service 的 OnStart 成功后一次性越过 Node 就绪发布屏障；
- 公共 Provider 契约与 Origin 进入 M17，etcd 在不改变公共契约的前提下进入 M18。

### M15：NATS RPC 端到端闭环

- 已于 2026-07-29 实现并完成 Windows、Linux、嵌入式及真实三节点 NATS 集群验收；
- 依赖 M14 公共发现快照；
- M11 RPC Runtime 和静态编解码器、M12 自定义扩展与 M6 NATS 的 Transport 适配；
- Node 级稳定请求/响应 Subject 与普通 Publish，ServiceName、RequestID 保留在线协议；
- 与 TCP 一致的调用、超时、取消和错误外观；
- 明确目标 Node Subject、服务入口过载响应和慢消费者观测；
- Running 与 Retired 都正常处理 RPC，业务自行决定退休期间的拒绝规则；
- TCP/NATS Transport 队列只限制消息数量，`max_payload_size` 独立限制单个业务
  payload；TCP 出站使用 `send_queue_messages`，NATS 入站回调使用
  `receive_queue_messages`；
- 同批迁移 M13 TCP 开发期配置名、删除 M5/M6 历史字节额度并完成 TCP 全量回归；
- 为 M16 准备停止入站和最终关闭两个 Transport 阶段；
- Windows/Linux 三节点 NATS 集群故障与性能验收；
- 不在 NATS 适配器复制代码生成和业务 API。

### M16：完整停止、异常恢复与进程集成

> 状态：已完成并通过 Windows、Linux、Race、真实 TCP 与三节点 NATS 集群验收。

- 详细方案见[M16 完整停止、异常恢复与进程集成设计](./M16-完整停止异常恢复与进程集成设计.md)；
- 为 `OnStop` 建立不调度普通业务 Runner 的独占生命周期 Await；
- Stop 停止准入和既有任务排空；
- Waiting、pendingCall 和 Await 恢复清理；
- 独占 finalizer 与 `OnStop(ctx)` 中的 Await RPC；
- 单个任务调用边界 panic 打印完整堆栈、只结束问题任务并继续 Service；真正框架不变量
  panic 采用分级恢复，无法证明 Scheduler 一致时只隔离目标 Service；
- TCP/NATS 整体故障在 Application 生命周期内持续恢复，不因普通网络错误自动停止进程；
- 提供无锁 `HealthStatus()`、`TransportStatus()` 和 Failed Service 本地诊断，区分生命周期、
  存活、就绪与降级；
- 在 M7 已完成的 M4/Application 接入上补齐完整排空、异常退出和退出码；
- 日志最终排空、资源逆序释放和进程退出码。

### M17：公共服务发现 Provider 与 Origin 内置发现

- 实现一个公开 `discovery/provider` SPI、一个 Application 私有注册入口和最小
  Factory/Provider 契约，允许未来接入 Consul 等自定义 Provider；
- 每个 Node 独占 Provider 实例，Provider 只能通过受限能力提交完整权威快照和报告状态，
  不能直接访问 Directory、RPC Runtime 或业务监听器；
- 框架统一负责快照校验、容量边界、TTL 旧快照保留、事件差异、Readiness 和
  `DiscoveryStatus()`；
- Provider 控制连接中断立即进入 Recovering，权威删除立即产生 Lost；仅在一个 TTL 后仍
  未恢复时清空旧快照；
- NATS 在业务 `OnStart` 前完成本地连接与订阅，TCP 完成监听与拨号管理器启动；Await RPC
  可以在 Context 内等待可发送 TCP 候选，不要求全局连接全部远端 Node；
- Origin 控制通道固定使用独立 TCP，不复用业务 RPC Transport、连接或协议；业务使用
  NATS 的 Node 也只额外建立一条轻量控制连接；
- `DiscoveryService` 可以与任意业务 Service 配置在同一 Node，不要求专用 Node；框架需
  在基础设施阶段先 Prepare 控制 Listener、再同步当前 Node Provider，且不改变普通业务
  `OnStart` 顺序；
- 实现单实例 Origin `DiscoveryService`、注册、心跳、TTL、首次全量、连续 Revision
  Delta、缺口全量重建和有界慢客户端隔离；
- 新 ServerEpoch 使用一次固定 1～5 秒权威收敛窗口，避免部分重注册目录制造伪 Lost；
- M17 限定可信内网，不实现 TLS、认证或未使用安全配置；安全通信后续独立立项；
- Hello 只同步目录，全部业务 `OnStart` 后再 Publish 完整 RawNode；Delta 只有完整 Node
  Upsert 和 Node Delete；
- TCP 长度分帧复用 M5，Discovery Payload 只包含 FrameType 与 Body，不设独立
  WireVersion、Magic、Checksum 或压缩字段；
- 冻结 `0x01～0x05/0x81～0x87/0xFF` FrameType、逐字段大端二进制布局、严格稳定排序和
  解码前容量校验，不使用 JSON、Protobuf 或反射；
- DiscoveryService 使用单系统 Actor、generation 最小堆和有界命令队列，直接复用 M5
  每连接有界 FIFO Writer；广播只编码一次，发送时复制到连接独占 M5 Buffer；
- 固定最多 8192 个已发布 Node、16384 条控制连接、65536 个公开 Service、16 MiB
  FullSnapshot 和每客户端 64 条待发发现消息，不开放 limits 配置；
- Origin 配置只保留 TTL 与 server Node/listen/address，心跳、超时和退避均由 TTL 派生；
- 私有或零公开 Service Node 仍同步远端目录但不发布空 Node；DiscoveryStatus 明确区分
  `NotRequired/Pending/Published`；
- 提供公开 Provider 一致性测试及 Origin Wire/Fuzz/Race/容量/跨平台/资源泄漏验收；
- 用 Consul 配置、注册、注销、blocking query/index、恢复和健康映射检查 SPI，确保未来
  只新增 Provider 包与配置块；M17 不实现 etcd、Consul、动态 `.so` 或 Provider sidecar
  协议。

### M18：etcd 服务发现 Provider

- 复用 M17 已冻结的 Provider SPI、状态机、完整快照 Sink 和一致性测试；
- 固定 `go.etcd.io/etcd/client/v3 v3.7.1`，兼容验证 etcd Server `3.6.14+` 和 `3.7.x`；
- 一个 Provider 连接一个逻辑集群并复用多 Endpoint，不聚合多个独立集群；
- 实现 namespace、必填本地网络、最多 64 个有效读取网络、认证和 TLS；
- 使用确定性 Protobuf 记录、Lease 和 Txn/CAS 维护本 Node 注册与 Session 所有权；
- 使用线性化分页 Range、固定 revision 和逐网络 Watch 建立私有权威镜像；
- 使用 `WithRequireLeader`、progress、ClusterID 和 Compaction 重建检测并恢复失活 Watch；
- Watch 压缩或断流后持续恢复，确定性鉴权、权限和配置错误立即暴露；
- etcd revision 和 LeaseID 保留在 Provider 内部，不进入 Directory、RPC 或业务 API；
- Withdraw 使用 ModRevision 与 SessionID 精确删除，Close 等待全部 Client/goroutine 退出；
- 完成真实 etcd 集群、Lease 过期、Watch 重建、认证/TLS、Race、容量和性能验收；
- 以不修改 Node、Directory、RPC 和业务发现 API 作为完成门禁，并用设计级 Consul 映射
  复核公共契约，但不在 M18 实现 Consul；
- Key 固定按 Network 前缀分层；`namespace` 可选且默认 `/origin`，最终 Review 已通过。

## 4. 后续能力

M18 之后再按独立系统继续增加小里程碑，包括：

| 能力 | 处理方式 | 前置依赖 |
|---|---|---|
| Module 静态树 | 独立里程碑，生命周期与 Service 对齐 | M16 |
| 同步与异步本地事件 | 独立里程碑，复用 Service 调度器 | M16 后；Module 接入时再组合 |
| Service 业务配置访问 | 独立里程碑，复用 M3 根配置 | M16 |
| 发现、失去发现、退休与恢复事件 | 服务发现状态机的一部分 | 服务发现 Provider |
| 关注筛选、Node 标签 | 服务发现筛选里程碑 | 服务发现 Provider |
| RoundRobin、Rand、ModKey、自定义路由 | RPC 路由里程碑 | 服务发现快照 |
| Broadcast 的多 Node 发现扩展 | M11 已生成统一 API 并实现当前 Node 本地投递；后续按发现快照扩展候选 Node | M14 与 M13/M15 |
| 外部 gRPC | 可选插件，不成为 Origin Native RPC 依赖 | M11、M12 |
| TcpModule | 独立适配器，复用 M5 | M16 |
| KCP、WebSocket、HTTP | 各自独立 Transport/Service 适配器 | 按实际项目需要 |
| Redis、数据库、MongoDB、Kafka | 独立 Module/适配器，复用通用 Await | M16 后的 Module 里程碑 |
| RPC 压缩 | 默认不实现，只有真实基准证明净收益后立项 | M13、M15 |
| 流式 RPC | 首版明确不支持，有实际业务需求后重新设计 | M13、M15 |

这些能力不再集中到一个“核心完备”里程碑，而是每个系统单独建立里程碑和实施计划。

普通 Go 类型、自定义结构体和混合 Protobuf 序列化已经从后续储备前移到 M11，不再允许
传输层先实现、数据契约后补齐。

## 5. M11～M16 范围防遗漏规则

1. M11 固定“契约、调用外观和内置数据表示”，M12 只补充自定义静态 Codec，
   M13 增加 TCP Transport，M14 增加公共服务发现目录、OnStart 生命周期 Await 和 Node
   就绪发布屏障，M15 增加 NATS Transport，M16 增加 OnStop 独占 Await、完整停止和异常
   收尾；
2. M11 的同 Node 闭环也必须经过生成编解码和 Service Ready FIFO，不允许直接调用业务
   方法形成只在开发环境成立的隐式短路；
3. M13/M15 不重新生成客户端、Dispatcher 或 Codec，不复制调用语义；M14 不复制
   TCP/NATS 各自的目标目录；
4. M11 内置数据表示完成前不得开工 M13；M12 自定义 Codec 只扩展特殊类型，不能修改
   M11 已冻结的数据布局；
5. 延后能力必须保留在本路线图、设计文档索引和迁移矩阵三处，进入实施前再分配实际编号；
6. 明确“不支持”的接口嵌入、多公开契约、流式 RPC、隐式 JSON/反射回退和手工覆盖 ID，
   不属于遗漏；只有真实需求证明收益后才重新 Review。

## 6. 执行规则

1. 当前只为即将开工的里程碑编写可执行实施计划。
2. 后续里程碑只保留范围和依赖，不提前锁死内部实现。
3. 一个里程碑未通过验收，不同时开工依赖它的后续里程碑。
4. 发现前置设计不足时，先回到对应详细设计确认，不把临时决定埋进实现。
5. 原最小闭环文档仅作为 M7～M16 的拆分储备。
6. 开工前必须在[里程碑设计文档复核清单](./里程碑设计文档复核清单.md)中完成 Review 记录；仍有草案或待补设计时不得编写实现代码。
