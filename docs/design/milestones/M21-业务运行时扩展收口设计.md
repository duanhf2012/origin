# Origin 第三版 M21 业务运行时扩展收口设计

> 文档状态：已实现并通过完整验收，第一批 15 项全部采用方案 A
>
> 启动日期：2026-08-01
>
> 前置里程碑：M3、M7、M9、M10、M14、M16、M17、M18、M19、M20

## 1. 里程碑目标

M21 是 Origin v3.0 最后一个业务能力里程碑，只收口四组已经进入设计储备、但尚未落地的
运行时扩展：

1. Service 业务配置访问；
2. Service—Module—子 Module 静态树；
3. Service 内本地同步/异步事件；
4. Service 公开 Retire/Resume 及发现状态更新。

四组能力保留各自独立的内部边界、测试和提交，但统一使用 `M21` 编号。M21 完成后只剩
M22 v3.0 稳定发布，不创建 M23，也不把外部数据库、Redis、Kafka、HTTP、KCP、WebSocket、
TcpModule 或 gRPC 适配器塞入 M21。

## 2. 必须继承的已确认结论

### 2.1 Module

- Module 是 Service 内部静态组件，不是部署、发现、RPC 路由或独立配置单元；
- 只允许在 `OnInit` 中构建静态树，业务使用普通强类型字段持有子 Module；
- 生命周期为 `OnInit`、`OnStart(ctx)`、`OnStop(ctx)`；启动父先子后、停止严格反序；
- 全部 Module 启动后才调用 `Service.OnStart`，`Service.OnStop` 在全部 Module 停止前调用；
- Module 复用所属 Service 的 Scheduler、TimerEngine、RPC、Await 和事件总线，不创建第二个
  Service 执行槽；
- Module 具有独立资源归属，用于 Timer、事件订阅、待投递任务和最终引用清理。

### 2.2 Service 业务配置

- 公开外观保留 `GetConfig(path, dst)`、`GetServiceConfig(path, dst)` 和
  `ParseServiceConfig(dst)`；
- Service 与全部 Module 共享同一份只读有效配置；
- `node_services.<NodeID>.<ServiceName>` 存在时整体替换公共配置，不做递归合并；
- 点分路径只访问 Mapping，不提供数组下标、通配符或转义；
- 推荐在 `OnInit` 一次解析到强类型字段，业务热路径不反复做字符串查找；
- 不增加 Viper、mapstructure 或其他配置依赖，不向业务返回内部可变 Map/AST。

### 2.3 本地事件

- 每个 Service 一个事件总线，Service 与全部 Module 共享；
- 订阅只允许在 `OnInit`，注册顺序就是监听顺序；
- 异步事件进入 M9 普通 Ready FIFO，外部 goroutine 只能异步投递；
- 同步事件只允许当前合法持有 Service 执行权的 Task 调用，不入队、不创建 goroutine；
- 同步和异步名称必须明确，不提供运行期 `EventMode`；
- Module 停止、启动回滚和 Service 停止都自动清理对应订阅。

### 2.4 Retire/Resume

- `Retired` 是稳定、可观察的运行状态，不是 Stop 的别名；
- Retired 仍正常处理精确 RPC、Notify、Broadcast、本地事件、Timer、Await 和后台任务；
- 自动单目标与 Broadcast 默认排除 Retired，`IncludeRetired()` 显式纳入，精确 `OnNode`
  始终允许；
- 退休不产生 Lost，不关闭 TCP/NATS，不暂停 Timer，不自动排空或停止；
- `CodeServiceRetired` 只由业务主动返回；
- 只有明确 Stop 能进入 Stopping，且 Stop 一旦发布便不能 Resume。

`Resume` 的唯一含义就是把仍在正常运行、但状态为 `Retired` 的 Service 显式恢复为
`Running`。它不是重新启动：已经进入 `Stopping`、`Stopped` 或 `Failed` 的一次性 Service
不能 Resume，也不会重新执行 `OnInit` 或 `OnStart`。

## 3. 当前代码事实

M21 设计以 `9a48c8c` 后的实现为准：

- `service.State` 目前只有 Created～Running、Stopping、Stopped、Failed，尚无 Retired；
- Discovery Provider DTO、M14 Directory、M19/M20 路由已经识别远端 Retired；
- `node.publishDiscovery` 当前总把本地公开 Service 编码为 Running，且只在启动时发布一次；
- Application 保存合并后的 `map[string]any`，M3 的严格来源树在 `LoadDir` 返回后没有保留可
  复用的只读解码视图；
- `service.Service` 已拥有 Scheduler、Timer、Await、DispatchAsync、GoSafe/RunSafe 和 Runtime
  接缝，但仓库尚无 Module 或本地事件实现；
- M17 Provider `Publish` 已接受完整 Node 期望，Origin/etcd Provider 都能保存最后期望并在
  连接恢复后重发，不需要修改第三方 Provider SPI。

## 4. 总体方案比较

### 方案 A：M21 内四个有序工作包（推荐）

先建立可复用的只读配置快照，再建立 Module 静态树和资源归属，随后在同一资源边界接入
本地事件，最后增加 Retire/Resume 与完整 Node 状态重发。每个工作包独立测试、Benchmark
和提交，最终用一个集成门禁验证四者协作。

优点是依赖顺序清楚、提交可审查、不会建立一个职责含混的“扩展总线”；缺点是实施计划
较长，但仍只占一个 M21 编号。

### 方案 B：建立统一 RuntimeExtension 抽象

把配置、Module、事件和状态切换都放入一个新的 RuntimeExtension，再一次性接入 Service。
集中装配较快，但四种完全不同的生命周期和性能路径会被迫共享大接口，后续适配器也容易
绕过 Service 原有能力，不建议采用。

### 方案 C：拆成多个公开包和新里程碑

分别建立 module、event、serviceconfig 和 retirement 公共包或继续增加 M23～M26。概念上
分得最开，但会制造多组 Runtime 适配接口，且直接违反全局编号封顶 M22 的约束，不采用。

## 5. 推荐业务外观草案

### 5.1 Module 与配置

```go
type PlayerService struct {
    service.Service

    config  PlayerConfig
    persist *PersistModule
}

func (s *PlayerService) OnInit() error {
    if err := s.ParseServiceConfig(&s.config); err != nil {
        return err
    }
    s.persist = &PersistModule{}
    return s.AddModule(s.persist)
}

type PersistModule struct {
    service.Module

    config PersistConfig
}

func (m *PersistModule) OnInit() error {
    return m.Service().GetServiceConfig("persist", &m.config)
}

func (m *PersistModule) OnStart(ctx context.Context) error {
    return m.load(ctx)
}

func (m *PersistModule) OnStop(ctx context.Context) error {
    return m.save(ctx)
}
```

`IModule` 与 `IService` 一样完整包含 `OnInit`、`OnStart(ctx)` 和 `OnStop(ctx)`。嵌入
`service.Module` 会为三者提供默认空实现，因此没有初始化、启动或停止逻辑的 Module 可以
只覆盖实际需要的方法；上例显式写全三项，是为了展示完整生命周期外观。

### 5.2 Service/Module 成员事件外观

```go
const PlayerLoginEventID service.EventID = 1001

type PlayerLoginEvent struct {
    PlayerID string
}

func (PlayerLoginEvent) EventID() service.EventID {
    return PlayerLoginEventID
}

func (m *PersistModule) OnInit() error {
    return m.SubscribeEvent(PlayerLoginEventID, m.onPlayerLogin)
}

func (m *PersistModule) onPlayerLogin(
    ctx context.Context,
    event service.Event,
) error {
    login, ok := event.(PlayerLoginEvent)
    if !ok {
        return errs.ErrInvalidArgument
    }
    return m.persist(ctx, login.PlayerID)
}

func (s *PlayerService) playerLogin(
    ctx context.Context,
    playerID string,
) error {
    event := PlayerLoginEvent{PlayerID: playerID}
    if err := s.NotifyEventSync(ctx, event); err != nil {
        return err
    }
    return s.NotifyEventAsync(event)
}
```

`NotifyEventSync`、`NotifyEventAsync` 和 `SubscribeEvent` 归属 `service.Service` 成员；
`service.Module` 提供同名方法并委托所属 Service 的同一个事件总线，因此 Service 和 Module
调用都不需要额外传入 owner 指针。事件按显式 EventID 查找，不设包级可变注册表，也不在
派发热路径反射查类型。

### 5.3 退休与恢复

```go
if err := s.Retire(ctx); err != nil {
    return err
}

// 维护或迁移完成后显式恢复。
return s.Resume(ctx)
```

业务若要在状态变化后调整自己的准入或 Timer，订阅框架内置的强类型
`service.ServiceStateChanged`，不要求所有 Service 为很少使用的状态钩子扩展生命周期接口。

### 5.4 GoSafe 与 RunSafe

`GoSafe(fn)` 启动一个新的业务 goroutine，并在该 goroutine 最外层 recover panic、记录完整
堆栈，避免普通业务 panic 直接终止进程。它只提供 panic 保底，不自动重启，也不替业务保存
Context、CancelFunc 或 WaitGroup；业务仍须在 `OnStop` 中 cancel 并 wait。

`RunSafe(fn)` 不创建 goroutine，而是在调用方当前 goroutine 同步执行一个 Job。Job panic
时记录堆栈并返回 `CodeInternal`，外层 Worker 可以继续处理下一项。它不会授予 Service
Scheduler 执行权，因此 Worker 仍不能借此并发修改只允许 Service 单执行槽访问的业务状态。

`RunSafe` 与 `Await` 不解决同一个问题：

| 对比项 | `RunSafe` | `Await` |
|---|---|---|
| 主要目的 | 把单次 panic 转为错误，隔离故障 | 等待慢操作时释放 Service 执行权 |
| 是否创建 goroutine | 否 | 否，等待函数在原 Task goroutine 执行 |
| 是否释放 Service 执行槽 | 否 | 普通业务 Task 中会释放，完成后按 FIFO 恢复 |
| Context/Deadline | 不管理 | 必须使用合法 Task Context，管理取消和 Deadline |
| 典型场景 | AOI、寻路、脚本或插件 Worker 的单个 Job | RPC、数据库、Redis、文件等可能阻塞的等待 |

如果 Worker 只使用 `GoSafe`，其中任意一个 Job panic 后虽然进程不会退出，但整个 Worker
goroutine 已经结束；逐 Job 使用 `RunSafe` 才能记录该 Job 的失败并继续下一项。普通 Service
业务等待 I/O 应使用 `Await`，不需要额外套 `RunSafe`。

典型组合是 `GoSafe` 保护 Worker 顶层，`RunSafe` 保护 Worker 循环中的单个 Job：

```go
func (m *AOIModule) OnStart(context.Context) error {
    m.workerCtx, m.cancelWorker = context.WithCancel(context.Background())
    m.workerWG.Add(1)
    return m.GoSafe(m.runWorker)
}

func (m *AOIModule) runWorker() {
    defer m.workerWG.Done()
    for {
        select {
        case <-m.workerCtx.Done():
            return
        case job, ok := <-m.jobs:
            if !ok {
                return
            }
            if err := m.RunSafe(func() { m.calculate(job) }); err != nil {
                m.release(job)
            }
        }
    }
}

func (m *AOIModule) OnStop(context.Context) error {
    m.cancelWorker()
    m.workerWG.Wait()
    return nil
}
```

## 6. 第一批已确认项

开发者于 2026-08-01 确认以下 15 项全部采用方案 A。完成最终书面复核和实施计划前仍不提前编码。

### 1. M21 内部组织

- **A（已确认）**：按“配置快照 → Module → 本地事件 → Retire/Resume”四个工作包顺序实施，
  最后执行统一集成验收，全部使用 M21 编号；
- B：四组能力一次性大提交；
- C：继续拆新 M 编号。

推荐 A：依赖清楚且符合 M22 封顶。

### 2. Module 公共包与最小接口

- **A（已确认）**：在现有 `service` 包提供 `service.IModule`、`service.Module` 和
  `AddModule(IModule) error`；业务嵌入 `service.Module`；
- B：新建公开 `module` 包；
- C：在仓库根目录新建 `origin.Module` 包外观。

推荐 A：与现有 `service.Service` 一致，不增加循环依赖或第二套基础包，也不返回无业务用途
的 ModuleID。

### 3. Module 能力、资源范围与容量

- **A（已确认）**：Module 直接复用 Timer、Await、DispatchAsync、GoSafe/RunSafe、子 Module
  和事件能力；每 Service 最多 4096 个 Module、树深最多 64，不预分配；停止时按 Module
  归属清理未开始任务、Timer 和订阅；
- B：Module 每次先 `Service()` 再调用全部能力，不建立资源归属；
- C：每个 Module 建独立 Scheduler/队列。

推荐 A：保留便捷外观，同时只有一个 Service 执行槽和一套容量事实。

### 4. 配置内部表示

- **A（已确认）**：扩展 M3 `config` 包，保留一次加载得到的不可变 Snapshot/View；Application
  持有根 Snapshot，Service Runtime 只持有效子视图；现有 `LoadDir` 复用同一解码器；
- B：继续保存 `map[string]any`，每次字段读取重新走 Map/JSON；
- C：引入第三方配置库。

推荐 A：保留来源定位、严格解码和原子写入，不重复 v2 的完整 Marshal/Unmarshal。

### 5. 模板 Service 配置选择

- **A（已按开发者意见确认）**：模板实例创建后与普通 Service 完全一样，只按实际
  ServiceName 读取 `node_services.<NodeID>.<实际ServiceName>`，不存在时读取
  `services.<实际ServiceName>`；不按 TemplateName 回退，也不递归合并；
- B：不存在实际实例配置时回退公共 TemplateName；
- C：模板、公共实例和 Node 实例多层递归合并。

采用 A：TemplateName 只负责创建类型，实例创建后配置、发现和 RPC 都只认实际
ServiceName，规则最少且没有第二套名称语义。需要共享字段时由业务放到自定义根配置并通过
`GetConfig` 读取。

### 6. 配置严格性、默认值与缺失

- **A（已确认）**：这里只指 `services`、`node_services` 和业务自定义根字段
  中的业务配置；业务结构体解码默认忽略未知配置字段，缺失字段保留调用方预填值，零值结构
  自然得到 Go 零值；没有整份 Service 配置时 `ParseServiceConfig` 返回 nil 并保持目标不变；
  只有显式 `GetConfig/GetServiceConfig(path)` 的路径不存在时返回 `ErrConfigNotFound`，避免
  路径拼写错误静默变成零值；框架自身的 Node/RPC/Discovery 配置继续严格校验；
- B：连显式路径缺失也静默返回 nil 并保留目标值；
- C：为每次读取增加 Strict/Optional/Default 等 Options。

推荐 A：业务配置保持宽松和 Go 默认值习惯，同时显式路径仍能发现拼写错误；不增加
Optional、默认值 Tag、必填 Tag 或 Validator 框架。

### 7. 配置生命周期

- **A（已确认）**：M21 配置在 Application 构建时冻结，Service/Module 只在生命周期内读取；
  不实现热更新、远端配置中心或运行期 Watch；
- B：M21 同时加入热更新回调；
- C：每次调用重新读取文件。

推荐 A：符合静态 Module 树和 `OnInit` 强类型缓存，不把热更新一致性风险带入 v3.0。

### 8. 本地事件公开外观

- **A（已按开发者意见确认）**：`SubscribeEvent`、`NotifyEventSync` 和
  `NotifyEventAsync` 作为 `service.Service` 成员方法；`service.Module` 提供同名委托方法；
  Event 通过 `EventID()` 表明类型，采用第 5.2 节外观；
- B：使用需要额外传 owner 的泛型顶层函数；
- C：新增 `origingen event` 代码生成器。

采用 A：事件总线本来就属于 Service，成员方法更自然，Module 也能直接调用，不增加生成
步骤或每次调用都重复传入 Service 指针。

### 9. EventID、注册和静态容量

- **A（已确认）**：业务显式提供非零 `uint32 EventID`；同一 Service 内相同 ID 必须绑定相同
  payload 类型；最多 4096 个 EventID、65536 个监听者，不预分配，不设全局注册表；
- B：运行时用 `reflect.Type` 作为事件身份；
- C：使用字符串名称并在每次派发时查 Map。

推荐 A：稳定、可诊断，反射只允许在 OnInit 做一次类型冲突校验，不进入派发热路径。

### 10. 监听者 error 与 panic

- **A（已确认）**：单个监听者 error/panic 被隔离并继续后续监听者；同步触发在全部监听者完成后
  返回按注册顺序聚合的错误；异步触发记录一次聚合摘要和指标；panic 带本地堆栈但不破坏
  Scheduler 执行权；
- B：首个 error/panic 立即中止后续监听者；
- C：监听者不允许返回 error。

推荐 A：事件是通知边界，一个观察者故障不应静默阻断其他观察者。

### 11. 同步事件中的 Await 与嵌套

- **A（已确认）**：同步监听者禁止 Await，保证 `NotifyEventSync` 是没有调度交错的
  当前调用栈；需要 RPC、数据库或其他 Await 的监听逻辑使用 `NotifyEventAsync`；同步事件
  仍允许嵌套，但单根任务最大深度 64；
- B：允许同步监听者 Await，等待期间释放 Service 执行权，恢复后继续后续监听者；
- C：同步事件自动转异步以避开 Await。

推荐 A：同步事件的状态观察最简单、延迟最低；异步事件仍获得完整 Origin Task Context 并
允许 Await。下方补充示例给出允许 Await 时产生调度交错的对照过程。

### 12. 异步事件调度与 payload 所有权

- **A（已确认）**：一次异步事件只占 M9 `MaxTasks` 的一个 Ready 项，入队时只捕获一次 Go
  值；成功后生产者不得再修改 payload 引用的可变数据，全部监听者在该任务内借用同一逻辑
  payload；框架不做反射深复制，不增加事件专用队列、goroutine 或配置；队列满返回现有
  `ErrServiceQueueFull`；
- B：每个监听者各入队一个任务；
- C：建立事件专用 Channel 和 Worker。

推荐 A：保持全局 FIFO、单执行权和统一过载边界，避免监听者数量放大队列占用。

### 13. Retire/Resume 公共 API 与幂等性

- **A（已确认）**：`Retire(ctx) error`、`Resume(ctx) error` 进入 IService；Running 上 Retire、
  Retired 上 Resume 执行转换，同状态重复调用返回 nil；Starting/Stopping/Stopped/Failed
  返回稳定状态错误；Service Task 内调用不自锁，外部 goroutine 在 ctx 内等待控制任务；
- B：无 Context 的 `SetRetired(bool)`；
- C：只允许 Service 自己在业务回调中修改状态。

推荐 A：语义明确，既支持业务自控，也支持管理协程，并能受取消和 Deadline 约束。
Retired 仍是可工作的运行状态，因此 `GoSafe` 与其他普通业务能力也应把 Retired 视为合法准入；
已经运行的 Worker 不受状态切换影响，新 Worker 是否应启动仍由业务决定。

### 14. 状态事件与发现发布顺序

- **A（已确认）**：Scheduler 边界先提交本地状态和进入时间，再接受一个内置
  `ServiceStateChanged` 异步事件，然后通过 Node 级合并发布器提交最新完整 Node 快照；
  `Retire/Resume` 在 Context 内等待对应或更新 generation 的 Provider Publish Ack。发布失败
  不回滚本地状态，Provider 保留最新期望并持续恢复；
- B：先等待 Provider 成功，再改变本地状态；
- C：只改变本地状态，调用方无法等待远端可见。

推荐 A：本地线性化点明确，业务可以尽快调整精确流量准入，同时仍能知道远端状态是否已经
确认；发布 I/O 通过 Await/Node 发布器执行，不阻塞 Service 唯一执行槽。

示例：`PlayerService` 调用 `Retire(ctx)` 后，先在本地变为 Retired，因此本进程的自动 RPC
候选立即不再选择它；随后 `ServiceStateChanged{Running, Retired}` 进入本 Service 事件队列，
业务可以暂停登录入口但继续存档；Node 再向 Provider 发布包含 Retired 的完整快照。其他 Node
收到快照后也从默认候选移除该实例，但保留发现记录和连接。Provider Ack 后 `Retire` 返回 nil；
若发布暂时失败，`Retire` 返回发现错误但本地仍保持 Retired，Provider 保存最新期望并在恢复后
重发，不能因为远端故障把本地状态悄悄回滚为 Running。

### 15. Node/Application 批量退休

- **A（已确认）**：M21 同时提供薄的 Node/Application `Retire(ctx)`、
  `Resume(ctx)` 编排；Retire 按启动顺序严格逆序，先摘除上层使用者/入口，再处理其依赖；
  Resume 按启动正序，先恢复依赖，再开放上层使用者；继续并聚合错误；不增加
  Node/Application Retired 状态，不增加默认 OS Signal 或命令；Stop 始终胜出；
- B：M21 只提供单 Service API；
- C：恢复 v2 的进程信号并自动退休全部 Service。

推荐 A：Origin 的启动顺序约定为“依赖先、使用者后”，因此退休应使用停止式逆序，恢复应
使用启动式正序，能避免依赖已经退休而上层仍继续接收默认流量。该编排只提供尽力而为的
确定顺序，不伪装跨 Service 事务。

### 补充示例：为什么不建议同步监听者 Await

假设当前任务把玩家等级从 9 改成 10，然后同步触发事件：

```go
func (s *PlayerService) levelUp(ctx context.Context) error {
    s.player.Level = 10
    return s.NotifyEventSync(ctx, PlayerLevelChanged{Level: 10})
}

func (m *RankModule) onLevelChanged(
    ctx context.Context,
    event service.Event,
) error {
    // 如果同步监听者允许 Await，这里会释放 Service 执行权。
    if err := m.Await(ctx, m.loadRank); err != nil {
        return err
    }
    // Await 期间其他任务可能已把玩家升到 11 级。
    // 这里若继续按事件中的 Level=10 覆盖状态，就会写回旧结果。
    return m.applyRank(event)
}
```

允许 Await 时，`NotifyEventSync` 仍会等监听者全部完成才返回，但“同步”不再表示中间没有其他
Service Task 运行。业务必须在每次 Await 后重新校验版本，理解成本较高。调整后的推荐方案是：

- 同步事件只做当前内存状态的快速通知，不允许 Await；
- 需要 RPC、数据库或 Redis 的监听者改用 `NotifyEventAsync`；
- 异步监听者是正常 Service Task，可以 Await，并遵守既有的“恢复后重新校验状态”规则。

## 7. 性能和低延迟约束

M21 实施计划必须保存以下基线并以前后对照验收：

- Module 直接能力调用、资源归属检查和 1/100/1000/4096 Module 启停；

不得为 Module 建独立执行槽，不得为每次事件创建 goroutine，不得在事件热路径反射查类型，

M21 已实现以下公共外观和运行时边界：

- `IService` 组合 `IServiceConfig`，提供 `GetConfig`、`GetServiceConfig` 和

- Service/Module 提供本地同步与异步事件；同步监听者禁止 Await，异步通知只占一个
