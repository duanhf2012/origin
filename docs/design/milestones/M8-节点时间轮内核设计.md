# Origin 第三版 M8 Node 时间轮内核设计

> 文档状态：已实现并通过 Windows/Linux 验收
> 创建日期：2026-07-27
> 适用里程碑：M8
> 前置里程碑：M0～M7

## 1. 结论

M8 先实现每个 Node 独立拥有的时间轮内核，不再让后续 Await、RPC、心跳、重连和业务
Timer 分别使用不同的超时实现。

本里程碑只解决“何时到期、如何取消、如何把到期 ID 交给所属 `DeadlineQueue`”：

- 不依赖 Service Scheduler；
- 不执行用户回调；
- 不提供 `ITimer`、Ticker 或 Cron；
- 不创建“每个 Deadline 一个 `time.Timer` 或 goroutine”；
- 不使用一套临时最小堆，后续再替换；
- 不负责 Context、RPC Future 或业务 Timer 的完成语义。

M9 Service Scheduler 的 Await Deadline、后续 RPC Deadline 和业务 Timer 都必须直接复用
M8，不允许再建立第二套 Deadline 调度器。

## 2. 为什么必须前置

原 M8 调度器草案计划先使用 `context.WithTimeout` 的 Go Runtime Timer，等业务 Timer
里程碑再迁移到 Node TimerEngine。该方案存在以下问题：

1. Await 和 RPC 会先形成一套基于 Runtime Timer 的完成、取消和停止逻辑；
2. 业务 Timer 又会形成另一套时间轮状态和生命周期；
3. 迁移时必须重新处理取消竞态、迟到到期、停止排空和统计；
4. Benchmark 得到的是临时实现数据，不能代表最终游戏服务器运行路径；
5. 与已经确认的“同一 Node 的内部 Deadline 和业务 Timer 共用一套引擎”冲突。

因此现在调整顺序成本最低：M8 尚未编码，可以先建立最终时间基础设施，再让所有上层系统
只负责自己的完成语义。

完整业务 Timer 也不能全部放进 M8，因为 Timer 回调必须进入尚未实现的 Service
Scheduler。把内核和业务接口拆开，可以消除这一循环依赖。

## 4. 分层边界

### 4.1 M8 Deadline 内核

M8 内核负责：

- 使用单调时间计算相对 Deadline；
- 注册一次性 Deadline；
- 按 ID 取消尚未交付的 Deadline；
- 推进分层时间轮；
- 把到期条目移动到所属 `DeadlineQueue` 的到期列表；
- 合并通知 `DeadlineQueue` 有到期项；
- 批量关闭 `DeadlineQueue` 并清理其全部条目；
- 停止 Node TimerEngine；
- 维护内核状态、计数和 Benchmark。

### 4.2 M9 Service Scheduler

M9 负责：

- 为每个 Service 调度器建立一条独立 `DeadlineQueue`；
- 把 Await Task 与内部 DeadlineID 关联；
- 消费 `DeadlineQueue` 的到期列表；
- 取消等待 Context、恢复原任务并映射超时错误；
- 保证到期、外部函数返回和 Stop 竞争时只完成一次。

M8 不认识 Task、Runner、Await 或 `context.Context`。

### 4.3 后续 Service Timer 接入

Service Scheduler 完成后，单独建立业务 Timer 接入里程碑，负责：

- 公开 `TimerID` 和 `ITimer`；
- `AfterFunc`、`TickerFunc`、`CronFunc`；
- 暂停、恢复和指针取消；
- 保存业务回调及其 Service/Module 资源作用域；
- 把到期回调转换成 Service Ready Task；
- 周期触发合并和 Cron 墙上时钟语义。

业务 `TimerID` 与 M8 的内部 `DeadlineID` 不承诺是同一类型。这样公开 ID 可以保持稳定，
而周期 Timer、暂停和恢复可以在内部更换下一次 Deadline，不把业务语义塞入时间轮内核。

### 4.4 后续 RPC 和系统组件

RPC Runtime、TCP 连接管理、服务发现等系统分别创建自己的 `DeadlineQueue`。它们消费到期
ID 后完成各自的 pending call、重连、心跳或 TTL 状态，不经过业务 Service Timer 任务
队列。

## 5. 包和实例归属

### 5.1 内部包

M8 推荐新增：

```text
internal/timerwheel
```

该包只提供给 Origin 自身使用，不成为业务兼容 API。包中不导入：

- `application`；
- `node`；
- `service`；
- `rpc`；
- `tcpnet`；
- `natsnet`。

`node` 可以依赖 `internal/timerwheel`，从而保持依赖方向单一。

### 5.2 每个 Node 一个 Engine

每个 `node.Node` 明确持有一个独立 `Engine`：

- 不使用包级全局时间轮；
- 不在多个 Node 之间共享 ID、`DeadlineQueue`、桶、锁或工作 goroutine；
- 同一进程开发模式和生产单 Node 模式走相同代码路径；
- Node 停止后 Engine 不能原地重新启动。

### 5.3 生命周期顺序

M8 调整 Node 内部顺序为：

```text
全部 Service OnInit 成功
    -> 启动当前 Node TimerEngine
    -> 按配置顺序执行 Service OnStart
    -> Node Ready
```

停止和启动失败回滚为：

```text
按实际进入 OnStart 的严格反序执行 OnStop
    -> 关闭全部 DeadlineQueue
    -> 停止 TimerEngine
    -> Node Stopped 或 Failed
```

理由：

- `OnInit` 失败时尚未启动后台资源，不需要额外回收；
- 后续 `OnStart` 可以依赖 Node 已经具备系统计时能力；
- Service 清理期间，TimerEngine 仍可为停止 Deadline 和后续 OnStop Await 提供计时；
- Engine 最后停止，避免上层尚未清理时提前失去 Deadline 能力。

M8 本身尚不开放业务 Timer，因此这里只建立正确的资源顺序。

## 6. 内部数据外观

不再使用含义模糊的 `Owner`。内部类型命名为 `DeadlineQueue`，因为它直接表达：

1. 当前上层组件通过它登记和取消一组 Deadline；
2. 到期的 DeadlineID 进入它自己的队列；
3. 关闭队列会批量清理这一组 Deadline。

Service Scheduler、RPC Runtime 和业务 Timer 分别持有自己的 `DeadlineQueue`，代码中不需要
再猜测“Owner 是谁”。

以下代码只表达职责，不锁死字段布局：

```go
package timerwheel

type DeadlineID uint64

const InvalidDeadlineID DeadlineID = 0

type Engine struct {
    // 内部状态、时间轮、DeadlineQueue 索引、唤醒源和统计。
}

type DeadlineQueue struct {
    // 只能由所属 Engine 创建，用于独立登记、取消和接收到期 Deadline。
}

func New(options Options) (*Engine, error)
func (engine *Engine) Start() error
func (engine *Engine) NewDeadlineQueue() (*DeadlineQueue, error)
func (engine *Engine) Close() error

func (queue *DeadlineQueue) ScheduleAfter(delay time.Duration) (DeadlineID, error)
func (queue *DeadlineQueue) Cancel(id DeadlineID) bool
func (queue *DeadlineQueue) ExpiredSignal() <-chan struct{}
func (queue *DeadlineQueue) DrainExpired(
    dst []DeadlineID,
    limit int,
) ([]DeadlineID, error)
func (queue *DeadlineQueue) Close()
```

固定语义：

- `ScheduleAfter` 只登记一次性单调 Deadline；
- `delay < 0` 返回参数错误；
- `delay == 0` 最早在后续引擎调度轮次到期，不能在调用栈内同步到期；
- `Cancel` 只在条目仍位于时间轮中时返回 `true`；
- 条目已到 `DeadlineQueue` 的到期列表时，交付权已经转给消费方，`Cancel` 返回 `false`；
- `ExpiredSignal` 是容量为 `1` 的合并通知，不表示只有一个到期项；
- `DrainExpired` 按到期交付顺序批量取出 ID；
- `limit <= 0` 是无效参数，不解释为无限；
- `DrainExpired` 返回 `error`，用于明确报告非法批次和 Queue 已关闭，不使用空 Slice 混淆
  “没有到期项”与“调用无效”；
- `DeadlineQueue.Close` 拒绝新登记并清理未到期和已到期 ID；清理数量进入统计，不增加
  返回值；
- `Engine.Close` 隐式关闭尚未关闭的 `DeadlineQueue`，等待工作 goroutine 退出；
- 关闭操作幂等；
- 所有方法都可以从不同框架 goroutine 并发调用。

具体 API 在 M8 实施计划中允许按 Go 可测试性做小幅收敛，但不得改变上述所有权和分层
语义。

## 7. 时间表示

### 7.1 单调 Tick

Engine 启动时记录带单调部分的基准时间。内部统一把 Deadline 转换为：

```text
deadline_tick = ceil((deadline - engine_start) / 10ms)
```

规则：

- 基础精度固定为 `10ms`；
- 正延迟向上取整，绝不提前到期；
- Engine 内部使用 `uint64` Tick；
- 相对时间使用 Go 单调时间差，不受时区、NTP 或系统墙上时间调整影响；
- 墙上时间和 Cron 不进入 M8；
- Tick 算术必须检查溢出，不能环绕到过去；
- 测试通过可注入 Clock 和 WakeSource 精确推进，不依赖真实 `Sleep`。

### 7.2 相同 Tick 的顺序

同一 `DeadlineQueue`、同一 `deadline_tick` 的条目按成功登记顺序交付。

不同 `DeadlineQueue` 之间不承诺全局业务顺序；时间轮只保证都不会提前到期。每条
`DeadlineQueue` 的到期列表保持自己的稳定顺序，避免一条队列的消费速度影响其他队列。

### 7.3 `10ms` 精度的取舍

开发者结合公开游戏引擎和游戏服务器框架的实践，确认首版基础 Tick 固定为 `10ms`。这一
选择不会改变单个 `timerEntry` 的内存，也不会改变登记和取消的平均 `O(1)` 复杂度。

`10ms` Tick 的固定语义：

- 量化附加延迟为 `0～<10ms`，均匀分布时平均约 `5ms`；
- 持续存在短 Deadline 且几乎每个 Tick 都有到期项时，最多约 `100` 个到期批次每秒；
- `0 < delay <= 10ms` 的 Deadline 统一向上取整到后续一个 Tick；
- 空 Engine 不周期唤醒，只有长 Deadline 时也不按 `10ms` 固定轮询；
- 更多 Deadline 可能在同一个 Tick 到期，上层必须批量消费并记录 P99/P99.9 延迟；
- 默认 `15s` 的 Await 和 RPC 超时几乎不受该量化误差影响。

首版不把精度暴露为用户配置，避免不同 Node 或项目使用不同 Tick 后产生难以复现的时序
差异。`10ms` 只是时间轮量化精度，不是“回调必定在 10ms 内执行”的实时性承诺。操作系统
调度、Go Runtime 暂停、Engine 获得 CPU 的时间以及上层 Service 排队都会使实际执行更晚；
框架只保证不因量化而提前触发，并记录到期延迟。

## 8. 分层时间轮结构

### 8.1 固定内部参数

首版使用五层、每层 `256` 个槽的分层时间轮：

| 层级 | 单槽跨度 | 整层覆盖范围 |
|---|---:|---:|
| L0 | `10ms` | `2.56s` |
| L1 | `2.56s` | 约 `10.9m` |
| L2 | 约 `10.9m` | 约 `46.6h` |
| L3 | 约 `46.6h` | 约 `497.1d` |
| L4 | 约 `497.1d` | 约 `348.4y` |

选择五层的原因：

- 约 `348.4y` 的覆盖范围已经超过 Go `time.Duration` 约 `292.5y` 的最大正值，不需要
  第六层或额外溢出堆；
- 只有 `1280` 个桶头，固定结构成本很小；
- 每层使用八位索引，定位和级联逻辑直接；
- 层数和槽数不进入配置，避免使用者误调底层算法参数。

如果 Benchmark 证明另一组参数在目标平台有显著收益，必须先更新本文并与开发者确认，
不能在代码中静默改变。

### 8.2 定位

登记时根据 `deadline_tick - current_tick` 选择最低的可容纳层级，再从 Deadline 的对应八位
计算槽号。

已经到期或落在当前 Tick 的条目进入 L0 的后续可处理位置，保证 `ScheduleAfter(0)` 也不会在
登记调用栈内同步交付。

### 8.3 桶和条目

每个桶使用侵入式双向链表：

- `timerEntry` 自己保存前驱、后继、层级和槽号；
- 登记和从已知桶取消为 `O(1)`；
- 不为链表节点额外分配对象；
- 同一桶尾插、头部开始迁移，以保持相同 Tick 的登记顺序；
- 条目离开桶后立即清除链表引用。

Engine 维护 `DeadlineID -> *timerEntry` 索引，使取消不需要扫描时间轮。

### 8.4 推进和级联

工作 goroutine 醒来后读取当前单调 Tick，并一次推进到当前时间：

1. 到达 L0 槽时，把真正到期的 ID 移动到所属 `DeadlineQueue` 的到期列表；
2. L0 回绕时级联 L1 当前槽；
3. 更高层按相同规则在低层回绕时逐层级联；
4. 迁移条目按剩余 Tick 重新定位到尽可能低的层级；
5. 一次推进必须能够跨越进程暂停、调试断点或系统长时间调度延迟；
6. 不能按遗漏的每个毫秒执行一次空循环。

级联成本与实际迁移条目数量相关，不与总容量或空 Tick 数量线性增长。

## 9. 唤醒策略

### 9.1 单一可复用唤醒源

每个 Engine 只持有：

- 一个可复用的底层 `time.Timer`；
- 一个结构变更唤醒 Channel；
- 一个停止 Channel。

禁止：

- 每个 Deadline 创建 `time.Timer`；
- 每个 Deadline 创建 goroutine；
- 空闲时固定每 `10ms` 唤醒；
- 每次新增 Deadline 都重建工作 goroutine。

### 9.2 事件驱动休眠

时间轮为每层维护非空槽位位图。推进完成后，根据各层最近的非空槽计算下一次需要处理的
Tick：

- L0 非空槽可以直接给出最近到期 Tick；
- 高层非空槽给出下一次需要级联的边界；
- 没有条目时停止底层 Timer，等待结构变更或停止信号；
- 新登记的 Deadline 早于当前唤醒点时，只发送一个合并结构变更信号；
- 取消当前最早 Deadline 可以保留一次无害的提前唤醒，不为取消增加全表扫描。

这样既保持 `10ms` 精度，也避免多 Node 开发进程在空闲时产生每 Node 每秒一百次唤醒。

### 9.3 底层 Timer Reset

工作 goroutine 独占底层 `time.Timer` 的 Stop、Drain 和 Reset。登记与取消方只修改受锁保护
的结构并发送合并信号，不直接操作 `time.Timer`，从而避免多个 goroutine 并发 Reset 的复杂
竞态。

## 10. DeadlineQueue 到期交付

### 10.1 不执行回调

Deadline 到期时，Engine 只执行：

1. 从时间轮和 ID 索引中移除条目；
2. 把 `DeadlineID` 追加到所属 `DeadlineQueue` 的到期列表；
3. 向该队列容量为 `1` 的通知 Channel 做非阻塞发送；
4. 继续处理其他 `DeadlineQueue` 和其他到期条目。

Engine 不调用函数指针，不执行 Service、RPC 或业务代码。

### 10.2 隔离

- 每条 `DeadlineQueue` 有独立到期列表和通知；
- 某条 `DeadlineQueue` 不消费时，不阻塞 Engine 和其他队列；
- 到期列表保存紧凑 ID，不复制业务闭包、RPC Payload 或 Context；
- M8 不为到期列表设置业务容量上限，因为到期项已经被接受，不能静默丢弃；
- 上层长期不消费属于组件故障，通过 Expired 数量和最老等待时间暴露；
- `DeadlineQueue` 或 Engine 关闭时必须清理全部已到期 ID。

### 10.3 批量消费

`DrainExpired` 接受复用 Slice 和批次上限：

- 调用方控制单次处理数量，避免一条 `DeadlineQueue` 独占执行时间；
- 返回值复用传入容量，减少常态分配；
- 到期列表仍有剩余时保持通知可见，避免丢失唤醒；
- “通知 Channel 为空”不能作为到期列表为空的唯一依据，真实状态受 Engine 锁保护。

## 11. 并发模型

### 11.1 单锁与单工作 goroutine

首版每个 Engine 使用一个短临界区锁保护：

- Engine 状态；
- 当前 Tick；
- 时间轮桶和非空位图；
- Deadline 索引；
- `DeadlineQueue` 登记及到期列表；
- 条目状态和对象池进出。

工作 goroutine 负责时间推进和底层唤醒源。公共方法只在锁内修改结构，不在锁内：

- 阻塞 Channel 发送；
- 写日志；
- 执行用户或上层代码；
- 等待 goroutine 退出。

首版不使用无锁链表或分片时间轮。只有 Benchmark 证明单锁成为真实瓶颈时，才与开发者
讨论增加实现复杂度。

### 11.2 状态裁决

`timerEntry` 至少区分：

```text
Free -> Scheduled -> Expired
                  \-> Canceled
```

所有转换在 Engine 锁内完成：

- `Cancel` 与到期竞争时只有一个成功；
- 到期先完成时，ID 进入 `DeadlineQueue` 的到期列表，`Cancel` 返回 `false`；
- 取消先完成时，ID 永远不能进入到期列表；
- `DeadlineQueue.Close` 与到期竞争时，关闭或到期只能拥有一次最终清理权；
- Engine Close 后新建 `DeadlineQueue` 和新增 Deadline 都失败。

## 12. ID、对象池和引用清理

### 12.1 DeadlineID

- `0` 永远无效；
- ID 在当前 Engine 生命周期内单调递增；
- ID 不使用指针、桶位置或池索引；
- 回收 `timerEntry` 时不复用旧 ID；
- ID 即将溢出时拒绝新增并返回明确错误，不能绕回；
- 不同 Node 的 ID 可以相同，调用必须经过所属 `DeadlineQueue`。

### 12.2 timerEntry 池

M8 从首版开始为 `timerEntry` 使用 Engine 私有 `sync.Pool`：

- 不使用全局 Pool；
- 取消时只在条目离开桶和 ID 索引后回收；
- 到期时先把不可复用的 DeadlineID 值复制到 `DeadlineQueue` 的到期列表，再让条目离开桶
  和 ID 索引并立即回收；到期列表不保存 `*timerEntry`；
- 回收前清空 `DeadlineQueue`、前驱、后继、Deadline 和状态；
- 从池取出后重新完整初始化；
- 测试模式提供默认关闭的统计与重复回收检查；
- 不池化 `DeadlineQueue`、Channel 或底层 `time.Timer`。

池化是已确认的低风险优化，因为条目完全由框架持有，且 M8 可以一次性建立所有权测试。

### 12.3 不需要对象池但必须复用的对象

以下对象通过长期持有或调用方复用避免重复分配，不再套一层 `sync.Pool`：

- 每个 Engine 的底层 `time.Timer`：整个 Engine 生命周期只创建一个，反复 Stop/Reset；
- 时间轮的 `1280` 个桶头和非空位图：Engine 创建时一次分配；
- `DeadlineQueue` 的到期列表：使用可增长环形队列并保留容量，出队后清空槽位；
- `DrainExpired` 的结果 Slice：优先复用调用方传入的 `dst`；
- 容量为 `1` 的合并通知 Channel：随 `DeadlineQueue` 长期存在。

这些对象生命周期长、数量少或已经可以原位复用，放入对象池不会减少常态分配，反而会增加
Reset、所有权和关闭竞态。

### 12.4 首版不采用分块内存池

一百万个同时活跃 Deadline 本身必然需要一百万份状态，`sync.Pool` 只能降低取消或到期后的
再次登记分配，不能减少活跃集合的内存。

连续内存块加空闲索引可以进一步减少堆对象数量并改善局部性，但会增加：

- 索引代替指针后的访问和边界检查；
- 分块扩容、空闲链表和代际校验；
- DeadlineID 与槽位复用的 ABA 风险；
- 大块内存无法及时释放的滞留问题；
- 并发取消、级联和回收代码复杂度。

首版保持 Engine 私有 `sync.Pool + *timerEntry`。百万容量 Benchmark 必须同时记录堆对象数、
GC 扫描成本和总内存；只有它们成为明确瓶颈时，才以同一测试集对比分块池，并按开发指导
原则与开发者确认后替换。

## 13. 配置

M8 不增加用户可调时间轮算法参数。以下值固定在实现中：

- 基础 Tick：`10ms`；
- 五层；
- 每层 `256` 槽；
- `DeadlineQueue` 通知 Channel 容量：`1`。

本里程碑不开放顶层 `timer` 配置，M7 对未实现 `timer` 字段的严格拒绝保持不变。Cron 时区、
业务批次和公开 Timer 能力进入后续 Service Timer 接入里程碑时再开放。

M9 的 `default_await_timeout: 15s` 和 RPC 的默认超时属于各自上层配置，不属于时间轮算法
配置。

## 14. 错误边界

M8 尽量复用现有错误码：

- 非法延迟、nil Clock、nil WakeSource 或非法批次：`CodeInvalidArgument`；
- Engine/`DeadlineQueue` 重复启动等非法状态：`CodeInvalidArgument`；
- Engine 已关闭或 `DeadlineQueue` 已关闭：使用内部哨兵错误，并在接入公开系统时映射为所属系统的
  稳定错误码；
- ID 耗尽或内部不变量破坏：`CodeInternal`。

取消不存在、已到期或不属于当前 `DeadlineQueue` 的 ID 返回 `false`，不为正常竞争创建
动态错误。
热路径错误不拼接 NodeID 或数量；诊断字段进入限频结构化日志和统计。

M8 不为尚未公开的内部包提前增加大量公共错误码。

## 15. 可观测性

- 当前 `DeadlineQueue` 数；

- 当前及历史最高 Scheduled/Expired；
- 工作 goroutine 唤醒总数；
- 空唤醒和结构变更唤醒总数；

限频日志；M8 尚不建立统一指标导出系统。

## 19. 完成标准

## 20. 开工 Review 已确认

开发者于 2026-07-27 确认以下全部结论，并要求直接实施：

1. 当前 M8 改为 Node 时间轮内核，原 Service Scheduler 顺延到 M9；
2. M8 使用 `internal/timerwheel`，不公开业务 API；
3. 每个 Node 一个 Engine，不使用 Application 全局 Engine；
4. 全部 Service `OnInit` 成功后启动 Engine，最后一个 Service `OnStop` 完成后停止；
5. 内核只提供一次性 Deadline、取消、`DeadlineQueue` 到期交付、

6. 采用五层、每层 `256` 槽、`10ms` Tick，不把精度开放为配置；
7. 采用非空槽位图和事件驱动唤醒，空闲时不进行 `10ms` 轮询；
8. 每个 Engine 只有一个可复用 `time.Timer` 和一个工作 goroutine；

10. 内部 `DeadlineID` 不承诺等同于后续公开 `TimerID`；
11. `timerEntry` 从首版使用 Engine 私有 `sync.Pool`；底层 `time.Timer`、桶、位图、
    `DeadlineQueue`、Channel 和环形队列不池化，只按生命周期复用；
12. M8 不开放 `timer` 配置；
13. M9 Await 和后续 RPC Deadline 必须直接使用本内核，不再使用独立 Runtime Timer；
14. Service Timer 公共接口在 Scheduler 之后单独立项；
15. 上述全部确认后，再创建
    `docs/plans/M8-节点时间轮内核实施计划.md`。

## 21. 实施与验收结果

M8 已按本文完成实现，实际代码边界如下：

- 新增 `internal/timerwheel`，包含五层时间轮、非空位图、单一工作 goroutine、可复用
  `time.Timer`、`DeadlineQueue`、侵入式条目链表、到期环形队列和 Engine 私有
  `timerEntry` 池；
- Node 构造时创建独立 Engine；全部 `OnInit` 成功后启动，全部已进入 `OnStart` 的
  Service 反序 `OnStop` 后关闭；
- Application 装配多个 Node 中途失败时，反序回收此前已经创建但尚未启动的 Node 资源；
- 到期通知只在 Queue 从空变为非空时发送，分批 Drain 后仍有剩余才补回通知，避免同批
  多条 Deadline 留下陈旧信号；
- Queue 关闭时清理待调度条目、已到期 ID 和缓冲通知；Engine 关闭会等待唯一工作
  goroutine 退出。

- Windows：Go 1.26.5，Windows/amd64，AMD Ryzen 7 7840HS；
- Linux：Go 1.26.5，Linux/amd64，8 vCPU QEMU；

已通过：

- `gofmt`、`go vet ./...`、`go test ./...`、`go test -race ./...` 和 `go build ./...`；
