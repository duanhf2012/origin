# Origin 第三版 M22 v3.0 发布前质量收口设计

> 文档状态：已完成实现与发布前质量验收
>
> 确认日期：2026-08-01
>
> 前置里程碑：M0～M21
>
> 全局编号约束：M22 是最后一个全局里程碑，不创建 M23

## 1. 里程碑定位

M22 是 Origin v3.0 的发布前质量收口，不再增加业务协议、数据库适配器或新的业务运行时
模型。它负责在最终兼容冻结前补齐进程级诊断、可控 pprof、权威平台验证和 RPC 性能
基线，并统一复核 M0～M21 的构建、依赖、竞态和跨平台结果。

M22 完成表示当前代码达到发布候选质量，不等同于已经发布 `v3.0.0`。正式标签、发布
制品、发布自动化、回滚演练和发布后的治理不属于本里程碑。面向使用者的文档、教程、
示例工程和使用示例同样完全排除，不作为 M22 的任务、交付物或验收条件。

M22 后不再通过增加 M23 延长全局建设序列。后续独立适配器、正式发布动作或其他产品
工作使用无全局 `Mxx` 的组件工作包管理。

## 2. 必须继承的现有事实

1. Application 是单个进程内 Node、共享 BufferPool、日志和最终清理的唯一所有者；
2. 一个 Application 可以装配多个 Node，一个 Node 可以同时装配多个普通 Service；
3. Service 实例由 Application 根据类型模板创建，`Setup` 传入的样本字段不会复制到运行
   实例，因此不能依赖样本注入 Application 指针；
4. Service 当前只通过最小只读 Runtime 取得 NodeID、ServiceName、Logger、配置、发现和
   RPC 等能力，不持有具体 `*application.Application`；
5. Service 已公开 `ExecutionStats()`、`TimerStats()` 和 `EventStats()`；
6. Node 已公开 `HealthStatus()`、`TransportStatus()`、`DiscoveryStatus()` 和
   `ServiceStatus()`；
7. BufferPool 已有可选的使用量统计；统计关闭时必须明确报告 Disabled，不能伪造零使用；
8. 现有 RPC 集成基准已覆盖同 Node Await、TCP Await 和 NATS Await 延迟，但尚无统一的
   Async 完成吞吐与双进程发布前矩阵；
9. v2 的 pprof 直接在 goroutine 中调用 `http.ListenAndServe`，没有保留 Server 和
   Listener 所有权，不能作为 v3 实现；
10. 当前仓库没有 CI 配置，Ubuntu 权威验证由人工执行；
11. `deploy/compose` 已提供 etcd 与 NATS 集群。MongoDB 虽可由 Compose 启动，但 Origin
    当前没有 MongoDB 适配器，M22 不建立虚假集成；
12. 当前 Go 基线固定为 `1.26.5`。

## 3. 总体方案

M22 使用四个相互独立但在同一里程碑内验收的工作包：

1. 统一 Diagnostics 数据面与可选 JSON Server；
2. Application 所有的可运行时启停 pprof Server；
3. Ubuntu 权威测试、跨平台构建、依赖和安全检查；
4. 同 Node、TCP、NATS 的 Async/Await RPC 性能矩阵。

Diagnostics 采用分层结构，而不是把采集、HTTP、存储和监控全部塞入一个函数：

```text
Service / Node / RPC / Go Runtime 叶子统计
                    ↓
         Application.Diagnostics()
                    ↓
       ┌────────────┴────────────┐
   本地管理 RPC             Diagnostics JSON Server
                                  ↓
                      业务自定义监控或未来独立组件
```

Origin 只生成当前不可变快照并提供稳定读取边界。历史时序存储、集中式监控、告警、界面
和 Prometheus Exporter 不进入 M22，也不进入游戏服务进程核心。

## 4. Diagnostics 公共边界

### 4.1 独立叶子包

新增公共 `diagnostics` 包。该包只能依赖标准库和稳定基础类型，不能反向依赖
`application`、`node`、`service` 或 `rpc`，从而允许 Application、Service 管理 RPC 和
业务监控适配器共同引用同一份快照类型而不产生包循环。

最小公开边界为：

```go
package diagnostics

type Source interface {
	Diagnostics() Snapshot
}

type Snapshot struct {
	SchemaVersion uint32
	CollectedAt   time.Time
	StartedAt     time.Time
	CollectCost   time.Duration
	Application   ApplicationSnapshot
	Runtime       RuntimeSnapshot
	BufferPool    BufferPoolSnapshot
	Nodes         []NodeSnapshot
}
```

`diagnostics.Source` 是 Prometheus 或其他监控方案唯一需要依赖的框架接口。业务侧可由消费
方定义更窄接口，但不需要 Origin 提供 Collector 注册表、全局 Metrics Registry 或
Prometheus 专用类型。

M22 不引入 `prometheus/client_golang` 直接依赖，不提供 `/metrics`，也不提交官方
Prometheus 使用示例。未来业务适配器只需读取 `diagnostics.Source.Diagnostics()`，即可
自行映射为 Prometheus、OpenTelemetry 或其他监控模型，无需修改 Origin 热路径或公开
Application 具体类型。

### 4.2 快照层次

`Snapshot` 至少包含以下稳定层次：

```text
ApplicationSnapshot
├── AppName、LifecycleState、StartedAt
├── DiagnosticsServerStatus、PprofStatus
├── RuntimeSnapshot
│   ├── Goroutines、GOMAXPROCS
│   ├── Heap 与对象核心统计
│   └── GC 核心累计统计
├── BufferPoolSnapshot
│   ├── Enabled
│   ├── InUseBuffers、InUseCapacity
│   └── Oversize 核心统计
└── NodeSnapshot[]
    ├── NodeID、LifecycleState
    ├── Health、Transport、Discovery
    ├── RPCSnapshot
    ├── DiscoveryDirectoryCounts
    └── ServiceSnapshot[]
        ├── ServiceName、LifecycleState、EnteredAt、ErrorCode
        ├── ExecutionSnapshot
        ├── TimerSnapshot
        └── EventSnapshot
```

Diagnostics 包使用自身的稳定快照 DTO，不把 Node、Service 或 RPC 内部可变对象、锁、
指针和错误接口泄漏给调用方。生命周期和 Transport 等枚举在诊断 DTO 中映射为稳定、
可读的字符串；失败只保留 Origin 稳定错误码和非敏感阶段信息，不复制原始第三方错误
文本。

快照不包含：

- 配置文件原文、环境变量值、密码、Token、TLS 私钥或认证信息；
- RPC 请求参数、响应内容、玩家标识或业务 Payload；
- 远端发现完整实例表、动态远端地址和业务 Label 全量；
- goroutine 栈、Heap Profile 或其他应由 pprof 按需取得的大体积信息；
- Module 内部业务字段或任意反射遍历结果。

远端发现只记录当前可见 Node 数、Service 数、Running 数、Retired 数和目录版本等有界
汇总，避免 8192 Node 上限在每次诊断中形成大规模远端对象复制。

### 4.3 现有局部查询继续保留

现有 `ExecutionStats()`、`TimerStats()`、`EventStats()` 和 Node Status 不删除。它们仍是
组件内部与本地业务代码的低成本局部查询入口，也是统一 Diagnostics 的叶子数据源。
监控和管理代码应优先使用 Application 聚合快照，避免自己重复遍历并形成不同口径。

Application 实现：

```go
func (app *Application) Diagnostics() diagnostics.Snapshot
```

未启动、启动中、运行中、退休中、停止中、已停止和失败对象都必须返回可解释快照。
Diagnostics 不能因为单个 Node 或 Service 已失败而整体返回 error；无法取得的局部数据以
状态和稳定错误码表示。

### 4.4 快照一致性和性能

一次快照按 Application 固定 Node 顺序和 Node 固定 Service 顺序采集。每个叶子统计必须
自身一致，但不建立覆盖整个 Application 的大锁，也不暂停 Scheduler、RPC 或网络收发。
`CollectedAt` 表示采集开始时间，`CollectCost` 表示完整聚合开销，因此调用方能够判断
大型 Application 快照的时间跨度。

Diagnostics 是冷路径：

- 不在热路径反射、拼接指标名、构建 Map 或创建动态 Label；
- 快照拥有自己的 Slice，不返回 Application 内部可变容器；
- 不为了复用一次诊断结果建立无界缓存或对象池；
- 不启动后台周期采样 goroutine；
- 不在 Origin 进程保存历史快照、时序数据库或本地诊断文件；
- Application 为 nil 或尚未绑定资源时返回完整零值语义，不 panic。

必须提供不同 Node/Service 规模的 Benchmark，并记录 `ns/op`、`B/op` 和 `allocs/op`。

## 5. RPC 诊断统计

### 5.1 范围

M22 补充当前缺失的 Node 级 RPC 汇总，使内部监控至少能够识别积压、吞吐、错误、超时
和流量变化。统计按同 Node、TCP、NATS 固定类别区分，不按 RPC Method、远端 Node、动态
地址、错误文本或请求内容建立 Map 和标签。

每类至少包含：

- 当前 outbound pending/in-flight；
- pending 最高水位；
- outbound accepted、completed、failed、timeout、rejected 累计值；
- inbound accepted、completed、failed、timeout、rejected 累计值；
- payload sent bytes 和 received bytes 累计值；
- Transport 已有重连和连续失败统计的映射。

Async 必须在回调最终完成时累计 completed，不能在请求仅进入发送队列时冒充完成。
Await 必须在响应完成校验、解码并返回后累计 completed。同 Node 调用必须遵循相同口径，
便于监控和 M22 性能矩阵对照。

### 5.2 热路径约束

统计只允许使用已有串行所有权中的普通整数或固定原子计数，不增加逐请求对象、动态 Map、
字符串格式化、接口装箱和 goroutine。M22 不在 RPC 热路径加入逐次延迟 Histogram；RPC
尾延迟由 M22 可复验性能工具测量，未来监控适配器不能通过隐藏注册回调侵入热路径。

必须分别基准测试诊断能力存在前后的同 Node、TCP 和 NATS 代表路径。若新增统计使相同
环境、相同负载的完成吞吐经复测后持续下降超过 3%，必须调整计数位置或范围，不能以
“监控需要”为由直接接受回退。

## 6. Diagnostics JSON Server

### 6.1 启动和公开方法

Diagnostics Server 是 Application 所有的可选进程级资源，默认关闭。命令行初始外观为：

```text
game-server start --app-name player --config ./config \
    --diagnostics 127.0.0.1:6061
```

同时公开：

```go
func (app *Application) StartDiagnosticsServer(address string) error
func (app *Application) StopDiagnosticsServer(ctx context.Context) error
func (app *Application) DiagnosticsAddress() (string, bool)
```

`--diagnostics` 只是启动初始状态，不形成永久强制策略。业务管理 RPC 可以在运行中关闭并
重新开启。相同实际地址重复开启幂等成功；已开启时改用不同地址返回状态冲突，调用方必须
先关闭再开启。监听 `:0` 时必须记录并返回 Listener 的实际地址。

### 6.2 HTTP 边界

M22 只提供：

```text
GET /debug/origin/diagnostics
```

端点返回当前 `diagnostics.Snapshot` 的 JSON 表示。JSON 顶层包含 `schema_version: 1`；时间
使用 RFC3339Nano，Duration 使用明确单位的字符串。最终 `v3.0.0` 后 Patch 可以增加可选
字段，但不能删除字段、改名或改变已有字段含义。

Server 必须使用私有 `http.Server` 和私有 `http.ServeMux`，不能注册到
`http.DefaultServeMux`。只接受 GET；其他方法返回 405。必须配置 ReadHeader、Write 和
Idle 超时，并限制请求头大小。端点不提供启动、停止、退休、恢复、修改配置或调用任意
Application 方法的控制能力。

### 6.3 安全和故障语义

默认示例只监听环回地址。调用方可以显式监听其他地址，但 Origin 必须记录不包含敏感值的
安全警告。M22 不内置 TLS 和认证；跨主机访问由内网隔离、反向代理、Sidecar 或业务运维
层负责。

命令行显式请求监听时，首次绑定失败必须在任何 Node 进入 OnStart 前使 Application 启动
失败并按已创建资源逆序回滚。运行中 Server 非预期退出时，记录稳定错误并在 Diagnostics
Server Status 中标记 Failed，但不停止游戏业务。完成清理后允许业务再次开启。

## 7. pprof 设计

### 7.1 所有权和公开外观

pprof 是整个 Go 进程的资源，不属于任一 Node 或 Service。Application 保留 Listener、
`http.Server`、私有 `ServeMux`、状态和关闭结果：

```go
func (app *Application) StartPprof(address string) error
func (app *Application) StopPprof(ctx context.Context) error
func (app *Application) PprofAddress() (string, bool)
```

启动命令为：

```text
game-server start --app-name player --config ./config \
    --pprof 127.0.0.1:6060
```

未指定时默认关闭。命令行只决定初始状态，运行中仍可关闭并再次开启。相同实际地址重复
开启幂等成功；已启用时切换地址返回状态冲突；关闭保持幂等并先停止接受新连接，再在调用
方 Context 内执行 `http.Server.Shutdown`。

### 7.2 私有路由和安全

pprof 必须把 `net/http/pprof` 的 Handler 显式安装到私有 ServeMux，禁止依赖空白导入和
DefaultServeMux 的全局注册副作用。Diagnostics Server 和 pprof 使用不同 Listener：关闭
临时 pprof 不影响持续的 JSON 监控，两者也可以采用不同网络暴露策略。

默认示例只监听环回地址，显式非环回监听记录安全警告。M22 不内置 pprof TLS 和认证；
远程访问使用安全隧道、反向代理或业务运维网络。

### 7.3 生命周期顺序

命令行 pprof 在日志初始化后、Node 启动前绑定，因此能分析启动过程。显式绑定失败导致
Application 启动失败。正常停止时保持 Diagnostics 和 pprof 可用，直到全部 Node 已经执行
停止或回滚；随后先停止接受诊断连接，再在剩余总体清理 Context 内 Shutdown，最后关闭
Crash 输出和日志。Context 已耗尽时仍必须立即 Close Listener，不能泄漏 goroutine 或端口。

## 8. Service 内的受限 Application 外观

RPC 实现是普通 Service 成员方法，但当前运行实例不能从 `Setup` 样本继承 Application
指针。M22 通过框架装配的受限接口解决访问问题，不使用包级全局变量，也不返回具体
`*application.Application`：

```go
type ApplicationRuntime interface {
	diagnostics.Source

	StartDiagnosticsServer(address string) error
	StopDiagnosticsServer(ctx context.Context) error
	DiagnosticsAddress() (string, bool)

	StartPprof(address string) error
	StopPprof(ctx context.Context) error
	PprofAddress() (string, bool)
}

func (s *Service) Application() ApplicationRuntime
```

Application 在构建 Node 时把该最小接口传给 Node，Node 再绑定到每个 Service Runtime。
该接口不开放 `Application.Stop()`、`Setup()`、Provider 注册、Node 构建和配置修改。
未装配的类型样本和零值 Service 调用 `Application()` 返回 nil；真实运行实例从 `OnInit`
开始必须返回同一非 nil 接口，停止后只允许读取最终 Diagnostics 和地址状态，不能重新开启
监听器。

管理 RPC 可以直接读取 `Diagnostics()`、`DiagnosticsAddress()` 和 `PprofAddress()`；
`StartPprof` 与 `StartDiagnosticsServer` 只执行短暂校验和 Listen，也可直接调用。两个 Stop
方法可能等待 HTTP 请求排空，必须由 Service 使用 `Await` 调用，避免阻塞 Service 串行
执行权。

Origin 不提供“按名称调用任意 Application 方法”的通用 RPC。业务必须显式定义管理 RPC，
校验调用权限和监听地址，并把 `diagnostics.Snapshot` 映射为自己的 RPC 契约 DTO；不能把
框架快照结构直接冻结为业务 Wire 契约。

### 8.1 控制状态与错误

Diagnostics 和 pprof 控制器各自使用 Application 私有互斥锁串行化 Start、Stop、Serve
异常和最终清理，不共享包级状态。Start 只允许在 Application 已经完成基础资源初始化后的
Starting 或 Running 阶段；Created、已经开始最终清理、Stopped 和 Failed 均返回状态冲突。
Stop 在所有阶段保持幂等：未启动、已经关闭和最终清理完成都返回 nil。

M22 增加两项进程诊断错误码：

- `CodeDiagnosticsUnavailable`：显式监听绑定、HTTP Serve 或受控关闭无法完成；
- `CodeDiagnosticsStateConflict`：已经监听其他地址、Application 生命周期不允许开启或两个
  并发控制请求的期望状态冲突。

空地址、无法解析的监听地址和 nil Context 使用现有 `CodeInvalidArgument`；Shutdown 的
Context 取消或超时继续映射现有 `CodeCanceled`、`CodeDeadlineExceeded`。Server 非预期
退出写入自身状态，后续 `Application.Diagnostics()` 仍必须成功返回，不把诊断故障伪装成
业务 Application 故障。

## 9. 兼容和版本规则

1. 公开 API、JSON Schema、配置和 RPC/Wire 的最终兼容冻结点是正式 `v3.0.0` 标签，不是
   M22 设计提交或候选验证开始；
2. 正式发布后的 Patch 可以为缺陷修复和可运维性增加小型、向后兼容的 API 或可选字段，
   但不能破坏既有 API、Wire、配置、JSON 字段或正确业务语义；
3. 独立的新功能进入 Minor；破坏性修改只能进入新的主版本；
4. M22 不建设 Deprecated 标记、迁移窗口或废弃统计系统；
5. Prometheus 不属于 v3.0 核心兼容面。稳定兼容边界是 `diagnostics.Source` 和 Snapshot，
   业务适配器自行管理 Prometheus 指标名和版本；
6. `schema_version` 只服务 Diagnostics JSON 演进，不重新给已经确认精简的 TCP/NATS
   Wire 增加分帧版本。

## 10. 权威测试与跨平台验证

### 10.1 平台分层

Ubuntu/amd64 是 M22 权威运行平台，必须完成：

- 全量单元和包级集成测试；
- 全量 Race；
- 覆盖率采集和低覆盖路径复核；
- 真实三节点 etcd、三节点 NATS 集成；
- Discovery 和 Transport 断开、Lost、恢复、重发与退出测试；
- Diagnostics/pprof 并发启停、端口冲突、部分启动失败和资源泄漏测试；
- RPC 端到端性能矩阵。

Windows/amd64 完成普通测试、Race 和构建。macOS/amd64、macOS/arm64、Linux/arm64 至少
完成编译验证；平台专用代码必须通过对应目标构建。M22 不新增 CI 文件，以上命令由人工在
Ubuntu 和当前 Windows 开发环境执行并把结果写入后续内部实施计划。

### 10.2 手工质量命令

M22 至少执行并记录：

```text
go test ./...
go test -race ./...
go test -coverprofile=<temporary-output> ./...
go vet ./...
go mod verify
go build ./...
生成器重跑与差异检查
依赖和已知漏洞检查
三平台目标构建
```

覆盖率数字不是唯一目标。必须查看逐函数和未执行分支，补齐能够稳定验证真实行为的测试；
不能为了提高百分比复制实现或引入生产测试钩子。

仓库暂不增加 GitHub Actions 或其他 CI 配置。MongoDB Compose 不参与验收，避免把“容器
正在运行”误写成 Origin 已经具备 MongoDB 集成。

## 11. RPC 性能矩阵

### 11.1 场景

统一测试以下六条路径：

| 位置与 Transport | 调用方式 |
|---|---|
| 同 Node 本地 Dispatcher | Async、Await |
| 跨 Node TCP | Async、Await |
| 跨 Node NATS | Async、Await |

跨 Node 使用同一台 Ubuntu 主机上的两个独立进程，通过 etcd 发现对方，并使用现有 NATS
集群。不能用同一进程两个 Node 代替跨进程测量，也不要求两台物理机器才能完成 M22。

Payload 固定为 32 B、1 KB 和 64 KB。M22 不加入接近 4M 上限的吞吐场景，最大 Payload
继续由已有边界测试验证。

### 11.2 计数口径和负载

完成吞吐是唯一 TPS/QPS 口径：

- Async 在最终 callback 完成时计数；
- Await 在响应校验、解码并返回时计数；
- 进入发送队列、写入 Socket 或收到 NATS Publish ACK 都不能冒充业务 RPC 完成。

负载固定为：

| Payload | 测量方式 |
|---|---|
| 32 B | 并发 1 测端到端延迟；并发 64 测完成 QPS |
| 1 KB | 并发 32 测完成 QPS 和 MiB/s |
| 64 KB | 并发 32 测完成 QPS 和 MiB/s |

每个场景预热 5 秒、测量 15 秒、独立执行 3 轮。记录完成 QPS、P50/P95/P99、错误数、
超时数、`B/op` 和 `allocs/op`；中途连接恢复、GC 异常或外部集群抖动必须记录，不能静默
删除不利样本。

### 11.3 基线与回退判断

M22 首次在 Ubuntu 建立环境绑定基线，不设置脱离 CPU、内核、NATS 和 etcd 环境的绝对
QPS 门槛。相同环境、相同提交条件下下降超过 15% 必须重跑；重跑后持续下降超过 25%
阻止 M22 收口。Diagnostics 新增热路径计数另受 3% 精细门禁约束。

基线记录必须包含 Go 版本、GOOS/GOARCH、CPU、逻辑核数、内存、NATS/etcd 版本、Transport
配置和测试提交，确保未来能够解释差异。

## 12. 依赖、安全和供应链检查

M22 不为追求形式上的零依赖复制成熟实现，也不因现有间接依赖就直接使用它。新增直接依赖
必须有当前功能的真实必要性、许可证和维护状态复核。Prometheus 已明确后置，因此不能把
现有 etcd 依赖树中的 `client_golang` 提升为 Origin 直接依赖。

依赖收口至少检查：

- `go.mod` 与 `go.sum` 可复验；
- `go mod verify` 成功；
- 直接依赖版本、许可证和维护状态；
- 可用工具报告的已知漏洞及实际可达性；
- 生成器、Protobuf 和 Go 工具版本与仓库声明一致；
- 构建和测试输出不写入仓库；
- Diagnostics 与 pprof 不输出凭证、配置秘密和业务 Payload。

## 13. 明确不做

M22 不实现：

1. Prometheus Exporter、`/metrics` 或 Prometheus 官方接入示例；
2. OpenTelemetry Exporter、Tracing 或自定义 Metrics 注册中心；
3. 进程内历史快照、时序数据库、Dashboard 和告警系统；
4. 面向使用者的手册、教程、示例工程和使用示例；
5. CI 配置和自动发布流水线；
6. 二进制、镜像、安装包、正式标签和 Release Notes；
7. 混合版本、回滚和正式发布演练；
8. MongoDB、Redis、Kafka、HTTP、WebSocket、KCP、TcpModule 或外部 gRPC 适配器；
9. RPC 逐 Method 高基数指标和逐请求延迟 Histogram；
10. 通过 Diagnostics HTTP 修改 Application 状态的控制端点；
11. Application 完整指针向 Service、Module 或 RPC 暴露；
12. M23 或其他新的全局里程碑编号。

## 14. 实施顺序

设计批准后的实施计划必须按以下依赖顺序拆分：

1. 建立 `diagnostics` 叶子 DTO 与 `Source`；
2. 补齐 RPC 有界统计及其基准；
3. 实现 Node/Application 聚合和 `Application.Diagnostics()`；
4. 建立受限 `Service.Application()` Runtime 装配；
5. 实现 Diagnostics JSON Server 与运行时启停；
6. 实现独立 pprof Server 与运行时启停；
7. 接入命令行初始参数和 Application 清理顺序；
8. 完成并发、失败、泄漏、安全和性能测试；
9. 在 Ubuntu 执行真实 etcd/NATS、全量质量和 RPC 性能矩阵；
10. 执行跨平台构建与最终文档回写。

每一步先写失败测试或 Benchmark，再修改生产代码。任何步骤发现需要扩大公开 Application
能力、引入 Prometheus 依赖或修改已确认 RPC 语义时，必须先回到本设计复核，不能在实现中
静默扩展。

## 15. 完成条件

M22 只有同时满足以下条件才算完成：

1. `diagnostics.Source`、Application 聚合、JSON Schema 和受限 Service 外观与本文一致；
2. Diagnostics Server 和 pprof 支持命令行初始开启、运行时关闭、重新开启和幂等清理；
3. 两个 HTTP Server 均无 DefaultServeMux、全局注册、端口或 goroutine 泄漏；
4. RPC 统计口径与 Async/Await 完成语义一致，热路径回退未超过门禁；
5. Ubuntu 权威全量测试、Race、覆盖率复核、Vet、依赖检查和真实集群测试通过；
6. 同 Node、TCP、NATS 的 Async/Await 性能矩阵完成并记录环境；
7. Windows 验证及 macOS/Linux 目标构建通过；
8. 没有未处理的 Critical 或 Important Review 问题；
9. 设计、代码、测试和内部实施记录不存在冲突、未决事项或占位结论；
10. 工作树只包含 M22 范围，完成后形成清晰提交；
11. 未混入使用者文档、使用示例、Prometheus、CI、发布制品或正式发版动作；
12. 路线图、设计索引、迁移矩阵和复核清单统一标记 M22 的真实定位；
13. 不创建 M23。

满足以上条件只表示发布候选质量收口完成。最终 `v3.0.0` 标签仍需在 M22 外由开发者明确
执行，届时才发生正式兼容冻结。

## 16. 实施与验收结论

M22 已按本设计完成实现，最终公开边界未发生扩张：

1. 新增稳定的 `diagnostics` Schema 1、`diagnostics.Source`、Application/Node/Service/RPC
   当前快照和只读 JSON Server；快照不包含配置原文、凭证、远端地址、动态 Label 或业务
   Payload；
2. Diagnostics 与 pprof 使用两个 Application 私有 Listener、ServeMux 和 Server，支持
   命令行初始监听、运行时停止及重新开启，生产代码未使用 `http.DefaultServeMux`；
3. Service 只通过 `ApplicationRuntime` 取得诊断与两个 Server 的受限管理能力，没有暴露
   Application 的停止、装配、Provider 或 Node 修改能力；
4. Local/TCP/NATS 只维护固定原子累计器。Local Await 同条件回退 1.29%，低于 3% 门禁，
   `allocs/op` 保持 26；
5. Windows 完成全仓测试、Race、覆盖率、Vet、构建、生成检查和目标交叉构建；Ubuntu 完成
   同等质量门禁、70.4% 覆盖率、依赖/漏洞检查、真实 etcd/NATS 集群兼容与故障恢复；
6. Ubuntu 完整 RPC 矩阵共 24 个场景、每场景三轮。72 个结果全部 0 error、0 timeout、
   0 pending_end，运行中没有 etcd/NATS 基础设施告警；环境和三轮中位数见
   [M22 实施计划](../../plans/M22-v3.0发布前质量收口实施计划.md)；
7. 没有加入 Prometheus 直接依赖、历史快照、CI、使用者文档、使用示例、发布制品、正式
   标签或 M23。

验收过程中发现并修正了 NATS 64 KiB 并发负载所需的 Payload 上限、集群节点广播、etcd
空闲端点 Ping 策略、Windows CPU Tick 校准与停止文件竞态等真实边界。最终长压测使用
Go 1.26.5、etcd 3.7.1 和 NATS 2.14.3，通过退出码、机器可读结果数量与错误总和三重校验。

因此 M22 与全局 M0～M22 建设序列均已完成。当前结论仍只是发布候选质量收口；正式
`v3.0.0` 发布继续由开发者在里程碑体系外单独决定。
