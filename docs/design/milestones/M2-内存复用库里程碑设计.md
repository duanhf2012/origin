# Origin 第三版 M2 内存复用库里程碑设计

> 文档状态：已实现并通过验收
> 创建日期：2026-07-25
> 最后更新：2026-07-25

## 1. 目标

M2 只实现一个独立、无业务语义的框架内部字节 Buffer 池，为后续 TCP 收发和 RPC 编解码减少重复堆分配。

完成 M2 后，应能够取得指定长度的 Buffer、在组件之间转移唯一所有权并最终释放；同时用测试、逃逸分析和 Benchmark 证明池化确有收益且不会长期保留超大内存。

M2 不接入 Application、Node、Service、TCP、NATS、Protobuf、Timer 或 RPC。

## 2. v2 对照与重构重点

v2 的 `util/bytespool` 已经按容量范围复用 `[]byte`，但存在以下不适合直接沿用的边界：

- 使用包级池和 `init()` 初始化，多个 Application 与测试共享隐藏状态；
- 直接传递来源不明的 `[]byte`，无法表达当前所有者；
- 释放时依靠切片容量反查池，错误切片可能污染池；
- 默认档位一直延伸到约 `1.9 MiB`，容易保留并不常用的大块内存；
- 构造出的实例与实际使用的全局池关系不直观；
- 没有把所有权转移、重复释放和释放后使用写成明确约束。

M2 完全重新实现，不依赖或复制 v2 代码。v2 只作为行为和问题对照。

## 3. 前置依赖

- 使用 M0 确认的 Go module、Go 1.26.5 和质量命令；
- 只依赖 Go 标准库；
- 不依赖 M1 日志，Buffer 热路径不记录日志；
- 不增加新的公共错误码；
- 不使用包级可变全局状态。

M2 即使位于 M1 之后，实现上仍保持为可独立使用的底层库。

## 4. 实现范围

### 4.1 包与可见性

代码放入：

```text
internal/bufferpool
```

该包只能被 Origin v3 仓库内部代码使用，业务 Service 和仓库外部项目不能直接导入。

M2 不建立 `pool`、`objectpool` 等通用包，也不向业务层公开任意类型对象池。

命名调研：

- [valyala/bytebufferpool](https://github.com/valyala/bytebufferpool) 直接用 `bytebufferpool` 表达字节 Buffer 池；
- [gRPC-Go](https://github.com/grpc/grpc-go/blob/master/mem/buffer_pool.go)使用较宽的 `mem` 包，但核心类型仍命名为 `BufferPool`；
- [gnet](https://github.com/panjf2000/gnet/tree/master/pkg/pool)把复用能力放在 `pkg/pool/byteslice` 和 `pkg/pool/bytebuffer` 层级下。

这些项目没有形成唯一命名，但专门负责复用的包通常会在包名、父目录或核心类型中体现 `pool`。M2 不使用过宽的 `mempool`，因为它只复用字节 Buffer，不提供任意对象内存池；最终使用 `bufferpool`，使目录职责在调用方尚未阅读类型前也能被识别。

### 4.2 最小使用外观

建议外观如下：

```go
package bufferpool

type Pool struct {
    // 内部字段不公开。
}

type Buffer struct {
    // 内部字段不公开。
}

type Options struct {
    TrackUsage bool
}

type BucketStats struct {
    Capacity     int
    InUseBuffers int64
}

type Stats struct {
    Enabled            bool
    InUseBuffers       int64
    InUseCapacityBytes int64
    ZeroSizeInUse      int64
    OversizeInUse      int64
    OversizeBytes      int64
    Buckets            []BucketStats
}

func NewPool(options Options) *Pool
func (p *Pool) Acquire(size int) *Buffer
func (p *Pool) Stats() Stats
func (b *Buffer) Bytes() []byte
func (b *Buffer) Release()
```

典型使用：

```go
buf := pool.Acquire(size)
data := buf.Bytes()

// 完整填充并使用 data。

buf.Release()
```

设计约束：

1. `Pool` 必须通过 `NewPool` 创建并始终以指针传递，开始使用后禁止复制。
2. `Acquire(size)` 返回的 `Bytes()` 长度等于 `size`，容量等于所属档位容量。
3. `Bytes()` 返回可写切片，不复制数据。
4. 不提供 `Append`、`Resize`、`Clone`、引用计数或共享所有权接口。
5. `Release` 直接定义在 Buffer 上，由 Buffer 返回自己的来源池，调用方不再额外保存 Pool。
6. `Pool` 不提供 `Close`；它不创建 goroutine、文件或其他必须主动关闭的资源。
7. `Options{}` 是默认低延迟配置，不记录使用量。
8. `Options{TrackUsage: true}` 开启统计，允许通过 `Stats` 观察尚未归还的 Buffer。
9. 不提供“开发环境”或“生产环境”枚举，也不读取环境变量；是否统计完全由使用者的启动配置决定。
10. 不引入函数式 Option；只有一个布尔开关时，显式结构体字段更清晰。

### 4.3 容量档位

固定档位为：

```text
16 B
32 B
64 B
128 B
256 B
512 B
1 KiB
2 KiB
4 KiB
8 KiB
16 KiB
32 KiB
64 KiB
```

规则：

1. `1`～`16 B` 统一进入 `16 B` 档位。
2. 其余请求向上取整到最近的 2 的幂档位。
3. 档位使用固定长度数组保存，不使用运行时可变配置。
4. 档位索引使用位运算计算，不在线性列表中逐项查找。
5. `Acquire(0)` 返回可正常释放的空 Buffer，但不进入任何容量档位。
6. `Acquire(size < 0)` 表示框架内部违反不变量，直接 panic。
7. 大于 `64 KiB` 的 Buffer 按请求大小直接分配，释放时不进入池。
8. 首版不建立 `8 B`、`128 KiB` 或更大默认档位。

档位只表示可复用容量，不进行预分配。每个档位按实际请求惰性创建对象。

### 4.4 底层复用方式

每个容量档位使用一个独立的 `sync.Pool`。

选择 `sync.Pool` 的原因：

- 标准库实现，无新增依赖；
- 适合多个网络 goroutine 并发取得和归还临时对象；
- 常见路径具有较低竞争；
- 运行时可以在 GC 周期中清理暂时不用的对象；
- 不需要额外维护容量、后台清理协程和关闭流程。

必须接受的语义：

- `sync.Pool` 可能随时丢弃已经归还的对象；
- M2 不能保证下一次 `Acquire` 一定复用；
- M2 不把池当成缓存、内存额度或背压机制；
- 池未命中时直接创建新 Buffer。

M2 不使用有界 channel 实现池。有界 channel 会增加固定容量参数、并发竞争和满池分支，但不能替代后续网络队列的背压。

### 4.5 可选使用量统计

M2 提供可选统计，但明确把它定义为“Buffer 未归还诊断”，而不是通用内存泄漏检测器。

`NewPool(Options{})` 不更新统计。`NewPool(Options{TrackUsage: true})` 在每次有效取得和首次有效释放时更新分档原子计数，`Stats` 返回当前快照。

建议快照至少包含：

```go
type BucketStats struct {
    Capacity     int
    InUseBuffers int64
}

type Stats struct {
    Enabled            bool
    InUseBuffers       int64
    InUseCapacityBytes int64
    ZeroSizeInUse      int64
    OversizeInUse      int64
    OversizeBytes      int64
    Buckets            []BucketStats
}
```

字段语义：

- `InUseBuffers`：已取得但尚未首次有效释放的 Buffer 数量；
- `InUseCapacityBytes`：这些 Buffer 的容量合计，不等同于 Go 进程实际堆内存；
- `Buckets`：各固定容量档位当前未归还数量；
- `ZeroSizeInUse`：尚未归还的空 Buffer 数量；
- `OversizeInUse` 和 `OversizeBytes`：尚未归还的超大 Buffer 数量和容量。

约束：

1. `TrackUsage=false` 时调用 `Stats()` 返回 `Enabled=false` 的零值快照，不尝试推算未记录的数据。
2. 不记录累计取得次数、命中率、峰值和调用栈，避免更多热路径原子操作及对象登记。
3. 不尝试统计 `sync.Pool` 当前缓存了多少对象；标准库没有提供可靠枚举能力，GC 也可以随时清理缓存。
4. 并发运行时，跨多个档位拼成的快照可能对应略有差异的时刻，只用于趋势诊断。
5. 在停止准入并确认没有并发取得和释放后，快照必须精确；`InUseBuffers != 0` 表示仍有 Buffer 未归还。
6. `InUseBuffers == 0` 只能证明 Buffer 生命周期已经配平，不能证明业务对象、切片副本、连接或其他 Go 内存不存在泄漏。
7. Stats 不记录 Buffer 指针和调用栈；若以后确实需要定位具体取得位置，应另建仅用于调试的诊断能力，不放入 M2 热路径。
8. `Stats()` 属于低频诊断接口，允许为 `Buckets` 快照分配一个小切片。

关闭统计时只多一个可预测的开关分支，不执行原子加减。实施时必须分别 Benchmark 关闭和开启统计两种模式；如果关闭统计仍出现可测量的明显回退，应调整字段布局或调用位置。

### 4.6 对外配置边界

M2 只实现 Go 构造参数，不读取 YAML、JSON、环境变量或命令行。

M7 接入 Application 时，应把 Application 级启动配置映射到 `Options.TrackUsage`。建议对外配置外观为：

```yaml
buffer_pool:
  track_usage: true
```

具体配置层级在 M7 的最小配置模型中最终确认，但必须保持以下语义：

1. 不根据编译方式、可执行文件名或环境名称自动判断；
2. 开发环境可以关闭，生产环境也可以按排障需要开启；
3. 该值只在创建 Pool 时读取；
4. 不支持运行中动态开关。

不支持动态开关的原因是：运行中才开启会漏掉此前已经取得但尚未归还的 Buffer，运行中关闭也会留下无法解释的半截计数，最终结果不能用于判断生命周期是否配平。

M2 的 `Stats()` 供内部框架读取。M7 接入时应提供 Application 级只读诊断入口；M15 在
Service、连接和队列已经停止并排空后，可以读取最终快照并对非零未归还数量进行告警。
M2 本身不依赖日志，也不提前定义 Application API。

## 5. Buffer 生命周期与所有权

### 5.1 单一所有权

一个 Buffer 在任意时刻只能有一个所有者。所有权可以转移，但不能复制成两个同时有效的所有者。

后续进入发送队列时采用以下规则：

```text
编码器持有
  → 成功投递到队列
  → 队列或 Writer 持有
  → 写入完成、失败或关闭
  → Release
```

转移成功后，原所有者不能再调用 `Bytes` 或 `Release`。M2 只建立这一约束和测试辅助场景，不实现网络队列。

### 5.2 Release

`Release` 采用以下规则：

1. `(*Buffer)(nil).Release()` 允许执行并直接返回，便于错误路径统一清理。
2. 第一次有效释放会把档位 Buffer 放回原 Pool。
3. 超过 `64 KiB` 的 Buffer 在释放时清除底层切片引用，由 GC 回收。
4. 空 Buffer 只清理自身，不进入档位池。
5. 在对象尚未被重新取得前，重复调用 `Release` 不会再次放回池，也不会 panic。
6. 释放后的 Buffer 不得再次使用；在尚未被重新取得前调用 `Bytes` 会 panic，以尽早暴露框架内部错误。
7. 同一个 Buffer 不支持由多个 goroutine 并发调用 `Bytes` 或 `Release`。

第 5 条只用于避免常见错误路径造成池污染，不承诺支持“释放后继续长期持有旧指针”。对象一旦释放，旧指针立即失效；如果其后对象已经被其他 goroutine 重新取得，Go 指针本身无法在不增加租约对象、generation 和额外分配的情况下识别旧所有者。

M2 不为这种非法使用增加复杂的引用计数或租约系统，而通过单一所有权、封闭包边界、竞态检测和后续队列测试约束正确使用。

### 5.3 数据与清理

- Buffer 记录来源 Pool、档位、有效长度和使用状态；
- 档位 Buffer 归还前把有效长度重置为零；
- 默认不清零底层字节，避免每次释放产生额外内存写入；
- 下一次使用者只能看到自己请求的有效长度；
- 框架必须在读取或发送前覆盖全部有效区域；
- M2 不向业务暴露旧数据；
- 特别敏感的数据由未来所属组件在释放前显式清零，不在 M2 增加全局开关。

## 6. 并发与资源边界

- `Pool.Acquire` 和不同 Buffer 的 `Release` 可以被多个 goroutine 并发调用；
- 单个 Buffer 仍遵循单一所有权，不是并发容器；
- Pool 不启动后台 goroutine；
- Pool 不保证保留数量，也不提供预热；
- 丢弃 Pool 之前，所属组件必须已经收回全部仍在使用的 Buffer；
- M7 接入后由 Application 持有 Pool，并由其中 Node 共享；
- M2 阶段只由测试显式创建 Pool，不建立默认全局实例。

## 7. 性能与内存约束

### 7.1 实现约束

- 档位定位不得产生堆分配；
- 稳态档位 Buffer 的 `Acquire → Bytes → Release` 目标为 `0 allocs/op`；
- 热路径不使用反射、`fmt`、接口抽象、日志或闭包；
- 不为了统计命中率在热路径增加原子计数；
- `TrackUsage=false` 时不在热路径执行统计原子操作；
- `TrackUsage=true` 时只维护当前未归还数量，不维护命中率、累计次数或峰值；
- 不实现小于 `16 B` 的栈上快速路径，留到 M5 的真实读取路径验证；
- 不使用 `unsafe`；
- 超大 Buffer 释放后不能被任何档位对象继续引用。

如果 Benchmark 显示某个优化会明显增加代码复杂度，或在常用尺寸上产生延迟回退，应按开发原则暂停并与开发者确认，不自行加入技巧性优化。

### 7.2 Benchmark

至少覆盖：

```text
16 B
32 B
64 B
256 B
1 KiB
4 KiB
32 KiB
64 KiB
128 KiB
```

每个尺寸至少比较：

- 直接分配且强制逃逸；
- 单 goroutine、`TrackUsage=false`；
- `RunParallel`、`TrackUsage=false`；
- 单 goroutine、`TrackUsage=true`；
- `RunParallel`、`TrackUsage=true`。

Benchmark 必须报告：

- `ns/op`；
- `B/op`；
- `allocs/op`。

直接分配基线必须显式制造与未来网络队列相近的逃逸，避免编译器把局部 `make` 优化到栈上后得到不公平结论。可以额外保存不逃逸的局部基线，但不能用它单独否定跨 goroutine 场景的池化收益。

M2 记录基础操作平均延迟；真实网络路径的 p50、p95、p99、吞吐和 GC 暂停在 M5/M13
集成后再测，避免用脱离网络所有权转移的微基准代替端到端数据。

### 7.3 突发流量与内存滞留

测试至少执行：

1. 固定 `GOMAXPROCS`；
2. 预热全部档位；
3. 多轮并发突发取得和释放；
4. 每轮结束后执行 GC，并记录 `HeapAlloc`、`HeapInuse` 和 GC 次数；
5. 单独验证 `128 KiB` 及更大 Buffer 释放后不重新进入池。

Go 分配器和 `sync.Pool` 的清理时机受运行时影响，因此不使用跨机器不稳定的精确字节数作为普通单元测试断言。实施计划应保存固定环境和命令下的基线；如果多轮 GC 后活跃内存持续无界增长，则里程碑不得验收。

## 8. 测试要求

### 8.1 单元测试

至少覆盖：

- `0`、边界值和每个容量档位；
- 请求长度与返回切片长度；
- 向上取整后的容量；
- `64 KiB` 与 `64 KiB + 1` 的池化边界；
- 负长度 panic；
- 空 Buffer 释放；
- nil Buffer 释放；
- 同一所有者立即重复释放不会重复入池；
- 释放后访问在可检测窗口内 panic；
- 大 Buffer 不污染容量档位；
- 归还后有效长度被重置；
- 默认不清零语义；
- 多个 Pool 相互隔离；
- Pool 开始使用后只通过指针传递。
- `TrackUsage=false` 时 `Stats().Enabled` 为 false；
- `TrackUsage=true` 时取得和释放后的总量、分档数量和容量；
- 空 Buffer 与超大 Buffer 的统计；
- 重复释放不会重复扣减统计；
- 静止点仍有未释放 Buffer 时统计不为零，全部释放后恢复为零。

### 8.2 并发与压力测试

至少覆盖：

- 多 goroutine 并发操作同一个 Pool；
- 多个独立 Pool 并发运行；
- 不同尺寸随机取得和释放；
- 重复突发后没有数据串用；
- 全部并发测试通过 `go test -race`；
- 测试结束后不残留 goroutine。

M2 不编写 TCP、NATS 或 RPC 集成测试，因为本里程碑尚未接入这些组件。Buffer 的真实所有权转移和错误路径集成测试进入 M5。

## 10. 明确不实现

- 通用 `ObjectPool[T]`；
- 业务可见的 Buffer 池；
- 包级默认 Pool；
- Pool 配置文件和动态容量档位；
- Pool 预热、后台收缩和关闭协程；
- 默认开启和运行中动态切换的统计；
- Buffer 指针登记、取得调用栈和通用内存泄漏分析器；
- 引用计数、共享 Buffer 和零拷贝消息；
- 自动安全清零；
- `timerEntry`、`pendingCall` 和业务消息池；
- Protobuf Marshal/Unmarshal；
- TCP 读写与发送队列；
- Application、Node 或 Service 接入；
- 内存额度、最大包长、队列容量和背压；
- `unsafe` 优化；
- 为小包预先加入栈上快速路径。

## 12. 验收标准

1. M2 只新增内部 Buffer 池，不引入后续里程碑能力。
2. 不使用包级可变状态或 `init()`。
3. 默认档位固定为 `16 B`～`64 KiB`。
4. 档位 Buffer 可以并发取得和释放，且通过竞态检测。
5. Buffer 的请求长度、容量、来源池和释放状态符合本文规则。
6. 立即重复释放不会造成同一对象被重复放回池。
7. 大于 `64 KiB` 的 Buffer 不进入池，也不在释放后保留底层切片引用。
8. 默认不清零，不实现引用计数和零拷贝。
9. 稳态池化路径的分配显著低于强制逃逸的直接分配路径。
10. 常用尺寸没有无法解释的明显延迟回退。
11. 突发流量结束并经过 GC 后没有持续无界增长。
12. 单元测试、竞态检测、Benchmark、逃逸分析和跨平台构建全部通过。
13. M2 不增加第三方依赖。
14. `TrackUsage=false` 不执行统计原子加减；`TrackUsage=true` 可以在静止点准确报告未归还 Buffer。
15. 开启与关闭统计分别保存串行和并发 Benchmark。

## 13. 二次 Review 结论

二次 Review 已检查详细设计、v2 `util/bytespool`、M0/M1 边界和 M2 草案，结论如下：

1. `16 B` 档位已加入，默认档位改为 `16 B`～`64 KiB`；仍不加入 `8 B` 和 `128 KiB`。
2. M2 仍只实现 Buffer 池，没有把 `timerEntry`、`pendingCall`、TCP 或 Application 接入带入本里程碑。
3. `sync.Pool` 适合复用但不提供缓存对象数量，因此不能把“池中对象数量”作为泄漏判断。
4. 真正对泄漏诊断有价值的是静止点的“取得但未归还”数量和容量，因此增加可选统计。
5. 框架不区分开发与生产环境，使用者通过 `Options.TrackUsage` 决定是否开启；关闭时避免所有网络请求承担原子计数成本。
6. 统计只能发现 Buffer 生命周期不配平，不能代替 Go heap profile、goroutine profile、连接统计或业务对象泄漏分析。
7. Pool 无独立资源和后台任务，不需要为了统计增加 `Close`；未来 Application 在停止并排空后读取快照即可。
8. `Release` 的重复调用保护、释放后旧指针边界和单一所有权已经明确，不增加 generation、引用计数或租约对象。
9. 超大 Buffer 不进入池，且单独统计其未归还数量和容量，可以覆盖最有风险的滞留场景。
10. Benchmark 已区分关闭统计、开启统计和强制逃逸直接分配，能够同时验证收益和诊断成本。
11. 统计只能在 Pool 创建时确定，运行中动态切换会产生不完整计数，已明确禁止。
12. M7 必须把该选项映射为 Application 级对外配置，但具体配置模型不提前放入 M2。

本轮未发现需要扩大 M2 范围的其他问题。

## 14. 开工 Review 已确认

已确认以下方案：

1. 包路径和包名使用 `internal/bufferpool` 与 `bufferpool`，明确表达这是 Buffer 内存池而不是普通 Buffer 数据结构包；
2. 使用 `NewPool(Options)`、`Acquire`、`Bytes`、`Release` 最小外观，不增加 Config、Close、Append 或 Resize；
3. `Release` 放在 Buffer 上，避免调用方额外保存或传错 Pool；
4. 固定 `16 B`～`64 KiB` 档位，大于 `64 KiB` 直接分配并在释放时丢弃；
5. 使用每档一个 `sync.Pool`，不使用有界 channel；
6. Release 支持 nil 和可检测窗口内的重复调用；释放后继续持有旧指针属于不支持的内部错误，不增加 generation 或租约对象；
7. 默认不清零，不提供安全清零开关；
8. 提供 `Options.TrackUsage` 和 `Stats`，由使用者在启动配置中决定是否统计，不由框架区分开发或生产环境；`Options{}` 和 `TrackUsage:false` 均表示默认关闭；
9. Stats 只统计当前未归还 Buffer，不记录调用栈、指针、累计次数、命中率或池内缓存数量；
10. 统计开关只在创建 Pool 时生效，不支持运行中动态切换；
11. M7 将统计开关映射为 Application 级对外配置，M2 不提前实现配置文件加载；
12. M2 只报告微基准平均耗时与分配，端到端延迟分位数留到 M5/M13；
13. 突发内存测试采用固定环境基线和“不得持续无界增长”，不使用易波动的跨机器精确字节阈值；
14. M2 通过 Review 后才创建 `M2-内存复用库实施计划.md` 并开始编码。

## 15. 实施结果

M2 已按本文边界完成：

- 新增 `internal/bufferpool`，实现 `16 B`～`64 KiB` 固定档位、单一所有权 Buffer 和默认关闭的可选未归还统计；
- 单元测试、并发测试、竞态检测、逃逸分析、Benchmark 和突发内存测试全部通过；
- 稳态池化路径在全部池化档位达到 `0 B/op、0 allocs/op`；
- 大于 `64 KiB` 的 Buffer 按设计直接分配，释放后清除底层切片引用；
- Windows/amd64 与 Linux/amd64 构建均通过；
- 未增加第三方依赖，也未提前接入 Application、网络或 RPC。

完整命令、测试范围、性能数据和内存基线见 [M2 内存复用库实施计划](../../plans/M2-内存复用库实施计划.md)。
