# Origin 第三版 M0 工程基础里程碑设计

> 文档状态：范围已确认，工程参数待逐项确认  
> 创建日期：2026-07-25  
> 最后更新：2026-07-25

## 1. 目标

M0 只建立后续所有代码共同依赖的工程基础，不实现日志、内存池、配置、命令、网络、Application、Service 或 RPC。

完成 M0 后，仓库应具备稳定的编译、测试、版本注入和基础错误表达能力，后续里程碑不再反复修改工程根基。

## 2. 实现范围

### 2.1 工程结构

- 创建 Go module；
- 确认 module path 和最低 Go 版本；
- 建立公开包与 `internal` 包的边界；
- 建立测试、Benchmark 和生成代码检查入口；
- 不复制 v2 与 M0 无关的第三方依赖。

### 2.2 基础错误

M0 只实现不依赖 RPC 的轻量错误基础：

- 稳定的错误码类型；
- `CodeInternal` 和 `CodeInvalidConfig` 等基础码的定义位置；
- 错误码、消息和本地 cause 的最小组合；
- `errors.Is`、`errors.As` 和 `Unwrap` 行为；
- 不实现 RPC 线协议错误编码。

完整错误码仍以[统一错误码设计](../details/2026-07-24-统一错误码设计.md)为依据，后续里程碑按需增加所属错误码。

### 2.3 构建信息

内置可由 `-ldflags -X` 注入的：

- `BuildTime`；
- `Version`；
- `Commit`。

规则：

- 未注入时允许为空；
- 库不在运行时伪造构建时间；
- M0 提供只读查询接口；
- help 和 version 的展示逻辑进入 M4。

### 2.4 质量入口

M0 至少提供并验证：

```text
go test ./...
go test -race ./...
go test -run=^$ -bench=. ./...
```

生成代码校验入口在 M0 建立约定，实际 `origin-gen` 到 M9 实现。

## 3. 明确不实现

- Zap 日志门面和文件输出；
- Buffer 池与其他对象池；
- YAML、JSON 配置加载；
- Command Runner 和 PID 文件；
- TCP、NATS 和任何网络协议；
- Application、Node、Service 和 Module；
- 调度器、Await、Timer 和 Deadline；
- Protobuf、RPC 代码生成和 RPC Runtime。

## 4. 依赖规则

- M0 优先只依赖 Go 标准库；
- 新增第三方依赖必须属于当前里程碑的明确需求；
- 后续日志、NATS、Protobuf 等依赖在各自里程碑加入；
- 不建立包含所有 v2 依赖的初始 `go.mod`；
- 不为了未来可能使用的能力提前创建抽象接口。

## 5. 开工前确认

1. Go module path；
2. 最低 Go 版本；
3. `BuildTime`、`Version`、`Commit` 所在包路径；
4. 基础错误包名称和公开边界；
5. 格式化、静态检查和 CI 的首版命令集合。

## 6. 验收标准

1. 新仓库可以在没有业务代码的情况下完成构建和测试。
2. `BuildTime`、`Version`、`Commit` 可以通过 ldflags 注入并被查询。
3. 未注入构建信息时不会产生错误或伪造值。
4. 基础错误支持码、消息、cause、`Is`、`As` 和 `Unwrap`。
5. M0 不引入 Zap、NATS、Protobuf、YAML 等后续依赖。
6. `go test ./...` 和 `go test -race ./...` 通过。
7. 工程目录和公开包边界有测试或编译用例约束。

## 7. 下一步

M0 参数确认并在[里程碑设计文档复核清单](./里程碑设计文档复核清单.md)中记录“允许实施”后，才编写独立实施计划。M0 验收完成后进入 M1 日志库，不同时实现后续里程碑。
