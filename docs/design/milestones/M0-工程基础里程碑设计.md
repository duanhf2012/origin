# Origin 第三版 M0 工程基础里程碑设计

> 文档状态：已实现并通过验收
> 创建日期：2026-07-25  
> 最后更新：2026-07-25

## 1. 目标

M0 只建立后续所有代码共同依赖的工程基础，不实现日志、内存池、配置、命令、网络、Application、Service 或 RPC。

完成 M0 后，仓库应具备稳定的编译、测试、版本注入和基础错误表达能力，后续里程碑不再反复修改工程根基。

## 2. 实现范围

### 2.1 工程结构

- 创建 Go module；
- 确认 module path 和最低 Go 版本；
- 建立公开包与 `internal` 包的边界；
- 在 `scripts` 目录提供 Windows、Linux amd64 构建脚本；
- 在 `examples/basic` 提供最小可编译示例；
- 建立测试、Benchmark 和生成代码检查入口；
- 不复制 v2 与 M0 无关的第三方依赖。

### 2.2 基础错误

M0 只实现不依赖 RPC 的轻量错误基础：

- 稳定的错误码类型；
- `CodeInternal` 和 `CodeInvalidConfig` 等基础码的定义位置；
- 错误码、消息和本地 cause 的最小组合；
- `errors.Is`、`errors.As` 和 `Unwrap` 行为；
- 不实现 RPC 线协议错误编码。

完整错误码仍以[统一错误码设计](../details/2026-07-24-统一错误码设计.md)为依据，后续里程碑按需增加所属错误码。

### 2.3 构建信息

内置可由 `-ldflags -X` 注入的：

- `BuildTime`；
- `Version`；
- `Commit`。

规则：

- 未注入时允许为空；
- 库不在运行时伪造构建时间；
- M0 提供只读查询接口；
- help 和 version 的展示逻辑进入 M4。

### 2.4 质量入口

M0 至少提供并验证：

```text
go test ./...
go test -race ./...
go test -run=^$ -bench=. ./...
```

生成代码校验入口在 M0 建立约定，实际 `origin-gen` 到 M11 实现。

## 3. 明确不实现

- Zap 日志门面和文件输出；
- Buffer 池与其他对象池；
- YAML、JSON 配置加载；
- Command Runner 和 PID 文件；
- TCP、NATS 和任何网络协议；
- Application、Node、Service 和 Module；
- 调度器、Await、Timer 和 Deadline；
- Protobuf、RPC 代码生成和 RPC Runtime。

## 4. 依赖规则

- M0 优先只依赖 Go 标准库；
- 新增第三方依赖必须属于当前里程碑的明确需求；
- 后续日志、NATS、Protobuf 等依赖在各自里程碑加入；
- 不建立包含所有 v2 依赖的初始 `go.mod`；
- 不为了未来可能使用的能力提前创建抽象接口。

## 5. 已确认工程参数

1. Go module path 使用 `github.com/duanhf2012/origin/v3`；
2. 最低 Go 版本使用 Go 1.26.5，`go.mod` 写入 `go 1.26.5`；
3. 构建信息使用公开包 `buildinfo`，提供 `BuildTime()`、`Version()` 和 `Commit()` 只读函数，内部字符串通过 `-ldflags -X` 注入；
4. 基础错误使用公开包 `errs`，`Code` 底层类型为 `uint32`；
5. M0 首批通用错误码为 `CodeOK=0`、`CodeCanceled=1`、`CodeDeadlineExceeded=2`、`CodeInternal=3`、`CodeInvalidArgument=4`、`CodeInvalidConfig=5`；
6. 首版质量命令为 `gofmt`、`go vet ./...`、`go test ./...`、`go test -race ./...` 和 `go test -run=^$ -bench=. -benchmem ./...`；
7. M0 不引入 staticcheck、golangci-lint 或任何第三方 Go module 依赖；
8. `scripts` 目录提供 `buildwin.bat` 和 `buildlinux.bat`：默认编译 `./...`，也允许通过参数指定构建目标；构建时关闭 CGO，并注入 BuildTime、Version 和 Commit；
9. 构建脚本默认使用带本地时区的当前时间、当前提交的精简哈希和当前提交上的精确 Git Tag；不使用历史中距离最近的 Tag，避免 v3 开发提交被标记成 v2 版本。三项信息分别允许通过 `ORIGIN_BUILD_TIME`、`ORIGIN_BUILD_VERSION`、`ORIGIN_BUILD_COMMIT` 覆盖。
10. 示例统一放入 `examples` 目录，不建立独立 Go module；`examples/basic` 作为最小示例持续演进，独立场景使用不同子目录。
11. 简单测试和 Go Example 与源码放在同一目录的 `*_test.go`；`testdata` 默认只保存测试数据；跨包集成测试和端到端测试分别放入 `tests/integration`、`tests/e2e`；确实需要独立进程时才在 `tests/helpers/<用途>` 建立辅助程序，不为简单验证随意建立 `main` 包。

## 6. 验收标准

1. 新仓库可以在没有业务代码的情况下完成构建和测试。
2. `BuildTime`、`Version`、`Commit` 可以通过 ldflags 注入并被查询。
3. 未注入构建信息时不会产生错误或伪造值。
4. 基础错误支持码、消息、cause、`Is`、`As` 和 `Unwrap`。
5. M0 不引入 Zap、NATS、Protobuf、YAML 等后续依赖。
6. `go test ./...` 和 `go test -race ./...` 通过。
7. 工程目录和公开包边界有测试或编译用例约束。
8. `scripts/buildwin.bat` 和 `scripts/buildlinux.bat` 均可成功完成对应目标系统的编译。
9. `examples/basic` 参与 `go build ./...`，并可独立运行。

## 7. 下一步

M0 已完成实现和验收。后续进入 M1 日志库前，仍须先重新阅读并 Review 对应设计；不同时实现后续里程碑。
