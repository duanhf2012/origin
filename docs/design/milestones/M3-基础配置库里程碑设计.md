# Origin 第三版 M3 基础配置库里程碑设计

> 文档状态：已实现并通过验收
> 创建日期：2026-07-25
> 最后更新：2026-07-26

## 1. 目标

M3 实现一个独立的基础配置库，负责：

- 从指定目录递归发现配置文件；
- 以稳定顺序读取 YAML 和 JSON；
- 把多个配置片段合并后解析到调用方提供的 Go 值；
- 在重复定义和格式错误时返回具有来源位置的错误；
- 不向调用方暴露中间配置树、Snapshot 或解析器对象。

M3 只处理“配置文件如何发现、解析、展开安全环境变量值、组合和解码”，不认识 Application、Node、Service、Module、日志、RPC 或服务发现等业务模型。

完成 M3 后，M4 可以复用目录扫描和配置检查能力，M7 可以在此基础上定义 Application、Node 与 Service 的最小配置结构。

Application、Node、RPC、Discovery 和 Service 业务配置的整体外观统一记录在[完整配置模型设计](../details/2026-07-26-完整配置模型设计.md)。该文档尚未确认的顶层字段不能由 M3 示例或实现隐式决定。

## 2. 前置依赖与边界

M3 依赖：

- M0 的 Go module、Go 1.26.5、`errs` 和质量门禁；
- Go 标准库；
- 固定版本的 YAML 解析依赖。

M3 不依赖：

- M1 日志；
- M2 BufferPool；
- Application、Node、Service 或命令行；
- 网络、NATS、Protobuf 或远端配置中心。

配置库不记录日志，不调用 `os.Exit`，也不创建 goroutine。所有失败均通过 `error` 返回，由最终调用方决定如何显示和退出。

## 3. v2 对照与重构重点

当前 `origin` 目录中的 v2 `cluster/parsecfg.go` 实际识别 `.json`、`.yml` 和 `.yaml`，并允许在多个文件中拆分 Node 与 Service 配置。这些使用习惯继续保留。

首版只保留 v2 Cluster 配置加载实际使用的 JSON 和 YAML，不增加 TOML。若以后出现明确的 TOML 项目需求，再单独增加解析适配，不扩大 M3 的实现和测试范围。

v3 不延续以下问题：

1. `filepath.Walk` 的处理顺序没有形成公开、可测试的确定性契约；
2. 先用 `json.Valid` 猜测格式，失败后再当 YAML 解析，错误格式与文件扩展名不一致；
3. YAML 先转 `map[string]interface{}`，再转 JSON，丢失原始文件、行和列；
4. 使用 `interface{}` 和未经检查的类型断言，错误配置可能 panic；
5. 使用 `os.ExpandEnv` 在解析前替换整份文件，缺失变量会静默变为空字符串，并可能改变配置语法结构；
6. 多文件组合规则散落在 Cluster 业务逻辑中，基础加载与 Node/Service 语义耦合；
7. 部分重复配置被拒绝，部分配置按遍历结果组合，通用规则不清晰；
8. 配置加载过程可能调用日志 `Fatal`，库代码直接控制进程；
9. `ParseServiceCfg` 每次通过 Map、JSON Marshal 和 JSON Unmarshal 重新转换完整配置。

M3 完全重新实现，不复制 v2 代码。v2 只作为兼容行为和问题来源的对照。

## 4. 包位置与公开外观

### 4.1 包位置

建议建立公开包：

```text
config
```

使用公开包的原因：

- M4 的自定义离线命令可能需要复用配置检查；
- M7 及后续 Application 需要使用；
- 项目代码可以在不启动 Origin Runtime 的情况下编写自己的配置检查工具；
- 包本身不暴露框架运行时状态，也不会造成 Service 绕过生命周期。

不建立 `internal/config` 与公开包装层两套重复 API。

### 4.2 核心 API

建议外观：

```go
package config

func LoadDir(dir string, dst any) error
```

规则：

- `LoadDir` 默认递归查找 JSON 和 YAML 文件，不要求调用方建立 Loader、Snapshot 或传入 Options；
- `dst` 必须是非 nil 指针；
- 配置树只在一次加载调用内部存在，合并和解码完成后释放；
- 不提供可变全局配置、注册表或 `init()`；
- 不提供 Loader、Snapshot 和接口类型，当前没有配置解析策略或替换实现的真实需求。

典型使用方式：

```go
var cfg Config

if err := config.LoadDir("./config", &cfg); err != nil {
    return err
}
```

## 5. 目录扫描规则

`LoadDir` 只接受目录，不同时兼容单文件路径。调用方只需要传入配置目录，库自动发现其中的 JSON 和 YAML 文件。

扫描规则：

1. `dir` 不能为空；
2. 入口必须存在并且是目录；
3. 使用 `filepath.WalkDir` 递归扫描；
4. 只读取扩展名为 `.json`、`.yml`、`.yaml` 的普通文件；
5. 扩展名按 ASCII 大小写不敏感匹配，使 Windows 与 Linux 行为一致；
6. 其他文件和目录不作为错误，也不读取；
7. 所有候选文件先转换为相对配置根目录的清理路径；
8. 相对路径分隔符统一为 `/`，再按字节字典序排序；
9. 文件读取、合并和错误返回都使用这一确定顺序；
10. 支持的配置文件数量为零时返回配置错误，避免空目录被当成有效配置；
11. 大小写折叠后相同的两个相对路径返回错误，避免同一目录在 Windows 与 Linux 得到不同结果。

文件名只决定格式和处理顺序，不决定 NodeID、ServiceName 或配置层级。

### 5.1 符号链接

兼顾扫描边界与 Kubernetes ConfigMap 挂载方式，建议采用：

- 不递归进入符号链接目录；
- 允许符号链接文件，但解析后的最终目标必须是普通文件；
- 最终目标必须仍位于配置根目录的真实路径内；
- 指向配置根目录外、形成循环或目标不存在的符号链接返回配置错误；
- 排序和错误来源使用配置目录中的逻辑相对路径，不使用临时目标目录名；
- 同一个目标被多个逻辑配置文件引用时，仍按多个配置片段处理，重复内容由合并规则检查。

这样既不会通过目录链接扫描到配置根目录以外，也能读取 Kubernetes ConfigMap 在挂载根目录下建立的文件链接。

## 6. 格式与解析依赖

### 6.1 格式选择

M3 支持：

- JSON：使用 Go 1.26.5 稳定的标准库 `encoding/json` 验证和解码严格 JSON；
- YAML：使用固定版本的第三方 YAML 库解析；
- `.yml` 与 `.yaml` 语义完全一致。

不支持 TOML、XML、INI、HCL 或无扩展名文件。

文件内容必须与扩展名一致：

- `.json` 必须通过严格 JSON 语法验证，不能把 YAML 内容写入 `.json`；
- `.json` 不支持 `//` 或 `/* */` 注释、尾随逗号及其他 JSONC/JSON5 扩展；
- `.yml` 和 `.yaml` 按 YAML 解析；
- 不在一种格式解析失败后自动尝试其他格式。

每个 JSON/YAML 文件只允许一个文档，YAML 多文档流首版不支持。两种格式解析后的根节点都必须是 Mapping；空文件、只有注释的文件、根 Scalar 和根 Sequence 均返回配置错误。

Go 1.26.5 的 `encoding/json/v2` 与 `encoding/json/jsontext` 仍需 `GOEXPERIMENT=jsonv2` 才能使用，API 不受 Go 1 兼容承诺保护，并且同样按标准 JSON 解析，不提供注释选项。M3 不启用该实验、不引入 JSONC/JSON5 库，也不在读取前自行删除注释。需要注释的配置统一使用 YAML。

### 6.2 YAML 依赖建议

建议固定：

```text
github.com/goccy/go-yaml v1.19.2
```

选择理由：

1. 提供 AST 和来源位置能力；M3 在其上实现统一的零 Tag/可选 `json` Tag 字段映射，不直接采用 YAML 专属 Tag 语义；
2. 默认拒绝重复 Mapping Key；
3. 支持严格未知字段检查；
4. 解析和类型错误能够包含行列与源代码位置；
5. 提供 AST 和从 Node 解码能力，适合实现多文件来源追踪；
6. 当前版本没有额外运行时依赖；
7. MIT 许可证；
8. v2 使用的 `gopkg.in/yaml.v3` 原仓库已经停止维护，v3 不继续使用旧导入路径。

本选择只引入 YAML 编解码能力，不启用跨文件 Anchor 引用、YAMLPath、校验器集成或全局自定义编解码注册。

官方资料：

- [goccy/go-yaml 项目说明](https://github.com/goccy/go-yaml)；
- [goccy/go-yaml v1.19.2 API](https://pkg.go.dev/github.com/goccy/go-yaml@v1.19.2)；
- [YAML 官方组织维护的 go-yaml 项目状态](https://pkg.go.dev/go.yaml.in/yaml/v3)。

## 7. 配置树与多文件合并

### 7.1 内部表示

每个文件先解析为仅在本次 `LoadDir` 调用中使用的内部配置树。每个节点至少能够追踪：

- 逻辑相对文件路径；
- 行号；
- 列号；
- 节点种类；
- Mapping Key 或 Sequence 中的位置。

内部配置树在合并和解码时保留必要的来源信息，错误返回后或 `LoadDir` 成功完成后即可释放。M3 不向使用者公开 `map[string]any`、AST 节点、源文件字节或配置树对象。

### 7.2 合并规则

按已排序文件顺序，将每个根 Mapping 合并到本次加载的内部配置树：

1. Mapping 与 Mapping：递归合并；
2. Sequence 与 Sequence：按文件顺序追加，单个文件内部顺序保持不变；
3. 同一路径的 Scalar、Null 或其他非容器值重复出现：返回错误；
4. 同一路径两侧节点种类不一致：返回错误；
5. 同一文件中的重复 Mapping Key：解析阶段直接返回错误；
6. Mapping Key 必须是字符串；
7. 不存在“后文件覆盖前文件”；
8. 不根据文件名或格式设置优先级；
9. YAML 与 JSON 片段使用相同合并规则。

示例：

`10-gateway.yaml`：

```yaml
nodes:
  - id: gateway-1
```

`20-game.json`：

```json
{
  "nodes": [
    {"id": "game-1"}
  ]
}
```

合并结果等价于：

```yaml
nodes:
  - id: gateway-1
  - id: game-1
```

如果两个文件都定义：

```yaml
log:
  mode: async
```

则第二个定义触发错误，错误消息同时指出第一次和第二次定义的文件、行和列。

Sequence 中的 NodeID、ServiceName 等业务唯一性不由 M3 判断。M7 解码为框架配置后，再按自己的模型报告重复 NodeID。

### 7.3 多文件拆分保证

配置文件边界不等于配置对象边界。M3 必须允许同一个父 Mapping 和同一个 Sequence 分散在多个文件中：

- 顶层 Mapping 可以在多个文件中分别补充日志、Node、Service 或发现配置；
- 最终配置模型中的顶层 `nodes` 列表可以在多个文件中分别声明不同 Node，使每个程序或 Node 拥有独立文件；
- 框架公共配置、Node 列表、Service 配置和各功能配置可以分别保存；
- Service 配置可以按 Service 或功能模块拆分；
- YAML 与 JSON 可以存在于同一个配置目录并共同组成最终配置。

以下内容只演示 Mapping 与 Sequence 的通用合并，不确认最终顶层配置模型：

`10-log.yaml`：

```yaml
log:
  mode: async
```

`20-gateway.yaml`：

```yaml
nodes:
  - id: gateway-1
    services:
      - GatewayService
```

`30-game.json`：

```json
{
  "nodes": [
    {
      "id": "game-1",
      "services": ["PlayerService", "SceneService"]
    }
  ]
}
```

三个文件必须能够组成同一份进程配置，不要求使用者把所有 Node 或 Service 写进一个大文件。配置中不建立 `application` 对象；Application 只是后续读取这些配置并管理 Node 的运行时对象。

Sequence 追加只负责保留片段，不判断元素身份。同一个 NodeID、ServiceName 或顺序项是否允许重复，由 M7 及所属业务模型校验；M3 不按数组元素中的 `id`、`name` 等字段进行隐式覆盖、拼接或去重。因此可以把不同 Node 分别放入不同文件，但同一个 NodeID 不能依靠写成两个列表元素来合并。

### 7.4 不实现覆盖层

M3 不实现：

- `base`、`dev`、`prod` 等环境覆盖；
- 按文件名前缀决定优先级；
- `include` 或 `import`；
- Patch、删除标记和数组按 ID 覆盖；
- 公共 Service 配置与 Node 专属配置的继承。

如果后续确实需要环境覆盖，应建立独立设计，显式定义优先级和删除语义，不能改变 M3 已有配置在无覆盖层时的结果。

## 8. 强类型解码

```go
func LoadDir(dir string, dst any) error
```

`LoadDir` 把完整合并配置解析到 `dst`。

规则：

- `dst` 必须是非 nil 指针；
- 支持结构体、Map、Slice 和基础类型指针，但完整根配置通常解析到结构体或 Map；
- 只处理结构体可导出字段；
- 字段名精确匹配；
- 使用统一的强类型解码规则，不因片段来自 JSON 或 YAML 而改变字段匹配；
- 未声明 Tag 的可导出字段按确定性规则自动转为 `snake_case`，例如 `DefaultTimeout` -> `default_timeout`、`NodeID` -> `node_id`、`HTTPServerURL` -> `http_server_url`；
- `json:"name"` 覆盖自动名称，`json:"-"` 忽略字段；
- `json:",omitempty"` 等未指定名称的 Tag 仍使用自动名称；Tag 中的 JSON 编码选项不改变配置解码规则；
- 不建立 Origin 私有的 `config` Tag，也不读取 `yaml` Tag；业务结构体为其他用途声明的 `yaml` Tag 对 `LoadDir` 没有效果；
- 匿名嵌入默认展开；多个字段、匿名嵌入或 Tag 映射为相同名称时返回配置模型冲突；
- 配置 Key 与最终字段名精确匹配，不进行大小写宽松匹配；
- 类型不匹配、数值溢出和自定义解码失败返回错误；
- 解码失败返回错误，不返回部分成功的配置对象；
- M3 不保留对 `dst` 解码结果中 Map 或 Slice 的引用。

M3 不执行 Application 或业务合法性校验。例如端口是否冲突、NodeID 是否重复、人数是否大于零，由拥有该模型的后续组件负责。

指定 Service 配置片段的读取属于 Service Runtime 已确认的 `GetServiceConfig` 和 `ParseServiceConfig` 能力，不在基础配置库重复提供 `DecodePath` 或 YAMLPath。

### 8.1 时间与字节大小类型

M3 提供两个轻量公开值类型，作为所有框架配置结构体的统一字段类型：

```go
type Duration time.Duration
type ByteSize int64

func (value Duration) Duration() time.Duration
func (value ByteSize) Bytes() int64
```

它们只负责严格解析、范围检查和读取底层值，不保存字符串，也不建立注册表或反射扩展机制。

`Duration` 的 JSON/YAML 外观：

- 必须是带单位字符串；
- 支持 `ns`、`us`、`ms`、`s`、`m`、`h`、`d`；
- `d` 固定等于 `24h`；
- 支持 `2h30m` 等单位从大到小的整数复合值；
- `0s` 表示零值；
- 拒绝裸整数、小数、负数、重复单位、乱序组合，以及 `day`、`w`、`y`。

`ByteSize` 的 JSON/YAML 外观：

- 必须是单个整数加 `B`、`KB`、`M`、`G` 或 `T`；
- `KB = 1024B`，其余单位逐级乘以 `1024`；
- `0B` 表示零值；
- 统一换算为 Byte；
- 拒绝裸整数、小数、负数、复合容量，以及 `byte`、`K`、`MB`、`GB`、`TB`、`KiB`、`MiB`、`GiB`、`TiB`；
- 乘法或向 `int64` 转换溢出时返回配置错误。

不允许用字段名携带单位。框架配置使用 `default_timeout`、`max_payload_size`、`max_age`，
不使用 `timeout_ms`、`max_payload_bytes`、`max_age_days`。

### 8.2 环境变量值展开

M3 保留 v2 的环境变量使用能力，但不继续调用 `os.ExpandEnv` 处理整份原始文件。

处理顺序固定为：

1. 按 JSON/YAML 语法解析单个文件并建立带来源位置的内部树；
2. 只遍历字符串 Scalar 值并展开 `${NAME}`；
3. 完成所有文件的确定性合并；
4. 按目标结构体执行强类型解码。

语法和安全规则：

- 只支持 `${NAME}`，变量名匹配 `[A-Za-z_][A-Za-z0-9_]*`；
- `$${NAME}` 产生字面量 `${NAME}`；
- 普通 `$` 不触发展开，`$NAME` 不支持；
- 不支持默认值、必填表达式、嵌套变量、命令替换或脚本执行；
- 不展开 Mapping Key、注释、字段名或非字符串 Scalar；
- 未定义变量立即返回配置错误；已定义为空字符串与未定义严格区分；
- 错误包含变量名、文件、行和列，但绝不包含变量值；
- 环境变量不能生成 Mapping、Sequence 或新的配置字段。

类型规则：

- 字符串中的内嵌占位符可以出现多个，展开结果仍是字符串；
- Scalar 完全由一个占位符组成时，内部节点标记为环境来源，强类型解码允许把结果严格转换到字符串、布尔、整数、浮点、`Duration`、`ByteSize` 或实现文本解码接口的目标；
- 环境来源转换不得放宽普通配置值的类型规则；
- 任何转换失败均返回目标类型错误，不静默使用零值。

M3 不读取 `.env` 文件，也不建立显式环境 Map 公共 API；测试通过进程环境隔离设置变量。环境配置覆盖层仍不属于 M3。

## 9. 未知字段、默认值与校验

### 9.1 未知字段

未知字段采用固定的严格规则，不提供开关：

- 当目标是结构体时，配置中无法匹配任何可导出字段的 Key 返回错误，以便启动前发现字段拼写错误；
- 若业务需要动态 Key，应解码到 Map。

Map 目标按 Map 的开放语义接受动态 Key，不受未知字段检查影响。

### 9.2 默认值

M3 不提供 `default` Tag、默认值表达式或反射式默认值注入。

调用方可以先构造强类型默认值，再让配置覆盖已出现的字段：

```go
cfg := DefaultConfig()

if err := config.LoadDir("./config", &cfg); err != nil {
    return err
}
```

配置字段是否必填、字段间约束和业务默认值由所属模型的 `Validate()` 或构造函数负责。这样不会在 M3 建立第二套校验框架。

## 10. 错误语义与来源位置

M3 复用 M0 的：

```text
errs.CodeInvalidArgument
errs.CodeInvalidConfig
```

建议规则：

- 空目录参数、nil 或非指针目标使用 `CodeInvalidArgument`；
- 目录不存在、读取失败、格式错误、重复定义和解码失败使用 `CodeInvalidConfig`；
- 底层文件系统和解析器错误作为本地 cause 保留；
- 不新增公开的大型 ConfigError 结构；
- 不通过错误字符串进行程序逻辑判断。

可定位到配置节点的错误消息统一包含：

```text
相对文件路径:行:列: 错误说明
```

重复定义包含两个来源：

```text
20-game.yaml:8:3: configuration path "application.mode" is already defined at 10-base.yaml:4:3
```

目录访问等无法定位到行列的错误至少包含清理后的目录或文件路径。

错误消息不得包含环境变量值、密码、Token 或整个配置文件内容。第三方 YAML 的带源码错误在返回前转换为不带颜色的文本，避免控制字符污染日志。

## 11. 资源使用边界

M3 不设置文件数量、单文件大小和目录总大小上限，也不提供相关 Options。配置读取失败、内存不足或文件系统限制按照正常错误返回。

基础配置库面向框架和业务启动配置，不建议用它加载数值表、地图或其他大型游戏资源，但首版不额外编写限制代码。M3 没有后台缓存和清理 goroutine。

## 12. 并发、生命周期与性能

- `LoadDir` 不依赖可变全局状态，可以并发加载不同目录；
- M3 不保存包级最近一次配置；
- M3 不监听文件变化；
- M3 不启动 goroutine；
- M3 不依赖日志和 BufferPool；
- `LoadDir` 返回后没有需要调用方关闭的配置库资源。

配置只在启动或离线检查时读取，不属于 RPC 热路径。首要目标是正确性、确定性和错误可定位性。

实现仍需避免明显的重复工作：

- 每个文件只读取和解析一次；
- 合并时不反复 Marshal/Unmarshal；
- 不为每个 Mapping Key 建立重复字符串副本，除非来源追踪确实需要；
- 不在没有 Benchmark 依据时加入对象池、`unsafe` 或复杂反射缓存。

## 13. 代码目录

预计新增：

```text
config/
├── loader.go
├── merge.go
├── error.go
├── loader_test.go
```

普通格式、目录和合并样本放在 `config/testdata`。M3 不需要辅助 `main`、`examples`、跨包集成测试或独立进程测试。

## 14. 测试与 Benchmark

### 14.1 目录扫描

至少覆盖：

1. 空目录参数、目录不存在和传入普通文件；
2. 递归扫描；
3. `.json`、`.yml`、`.yaml` 三种扩展名及大小写形式；
4. 忽略不支持扩展名；
5. 相对路径排序在重复运行中一致；
6. 大小写折叠路径冲突；
7. 空配置目录；
8. 不递归符号链接目录；
9. 允许目标仍位于根目录内的符号链接文件；
10. 拒绝越出根目录、循环、失效和非普通文件链接；
11. Windows 与 Linux 路径分隔符归一化。

符号链接能力在不支持创建符号链接或权限不足的平台测试中可以显式 Skip，但普通扫描测试不能被跳过。

### 14.2 格式与合并

至少覆盖：

1. JSON、YAML 和两种格式混合；
2. JSON 文件中出现 YAML 语法；
3. JSON 注释、尾随逗号和 JSON5 语法被拒绝；
4. YAML 语法错误；
5. 空文档、多文档、根 Scalar 和根 Sequence；
6. 同文件重复 Mapping Key；
7. 跨文件 Mapping 递归合并；
8. Sequence 按文件顺序追加；
9. Scalar、Null 和节点种类冲突；
10. 非字符串 Mapping Key；
11. 重复错误同时包含两处来源；
12. 文件排序改变输入创建顺序但不改变最终结果；
13. Node 与 Service 可以跨多个文件和两种格式拆分。

### 14.3 强类型解析

至少覆盖：

1. 完整结构体解码；
2. 嵌套结构、Map、Slice 和基础类型；
3. 零 Tag 自动 `snake_case` 映射对 JSON、YAML 和混合来源结果一致；
4. 同一结构体解码 JSON、YAML 和混合来源；
5. nil、非指针和 nil 指针目标；
6. 类型不匹配与数值溢出；
7. 固定拒绝未知结构体字段；
8. Map 接受动态 Key；
9. 预初始化默认值在字段缺失时保留；
10. 多个 `LoadDir` 并发调用通过竞态检测；
11. `Duration` 支持全部合法单位、复合值、零值和边界溢出；
12. `Duration` 拒绝裸整数、小数、负数、重复或乱序单位；
13. `ByteSize` 支持零值和全部简写单位的边界溢出；
14. `ByteSize` 支持 `B`、`KB`、`M`、`G`、`T` 的固定二进制语义并拒绝其他别名；
15. `${NAME}` 可以在字符串 Scalar 中安全展开；
16. 未定义变量、非法变量名和目标类型转换失败具有来源错误；
17. 环境变量不能修改字段名或生成 Mapping、Sequence；
18. 环境变量值不会出现在错误信息中；
19. 零 Tag 字段和常见连续大写缩写得到稳定的 `snake_case` 名称；特殊名称通过 `json` Tag 明确指定；
20. `json` Tag 改名、忽略和空名称行为正确；
21. `yaml` Tag 不改变 `LoadDir` 字段映射；
22. 普通字段、匿名嵌入和 Tag 的名称冲突在解码前报错。

### 14.4 资源与健壮性

至少覆盖：

1. 多次加载不泄漏文件句柄和 goroutine；
2. 错误路径不返回成功结果；
3. 对解析和合并增加 Fuzz 测试，任意输入不得造成框架 panic；
4. 全部并发测试通过 `go test -race`。

### 14.5 Benchmark

保存至少以下基线：

- 单个 4 KiB YAML 文件加载；
- 100 个 4 KiB JSON/YAML 混合配置文件扫描、解析和合并；
- 1 MiB YAML 配置加载；
- 完整结构体 `LoadDir`；
- 严格未知字段检查。

报告 `ns/op`、`B/op` 和 `allocs/op`。M3 不预设微秒阈值，但同一输入规模不能出现明显的超线性增长。

## 15. 明确不实现

M3 不实现：

- Application、Node、Service 和 Module 配置结构；
- NodeID 或 ServiceName 唯一性；
- Node 与 Service 启停顺序校验；
- 公共、Node 专属和 Service 配置继承；
- CLI 参数覆盖；
- `include`、环境覆盖、Patch 和删除语义；
- 默认值 Tag、必填 Tag 和通用 Validator；
- 配置热更新和文件监听；
- 远端配置中心；
- 密钥解密；
- TOML、XML、INI 或 HCL；
- YAML 多文档和跨文件 Anchor；
- 数值表、地图或其他大型游戏资源加载；
- 包级全局配置、日志、goroutine 和缓存；
- 可修改的 Map、AST 或原始字节访问；
- 配置写回和格式化。

## 17. 验收标准

1. M3 只新增独立配置库，不引入 Application 或业务配置模型；
2. 同一配置目录在重复运行中得到稳定的文件顺序和合并结果；
3. JSON、YAML 和混合目录均可正确加载；
4. 不通过扩展名猜测以外的回退改变文件格式；
5. 重复定义不静默覆盖；
6. Mapping 递归合并、Sequence 稳定追加；
7. 格式、合并和强类型错误具有文件、行和列；
8. 固定的严格规则能够发现未知结构体字段；
9. 完整配置可以解析到强类型目标；
10. 配置树、Snapshot 和解析器对象不对外暴露；
11. 不设置文件数量和大小限制，也不提供相关 Options；
12. 符号链接不能使扫描越出配置根目录；
13. 只在字符串 Scalar 中安全展开 `${NAME}`，不读取 `.env`，不建立环境覆盖层，也不启动后台任务；
14. 普通测试、竞态检测、Fuzz 种子、Benchmark 和跨平台构建全部通过；
15. 只增加已确认的 YAML 依赖及其必要模块记录；
16. `Duration` 和 `ByteSize` 对 JSON/YAML 使用相同严格语义，不接受无单位数值；
17. 环境变量缺失、非法语法或类型错误可以定位到源文件，变量值不会泄露。

## 18. 开工 Review

### 18.1 已确认

1. 包路径使用公开的 `config`，不建立 `internal/config`；
2. 唯一公开加载入口为 `LoadDir(dir, dst)`，不建立 Loader、Snapshot、`DecodePath` 或 `Files`；
3. 默认递归发现配置文件，不提供 Options，不设置文件数量或大小上限；
4. 只支持标准 JSON、YAML，不支持 TOML、JSONC 或实验 JSON v2；
5. 配置可以跨多个文件拆分，不建立 Application 配置对象；
6. 不支持后文件覆盖、环境覆盖层、`include`、Patch 或热更新；
7. 默认值由调用方先初始化结构体，M3 不实现默认值 Tag；
8. M3 只复用现有通用错误码，不公开大型 ConfigError；
9. Application、Node、Service、RPC 和 Discovery 业务模型不进入 M3；
10. 不建立框架级 `global`，业务自行定义顶层配置并由后续 Runtime 提供根路径读取；
11. 外部时间使用带单位字符串；容量使用二进制定值的 `B`、`KB`、`M`、`G`、`T`；
12. YAML 依赖使用实施时验证过的最新固定稳定版本；当前验证版本为 `github.com/goccy/go-yaml v1.19.2`；
13. 符号链接、来源位置、错误脱敏、Fuzz、竞态检测和 Benchmark 按本文建议执行，属于实现安全边界，不再作为业务方案选择。
14. 普通配置字段不要求 Tag，默认自动映射为 `snake_case`；需要改名或忽略时才使用标准 `json` Tag；
15. `yaml` Tag 不属于 `LoadDir` 契约，不建立 Origin 私有 `config` Tag；
16. 结构体解码固定拒绝未知字段，不提供宽松模式开关；确需动态 Key 时使用 Map；
17. Mapping 递归合并、Sequence 按稳定文件顺序追加；同路径 Scalar、Null 或节点类型重复时报错；
18. `Duration` 和 `ByteSize` 是 `config` 包公开统一类型，框架和业务均可复用；
19. 环境变量采用解析后的字符串 Scalar `${NAME}` 安全展开规则。
