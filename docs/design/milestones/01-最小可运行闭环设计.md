# Origin 第三版 M0 最小可运行闭环设计

> 文档状态：范围已确认，具体方案待继续确认
>
> 创建日期：2026-07-25
>
> 最后更新：2026-07-25

## 1. 目的

M0 只验证 Origin v3 最危险、最基础的端到端骨架：

> 两个 Node、两个 Service 通过真实 TCP 完成一次生成式 Protobuf RPC；调用方使用 Await 顺序编程；最后通过 OnStop 再次调用 RPC 存档并按顺序关闭。

M0 不追求功能完备，也不承担 v2 的源码级兼容。已经确认但不影响该闭环成立的详细设计全部保留到后续里程碑。

## 2. 验证场景

示例 Application 包含：

- `player-node`：运行 `PlayerService`；
- `db-node`：运行 `DBService`。

`DBService` 使用进程内 Map 作为可控存储，不在 M0 引入正式数据库适配器。

完整流程：

1. Application 读取最小 YAML 配置。
2. `db-node` 先启动并监听 TCP。
3. `player-node` 后启动，并根据静态配置定位 `db-node.DBService`。
4. 测试驱动向 `PlayerService` 提交保存任务。
5. `PlayerService` 调用生成的 `AwaitSavePlayer`。
6. RPC 通过真实 TCP 到达 `DBService`，完成 Protobuf 解码、内存保存和响应。
7. `AwaitSavePlayer` 等待期间，`PlayerService` 释放执行权并处理另一条已经准入的测试任务。
8. 原 RPC 完成后，原任务重新取得执行权并从 Await 后继续运行。
9. 收到 Stop 后，`PlayerService` 拒绝新任务、排空已经接受的任务，并在 `OnStop` 中再次通过 `AwaitSavePlayer` 完成最终存档。
10. `player-node` 完全停止后，`db-node` 才停止。

测试驱动只用于提交 Service 内部任务，不因此在 M0 建立本地事件系统或新的业务公开 API。

## 3. 两种部署方式

同一套示例必须支持：

### 3.1 单进程双 Node

一个 Application 在同一进程内按顺序启动 `db-node` 和 `player-node`。

### 3.2 双进程单 Node

两个进程使用同一套配置结构，各自选择启动一个 Node。测试明确先启动 DB 进程，再启动 Player 进程。

两种方式都必须经过相同的 TCP、帧协议、Protobuf、RPC Runtime 和错误路径。M0 不实现进程内 RPC 短路，避免开发模式隐藏真实部署问题。

## 4. M0 必须实现的范围

### 4.1 Application 与最小配置

M0 实现：

- 一个 Application 可以选择启动一个或多个 Node；
- Node 使用稳定的 NodeID；
- 单进程模式支持显式 Node 启动顺序；
- 默认停止顺序为实际启动顺序的反序；
- YAML 配置 Node 监听地址和静态远端 Node 地址；
- 配置错误在启动前返回，不静默忽略；
- 配置整体关闭 Deadline、RPC 默认超时、最大包长和队列上限。

每个 Node 在 M0 只运行一个 Service，因此不实现 Node 内多个 Service 的显式排序、部分排序补全和 Service 业务配置通用解析。

### 4.2 Node 与 Service 生命周期

M0 的最小状态：

```text
Starting
Running
Stopping
Stopped
Failed
```

M0 实现：

- Node 基础设施先于 Service 启动，并晚于 Service 停止；
- Service 提供 `OnInit`、`OnStart(ctx)` 和 `OnStop(ctx)`；
- 已启动组件失败时执行最小逆序清理；
- Running 才接受新的入站 RPC 和内部业务任务；
- Stopping 拒绝新任务，但允许已经接受的任务排空；
- Stopped 后不再存在业务 Runner、RPC 恢复或回调。

M0 不实现 Module、就绪门、Retired、Resume 和动态生命周期扩展。

### 4.3 Service 单执行槽与 Await

M0 实现：

- 每个 Service 任意时刻只有一个任务拥有业务执行权；
- Service 使用 FIFO Ready 队列；
- 未调用 Await 的普通任务由当前 Runner 继续执行，不为每个任务创建 goroutine；
- `Await` 明确释放执行权，原 Go 调用栈与原 goroutine 保持绑定；
- 调度器创建替代 Runner 处理后续 Ready 任务；
- 等待完成后，原任务进入 Ready 队尾；
- 原任务重新获得执行权后从 Await 后继续执行；
- 默认 Await 和 RPC 超时为 `15s`，显式 Context Deadline 优先；
- `OnStop` 使用独占 finalizer 路径，其 Await 不再调度新的普通业务任务。

M0 限制 Service 已接受但未完成的任务总数。任务一旦被接受，其 Await 恢复不能再被普通队列上限拒绝。具体默认容量在调度原型和 Benchmark 后确认。

### 4.4 最小 RPC 契约与代码生成

M0 只接受以下严格子集：

```go
type DBRPC interface {
    SavePlayer(
        ctx context.Context,
        req *pb.SavePlayerRequest,
    ) *pb.SavePlayerResponse
}
```

生成代码至少包含：

```go
AwaitSavePlayer(
    ctx context.Context,
    req *pb.SavePlayerRequest,
) (*pb.SavePlayerResponse, error)
```

M0 规则：

- 使用 Go 接口声明 RPC；
- Context 必须是第一个参数；
- 一个 Protobuf Request、一个 Protobuf Response；
- 业务接口不声明 `error`，生成客户端统一追加框架 `error`；
- 只支持一元请求—响应；
- 生成强类型客户端和服务端 Dispatcher；
- 生成期拒绝接口嵌入、非法参数和不在 M0 子集中的签名；
- 普通业务代码不直接操作 Future、Call 或 pending 表。

M0 不生成公开的 `AsyncXxx`、`NotifyXxx` 和 `BroadcastXxx`。它们后续仍复用同一个 RPC 调用核心。

### 4.5 静态目标定位

M0 客户端只支持通过明确的：

```text
NodeID + ServiceName
```

取得强类型单目标客户端。

NodeID 从静态配置解析到 TCP 地址，ServiceName 由目标 Node 的本地 Service 注册表解析。M0 不实现动态服务发现、任意实例选择、RoundRobin、标签筛选和 `AwaitService`。

### 4.6 最小 TCP Runtime

M0 实现：

- 单进程和双进程共用真实 TCP；
- Node 握手和对端身份校验；
- 一元请求和响应帧；
- RequestID 关联 pending 调用；
- 有界发送队列；
- 最大网络包长度；
- 完整写入和短写处理；
- 连接断开时一次性完成全部 pending 为传输失败；
- 基本关闭和资源释放。

M0 不实现自动重连、复杂退避、压缩、连接迁移、连接池和进程内短路。

每对 Node 的连接数量、主动连接方、重复连接裁决、帧布局和 ID 算法属于 M0 开工前确认项。

### 4.7 内部 Deadline

M0 只实现 RPC 和 Await 所需的内部 Deadline 能力：

- Node 内只有一个内部 Deadline 调度入口；
- pendingCall 正常完成、取消或断线时取消对应 Deadline；
- Deadline 到期只完成内部状态，不执行 Service 用户代码；
- 采用池化的内部定时条目时，遵守新的 TimerID、完整 Reset 和防 ABA 规则。

M0 不向 Service 暴露 `ITimer`，不实现业务 Timer、Ticker、Cron、PauseTimer 和 ResumeTimer。完整 TimerEngine 在后续里程碑实现时继续复用相同内部边界。

内部 Deadline 首版使用 Go Runtime Timer、最小堆还是精简时间轮，需要在实施计划前确认。

### 4.8 内存复用

M0 实现：

- Application 创建一个内部 Buffer 池，供其中 Node 共享；
- 网络队列通过 `*Buffer` 转移单一所有权；
- 默认容量档位为 `32 B` 到 `64 KiB` 的 2 的幂；
- 大于 `64 KiB` 的 Buffer 直接分配，释放时交给 GC；
- 不建立 `8 B`、`16 B` 和 `128 KiB` 默认档位；
- 接收 Buffer 在 Protobuf 解码完成或失败后释放；
- 发送 Buffer 在完整写入、失败或连接关闭后释放；
- Protobuf 尽量直接编码到最终发送 Buffer；
- Future 和 Call 的内部状态合并为池化的 `pendingCall`；
- Protobuf Request 和 Response 业务消息不池化；
- Request 元数据优先使用值类型或预分配队列槽位。

内存池不替代最大包长、有界发送队列和 Service 任务上限。完整所有权、Reset 和防 ABA 规则见 [内存复用与对象池设计](../details/2026-07-25-内存复用与对象池设计.md)。

### 4.9 最小优雅停止

M0 停止顺序：

1. Application 进入关闭流程；
2. 按停止顺序逐个停止 Node；
3. Node 停止 Service 新任务准入；
4. Service 排空 Stop 前已经接受的 Ready、Waiting 和 pendingCall；
5. Service 使用独占 finalizer 执行 `OnStop(ctx)`；
6. `PlayerService.OnStop` 仍可通过 `AwaitSavePlayer` 调用尚未停止的 `DBService`；
7. `OnStop` 返回后关闭 Service Scheduler；
8. 关闭 RPC Runtime、TCP 和内部 Deadline；
9. 释放剩余 Buffer 和 pendingCall；
10. Node 进入 Stopped。

M0 不处理 Async 回调、业务 Timer、本地事件和 Module 资源的排空，因为这些能力不进入 M0。

关闭 Deadline 到期后的返回值、进程级处理和默认时间属于 M0 开工前确认项。

### 4.10 最小错误和日志

M0 只定义：

```text
CodeInternal
CodeInvalidConfig
CodeTargetUnavailable
CodeDeadlineExceeded
CodeCanceled
CodeTransportFailed
CodeServiceStopping
CodeOverloaded
```

RPC 响应至少携带错误码和必要消息，不传输 cause、堆栈和任意 Details。

M0 使用最小日志能力记录：

- Node 和 Service 生命周期；
- TCP 连接和断开；
- RPC RequestID、目标和错误；
- Await 超时和 Stop 超时；
- 未释放对象和异常状态。

M0 不建设完整日志、Trace 和 Profiler 系统。示例程序可以把操作系统停止信号转换为 Application Context 取消，但信号系统本身不作为独立 M0 模块。

## 5. 明确不进入 M0

- Module 和 Module 树；
- Node 内多个 Service 的排序规则；
- Service 业务配置通用访问；
- Service 就绪门和 `AwaitService`；
- 内置服务发现、etcd、TTL 和发现事件；
- 服务关注筛选和标签；
- Retired 和 Resume；
- 自动实例选择、RoundRobin、Rand、ModKey 和自定义路由；
- 公开的 Async、Notify 和 Broadcast；
- 本地同步和异步事件；
- 业务 `ITimer`、一次性 Timer、Ticker 和 Cron；
- NATS RPC；
- 外部 gRPC 插件；
- 普通 Go 类型、自定义结构体和混合 Protobuf 序列化；
- 压缩、自动重试和进程内 RPC 短路；
- 模板 Service；
- KCP、WebSocket、HTTP、Gin 和通用网络框架；
- MySQL、Redis、MongoDB 和 Kafka 等正式适配器；
- 业务可见通用对象池和 Protobuf 消息池；
- 完整日志、Trace、Profiler 和控制台；
- v2 源码级兼容层。

这些能力继续保留在 [v2 功能迁移矩阵](../../migration/第二版功能盘点与第三版迁移矩阵.md) 和各详细设计中。

## 6. 关键组件边界

| 组件 | M0 职责 |
|---|---|
| Application | 最小配置、Node 选择和顺序启停 |
| Node Runtime | TCP、RPC、Deadline、Service 注册与回收 |
| Service Runtime | 生命周期、FIFO、单执行槽、Await 和 finalizer |
| Contract Generator | 校验严格 RPC 子集并生成客户端与 Dispatcher |
| RPC Manager | 精确目标、RequestID、pendingCall、超时和错误 |
| TCP Transport | 握手、帧读写、有界队列和连接关闭 |
| Deadline Scheduler | RPC 与 Await 的一次性内部 Deadline |
| Memory Reuse | Buffer 和 pendingCall 的专用池及所有权 |

业务代码不能依赖连接、Buffer、pending 表、Deadline 条目和调度器内部结构。

## 7. 实施计划前必须确认

| 优先级 | 设计点 | 必须确认的内容 |
|---|---|---|
| 1 | RPC 线协议 | 帧头、版本、标志、大小端、错误布局和最大包 |
| 2 | ContractID 与 MethodID | 位数、生成输入、稳定性和碰撞处理 |
| 3 | 代码生成 | 标记、命令、输出位置、Dispatcher 注册 |
| 4 | TCP 连接 | 每对 Node 连接数、主动方、握手和重复连接裁决 |
| 5 | Deadline | Go Runtime Timer、最小堆或精简时间轮 |
| 6 | 调度容量 | 已接受任务总上限、过载错误和内部恢复保障 |
| 7 | 优雅停止 | 默认关闭时间、预算范围和超时后的进程级处理 |
| 8 | YAML | 最小字段名、默认值和命令行 Node 选择方式 |
| 9 | 工程基础 | Go module path、最低 Go 版本和 Protobuf 版本 |

上述方案未确认前，不在实现阶段自行补成隐式规则。

## 8. 风险优先验证

完整实现前先验证三个高风险点：

1. Await Runner 交接能否保持 Service 单执行槽，并且无 Await 快速路径不创建额外 goroutine。
2. Go 接口生成、Protobuf、帧协议和 TCP pending 能否形成稳定最短链路。
3. Buffer 和 pendingCall 池能否减少分配，并在成功、超时、取消、断线和 Stop 路径保持唯一释放。

基准至少记录：

- `allocs/op` 和 `B/op`；
- p50、p95、p99；
- Await 挂起、恢复和 Runner 交接成本；
- 并发请求下 goroutine 数量；
- Ready、Waiting、pending 和发送队列水位；
- 池化与直接分配的差异；
- 突发流量结束后的内存滞留。

不在 M0 文档中凭经验写死性能门槛。性能与代码简洁性冲突时，按照开发指导原则提供 Benchmark 数据后确认。

## 9. 验收标准

M0 必须同时满足：

1. 示例能够以单进程双 Node 和双进程单 Node 运行。
2. 两种方式使用相同 TCP、帧协议、Protobuf 和错误语义。
3. `AwaitSavePlayer` 完成真实请求—响应。
4. Await 等待期间，同一 Service 能执行另一条已准入任务。
5. 任意时刻只有一个任务访问 Service 状态。
6. 无 Await 的连续任务复用 Runner，不为每个任务创建 goroutine。
7. 默认 15 秒超时和显式 Context Deadline 生效。
8. 断线、超时和取消只完成 pendingCall 一次。
9. Player Node 的 `OnStop` 能在 DB Node 停止前完成最终存档。
10. Stop 排空后不再存在业务 Runner、RPC 恢复和 pendingCall。
11. Buffer 在成功、解码失败、写失败和连接关闭路径恰好释放一次。
12. 迟到响应不能操作已经复用的 pendingCall。
13. 最大包长、发送队列和任务上限能够拒绝过载。
14. 启停失败执行最小逆序清理。
15. 竞态检测和泄漏检查通过。
16. 保存可复现的性能与分配基线。

## 10. 测试层级

M0 至少包含：

- 配置、Node 顺序和 Service 状态机单元测试；
- Service FIFO、单执行槽、Await 和 finalizer 测试；
- RPC 生成器合法与非法契约测试；
- 帧编解码、RequestID、pendingCall 和错误码测试；
- Buffer 档位、所有权、Reset、重复释放和迟到响应测试；
- 真实 TCP 双 Node 集成测试；
- 单进程和双进程端到端测试；
- 超时、取消、短写、断线、队满和 Stop 故障测试；
- 重复启停和失败清理测试；
- `go test -race`、逃逸分析和基础 Benchmark。

测试必须覆盖正常路径和资源释放路径。
