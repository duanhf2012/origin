# Origin 第三版内存复用与对象池设计

> 文档类型：详细设计储备

## 1. 文档状态与范围

- 状态：本文范围内的方案已确认
- 确认日期：2026-07-25
- 适用版本：Origin v3

本文定义 Origin v3 内部字节缓冲区和高频短生命周期对象的复用原则，重点覆盖：

- TCP 收发缓冲区；
- Protobuf 编码缓冲区；
- TimerEngine 内部 `timerEntry`；
- RPC 内部 `pendingCall`；
- 所有权转移、释放时机和防 ABA 规则；
- 逃逸分析、分配统计和 Benchmark 要求。

本文不设计业务可见的通用对象池，也不规定 TimerEngine、RPC 线协议、Service 调度器的完整实现。各系统只在自己的设计中说明对象何时进入和退出池。

## 2. 设计目标

1. 在不明显增加代码复杂度的前提下，减少高频路径的堆分配和 GC 压力。
2. 通过明确的单一所有权和集中释放点，避免重复释放、释放后使用和对象串用。
3. 内存复用只作为性能优化，不承担队列容量、内存上限和可靠缓存职责。
4. 池化对象不暴露给业务层，避免使用者承担生命周期管理。
5. 不建立万能对象池；每种对象按自身生命周期使用专用池。
6. 性能收益必须通过逃逸分析、分配统计和 Benchmark 验证。

## 3. 总体原则

Origin v3 使用以下两类复用方式：

### 3.1 字节缓冲区池

用于 TCP 接收、发送和 Protobuf 编码等高频临时字节数据。缓冲区可能跨 goroutine 转移所有权，因此使用内部 `Buffer` 对象表示所有权。

### 3.2 专用类型对象池

用于框架内部、生命周期封闭且释放点唯一的固定类型，例如：

- `timerEntry`；
- `pendingCall`。

每种类型拥有自己的取得、重置和释放函数。不向业务层提供 `ObjectPool[T]` 等通用 API。

Go `sync.Pool` 中的对象可能被运行时随时清理，因此：

- 不能依赖池保存对象；
- 不能把池当成固定容量缓存；
- 不能通过池替代队列上限和背压；
- 池未命中时必须能够正常创建新对象。

## 4. 池的归属

字节缓冲区池由 Application 创建，并由其中的 Node 共享：

```text
Application
└── BufferPool
    ├── Node A RPC Runtime
    └── Node B RPC Runtime
```

不使用包级全局字节池。这样可以：

- 隔离不同 Application 和测试；
- 明确配置与生命周期归属；
- 避免隐藏的全局状态；
- 保持单进程多 Node 与单进程单 Node 使用相同实现。

`timerEntry` 池属于 Node TimerEngine，`pendingCall` 池属于 Node RPC Runtime。它们不在不同 Application 之间共享。

Application 只有在全部 Node、连接和待发送队列停止并释放 Buffer 后，才能丢弃字节池。`sync.Pool` 创建并开始使用后不得复制，整个生命周期只通过指针传递。

## 5. 网络 Buffer 设计

### 5.1 内部外观

概念外观如下，最终命名可以在实现计划中细化：

```go
type Pool struct {
    buckets []bucket
}

type Buffer struct {
    data   []byte
    owner  *Pool
    bucket uint8
    pooled bool
}

func (p *Pool) Acquire(size int) *Buffer
func (b *Buffer) Bytes() []byte
func (p *Pool) Release(buf *Buffer)
```

网络热路径直接持有具体 `*Pool`，不为了可替换性增加接口调用和装箱。该类型位于框架内部包，Service 和业务 Module 不可访问。

使用 `*Buffer` 而不是直接池化来源不明的 `[]byte`，用于：

- 记录缓冲区所属 Pool；
- 记录准确容量档位；
- 表达队列之间的所有权转移；
- 防止外部切片或非标准容量切片污染池；
- 让发送失败和连接关闭时具有统一释放对象。

### 5.2 容量档位

M0 默认档位为：

```text
32 B
64 B
128 B
256 B
512 B
1 KiB
2 KiB
4 KiB
8 KiB
16 KiB
32 KiB
64 KiB
```

规则：

1. `Acquire(0)` 返回空 Buffer，不进入档位池。
2. 请求容量向上取整到最接近的 2 的幂档位。
3. 档位可以通过位运算定位，不在线性列表中逐项查找。
4. 大于 `64 KiB` 的缓冲区按实际大小直接分配。
5. 超过最大档位的缓冲区释放时直接丢弃引用，由 GC 回收。
6. M0 不建立 `8 B` 和 `16 B` 档位；小于等于 `32 B` 统一使用 `32 B`。
7. 是否增加 `128 KiB` 以上档位，必须根据真实包长分布和内存滞留 Benchmark 决定。

增加容量档位不代表预分配对应内存。每个档位使用按需创建的 `sync.Pool`。

### 5.3 小包栈上快速路径

接收路径可以验证固定 `[32]byte` 临时数组的小包快速路径：

```go
var small [32]byte
body := small[:size]
```

只有逃逸分析证明该数组保持在栈上，并且 Benchmark 证明收益稳定时才采用。否则小包统一使用 `32 B` 池，不为微小收益增加分支和维护成本。

## 6. Buffer 所有权

一个 Buffer 任意时刻只能有一个所有者。可以转移所有权，不能共享所有权。

M0 不使用引用计数，不支持一个 Buffer 同时被多个 Service、连接或异步任务持有。

### 6.1 接收路径

```text
TCP ReadLoop
  → 读取并校验固定帧头
  → Acquire 消息体 Buffer
  → 读取完整消息体
  → 解码 Protobuf
  → Release Buffer
  → 将独立消息投递给 Service
```

具体规则：

1. 固定长度帧头优先使用栈上数组，不进入池。
2. 包长校验必须发生在申请消息体之前。
3. `io.ReadFull`、解码失败和连接断开等错误路径必须释放 Buffer。
4. M0 的 Protobuf 解码结果不得引用输入 Buffer。
5. 解码完成后立即释放 Buffer，Service 不参与网络内存释放。
6. M0 禁止零拷贝解码和跨 Service 共享 Buffer。

### 6.2 发送路径

```text
RPC 编码器
  → 计算帧头和 Protobuf 总长度
  → Acquire 完整帧 Buffer
  → 直接编码
  → 转移给有界发送队列
  → Writer 完整写入、失败或关闭
  → Release Buffer
```

具体规则：

1. 使用 Protobuf 大小计算和追加编码能力，尽量直接写入最终发送 Buffer。
2. 避免先生成 body，再复制到完整网络帧。
3. 成功加入发送队列后，编码器失去所有权。
4. 只有 Writer 可以释放发送队列中的 Buffer。
5. 完整写入、写失败和连接关闭使用同一释放路径。
6. 连接关闭时必须释放尚未发送的全部队列项。
7. RPC 取消不能释放已经转移给发送队列的 Buffer。
8. pending 请求不长期保存发送 Buffer；M0 不支持自动重试。

长循环中不使用延迟到循环退出的 `defer Release`，而是在每条完成和错误路径显式释放。

### 6.3 清零规则

Buffer 默认不清零，以避免大块内存重复写入。

框架必须保证：

- 只发送实际有效长度；
- 读取和编码前覆盖全部有效区域；
- 释放后不再读取；
- 不向业务暴露可能包含旧数据的 Buffer。

特别敏感的数据由所属内部组件在释放前显式清零。M0 不增加全局安全清零模式。

## 7. TimerEntry 专用池

TimerEngine 从首版实现开始使用内部 `timerEntry` 专用池，不池化或手工复用 Go 标准库的 `time.Timer`。

池化对象可以包含：

```go
type timerEntry struct {
    id         TimerID
    deadline   int64
    interval   int64
    callback   func()
    owner      timerOwner
    state      timerState
    bucket     uint32
    generation uint64
}
```

该结构只说明需要清理的引用和状态，不提前锁死时间轮节点的最终布局。

### 7.1 释放条件

只有确认 Timer 已经脱离以下全部位置时，才能释放：

- 时间轮或其他到期结构；
- TimerID 索引；
- 暂停列表；
- 待投递列表；
- 已排队但未完成的回调；
- 正在运行或 Waiting 的回调。

一次性 Timer 在完整结束后释放；周期 Timer 和 Cron 只有在取消并完成全部清理后释放；暂停状态仍属于活跃 Timer，不能释放。

### 7.2 防 ABA

TimerID 不能使用对象地址、池索引或会随对象复用的标识。

每次从池中取得 `timerEntry` 时分配新的单调递增 TimerID。旧 ID 的取消、暂停或恢复操作只能查询旧 ID；即使底层对象已经复用，也不能操作新 Timer。

### 7.3 Reset

释放前必须清理：

- callback 闭包；
- Service、Module 和内部所有者引用；
- Context；
- 参数和错误；
- 时间轮链表或桶索引；
- TimerID、generation 和运行状态。

Timer 对象池只减少创建与销毁成本，不能减少当前活跃 Timer 本身需要的内存。

## 8. RPC PendingCall 专用池

v3 不复制 v2 中 Future、Call 和 Request 多套重叠对象。请求—响应调用使用一个内部 `pendingCall` 表达等待状态：

```go
type pendingCall struct {
    requestID RequestID
    target    rpcTarget
    deadline  int64
    timerID   TimerID

    state    atomic.Uint32
    done     chan rpcResult
    response proto.Message
    err      error
}
```

该结构为语义示例，最终字段布局由 RPC 线协议和调度实现确定。普通业务用户不能取得 `pendingCall`。

### 8.1 生命周期

```text
从池取得
  → 初始化全新 RequestID
  → 登记到 pending 表
  → 发送请求
  → 响应、超时、取消竞争一次性完成
  → 从 pending 表删除
  → Await 或 Async 消费结果
  → 清理全部引用
  → 放回池
```

响应到达不等于可以立即释放。只有消费者已经复制结果和错误后才能释放：

- Await 在等待 goroutine 取得结果后释放，再等待重新获得 Service 执行权；
- Async 在完成回调已经取得所需结果后释放；
- 立即发送失败、取消和超时也进入同一个完成与释放路径。

### 8.2 防止迟到事件操作复用对象

响应、Timeout 和取消事件不能依靠长期保存的 `*pendingCall` 指针完成请求，而应使用连接标识和 RequestID 查询 pending 表。

请求完成并从 pending 表删除后，迟到响应或旧 Timeout 找不到原记录并直接丢弃。这样即使对象已经被新请求复用，旧事件也不能修改新状态。

完成状态采用一次性终态转换，响应、超时、取消和断线中只能有一个成为完成者。

### 8.3 Reset

释放前必须清理：

- RequestID、目标和 Deadline；
- TimerID；
- response、error 和 Context；
- 回调、Service 和调度器引用；
- channel 中可能残留的结果；
- 原子状态。

如果最终设计使用可复用 channel，必须证明不存在迟到发送和残留结果；否则 channel 单独创建，不为了少一次分配引入竞态。

## 9. Request 与其他对象

### 9.1 Protobuf 业务消息

M0 不池化 Protobuf Request 和 Response。

Protobuf 消息可能包含 slice、map、bytes、嵌套消息和 unknown fields。业务代码也可能在调用结束后保存消息指针。自动池化容易产生数据串用、重置遗漏和长期引用。

### 9.2 网络请求元数据

网络发送项、解析后的帧头和小型请求元数据优先使用：

- 栈上值；
- 有界环形队列中的预分配槽位；
- Service Ready 队列中的值类型。

能够由队列槽位自然复用时，不再增加对象池。

### 9.3 后续候选

RPC 服务端任务、Service 调度节点等对象只有在逃逸分析和 Benchmark 显示为显著热点后，才能新增各自的专用池。

Context、error、任意闭包和业务结构体不由 Origin 自动池化。

## 10. 内存池不替代背压

内存池只减少重复分配，不能限制同时在用的对象数量。

M0 仍必须具有：

- 最大网络包长度；
- 有界连接发送队列；
- 每连接待发送字节上限；
- Service Ready 和 Waiting 上限；
- 队满或过载时的明确错误。

大量消息同时积压时，应通过准入和背压控制内存，而不是扩大池容量。

## 11. 性能验证

字节池至少覆盖以下消息大小：

```text
64 B
256 B
1 KiB
4 KiB
32 KiB
128 KiB
```

对象池至少比较：

- 直接创建和专用池化的 `allocs/op`、`B/op`；
- RPC 成功、超时、取消和断线路径；
- Timer 创建、触发、取消和周期重排；
- 并发 Get/Put 的锁竞争；
- 突发流量结束后的内存滞留；
- p50、p95、p99 延迟；
- GC 次数和暂停。

使用逃逸分析和 Benchmark 验证：

```bash
go test -gcflags="all=-m=2" ./...
go test -bench=. -benchmem ./...
```

网络 Buffer 和 pendingCall 需要跨 goroutine 或 pending 表，可能不可避免地逃逸到堆。池化目标是摊薄这些不可避免的分配，而不是要求所有对象都停留在栈上。

## 12. 测试要求

至少覆盖：

1. 每个容量档位取得和释放正确；
2. 非标准或超大 Buffer 不会污染档位池；
3. 接收、解码失败、写失败和连接关闭都恰好释放一次；
4. Buffer 转移给发送队列后调用方不再访问；
5. 连接关闭会释放全部未发送 Buffer；
6. Timer 触发、取消、暂停、恢复和停止清理后才能回池；
7. 旧 TimerID 不能操作已复用对象；
8. Timer Reset 不保留 callback、Service 或 Context；
9. RPC 响应、超时、取消和断线只完成一次；
10. pendingCall 只有在结果被消费后才回池；
11. 迟到响应和旧 Timeout 不能操作已复用 pendingCall；
12. pendingCall Reset 不残留 response、error、channel 数据和所有者引用；
13. 高并发 Acquire、Release、完成和取消通过竞态检测；
14. 池化与直接分配的对比 Benchmark 能证明收益，没有明显延迟回退。

## 13. 已确认结论

- M0 实现框架内部网络 Buffer 池；
- 字节池由 Application 持有并由其中 Node 共享；
- 网络队列使用 `*Buffer` 表达单一所有权；
- 默认容量档位从 `32 B` 到 `64 KiB`，不建立 `8 B`、`16 B` 和 `128 KiB` 默认档位；
- 默认不清零，不支持零拷贝和引用计数；
- TimerEngine 从首版起池化自己的 `timerEntry`，不池化 `time.Timer`；
- Future 和 Call 合并为内部 `pendingCall` 并使用专用池；
- Protobuf 业务消息不池化；
- Request 元数据优先采用值类型或预分配队列；
- 不向业务提供通用对象池；
- 所有池化对象必须具有唯一释放点、完整 Reset 和防 ABA 规则；
- 池化不替代最大包长、有界队列和背压；
- 后续新增对象池必须由逃逸分析和 Benchmark 证明收益。
