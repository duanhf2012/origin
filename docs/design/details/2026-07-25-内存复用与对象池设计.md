# Origin 第三版内存复用与对象池设计

> 文档类型：详细设计储备

## 1. 文档状态与范围

- 状态：本文范围内的方案已确认
- 确认日期：2026-07-25
- 适用版本：Origin v3

本文定义 Origin v3 内部字节缓冲区和高频短生命周期对象的复用原则，重点覆盖：

- TCP 收发缓冲区；
- Protobuf 编码缓冲区；
- TimerEngine 内部 `timerEntry`；
- RPC 内部 `pendingCall`；
- 所有权转移、释放时机和防 ABA 规则；
- 逃逸分析、分配统计和 Benchmark 要求。

本文不设计业务可见的通用对象池，也不规定 TimerEngine、RPC 线协议、Service 调度器的完整实现。各系统只在自己的设计中说明对象何时进入和退出池。

M2 已实现独立的 `internal/bufferpool`；Application 归属在 M7 接入，TCP 所有权在 M5
接入，`timerEntry` 在 M8 TimerEngine 接入，`pendingCall` 在 M12/M13 接入。

## 2. 设计目标

1. 在不明显增加代码复杂度的前提下，减少高频路径的堆分配和 GC 压力。
2. 通过明确的单一所有权和集中释放点，避免重复释放、释放后使用和对象串用。
3. 内存复用只作为性能优化，不承担队列容量、内存上限和可靠缓存职责。
4. 池化对象不暴露给业务层，避免使用者承担生命周期管理。
5. 不建立万能对象池；每种对象按自身生命周期使用专用池。
6. 性能收益必须通过逃逸分析、分配统计和 Benchmark 验证。

## 3. 总体原则

Origin v3 使用以下两类复用方式：

### 3.1 字节缓冲区池

用于 TCP 接收、发送和 Protobuf 编码等高频临时字节数据。缓冲区可能跨 goroutine 转移所有权，因此使用内部 `Buffer` 对象表示所有权。

### 3.2 专用类型对象池

用于框架内部、生命周期封闭且释放点唯一的固定类型，例如：

- `timerEntry`；
- `pendingCall`。

每种类型拥有自己的取得、重置和释放函数。不向业务层提供 `ObjectPool[T]` 等通用 API。

Go `sync.Pool` 中的对象可能被运行时随时清理，因此：

- 不能依赖池保存对象；
- 不能把池当成固定容量缓存；
- 不能通过池替代队列上限和背压；
- 池未命中时必须能够正常创建新对象。

## 4. 池的归属

字节缓冲区池由 Application 创建，并由其中的 Node 共享：

```text
Application
└── BufferPool
    ├── Node A RPC Runtime
    ├── Node A TcpModule Adapter
    ├── Node B RPC Runtime
    └── Node B TcpModule Adapter
```

不使用包级全局字节池。这样可以：

- 隔离不同 Application 和测试；
- 明确配置与生命周期归属；
- 避免隐藏的全局状态；
- 保持单进程多 Node 与单进程单 Node 使用相同实现。

`timerEntry` 池属于 Node TimerEngine，`pendingCall` 池属于 Node RPC Runtime。它们不在不同 Application 之间共享。

Application 只有在全部 Node、连接和待发送队列停止并释放 Buffer 后，才能丢弃字节池。`sync.Pool` 创建并开始使用后不得复制，整个生命周期只通过指针传递。

## 5. 网络 Buffer 设计

### 5.1 内部外观

核心外观如下，省略了统计字段和固定档位数组长度：

```go
type Pool struct {
    buckets []bucket
}

type Options struct {
    TrackUsage bool
}

type Buffer struct {
    data   []byte
    owner  *Pool
    size   int
    bucket uint8
    active bool
}

func NewPool(options Options) *Pool
func (p *Pool) Acquire(size int) *Buffer
func (b *Buffer) Bytes() []byte
func (b *Buffer) Release()
func (p *Pool) Stats() Stats
```

`Options.TrackUsage` 的零值为 false，统计默认关闭。网络热路径直接持有具体 `*Pool`，不为了可替换性增加接口调用和装箱。该类型位于框架内部包，Service 和业务 Module 不可访问。

使用 `*Buffer` 而不是直接池化来源不明的 `[]byte`，用于：

- 记录缓冲区所属 Pool；
- 记录准确容量档位；
- 表达队列之间的所有权转移；
- 防止外部切片或非标准容量切片污染池；
- 让发送失败和连接关闭时具有统一释放对象。

### 5.2 容量档位

M2 默认档位为：

```text
16 B
32 B
64 B
128 B
256 B
512 B
1 KiB
2 KiB
4 KiB
8 KiB
16 KiB
32 KiB
64 KiB
```

规则：

1. `Acquire(0)` 返回空 Buffer，不进入档位池。
2. `1`～`16 B` 进入 `16 B` 档位，其余请求向上取整到最接近的 2 的幂档位。
3. 档位可以通过位运算定位，不在线性列表中逐项查找。
4. 大于 `64 KiB` 的缓冲区按实际大小直接分配。
5. 超过最大档位的缓冲区释放时直接丢弃引用，由 GC 回收。
6. M2 不建立 `8 B` 档位；小于等于 `16 B` 统一使用 `16 B`。
7. 是否增加 `128 KiB` 以上档位，必须根据真实包长分布和内存滞留 Benchmark 决定。

增加容量档位不代表预分配对应内存。每个档位使用按需创建的 `sync.Pool`。

### 5.3 小包栈上快速路径

接收路径可以验证固定 `[32]byte` 临时数组的小包快速路径：

```go
var small [32]byte
body := small[:size]
```

只有逃逸分析证明该数组保持在栈上，并且 Benchmark 证明收益稳定时才采用。否则小包按 `16 B` 或 `32 B` 档位使用池，不为微小收益增加分支和维护成本。

### 5.4 未归还统计

M2 提供 `Options.TrackUsage` 启动开关和只读 `Stats()`：

- 默认 false，不执行统计原子加减；
- true 时统计当前已经取得但尚未释放的 Buffer 数量、容量、各档位和超大 Buffer；
- 框架不判断开发或生产环境，由使用者在 Application 启动配置中决定；
- 开关只在 Pool 创建时生效，不支持运行中动态切换；
- 静止点非零表示仍有 Buffer 未归还，但不能证明其他 Go 对象不存在内存泄漏；
- 不统计 `sync.Pool` 内缓存对象，不记录 Buffer 指针、调用栈、命中率、累计次数和峰值；
- 开启与关闭统计必须分别保存串行和并发 Benchmark。

M2 只实现 Go 构造参数。Application 对外配置和最终停止告警分别在 M7、M14 接入。

## 6. Buffer 所有权

一个 Buffer 任意时刻只能有一个所有者。可以转移所有权，不能共享所有权。

M2 不使用引用计数，不支持一个 Buffer 同时被多个组件、连接或异步任务持有。

### 6.1 接收路径

```text
TCP ReadLoop
  → 读取并校验长度帧头
  → Acquire 消息体 Buffer
  → 长度大于零时直接读取完整消息体到最终 Buffer
  → 将 Buffer 唯一所有权转移给内部 Handler
      ├── RPC Adapter：解码 Protobuf 后 Release
      └── TcpModule Adapter：转移给 Service 事件，事件处理完成后 Release
```

具体规则：

1. 最长四字节的长度帧头优先使用栈上数组，不进入池。
2. 包长校验必须发生在申请消息体之前。
3. 零长度 payload 使用有效的零长度 Buffer，不申请底层字节数组，也不调用 `io.ReadFull`；
   它与 nil Buffer 是两种不同状态。
4. `io.ReadFull` 失败和转移前连接断开由 ReadLoop 释放 Buffer。
5. 所有权进入 Handler 后，Handler 必须在解码失败、事件投递失败和 panic 路径释放，或者
   继续转移给唯一的内部事件所有者。
6. M11/M12 的 Protobuf 解码结果不得引用输入 Buffer，解码完成后立即释放。
7. TcpModule 可以把 Buffer 转移给 Service 异步事件以避免复制；事件处理完成、丢弃、
   队列拒绝或 Service 停止时都必须释放。
8. 业务代码不直接管理 Buffer。异步事件中的唯一所有权转移不是共享所有权或引用计数。
9. 首个 RPC 闭环仍禁止零拷贝解码和跨 Service 共享 Buffer。

### 6.2 发送路径

```text
RPC 编码器 / TcpModule Codec
  → 计算 payload 长度
  → Acquire payload Buffer
  → 直接编码到 Buffer
  → 转移给有界发送队列
  → Writer 使用队列项中的长度头和 payload 完整写入、失败或关闭
  → Release Buffer
```

具体规则：

1. RPC 使用 Protobuf 大小计算和追加编码能力，尽量直接写入最终 payload Buffer；
   TcpModule Codec 遵循相同原则。
2. 长度头最多四字节，保存在预分配发送队列项中，不为了拼接帧头复制完整 payload。
3. 成功加入发送队列后，编码器失去所有权。
4. 只有 Writer 可以释放发送队列中的 Buffer。
5. 完整写入、写失败和连接关闭使用同一释放路径。
6. 连接关闭时必须释放尚未发送的全部队列项。
7. RPC 取消或 TcpModule 上层事件取消不能释放已经转移给发送队列的 Buffer。
8. 有效的零长度 Buffer 可以进入发送队列并转移所有权，仍占用一个帧槽位。
9. pending 请求不长期保存发送 Buffer；M12 的连接管理器可以重连，但不能自动重发已经
   失败的非幂等 RPC。

接收端从 socket 直接读入池化 Buffer，发送端从最终编码 Buffer 通过独立长度头和
scatter/gather 写出。正常热路径不创建中间消息体切片，不把帧头与完整 payload 拼成新的
大切片，也不做无意义的 `[]byte`/`string` 转换。最终是否采用 `net.Buffers` 必须由 Windows
和 Linux Benchmark 与完整帧复制方案对照决定。

长循环中不使用延迟到循环退出的 `defer Release`，而是在每条完成和错误路径显式释放。

### 6.3 清零规则

Buffer 默认不清零，以避免大块内存重复写入。

框架必须保证：

- 只发送实际有效长度；
- 读取和编码前覆盖全部有效区域；
- 释放后不再读取；
- 不向业务暴露可能包含旧数据的 Buffer。

特别敏感的数据由所属内部组件在释放前显式清零。M2 不增加全局安全清零模式。

## 7. Timer 专用池

M8 TimerEngine 从首版实现开始使用内部 `timerEntry` 专用池，不池化或手工复用 Go 标准库的
`time.Timer`。M8 内核条目只保存 Deadline 数据，不保存业务回调：

```go
type timerEntry struct {
    id           DeadlineID
    deadlineTick uint64
    queue        *DeadlineQueue

    wheelPrev *timerEntry
    wheelNext *timerEntry
    queuePrev *timerEntry
    queueNext *timerEntry

    level uint8
    slot  uint8
    state entryState
}
```

这是 M8 实施后的实际职责布局：时间轮桶链表和 Queue 待调度链表分别使用独立前后指针，
从已知 ID 取消以及 Queue 批量关闭都不需要扫描其他条目。实现已经通过逃逸分析和百万
活跃条目 Benchmark；数据见
[M8 Node 时间轮内核设计](../milestones/M8-节点时间轮内核设计.md#21-实施与验收结果)。

M10 业务 Timer 层另行保存公开 TimerID、callback、周期、暂停状态、Service/Module 资源
作用域和当前 DeadlineID。业务 Timer 容器同样由框架私有池复用，但不能与 M8
`timerEntry` 混用。

### 7.1 释放条件

M8 `timerEntry` 只有确认已经脱离以下位置时才能释放：

- 时间轮桶；
- DeadlineID 索引；
- Engine 的结构修改临界区。

到期时先把 DeadlineID 值复制到 `DeadlineQueue` 的到期列表，再立即释放 `timerEntry`；
到期列表不保存对象指针。

M10 业务 Timer 容器只有在已经取消或自然完成，并且脱离公开 TimerID 索引、暂停列表、
Service Ready、正在运行或 Waiting 回调后才能释放。周期 Timer 和 Cron 的下一次
DeadlineID 取消或完成后，才能清理业务容器。

### 7.2 防 ABA

DeadlineID 和公开 TimerID 都不能使用对象地址、池索引或会随对象复用的标识。

每次从池中取得 M8 `timerEntry` 时分配新的单调递增 DeadlineID。旧 DeadlineID 即使在
底层对象已经复用后，也不能取消新的 Deadline。

M10 每次创建业务 Timer 时分配新的公开 TimerID。暂停、恢复和周期触发可以更换内部
DeadlineID，但不改变当前业务 TimerID。

### 7.3 Reset

M8 `timerEntry` 释放前必须清理：

- `DeadlineQueue` 引用；
- 前驱和后继；
- Deadline；
- 层级和桶索引；
- DeadlineID 和运行状态。

M10 业务 Timer 容器释放前另行清理 callback、Service、Module、Context、参数、错误、
TimerID 和 DeadlineID。

Timer 对象池只减少创建与销毁成本，不能减少当前活跃 Timer 本身需要的内存。

## 8. RPC PendingCall 专用池

v3 不复制 v2 中 Future、Call 和 Request 多套重叠对象。请求—响应调用使用一个内部 `pendingCall` 表达等待状态：

```go
type pendingCall struct {
    requestID RequestID
    target    rpcTarget
    deadline  int64
    deadlineID DeadlineID

    state    atomic.Uint32
    done     chan rpcResult
    response proto.Message
    err      error
}
```

该结构为语义示例，最终字段布局由 RPC 线协议和调度实现确定。普通业务用户不能取得 `pendingCall`。

### 8.1 生命周期

```text
从池取得
  → 初始化全新 RequestID
  → 登记到 pending 表
  → 发送请求
  → 响应、超时、取消竞争一次性完成
  → 从 pending 表删除
  → Await 或 Async 消费结果
  → 清理全部引用
  → 放回池
```

响应到达不等于可以立即释放。只有消费者已经复制结果和错误后才能释放：

- Await 在等待 goroutine 取得结果后释放，再等待重新获得 Service 执行权；
- Async 在完成回调已经取得所需结果后释放；
- 立即发送失败、取消和超时也进入同一个完成与释放路径。

### 8.2 防止迟到事件操作复用对象

响应、Timeout 和取消事件不能依靠长期保存的 `*pendingCall` 指针完成请求，而应使用连接标识和 RequestID 查询 pending 表。

请求完成并从 pending 表删除后，迟到响应或旧 Timeout 找不到原记录并直接丢弃。这样即使对象已经被新请求复用，旧事件也不能修改新状态。

完成状态采用一次性终态转换，响应、超时、取消和断线中只能有一个成为完成者。

### 8.3 Reset

释放前必须清理：

- RequestID、目标和 Deadline；
- TimerID；
- response、error 和 Context；
- 回调、Service 和调度器引用；
- channel 中可能残留的结果；
- 原子状态。

如果最终设计使用可复用 channel，必须证明不存在迟到发送和残留结果；否则 channel 单独创建，不为了少一次分配引入竞态。

## 9. Request 与其他对象

### 9.1 Protobuf 业务消息

M11/M12 不池化 Protobuf Request 和 Response。

Protobuf 消息可能包含 slice、map、bytes、嵌套消息和 unknown fields。业务代码也可能在调用结束后保存消息指针。自动池化容易产生数据串用、重置遗漏和长期引用。

### 9.2 网络请求元数据

网络发送项、解析后的帧头和小型请求元数据优先使用：

- 栈上值；
- 有界环形队列中的预分配槽位；
- Service Ready 队列中的值类型。

能够由队列槽位自然复用时，不再增加对象池。

### 9.3 后续候选

RPC 服务端任务、Service 调度节点等对象只有在逃逸分析和 Benchmark 显示为显著热点后，才能新增各自的专用池。

Context、error、任意闭包和业务结构体不由 Origin 自动池化。

## 10. 内存池不替代背压

内存池只减少重复分配，不能限制同时在用的对象数量。

对应里程碑仍必须具有：

- 最大网络包长度；
- 有界连接发送队列；
- 每连接待发送字节上限；
- Service Ready 和 Waiting 上限；
- 队满或过载时的明确错误。

大量消息同时积压时，应通过准入和背压控制内存，而不是扩大池容量。

## 11. 性能验证

字节池至少覆盖以下消息大小：

```text
16 B
32 B
64 B
256 B
1 KiB
4 KiB
32 KiB
128 KiB
```

对象池至少比较：

- 直接创建和专用池化的 `allocs/op`、`B/op`；
- RPC 成功、超时、取消和断线路径；
- Timer 创建、触发、取消和周期重排；
- 并发 Get/Put 的锁竞争；
- 突发流量结束后的内存滞留；
- p50、p95、p99 延迟；
- GC 次数和暂停。

使用逃逸分析和 Benchmark 验证：

```bash
go test -gcflags="all=-m=2" ./...
go test -bench=. -benchmem ./...
```

网络 Buffer 和 pendingCall 需要跨 goroutine 或 pending 表，可能不可避免地逃逸到堆。池化目标是摊薄这些不可避免的分配，而不是要求所有对象都停留在栈上。

## 12. 测试要求

至少覆盖：

1. 每个容量档位取得和释放正确；
2. 非标准或超大 Buffer 不会污染档位池；
3. 接收、解码失败、写失败和连接关闭都恰好释放一次；
4. Buffer 转移给发送队列后调用方不再访问；
5. 连接关闭会释放全部未发送 Buffer；
6. M8 timerEntry 到期复制 DeadlineID 后或取消完成后才能回池；
7. 旧 DeadlineID 和公开 TimerID 都不能操作已复用对象；
8. M8 timerEntry Reset 不保留 `DeadlineQueue` 或链表引用，M10 业务 Timer Reset 不保留
   callback、Service 或 Context；
9. RPC 响应、超时、取消和断线只完成一次；
10. pendingCall 只有在结果被消费后才回池；
11. 迟到响应和旧 Timeout 不能操作已复用 pendingCall；
12. pendingCall Reset 不残留 response、error、channel 数据和所有者引用；
13. 高并发 Acquire、Release、完成和取消通过竞态检测；
14. 池化与直接分配的对比 Benchmark 能证明收益，没有明显延迟回退。

## 13. 已确认结论

- M2 实现独立的框架内部 Buffer 池；
- M7 接入 Application 后，字节池由 Application 持有并由其中 Node 共享；
- 网络队列使用 `*Buffer` 表达单一所有权；
- 默认容量档位从 `16 B` 到 `64 KiB`，不建立 `8 B` 和 `128 KiB` 默认档位；
- `Options.TrackUsage` 由使用者在启动时决定且默认关闭，不根据开发或生产环境自动判断；
- 开启统计时只报告当前未归还 Buffer，关闭统计时不执行统计原子加减；
- 默认不清零，不支持零拷贝和引用计数；
- M8 TimerEngine 从首版起池化只包含 Deadline 数据的 `timerEntry`，不池化 `time.Timer`；
- M10 业务 Timer 回调容器使用独立专用池，不与 `timerEntry` 混用；
- Future 和 Call 合并为内部 `pendingCall` 并使用专用池；
- Protobuf 业务消息不池化；
- Request 元数据优先采用值类型或预分配队列；
- 不向业务提供通用对象池；
- 所有池化对象必须具有唯一释放点、完整 Reset 和防 ABA 规则；
- 池化不替代最大包长、有界队列和背压；
- 后续新增对象池必须由逃逸分析和 Benchmark 证明收益。
