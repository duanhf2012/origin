# Origin 第三版完整配置模型设计

> 文档类型：详细设计草案
> 状态：待逐项确认
> 创建日期：2026-07-26
> 最后更新：2026-08-01
> 适用版本：Origin v3

## 1. 文档目的

本文集中整理 Origin v3 当前已经讨论到的完整配置外观，解决以下问题：

- 明确基础配置库与 Application、Node、Service 等配置模型的边界；
- 对照 v2，防止重构时遗漏已有配置能力；
- 给出可拆分到多个 JSON/YAML 文件的整体示例；
- 汇总 TCP、NATS、服务发现和关注筛选需要的配置；
- 标出尚未确认的字段和语义，避免示例被误认为最终实现。

本文不代替各独立系统的详细设计。日志、服务发现、RPC、生命周期和 Service 业务配置的具体行为仍以各自设计文件为准。

## 2. 精简原则

完整配置模型遵守以下原则：

1. 首版只提供当前框架启动所需的配置，不提前增加通用配置中心能力；
2. 只支持标准 JSON、YAML，不支持 TOML、JSONC 或 JSON5；
3. 配置入口只接受目录，目录内可以按功能、Node 和 Service 拆分文件；
4. 基础配置库只提供 `LoadDir(dir, dst)`，不公开 Loader、Snapshot、AST、原始 Map 或路径查询对象；
5. 不提供 Options，不限制文件数量和文件大小；
6. 支持安全的环境变量值展开，但不支持环境配置覆盖层、`include`、Patch、热更新和远端配置中心；
7. 配置名称、默认值和合并行为必须明确，禁止通过文件顺序静默覆盖；
8. 不把 RPC 方法或契约重复写入配置，RPC 元数据由 `origingen` 生成和注册。

基础配置库的具体边界见 [M3 基础配置库里程碑设计](../milestones/M3-基础配置库里程碑设计.md)。

## 3. 基础加载外观

公开入口建议固定为：

```go
func LoadDir(dir string, dst any) error
```

使用示例：

```go
var cfg Config

if err := config.LoadDir("./config", &cfg); err != nil {
    return err
}
```

多个文件的发现、排序、解析和合并都在一次调用内完成。内部可以临时建立带来源信息的配置树，但调用结束后不向外暴露。

Application、Node 和 Service 需要的局部配置视图由上层配置模型在加载阶段建立。Service 业务继续使用已经确认的：

```go
GetConfig(path string, dst any) error
ParseServiceConfig(dst any) error
GetServiceConfig(path string, dst any) error
```

`GetConfig` 从合并后的配置根按点分路径读取任意命名字段；另外两个接口读取当前 Service 的有效配置。三个接口属于 Service Runtime，不要求基础配置库公开 Snapshot 或 `DecodePath`。

## 4. JSON 与 YAML

### 4.1 支持范围

首版只识别：

```text
.json
.yml
.yaml
```

扩展名大小写不敏感，文件内容必须与扩展名一致。

JSON 使用 Go 1.26.5 稳定的 `encoding/json`：

- 不支持 `//` 和 `/* */` 注释；
- 不支持尾随逗号；
- 不支持 JSONC、JSON5；
- 不启用实验性的 `encoding/json/v2`；
- 不在解析前自行删除注释。

需要注释的配置使用 YAML。

### 4.2 配置结构体 Tag

Origin 配置结构体默认不要求 Tag。未声明 Tag 的可导出 Go 字段自动映射为 `snake_case`：

```go
type RPCConfig struct {
    MaxPayloadSize   ByteSize
    MaxBroadcastSize ByteSize
    TCP              RPCTCPConfig
}

type RPCTCPConfig struct {
    SendQueueMessages int
    ReadIdleTimeout   Duration
    WriteTimeout      Duration
}
```

对应：

```yaml
max_payload_size: 4M
max_broadcast_size: 64M
tcp:
  send_queue_messages: 16384
  read_idle_timeout: 15s
  write_timeout: 15s
```

常见映射：

- `DefaultTimeout` -> `default_timeout`；
- `NodeID` -> `node_id`；
- `RPCConfig` -> `rpc_config`；
- `HTTPServerURL` -> `http_server_url`。

只有需要覆盖默认名称或忽略字段时才写标准 `json` Tag：

```go
type ServerConfig struct {
    ListenAddress string `json:"listen"`
    RuntimeCache  any    `json:"-"`
}
```

规则：

- `json:"name"` 覆盖默认名称，`json:"-"` 忽略字段；
- `json:",omitempty"` 等没有名称的 Tag 仍使用自动 `snake_case`；
- `omitempty`、`string` 等 JSON 编码选项不改变配置解码规则；
- JSON 和 YAML 使用完全相同的映射结果；
- 配置加载不读取 `yaml` Tag，也不定义 Origin 私有的 `config` Tag；
- `yaml` Tag 可以被其他库使用，但对 `config.LoadDir` 没有效果；
- 多个字段或匿名嵌入产生相同配置名时，在解码前报配置模型冲突，不静默选择；
- 无法自然表达或存在歧义的特殊名称由开发者显式添加 `json` Tag。

“不维护 `yaml` 或 `config` Tag”表示 Origin 不需要实现它们的优先级、冲突检测和跨格式兼容规则，并不是禁止业务结构体因其他用途存在这些 Tag。

### 4.3 时间与字节大小

所有 JSON/YAML 固定时长使用带单位字符串：

```yaml
default_timeout: 15s
retry_interval: 500ms
retention: 14d
```

支持 `ns`、`us`、`ms`、`s`、`m`、`h`、`d`；`d` 固定为 `24h`。允许 `2h30m` 等从大到小的组合，不接受无单位整数、小数、负数或重复单位。

所有 JSON/YAML 字节大小使用 Origin 简写单位：

```yaml
max_payload_size: 4M
buffer_size: 64KB
max_file_size: 512M
```

只支持 `B`、`KB`、`M`、`G`、`T`，并固定采用二进制倍数：`KB = 1024B`，其余逐级乘以 `1024`。不接受无单位整数、`K`、`MB`、`GB`、`KiB`、`MiB` 或 `4byte`。配置加载时统一换算为 Byte，并检查溢出。

字段名不再携带单位，例如使用 `max_payload_size`、`max_age`，不使用
`max_payload_bytes`、`max_age_days`。

### 4.4 环境变量

v2 在解析配置前对整份文件执行 `os.ExpandEnv`。该方式虽然方便，但未定义变量会静默变为空字符串，而且替换内容可能改变 JSON/YAML 结构。

v3 保留环境变量能力，但采用更安全的值级展开：

```yaml
discovery:
  etcd:
    auth:
      username: ${ETCD_USERNAME}
      password: ${ETCD_PASSWORD}

database:
  dsn: postgres://${DB_USER}:${DB_PASSWORD}@db.example.com/game

scheduler:
  default_await_timeout: ${AWAIT_TIMEOUT}
```

规则：

- 只展开解析后的字符串 Scalar 值，不展开字段名、注释、Mapping 或 Sequence；
- 只支持 `${NAME}`，变量名匹配 `[A-Za-z_][A-Za-z0-9_]*`；
- 不支持 `$NAME`、`${NAME:-default}`、嵌套变量、命令替换或脚本；
- `$${NAME}` 表示字面量 `${NAME}`；
- 未定义变量返回带文件、行列和变量名的配置错误；
- 已定义为空字符串的变量允许展开，再由目标类型或业务校验决定是否合法；
- 完整 Scalar 只有一个占位符时，可以按目标基础类型、`Duration`、`ByteSize` 或文本解码接口严格转换；
- 占位符和普通文本混合时，结果只能作为字符串；
- 环境变量值不得写入日志或错误详情。

环境变量只提供值，不形成 `dev`、`prod` 等配置覆盖层，也不能改变配置树形状。这样可以满足 Kubernetes Secret、容器地址和部署参数注入，同时保留确定性合并与严格类型检查。

### 4.5 多文件

建议目录按职责拆分，例如：

```text
config/
├── 10-log.yaml
├── 20-discovery.yaml
├── 30-server-info.yaml
├── nodes/
│   ├── 10-gateway.yaml
│   ├── 20-game.yaml
│   └── 30-db.json
└── services/
    ├── player.yaml
    └── database.yaml
```

文件名只用于阅读和稳定排序，不决定配置类型或覆盖优先级。

## 5. v2 配置能力对照

当前 `origin` 目录中的 v2 主要配置能力如下：

| v2 配置 | v2 作用 | v3 安排 |
|---|---|---|
| `RpcMode.Type` | 选择默认 TCP 或 NATS | 改为每个 Node 的 `rpc.transport` |
| `RpcMode.Nats` | NATS 地址与随机策略 | 改为每个 Node 的 `rpc.nats` |
| `Discovery.Origin` | Origin 内置动态服务发现 | 保留为内置顶层 Provider，不依赖外部中间件 |
| `Discovery.Etcd` | etcd 动态服务发现 | 保留为内置顶层 Provider |
| 未配置动态 Discovery | 从配置文件发现 Node | 不保留独立 `static` Provider |
| `NodeList` | Node 地址、Service 和 RPC 参数 | 保留，并增加标签和 Application 管理 |
| `AllowDiscovery` | 按 Master、网络、Node、Service 正则筛选 | 重构为 Service 精确名称和 Node 标签 |
| `Global` | 全局业务配置 | 删除框架级概念；业务可定义任意顶层字段并通过根路径读取 |
| `Service` | Service 公共业务配置 | 保留 |
| `NodeService` | 指定 Node 的 Service 业务配置 | 保留；存在时整体替换公共 Service 配置 |
| `_ServiceName`、`Private` | 控制 Service 或 Node 是否公开 | 保留，私有 Service 只移除一个前导 `_` |

v3 保留能力，不复用 v2 的全局 Cluster、运行时正则和 Map 类型断言实现。

## 6. 建议的完整配置外观

### 6.1 顶层结构

为了接近 v2 并方便按 Node 拆文件，建议采用以下顶层字段：

```yaml
log: {}
buffer_pool: {}
discovery: {}
server_info: {}
nodes: []
services: {}
node_services: {}
```

其中：

- `log`：日志系统；
- `buffer_pool`：Application 内部共享 BufferPool 的低频诊断开关；
- `discovery`：项目内全部 Node 共用的服务发现 Provider 配置；
- `server_info`：业务自行定义的示例字段，不是 Origin 保留名称；
- `nodes`：所有可启动 Node，并分别保存各自的 RPC Transport；
- `services`：Service 公共业务配置；
- `node_services`：指定 Node 的 Service 业务配置。

顶层不设置 `application` 字段。Application 是把一个或多个 Node 按顺序运行起来的进程内管理者，不是需要业务配置的运行对象：

- 更接近 v2 的 `NodeList`；
- Node 文件少一层缩进；
- Node 启动顺序直接使用命令行参数顺序，未传参数时使用 `nodes` 声明顺序；
- 服务发现设计和模板 Service 设计已经使用顶层 `nodes` 示例。

`discovery` 配置只定义一次，但 Application 不持有共享 Provider 实例或连接。每个启动的
Node 根据同一份顶层配置创建和释放自己的 Discovery Provider，保持 Node 生命周期和资源
所有权隔离。框架内置 `origin`、`etcd`，Application 还可以在加载配置前通过唯一注册入口
增加 `consul` 等自定义 Provider；配置结构和严格校验规则与内置实现一致。

## 7. 完整拆分示例

本节用于展示各部分如何组合。带有“待确认”的字段只表示建议外观，不代表已经允许实施。

### 7.1 Node 启停顺序

配置中不提供 `start_order` 和 `stop_order`：

- 显式传入 `--node gateway-1,game-1,db-1` 时，严格按参数从左到右顺序启动；
- 未传入 `--node` 时，按顶层 `nodes` 声明顺序启动全部 Node；
- Stop 和启动失败回滚始终按本次实际成功启动顺序的严格倒序执行；
- 被依赖 Node 应放在启动顺序前面，使其在倒序停止时晚于依赖方停止。

### 7.2 日志

`10-log.yaml`：

```yaml
log:
  mode: async

  console:
    enabled: true
    level: info
    format: text

  file:
    enabled: false
    level: debug
    format: json
    path: logs/origin.log
```

完整滚动、保留、自定义 Encoder 和同步模式见 [日志系统设计](./2026-07-25-日志系统设计.md)，本文不重复扩展。

### 7.3 Node 的 RPC Transport

TCP/NATS 选择属于每个 Node，不存在 Application 级默认 Transport。同一进程可以启动 TCP Node 和 NATS Node；每个 Node 严格按自己的配置建立网络资源。

TCP Node 建议外观：

```yaml
nodes:
  - id: game-1
    scheduler:
      max_tasks: 20000
      max_await_tasks: 10000
      default_await_timeout: 15s
    rpc:
      transport: tcp
      max_payload_size: 4M
      max_broadcast_size: 64M
      tcp:
        listen: 0.0.0.0:7201
        advertise: 10.0.1.21:7201
        send_queue_messages: 16384
        read_idle_timeout: 15s
        write_timeout: 15s
```

其中以下内容已经确认：

- TCP 与 NATS 使用相同 RPC 外观和语义；
- RPC 与通用 Await、Redis、数据库等等待共用
  `scheduler.default_await_timeout`，省略时最终兜底为 `15s`；不增加
  `rpc.default_timeout`；
- TCP 与 NATS 的 RPC 消息都必须限制最大长度，首版默认值为 `4M`；
- TCP 按 Node 管理连接，不按 Service 或 RPC 方法创建连接；
- RPC 配置只公开 `send_queue_messages`，表示每条连接最多等待发送的完整 RPC 包数量；
  默认 `16384`，最大 `65536`；
- TCP 发送队列只限制消息数量，不再配置或内部维护待发送 payload 字节额度；
- 帧数达到上限立即返回 Transport 过载，不阻塞 Service Runner；
- `read_idle_timeout` 是连接读空闲超时，RPC 默认 `15s` 并使用轻量 Ping/Pong 检测传输健康；
  `0s` 表示同时关闭应用层心跳和 M5 ReadTimeout；
- `write_timeout` 默认 `15s`，限制一个完整 TCP 帧的写入时间；读写超时都使当前物理连接
  关闭并由 Node 连接管理器决定是否重连；
- 同一进程允许混合运行 TCP Node 和 NATS Node；
- 混合运行不表示两种 Transport 自动互通。首版只有 Transport 兼容的 Node 才能互相 RPC，框架不隐式建立 TCP/NATS 桥接；
- 首版不实现 RPC 消息压缩，也不提供压缩阈值配置；
- RPC 线协议不预留压缩标志位和算法编号，避免每个低延迟小包承担无用途字段和分支；
- 后续只有在真实业务基准证明压缩能够带来净收益时，才使用新的 TCP WireVersion 设计
  完整的协商和安全上限；即使实现，默认仍然关闭。

`max_payload_size` 表示单个 RPC 业务 payload 的最大字节数，不是 TCP/NATS 队列长度，也
不是压缩配置。TCP 出站队列使用 `send_queue_messages`，NATS 入站 Subscription 回调队列
使用 `receive_queue_messages`，Await/Async 在途 pending 上限由 Runtime 独立管理。接收端必须在
分配完整消息缓冲区和反序列化之前校验单消息限制。未来若增加压缩，还必须分别限制压缩
前后的消息长度，避免解压膨胀。

`max_broadcast_size` 是 M20 冻结字段，限制一次 Broadcast 的
`payload_size × 意图目标数`，默认 `64M`、最大 `1G`。它使用 Origin `ByteSize` 字符串，
不接受裸整数；以 `int64` 计算并检查溢出。超过上限时在编码 Buffer 申请和任何目标提交前
整体拒绝，不因当前断开目标数量降低计算结果。该字段限制一次广播放大，不取代单 payload
上限和各 Transport 的消息数背压。

上述发送队列容量只在实际入队时占用对应 payload 内存，不会在建立连接时预分配消息体。
只保留消息数量上限后，最坏内存由“队列数量 × 单消息上限”共同决定。对于拥有大量可信
Node 连接且小 RPC 突发极高的项目，可以把 `send_queue_messages` 调高到 `65536`；提高前
必须复核单连接平均消息大小、总连接数、队列高水位、最坏内存和 p99 排队延迟，不能用
超大队列长期掩盖过载。

### 7.4 NATS 替代示例

NATS Node 建议外观：

```yaml
nodes:
  - id: chat-1
    scheduler:
      max_tasks: 20000
      max_await_tasks: 10000
      default_await_timeout: 15s
    rpc:
      transport: nats
      max_payload_size: 4M
      max_broadcast_size: 64M
      nats:
        namespace: game-prod
        urls:
          - nats://nats-1:4222
          - nats://nats-2:4222
          - nats://nats-3:4222
        receive_queue_messages: 16384
        auth:
          username: ${NATS_USERNAME}
          password: ${NATS_PASSWORD}
        tls:
          enabled: false
          ca_file: ""
          cert_file: ""
          key_file: ""
          server_name: ""
          insecure_skip_verify: false
```

NATS 与 TCP 是 Transport 选择，不改变 `allow_discovery`、RPC 客户端、路由和发现事件的
业务语义。NATS RPC 沿用 v2 的 Node 级稳定请求/响应 Subject；ServiceName 与 RequestID
保留在统一 RPC 线协议中，关注一个远端 Service 不会新增 NATS Subscription。字段名称和
多地址策略由 M6 设计确认。

`namespace` 必填，不提供默认值，也不从进程 AppName 推导。Namespace 和 NodeID 都使用
63 字符以内的小写 kebab-case。NATS Request 和 Response Subscription 分别使用
`receive_queue_messages` 限制待回调消息数量，默认 `16384`、最大 `65536`，不提供
`pending_size`；单条业务载荷仍由 `max_payload_size` 限制。TCP/NATS 下的 Retired
Service 都继续保持发现、连接、精确路由和普通入站 RPC 能力，业务可以自行返回
`CodeServiceRetired`，框架不自动拦截；M19 的 `ToService` 自动选择只接受 Running。

`send_queue_messages` 是 TCP 出站队列，`receive_queue_messages` 是 NATS 入站回调队列，
两者方向不同，不能合并成同一个 `queue_messages`。NATS RPC 不在 nats.go 之外建立发送
队列，并固定关闭断线 Reconnect Buffer。M6 内部连接超时、Ping、Drain 和重连参数使用
框架安全默认值，不暴露为 Node 业务配置；认证和 TLS 因部署环境确实存在差异而继续公开。

`transport: tcp` 必须只提供 `tcp` 配置块；`transport: nats` 必须只提供 `nats` 配置块。
当前 Transport 对应块缺失、同时存在两个块或使用迁移前旧字段时，均在配置冷路径报错。

### 7.5 Origin 内置服务发现

建议 v3 正式支持 Origin 内置动态服务发现。它不是只供测试使用的临时实现，而是小中型项目无需部署第三方协调中间件时的可选生产方案。

主要价值：

- 只部署 Origin 程序即可完成 Node 和 Service 动态注册；
- 减少 etcd 集群的部署、监控、证书、升级和故障处理成本；
- TCP 与 NATS 可以共用同一套发现、筛选、退休和路由语义；
- 延续 v2 的使用习惯，已有项目迁移时不被迫引入新的基础设施；
- 发现更新不进入 RPC 热路径，RPC 只读取本地已经发布的只读路由快照。

首版内置发现只负责：

- Node 地址、标签和公开 Service 注册；
- TTL、心跳与失效清理；
- Service 新增、删除和状态变化；
- 全量快照和增量变化通知；
- 退休状态发布；
- 配合本地 `allow_discovery` 生成可见服务快照；
- 产生发现、失去发现和退休状态事件。

首版不实现：

- etcd 一类通用 KV 存储；
- 分布式锁、配置中心和选主 API；
- Raft 或其他强一致性共识协议；
- 持久化发现目录；
- 复杂健康探测和跨数据中心一致性。

需要强一致协调、持久租约管理或已有 etcd 基础设施的项目，继续选择 etcd Provider。内置发现和 etcd 使用相同的上层 Provider 语义，不让业务 Service 感知具体实现。

v3 不再配置 `IsMaster` 或 `masters`。框架提供保留名称 `DiscoveryService` 的内置 Service；需要承载内置发现端的 Node，像配置普通 Service 一样把它写入 `services`：

```yaml
discovery:
  type: origin
  origin:
    ttl: 15s
    server:
      node: discovery-1
      listen: 0.0.0.0:7100
      address: 10.0.1.10:7100

nodes:
  - id: discovery-1
    rpc:
      transport: tcp
      tcp:
        listen: 0.0.0.0:7000
        advertise: 10.0.1.10:7000
    services:
      - DiscoveryService
      - AdminService

  - id: game-1
    rpc:
      transport: tcp
      tcp:
        listen: 0.0.0.0:7201
        advertise: 10.0.1.21:7201
```

`DiscoveryService` 使用普通 Service 的构造、生命周期、调度和停止规则，但它属于框架
保留的系统 Service，业务不能注册同名 Service。TTL 属于 Provider 协议配置，统一使用
`discovery.origin.ttl`，不再通过普通 `services.DiscoveryService` 业务配置提供。

`origin` 表示 Origin 自带的动态服务发现，不依赖 etcd。M17 固定使用独立 TCP 控制通道，
不再提供 `origin.transport`，也不复用 Node 的业务 RPC Runtime、TCP 连接或线协议。

- `server.node` 指定唯一包含 `DiscoveryService` 的 Node；
- `server.listen` 只由该 Node 使用，`server.address` 供全部 Provider 客户端引导连接；
- `DiscoveryService` 可以与任意普通业务 Service 配置在同一 Node，不要求专用 Node；
- 业务 RPC 使用 NATS 的 Node 同样建立一条轻量 TCP 发现控制连接；
- 发现控制通道只传输注册、心跳、快照和状态变化，不桥接业务 RPC；
- 同一 Application 仍可混合 TCP/NATS Node，但不同业务 RPC Transport 的 Node 默认不能直接互调。

这样不会因共享 Discovery 配置推翻“RPC Transport 按 Node 配置”的既有结论，也不需要
建立 TCP/NATS 业务桥。共置 Node 在全部纯 `OnInit` 后先 Prepare 控制 Listener，再完成
自身 Provider 首次同步，最后按原配置顺序执行全部 Service `OnStart`；Prepare 不执行用户
回调、不开放业务 RPC，也不提前发布当前 Node。同一 Application 选择多个 Node 时，
`server.node` 必须位于显式启动顺序第一位，框架不静默重排。

首版一个 Origin 发现域只支持一个 `DiscoveryService`：

- 不实现多个 Master、Leader 选举、发现端复制或多来源快照合并；
- Node 每次启动生成新的会话 ID；旧连接仍活跃时拒绝不同 Session，旧连接断开后允许新
  Session 立即接管；
- TTL 默认 `15s`、范围 `3s～5m`，心跳周期为 `TTL / 3` 且不得小于 `1s`；
- 发现服务短暂不可用时最多保留现有只读快照一个 TTL；恢复后重新注册并用全量快照做差异更新，超过 TTL 仍未恢复则发布 `Lost`；
- 新 ServerEpoch 固定等待 `min(TTL / 3, 5s)`、最低 `1s` 后再发布首个权威完整目录，避免
  把陆续重注册期间的部分集合错误解释为批量 Lost；
- 发现服务不可用期间不能发现新 Node、接收退休变化或可靠判断 NATS 目标是否仍存活；
- M17 Origin 控制通道限定可信内网，不配置 TLS、Token 或其他认证字段；
- 需要服务发现高可用或强一致时使用 etcd Provider。

选择单实例是为了避免多连接、重复事件、会话冲突、网络分区裁决和大幅扩张的故障测试矩阵。内置发现保持轻量，生产环境通过进程管理器自动拉起 `DiscoveryService`。

### 7.6 不提供 `static` Provider

框架首版只内置 `origin` 和 `etcd`，不再把 v2 的“从完整配置读取全部 Node”包装成
`static` Provider。自定义 Provider 仍可通过公开 SPI 注册，因此“只内置两种”不等于
Provider 类型被硬编码为封闭枚举。理由是：

- Origin 内置发现已经覆盖“不依赖第三方中间件”的主要场景；
- 生产部署本来按一个 Node 一个程序运行，完整静态 Node 清单容易掩盖动态启停、TTL 和失去发现问题；
- 测试静态目标属于 TCP/NATS 基础库或 RPC 集成测试夹具，不需要成为正式服务发现模式；
- 删除一套 Provider、状态差异和配置语义，降低实现与测试复杂度。

自定义 Provider 沿用 `type + 同名配置块`：

```yaml
discovery:
  type: consul
  consul:
    addresses:
      - 127.0.0.1:8500
    ttl: 15s
```

外层只允许 `type` 和选中的同名块。框架先从当前 Application 私有注册表找到 Factory，
再由 Factory 使用公开的严格解码能力解析自己的配置；未注册名称、同时存在多个 Provider
块或自定义块中存在未知字段都在创建任何 Node 前失败。详细 SPI、快照和生命周期规则见
[服务发现提供者设计](./2026-07-26-服务发现提供者设计.md)。

### 7.7 etcd 服务发现

建议外观：

```yaml
discovery:
  type: etcd
  etcd:
    endpoints:
      - https://etcd-1.example.com:2379
      - https://etcd-2.example.com:2379
      - https://etcd-3.example.com:2379
    # 可省略，默认 /origin。
    namespace: /origin/game-prod
    local_network: cn-east
    watch_networks:
      - cn-north
    ttl: 15s
    dial_timeout: 5s
    request_timeout: 5s

    auth:
      username: origin
      password: change-me
      token: ""

    tls:
      ca_file: certs/etcd-ca.pem
      cert_file: certs/origin-client.pem
      key_file: certs/origin-client-key.pem
      server_name: etcd.example.com
      insecure_skip_verify: false
```

首版 etcd 配置支持：

- 单 endpoint 和多 endpoint；
- 一个必填本地网络和零个或多个关注网络，有效范围最多 64 个；
- 无认证、用户名/密码认证和 Token 认证；
- 明文 HTTP、使用系统 CA 的 HTTPS、自定义 CA HTTPS 和双向 TLS；
- TLS ServerName 覆盖，以及仅供开发环境显式使用的 `insecure_skip_verify`；
- 租约 TTL、连接超时和单次请求超时；
- Node 注册、刷新、退休和失去发现事件。

约束：

- `endpoints` 不能为空，必须显式使用统一的 HTTP 或 HTTPS，禁止 Path、Query 和 UserInfo；
- `namespace` 可省略并默认 `/origin`；显式值必须是绝对前缀，不允许根路径 `/` 或尾随 `/`；
- `local_network` 必填；读取范围自动包含它，不需要在 `watch_networks` 中重复配置；
- Node 只发布到 `local_network`；去重后的读取网络最多 64 个；
- `ttl` 默认 `15s`，范围 `3s～5m`，必须为整数秒；
- `request_timeout` 只限制单次 etcd 操作，不替代租约 TTL；
- `cert_file` 和 `key_file` 必须同时配置；
- `username` 与 `password` 必须同时配置，`token` 与二者互斥；
- HTTP 禁止 TLS 字段；HTTPS 最低 TLS 1.2；
- HTTPS 未配置 `ca_file` 时使用系统根证书，配置后只信任指定 CA；
- `insecure_skip_verify` 默认 `false`，启用时必须输出明确警告；
- TLS 文件相对路径统一相对于配置根目录解析；
- 认证密码和 TLS 私钥内容不得进入日志、错误详情或配置转储。

首版不把 etcd Go Client 的所有底层字段逐项暴露为配置。gRPC KeepAlive、Endpoint
AutoSync、DialOption、客户端日志器、Range 分页、Watch progress 和消息大小等使用框架
内部安全默认值，避免配置与具体依赖版本强耦合。若真实部署场景证明必须调整，再增加独立
高级配置。Key 固定按 Network 分层；普通项目无需配置 `namespace`，共享 etcd 集群时才
需要显式覆盖。

### 7.10 私有 Node 与 Service

保留 v2 的简洁语法：

```yaml
nodes:
  - id: admin-1
    private: true
    services:
      - AdminService

  - id: game-1
    services:
      - PlayerService
      - _DebugService
      - _scene-debug:SceneService
```

规则：

- `private: true` 表示该 Node 不向服务发现发布任何业务 Service；
- Service 名称以一个 `_` 开头表示该实例私有；
- `_DebugService` 的实际运行时名称为 `DebugService`；
- `_scene-debug:SceneService` 的实际实例名为 `scene-debug`，模板名仍为 `SceneService`；
- 私有 Service 正常创建、启动并可被同 Node 业务使用，但不发布到 Discovery Provider；
- `private: true` 或规范化后没有公开 Service 的 Node 仍创建 Discovery Provider 并同步
  远端权威目录，只是不发布空 Node；其发布状态为 `NotRequired`；
- `_` 只是配置标记，不属于运行时 `ServiceName`；
- 只移除一个前导 `_`，`__Service`、单独的 `_` 以及去除后产生空名称的配置均为错误；
- 同一 Node 中公有和私有写法规范化后名称冲突，必须在启动前报错。

### 7.12 业务自定义配置与任意路径读取

v3 不保留框架级 `global` 概念。业务可以按照项目约定直接定义任意顶层结构：

```yaml
server_info:
  field1: value-1
  field2: 100

gameplay:
  save_interval: 5m
```

最终可执行程序不再定义或向 `application.New` 传入 `ProjectConfig`。`app.Start()` 内部从 M4
取得已经校验的配置目录，调用 M3 加载完整配置根，并由当前 Application 独占持有。业务入口
看不到框架 Config、原始 Map、Snapshot 或 AST。

Application 从内部配置根严格解码 `nodes`、`buffer_pool` 等已实现框架区域，
其他任意顶层名称作为业务配置保留。框架已知区域内部仍拒绝未知字段；业务通过
`ParseServiceConfig` 解码目标结构体时忽略未知字段，缺失字段保留调用方预填值或 Go 零值。
由于顶层业务名称由项目自由定义，Origin 不把所有未知顶层名称直接判定为错误。
根配置在 Application 运行期间不可修改。

Service 和 Module 可以通过根配置路径读取任意命名字段：

```go
var field1 string
if err := s.GetConfig("server_info.field1", &field1); err != nil {
    return err
}

var nodes []node.Config
if err := s.GetConfig("nodes", &nodes); err != nil {
    return err
}
```

`GetConfig(path, dst)` 从合并后的配置根开始查找，因此既能读取 `server_info`、`gameplay` 等业务自定义字段，也能读取 `log`、`discovery`、`services`、`node_services` 等框架字段。首版路径仍只支持点分 Mapping，不支持数组下标；需要数组时读取完整 Slice。

Origin 不保留 `global`、`business`、`custom` 等业务容器名，也不规定业务配置必须放在哪一层。顶层业务字段是否集中、如何命名和分层完全由项目自行约定。

该接口只解码到调用方提供的非 nil 指针，不返回内部 Map、AST 或可变引用。对于当前 Service 的有效业务配置，仍优先使用 `GetServiceConfig` 和 `ParseServiceConfig`，因为它们已经应用 Node 专属整体替换规则；直接读取 `services` 或 `node_services` 得到的是原始配置区，不是有效结果。

### 7.13 Service 公共业务配置

`services/player.yaml`：

```yaml
services:
  PlayerService:
    max_players: 5000

    save_mongo:
      url: mongodb://127.0.0.1:27017
      database: game
      retry_count: 3
```

Service 在 `OnInit` 中通过 `ParseServiceConfig` 一次解析到强类型结构；Module 通过所属 Service 的 `GetServiceConfig` 读取同一只读配置视图。

模板实例创建完成后与普通 Service 一样只按实际 `ServiceName` 读取配置。例如
`scene-1001:SceneService` 使用 `services.scene-1001`，不回退 `services.SceneService`。共享配置
放到业务自定义根路径并通过 `GetConfig` 读取，不增加模板继承规则。

### 7.14 Node 专属 Service 配置

为保留 v2 `NodeService` 能力，建议外观：

```yaml
node_services:
  game-1:
    PlayerService:
      max_players: 10000
```

已确认采用整体替换：

- 当前 Node 和 Service 存在 `node_services` 配置时，完整使用该对象；
- 不再读取或递归合并 `services` 中同名公共配置；
- 没有 Node 专属配置时，使用公共 Service 配置；
- 两处都不存在时，该 Service 没有业务配置；
- Node 专属配置不能为 `null`，不能通过空对象表达“继承公共字段”；
- 需要复用公共字段时由项目显式拆出业务顶层配置，并通过 `GetConfig` 读取，不在框架中增加继承和覆盖规则。

上述 ServiceName 对模板实例同样表示实际名称，不使用 TemplateName。

## 8. `allow_discovery` 已确认语义

### 8.1 字段状态

- 完全未配置 `allow_discovery`：发现 Provider 范围内全部公开 Service；
- 显式配置 `allow_discovery: []`：不发现任何远端业务 Service；
- 配置一个或多个规则：只发现至少匹配一条规则的 Service；
- `allow_discovery: null`：配置错误；
- `allow_discovery: [{}]`：配置错误。

### 8.2 组合关系

- 一条规则中的多个 `services` 使用 OR；
- 同一标签的多个允许值使用 OR；
- 不同标签之间使用 AND；
- 多条 `allow_discovery` 规则之间使用 OR；
- 缺少 `services` 表示不限制 Service 名称；
- 缺少 `node_labels` 表示不限制目标 Node 标签。

### 8.3 匹配规则

- Service 使用实际 `ServiceName` 精确匹配；
- Node 标签区分大小写并精确匹配；
- 首版不支持正则、通配符和模板名称筛选；
- 标签匹配只表示目标 Node 的标签，不自动引用当前 Node 的同名标签；
- TCP 只为至少存在一个可见 Service 的目标 Node 产生连接需求；
- NATS 仍使用相同的可见服务和路由筛选，只是不建立逐 Node TCP 连接。

完整事件和退休状态语义见 [服务发现与关注筛选设计](./2026-07-24-服务发现与关注筛选设计.md)。

## 9. 多文件合并边界

基础配置库只执行通用合并：

- Mapping 与 Mapping 递归合并；
- Sequence 与 Sequence 按稳定文件顺序追加；
- 同一路径 Scalar 或不同节点类型重复时返回错误；
- 不按后加载文件覆盖前文件；
- 不根据 Sequence 元素中的 `id` 或 `name` 隐式合并。

因此：

- 不同 Node 可以分别放在不同文件；
- 不同 Service 的公共配置可以分别放在不同文件；
- 同一个 Node 不能写成两个 `nodes` 元素并期待按 `id` 自动拼接；
- NodeID、ServiceName 和顺序列表的业务唯一性由上层框架配置模型校验。

M3 配置加载方案、公共 Provider 配置联合和 M17 Origin 最终配置面均已确认。M18 etcd
配置字段、最多 64 个有效网络、默认值、认证、TLS 和 Network Key 分层已经确认；
`namespace` 可选且默认 `/origin`。Origin 只
公开 `ttl`、`server.node`、`server.listen` 和 `server.address`；心跳、冷启动收敛、

## 11. 当前结论

已确认并可以同步到相关设计：

1. 配置目录支持拆分多个文件；
2. 首版只支持标准 JSON 和 YAML；
3. 基础加载公共外观收紧为 `LoadDir(dir, dst)`；
4. 不公开 Loader、Snapshot、AST、原始 Map 和通用路径查询；
5. Node 下直接配置本地 `services` 和远端 `allow_discovery`；
6. TCP、NATS 使用相同的关注筛选、RPC 和路由语义；
7. Origin 内置服务发现不依赖外部中间件，并保留 etcd 支持；
8. 发现与失去发现事件、退休状态事件继续保留；
9. `nodes` 为顶层字段，配置中不建立 `application`、`start_order` 或 `stop_order`；
10. RPC Transport 按 Node 配置；
11. 同一进程允许混合运行 TCP 与 NATS Node，但首版不提供两种 Transport 之间的隐式桥接；
12. 首版只内置 `origin` 和 `etcd`、不实现 `static`，Application 可以在加载配置前注册
    `consul` 等自定义 Provider；
13. Origin 内置发现端使用保留名称 `DiscoveryService` 的普通 Service，一个发现域首版
    只允许一个实例，但允许与任意业务 Service 配置在同一 Node；
14. etcd 支持单逻辑集群多 Endpoint、最多 64 个有效网络、用户名/密码或 Token 认证，
    以及完整 TLS 部署场景；
15. Discovery Provider 配置位于顶层，使用 `type + 同名配置块` 且项目只选择一套
    Provider；每个 Node 根据共享配置独立创建并释放 Provider 实例；
16. 保留 v2 的 `private: true` 和 `_ServiceName` 私有语法，私有实例不发布到服务发现；
17. 删除框架级 `global` 概念；业务可以自行定义任意顶层层级，Service 通过 `GetConfig` 从根配置读取；
18. Node 专属 Service 配置存在时整体替换公共 Service 配置，不递归合并；
19. 所有外部固定时长使用带单位字符串，所有外部字节大小使用 Origin 简写单位字符串；
20. 保留环境变量能力，但只在解析后的字符串 Scalar 中安全展开 `${NAME}`，不再使用 v2 的整份文本 `os.ExpandEnv`；
21. 完整配置外观中的待确认项不得提前进入实现。
22. 最终业务入口不定义或传入 `ProjectConfig`；Application 内部加载并独占完整只读配置根；
23. 框架已知区域严格拒绝未知字段；业务目标结构体忽略未知字段、缺失字段保留预填值或
    Go 零值，任意业务顶层名称允许保留；
24. Application 生命周期超时不增加配置区域；`application.Options` 的 Start/Stop Timeout
    默认均为零并表示无限等待，只有正数才启用 Deadline。
25. RPC 不定义 `rpc.default_timeout`；通用 Await、生成的 `AwaitXxx`、`AsyncXxx`
    pending、Redis 和数据库等框架等待共用 Node 的
    `scheduler.default_await_timeout`，省略时最终使用内置 `15s`。
26. M17 Origin 配置只保留 `ttl` 与 `server.node/listen/address`，其余容量、超时和恢复
    参数使用框架固定边界或由 TTL 派生。
27. M20 增加 `rpc.max_broadcast_size`，默认 `64M`、最大 `1G`，按 payload 与全部意图
    目标数计算；超限时零投递。

## 12. 格式依据

- Go 标准库时长使用 `ns`、`us`/`µs`、`ms`、`s`、`m`、`h` 等单位；Origin 在此基础上增加适合配置文件的整数 `d`，固定解释为 `24h`：[time.ParseDuration](https://pkg.go.dev/time#ParseDuration)；
- Kubernetes 和 IEC 使用较长的二进制单位避免歧义，但 Origin 为提高高频配置的可读性，采用更接近 Nginx 等服务器配置的短单位，并在解析规则中固定为二进制倍数：[Resource units in Kubernetes](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#resource-units-in-kubernetes)、[Nginx size configuration](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)；
- `goccy/go-yaml` 原生存在 `json`/`yaml` Tag 优先级差异；Origin 在统一解码层采用零 Tag 自动命名和可选 `json` Tag 覆盖，避免两种文件格式产生不同字段名：[goccy/go-yaml](https://github.com/goccy/go-yaml#2-struct-field-names)。
