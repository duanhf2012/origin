# Origin 第三版服务发现提供者设计

> 文档类型：详细设计
> 状态：公共契约与 Origin 核心语义已确认；Wire 字段、容量和默认值待确认
> 创建日期：2026-07-26
> 最后更新：2026-07-30
> 适用版本：Origin v3

## 1. 范围

本文定义服务发现数据从哪里产生、Provider 如何接入 Node，以及 Origin 内置发现和 etcd
Provider 如何配置、注册、续约和失效。公共契约同时以未来可以增加 Consul 或项目自定义
Provider 为验收条件，但 M17/M18 不实现 Consul。

关注筛选、可见快照、发现/失去发现/退休事件见[服务发现与关注筛选设计](./2026-07-24-服务发现与关注筛选设计.md)，不在本文重复。

## 2. 已确认边界与里程碑拆分

已确认：

1. Application 只管理 Node 启停；
2. Origin、etcd 和第三方 Provider 输出相同的 Node、Service、会话与状态变化语义；
3. Provider 只更新原始发现目录，不直接调用业务监听器；
4. 发现数据更新不进入 RPC 调用热路径，RPC 路由读取已经发布的只读快照；
5. 框架内置 `origin` 和 `etcd`，不实现独立 `static` Provider，但允许 Application 注册
   `consul` 等自定义 Provider；
6. Origin 内置发现首版只支持一个 `DiscoveryService`，不实现多实例高可用；
7. etcd 配置支持多 Endpoint、网络、认证和 TLS 场景，但不直接暴露全部底层 Client
   调优项。

Discovery Provider 配置放在顶层，整个项目只选择一套 Provider。Application 不持有共享 Provider 实例或连接；每个启动的 Node 根据同一份顶层配置独立创建和释放自己的 Provider，保持 Node 生命周期与资源所有权隔离。

公共契约、Origin 和 etcd 一起设计，避免到 M18 才反向修改 Node、Directory、RPC 或业务
API；实现仍拆成两个里程碑：

- M17 实现最小公共 Provider 基座、公开扩展 SPI、Origin Provider 和公共一致性测试；
- M18 只增加 etcd Provider、Lease/Watch/认证/TLS 和 etcd 故障矩阵；
- M18 接入后不得修改 Node、Directory、RPC 或业务发现 API；如果 etcd 暴露出公共契约
  缺陷，必须先重新 Review，不能在 etcd 适配器中建立旁路。

## 3. 公共 Provider 契约

### 3.1 一个小而完整的公开扩展面

公开扩展位于独立的 `discovery/provider` 包。第三方实现者只需要：

1. 提供一个 Factory；
2. 实现一个 Provider；
3. 在 Application 加载配置或启动前注册一次。

概念接口保持为：

```go
type Factory func(Context) (Provider, error)

type Provider interface {
    Start(context.Context) error
    Publish(context.Context, Node) error
    Withdraw(context.Context) error
    Close(context.Context) error
}
```

这里展示的是已确认的最小能力集合，最终 Go 命名在 M17 实施计划中冻结，但不得把一个
Provider 拆成注册器、租约器、Watcher、重试器等多组要求第三方分别实现的接口。

框架通过创建 `Context` 交给 Provider 一个受限能力句柄，用于提交完整快照和报告状态。
快照 Sink 与状态 Reporter 是框架提供的能力，不是第三方还要实现或注册的扩展点。
Provider 不获得 `Application`、`Node`、内部 Directory、RPC Runtime 或业务监听器指针，
不能绕过框架校验直接修改目录或触发业务事件。

SPI 跟随 Origin v3 模块的兼容性规则，并由公开契约测试固定行为；M17 不实现 Go `.so`
动态装载或独立 Provider 进程协议。将来需要 sidecar 时，可以用一个普通的已注册 Provider
作为进程间适配器，不改变本契约。

### 3.2 Application 私有注册

自定义 Provider 使用唯一入口注册：

```go
err := app.RegisterDiscoveryProvider("consul", consul.NewFactory())
```

规则：

- 注册表属于单个 Application，不使用包级可变全局变量；
- 必须在加载项目配置或启动 Application 前注册；
- 名称使用稳定的小写标识，重名、非法名称立即返回错误；
- 内置 `origin`、`etcd` 名称保留，第三方不能覆盖；
- 配置引用未注册 Provider 时，在创建任何 Node 前失败；
- “替换”表示项目配置选择另一个 Provider，不表示运行期热切换或覆盖内置实现。

### 3.3 严格配置联合

顶层配置固定使用 `type + 同名配置块`：

```yaml
discovery:
  type: consul
  consul:
    addresses:
      - 127.0.0.1:8500
    ttl: 15s
```

框架只允许 `type` 和与其同名的一个配置块，拒绝同时提供多套 Provider 配置。框架先按
已注册名称找到 Factory，再把选中块作为只读原始配置交给 Factory；公开配置包装器提供
严格解码能力，未知字段必须报错，不能退化为长期传播的 `map[string]any`。

Origin、etcd 和自定义 Provider 的 TTL 均放在各自配置块内，不放入
`services.DiscoveryService`。密码、Token、私钥和证书内容不得进入日志、错误详情、状态
快照或配置转储。

### 3.4 完整权威快照

Provider 对框架只提交完整权威快照，不公开 Add/Update/Delete 增量写接口：

- Origin 或 Consul 的全量查询可以直接生成完整快照；
- etcd Watch 先更新 Provider 私有镜像，再提交完整快照；
- Provider 自己的 revision、Consul index、etcd revision 等只用于本实现排序，不能进入
  Directory 或业务 API；
- 框架统一校验 NodeID、SessionID、Labels、Transport、Address、ServiceName、状态和
  RPC 契约；
- 框架限制节点数、服务数和总大小，深拷贝可变容器，规范化后原子替换 Directory；
- 无变化快照必须被识别并跳过，不能产生伪事件。

第三方 Provider 不需要理解业务监听器、RPC 路由或 Directory 差异算法，只需持续给出
自己当前确认的完整远端事实。

### 3.5 生命周期、期望发布与恢复

每个 Node 独占一个 Provider 实例。框架串行化生命周期操作并持有公共状态机，具体
Provider 持有后端连接、租约、Watch、心跳和重连资源：

1. `Start` 在 Node 的纯 `OnInit` 全部完成后执行，只有后端控制连接可用、订阅或 Watch
   就绪并提交首个权威快照后才成功；
2. `Start` 受启动 Context 限制；初次同步失败时不能进入任何业务 `OnStart`；
3. 全部业务 `OnStart` 成功后，Node 向 Provider 提交完整本地 Node 发布期望；
4. `Publish` 和 `Withdraw` 必须幂等；Provider 暂时不可用只改变 Readiness 并持续收敛，
   不重复执行任何业务 `OnInit` 或 `OnStart`；
5. 后端恢复后 Provider 必须重新建立 Watch/订阅，并按当前期望自动重新发布本 Node；
6. 正常 Stop 先 Withdraw，再停止 RPC 入站和业务，最后 Close Provider；
7. `Close` 返回后禁止再提交快照或状态，全部 Provider goroutine、连接、租约和订阅均已
   退出。

框架拥有 Readiness、旧快照保留 TTL、快照差异和事件语义；Provider 拥有后端协议、
连接恢复、租约续期和私有 revision。框架可以提供统一的退避参数或工具，但不要求所有
后端伪装成相同连接模型。

### 3.6 断线、权威变化与 Lost

不对已确认的发现变化做防抖：

- 主动注销、Origin TTL 过期、etcd Lease 删除或过期、权威全量快照缺少旧实例，以及
  同 NodeID 的 SessionID 替换，均立即应用并产生对应事件；
- 本地 Provider 控制连接或 Watch 中断时，立即进入 `Recovering`、令 Node Readiness 为
  false，但这只表示暂时失去权威来源，不能立即推断全部远端实例已经消失；
- 断线期间最多保留最后权威快照一个 Provider TTL；超过 TTL 仍未恢复时，框架提交空
  远端快照并产生 `Lost`；
- TTL 内恢复后立即用新的权威全量快照对账；其中缺少的实例立即 `Lost`，新增实例立即
  `Discovered`，SessionID 替换产生旧会话 `Lost` 加新会话 `Discovered`，未变化实例不产生
  伪事件。

因此“断线立即报告”作用于 Provider 健康和 Readiness；“确认实例消失后立即 Lost”作用于
业务发现事件。短暂控制连接断开又恢复、且权威实例集合没有变化时不产生 Lost/Discovered，
不会造成服务间状态不一致。

### 3.7 状态快照

Node 提供无锁、无分配的 `DiscoveryStatus()`，至少包含：

- Provider Kind；
- `Starting/Ready/Recovering/Stopped` 状态；
- 是否完成首次同步；
- 本 Node 是否已在后端确认发布；
- 重连次数与连续失败次数；
- 稳定错误码，不保存动态 error 文本。

该快照用于区分“控制连接已建立但尚未完成首次同步”“远端目录已同步但本 Node 发布失败”
以及 RPC Transport 自身故障。它不包含 Endpoint、账号、Token、证书、Provider revision
或远端 Node 列表。

### 3.8 `OnStart` 前的 RPC 可用性

进入业务 `OnStart` 前必须满足：

- NATS 本地连接、Request/Response Subscription 和 `max_payload` 校验全部完成；
- TCP 监听、Accept 循环和拨号管理器已经运行；
- Provider 首个权威快照已经应用，TCP 已为候选目标安装路由并开始拨号。

TCP 不等待全部已发现目标建立连接，否则一个无关或故障目标会阻塞整个 Node 启动。
`AwaitService` 继续只表示目录中存在可路由实例，不混入 Transport 状态。生成的 Await RPC
在发送前没有可用 TCP 连接时，使用调用 Context 无轮询等待任一候选变为可发送；NATS 在
本地连接 Ready 且目标已经发布后即可发送。非 Await 的 Notify/Async 保持快速失败，不建立
隐藏的无界等待队列。

### 3.9 Provider 一致性测试

M17 公开 `discovery/providertest` 契约测试和必要的假 Sink/状态观察工具。内置 Origin、
M18 etcd 及未来 Consul 都必须通过同一组基础行为：

- 首次快照、空快照、无变化快照；
- 发布、重复发布、撤销、重复撤销；
- 权威删除立即 Lost，控制断线先 Recovering、一个 TTL 后才批量 Lost；
- SessionID 替换、恢复全量对账和无伪事件；
- 严格配置、秘密信息脱敏、容量上限；
- Close 后无回调、无 goroutine 泄漏，并通过 Race。

后端特有协议仍由各 Provider 自己补充集成、故障和性能测试。公开测试包只固定公共契约，
不要求第三方实现 Origin、etcd 或 Consul 专属测试接口。

## 4. v2 对照

v2 的 Origin Discovery 使用：

- `MasterNodeList` 判断哪些 Node 自动注入 `DiscoveryMaster`；
- `LocalMasterNodeId` 指定当前 Node 只向哪个 Master 注册；
- Master 在内存中维护 Node 目录并通过 RPC 推送快照；
- NATS 模式通过 Ping 和 TTL 判断失联；
- TCP 模式主要依赖连接断开判断失联。

该实现可以完成按 Master 分区的发现，但多个 Master 之间没有选主、共识或完整目录复制，因此不能把 `MasterNodeList` 直接等同于高可用集群。v3 保留内置发现能力，不保留隐式 Master 角色和自动注入 Service 的方式。

## 5. Origin 内置发现

### 5.1 显式 `DiscoveryService`

框架提供保留名称 `DiscoveryService` 的内置 Service。它可以配置在任意 Node，并允许与
任意普通业务 Service 共存，不要求建立只能承载发现服务的专用 Node：

```yaml
nodes:
  - id: discovery-1
    rpc:
      transport: tcp
      tcp:
        listen: 0.0.0.0:7000
        advertise: 10.0.1.10:7000
    services:
      - DiscoveryService
      - AdminService
```

规则：

- 不提供 `IsMaster`；
- 不根据服务器列表隐式创建 Service；
- `DiscoveryService` 使用普通 Service 的构造、生命周期、调度、退休和优雅停止机制；
- `DiscoveryService` 是框架保留名称，业务不能注册同名 Service；
- 同一 Node 可以同时配置一个 `DiscoveryService` 和多个普通业务 Service；
- 其 RPC 契约是框架内部契约，不进入普通业务 RPC 广播和路由选择。

`DiscoveryService` 不再从普通 Service 业务配置读取 TTL。TTL 属于 Provider 后端协议，
统一位于顶层 `discovery.origin.ttl`。

### 5.2 客户端引导

使用 Origin Provider 时，项目必须在顶层显式配置发现服务器：

```yaml
discovery:
  type: origin
  origin:
    ttl: 15s
    server:
      node: discovery-1
      listen: 0.0.0.0:7100
      address: 10.0.1.10:7100
```

TCP 不能依赖尚未建立的服务发现查找 `DiscoveryService`，所以服务器 NodeID 和地址属于
必要的引导配置。只有 `server.node` 指定且实际配置了 `DiscoveryService` 的 Node 使用
`listen`；其他 Node 只使用 `address`。

M17 的 Origin 控制通道固定使用独立 TCP：

- 不再提供 `origin.transport` 配置；
- 复用 M5 的通用 TCP 基础组件，不复用业务 RPC Runtime、业务 TCP 连接或 RPC 线协议；
- 业务 RPC 使用 NATS 的 Node 也建立一条轻量 TCP 发现控制连接；
- 控制通道只承载发现数据，不桥接不同 Transport 的业务 RPC；
- 同一 Application 仍允许混合 TCP/NATS Node，但业务 RPC 只路由到 Transport 兼容目标；
- 控制监听地址不得与当前 Node 的业务 TCP Listener 冲突。

每个普通 Node 都根据顶层配置创建自己的 Provider 客户端；Provider 客户端、私有镜像、
心跳和取消函数均归对应 Node 所有。

同一进程同时启动发现 Node 和业务 Node 时，应把发现 Node 放在启动参数最前面：

```text
game-server start --app-name game-dev --node discovery-1,game-1
```

这样 `discovery-1` 先进入 `Ready`，Stop 时 Application 按实际启动顺序的严格倒序先停止 `game-1`，最后停止 `discovery-1`。

### 5.3 共置 Node 的自举边界

已确认 `DiscoveryService` 可以与普通业务 Service 共置，因此不能通过“发现 Node 不创建
Provider”规避自举。固定顺序为：

1. Node 仍先完成全部 Service 的纯 `OnInit`；
2. 框架在基础设施阶段识别 `DiscoveryService`，先 Prepare 独立控制 Listener；
3. Listener Ready 后启动当前 Node 自己的 Origin Provider，并通过该 Listener 完成首次
   权威同步；
4. 然后按原配置顺序执行全部 Service 的 `OnStart`，不强制把 `DiscoveryService` 调整到
   Service 列表第一位；
5. 任一后续启动失败时关闭 Provider 和已 Prepare 的控制 Listener，并执行既有严格反序
   回滚。

控制 Listener 属于保留系统 Service 的框架资源，Prepare 不执行用户回调、不开放业务
RPC，也不表示该 Node 已经发布。当前 Node 的所有普通 Service 仍只在全部 `OnStart`
成功后一次性发布。

如果同一 Application 选择了多个 Node，`server.node` 必须位于显式启动顺序第一位；
框架不静默重排用户顺序，顺序错误在启动前失败。这里限制的是启动顺序，不限制
`DiscoveryService` 与其他业务 Service 共置。

### 5.4 首版单实例规则

一个 Origin 发现域只配置一个 `DiscoveryService`。首版不支持多个 Master、Leader 选举、发现端复制或客户端合并多个发现源。

原因：

- 多实例会增加每个 Node 的控制连接；
- 需要处理重复快照、事件去重、会话冲突和不同发现源的版本比较；
- 需要定义网络分区、部分实例恢复和旧数据重新出现时的裁决；
- 测试矩阵会从单一注册/续约流程扩展到大量故障组合；
- 这些复杂度与首版“内置、轻量、不依赖中间件”的定位不匹配。

需要服务发现高可用的项目使用 etcd Provider，由 etcd 集群负责租约存储和一致性。

### 5.5 会话、TTL 与失效

- Node 每次启动生成随机会话 ID；
- 实例身份为 `NodeID + SessionID`；
- 相同 `NodeID + SessionID` 允许控制连接断开后重新绑定；
- 相同 NodeID 的旧控制连接仍活跃时，不同 SessionID 注册返回重复 Node 错误；
- 旧控制连接已经断开时，允许不同 SessionID 立即接管，不再等待旧 TTL；接管立即产生
  旧 Session `Lost` 和新 Session `Discovered`；
- 被接管的旧 Session 后续重连必须拒绝，不能反向覆盖当前活跃 Session；
- TTL 默认 `15s`，最小 `3s`；
- 心跳周期为 `TTL / 3`，最小 `1s`；
- TTL 判断使用单调时钟；
- 主动退休和正常停止通知唯一 `DiscoveryService`；
- 异常退出由 TTL 清理；
- `DiscoveryService` 连接中断时，Node 最多保留当前只读发现快照一个 TTL，不立即批量发布 `Lost`；
- 快照保留期间，TCP 连接断开等独立 Transport 事实仍可移除不可达路由；
- 超过一个 TTL 仍未恢复时，缓存实例过期并按正常差异规则发布 `Lost`；
- `DiscoveryService` 恢复后，Node 重新注册并以新的权威全量快照立即对账；快照中缺少的旧实例立即发布 `Lost`，不再增加第二段防抖 TTL；
- 发现服务不可用期间不能发现新 Node、接收退休变化或可靠判断 NATS 目标是否仍存活，相关状态必须暴露给监控。

单实例是发现控制面的单点，但不要求发现端短暂故障时立即中断所有既有 TCP RPC。生产环境应由 systemd、Kubernetes 等进程管理器自动拉起它；需要发现层自身高可用时使用 etcd。

### 5.6 初始全量、有序增量与背压

Origin 私有控制协议使用“首次全量、后续有序增量、缺口重新全量”：

- `DiscoveryService` 每次进程启动生成新的 `ServerEpoch`，当前 Epoch 内维护单调递增的
  `Revision`；
- 客户端完成注册后先取得 `ServerEpoch + Revision + FullSnapshot`；
- 后续注册、更新、主动撤销、Session 接管和 TTL 到期产生连续 Revision 的 Delta；
- Provider 先把 Delta 应用到自己的私有镜像，再向公共 Snapshot Sink 提交一份完整权威
  快照；
- Epoch 改变、Revision 不连续、帧校验失败或客户端本地镜像失效时，丢弃镜像并请求当前
  完整快照；
- 服务端不维护无限 Delta 历史，不能连续衔接时直接重新发送当前完整快照。

每条客户端连接只有一个固定有界发送队列。队列满时服务端关闭该慢连接，由客户端按恢复
流程重连并获取最新全量快照；不阻塞注册/TTL 处理，不静默丢 Delta，也不无限积累补发
历史。节点数、服务数、连接数、队列长度、单帧长度和完整快照大小的具体上限在 M17
容量批次统一冻结。

### 5.7 新 ServerEpoch 的权威收敛

`DiscoveryService` 为纯内存单实例。服务端重启后，各 Node 会陆续重新注册；如果第一条
注册到达就把当前部分目录宣布为权威，会把尚未来得及重连的健康 Node 错误发布为 `Lost`，
随后又发布 `Discovered`。

因此只有新 `ServerEpoch` 冷启动使用一次收敛窗口：

- 服务端立即接受注册，但先报告 `Warming`，不发布部分目录为权威 FullSnapshot；
- 窗口固定为 `min(TTL / 3, 5s)`，最低 `1s`，不增加业务配置项；
- 已持有旧快照的客户端保持 `Recovering` 并继续遵守原来的一个 TTL 本地过期时间；
- 新启动且没有旧快照的 Provider 等待窗口结束和首个权威全量后，才完成 `Start`；
- 窗口结束时服务端发布一份权威 FullSnapshot，此后注册、撤销、Session 接管和 TTL
  到期全部立即产生 Delta，不再使用收敛窗口；
- 如果客户端旧快照先达到一个 TTL，仍立即清空，冷启动窗口不能无限延长旧事实。

该窗口只解决“服务端刚重启时还没有重新收齐注册”的权威建立问题，不是对已确认实例变化
做防抖。

### 5.8 可信内网安全边界

M17 Origin Provider 定位为可信内网发现，首版不实现 TLS、mTLS、Token 或自定义 HMAC：

- `listen` 必须显式配置，不提供隐式公网监听默认值；
- 部署必须使用防火墙、安全组、容器 NetworkPolicy 等限制控制端口；
- 不能把控制端口直接暴露到公网或其他不可信网络；
- Session 冲突规则只解决实例所有权，不构成身份认证；
- 不实现“明文 Token”这种看似认证、实际可被窃取的半套安全方案；
- 需要现成认证、TLS 和高可用时使用 M18 etcd Provider。

未来增加 Origin 安全层时在独立 TCP `net.Conn` 外包装标准 TLS，不修改 Provider SPI、
Full/Delta 语义、Directory、RPC 或业务 API；安全能力应作为独立里程碑完整设计，不能在
M17 预留未使用字段。

## 6. etcd Provider

### 6.1 配置外观

```yaml
discovery:
  type: etcd
  etcd:
    endpoints:
      - https://etcd-1.example.com:2379
      - https://etcd-2.example.com:2379
      - https://etcd-3.example.com:2379
    namespace: /origin/game-prod
    local_network: cn-east
    watch_networks:
      - cn-east
      - cn-north
    ttl: 15s
    dial_timeout: 5s
    request_timeout: 5s

    auth:
      username: origin
      password: change-me
      token: ""

    tls:
      ca_file: certs/etcd-ca.pem
      cert_file: certs/origin-client.pem
      key_file: certs/origin-client-key.pem
      server_name: etcd.example.com
      insecure_skip_verify: false
```

### 6.2 支持场景

- 单 endpoint 和 etcd 集群多 endpoint；
- 明文 HTTP；
- 使用系统根证书的 HTTPS；
- 自定义 CA 的 HTTPS；
- 双向 TLS；
- 无认证、用户名/密码认证和 Token 认证；
- 单网络和关注多个网络；
- Kubernetes ConfigMap/Secret 以文件片段挂载到配置目录。

### 6.3 校验和默认值

- `endpoints` 至少一个，且不得混用 HTTP 与 HTTPS；
- `namespace` 必须是非根绝对前缀；
- `ttl` 默认 `15s`，最小 `3s`；
- `dial_timeout` 默认 `5s`；
- `request_timeout` 默认 `5s`，只限制一次 etcd 操作；
- `cert_file` 与 `key_file` 必须同时配置；
- `token` 与 `username/password` 互斥；
- HTTPS 没有 `ca_file` 时使用系统根证书；
- `insecure_skip_verify` 默认关闭，启用时输出一次明确警告；
- TLS 相对路径统一相对于配置根目录解析；
- 密码、私钥内容和认证 Token 不得写入日志、错误详情或配置转储。

首版不暴露 etcd Client 的 gRPC KeepAlive、Endpoint 自动同步、自定义 DialOption、内部日志器和消息大小等高级字段。框架固定安全默认值，避免配置与具体 etcd 依赖版本耦合；真实部署出现明确需求后再增加独立高级配置。

### 6.4 运行规则

- 每个 Node 持有自己的 etcd Client、Lease、Watch 和取消函数；
- 同一 Node 内复用一个 Client，不按操作创建连接；
- 注册 Key 绑定租约，续约失败后重新授予 Lease 并注册；
- Watch 必须以“初始 Range 快照 + Revision 后续 Watch”避免查询与监听之间丢事件；
- Watch 压缩或断流时使用有上限并带抖动的退避持续重建，直到 Application Stop；确定性
  鉴权、权限或配置错误立即报告，不伪装成普通网络抖动；
- 退休状态通过同一租约 Key 更新；
- 正常停止先发布退休/注销，再撤销 Lease 并关闭 Client；
- Provider goroutine 只生成内部变化，不直接执行 Service 业务代码。

## 7. 已确认结论与待确认项

已确认：

1. 框架内置 `origin` 和 `etcd`，不实现 `static`，同时允许 Application 注册自定义 Provider；
2. Origin 内置发现端显式配置为保留名称 `DiscoveryService` 的普通 Service；
3. 一个 Origin 发现域首版只允许一个 `DiscoveryService`，但它可以与任意业务 Service
   配置在同一 Node；
4. 默认 TTL 为 `15s`，心跳周期为 `TTL / 3`；
5. 需要服务发现高可用时使用 etcd；
6. etcd 只公开部署场景所需字段，不直接暴露底层 Client 调优项；
7. Discovery Provider 配置位于顶层，整个项目只选择一套方案；
8. Application 不共享 Provider 实例或连接，每个 Node 根据顶层配置独立实例化并拥有自己的资源；
9. 公开 SPI 只有一个包、一个注册入口和最小 Factory/Provider 契约，复杂状态机由框架承担；
10. Provider 只提交完整权威快照，框架统一校验、差异和事件；
11. 控制连接断开立即报告 Recovering，但只在一个 TTL 后仍未恢复时清空旧快照；
12. 权威删除和恢复后的全量对账立即产生变化，不做事件防抖；
13. `AwaitService` 不混入 Transport 状态，Await RPC 自己等待可发送 TCP 候选；
14. M17 提供公开一致性测试，未来 Consul 必须通过同一公共契约；
15. Origin 控制通道固定使用独立 TCP，不复用业务 RPC Transport、连接或协议；
16. Origin 内部同步使用首次全量、连续 Revision Delta 和缺口全量重建；
17. 相同 NodeID 的活跃旧连接阻止新 Session；旧连接断开后新 Session 可以立即接管；
18. 慢客户端队列满时断开并通过全量重连恢复，不阻塞服务端或静默丢 Delta；
19. `DiscoveryService` 可以与业务 Service 共置，框架先 Prepare 控制 Listener，再完成
    当前 Node Provider 首次同步，最后按原顺序执行全部 `OnStart`；
20. 新 ServerEpoch 使用一次 1～5 秒固定收敛窗口，不能把部分重注册目录冒充权威快照；
21. M17 Origin Provider 只支持可信内网明文控制通道，不实现 TLS、认证或预留安全字段。

待确认：

1. Origin 私有 Wire 的具体字段、编码和版本拒绝规则；
2. 节点、服务、连接、队列、帧和快照容量上限；
3. 控制连接超时、退避和配置默认值。

## 8. 官方实现依据

- etcd 的 TLS 部署支持服务端验证、自定义 CA 和客户端证书认证：[etcd Transport security model](https://etcd.io/docs/v3.7/op-guide/security/)；

## 9. 里程碑顺序更新

2026-07-29 已确认先以 M14 实现 Transport 无关的 Node 本地发现目录、关注筛选、不可变
可见快照和监听基础。本文定义的 Origin 与 etcd Provider 不混入 M14，后续只通过 M14
冻结的完整原始快照入口提供数据。

原 M14 NATS RPC 顺延为 M15；原 M15 完整停止顺延为 M16。M17 实现公共 Provider
契约与 Origin，M18 在不修改公共契约的前提下增加 etcd。该调整不改变本文已确认的单实例
Origin 发现端和 etcd 部署能力。
