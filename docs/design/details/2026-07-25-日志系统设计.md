# Origin 第三版日志系统设计

> 文档状态：已确认，M1 开工 Review 已通过
> 创建日期：2026-07-25  
> 最后更新：2026-07-26

## 1. 目标

日志是 Origin v3 的前置基础库，在框架主体实现前完成最小可用版本。首版目标是：

- 为 Application、Node、Service、RPC、网络和调度器提供统一结构化日志；
- 满足游戏服务器低延迟场景，减少关闭日志和结构化编码产生的额外开销；
- 控制台与文件使用相互独立的日志级别；
- 支持显式打印当前程序调用栈；
- 普通结构化日志的编码和活动日志文件写入由独立日志协程执行；
- 支持异步投递和等待写完两种调用模式；
- 在不拖慢普通日志热路径的前提下，尽量降低异常退出时的日志丢失；
- 支持自定义输出编码或完全替换底层日志库；
- 保持接口精简，不把文件滚动、远程日志、Trace 和 Profiler 混入日志核心。

## 2. 实现选择

v3 默认使用 Zap，不同时维护 slog 和 Zap 两套实现。M1 固定使用 `go.uber.org/zap v1.28.0`；这是 2026-07-25 复核时的最新正式版本，使用 MIT 许可证，复核依据见 [Zap v1.28.0 Release](https://github.com/uber-go/zap/releases/tag/v1.28.0) 与该版本的 [LICENSE](https://github.com/uber-go/zap/blob/v1.28.0/LICENSE)。Origin 在 Zap 外提供稳定的 Logger 门面，业务代码和框架其他模块不直接依赖 Zap 类型。

核心代码使用非 Sugared Logger 和类型化字段，不在热路径使用 `printf` 风格接口。日志由 Application 创建并向 Node、Service 等组件派生，禁止重新建立 v2 的全局可变 Logger。

底层日志库通过精简的 Handler 扩展点替换：

```go
type Handler interface {
    Enabled(level Level) bool
    Write(record Record, fields []Field) error
    Sync() error
    Close() error
}
```

业务始终使用 Origin 的具体 `Logger`，不直接持有 Handler。Origin 只内置 Zap Handler；使用者可以在 Application 启动时注入其他日志库的 Handler 适配器。

- `log` 定义稳定的公共 Config、Level、Field、Record、Handler、Logger、Runtime、Stats 和 Crash 控制，不导入 Zap；
- `log/zaplog` 实现默认 Zap Handler，可以依赖 `log`，反向依赖被禁止；
- `log/internal/rotate` 是文件滚动和归档的内部共享实现，不进入业务 API；
- 不使用 `init()`、Zap 全局 Encoder 注册表或 Origin 包级可变注册表。

`Record` 至少包含：

```go
type Record struct {
    Time    time.Time
    Level   Level
    Message string
    Caller  Caller
    Stack   string
}

type Caller struct {
    PC   uintptr
    File string
    Line int
}
```

替换边界遵守：

- `Level`、`Record` 和 `Field` 由 Origin 定义，禁止在公共接口暴露 `zap.Field`；
- 常用 Field 使用明确类型，只有显式 `Any` 允许进入反射兼容路径；
- `ErrorStack`、级别判断和固定字段派生由 Origin Logger 统一提供；
- `Enabled` 会被多个业务协程并发调用，Handler 必须保证它并发安全；
- `Write` 只由日志协程串行调用，`Sync`、`Close` 只由日志生命周期控制路径调用，自定义 Handler 不需要为这些方法重复加锁；
- `Write` 返回后 Handler 不得继续引用 `Record`、`fields` 或其中由日志事件拥有的临时内存；确需异步保留时必须自行复制；
- 支持启动时选择 Handler，不支持运行时替换 Handler；
- 运行时只允许调整实现明确支持的日志级别；
- 默认 Zap Handler 的字段转换成本必须通过 Benchmark 验证。

调用者文件名、行号和显式堆栈由 Origin Logger 门面统一确定，而不是由各 Handler 猜测包装层深度。这样替换日志库后仍能得到一致的调用位置。

Origin Logger 通过 Application 级日志调度器把 Record 和 Field 投递给独立日志协程。Handler 的 `Write` 只由日志协程调用。`With` 是 Origin Logger 的不可变派生能力，不下沉到 Handler；自定义 Handler 通过 `Sync` 和 `Close` 接入 Application 生命周期。

公共构造与生命周期 API 固定为：

```go
// package log
func DefaultConfig() Config
func NewRuntime(config Config, handler Handler) (*Runtime, error)
func NewNop() Logger

func (r *Runtime) Logger() Logger
func (r *Runtime) Stats() Stats
func (r *Runtime) Flush(ctx context.Context) error
func (r *Runtime) Close(ctx context.Context) error

// package zaplog
func New(config log.Config, options ...Option) (*log.Runtime, error)
func NewHandler(config log.Config, options ...Option) (log.Handler, error)
```

`Stats` 是值快照，首版字段固定为：

```go
type Stats struct {
    DroppedDebug          uint64
    DroppedInfo           uint64
    DroppedWarn           uint64
    DroppedError          uint64
    WriteFailures         uint64
    ReliableWriteTimeouts uint64
}
```

`Logger` 不包含 Flush、Close 或 Handler 访问能力；`Runtime` 是日志协程和 Handler 的唯一生命周期所有者。`Stats()` 返回不可变计数快照，至少用于观察各级别丢弃数和输出失败数，不暴露内部队列。`zaplog.New` 是使用内置实现的简洁入口，`log.NewRuntime` 用于注入自定义 Handler。

Application、Node 和 Service 可以通过 `With` 派生一个自动携带固定字段的新 Logger。例如：

```go
appLogger := rootLogger.With(
    log.String("application", "game"),
)

nodeLogger := appLogger.With(
    log.String("node_id", "gateway-1"),
)

serviceLogger := nodeLogger.With(
    log.String("service", "PlayerService"),
)

serviceLogger.Info("service started")
```

上面的日志自动包含：

```text
application=game
node_id=gateway-1
service=PlayerService
```

`With` 返回新的 Logger，不修改父 Logger，也不保存 Application、Node 或 Service 对象引用。它只保存这些稳定字段，避免每条日志重复填写，并降低漏写 `node_id`、`service` 等定位信息的概率。

只对生命周期内保持不变的字段使用 `With`。RPC 的 `request_id`、`contract`、`method`、`target`、`duration`、错误码，以及 `player_id` 等随请求变化的字段，必须只在对应日志调用中追加，不能写入 Service Logger。

### 2.1 公共调用外观

首版 Logger 提供：

```go
logger.Enabled(level)
logger.Log(level, message, fields...)
logger.Debug(message, fields...)
logger.Info(message, fields...)
logger.Warn(message, fields...)
logger.Error(message, fields...)
logger.ErrorStack(message, fields...)
logger.With(fields...)
logger.WithCallerSkip(skip)
```

`Log` 用于日志级别由配置或参数动态决定的通用组件。普通业务优先使用 Debug、Info、Warn 和 Error，使调用点的严重程度直接可见。

包级提供 `log.NewNop()`。Nop Logger 只用于单元测试或明确禁用日志的组件，不创建协程或文件。正常 Config 的所有输出均关闭仍然返回配置错误，不能静默创建 Nop Logger。

首版类型化 Field 构造函数为：

```go
log.String(key, value)
log.Bool(key, value)
log.Int(key, value)
log.Int32(key, value)
log.Int64(key, value)
log.Uint(key, value)
log.Uint32(key, value)
log.Uint64(key, value)
log.Float32(key, value)
log.Float64(key, value)
log.Duration(key, value)
log.Time(key, value)
log.Bytes(key, value)
log.Err(err)
log.Any(key, value)
```

`Err` 使用固定字段名 `error`。稳定错误码使用独立数值字段记录，例如 `log.Uint32("error_code", uint32(errs.CodeOf(err)))`。`Any` 属于需要反射和调用方快照的慢路径，不用于框架热路径。

## 3. 日志级别

首版只对外提供：

```text
Debug
Info
Warn
Error
```

框架库禁止调用 `Fatal`、`Panic`、`DPanic` 或 `os.Exit`。不可恢复错误由日志记录后向上返回，最终是否结束进程由 Application 入口决定。

每个输出端都有独立的最低级别：

```yaml
log:
  console:
    enabled: true
    level: info
    format: json

  file:
    enabled: true
    level: debug
    format: json
    path: logs/origin.log
```

建议默认值为：

- 模式：`async`；
- 控制台：开启，级别为 `Info`，格式为 `text`；
- 文件：默认关闭；
- 文件启用后的默认级别：`Debug`，保留更完整的现场信息；
- 内置输出格式同时支持 `json` 和 `text`；
- 内置文件路径默认使用 `logs/origin.log`；
- 部署模板可以显式开启文件输出，不能因为文件不可写导致静默丢失控制台日志。

`log.DefaultConfig()` 返回上述完整有效配置。`log.Config{}` 不表示默认配置，构造时返回 `errs.CodeInvalidConfig`；首版不对零值字段逐项静默补默认值，避免无法区分显式关闭和忘记初始化。普通使用方式是先取得默认配置再修改：

```go
config := log.DefaultConfig()
config.File.Enabled = true
config.File.Path = "logs/origin.log"

runtime, err := zaplog.New(config)
```

注入自定义 Handler 时，`log.NewRuntime` 只校验公共 Runtime 配置和 Handler 非 nil；具体输出字段由 Handler 的构造函数校验。`zaplog.New` 组合并校验完整控制台和文件配置，两个输出均关闭时返回 `errs.CodeInvalidConfig`。

### 3.1 JSON 格式

`format: json` 表示每条日志编码为一行独立 JSON 对象，即 JSON Lines，不把整个日志文件编码为一个 JSON 数组：

```json
{"time":"2026-07-25T10:30:00.123+08:00","level":"info","msg":"service started","node_id":"game-1"}
```

JSON 格式适合 Kubernetes、Loki、ELK 和其他日志采集系统。字段名和字段类型必须稳定，字符串中的换行和特殊字符由编码器正确转义。

### 3.2 Text 格式

`format: text` 表示每条日志编码为一行便于开发者直接阅读的文本：

```text
2026-07-25 10:30:00.123 INFO service started node_id=game-1
```

Text 格式仍然保留结构化字段，不退化为任意 `printf` 文本。字段值中的空白、换行和特殊字符必须正确转义，保证一条普通日志只占一行；显式堆栈字段可以使用受控的多行内容。

### 3.3 自定义输出格式

M1 不支持基于字符串占位符的任意格式模板，但支持注册自定义 Encoder。

只需要改变输出格式、仍然使用 Zap 时，在 Zap Handler 适配包中注册 Encoder：

```go
handler, err := zaplog.NewHandler(
    config,
    zaplog.WithEncoder("ecs", newECSEncoder),
)
```

配置可以引用已经注册的名称：

```yaml
format: ecs
```

自定义 Zap Encoder 的类型只出现在 Zap Handler 适配包，不进入 Origin Logger、Field、Record 或业务代码。需要完全替换日志库时，实现 Origin Handler，由该 Handler 自行决定编码方式。

注册是构造期、实例级行为：

```go
type EncoderFactory func(zapcore.EncoderConfig) (zapcore.Encoder, error)

func WithEncoder(name string, factory EncoderFactory) Option
```

- Option 只作用于本次 `zaplog.New` 或 `zaplog.NewHandler`，不修改全局状态；
- `json`、`text` 是保留名称；空名称、重复名称、覆盖保留名称或 nil factory 都返回 `errs.CodeInvalidConfig`；
- factory 在构造 Handler 时按实际启用的输出端调用，每个输出端获得独立 Encoder；
- factory 失败时构造失败，并逆序清理已经打开的文件等资源；
- Handler 关闭后，不再持有本次构造产生的 Encoder 和输出资源。

因此扩展边界为：

- 使用 `json`、`text`：直接使用内置 Zap Handler；
- 自定义格式但继续使用 Zap：注册自定义 Encoder；
- 替换 Zap：注入自定义 Handler。

### 3.4 文件扩展名

内置文件输出默认并推荐使用：

```yaml
path: logs/origin.log
```

`.log` 表示这是日志文件，不代表其内部编码。即使 `format: json`，文件仍保留 `.log`，因为其内容是逐行 JSON，而不是一个完整 JSON 文档。滚动后的名称也保留 `.log`，例如：

```text
origin.log
origin-2026-07-25T23-59-59.123.log.gz
```

自定义 Handler 不受该文件名约定限制。

### 3.5 调用文件与行号

所有实际输出的内置日志都必须包含调用文件名和行号，统一使用 `caller` 字段：

```json
{"level":"info","caller":"service/player.go:128","msg":"service started"}
```

```text
2026-07-25 10:30:00.123 INFO service/player.go:128 service started
```

调用位置必须满足：

- 指向真正调用 `Debug`、`Info`、`Warn`、`Error` 或 `ErrorStack` 的业务或框架代码；
- 不能指向 Origin Logger 门面、Zap Handler 或字段转换代码；
- 使用相对于工程或包的短路径，不输出构建机器的完整绝对路径；
- `ErrorStack` 同时包含 `caller` 和 `stack`，堆栈的第一条业务帧与 caller 一致；
- 日志级别未启用时，不能解析调用位置；
- `caller` 是框架保留字段，普通 Field 不能覆盖。

Logger 内部维护固定包装层深度。确实需要在业务侧继续包装日志方法时，可以通过不可变派生方法调整额外深度：

```go
helperLogger := logger.WithCallerSkip(1)
```

`WithCallerSkip` 返回新 Logger，不修改父 Logger。它只面向日志辅助封装，不应在普通业务调用中使用。调用位置解析的成本需要纳入日志 Benchmark。

控制台和文件不能先经过一个共同最低级别再分流，必须分别构建 Zap Core 和 LevelEnabler，再使用 Tee 组合。否则较高的控制台级别可能错误过滤掉本应写入文件的 Debug 日志。

日志库的默认控制台格式为 Text。Kubernetes 部署模板应显式把控制台格式配置为 JSON，并保留明确的 `level` 字段。控制台可将 `Error` 写入 stderr，将 `Debug`、`Info`、`Warn` 写入 stdout；两条范围必须互斥，禁止同一日志重复输出。

## 4. 显式堆栈日志

“是否携带堆栈”不是新的日志级别。普通 `Error` 默认不携带完整调用栈，只有调用显式接口时才采集堆栈，避免每个错误都承担堆栈采集和大文本输出成本。

首版接口外观：

```go
logger.Debug("rpc request received", fields...)
logger.Info("service started", fields...)
logger.Warn("send queue is nearly full", fields...)
logger.Error("rpc failed", fields...)
logger.ErrorStack("unexpected scheduler state", fields...)
```

`ErrorStack` 的级别固定为 `Error`，并额外写入 `stack` 字段。严重程度写在方法名中比单独的 `Stack` 更清楚，也避免增加 `Stack(level, ...)` 这种可变外观。

如果未来存在 Warn 级堆栈的明确场景，再根据实际使用情况决定是否增加 `WarnStack`，首版不提前扩展。

实现必须遵守：

- 在调用 `ErrorStack` 的原始协程中采集一次堆栈并写入 `Record.Stack`，日志协程和 Zap Handler 只负责输出该快照；
- 不修改 Logger 或 Core 上的共享 `stack` 开关；
- 正确补偿 Origin 日志包装层的调用深度；
- 先进行 Error 级别检查，所有输出端都不接收时不采集堆栈；
- 堆栈日志属于异常慢路径，允许为清晰和并发安全发生少量临时分配；
- 同一条带栈日志经过控制台和文件 Core 时只采集一次堆栈。

v2 通过临时修改 Logger 中共享的 `stack bool` 控制 `AddStacktrace`。该方式在并发日志下可能发生竞态，v3 禁止沿用。

## 5. 文件滚动与保留

文件输出同时支持按大小滚动和按日期滚动。两种触发条件作用于同一个活动文件，任意条件满足就滚动一次，不能建立两份内容相同、滚动规则不同的文件输出。

建议配置外观：

```yaml
log:
  file:
    enabled: true
    level: debug
    format: json
    path: logs/origin.log

    rotation:
      max_size: 512M
      by_date: true
      timezone: Local

    retention:
      max_age: 14d
      max_files: 30
      compress: true
```

以上是 M3/M7 接入后的文件配置外观。M1 已实现的独立 Go API 仍使用其明确单位的 `MaxSizeMB`、`MaxAgeDays` 字段；框架装配层负责把 `ByteSize` 和 `Duration` 校验并换算后传入，避免破坏已完成里程碑的公开 API。

具体语义：

- 每条日志记录默认使用操作系统本地时区显示时间，并保留时区偏移；
- `rotation.timezone` 只控制自然日边界与归档文件时间，不改变日志记录的显示时区；
- `max_size > 0B` 时启用大小滚动；
- `by_date: true` 时按配置时区的自然日边界滚动，不按“进程启动后每 24 小时”计算；
- `timezone` 首版只接受 `Local` 或 `UTC`，不支持任意 IANA 时区；
- 进程跨过日期边界后，在第一条新日志写入前完成日期滚动；
- 大小和日期同时触发时只滚动一次；
- `max_age > 0s` 时删除超过期限的归档；
- `max_files > 0` 时只保留最近指定数量的归档；
- 保留期限和保留数量同时配置时，任意清理条件满足即可删除；
- `compress` 只压缩已经滚动的归档，不压缩当前活动文件；
- 当前活动文件始终使用 `path` 指定的稳定名称，归档文件名包含滚动时间；
- 同一个日志文件只允许一个进程写入。不同进程不得配置相同文件路径。

实现采用一个 Origin 内置的滚动文件 Writer：

- 日志协程串行执行活动文件的日期检查、大小检查、关闭、重命名、打开和写入，不再为这一层增加互斥锁；
- 滚动后只向一个 Application 级归档维护协程提交“需要维护”的合并信号，由它执行归档扫描、期限和数量清理以及可选 gzip 压缩；
- 维护信号可以合并，归档协程每次都以目录当前状态为准，因此不会因为重复或合并信号漏掉归档；
- 归档名发生同毫秒冲突时追加递增序号，禁止覆盖已有归档；
- gzip 先写同目录临时文件，成功关闭后再原子改名；只有压缩文件完整生成后才删除原归档，启动时清理或重试上次异常退出留下的临时文件；
- Application 关闭时先停止活动文件写入，再等待归档维护结束并关闭文件；
- 首版不采用 Lumberjack。最终 Review 发现其 v2/v3 都会启动无法通过 `Close` 停止的内部维护协程，与 Origin 的重复启停和无 goroutine 泄漏要求冲突；
- 不使用 v2 的 `file-rotatelogs`，该项目已经归档；
- 该 Writer 只实现本节已经确认的能力，不扩展为通用文件系统或备份框架。

文件滚动属于文件 Handler 内部能力，不进入 Logger、Field 和自定义 Handler 的公共语义。自定义 Handler 是否支持文件滚动，由其自身决定。

## 6. 日志协程与投递

### 6.1 执行边界

每个 Application 创建一个日志调度器和一个日志协程。所有 Logger 派生实例共享该调度器。

Service 工作协程只执行：

1. 判断对应级别是否启用；
2. 预占日志队列槽位；
3. 记录时间和调用位置；
4. `ErrorStack` 时采集当前调用栈；
5. 把 Record 和 Field 复制到日志事件拥有的内存；
6. 将事件提交给日志协程。

以下工作只能在日志协程执行：

- JSON、Text 或自定义 Encoder 编码；
- Zap Handler `Write`；
- 普通日志的 stdout、stderr 和活动文件 I/O；
- 活动文件滚动。

不能为每条日志创建 goroutine。caller 和当前 goroutine 的 stack 无法延迟到日志协程采集，因此仍然属于调用协程的必要成本。

常用类型 Field 复制为日志事件拥有的值。`Any` 等可能引用可变对象的字段必须在提交前序列化为不可变快照，不能把可能继续变化的对象指针交给日志协程。因此 `Any` 是“编码在调用协程执行”的明确例外和显式慢路径；框架热路径禁止使用 `Any`。

### 6.2 两种调用模式

生产环境使用异步模式：

```yaml
log:
  mode: async
```

`Debug`、`Info`、`Warn` 和普通 `Error` 成功入队后立即返回，不等待 Encoder 或 Writer。只有显式 `ErrorStack` 是可靠性例外：它等待日志协程完成所有已启用 Writer 的本次写入后再返回，但不为每条带栈错误执行磁盘 `fsync`。这样不会让可能形成故障风暴的普通 Error 阻塞 Service；需要可靠记录的严重异常必须明确使用 `ErrorStack`。

异步模式下 `ErrorStack` 的等待使用内部固定上限 `1s`，首版不增加配置项。超过上限时累计可靠写出失败指标，尝试一次不经过 Logger 的最小 stderr 兜底后返回，不能永久占住 Service 执行槽。`1s` 是异常慢路径的保底值，不是正常日志延迟目标；实现后必须用磁盘故障和阻塞 Writer 测试验证。

首版不在 YAML 暴露队列容量。M1 内部固定默认容量为十进制 `10000` 条事件，并通过事件实际大小、突发日志量和 Benchmark 记录其内存与延迟基线。如果数据表明需要调整，必须先与开发者确认；只有真实项目数据证明固定容量不适用时，再增加明确归类为高级调优项的配置。

开发环境使用等待写完模式：

```yaml
log:
  mode: sync
```

`sync` 仍然由日志协程执行编码和 I/O，但调用方会等待该事件完成。日志方法返回时已经完成所有启用 Writer 的调用，方便在下一行设置断点查看日志。

### 6.3 队列满

日志队列必须有界。异步模式下，`Debug`、`Info`、`Warn` 和普通 `Error` 遇到队列满时：

- 丢弃当前新日志，保留已经进入 FIFO 队列的事件；
- 不等待队列空位；
- 不退化为调用协程同步写日志；
- 不创建临时 goroutine；
- 按级别累计原子丢弃计数；
- 队列恢复后由日志协程直接输出丢弃汇总；
- 丢弃计数同时暴露给监控指标。

`ErrorStack` 和同步模式遇到队列满时等待空位，并等待本次写入完成，不执行普通丢弃策略。异步模式的 `ErrorStack` 等待受 `1s` 上限和 Logger 关闭状态共同控制；超时或 Logger 已经停止准入时，改走第 7 节定义的最后可用 stderr 兜底。开发用同步模式本身允许等待 I/O，Application 关闭时仍由 `Close(ctx)` 限制总时间。

### 6.4 输出规则

- M1 不向使用者暴露第二套输出字节缓冲配置；
- 日志协程编码一条日志后直接调用对应 Handler Writer；
- stdout 阻塞、磁盘异常和文件滚动只会阻塞日志协程；
- 输出变慢可能使事件队列逐渐填满，但不能把 I/O 转移回 Service 工作协程；
- 文件跨自然日时，日志协程在处理新一日第一条日志前执行 Rotate；
- 归档清理和压缩由唯一、可停止的归档维护协程处理，它不编码或写入活动日志；
- Handler `Write` 返回错误时，日志调度器累计输出失败指标，并使用不经过 Logger 的最小 stderr 兜底，避免递归写日志；
- 如果 Benchmark 证明逐条 Writer 调用成为瓶颈，优先在日志协程内部增加批量写入，不新增普通业务必须理解的配置字段。

### 6.5 自定义 Handler

- 自定义 Handler 的 `Write` 也只由日志协程调用；
- 自定义 Handler 不应再次建立事件队列，避免双重排队和关闭顺序复杂化；
- 自定义 Handler 必须使用目标日志库的同步写入入口；可以使用由 `Write`、`Sync` 驱动的字节缓冲，但不能再启动后台日志投递或输出 goroutine；
- `Sync` 刷新已经接收但尚未写出的数据；
- `Close` 关闭 Handler 持有的文件等资源；
- `Close` 返回后不能再次调用 `Write`。

### 6.6 错误码

日志库只增加两个可由调用方稳定处理的错误码：

- `errs.CodeLogClosed`：Runtime 已经关闭，不能再接受 Flush 屏障或其他生命周期操作；
- `errs.CodeLogOutputFailed`：默认输出的创建、Sync 或 Close 失败，底层原因只保留在本地 cause。

配置错误复用 `errs.CodeInvalidConfig`，Context 取消和超时复用 `errs.CodeCanceled`、`errs.CodeDeadlineExceeded`。普通日志方法不返回 error；满队列和异步 Write 失败通过 `Stats`、指标和最小 stderr 兜底观察，不为每种文件系统错误继续增加固定错误码。

## 7. 异常退出与日志可靠性

### 7.1 能够保障的路径

v3 采用分层可靠性，不使用 WAL，也不对每条日志执行 `fsync`：

1. 普通 `Debug`、`Info`、`Warn` 和 `Error` 保持低延迟异步投递，进程突然终止时队列尾部可能丢失；
2. 普通 `Error` 仍保持异步；显式 `ErrorStack` 在内部 `1s` 上限内等待日志协程实际调用 Writer，显著缩小关键异常只停留在内存中的窗口且不会无限阻塞 Service；
3. 正常收到 `SIGTERM`、`SIGINT` 或 Application Stop 时，先完成 Node、Service 停止，再关闭日志准入、排空队列、执行 `Sync` 和 `Close`；
4. 框架拥有的 goroutine 在可恢复边界捕获 panic 时，先提交 `ErrorStack`，再以短 Deadline 调用日志 Runtime 的 `Flush(ctx)`；如何处置 panic 仍由所属运行时规则决定，日志系统不负责吞掉 panic；
5. M1 提供基于 `runtime/debug.SetCrashOutput` 的显式进程级安装能力，把未捕获 panic 和 runtime fatal 除 stderr 外再写入独立的 `origin.crash.log`。该文件保存 Go runtime 原始崩溃文本，不混入 JSON Lines 活动文件；
6. Logger Runtime 和 Zap Handler 不自动注册 Crash 输出。M14 最终进程入口在显式启用内置文件输出时，默认按活动日志路径派生 `logs/origin.crash.log` 并安装一次；文件输出默认关闭时不会安装。

日志 Runtime 的 `Flush(ctx)` 语义是：向日志协程提交屏障，等待屏障前的事件完成，然后执行 Handler `Sync`。它不关闭 Logger，可以由进程级异常处理或测试使用。`Flush` 和 `Close` 只由 Application 持有，不组合进业务 Logger，避免 Service 或 Module 误关共享日志设施。正常关闭使用 `Close(ctx)`，其顺序见第 9 节。

独立 crash 文件以追加方式打开。日志包公开：

```go
// package log
func InstallCrashOutput(fileConfig FileConfig) (*CrashOutput, error)
func (output *CrashOutput) Close() error
```

该 API 明确修改进程级状态。只有最终可执行程序入口可以持有一个 `CrashOutput`，每个 Application、Logger Runtime 和 Handler 都不得自行安装。安装前，如果旧 crash 文件已经超过活动日志的 `max_size`，先按相同命名规则滚动；旧 crash 归档复用期限、数量和压缩规则。`SetCrashOutput` 成功后关闭安装过程打开的原始文件句柄，由 Go Runtime 持有复制后的描述符。正常关闭时由进程所有者调用幂等 `Close()` 取消注册。文件描述符与替换行为以 Go 标准库 [`runtime/debug.SetCrashOutput`](https://pkg.go.dev/runtime/debug#SetCrashOutput) 的契约为准。

同一进程只允许一个 Crash 输出所有者。重复安装属于调用者违反所有权约束；为遵守“禁止包级可变全局状态”，日志包不增加隐式全局注册表。Go 的 `SetCrashOutput` 只支持一个额外文件，后一次注册会替换前一次注册，因此最终入口必须严格维持唯一所有权。

因为一次 fatal 后进程已经结束，不在运行期间为 crash 文件增加第二套滚动调度器，只在下一次安装前处理旧文件。M1 完成 Crash 文件、滚动、保留、压缩和注册的独立能力；M14 只负责把该能力接入最终进程生命周期。

### 7.2 无法完全保障的路径

以下情况无法由进程内异步日志系统保证不丢失：

- `SIGKILL`、硬 OOM Kill、宿主机断电或内核/硬件故障；
- 业务或第三方代码直接调用 `os.Exit`；
- 日志文件系统本身损坏、只读、空间耗尽或阻塞超过关闭 Deadline；
- 已经由 Writer 交给操作系统、但尚未持久化到存储介质的数据。

若要求断电后也逐条不丢，只能引入同步 `fsync`、WAL 或进程外可靠日志代理，这会明显增加延迟与复杂度，不进入 M1。Kubernetes 部署必须给 `SIGTERM` 后的 Application Stop、日志排空和 `Sync` 留出足够的 termination grace period；最终 `SIGKILL` 只是保底，不是正常关闭方式。

独立 crash 文件是 runtime 紧急输出通道，属于“所有业务日志经日志协程输出”规则的唯一例外。文件打开失败时仍保留 runtime 原有的 stderr 崩溃输出。

## 8. 热路径规则

- 正常 RPC 成功不默认记录 Info 日志；
- 单请求明细只在 Debug 开启时记录；
- 构造代价较高的字段前先检查对应级别是否启用；
- 日志级别未启用时不解析 caller；
- 使用类型化字段，不在框架热路径使用反射字段和 Sugared Logger；
- 异步模式不隐藏级别判断、事件复制、caller 和显式 stack 的成本；
- 重复网络和 RPC 错误支持采样或限流，防止故障时形成日志风暴；
- 不默认打印完整 Protobuf 请求、响应、令牌和其他敏感数据；
- 不持有 Service 调度锁或网络队列锁执行可能阻塞的文件写入；
- Error 和 ErrorStack 不替代统一错误码，日志必须尽量携带稳定错误码；
- `ErrorStack` 会在最多 `1s` 内等待实际写出，禁止把它当作高频业务分支日志；
- 普通异步日志的可靠性、延迟和内存占用必须一起 Benchmark，不能只追求吞吐。

## 9. 生命周期

- Application 创建根 Logger；
- Node 和 Service 从父 Logger 派生固定字段；
- 启动失败时仍能使用已经初始化的控制台输出；
- Logger 是 Application 最后停止的基础设施。必须先停止所有 Node 和 Service，允许它们在排空及 `OnStop` 中继续记录日志；
- Node 和 Service 全部停止后，Application 调用日志 Runtime 的 `Close(ctx)`：停止新日志准入、排空已接受事件、执行 Handler `Sync`、停止并等待归档维护协程，最后执行 Handler `Close`；
- Service 和 Node 不各自关闭共享 Logger；
- `Sync` 或 `Close` 失败作为关闭错误向上返回或写入最后可用的 stderr，不能递归写日志；
- `Close` 必须幂等，部分初始化失败时也能安全调用。

## 10. M1 范围

M1 必须实现：

- 固定 `go.uber.org/zap v1.28.0` 的 Zap 基础 Logger；
- 可替换 Handler 与自定义 Zap Encoder；
- 控制台和文件独立开关、级别和 `json`、`text` 编码；
- `Log`、`Debug`、`Info`、`Warn`、`Error` 和 `ErrorStack`；
- 显式 Nop Logger；
- String、Bool、常用数值、Duration、Time、Bytes、Err 和 Any 类型化 Field；
- 文件名与行号 caller，以及日志辅助封装使用的 `WithCallerSkip`；
- 固定字段派生；
- 级别快速判断；
- 可独立创建和关闭的单日志 Runtime 及其日志协程，M7 再由 Application 持有；
- 异步投递和等待写完两种模式；
- 有界事件队列、异步满队列丢弃计数与关闭排空；
- 调用方统一 `Sync` 和 `Close`；
- `ErrorStack` 可靠写出、`Flush(ctx)` 和独立 crash 文件；
- 单一文件 Writer 的大小与按日滚动；
- 按期限、数量保留和可选压缩；
- 日志配置校验；
- `DefaultConfig()` 有效、`Config{}` 拒绝以及文件默认关闭；
- 实例级自定义 Encoder 注册；
- `CodeLogClosed` 和 `CodeLogOutputFailed`；
- M1 只接受 Go `Config` 结构体，不依赖 M3；本文 YAML 示例到 M3/M7 集成时再接入；
- 并发写入和竞态测试；
- 关闭级别日志与带字段日志的基础 Benchmark。

M1 暂不实现：

- slog 适配器；
- 远程日志；
- 运行时动态增加任意输出端；
- Trace 和 Profiler；
- 按 Service 单独创建日志文件；
- 运行时热更新完整日志配置。

## 11. 验收要求

1. 控制台 `Info`、文件 `Debug` 时，Debug 只进入文件，Info 同时进入两端。
2. 控制台与文件的启用状态和级别可以独立配置。
3. 控制台和文件分别使用 `json`、`text` 的全部组合都能正确输出。
4. JSON 输出为一行一个合法 JSON 对象，Text 普通日志保持一条一行。
5. 默认文件使用 `logs/origin.log`，JSON 编码不改变 `.log` 扩展名。
6. 所有已输出日志的 `caller` 都指向实际调用代码的短文件路径和行号。
7. 使用 `With` 和 `WithCallerSkip` 派生后，caller 仍然正确。
8. 被级别过滤的日志不解析 caller。
9. `Error` 不带完整堆栈，`ErrorStack` 带一个正确调用栈。
10. 并发调用 `Error` 和 `ErrorStack` 不发生竞态或相互污染。
11. 输出端全部过滤 Error 时，`ErrorStack` 不采集堆栈。
12. Kubernetes 控制台 JSON 中包含可检索的 `level`、`caller`、`node_id`、`service` 和错误码字段。
13. Logger 关闭由 Application 统一管理，Node 和 Service 停止不会提前关闭共享输出端。
14. `go test -race` 通过，并保存关闭日志、普通字段日志、caller 和堆栈日志的分配基线。
15. 达到大小上限时只滚动一次，活动文件继续正常写入。
16. 跨越配置时区的自然日后，第一条日志写入新文件。
17. 大小与日期同时满足时不生成重复空文件。
18. 保留期限、保留数量和压缩分别生效，并且不会删除当前活动文件。
19. 所有普通 Encoder、Handler、控制台和活动日志文件 I/O 只在日志协程执行；只有 `Any` 快照、归档维护、最小 stderr 故障兜底和 runtime crash 输出属于文档明确列出的例外。
20. 异步模式的 `Debug`、`Info`、`Warn` 和普通 `Error` 入队后返回，队列满时不阻塞并能观测丢弃计数。
21. 同步模式由日志协程写入，但调用方等待事件完成。
22. 默认 Handler 不要求使用者理解或配置第二套输出缓冲。
23. 跨自然日时在新一日第一条日志写入前滚动文件。
24. 自定义 Encoder 可以用于控制台或文件，自定义 Handler 可以完全替换 Zap。
25. Application 关闭能够排空事件、执行 `Sync` 并关闭文件句柄。
26. 保存异步入队、同步等待、队列满、逐条输出和跨日滚动的延迟与分配基线。
27. 异步模式下 `ErrorStack` 不执行普通满队列丢弃策略：在 `1s` 内完成所有启用 Writer 的 `Write`，或者超时后记录指标并走最小 stderr 兜底；普通 `Error` 仍保持非阻塞异步语义。
28. `Flush(ctx)` 等待屏障前日志并调用 Handler `Sync`，超时能够返回且不会死锁。
29. 正常 Stop 后队列排空，归档维护协程和日志协程都能结束，重复创建、关闭 Application 不发生 goroutine 泄漏。
30. 未捕获 panic 的 runtime 崩溃文本同时出现在 stderr 和独立 crash 文件；crash 文件失败不影响 stderr。
31. `Record.Time`、caller 和 stack 都表示原始调用点，而不是日志协程处理事件的时间和位置。
32. `Config{}` 被拒绝，`DefaultConfig()` 可以直接创建仅控制台输出的默认 Runtime。
33. 两个日志 Runtime 使用同名自定义 Encoder 时互不污染，关闭后无全局注册残留。
34. Logger Runtime 和 Handler 不隐式调用 `SetCrashOutput`；显式安装和重复关闭 CrashOutput 均通过测试。
