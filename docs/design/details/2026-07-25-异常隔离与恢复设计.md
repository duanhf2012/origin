# Origin 第三版异常隔离与恢复设计

> 文档状态：推荐方案，待开发者确认  
> 创建日期：2026-07-25  
> 最后更新：2026-07-25

## 1. 目标

本设计处理 Go `panic`、框架拥有的 goroutine 异常和业务回调异常。目标是：

- 单个 RPC、Timer、事件或扩展回调 panic 时，不直接带崩整个进程；
- 捕获点少而明确，不在每层重复 `recover`；
- Service 单执行槽在 panic 后能够正确归还，不形成永久卡死；
- Await、RPC、异步回调等任务发生 panic 后一定完成，不能让调用方永远等待；
- 启动和停止阶段发生 panic 时仍执行可安全完成的回滚与清理；
- 本地保留完整堆栈，对远端只返回统一错误码；
- 不把 runtime fatal、内存损坏等不可恢复问题伪装成“已经恢复”。

## 2. v2 对照与需要修正的问题

v2 已经在 Service Release、Timer、Event、并发 Worker、RPC、网络模块等位置使用 `defer/recover`，这说明“业务回调异常不能直接结束整个进程”的方向是正确的。

v3 不直接沿用以下实现：

- 恢复代码散落在不同包，日志内容和后续行为不一致；
- 部分位置只打印堆栈，没有完成当前任务或归还调度状态；
- `GoRecover(callback, -1)` 可以无限重新启动持续 panic 的函数，形成 CPU 和日志风暴；
- 多层嵌套恢复可能重复打印同一个 panic；
- 无法区分业务回调 panic 与调度器内部不变量损坏；
- 无法捕获业务自行通过原生 `go` 创建的其他 goroutine 中的 panic。

v3 采用统一边界和统一完成语义，不提供通用的“panic 后无限重启”能力。

## 3. Go 的恢复边界

`recover` 只能捕获同一个 goroutine 调用栈中正在展开的 panic。Application 在主 goroutine 中增加一个顶层 `recover`，不能捕获其他 goroutine 的 panic。

因此必须遵守：

1. 每个由 Origin 创建的 goroutine 都有且只有一个最外层 goroutine 保护边界；
2. Service Runner 在每个业务任务调用边界恢复业务 panic；
3. 生命周期、路由选择器和其他用户扩展点在各自最外层用户代码调用边界恢复；
4. 不在同一调用链的多个层级重复恢复同一个 panic；
5. 业务直接创建的原生 goroutine 不在 Origin 的保护范围内。

Service 业务需要并行等待时应使用 `Await`、异步 RPC 或框架任务，不应为了规避顺序调度自行创建 goroutine。首版不提供可能诱导业务并发访问 Service 状态的通用 `SafeGo`。

## 4. 两类 panic

### 4.1 用户代码 panic

以下调用由框架明确包围，因此可以恢复：

- RPC 业务处理函数；
- Timer、Ticker、Cron 回调；
- 同步或异步本地事件处理函数；
- Async 完成回调；
- Service 和 Module 生命周期回调；
- 自定义路由、发现监听器和其他插件扩展点；
- 自定义程序命令回调。

用户代码 panic 只让当前调用失败，框架内部状态仍由调用边界负责收尾。

### 4.2 框架内部 panic

调度器队列、执行槽、pendingCall、网络帧和对象所有权等框架内部代码，不使用业务回调的 `recover` 包围。

框架内部 panic 到达所属组件的 goroutine 边界时：

1. 使用最后可用的日志和 stderr 记录 panic 与堆栈；
2. 将 Node 或 Application 标记为 `Failed`；
3. 触发受 Deadline 限制的统一停止和资源清理；
4. 清理完成后返回非零进程退出码。

框架内部不变量已经损坏时，继续处理业务可能扩大数据损坏。异常捕获在这里用于“留下现场并优雅收尾”，不承诺进程继续提供服务。

## 5. 统一恢复器

框架内部只维护一个精简恢复实现。概念外观如下：

```go
type PanicInfo struct {
    Value     any
    Stack     []byte
    Component string
    Operation string
}
```

`PanicInfo` 是诊断数据，不通过 RPC 线协议发送。恢复器必须：

1. 在原 goroutine 的 deferred 函数中调用 `recover`；
2. 立即复制当前 panic 堆栈；
3. 补充 Application、Node、Service、Module、任务类型和 RequestID 等已有上下文；
4. 只记录一次 `ErrorStack`；
5. 调用当前边界的完成函数，归还执行槽、完成 Future 或返回生命周期错误；
6. 清空可能持有大对象的临时引用。

panic 属于异常慢路径，允许堆栈复制和错误对象产生少量分配，不为它引入对象池。

## 6. Service 任务 panic

Service Runner 只在调用具体业务任务的位置安装恢复边界，Runner 循环和调度器内部代码不放在该边界内。

业务任务 panic 后：

1. 当前任务立即结束，不再执行该任务 panic 点之后的代码；
2. 当前任务归还 Service 唯一执行槽；
3. 入站 RPC 返回 `CodeInternal`，Message 使用固定安全文本，不包含 panic 值、堆栈和文件路径；
4. Async 调用完成对应 Future，并以 `CodeInternal` 调用完成回调；
5. Notify 和异步本地事件没有远端返回，只记录失败；
6. Ready 队列中的后续任务仍可继续执行；
7. Waiting 任务恢复后仍进入相同业务任务边界。

首版推荐沿用 v2 的可用性方向：普通业务任务 panic 只终止当前任务，Service 继续运行。框架不提供事务回滚，panic 前已经完成的业务状态修改不会自动撤销。因此关键状态修改仍应通过正常错误返回、数据库事务或业务补偿保证一致性，不能依赖 panic 恢复。

首版不增加 `continue/stop_service/stop_application` 多档配置。若真实项目证明“某类 Service panic 后必须立即失败停止”，再设计 Service 级策略，避免现在增加一套难以验证的状态分支。

## 7. Timer、事件和扩展点

- 一次性 Timer 回调 panic 后按已经触发完成处理；
- Ticker 或 Cron 回调 panic 后自动取消当前定时器，避免同一错误无限重复；
- 同步事件的某个监听器 panic 后终止本次监听器调用，不再从 panic 点继续；
- 异步事件按一个普通 Service 任务处理；
- 自定义路由选择器 panic 返回已经定义的路由选择失败错误；
- Discovery 监听器 panic 只终止当前通知，不破坏 Provider 主循环；
- 扩展点 panic 后是否继续调用同一事件的后续监听器，由该扩展点自己的既有顺序语义决定，不能由通用恢复器隐式改变。

## 8. Await 和 Future

Await 本身不依赖 panic 作为控制流。

如果负责执行阻塞函数的外部 goroutine panic：

1. 外部执行边界恢复 panic；
2. Future 以 `CodeInternal` 完成；
3. Waiting 任务进入 Ready 队列；
4. 原 Service goroutine 恢复后从 `Await` 返回错误；
5. pending、Deadline 和计数只清理一次。

如果 Service 任务在 Await 返回后 panic，按普通 Service 任务 panic 处理。无论在哪一侧 panic，都不能遗留永远无法完成的 Future。

## 9. 生命周期 panic

### 9.1 OnInit 和 OnStart

`OnInit`、`OnStart` 或对应 Module 回调 panic，等价于返回 `CodeInternal`：

- 当前组件启动失败；
- 不继续启动依赖它的后续组件；
- 已经成功启动的组件按既定逆序回滚；
- 当前回调 panic 前创建且尚未注册给框架的资源，仍只能由业务自己的局部 `defer` 清理。

### 9.2 OnStop

`OnStop` 或 Module 停止回调 panic 时：

- 记录本地堆栈并加入停止聚合错误；
- 不再次执行已经 panic 的回调；
- 继续停止其他 Module、Service 和 Node；
- 最终仍关闭调度器、网络、日志等框架资源。

### 9.3 Application 入口

命令 Runner 和 Application Run 入口各自只有一个顶层恢复边界：

- Application 尚未启动时，panic 转成启动错误并执行已注册资源的逆序清理；
- Application 运行中主控制路径 panic 时，状态转为 `Failed` 并触发统一 Stop；
- 清理后向命令 Runner 返回非零退出码；
- 顶层恢复不负责捕获其他 goroutine 的 panic。

## 10. 日志、错误码和观测

- panic 使用日志系统的 `ErrorStack` 或传入已经捕获堆栈的等价内部入口；
- 本地日志至少包含 `application`、`node_id`、`service`、`component`、`operation`、任务类型和可用的 RequestID；
- panic 值必须安全转成文本，禁止调用可能再次 panic 的复杂格式化逻辑；
- RPC 统一返回 `CodeInternal`，不新增对外 `CodePanic`；
- 本地聚合错误可以保留 panic cause 和堆栈引用，但线协议不发送；
- 每个恢复边界累计低基数 panic 计数，标签只使用组件类别和操作类别，不使用玩家 ID、RequestID 等高基数字段；
- 重复 panic 日志可以按堆栈指纹限流，但计数不能采样丢失。

## 11. 不可恢复情况

以下情况不能依赖 `recover`：

- runtime 主动抛出的 fatal error；
- 栈溢出；
- 严重内存不足或操作系统 OOM Kill；
- `SIGKILL`、断电和硬件故障；
- cgo 或其他非 Go 代码破坏进程状态；
- 业务原生 goroutine 没有自己的恢复边界。

这些情况由独立 crash 文件和 stderr 保存 runtime 现场，具体规则见[日志系统设计](./2026-07-25-日志系统设计.md)。

## 12. M16 范围

M16 实现：

- Application、Node 基础设施 goroutine 的最外层保护；
- Service 单任务业务边界；
- RPC Dispatcher、Await 外部执行函数和 Future 完成保护；
- `OnInit`、`OnStart`、`OnStop` 生命周期边界；
- `CodeInternal` 转换和本地堆栈日志；
- panic 后任务、执行槽、pendingCall 和资源只完成一次；
- 禁止通用无限自动重启。

Timer、事件、Module 和 Discovery 的具体恢复接入随对应能力进入后续里程碑，但统一遵守本文边界。

## 13. 验收要求

1. 一个 RPC handler panic 不结束进程，并向调用方返回 `CodeInternal`。
2. panic 后 Service 执行槽被归还，后续任务可以继续执行。
3. Await 外部函数 panic 后 Future 正常完成，原任务不会永久 Waiting。
4. `OnStart` panic 触发已启动组件逆序回滚。
5. `OnStop` panic 不阻止剩余组件清理。
6. 框架内部 goroutine panic 触发 Application 失败和受控停止，而不是继续处理业务。
7. 同一个 panic 只记录一次完整堆栈。
8. 远端错误不包含堆栈、文件路径和 panic 内部值。
9. Ticker 或 Cron 回调 panic 后不会无限重复执行。
10. 不存在 panic 后未完成的 pendingCall、未归还执行槽和 goroutine 泄漏。
11. 业务原生 goroutine 的限制在开发文档中明确说明。
12. `go test -race`、故障注入和 goroutine 泄漏检查通过。
