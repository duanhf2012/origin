# Origin 第三版应用与节点生命周期设计

> 文档类型：详细设计储备

## 1. 文档状态

- 状态：已确认
- 确认日期：2026-07-22
- 最后更新：2026-07-26
- 适用版本：Origin v3
- 讨论范围：Application、Node 的所有权关系、网络隔离、启动选择、启停顺序及失败处理

本文记录已经确认的设计结论。RPC 契约、服务发现与连接筛选、Service 执行模型将在各自的设计文档中单独讨论，不在本文中提前确定。

## 2. 背景

Origin v2 的运行层级为 Node、Service、Module，一个进程只能启动一个 Node。Node 标识、Cluster、Service 注册表和信号处理等状态由包级全局对象持有，因此无法在同一进程中安全地创建多个彼此独立的 Node。

Origin v3 需要在 Node 之上增加 Application。Application 作为程序启动和停止的管理单元，可以在同一个操作系统进程内承载并管理多个 Node。开发环境可利用这一能力在单个进程中启动多个 Node；生产环境仍以“一个进程运行一个 Node”为主要部署方式。

开发环境的多 Node 运行必须尽量复现生产环境的网络行为和启停时序，避免因为共享连接、内存短路或并行启停而掩盖只会在真实部署中出现的问题。

## 3. 目标

1. 建立清晰的 `Application → Node → Service → Module` 所有权层级。
2. 一个 Application 可以配置多个 Node，并可在启动时选择其中一个或多个 Node。
3. 多个 Node 在同一进程中运行时仍保持身份、服务、网络和生命周期隔离。
4. 各 Node 顺序启动、按实际启动顺序的严格倒序停止，模拟生产环境逐个启停程序的行为。
5. 显式传入 Node 时使用启动参数中的顺序；未传入时使用配置中的声明顺序。
6. 配置错误、启动失败和停止失败均有明确且可测试的处理规则。

## 4. 非目标

本文不确定以下内容：

- RPC 使用代码生成还是运行时注册；
- 服务发现的关注规则及 TCP 连接筛选策略；
- Service 的单协程、多协程和协作式调度模型。

这些内容与 Application 生命周期存在接口关系，但会在后续设计中分别确认。

## 5. 核心层级与职责

### 5.1 Application

Application 对应一个正在运行的操作系统进程，是程序级生命周期管理器。业务只需调用
无参数的 `app.Start()`；Application 在内部承接命令参数和运行 Context。它负责：

- 加载并校验框架和 Node 配置；
- 创建并持有本次选中的 Node；
- 根据内部收到的启动参数或 Node 声明顺序确定本次实际启动顺序；
- 记录成功启动的 Node，并据此生成严格倒序的停止顺序；
- 按顺序启动、停止和回滚 Node；
- 接收程序级退出信号，并触发统一停止流程；
- 汇总 Node 启停过程中产生的错误和状态。

Application 不负责：

- 合并多个 Node 的身份；
- 合并多个 Node 的 TCP/NATS 连接状态；
- 直接持有某个 Node 的 Service 或 Module；
- 绕过 Node 的生命周期直接操作其内部对象。

### 5.2 Node

Node 是独立的逻辑运行单元。每个 Node 独立持有：

- 唯一 Node ID；
- Service 注册表和 Service 实例；
- RPC 服务端、RPC 客户端及连接管理状态；
- 服务发现状态和路由状态；
- Node 级配置与生命周期状态。

Node 不再依赖包级全局单例保存运行状态。同一个 Application 中的两个 Node 必须能够独立启动、停止、失败和释放资源。

为了保留 v2 简洁的 `Setup` 外观，最终可执行程序可以在多个 `init_*.go` 的 `func init()`
中，对自己明确持有的 Application 实例调用 `app.Setup`，登记当前实例可用的 Service Go
类型。类型目录由该 Application 持有，不保存传入的类型样本对象；每个 Node 根据配置创建
独立 Service 实例。Origin 不建立包级默认 Application 或 Service 目录，不同 Application
仍完全隔离。

### 5.3 Service 与 Module

Service 只属于一个 Node，Module 只属于一个 Service 或其 Module 子树。禁止 Service 或 Module 通过包级全局运行实例注册表隐式访问其他 Node 的对象；只读 Service 类型目录不能用于取得运行实例。跨 Node 交互统一通过后续确定的 RPC 与路由抽象完成。

## 6. 网络隔离原则

### 6.1 每个 Node 拥有独立网络端点

生产环境主要采用一个进程运行一个 Node。为了让开发环境能够暴露与生产环境相同的问题，即使多个 Node 位于同一个 Application 中，每个 Node 仍应拥有独立的监听地址、连接管理器和连接生命周期。

Application 不共享单一 TCP 监听端点，也不把多个 Node 复用到同一条 Application 级连接中。

### 6.2 同进程 Node 之间不自动短路

默认开发和集成测试模式下，同一 Application 内不同 Node 之间的调用仍经过真实配置的 TCP 或 NATS 传输，不自动替换为内存直接调用。这样可以覆盖：

- 单个 Node 独立断线和重连；
- 连接建立与关闭时序；
- Node 级背压、拥塞和超时；
- Node 级握手、鉴权和发现状态变化；
- 一个 Node 失败而同进程其他 Node 继续运行；
- 多连接之间的竞争和资源上限。

如果未来增加 `inproc` 传输，它必须是显式启用的测试能力，不能替代默认集成测试和生产等价性验证。

## 7. Node 选择

启动入口可以指定一个 Node、多个 Node 或全部 Node。未被本次启动的 Node 不参与启动、停止和失败回滚。

示例配置：

```yaml
nodes:
  - id: node_a
  - id: node_b
  - id: node_c
  - id: node_d
```

配置中不建立 `application`、`start_order` 或 `stop_order` 字段。Application 只是读取顶层 Node 配置并管理多个 Node 运行的进程内对象。

## 8. 有效启动顺序

Application 按以下规则生成本次启动顺序：

1. 命令行显式传入 `--node node_c,node_a` 时，严格按参数从左到右启动 `node_c`、`node_a`；
2. 未传入 `--node` 时，按顶层 `nodes` 的声明顺序启动全部 Node；
3. 不把未写入 `--node` 的 Node 自动追加到本次启动列表；
4. NodeID 两侧空白可以清理，空项、重复项和未知 NodeID 在创建任何 Node 前返回参数错误。

对于上面的配置：

```text
--node node_c,node_a  =>  node_c → node_a
未传入 --node        =>  node_a → node_b → node_c → node_d
```

Application 必须顺序启动 Node，不并行启动。前一个 Node 完成启动并进入 `Ready` 状态后，才能启动下一个 Node。

Node 内部先启动 Transport、RPC Runtime 和服务发现等基础设施，再执行业务 Service 的 `OnStart`。Service 可以在 `OnStart` 中等待已经启动的远端 Node，但不能依赖有效启动顺序中尚未开始的后续 Node；否则会等待到启动 Context 结束并导致 Node 启动失败。详细规则见 [Service 启动与就绪设计](./2026-07-24-服务启动与就绪设计.md)。

Node 进入 Ready 后，运行期 RPC Transport 的 Recovering/Failed 不修改 Node 生命周期状态；
Node 和 Application 继续保持 Ready/Running，入站健康、重连和发现发布情况由
`Node.TransportStatus()` 单独表达。运行期出现无法恢复的 Failed Service 同样不立即触发
Stop；Application 保存首次根因，正式 Stop 完整清理后返回失败并使用退出码 `1`。

生命周期 Ready 不等于外部探针 Ready。全部公开 Service 都进入 Failed，或者 TCP Listener、
NATS 整体 RPC 能力进入 Recovering 时，Node 仍保持生命周期 Ready 且进程存活，但外部
就绪为失败；恢复后自动恢复外部就绪。TCP 单个远端目标连接断开只影响该目标路由，不改变
当前 Node 的整体就绪。Origin 不因此自行 Stop 或重启进程。

Node 通过 `HealthStatus()` 返回 Liveness、Readiness、Degraded 和 ErrorCode 四字段无锁
快照。部分公开 Service Failed 时仍保持就绪但标记 Degraded；Retired 不视为故障；没有
公开 Service 的内部 Node 不会被空集合误判为全部失败。必需 Discovery Provider 不可用时
返回 `CodeDiscoveryUnavailable` 并取消就绪，恢复发布后自动恢复。单次超时、队列过载和
已经恢复的任务 panic 不改变健康状态。

### 8.1 Node 内 Service 顺序

一个 Node 中多个 Service 的顺序只使用 `nodes[].services` 配置声明顺序，不再增加独立的
`service_start_order` 或 `service_stop_order`：

1. 所有 Service 按配置顺序依次执行 `OnInit`；
2. 单个 `OnInit` 失败不跳过后续 Service；全部调用结束后按配置顺序聚合错误；
3. 只要存在 `OnInit` 错误，当前 Node 就不调用任何 `OnStart` 或业务 `OnStop`；
4. 全部 `OnInit` 成功后，再启动 Node 运行期基础设施并按同一配置顺序依次执行 `OnStart`；
5. 前一个 Service 的 `OnStart` 返回后，才能进入后一个 Service；
6. 真正进入过 `OnStart` 的 Service，包括最终返回错误的 Service，按进入顺序记录到启动列表；
7. 正常 Stop 和启动失败回滚都按该实际启动列表的严格倒序执行 `OnStop`；
8. 配置中没有声明的 Service 即使已通过 `app.Setup` 注册类型，也不会被当前 Node 创建或
   加入启停顺序。

例如：

```yaml
nodes:
  - id: game-1
    services:
      - DBProxyService
      - PlayerService
      - SceneService
```

固定顺序为：

```text
启动：DBProxyService -> PlayerService -> SceneService
停止：SceneService -> PlayerService -> DBProxyService
```

该规则使依赖 Service 放在配置前面即可先启动、后停止，与 Node 之间使用启动顺序和严格
倒序停止的规则保持一致。

## 9. 有效停止顺序

Application 不接受独立停止顺序配置。停止顺序固定为本次“实际成功启动顺序”的严格倒序：

1. 每个 Node 进入 `Ready` 后才追加到成功启动列表；
2. 收到 Stop 时，从成功启动列表末尾向前逐个停止；
3. 启动失败回滚时，同样倒序停止此前已经成功启动的 Node；
4. 没有成功进入 `Ready` 的 Node 不在该列表中，其部分资源由自身启动失败清理路径释放。

例如：

```text
启动：node_c → node_a
停止：node_a → node_c
```

Application 必须顺序停止 Node，不并行停止。前一个 Node 完成停止并进入 `Stopped` 状态后，才停止下一个 Node。

如果业务 Node 的 Service 在 `OnStop` 中需要调用 `DBService` 存档，应把 DB Node 放在启动参数的前面，使 DB Node 在严格倒序停止时自然位于后面。被依赖 Node 在依赖方 `OnStop` 完成前保持可路由；不能先让所有 Node 同时退休，再依赖普通 RPC 完成存档。Service finalizer、Await 和基础设施保活规则见 [Origin v3 Service 优雅停止设计](./2026-07-24-服务优雅停止设计.md)。

## 10. 生命周期状态

Application 至少应能观察 Node 的以下状态：

- `Created`：对象已经创建，尚未开始启动；
- `Starting`：正在初始化和启动；
- `Ready`：启动完成，可以提供服务；
- `Stopping`：正在停止并释放资源；
- `Stopped`：停止和资源释放完成；
- `Failed`：启动或运行过程失败。

状态转换必须由 Node 自身管理，Application 只发出生命周期命令并观察结果，不能直接修改 Node 内部状态。

## 11. 配置校验

Application 在创建任何 Node 之前完成全部静态校验。以下情况属于配置错误，Application 必须拒绝启动：

- `nodes` 中存在重复或空的 Node ID；
- 启动入口指定了配置中不存在的 Node ID；
- 启动参数中存在空或重复 Node ID；
- 同一 Application 内启用 TCP 传输的多个 Node，其监听地址发生冲突。

配置采用严格未知字段检查；旧的 `start_order`、`stop_order` 或 `application` 字段必须直接返回配置错误，不能静默忽略。

## 12. 错误与回滚

### 12.1 启动失败

任意 Node 启动失败时：

1. Application 立即停止启动后续 Node；
2. 保留失败 Node、失败 Service、生命周期阶段和原始错误链；
3. 逆序遍历本次已经成功启动的 Node；
4. 按倒序逐个停止这些 Node；
5. 返回包含启动错误和回滚错误的聚合结果；
6. 最外层 `app.Start()` 在全部回滚结束后打印一次 Error 日志，并以非零退出码结束程序。

失败 Node 如果已经分配了部分资源，必须由其自身启动失败处理负责释放；Application 不越过 Node 边界清理其内部资源。

`OnInit` 返回非 nil error 明确属于 Node 启动失败。Node 继续按配置顺序完成其余 Service
的纯 `OnInit`，然后使用 `errors.Join` 聚合全部初始化错误；当前 Node 不进入 `OnStart` 或
`Ready`，也不调用任何业务 `OnStop`。Application 必须停止此前已经成功启动的所有 Node。
Service 和 Node 只包装并返回错误，不在每一层重复打印同一个 error。

`OnStart` 返回非 nil error 同样属于 Node 启动失败。当前失败 Service 与此前真正进入过
`OnStart` 的 Service 均按进入顺序的严格反序执行一次 `OnStop`；清理错误加入最终聚合结果，
但不能覆盖原始启动错误。框架库不在错误点直接调用 `os.Exit`，最外层只在全部清理和日志
刷新完成后决定非零退出码。

Application 在启动过程中收到 Stop 或进程信号时，不再启动新的 Node 或进入新的 Service
生命周期回调。当前无 Context 的 `OnInit` 返回后停止后续初始化；Transport 重试和当前
`OnStart` 通过 startCtx 取消；已经进入过 `OnStart` 的 Service 与已经 Ready 的 Node 仍按
严格反序清理。单纯由 Stop 取消且清理成功时属于正常退出，退出码为 `0`；Stop 到达前已经
存在真实启动错误时仍保留该错误并使用退出码 `1`。

### 12.2 停止失败

任意 Node 停止失败时，Application 记录错误，但仍继续停止倒序列表中的后续 Node。全部停止尝试结束后，Application 返回聚合错误。单个 Node 的停止失败不能阻止其他 Node 释放资源。

### 12.3 重复命令

对已经 `Ready` 的 Node 重复执行启动，或对已经 `Stopped` 的 Node 重复执行停止，统一按幂等成功处理，不得触发第二套并发生命周期流程，也不得重复分配或重复释放资源。Node 处于 `Starting` 或 `Stopping` 等过渡状态时收到不兼容的生命周期命令，应返回明确的状态错误。

## 13. 与 Origin v2 的兼容关系

v3 保留 Node、Service、Module 的概念和总体层级，在 Node 之上新增 Application。兼容目标
是保留用户对这些概念的理解及主要功能，并允许继续在业务 `init_*.go` 中用接近 v2 的
`app.Setup` 登记 Service 类型，最终由无参数 `app.Start()` 启动；v3 不复用 v2 全局保存
可变 Service 实例的实现。

生产环境只选择一个 Node 启动时，Application 仍然存在，但其有效启停顺序中只有一个 Node。这样单 Node 与多 Node 使用同一套入口和生命周期逻辑，避免形成两套实现。

## 14. 验收标准

后续实现至少需要通过以下验证：

1. 一个 Application 能在同一进程中依次启动多个拥有独立端口的 Node。
2. 多 Node 运行时不存在共享 Node ID、Service 运行实例注册表或连接状态；Application 私有只读类型目录只能用于分别创建实例。
3. 未传入 `--node` 时，启动使用顶层 `nodes` 声明顺序，停止使用实际启动顺序的反序。
4. 传入多个 NodeID 时，严格使用参数顺序启动，并以其实际成功启动顺序的反序停止。
5. 选择部分 Node 启动时，只启动选中 Node，不自动追加其他 Node。
6. Node 的任一 Service `OnInit` 返回 error 后仍完成当前 Node 其余纯 `OnInit` 并聚合错误，
   但不会进入任何 `OnStart` 或启动后续 Node；Application 停止此前已经成功启动的全部
   Node，最外层打印聚合错误并以非零退出码结束。
7. 任一 `OnStart` 返回 error 后，当前失败 Service 与此前进入过 `OnStart` 的 Service 严格
   反序执行 `OnStop`，再回滚此前已经 Ready 的 Node。
8. 启动中收到 Stop 后不再进入新的生命周期回调；纯取消且清理成功使用退出码 `0`。
9. Node 停止失败不会阻止其他 Node 的停止，最终可以获得完整聚合错误。
10. 同一 Application 内不同 Node 的 TCP/NATS 调用不会自动变为内存直接调用。
11. 配置中出现未知字段、重复或地址冲突的 Node，或者启动参数出现未知、空、重复 NodeID 时，在创建 Node 前返回错误。
