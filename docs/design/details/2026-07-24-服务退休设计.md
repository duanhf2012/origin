# Origin 第三版服务退休设计

> 文档类型：详细设计储备

## 1. 文档状态与范围

- 状态：本文范围内的方案已确认
- 首次确认：2026-07-24
- 最后更新：2026-07-30
- 适用版本：Origin v3

本文只规定 Service 退休状态，以及退休与正式停止之间的状态边界。

2026-07-29 最新确认覆盖早期“退休自动拒绝新入站 RPC”的方案：`Retired` 只是一项框架
维护并对外发布的可观察状态。Origin 不因退休自动拒绝 RPC、摘除路由、暂停 Timer 或进入
停止流程，具体业务行为由项目决定。

2026-07-30 的 M19 只增加自动摘流例外：`ToService` 自动实例选择排除 Retired；
`ToServiceOnNode` 精确调用、普通入站准入、发现可见性和连接需求保持不变。

本文暂不确定：

- `Retire`、`Resume` 的最终公开 API 外观；
- `OnRetire`、`OnResume` 等状态钩子的名称和调度顺序；
- Node 与 Application 的退休编排。

## 2. 设计目标

1. 提供一个介于正常运行和正式停止之间的稳定、可观察状态；
2. 业务可以用该状态表达维护、迁移、人数控制或临时降级；
3. 框架不替业务猜测哪些 RPC、Timer 或事件应当停止；
4. 只有明确收到 Stop 信号，Service 才进入正式关闭流程；
5. 其他 Node 可以通过服务发现观察状态并自行调整业务；
6. 状态语义简单，不把退休、摘流、排空和停止绑定成隐式流程。

## 3. 状态模型

```text
Running  -> Retired
Retired  -> Running     仅由明确恢复操作触发
Running  -> Stopping    仅由明确 Stop 信号触发
Retired  -> Stopping    仅由明确 Stop 信号触发
Stopping -> Stopped
```

`Retired` 是稳定运行状态：

- 不会因任务排空自动进入 `Stopping`；
- 不会自动关闭 Service、Transport、Timer 或其他资源；
- 不会自动调用 `OnStop`；
- 没有 Stop 或 Resume 信号时可以一直保持 `Retired`。

## 4. 状态切换

状态切换必须在 ServiceScheduler 的有序控制边界内完成：

1. 把状态从 `Running` 原子切换为 `Retired`，或从 `Retired` 切回 `Running`；
2. 更新状态进入时间和统计；
3. 向 Discovery Provider 发布最新状态；
4. 通过服务发现状态事件通知本地监听者。

状态锁内不能调用用户代码、执行网络操作或直接回调发现监听器。状态发布和业务回调使用
各自既有的异步边界。

## 5. RPC、事件和后台任务

`Running` 与 `Retired` 使用相同的框架准入规则：

- 请求—响应 RPC 正常进入 Service Ready 队列；
- Notify 和 Broadcast 正常投递；
- 单目标选择和自动路由不会排除退休实例；
- Service 可以继续发起出站 RPC、Redis 和数据库访问；
- 本地同步、异步事件正常执行；
- Timer、Await 恢复和异步结果回调正常执行；
- TCP/NATS 连接不会仅因退休关闭。

业务需要摘流时，在自己的 RPC 实现、路由策略或状态钩子中明确处理。例如业务可以查询
当前 Service 状态后返回统一的 `errs.ErrServiceRetired`，也可以只拒绝登录类 RPC、继续
允许存档和管理 RPC。Origin 不在通用 Dispatcher 中增加退休判断。

这种边界避免框架统一拒绝后，业务无法在退休期间完成迁移、存档、管理或恢复操作。

## 6. Timer 行为

Service 退休时不自动暂停或取消任何 Timer。业务需要暂停某个 Timer 时，保存其 TimerID
并显式调用：

```go
PauseTimer(timerID TimerID) bool
ResumeTimer(timerID TimerID) bool
```

框架不猜测 Timer 属于流量入口、后台维护还是状态保存。

## 7. 与正式 Stop 的边界

只有明确 Stop 信号可以使 `Running` 或 `Retired` 进入 `Stopping`。进入 `Stopping` 后才
执行：

- 关闭新任务准入；
- 排空 Ready、Running、Awaiting 和 RPC pending；
- 取消或清理 Timer；
- 执行 `OnStop` 及其受控 Await；
- 关闭业务和 Transport 资源；
- 最终进入 `Stopped`。

退休不会提前执行上述步骤，也不会在任务排空后自动停服。完整停止顺序见
[Service 优雅停止设计](./2026-07-24-服务优雅停止设计.md)。

## 8. 服务发现与连接

退休不会使 Service 从发现目录消失：

- 不产生 `Lost`；
- Service 查询结果继续包含该实例及 `Retired` 状态；
- `ToServiceOnNode` 精确 RPC/Notify 仍可选择该实例；Broadcast 留待独立里程碑；
- `ToService` 自动实例选择不再把该实例作为新流量候选；
- TCP 连接需求保持不变；
- `Running <-> Retired` 产生明确状态变化通知；
- 发现和失去发现事件均携带相应 Service 的状态，Lost 携带最后已知状态。

发现事件只是状态同步信号。业务跨越 Await 后提交状态前，需要重新查询当前最新快照。

## 9. 错误处理

`CodeServiceRetired` 和 `ErrServiceRetired` 继续作为推荐的统一错误语义保留，但改由业务
显式返回。Origin Runtime 和 RPC Dispatcher 不因看到 `Retired` 自动产生该错误；M19
自动路由器只摘除候选并在没有其他 Running 实例时返回 `CodeRPCNoRoute`。

Notify 和 Broadcast 没有远端错误响应时，业务自行决定忽略、处理或记录指标；框架不因
退休静默丢弃。

## 10. 并发与调度约束

- 状态切换由 ServiceScheduler 串行化；
- 状态切换不创建第二个业务执行协程；
- RPC、Timer、事件和 Await 恢复继续共用唯一 Service 执行槽；
- 状态监听回调进入监听方 Service Runner；
- Provider、TCP、NATS 或 Timer goroutine 不直接执行业务状态回调；
- 正式 Stop 与 Resume 竞争时，`Stopping` 一旦发布便不能恢复到 `Running`。

## 11. 可观测性

至少提供：

- 当前状态和状态进入时间；
- 退休、恢复次数及退休持续时间；
- 状态发布到 Discovery Provider 的延迟；
- 远端可见状态和本地实际状态不一致的持续时间；
- 业务主动返回 `CodeServiceRetired` 的数量可以按普通 RPC 错误码统计。

框架不再提供“因退休自动拒绝 RPC”的内部计数，因为不存在该自动行为。

## 12. 测试要求

后续实现至少验证：

1. `Running -> Retired -> Running` 状态转换；
2. Retired 不会自动进入 Stopping；
3. 只有明确 Stop 信号能进入 Stopping；
4. Retired 仍能接收请求—响应 RPC、Notify 和 Broadcast；
5. Retired 仍能执行本地事件、Timer、Await 恢复和异步回调；
6. Retired 仍能发起出站操作；
7. 业务可以主动返回 `ErrServiceRetired`；
8. 退休不产生 Lost，不关闭 TCP/NATS 连接；
9. 远端监听者能观察 Running 与 Retired 状态变化；
10. Stop 与 Resume 竞争时不会从 Stopping 恢复；
11. 全程满足 Service 单执行槽约束。

## 13. 已确认结论

- `Retired` 是稳定、可观察的运行状态；
- 框架不因退休自动拒绝或丢弃任何 RPC、Notify、Broadcast；
- `ToService` 自动路由排除退休实例，`ToServiceOnNode` 精确路由仍可调用；
- 退休不自动暂停 Timer、关闭连接、排空或停止；
- 业务自行决定退休期间允许和拒绝的具体操作；
- `CodeServiceRetired` 保留给业务主动返回；
- 退休状态通过服务发现发布，且不冒充 Lost；
- 只有明确 Stop 信号启动正式关闭。
