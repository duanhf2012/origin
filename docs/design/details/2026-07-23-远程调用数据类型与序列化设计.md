# Origin 第三版远程调用数据类型与序列化设计

> 文档类型：详细设计储备

## 1. 文档范围

本文记录 Origin v3 RPC 在数据类型、序列化、传输边界和低延迟方面已经确认的设计。服务发现、服务调度模型和流式 RPC 不属于本文范围。接口签名、生成方法与调用分类见 [Origin v3 RPC 接口与调用语义设计](./2026-07-23-远程调用接口与调用语义设计.md)，`Await` 与任务恢复规则见 [Origin v3 Service 协作式调度设计](./2026-07-23-服务协作式调度设计.md)，Deadline 的统一定时机制见 [Origin v3 定时器系统设计](./2026-07-23-定时器系统设计.md)。

### 1.1 里程碑落地顺序

完整类型规则保持不变，但实现拆成两个可独立验收的小里程碑：

| 里程碑 | 实现范围 | 明确不实现 |
|---|---|---|
| M11 | 顶层 Protobuf、基础整数与浮点数、布尔值、字符串、`[]byte`、普通结构体、指针、数组、Slice、Map、嵌套 Protobuf；生成器类型识别、契约指纹、静态编解码、同 Node Dispatcher 闭环 | 自定义 Codec、TCP、NATS |
| M12 | 自定义静态 Codec 和特殊类型扩展 | TCP、NATS、RequestID、pendingCall、发现和路由 |
| M13 | 复用 M11 内置数据表示和 M12 自定义扩展接入 TCP RPC | 新增或修改业务数据编码规则 |
| M14 | 复用 M11 内置数据表示和 M12 自定义扩展接入 NATS RPC | 新增或修改业务数据编码规则 |

该拆分只改变实施顺序，不改变第 5～7 节已经确认的最终语义。M13/M14 不得在 Transport
适配器中再实现第三套 Codec，也不得先接入网络、再回头改变数据布局。

## 2. 设计目标

1. 业务开发者使用 Go 接口定义 RPC，不要求使用 `.proto` 定义 Origin Native RPC。
2. RPC 调用外观保持统一，不区分“普通 RPC”和“低延迟 RPC”。所有 RPC 底层都按低延迟目标实现。
3. RPC 入参和出参允许使用 Go 原生类型、普通 Go 结构体或 Protobuf 生成的消息类型，并允许在普通 Go 结构体和容器中组合这些类型。
4. 不使用 msgp，不为业务项目增加额外的序列化生成器。业务侧只使用 `origingen`。
5. TCP 与 NATS 使用同一套 Origin Native RPC 语义；外部 gRPC 通过可选插件提供。
6. 优先保持代码精简、清晰和可维护。性能与可维护性发生冲突时，先提供方案和基准依据，再由开发者确认取舍。

## 3. RPC 定义和调用模型

Origin Native RPC 使用 Go 接口作为契约，由 `origingen` 在编译前生成：

- 强类型客户端；
- 服务端注册代码；
- 方法描述信息；
- TCP 与 NATS 适配代码；
- 静态序列化与反序列化代码。

第一版支持：

- 一元请求与响应；
- 异步调用；
- 单向通知。

第一版不支持流式 RPC。

### 3.1 Context、Deadline 与默认超时

所有由 `origingen` 生成的 RPC 调用函数都接受 `context.Context`，并统一遵循以下规则：

1. 调用方传入的 Context 已有 Deadline 时，原样继承该 Deadline，不再附加默认超时；
2. Context 没有 Deadline 时，依次查找 `Service.SetDefaultAwaitTimeout` 和当前 Node 的
   `scheduler.default_await_timeout`；
3. 前两级均未配置时，使用 Origin 内置默认超时 `15s`；
4. 调用方可以通过显式 Deadline 设置比默认值更短或更长的超时，默认值不能反向截断显式 Deadline；
5. 优先级固定为：
   `调用方显式 Deadline > Service.SetDefaultAwaitTimeout > Node scheduler.default_await_timeout > Origin 内置 15s`；
6. RPC 不增加 `rpc.default_timeout`，并与通用 Await、Redis、数据库等等待共用这一套默认值；
7. 一次调用只使用一个有效 Context、一个有效 Deadline 和一个逻辑计时器；显式 Deadline
   继续使用调用方 Context 已有的 Go Runtime Timer，不登记 M8；
8. 没有 Deadline 的合法 Context 使用统一默认值和一条 M8 Deadline；M8 派生 Context
   必须公开计算后的 `Deadline()`，但不能创建第二个 Go Runtime Timer；
9. `context.Background()` 和 `context.TODO()` 在超时选择层属于没有 Deadline，但不能
   绕过 `Service.Await` 和生成 `AwaitXxx` 的 Origin Task Context 执行权校验。

`15s` 是防止请求无限等待的最终兜底值，不是业务目标延迟。Redis、数据库、战斗服内部 RPC 等延迟敏感路径应根据业务要求显式设置更短的 Deadline。

一次请求与响应 RPC 的超时范围从调用进入 RPC 客户端开始，覆盖本地排队、路由、传输、服务端处理、响应传输和客户端内部 Future 完成的全过程。异步 RPC 同样适用：生成的 `AsyncXxx` 立即返回，内部 Future 最迟在有效 Deadline 到达时完成为超时，并把强类型回调投递回调用方 Service。

单向通知没有远端响应，但生成的调用函数仍使用相同的有效 Context 约束本地编码、路由、
排队和发送接受过程；接受后不创建 pending 或超时项，也不等待或约束远端业务执行。

如果 RPC 在 `Await` 内执行，`Await` 传入的 Context 已包含有效 Deadline，RPC 直接继承，不重复创建另一套默认超时。RPC 本地超时后的远端取消协议属于后续 RPC 调用语义设计，不能影响客户端按时完成。

## 4. 传输边界

### 4.1 Origin Native RPC

Origin Native RPC 支持 TCP 和 NATS。单次部署选择一种 Native 传输模式，RPC 接口和业务代码不因传输方式变化。

### 4.2 外部 gRPC

gRPC 作为可选适配插件，可以与 Origin Native TCP 或 NATS 同时启用。Origin 核心不依赖 gRPC。

可暴露为标准 gRPC 的方法，其顶层请求和响应必须是 Protobuf 消息。普通 Go 结构体即使嵌套了 Protobuf 结构体，也不会自动成为标准 gRPC 契约。

## 5. 统一类型处理原则

`origingen` 根据 RPC 每个顶层入参和出参的声明类型，在生成阶段静态选择编解码路径。类型选择只发生在 RPC 参数边界，不在递归处理结构体字段或容器元素时动态切换。

顶层参数分为两类：

1. 顶层类型是 Protobuf 生成的消息类型时，使用标准 Protobuf 线协议；
2. 其他 Go 类型使用 Origin 静态编解码协议。

每个入参和出参独立判定，因此同一个 RPC 方法可以同时使用 `int64`、`string`、`*int`、普通 Go 结构体和顶层 Protobuf 消息，不要求为了统一序列化而包装成同一种请求结构。

RPC 可以声明多个输入和多个输出。每个位置独立选择编解码路径，并由生成的内部请求、响应布局写入同一个 RPC 帧。参数数量、Context、可变参数、`error` 位置和生成方法名称属于 RPC 接口与调用语义设计。

生成器通过类型是否为 Protobuf 消息静态识别第一类。Protobuf 生成类型通常以指针形式实现 `proto.Message`；如果值类型或其指针能够被静态识别为 Protobuf 消息，`origingen` 应生成对应的取址、空值检查和编解码代码，不在热路径使用反射判断。

### 5.1 顶层 Protobuf 消息

当 RPC 的某个顶层入参或出参本身是 Protobuf 消息时：

- 编码使用 `proto.Marshal` 或等价的 Protobuf 高性能 API；
- 解码使用 `proto.Unmarshal` 或等价的 Protobuf 高性能 API；
- TCP 与 NATS 中承载的是标准 Protobuf 消息字节；
- 保留 Protobuf 字段编号、unknown fields、`optional`、`oneof` 和 Opaque API 语义；
- Protobuf 消息外部仍由 Origin RPC 帧负责方法、请求序号、路由和错误等元数据，因此不能仅凭消息字节直接充当完整 gRPC 请求。

例如：

```go
type PlayerRPC interface {
    Load(ctx context.Context, req *pb.LoadRequest) (*pb.LoadResponse, error)
}
```

`req` 和返回的 `*pb.LoadResponse` 都是顶层 Protobuf 消息，使用标准 Protobuf 序列化。

### 5.2 顶层 Go 类型

顶层参数不是 Protobuf 消息时，使用 Origin 静态编解码。基础规则如下：

- 基础整数、浮点数、布尔值和字符串使用 Origin 内置二进制编码；
- `[]byte` 使用原始字节快速路径；
- 指针保留 `nil` 和零值的区别；
- 普通 Go 结构体只处理导出字段；
- 结构体中的小写非导出字段和运行时内部字段不进入线协议；
- Slice、数组和 Map 递归处理其元素、键和值；
- 不支持的类型必须由 `origingen` 在生成阶段报出完整字段路径；
- M12 起用户可以通过 Origin 自定义静态编解码接口扩展特殊类型；M11 只保留编译期扩展
  接缝，不开放自定义入口。

普通 Go 结构体不要求 Tag，也不维护字段编号。只处理导出字段并严格按声明顺序编码；字段
追加、插入、删除、重排、重命名或类型修改都会改变完整契约指纹，属于不兼容修改。需要
字段级兼容演进时使用顶层 Protobuf；普通结构体不兼容演进使用新版本 RPC 契约或协调节点
更新顺序。

Map Key 与 M11 支持的基础类型对齐，只支持 `bool`、有符号整数、无符号整数、
`float32`、`float64`、`string` 及其具名定义类型和别名。Protobuf Enum 按具名整数处理，
可以作为 Map Key。Map Key 不因为满足 Go `comparable` 约束而获得额外类型支持；
`uintptr`、`complex64`、`complex128`、`unsafe.Pointer`、指针、接口、Channel、数组和
结构体均不能作为首版 Map Key。

#### 5.2.1 M11 基础值的固定顺序布局

M11 的方法输入和输出采用 Origin 固定顺序二进制格式。MethodID 和 ContractFingerprint
已经确定参数数量、声明类型与位置，因此每条方法载荷不再重复写入字段 Tag、类型、数量
或格式版本。逻辑位置仍进入契约规范化字节，线格式版本也进入完整指纹。

固定宽度数值全部使用小端序：`bool`、`int8`、`uint8` 为一字节，16/32/64 位整数使用
对应宽度，`float32` 和 `float64` 使用 IEEE 754 的四字节和八字节表示。`int`、`uint`
统一使用八字节线值，目标架构解码时做范围检查；有符号整数使用对应宽度的二进制补码。
首版不支持 `uintptr`。

`string` 使用四字节 `uint32` 长度和连续原始字节，不额外校验 UTF-8，保持 Go string
可以承载任意字节的语义。`[]byte` 与可空的顶层 Protobuf 消息使用四字节
presence/长度，其中 `0xFFFFFFFF` 表示 nil，`0` 表示非 nil 空值，其余值表示紧随其后的
内容长度。这样既保留 nil/空语义，又能让编码器在同一 Buffer 中为 Protobuf 预留长度、
调用官方 `proto.MarshalAppend` 直接追加并回填长度，不要求生成隐藏的 Protobuf
请求/响应包装类型。

具名定义类型使用底层基础类型的线布局，但契约指纹保留完整包路径、类型名和底层类型；
Go 别名规范化为目标类型，`byte`、`rune` 分别规范化为 `uint8`、`int32`。解码必须拒绝
截断、非法 bool、长度越界、整数溢出和多余尾部数据，并在切片、分配或调用 Protobuf
解码之前校验长度及 RPC 最大消息限制。

该布局也作为普通结构体和容器递归编码的基础。普通结构体使用已确认的无 Tag 固定声明
顺序布局；完整 ContractFingerprint 在业务载荷解码前拒绝不同 Schema。需要 Protobuf
字段级演进能力时，业务应使用一个顶层 Protobuf 请求或响应；外部 gRPC 插件负责完整协议
适配，不要求与 Origin Native RPC 共用方法载荷格式。

固定顺序的顶层位置不提供自动跨签名兼容：追加、插入、删除、重排或修改任一输入/输出
类型都属于不兼容修改。MethodID 继续只标识契约和方法名，完整 ContractFingerprint 在
业务载荷解码前拒绝不一致契约。兼容演进应保持 Go RPC 签名不变，并优先在顶层 Protobuf
消息内部按其字段规则完成；不兼容需求使用新的版本化 RPC。

#### 5.2.2 `[]byte` 的业务所有权

M11 对所有业务可见的普通 `[]byte` 使用安全的独立所有权：

- 服务端输入解码时按实际长度分配并复制，不向业务暴露请求 Buffer 的子切片；
- Await 返回值和 Async 回调值在释放响应 Buffer 前复制为业务独立 Slice；
- nil 保持 nil，非 nil 空值保持非 nil 空 Slice；
- 业务可以在 RPC 方法或回调返回后继续保存、读取和修改 Slice；
- 修改业务 Slice 不会改变请求、响应或其他调用的数据；
- 普通业务 Slice 不从 BufferPool 借出，也不要求业务调用 Release。

这条规则会使每个非空 `[]byte` 解码产生一次必要的分配和复制，但避免使用外观完全相同的
普通 Slice 隐藏“只能在当前回调内使用”的生命周期约束。M11 不增加 `BorrowedBytes`、
引用计数、自动失效检查或公开 Buffer；只有代表性 Benchmark 证明该复制是显著热点时，
后续设计才可以增加名字和生命周期都明确的显式借用类型，不能改变普通 `[]byte` 的语义。

### 5.3 顶层容器的判定

Slice、数组、Map 或其他容器本身不是 Protobuf 消息，所以顶层容器使用 Origin 静态编解码。即使其元素是 Protobuf 生成类型，也按容器元素的普通 Go 结构递归处理。

普通 Slice 和 Map 使用四字节 presence/元素数量，区分 nil 与非 nil 空容器；数组长度由
静态类型确定，不在线上重复编码。Map 按 Go 当前遍历顺序写入，不排序，也不承诺相同 Map
每次得到逐字节相同 payload；解码后的 Key/Value 语义必须一致。该选择避免排序、临时 Key
Slice 和额外分配。

例如：

```go
type PlayerRPC interface {
    BatchSave(
        ctx context.Context,
        profiles map[int64]*pb.PlayerProfile,
    ) error
}
```

顶层参数是 Map，不是 Protobuf 消息，因此整个参数走 Origin 静态编解码；其中的 `*pb.PlayerProfile` 按普通 Go 结构体字段处理，不为每个元素调用 `proto.Marshal`。

## 6. Go 结构体内的 Protobuf 字段

当顶层参数是普通 Go 结构体时，整个对象图都使用 Origin 静态编解码。结构体字段中出现的 Protobuf 生成类型只被视为普通 Go 结构体，不调用 `proto.Marshal`，也不在字段中嵌入一段 Protobuf 线协议。

例如：

```go
type Request struct {
    ID         int64
    Profile    pb.PlayerProfile
    ProfilePtr *pb.PlayerProfile
    Profiles   map[int64]pb.PlayerProfile
}
```

如果 `Request` 是 RPC 顶层参数，以上字段均由 Origin 静态结构体编解码器处理：

- `Profile` 按普通 Go 结构体处理；
- `ProfilePtr` 先编码 `nil` 状态，再按普通 Go 结构体处理非空值；
- `map[int64]pb.PlayerProfile` 按普通 Map 编码，不要求改为 `map[int64]*pb.PlayerProfile`；
- 递归过程中不调用任何 Protobuf 消息编解码接口。

现代 Protobuf 生成代码中的 `state`、`sizeCache` 和 `unknownFields` 等小写内部字段不会进入 Origin 线协议。由此也带来明确边界：Protobuf 未知字段不会经过一次 Origin Native RPC 往返得到保留。

同一个 Protobuf 生成类型因此可能有两种传输表示，具体只由它在 RPC 边界的位置决定：

- 它自身是顶层 RPC 参数时，使用标准 Protobuf 线协议；
- 它位于普通 Go 结构体或容器内部时，使用 Origin 静态结构体协议。

生成器必须完全根据声明类型和位置静态确定表示，禁止根据运行时值、接口实现或实际对象类型改变线协议。

## 7. optional、oneof 与 Opaque API

这些 Protobuf 能力是否可用，取决于消息使用顶层 Protobuf 路径还是嵌套的普通 Go 结构体路径。

### 7.1 顶层 Protobuf 路径

顶层 Protobuf 消息直接使用标准 Protobuf 编解码，因此：

- 支持 `optional`；
- 支持 `oneof`；
- 支持 Open、Hybrid 和 Opaque API；
- 保留 unknown fields；
- 兼容 Protobuf 自身的字段演进规则。

顶层 Protobuf 消息不要求为了 Origin Native RPC 改成 Open 或 Hybrid API。

### 7.2 嵌套普通结构体路径

Protobuf 生成类型位于普通 Go 结构体或容器内部时，按导出字段递归处理：

- Open Struct API 中由指针表达的 `optional` 字段按普通 Go 指针处理，可以保留“未设置”和“设置为零值”的区别；
- `oneof` 通常表现为接口字段和包装类型，首版 Origin 静态结构体编码不支持该动态接口字段；
- Opaque API 隐藏逻辑字段，首版 Origin 静态结构体编码无法按普通字段读取。

因此，包含 `oneof` 或使用 Opaque API 的 Protobuf 类型可以直接作为顶层 Protobuf 参数，但首版不能嵌套在走 Origin 静态编解码的普通 Go 结构体或容器中。

如果需要嵌套使用，应选择以下一种方式：

- 将该 Protobuf 消息改为 RPC 顶层参数，使其走标准 Protobuf 编解码；
- 对嵌套消息使用 Open 或 Hybrid API，并且不使用 `oneof`；
- 为包含它的 Go 类型提供显式的 Origin 自定义静态编解码器。

`origingen` 发现不支持的嵌套 `oneof` 或 Opaque 消息时，必须在生成阶段报出从 RPC 方法、顶层参数、容器到具体字段的完整路径。例如：

```text
cannot generate Origin codec for game.SaveRequest.Profile

reason:
  pb.PlayerProfile is nested in an Origin-encoded Go struct
  the message uses Protobuf Opaque API

solutions:
  1. use pb.PlayerProfile as a top-level RPC parameter
  2. generate it with API_OPEN or API_HYBRID
  3. provide a custom Origin codec for game.SaveRequest
```

禁止把嵌套 Opaque 消息静默编码为空结构体，也禁止延迟到运行时才失败。

官方参考：

- [Protobuf Go Opaque API 迁移说明](https://protobuf.dev/reference/go/opaque-migration/)
- [Protobuf Go API level 说明](https://protobuf.dev/reference/go/go-generated-opaque/#api-level)

## 8. 低延迟约束

所有 RPC 共用以下底层要求：

- 客户端、服务端路由和编解码代码均在编译前生成；
- 普通 Go 类型热路径不使用反射、JSON 和字符串方法查找；
- 顶层 Protobuf 消息直接使用 Protobuf 生成代码和标准线协议，不重复生成一套消息字段编解码；
- 基础类型使用专用快速编码；
- 尽可能预估消息大小并向已有缓冲区追加；
- 控制内存分配和数据复制；
- 首版所有 RPC 消息均不压缩，不引入压缩库、压缩阈值和相关热路径分支；
- RPC 线协议不预留压缩标志位和算法编号，避免每个低延迟小包承担无效字段和分支；
- 后续只有在真实游戏业务基准证明压缩存在净收益时，才通过新的不兼容协议 Magic
  设计默认关闭的压缩实现、算法协商和安全上限；
- 不自动合并请求，避免批处理增加等待时间；
- 使用有界队列、超时和背压，避免负载升高时延迟无限累积；
- 未显式设置 Deadline 的 RPC 使用可配置的分级默认值，并以 Origin 内置 `15s` 作为最终兜底；
- TCP 和 NATS 分别进行基准测试，不能假定两者延迟相同。

性能验证至少记录：

- 顶层 Protobuf 和普通 Go 结构体两条路径各自的编解码耗时；
- 每次操作的内存分配次数和字节数；
- 请求排队时间；
- RPC 往返时间；
- RPC 超时数量，并区分显式 Deadline、`Service.SetDefaultAwaitTimeout`、
  `Node scheduler.default_await_timeout` 和内置 `15s` 的来源；
- P50、P95 和 P99 延迟；
- 不同消息大小下的吞吐量。

最大消息长度限制与压缩无关。TCP 与 NATS 接收端都必须在申请完整消息内存和执行反序列化之前校验最大长度，首版配置默认上限为 `4M`。

Protobuf 空消息本身的标准 Protobuf 内容可能为零字节，但只要它占据一个 M11 方法参数
位置，Origin 固定顺序方法载荷仍包含四字节 presence/长度。只有没有业务输入或没有业务
输出的方法载荷才可以为零字节。M5 TCP 继续允许零长度 payload；M13 RPC 线协议仍包含
自己的请求类型、标识和方法等协议头，RPC 解码器按协议头校验完整性，不由 TCP 层禁止
空业务消息。

## 9. 生成期失败原则

对于嵌套结构体路径中的 oneof、Opaque API、未支持的接口类型或其他无法静态编码的类型，`origingen` 必须：

1. 在生成阶段终止；
2. 输出 RPC 方法、参数、结构体和字段的完整路径；
3. 说明不支持原因；
4. 给出可执行的修改建议；
5. 不使用反射、JSON 或空对象作为隐式回退方案。

M11 已经包含普通指针、数组、Slice、Map、普通结构体和嵌套 Protobuf。`origingen`
扫描到 `uintptr`、复数、`unsafe.Pointer`、接口、函数、Channel、循环对象图、非法
Map Key、嵌套 `oneof` 或嵌套 Opaque API 时，必须在生成阶段按永久不支持错误处理，并
展示完整方法、参数、容器和字段路径。只有自定义静态 Codec 属于 M12 的阶段性能力边界。

生成器必须先验证扫描范围内全部可达类型，再渲染任何文件；任一类型失败时整次生成返回
非零状态且不写部分文件。`origingen rpc --check ./...` 必须在不修改工作树的前提下检查
类型合法性以及生成文件是否缺失、过期或多余。

## 10. 测试要求

至少覆盖：

1. 顶层 `int64`、`string`、`*int` 和普通 Go 结构体使用 Origin 静态编解码；
2. 顶层 Protobuf 消息的字节能够被标准 `proto.Unmarshal` 解析；
3. 顶层 Protobuf 消息往返后保留 unknown fields、`optional`、`oneof` 和 Opaque API 语义；
4. 同一 RPC 方法混合 Go 原生参数和 Protobuf 参数时，每个参数独立选择正确编解码路径；
5. 普通 Go 结构体中的 Protobuf 值、指针、Slice 和 Map 元素均按普通 Go 结构递归处理；
6. 顶层 `map[int64]*pb.PlayerProfile` 使用 Origin 容器协议，不对元素调用 Protobuf 消息编解码；
7. 同一个 Protobuf 类型在顶层路径和嵌套路径下分别得到已定义的两种线协议表示；
8. 嵌套 `oneof` 和 Opaque API 在生成阶段失败，并输出完整字段路径；
9. TCP 与 NATS 对同一 RPC 声明采用完全相同的参数分流和数据语义；
10. gRPC 插件复用顶层 Protobuf 请求与响应时不进行字段级二次转换；
11. 空指针、空消息、零值、空 Slice、空 Map 和 `nil` 容器的边界语义；
12. M11 每种基础类型的固定小端布局、`int`/`uint` 跨架构范围检查和非法尾部拒绝；
13. nil 与非 nil 空 `[]byte`、nil 与非 nil 空顶层 Protobuf 的不同线表示；
14. 具名定义类型、Go 别名、`byte` 和 `rune` 的规范化与契约指纹；
15. 请求或响应 Buffer 释放并复用后，业务保存的输入、Await 返回和 Async 回调
    `[]byte` 仍保持独立且内容不变；
16. 两条编解码路径的耗时、内存分配、消息大小和并发压力基准。

## 11. 本设计的取舍

本设计在 RPC 顶层参数边界静态选择两条路径：

- 顶层 Protobuf 消息使用标准 Protobuf 序列化，保留 unknown fields、`optional`、`oneof` 和 Opaque API，并可以复用到外部 gRPC 适配；
- Go 原生类型、普通 Go 结构体和容器使用 Origin 静态编解码，允许自由组合 Go 类型。

普通 Go 结构体或容器内部的 Protobuf 生成类型继续按普通 Go 结构递归处理，不切换成嵌套 Protobuf 字节。这样避免在一个对象图中混合两套字段编号、长度和空值规则，也避免为 Map、Slice 和指针增加 Protobuf 特殊分支。

代价是同一个 Protobuf 类型作为顶层消息和作为 Go 结构体字段时具有不同线协议表示；包含 `oneof` 或使用 Opaque API 的消息首版不能走嵌套结构体路径。该差异必须由 `origingen` 静态确定、在生成文档中展示，并通过兼容性测试锁定。

标准 Protobuf 消息字节只解决数据载荷的跨语言表示。完整跨语言 RPC 仍由显式的 gRPC 适配插件提供，因为 Origin Native TCP/NATS 还包含自己的帧、路由、服务发现和调用语义。

## 12. M11 普通 Go 类型实现结论

1. 普通结构体只按导出字段声明顺序编码，不使用 Tag 或稳定字段 ID；
2. Map 不排序，不保证 payload 字节确定性，只保证数据往返语义；
3. 循环和自引用类型在生成阶段拒绝；
4. 单个 Slice 或 Map 最多 `1048576` 个元素，静态类型图最多嵌套 64 层；
5. 所有长度、数量和容量计算先校验剩余 payload、最大消息长度和整数溢出，再执行分配；
6. 显式 `struct{}` 支持零字节编码；没有可序列化导出字段的具名结构体生成期失败；
7. 普通结构体路径下的 Protobuf Open/Hybrid 使用导出字段，`oneof` 和 Opaque API
   生成期失败；
8. Schema、Codec 稳定标识和格式版本共同进入完整契约指纹；
9. M11 不开放运行时自定义 Codec。生成器内部保留大小计算、编码、解码和 Codec 标识的
   静态计划；M12 自定义 Codec 由生成器选择并产生直接函数调用，不在 RPC 热路径查表。

这些规则由 M11 固定，TCP/NATS Transport 不得修改。M12 只扩展特殊类型的静态 Codec，
不得改变 M11 内置类型的线格式。
